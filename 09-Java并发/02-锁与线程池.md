# 锁与线程池

## 504. `synchronized` 是什么？

**面试回答**

`synchronized` 是 Java 的内置监视器同步机制，对同一监视器提供可重入互斥；释放监视器 happens-before 后续对同一监视器的获取，因此它同时建立临界区的可见性与顺序保证。

**原理与理解**

每个对象都关联监视器。线程进入 synchronized 前获取它，正常返回或异常退出都会自动释放；同一线程可重复获取，重入次数需成对释放。

**成立条件与边界**

它只保护所有访问都遵守同一锁协议的共享状态；锁错对象、部分路径未加锁或把可变对象逸出都可能失效。现代 JVM 会优化锁，不能固定称为“重量级”。

**实际场景（通用工程）**

对余额的“检查 + 扣减”应在同一把锁保护的临界区完成；仅给扣减语句加锁而把检查放在外面仍有竞态。

**常见追问**

- synchronized 能保证什么？——同锁互斥，并建立 unlock 到后续 lock 的 happens-before。
- 异常退出会释放锁吗？——会自动执行解锁。

**易错点**

互斥的是同一个监视器，不是“代码长得一样”就会互斥。

## 505. `synchronized` 可以锁什么？

**面试回答**

同步代码块锁表达式计算出的对象；实例 synchronized 方法锁调用对象 `this`；static synchronized 方法锁声明该方法的 Class 对象。

**原理与理解**

不同实例的实例同步方法使用不同监视器，可以并行；静态同步与对 `SomeClass.class` 的同步争同一监视器。类锁和某个实例锁也不是同一把锁。

**成立条件与边界**

锁对象应稳定、私有且不被外部代码共享或替换；不要锁字符串常量、装箱缓存对象或可重新赋值引用。锁住集合不代表绕过该锁的访问安全。

**实际场景（通用工程）**

用 `private final Object lock = new Object()` 保护一个明确不变量，比公开的 `synchronized(this)` 更不易被外部代码意外竞争。

**常见追问**

- 两个实例同步方法互斥吗？——只有调用同一实例时互斥。
- static 与实例同步互斥吗？——默认不互斥，锁对象不同。

**易错点**

“锁方法”只是语法表象，真正锁的是对象监视器。

## 506. `volatile` 是什么？

**面试回答**

`volatile` 修饰字段，使读写成为 JMM 同步动作：对该变量的写 synchronizes-with 后续对它的读，从而为写前动作与读后动作建立 happens-before；它还保证该字段单次读写具有 volatile 内存语义。

**原理与理解**

实现可借助编译器屏障和硬件内存序，但 JMM 不要求“每次直接访问物理主内存”。volatile 常用于发布不可变状态、状态标志和单写者协议。

**成立条件与边界**

volatile 不把复合读改写变成一个原子动作，见 [[09-Java并发/02-锁与线程池#507. `volatile` 能保证原子性吗？]]。它只约束围绕该变量的合法重排，不是禁止所有指令重排，也不保证线程立刻获得 CPU。

**实际场景（通用工程）**

一个线程先写入配置对象，再写 `volatile ready = true`；另一线程读到 ready 为 true 后，可看到发布前的配置写入，前提是对象后续不被无序修改。

**常见追问**

- volatile 写读如何传递可见性？——通过 synchronizes-with 与 happens-before。
- 能代替锁吗？——只有不需要复合不变量和互斥时才可能。

**易错点**

“volatile 变量总从主内存读取、修改后立刻被所有线程看到”不是 JMM 的规范表述。

## 507. `volatile` 能保证原子性吗？

**面试回答**

volatile 能保证该字段一次读或写的原子访问语义，但不能让 `count++`、“检查后更新”等多步操作整体原子；这些需要锁、原子类或更高层并发工具。

**原理与理解**

两个线程可能都读到相同 count，各自计算加一后依次写回，最终丢失一次更新。volatile 解决可见性与排序，不能阻止两条执行流在读和写之间交错。

**成立条件与边界**

简单赋值是否足够还取决于业务不变量；多个 volatile 字段分别可见，也不意味着它们的组合快照原子。单写多读的替换式发布通常可用 volatile。

**实际场景（通用工程）**

停止标志可用 volatile；并发请求计数使用 AtomicLong/LongAdder 或锁，并根据是否需要精确即时值选择。

**常见追问**

- `volatile long` 的读写是否原子？——volatile long/double 读写必须原子，但复合运算仍不原子。
- 原子类为什么可自增？——使用原子 read-modify-write 操作，而非普通 ++。

**易错点**

“不保证原子性”针对复合操作，不能反过来说 volatile 的单次读写会被任意撕裂。

## 508. `synchronized` 和 `volatile` 有什么区别？

**面试回答**

synchronized 通过同一监视器的互斥把一段复合操作串行化，并建立可见性；volatile 不互斥，只对一个字段提供 volatile 读写与 happens-before，适合状态发布而非跨变量不变量。

**原理与理解**

锁竞争时线程可能阻塞；volatile 访问通常不会因该字段本身阻塞，但高频写仍可能有缓存一致性成本。两者都属于 JMM 同步机制。

**成立条件与边界**

不能固定说 synchronized “很重”或 volatile “几乎无开销”。如果逻辑是 `if (state == A) state = B`，即使 state 是 volatile 也需要 CAS 或锁保证条件更新原子。

**实际场景（通用工程）**

生命周期停止信号可用 volatile；库存“读取、校验、扣减”需要数据库原子语句、锁或其他完整并发控制。

**常见追问**

- 哪个提供互斥？——synchronized。
- 两者能一起用吗？——可以，但应先明确每个机制负责的不变量与发布关系。

**易错点**

选择标准不是“谁更快”，而是是否需要互斥、复合原子性与条件等待。

## 509. 什么是死锁？

**面试回答**

死锁是多个线程形成资源等待环，每个线程都等待只有环中其他线程才能释放的资源，因而整体无法继续推进。Java 不要求自动检测或恢复监视器死锁。

**原理与理解**

典型情形是线程 A 持 L1 等 L2，线程 B 持 L2 等 L1。死锁不同于长时间锁竞争、活锁和饥饿，诊断时要看等待关系而非只看“线程卡住”。

**成立条件与边界**

带超时或可中断获取可能让线程退出等待，因此未必永久。数据库、连接池与线程池之间也能形成资源死锁，不只发生在 synchronized。

**实际场景（通用工程）**

使用 `jcmd Thread.print`、`jstack` 或 ThreadMXBean 获取线程 dump，确认锁拥有者和等待环，再修正锁顺序或资源协议。

**常见追问**

- 如何避免？——全局锁顺序、缩小持锁范围、避免持锁调用外部服务、使用超时并处理失败。
- 死锁与活锁？——死锁不动，活锁线程持续动作但业务无进展。

**易错点**

CPU 低且线程 BLOCKED 不必然是死锁，可能只是热点锁竞争。

## 510. 死锁产生的四个必要条件是什么？

**面试回答**

经典 Coffman 条件是互斥、持有并等待、不可剥夺、循环等待；在该资源模型中四者同时成立才可能形成死锁，破坏任一条件可用于预防。

**原理与理解**

统一锁顺序破坏循环等待；一次获取全部资源可减少持有并等待；tryLock 超时允许主动放弃，弱化不可剥夺/无限等待。

**成立条件与边界**

这是分析可重用互斥资源的经典模型，不是证明任意分布式停滞的万能公式。减少持锁时间能降低概率，但并不必然破坏四个条件。

**实际场景（通用工程）**

按账户 ID 从小到大获取转账双方锁，所有路径遵循同一顺序，避免 A→B 与 B→A 形成环。

**常见追问**

- 最常用破坏哪个？——通常是固定资源获取顺序来破坏循环等待。
- tryLock 失败后怎么办？——释放已持资源、退避或返回失败，不能继续占锁空等。

**易错点**

“破坏任意条件即可”说的是设计协议，不是死锁发生后随意释放 Java 内置锁。

## 511. 什么是线程池？

**面试回答**

线程池把任务提交与线程生命周期分离：Executor 接收任务，由受控数量的工作线程执行，并通过队列、线程工厂、拒绝策略、关闭与监控形成完整资源管理机制。

**原理与理解**

ThreadPoolExecutor 默认按需创建核心工作线程，而不是构造时就预建全部线程；可调用 prestart 方法提前启动。工作线程循环从队列取任务，执行后继续复用。

**成立条件与边界**

线程池不自动让任务更快，也不是所有并发模型都复用线程。虚拟线程执行器通常每任务创建虚拟线程；它仍需要限制数据库连接、外部 API 等稀缺资源。

**实际场景（通用工程）**

异步任务使用命名线程工厂、有界队列、明确拒绝语义，并在应用关闭时 shutdown、等待终止和记录未完成任务。

**常见追问**

- 核心参数？——见 [[09-Java并发/02-锁与线程池#514. ThreadPoolExecutor 有哪些核心参数？]]。
- execute 与 submit？——submit 返回 Future，异常可能被 Future 捕获；execute 的未捕获异常走线程处理链路。

**易错点**

线程池不是“预先创建固定一批线程”的唯一形态，也不能忽略生命周期关闭。

## 512. 为什么要使用线程池？

**面试回答**

平台线程池用于复用线程、控制并发和排队、统一异常与生命周期管理，并把过载显式转化为排队、反压或拒绝，保护 CPU、内存和下游资源。

**原理与理解**

创建平台线程涉及栈与操作系统资源；无界创建会放大上下文切换和内存占用。池把并发量设为容量边界，并提供队列与统计指标。

**成立条件与边界**

队列不是天然限流：无界队列可能把过载变成高延迟和 OOM。线程池大小公式只能作为起点，需结合服务时间、等待比例、CPU、连接池和 SLO 压测。

**实际场景（通用工程）**

异步写日志若允许丢弃，要显式定义采样/降级；订单等关键任务若拒绝，则需让调用方感知并重试或持久化，不能静默丢失。

**常见追问**

- 线程池如何保护系统？——限制同时执行与等待任务数量，并在饱和时采取明确策略。
- 为什么不能直接 newCachedThreadPool？——线程上限近似无界，突发负载可能耗尽资源。

**易错点**

线程池的核心价值不只是线程复用，更是容量治理和过载语义。

## 513. 线程池相比频繁创建线程有什么优势？

**面试回答**

对平台线程而言，线程池减少创建销毁成本、降低线程数量波动、改善任务启动延迟，并集中提供命名、监控、取消、关闭和拒绝控制。

**原理与理解**

线程复用保持一组 worker，任务通过队列交付。统一 ThreadFactory 可设置名称、优先级和 UncaughtExceptionHandler，钩子与指标可观察活跃数、队列和完成数。

**成立条件与边界**

若任务长时间阻塞而池过小会饥饿；池过大又会竞争资源。虚拟线程降低了“频繁创建线程”的成本，通常不应再把大量独立阻塞任务塞进小型虚拟线程池。

**实际场景（通用工程）**

CPU 密集任务用接近可用处理器数的受控并行度起步；阻塞任务结合连接池容量与压测调整，而非只套 `CPU × 2`。

**常见追问**

- 响应一定更快吗？——线程已就绪可降低启动成本，但排队过长反而增加延迟。
- 如何观察？——队列长度、活跃线程、拒绝数、任务等待/执行时长和下游饱和度。

**易错点**

“用了线程池就高性能”错误，错误容量与队列配置同样会拖垮服务。

## 514. ThreadPoolExecutor 有哪些核心参数？

**面试回答**

常用构造器有七个核心参数：`corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`unit`、`workQueue`、`threadFactory`、`handler`，共同决定线程、队列与过载行为。

**原理与理解**

提交任务时：运行线程少于 core，优先新建 worker；否则尝试入队；队列拒绝后再尝试扩到 maximum；仍无法接收或线程池已关闭则拒绝。

**成立条件与边界**

该流程会受运行状态、竞态重检、队列类型和预启动配置影响。使用无界队列时，任务通常不会因队列满而扩到 maximum，使最大线程数几乎不起作用。

**实际场景（通用工程）**

配置前先给出任务执行时长、峰值提交速率、允许排队时间、内存预算和拒绝后的业务动作，再确定七个参数。

**常见追问**

- 为什么先排队再扩到最大线程？——ThreadPoolExecutor 的默认 execute 决策如此，队列策略因此非常关键。
- 核心线程会立刻创建吗？——默认按需，除非 prestart。

**易错点**

只背七个名称而说不清 `core → queue → max → reject` 的交互，无法指导实际配置。

## 515. corePoolSize 是什么？

**面试回答**

`corePoolSize` 是线程池优先维持的核心工作线程目标：提交任务且 worker 少于 core 时，即使有空闲 worker，execute 也会尝试创建新 worker，直到达到 core。

**原理与理解**

默认核心线程也按需创建，并在空闲时不超时；调用 `allowCoreThreadTimeOut(true)` 后，只要 keepAliveTime 大于 0，核心线程也可回收。

**成立条件与边界**

core 可在运行时调整，不等于固定并发度；任务还会受队列、锁、下游连接和 CPU 限制。线程工厂创建失败时也可能达不到目标。

**实际场景（通用工程）**

核心数设置为稳定负载的起点，结合活跃率和排队时长观测调整，不把它当“每秒可处理请求数”。

**常见追问**

- 构造后就有 core 个线程吗？——默认没有，按需或显式 prestart。
- 核心线程永不回收吗？——默认空闲不超时，可配置允许超时。

**易错点**

corePoolSize 不是“永远存在的线程数量”，而是线程池创建和保留 worker 的策略参数。

## 516. maximumPoolSize 是什么？

**面试回答**

`maximumPoolSize` 是 ThreadPoolExecutor 可同时存在的 worker 上限；当 worker 已达 core 且队列无法接收任务时，线程池才尝试扩容到该上限。

**原理与理解**

有界队列与较大 maximum 可吸收短时突发；SynchronousQueue 不存任务，常直接促使扩容。超过 maximum 或创建失败则进入拒绝逻辑。

**成立条件与边界**

无界队列通常永不“满”，因此 maximum 大多不起作用。最大线程数也不是系统安全并发上限，数据库连接池、CPU 和内存可能更早饱和。

**实际场景（通用工程）**

若数据库连接池只有 20 个连接，把执行数据库任务的最大线程设为 200 可能只制造 180 个等待者和更高延迟。

**常见追问**

- 何时创建非核心 worker？——队列不能接收新任务且 worker 未达 maximum。
- maximum 越大越好吗？——不是，会增加竞争、内存和上下文切换。

**易错点**

忽略队列类型单独讨论 maximumPoolSize 没有意义。

## 517. workQueue 是什么？

**面试回答**

`workQueue` 是保存已提交但尚未由 worker 开始执行的 Runnable 任务队列，类型和容量决定排队顺序、扩容触发与过载特性。

**原理与理解**

ArrayBlockingQueue 有界；LinkedBlockingQueue 可有界或默认近似无界；SynchronousQueue 容量为零，只做直接移交。PriorityBlockingQueue 按优先级取任务，但默认也无界。

**成立条件与边界**

队列容量必须按每个任务对象占用、峰值等待时间和内存预算设置。`submit` 提交的 Callable 会包装成 FutureTask 入队；任务取消也不保证立即从所有队列实现中移除。

**实际场景（通用工程）**

若允许最多等待 2 秒，可由峰值到达率与处理能力估算初始容量，再用压测校准，而不是随意设 10000。

**常见追问**

- 有界队列有什么价值？——把过载显式暴露为扩容或拒绝。
- SynchronousQueue 存任务吗？——不存，只在生产者与消费者间直接交接。

**易错点**

无界队列没有消除过载，只是把拒绝推迟成延迟增长或内存耗尽。

## 518. 拒绝策略是什么？

**面试回答**

拒绝策略是在 Executor 无法接受新任务时调用的处理器；不仅线程与有界队列饱和会触发，线程池已经 shutdown 后提交任务也会被拒绝。

**原理与理解**

`RejectedExecutionHandler.rejectedExecution` 决定抛异常、调用者执行、丢弃或自定义持久化/降级。它是容量边界的一部分，必须与业务可靠性共同设计。

**成立条件与边界**

拒绝发生时任务尚未被线程池接受，不等于任务一定从未在其他系统执行；上游重试要考虑幂等。自定义策略不得无限阻塞或递归提交导致更大故障。

**实际场景（通用工程）**

关键通知任务被拒绝时记录指标并持久化到可靠队列；可丢统计任务则显式采样，并让监控看到丢弃量。

**常见追问**

- 何时拒绝？——执行器关闭，或在当前状态下 worker 与队列均不能接收。
- 为什么不能静默丢关键任务？——调用方会误以为提交成功，造成业务数据缺口。

**易错点**

“队列满就必然拒绝”不完整，线程池可能先继续扩到 maximum。

## 519. 常见拒绝策略有哪些？

**面试回答**

ThreadPoolExecutor 内置 AbortPolicy、CallerRunsPolicy、DiscardPolicy、DiscardOldestPolicy：分别抛 RejectedExecutionException、由调用线程执行、静默丢新任务、丢队首任务后重试提交。

**原理与理解**

CallerRunsPolicy 仅在线程池未 shutdown 时调用任务的 run，可形成同步反压；若已关闭则丢弃。DiscardOldest 会移除队首，随后再次 execute，不适合任务有严格优先级或不可丢失的场景。

**成立条件与边界**

CallerRuns 可能把慢任务带入 HTTP/事件线程并放大延迟；两个 Discard 策略没有业务补偿。Abort 让调用方感知，但必须处理异常。

**实际场景（通用工程）**

面向用户请求的异步任务若采用 CallerRuns，要评估调用线程被占用的延迟；关键任务更适合明确失败并进入持久化重试。

**常见追问**

- 默认策略？——AbortPolicy。
- CallerRuns 一定不丢任务吗？——执行器已关闭时不会运行，而且进程崩溃等外部故障仍可能丢。

**易错点**

DiscardOldest 丢的是队列头，不保证就是“最不重要”或最早提交的业务任务。

## 520. Tomcat 为什么使用线程池处理请求？

**面试回答**

Tomcat Connector 使用内部或共享 Executor 执行请求处理，以复用/管理平台线程或选择虚拟线程执行器，并通过 `maxThreads`、`maxConnections`、`acceptCount` 等边界协调执行与连接过载。

**原理与理解**

Connector 接收网络连接并把可执行请求交给容器线程。使用共享 Executor 时，Connector 自身部分线程属性会被 Executor 配置取代；Tomcat 11 还提供 StandardVirtualThreadExecutor。

**成立条件与边界**

“一个 HTTP 请求从连接到完成始终占一个线程”不总成立，Servlet 异步、非阻塞 I/O 和 HTTP/2 会改变关系。线程上限也不等于连接上限，队列与操作系统 backlog 需一起看。

**实际场景（项目核验项）**

简历确认使用 Spring Boot，但未确认嵌入式 Tomcat 版本、线程参数或是否启用虚拟线程；面试前从依赖与配置核验，不扩写调优经历。

**常见追问**

- maxThreads 与 maxConnections？——一个约束同时处理请求的执行线程，一个约束服务器接受并处理的连接量，语义不同。
- 为什么 ThreadLocal 要清理？——平台工作线程复用会让线程关联值跨请求残留；此前笔记已有完整边界。

**易错点**

Tomcat 的过载控制不是只有一个“最大线程数”参数。

## 521. ConcurrentHashMap 和 HashMap 有什么区别？

**面试回答**

HashMap 不提供并发访问保证；ConcurrentHashMap 支持并发读取和更新，并为单键操作提供明确的原子与 happens-before 语义，同时不允许 null 键或 null 值。

**原理与理解**

ConcurrentHashMap 的读取通常不阻塞，更新可并发进行；某键的非 null 更新结果 happens-before 后续读取到该结果。迭代器弱一致，不抛 ConcurrentModificationException。

**成立条件与边界**

线程安全不代表一组多步操作原子，应使用 putIfAbsent、compute、merge 等复合 API。size、forEach、reduce 等聚合在并发更新时反映瞬时状态，适合监控估计而非事务控制。

**实际场景（通用工程）**

本地注册表用 `computeIfAbsent` 原子初始化每键对象；若缓存需容量、过期和加载合并，应选择专业缓存而非只用 ConcurrentHashMap。

**常见追问**

- 为什么不允许 null？——并发 get 返回 null 需无歧义地表示当前不存在映射。
- 遍历时能修改吗？——可以并发修改，迭代器弱一致但不是固定快照。

**易错点**

不能把“不会抛 ConcurrentModificationException”理解为遍历看到精确一致数据。

## 522. Java 8 ConcurrentHashMap 大致如何保证线程安全？

**面试回答**

以 OpenJDK 8 实现为例，它使用 volatile 可见字段、CAS 初始化/占用空桶、synchronized 保护部分桶更新，并用 TreeBin、ForwardingNode 与协作扩容处理树化和迁移；不是单一的“CAS + 锁桶头”口诀。

**原理与理解**

读路径依据 volatile 发布读取节点；put 遇空桶可 CAS 安装首节点，非空普通桶会在校验桶头后同步更新，树桶和扩容节点走专门协议。计数使用分散更新降低热点。

**成立条件与边界**

这些是具体 JDK 实现细节，公共契约应以 ConcurrentMap API 为准；不同版本可变化。synchronized 的对象和桶结构也会在扩容、树化时改变，不能拿内部节点作为外部锁。

**实际场景（通用工程）**

面试先回答单键 API 契约与复合方法，再概述 JDK 8 实现；真实项目不应依赖桶数量、锁对象或 resize 内部细节。

**常见追问**

- JDK 8 还使用 Segment 吗？——实现不再用 JDK 7 的 Segment 分段结构。
- 读完全没有同步吗？——通常不加互斥锁，但依赖 volatile/CAS 建立的内存语义。

**易错点**

“锁粒度永远是桶头节点、所有读绝对无同步成本”都过度绝对。
