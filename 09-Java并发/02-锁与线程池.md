# 锁与线程池

## 504. `synchronized` 是什么？

**面试回答**

synchronized 是 Java 的关键字，用于实现线程同步：给代码块或方法加锁，保证同一时刻只有一个线程能执行被锁的代码，从而保证线程安全。

**理解**

synchronized 通过「对象锁」（监视器锁 monitor）实现互斥：进入 synchronized 代码块/方法前要先获得锁，同一把锁同时只能被一个线程持有，其他线程要等。它解决「共享可变数据」的并发访问问题，是 Java 最基本的同步手段。

**场景**

项目里对共享的计数器、共享集合等临界资源，用 synchronized 保护，防止并发出错。

**常见追问**

- synchronized 锁的是什么？（对象，监视器锁）
- 它保证什么？（互斥，同一时刻一个线程执行）

**易错点**

synchronized 是「互斥锁」，保证「同时一个线程进临界区」；但锁的对象要正确，否则达不到同步效果。

## 505. `synchronized` 可以锁什么？

**面试回答**

可以锁：①对象（同步代码块 `synchronized(obj)`）；②实例方法（锁的是 this）；③静态方法（锁的是类的 Class 对象）。

**理解**

synchronized 本质是「锁对象」：同步代码块显式指定锁对象；实例方法锁的是当前对象 this；静态方法锁的是类的 Class 对象。多个线程争同一把锁才互斥，锁不同对象互不影响。所以「锁谁」很关键，锁错了达不到同步。

**场景**

项目里对共享资源，用 `synchronized(this)` 或锁同一个对象来保证互斥；静态方法加锁则锁整个类的 Class 对象。

**常见追问**

- 实例方法锁什么？（this 当前对象）
- 静态方法锁什么？（类的 Class 对象）

**易错点**

三种情况锁的对象不同（对象/this/Class），核心是「同一把锁才互斥」；锁的对象选错会失效。

## 506. `volatile` 是什么？

**面试回答**

volatile 是 Java 关键字，用于修饰变量，保证变量的「可见性」和「有序性」：一个线程修改了 volatile 变量，其他线程能立刻看到最新值，且禁止指令重排。

**理解**

volatile 解决「可见性」问题——普通变量可能被线程缓存到工作内存，别的线程改了看不到；volatile 变量每次读写都直接操作主内存，保证可见。它还通过内存屏障禁止指令重排。但它「不保证原子性」。

**场景**

项目里用 volatile 修饰「状态标志位」（如 boolean running），让一个线程停止、其他线程立刻看到。

**常见追问**

- volatile 保证什么？（可见性、有序性）
- 保证原子性吗？（不保证，见 [[09-Java并发/02-锁与线程池#507. `volatile` 能保证原子性吗？]]）

**易错点**

volatile 保证「可见性 + 有序性」，但「不保证原子性」；别把它当锁用。

## 507. `volatile` 能保证原子性吗？

**面试回答**

不能。volatile 只保证可见性和有序性，不保证原子性；像 `count++` 这种「读-改-写」复合操作，volatile 无法保证多个线程同时执行时结果正确。

**理解**

`count++` 是三步（读、加、写），volatile 只保证「读到的值是最新的」，但两个线程仍可能同时读到同一个旧值、各自加一、写回，丢失一次更新。要保证原子性需要 synchronized、Lock 或 AtomicInteger（CAS）。

**场景**

项目里自增计数不能用 volatile 保证正确，要用 AtomicInteger 或加锁；volatile 只适合简单的标志位。

**常见追问**

- 为什么 volatile 不能保证 count++ 原子？（count++ 是读改写三步，volatile 只保证可见性）
- 要原子性用什么？（synchronized、Lock、原子类）

**易错点**

「volatile 保证原子性」是常见错误；它只保证可见性，复合操作的原子性要靠锁或 CAS。

## 508. `synchronized` 和 `volatile` 有什么区别？

**面试回答**

synchronized 保证「原子性、可见性、有序性」，是重量级互斥锁，会阻塞线程；volatile 只保证「可见性和有序性」，不保证原子性，是轻量的，不阻塞。

**理解**

synchronized 通过加锁实现「互斥 + 可见性」，能保证复合操作原子性，但会阻塞、开销大；volatile 只能保证「读写主内存的可见性」和「禁止重排」，不能保证原子性，但不阻塞、开销小。适用场景不同：volatile 适合标志位，synchronized 适合需要原子性的临界区。

**场景**

项目里简单状态标志用 volatile；需要保证原子操作（如自增、复合读写）用 synchronized 或原子类。

**常见追问**

- 谁保证原子性？（synchronized，volatile 不保证）
- 谁开销小？（volatile）

**易错点**

核心区别是「是否保证原子性」和「是否阻塞」；synchronized 全保证但重，volatile 轻但只保证可见性/有序性。

## 509. 什么是死锁？

**面试回答**

死锁是多个线程互相持有对方需要的锁，又都在等待对方释放，形成循环等待，导致所有相关线程都无法继续执行、永久卡死。

**理解**

比如线程 A 持锁 1 等锁 2，线程 B 持锁 2 等锁 1，两者互相等，谁也不能前进。死锁一旦发生，线程永久阻塞。要避免，就要打破「循环等待」等死锁条件（如统一加锁顺序）。

**场景**

项目里多线程以不同顺序获取多个锁时可能死锁；统一加锁顺序、避免嵌套锁可预防。

**常见追问**

- 死锁的本质？（循环等待资源）
- 怎么避免？（统一加锁顺序、避免嵌套锁、加锁超时）

**易错点**

死锁是「循环等待」导致的永久卡死；预防核心是「打破循环等待」（统一锁顺序）。

## 510. 死锁产生的四个必要条件是什么？

**面试回答**

四个条件：①互斥（资源不能共享）；②持有并等待（持有资源同时等待别的资源）；③不可剥夺（资源不能被强行抢占）；④循环等待（形成资源等待环）。四个同时满足才死锁，破坏任意一个即可预防。

**理解**

互斥：锁只能被一个线程持有；持有并等待：占着一个又等另一个；不可剥夺：别人不能抢走你持有的锁；循环等待：A 等 B、B 等 A 形成环。预防死锁就是破坏其中之一，最常用的是「破坏循环等待」（统一加锁顺序）。

**场景**

项目里避免死锁主要靠「统一加锁顺序」破坏循环等待，或减少锁的持有时间。

**常见追问**

- 四个条件？（互斥、持有并等待、不可剥夺、循环等待）
- 破坏哪个最常用？（循环等待，统一加锁顺序）

**易错点**

四个条件要能说全，且知道「破坏任意一个即可防死锁」；最实用的是破坏「循环等待」。

## 511. 什么是线程池？

**面试回答**

线程池是预先创建一批线程、统一管理复用这些线程的机制：任务提交给线程池，由池里的空闲线程执行，执行完线程不销毁、继续处理下一个任务。

**理解**

线程池把「线程」当作资源池化管理：不用每个任务都 new 线程、用完销毁，而是复用固定数量的线程。它通过 corePoolSize、maximumPoolSize、workQueue 等参数控制线程数量和任务排队，避免频繁创建销毁线程的开销。

**场景**

项目里用线程池（或 Tomcat 自带的线程池）处理并发请求、执行异步任务。

**常见追问**

- 线程池解决什么？（线程复用，避免频繁创建销毁）
- 核心参数？（见 [[09-Java并发/02-锁与线程池#514. ThreadPoolExecutor 有哪些核心参数？]]）

**易错点**

线程池核心是「复用线程」，用「任务排队 + 线程复用」取代「一任务一线程」，降低成本。

## 512. 为什么要使用线程池？

**面试回答**

为了复用线程、避免频繁创建销毁线程的开销，同时能控制并发线程数量、统一管理线程，防止线程无限创建导致资源耗尽。

**理解**

频繁 new 线程很贵（创建、销毁、上下文切换开销），且不控制数量会创建过多线程拖垮系统。线程池复用固定数量的线程，任务排队处理，既省开销又能「限流」——控制最大并发数，保护系统资源。

**场景**

项目里用线程池处理异步任务和并发请求，既高效又不会让线程数失控。

**常见追问**

- 频繁创建线程有什么问题？（开销大、数量失控）
- 线程池的两个好处？（复用 + 限流/管理）

**易错点**

线程池的价值是「复用（省开销）+ 控制（限流）」，两者都要答到，不只是「快」。

## 513. 线程池相比频繁创建线程有什么优势？

**面试回答**

①降低资源开销（复用线程，避免反复创建销毁）；②提高响应速度（线程已存在，任务来了直接用）；③便于统一管理和限流（控制线程数量、任务队列、拒绝策略）。

**理解**

频繁创建线程：每个任务都经历「创建 → 执行 → 销毁」，开销大、响应慢，且线程数不可控。线程池预先建好线程复用，任务直接交给空闲线程，快且省；还能通过参数限制最大线程数，防止资源耗尽，并统一管理（监控、拒绝策略）。

**场景**

项目里用线程池后，异步任务不必每次开新线程，既快又稳定，还能控制并发上限。

**常见追问**

- 三个优势？（省开销、快响应、便管理）
- 怎么「限流」？（maximumPoolSize 限制最大线程数）

**易错点**

优势是「复用省开销 + 快 + 可控」，重点在「复用」和「可控」，不是简单「更快」。

## 514. ThreadPoolExecutor 有哪些核心参数？

**面试回答**

七个核心参数：corePoolSize（核心线程数）、maximumPoolSize（最大线程数）、keepAliveTime（空闲线程存活时间）、unit（时间单位）、workQueue（任务队列）、threadFactory（线程工厂）、handler（拒绝策略）。

**理解**

这七个参数决定了线程池的行为：核心线程数、最多线程数、非核心线程空闲多久回收、任务队列类型、线程怎么创建、队列满了怎么拒绝。理解它们就能合理配置线程池。

**场景**

项目里创建线程池时要根据任务类型（CPU 密集/IO 密集）配置这些参数，避免配错导致性能问题。

**常见追问**

- 七个参数分别？（corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler）
- 队列满了怎么办？（触发拒绝策略）

**易错点**

七个参数要能说全；核心是「核心线程、最大线程、队列、拒绝策略」之间的协作关系。

## 515. corePoolSize 是什么？

**面试回答**

corePoolSize 是核心线程数，即线程池中「常驻」的线程数量，即使这些线程空闲也不会被回收（除非设置了 allowCoreThreadTimeOut）。

**理解**

线程池创建后，会按需创建线程，最多到 corePoolSize 个核心线程。这些核心线程是「保底」的：任务来了优先用它们，空闲时也保留着不销毁（默认），随时能接任务。核心线程数要根据业务并发量合理设置。

**场景**

项目里配置核心线程数为常驻并发处理能力，保证有稳定数量的线程随时可用。

**常见追问**

- 核心线程会被回收吗？（默认不会，除非 allowCoreThreadTimeOut）
- 核心线程数怎么定？（看并发量和任务类型）

**易错点**

corePoolSize 是「常驻核心线程」，空闲也不回收（默认）；它决定「常态并发能力」。

## 516. maximumPoolSize 是什么？

**面试回答**

maximumPoolSize 是最大线程数，即线程池允许创建的最大线程数量上限，当核心线程忙不过来、队列也满了时，会创建额外线程，但总数不超过这个值。

**理解**

线程池的线程数不会无限增长，maximumPoolSize 是上限。当任务数超过核心线程处理能力、且队列也满了，线程池才会创建超过 corePoolSize 的「非核心线程」来救急，但最多到 maximumPoolSize。它用于「限流」，防止线程无限创建。

**场景**

项目里设置 maximumPoolSize 作为并发上限，保护系统不被过多线程拖垮。

**常见追问**

- 什么时候创建非核心线程？（核心线程满 + 队列满）
- 它起什么作用？（限流，上限）

**易错点**

maximumPoolSize 是「线程数上限」，只有「核心线程满 + 队列满」时才会扩到它；它用于限流。

## 517. workQueue 是什么？

**面试回答**

workQueue 是任务队列，用于存放「提交了但还没被线程执行」的任务，线程空闲时从队列里取任务执行。

**理解**

任务提交后，若核心线程都在忙，任务先进 workQueue 排队等待。队列有多种类型：有界队列（如 ArrayBlockingQueue）、无界队列（如 LinkedBlockingQueue）、同步队列（SynchronousQueue，不存任务直接交接）等。队列类型和大小影响线程池行为（无界队列可能导致任务堆积、内存问题）。

**场景**

项目里根据业务选队列：需要限流用有界队列，配合拒绝策略；任务量可控可用无界队列。

**常见追问**

- workQueue 存什么？（等待执行的任务）
- 有界和无界队列区别？（有界满了触发拒绝，无界可能堆积）

**易错点**

workQueue 是「任务缓冲」，队列的选择（有界/无界）直接影响线程池是否触发拒绝、是否堆积，别忽视。

## 518. 拒绝策略是什么？

**面试回答**

拒绝策略是线程池「忙不过来」时的处理规则：当线程数达到 maximumPoolSize 且队列也满了，新提交的任务无法处理，就按拒绝策略处理（丢弃、抛异常、或交给调用者执行等）。

**理解**

线程池「满负荷」的标志是「线程满 + 队列满」，此时再来任务就触发拒绝策略。它定义了「实在处理不了时怎么办」，是一种兜底，防止系统被无限堆积的任务压垮。

**场景**

项目里配置合适的拒绝策略，避免线程池过载时任务无限堆积导致 OOM。

**常见追问**

- 什么时候触发？（线程满 + 队列满）
- 为什么要拒绝策略？（兜底，防止过载）

**易错点**

拒绝策略的触发条件是「线程满 + 队列满」，是「过载兜底」；不是队列一满就触发（还要看线程数）。

## 519. 常见拒绝策略有哪些？

**面试回答**

常见四种：AbortPolicy（默认，抛异常）、CallerRunsPolicy（交给调用者线程执行）、DiscardPolicy（直接丢弃）、DiscardOldestPolicy（丢弃队列最老的任务）。

**理解**

AbortPolicy：拒绝并抛 RejectedExecutionException，默认策略，让调用者感知过载；CallerRunsPolicy：不丢任务，交给提交任务的线程自己执行，能「反压」降低提交速度；DiscardPolicy：静默丢弃新任务；DiscardOldestPolicy：丢弃队列里最久的一个任务，再尝试提交新任务。各有适用场景。

**场景**

项目里根据业务选：重要任务用 CallerRunsPolicy 或 AbortPolicy，可丢弃的用 DiscardPolicy。

**常见追问**

- 默认是哪个？（AbortPolicy，抛异常）
- CallerRunsPolicy 特点？（交给调用者线程跑，反压）

**易错点**

四种策略的行为要区分清楚（抛异常/调用者跑/丢弃新/丢弃最旧）；默认 AbortPolicy 会抛异常。

## 520. Tomcat 为什么使用线程池处理请求？

**面试回答**

因为每个 HTTP 请求需要一个线程处理，Tomcat 用线程池复用线程：避免每个请求都创建/销毁线程的开销，同时限制最大并发线程数，防止请求过多时线程无限创建拖垮服务器。

**理解**

Web 请求是「大量、短生命周期」的任务，正好适合线程池。Tomcat 用线程池：请求来了从池里拿线程处理，处理完归还复用，省去频繁创建销毁；同时用最大线程数限制并发，请求多了排队，保护服务器资源。这也是「为什么 ThreadLocal 用完要 remove」的原因——线程被复用。

**场景**

项目部署在 Tomcat 上，所有请求都由 Tomcat 线程池里的线程处理，线程复用提高了吞吐、控制了并发。

**常见追问**

- 线程池对 Tomcat 的好处？（复用 + 限并发）
- 和 ThreadLocal 残留有什么关系？（线程复用导致数据残留风险）

**易错点**

Tomcat 用线程池是「复用 + 限流」的典型应用；它也引出了「线程复用 → ThreadLocal 要清理」的问题。

## 521. ConcurrentHashMap 和 HashMap 有什么区别？

**面试回答**

HashMap 线程不安全，多线程并发读写可能出问题（数据覆盖、死循环等）；ConcurrentHashMap 是线程安全的，支持并发读写且性能好，适合多线程场景。

**理解**

HashMap 没有任何同步，并发 put 可能导致数据丢失、JDK7 甚至可能链表成环（JDK8 已修复但仍有并发问题）；ConcurrentHashMap 用分段/CAS + synchronized 等方式保证线程安全，且读操作大多不加锁，并发性能远好于 Hashtable（全表锁）。多线程共享 Map 要用 ConcurrentHashMap。

**场景**

项目里需要多线程共享的 Map（如本地缓存、统计计数）用 ConcurrentHashMap，而不是 HashMap。

**常见追问**

- HashMap 线程安全吗？（不安全）
- ConcurrentHashMap 比 Hashtable 好在哪？（更细粒度，并发性能好）

**易错点**

核心区别是「线程安全」；ConcurrentHashMap 用细粒度锁/CAS，比 Hashtable 全表锁并发好，是并发 Map 的首选。

## 522. Java 8 ConcurrentHashMap 大致如何保证线程安全？

**面试回答**

JDK 8 的 ConcurrentHashMap 用「CAS + synchronized」保证线程安全：对空桶用 CAS 无锁插入，对已有节点的桶用 synchronized 锁住该桶的头节点，且读操作不加锁（配合 volatile），实现细粒度并发。

**理解**

它放弃了 JDK7 的分段锁，改用「节点级别的锁」：put 时，如果桶是空的用 CAS 尝试插入（无锁）；如果桶里有节点，就 synchronized 锁住桶的头节点再插入。这样锁的粒度缩小到「单个桶」，不同桶之间并发，读操作几乎无锁，性能很好。

**场景**

项目里 ConcurrentHashMap 在并发环境下安全高效，靠的就是这种「CAS + 细粒度锁」的设计。

**常见追问**

- 空桶怎么插入？（CAS 无锁）
- 锁的粒度多大？（单个桶，细粒度）

**易错点**

JDK8 ConcurrentHashMap 是「CAS + synchronized（锁桶头节点）」，不是分段锁；锁粒度是「桶」级别，读不加锁。
