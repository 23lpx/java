# 并发进阶

## 591. CAS 是什么？

**面试回答**

CAS（Compare And Swap，比较并交换）是一种无锁的原子操作：先比较内存里的当前值是否等于预期值，相等才把值更新为新值，否则不更新。它靠 CPU 的原子指令实现，是很多并发工具（如原子类）的基础。

**理解**

CAS 的核心是「先比再换」三步：读当前值、和预期值比较、相等则交换成新值。这三步由 CPU 的原子指令（如 cmpxchg）保证一次性完成，中间不会被别的线程打断，所以无需加锁也能保证原子性。Java 里 AtomicInteger 的 `compareAndSet` 底层就是 CAS。

**场景**

项目里用 AtomicInteger 做并发安全的计数器，`incrementAndGet` 内部就是「CAS + 自旋」实现的，避免了加锁开销。

**常见追问**

- CAS 全称？（Compare And Swap，比较并交换）
- 它靠什么保证原子？（CPU 原子指令）

**易错点**

CAS 是「无锁」的原子操作，但不是「没有失败重试」——失败后通常要自旋重试（见下一题）。

## 592. CAS 有什么问题？

**面试回答**

CAS 主要有三个问题：①ABA 问题（值从 A 变 B 又变回 A，CAS 察觉不到）；②自旋开销（失败会一直循环重试，浪费 CPU）；③只能保证单个变量的原子性。

**理解**

ABA：线程拿到值 A，期间别的线程把值改成 B 又改回 A，此时 CAS 比较还是 A，误以为没变，实际已经变过。自旋：CAS 失败就重试，竞争激烈时一直空转，CPU 开销大。单变量限制：CAS 一次只能原子更新一个变量，多个变量一起原子更新它做不到（要用锁或封装）。

**场景**

项目里高并发下大量线程争同一个 AtomicInteger 时，自旋会带来 CPU 开销；要解决 ABA 可以用 AtomicStampedReference（带版本号）。

**常见追问**

- ABA 问题怎么解决？（加版本号，如 AtomicStampedReference）
- 自旋的代价？（竞争激烈时空转耗 CPU）

**易错点**

CAS 的 ABA 和自旋是重点；它「只保证单个变量原子」这一点容易被忽略。

## 593. AQS 是什么？

**面试回答**

AQS（AbstractQueuedSynchronizer，抽象队列同步器）是 Java 并发包里很多锁和同步器的底层框架，它维护一个「等待队列」和一个 int 类型的 state 状态，通过 state 的 CAS 操作 + 队列管理来实现锁的获取与等待。

**理解**

AQS 是一个抽象框架：用 int 的 state 表示「是否被占用/占用几次」，用 CAS 修改 state 来抢锁，抢不到的线程进入一个 FIFO 等待队列阻塞排队。ReentrantLock、CountDownLatch、Semaphore、线程池等底层都基于 AQS。它把「抢锁、排队、唤醒」这套通用逻辑抽出来，让各同步器只需实现少量方法。

**场景**

项目里用的 ReentrantLock、CountDownLatch 等，底层都是 AQS 在管理「state + 等待队列」，开发者无需自己实现锁的排队逻辑。

**常见追问**

- AQS 的核心是什么？（state 状态 + 等待队列）
- 哪些类基于 AQS？（ReentrantLock、CountDownLatch、Semaphore 等）

**易错点**

AQS 是「框架」，不是具体的锁；它通过「state + CAS + 队列」支撑了并发包里大量同步器。

## 594. ReentrantLock 是什么？

**面试回答**

ReentrantLock 是 Java 提供的可重入的显式锁，是 Lock 接口的实现，支持手动 lock()/unlock()，功能比 synchronized 更丰富（如可中断、可超时、公平锁、条件变量等），底层基于 AQS。

**理解**

「可重入」指同一个线程已持有锁时，再次获取同一把锁不会被自己阻塞（记录持有次数）。ReentrantLock 需要手动加锁解锁（通常用 try-finally 保证 unlock）。它提供了 synchronized 没有的能力：尝试加锁 tryLock、可超时、可中断、公平锁、多个条件变量。

**场景**

项目里需要「尝试获取锁不阻塞」或「超时获取锁」的场景，用 ReentrantLock 的 tryLock(timeout)，比 synchronized 更灵活。

**常见追问**

- 可重入是什么意思？（同一线程可重复获取同一把锁）
- 它需要手动解锁吗？（要，通常 try-finally 里 unlock）

**易错点**

ReentrantLock 必须手动 unlock（否则锁不释放），且 unlock 要放 finally 里；「可重入」是它和普通锁的重要区别。

## 595. synchronized 和 ReentrantLock 有什么区别？

**面试回答**

synchronized 是关键字、自动加锁解锁、使用简单但功能少；ReentrantLock 是类、需手动 lock/unlock、功能更丰富（可超时、可中断、公平锁、多条件变量）。两者都是可重入锁，性能差距不大，一般优先用 synchronized，需要高级特性时用 ReentrantLock。

**理解**

区别：①实现：synchronized 是 JVM 层面的关键字，ReentrantLock 是 JDK 层面的类（基于 AQS）；②释放：synchronized 自动释放（代码块/方法结束），ReentrantLock 要手动 unlock；③功能：ReentrantLock 支持 tryLock 超时、lockInterruptibly 可中断、公平锁、多个 Condition，synchronized 不支持；④可重入：两者都支持。JDK 6 后 synchronized 做了大量优化，性能与 ReentrantLock 接近，所以日常优先 synchronized，特殊需求用 ReentrantLock。

**场景**

项目里一般场景用 synchronized（简单、不易忘解锁）；需要「超时获取锁」或「公平锁」等特性时才用 ReentrantLock。

**常见追问**

- 谁功能更丰富？（ReentrantLock）
- 谁自动释放锁？（synchronized）
- 怎么选？（一般 synchronized，高级需求 ReentrantLock）

**易错点**

核心区别是「自动 vs 手动、功能多少」；不是「ReentrantLock 一定更快」，日常优先 synchronized。

## 596. 什么是 Java 内存模型 JMM？

**面试回答**

Java 内存模型（JMM）是一套规范，定义了多线程环境下「线程与主内存之间如何交互、变量的读写规则」，是保证可见性、原子性、有序性的抽象模型，不是真实存在的物理内存结构。

**理解**

JMM 规定：每个线程有自己的「工作内存」，主内存是共享的；线程对变量的操作要先从主内存读到自己工作内存，改完再写回。JMM 是「规范/约定」，它规定了一套规则（如 volatile、synchronized、happens-before 原则）来保证多线程下的可见性、有序性等。它是理解并发问题的理论框架，不是 JVM 运行时数据区里的真实区域。

**场景**

项目里用 volatile 修饰状态标志、用 synchronized 保护共享数据，背后就是 JMM 规定的可见性、原子性、有序性规则在起作用。

**常见追问**

- JMM 是真实内存吗？（不是，是抽象规范/模型）
- JMM 规定什么？（线程与主内存的交互规则、保证三大特性）

**易错点**

JMM 是「抽象规范」，不是 JVM 内存区域；别把它和「堆、栈」这些真实内存结构混为一谈。

## 597. 什么是可见性？

**面试回答**

可见性指一个线程修改了共享变量的值，其他线程能立即看到这个最新值，而不是读到过期的旧值。

**理解**

没有可见性保证时，线程可能把变量缓存在自己的工作内存里，别的线程改了主内存的值，这个线程仍读自己缓存的旧值，导致数据不一致。volatile、synchronized、锁等机制能保证可见性——让变量的修改及时同步到主内存、读取时从主内存拿最新值。

**场景**

项目里用 volatile 修饰「运行标志位」，让一个线程停止任务、其他线程立刻看到标志变化，就是保证可见性。

**常见追问**

- 不可见会怎样？（读到过期旧值）
- 怎么保证可见性？（volatile、synchronized、锁）

**易错点**

可见性是「修改能被及时看到」，是并发三大特性之一；它针对「共享变量的读写一致性」。

## 598. 什么是原子性？

**面试回答**

原子性指一个或多个操作在执行过程中不可分割，要么全部执行完，要么都不执行，中间不会被其他线程打断，不会出现中间状态。

**理解**

比如 `count++` 是「读、加、写」三步，如果这三步不能作为一个整体执行，两个线程同时执行就可能丢失更新——这就是「不具原子性」。synchronized、Lock、原子类（CAS）能保证一段操作的原子性。原子性解决的是「复合操作被交错执行」的问题。

**场景**

项目里对共享计数器的自增，用 AtomicInteger 或加锁保证「读改写」的原子性，避免并发下计数不准。

**常见追问**

- 原子性解决什么？（复合操作被交错、中间状态）
- 怎么保证？（synchronized、Lock、原子类）

**易错点**

原子性是「操作不可分割」；volatile 不保证原子性，只有锁或 CAS 能保证复合操作的原子性。

## 599. 什么是有序性？

**面试回答**

有序性指程序执行的顺序符合代码的书写顺序（或符合预期的逻辑顺序）；但为了性能，编译器和 CPU 可能做指令重排，有序性就是通过规则禁止那些「会影响正确性」的重排。

**理解**

编译器和 CPU 为优化性能，可能把没有依赖关系的指令调整顺序（指令重排）。单线程下重排不影响结果，但多线程下可能因为执行顺序变了而出现错误（如双重检查锁单例里的问题）。volatile、synchronized 通过内存屏障等机制禁止某些重排，保证有序性。

**场景**

项目里经典的单例「双重检查锁」要用 volatile 修饰实例，就是为了禁止指令重排、保证有序性，防止拿到未初始化的对象。

**常见追问**

- 有序性针对什么？（指令重排）
- 为什么会有重排？（编译器/CPU 优化性能）
- 怎么保证有序性？（volatile、synchronized 等）

**易错点**

有序性不是「不重排」，而是「禁止影响正确性的重排」；它和可见性、原子性并称并发三大特性。
