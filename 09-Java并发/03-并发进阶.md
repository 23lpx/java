# 并发进阶

## 591. CAS 是什么？

**面试回答**

CAS 是 compare-and-set/exchange：原子读取某位置的当前值，只有它等于预期值时才写入新值，并返回成功标志或见证值。AtomicInteger、VarHandle 等用它构造无锁状态更新。

**原理与理解**

典型循环先读取旧值、计算新值，再 CAS；失败说明竞争期间值发生变化，调用方可重读并重试。JVM 可用硬件原子指令、运行时支持或其他合法方式实现，API 不要求固定 CPU 指令。

**成立条件与边界**

`compareAndSet` 提供规定的原子与内存语义；weak CAS 还允许伪失败并有不同的 plain/acquire/release 变体。CAS 只完成一次条件更新，整个算法是否无锁、是否公平由外层协议决定。

**实际场景（通用工程）**

并发递增使用 `AtomicInteger.incrementAndGet`；若用 `updateAndGet`，更新函数可能因 CAS 重试执行多次，所以必须无副作用。

**常见追问**

- CAS 失败代表什么？——当前值不等于预期值；weak 版本还可能伪失败。
- 为什么常配合循环？——竞争失败后需基于新状态重新计算。

**易错点**

“CAS 就是 CPU 的 cmpxchg 且一定比锁快”不是 Java API 契约。

## 592. CAS 有什么问题？

**面试回答**

CAS 常见风险是 ABA、竞争激烈时反复重试消耗 CPU、缺少等待/公平机制，以及多字段不变量难以直接表达；这些是算法权衡，不代表 CAS 本身不原子。

**原理与理解**

ABA 指值从 A 变到 B 再回 A，仅比较值会忽略中间版本。可用 AtomicStampedReference 携带版本；多个字段也可封装为不可变对象后对一个 AtomicReference 原子替换。

**成立条件与边界**

并非所有 CAS 都自旋，失败后可以返回、阻塞或退避。高竞争计数可评估 LongAdder，但其 sum 在并发更新时不是原子快照。版本号也需考虑回绕与业务语义。

**实际场景（通用工程）**

库存状态若只有数值相同仍不足以识别业务版本，应使用版本列进行条件更新；失败后重新读取并限制重试，而不是无限空转。

**常见追问**

- ABA 如何解决？——把版本/时间戳与值一起比较。
- CAS 只能更新一个变量吗？——一次操作针对一个原子位置，但可让该位置引用包含多个字段的不可变状态。

**易错点**

“CAS 只能保证单个业务字段”过度绝对，关键在于原子比较的状态是否完整表达不变量。

## 593. AQS 是什么？

**面试回答**

AQS（AbstractQueuedSynchronizer）是构建阻塞锁和同步器的框架：用一个 int state 表示同步状态，提供原子访问，并维护基于 CLH 变体的等待队列，支持独占和共享获取。

**原理与理解**

子类实现 `tryAcquire/tryRelease` 或共享版本来定义 state 语义；AQS 负责入队、阻塞、取消、唤醒和 ConditionObject 等通用机制。ReentrantLock、Semaphore、CountDownLatch 等直接或间接使用它。

**成立条件与边界**

AQS 是框架而非锁；同步队列虽按 FIFO 维护基础排队关系，但获取策略可插队，不能据此断言所有 AQS 同步器严格公平。state 含义完全由子类定义。

**实际场景（通用工程）**

实现“一次性门闩”可用 CountDownLatch，不应为业务场景直接继承 AQS；只有在标准同步器无法表达时才设计并严格测试自定义同步器。

**常见追问**

- AQS 核心组成？——同步 state、等待队列、独占/共享获取释放协议。
- 线程池基于 AQS 吗？——ThreadPoolExecutor 的 Worker 内部使用 AQS，但线程池整体不能简单等同一个 AQS 同步器。

**易错点**

“CAS 抢不到就进入严格 FIFO 队列”忽略取消、传播、非公平获取与实现细节。

## 594. ReentrantLock 是什么？

**面试回答**

ReentrantLock 是实现 Lock 的可重入互斥锁，具有与 synchronized 类似的基本内存语义，并提供可中断获取、`tryLock`、定时获取、可选公平策略和多个 Condition。

**原理与理解**

同一线程重复 lock 会增加持有计数，必须同次数 unlock。典型写法是在 lock 成功后立即进入 try，并在 finally 中释放；Condition 的 await/signal 必须持有关联锁。

**成立条件与边界**

公平构造尽量偏向等待最久的线程，但吞吐通常更低，且无参 `tryLock()` 即使公平锁也可插队。公平不保证操作系统调度绝对公平。

**实际场景（通用工程）**

跨多个等待条件的有界缓冲区可使用同一 ReentrantLock 的 notEmpty/notFull 两个 Condition；简单临界区优先选择更易审计的 synchronized。

**常见追问**

- 可重入是什么？——持锁线程可再次获取同一锁，持有计数递增。
- 为什么 unlock 放 finally？——异常路径也必须释放，且只在成功加锁后执行。

**易错点**

`lockInterruptibly` 可响应中断，普通 `lock()` 等待过程不等同于可中断获取。

## 595. synchronized 和 ReentrantLock 有什么区别？

**面试回答**

两者都可重入并提供互斥与可见性。synchronized 是语言级监视器、作用域退出自动释放；ReentrantLock 是显式 Lock，需 finally 解锁，并额外支持 try/定时/可中断获取、公平选项和多个 Condition。

**原理与理解**

synchronized 使用对象 wait set 配合 wait/notify；ReentrantLock 可为一把锁创建多个条件队列。选择应根据所需语义、可维护性和观测能力，而不是旧版本性能口诀。

**成立条件与边界**

不能说 ReentrantLock 一定更快，现代 JVM 会优化 synchronized。synchronized 进入锁的等待不能像 lockInterruptibly 那样直接响应中断，但在锁内执行的可中断操作仍可响应。

**实际场景（通用工程）**

只需短临界区时使用 synchronized 降低漏解锁风险；需要获取超时以避免跨资源无限等待时使用 ReentrantLock.tryLock，并设计失败路径。

**常见追问**

- 谁能自动释放？——synchronized 在正常或异常退出时自动释放。
- 谁支持多个条件？——ReentrantLock 的 Condition。

**易错点**

两者差异不只是“关键字与类”，还包括获取、释放和条件等待契约。

## 596. 什么是 Java 内存模型 JMM？

**面试回答**

JMM 是 JLS 对多线程执行允许行为的规范：定义共享变量读写、同步动作、program order、synchronization order、happens-before、数据竞争和 final 字段发布等规则。

**原理与理解**

它检查一次执行中每个读允许观察哪个写，而不是描述 CPU 缓存如何复制到“工作内存”。无数据竞争的正确同步程序具有顺序一致性外观，这是编写并发代码的重要基础。

**成立条件与边界**

JMM 不等于 JVM 堆栈结构，也不承诺所有线程实时看到全局最新值；只有建立 happens-before 等规则时才得到跨线程可见与顺序保证。

**实际场景（通用工程）**

任务提交到 Executor 前的动作 happens-before 任务开始执行；Future.get 成功返回后可看到任务完成前的动作，这是并发 API 建立的内存一致性效果。

**常见追问**

- 什么是 happens-before？——若 A happens-before B，则 A 的效果对 B 可见且在内存模型中排在 B 前。
- 什么是数据竞争？——同一共享变量的冲突访问未被 happens-before 排序。

**易错点**

“主内存 + 每线程工作内存”是解释模型，不应当作真实硬件缓存结构背诵。

## 597. 什么是可见性？

**面试回答**

可见性是一个线程的写在另一个线程读时按 JMM 保证可观察；可靠保证来自 happens-before，而不是“过一会自然刷新”或线程睡眠。

**原理与理解**

同监视器 unlock→lock、volatile write→后续 read、Thread.start、线程终止→join，以及并发工具契约都可建立可见性链。

**成立条件与边界**

可见不等于原子：线程能看到最新 count，仍可能在复合更新中丢失结果。“立即看到”也不是调度时限承诺，只是在读发生时约束允许观察的写。

**实际场景（通用工程）**

主线程设置普通配置字段后调用 worker.start，worker 可看到启动前写入；若线程已运行，则需要 volatile、锁或其他发布机制。

**常见追问**

- sleep 能刷新可见性吗？——没有同步语义。
- final 字段有什么特殊性？——构造期间未逸出并正确发布时具有额外初始化安全保证。

**易错点**

缓存一致性硬件不是 Java 层正确性的替代品，缺少 happens-before 的程序仍可能有数据竞争。

## 598. 什么是原子性？

**面试回答**

并发语境的原子性指某次操作在规定范围内不可被其他线程观察为部分完成，或以单一线性化点生效；它不等同数据库事务的自动回滚语义。

**原理与理解**

单次变量读写、CAS、锁保护临界区和并发容器的指定方法具有不同原子范围。`count++` 包含读与写，不是一个原子操作。

**成立条件与边界**

JLS 允许非 volatile long/double 在某些实现中分两次 32 位访问，但 volatile long/double 必须原子；实际 JVM 常更强，代码仍应按规范同步。单方法原子也不保证多个调用组成的流程原子。

**实际场景（通用工程）**

“余额足够再扣款”是跨读写的不变量，不能只把余额字段换成 AtomicInteger；应使用一次原子更新、数据库条件语句或锁覆盖完整检查。

**常见追问**

- AtomicInteger 能保证任意业务原子性吗？——只保证其方法定义的单值操作，跨对象流程仍需协调。
- 原子性与隔离性一样吗？——不一样，前者关注不可分割操作，后者是事务并发可见规则。

**易错点**

“要么全部成功、要么全部失败”容易让人误以为 Java 原子操作自带事务回滚。

## 599. 什么是有序性？

**面试回答**

有序性指线程内动作遵循 intra-thread semantics，线程间通过 synchronization order 和 happens-before 建立必要顺序；编译器与处理器仍可做不改变合法可观察行为的重排。

**原理与理解**

volatile、锁、start/join 等形成顺序边，使发布前写入不能被合法地观察为发生在对应获取之后。正确同步程序不应依赖实际机器指令恰好按源码排列。

**成立条件与边界**

volatile 只对围绕该变量的内存语义建立约束，不是关闭所有优化。单线程“看起来按顺序”也不能推导出其他线程观察相同总顺序。

**实际场景（通用工程）**

双重检查单例的实例引用必须安全发布，volatile 防止其他线程观察到不满足构造发布规则的状态；更简单的方案是静态初始化或枚举。

**常见追问**

- happens-before 是物理时间先后吗？——不是，它是内存模型中的偏序关系。
- 为什么允许重排？——给 JIT 与硬件优化空间，只要不产生规范禁止的行为。

**易错点**

有序性不是“程序永远严格按源码逐句执行”，而是可观察结果满足语言与同步规则。
