# 线程基础

## 494. 什么是进程？

**面试回答**

进程是操作系统中一个正在运行的程序实例及其资源与隔离边界，通常拥有独立虚拟地址空间、打开的文件、权限和至少一个线程；具体调度与资源模型由操作系统决定。

**原理与理解**

同一可执行程序可以启动多个进程。进程内线程共享大部分进程资源，进程间通信则通常经过管道、Socket、共享内存等显式机制。

**成立条件与边界**

“进程是资源分配的最小单位”是教学口诀，不是跨所有操作系统的严格定义；CPU 实际调度对象通常是内核线程。容器也不是 JVM 进程本身，而是额外的资源与命名空间边界。

**实际场景（通用工程）**

启动一个 Java 服务通常产生一个 JVM 进程；同机启动两个实例会有两个进程、各自堆和 GC，即使运行同一份代码。

**常见追问**

- 进程间能共享内存吗？——默认地址空间隔离，但操作系统可提供显式共享内存。
- JVM 与进程是什么关系？——常见部署是一实例一 JVM 进程，不能把 JVM 规范等同操作系统进程。

**易错点**

程序是静态代码，进程是一次运行实例；一个程序不只对应一个进程。

## 495. 什么是线程？

**面试回答**

线程是进程内的一条执行流。Java 的 `Thread` 既可以是通常映射到内核线程的平台线程，也可以是由 Java 运行时调度、复用少量载体线程的虚拟线程。

**原理与理解**

同一进程内线程共享堆和进程资源，但每条线程有独立执行栈与程序计数位置。平台线程通常由操作系统调度；虚拟线程由 JVM 调度并在阻塞时尝试卸载载体线程。

**成立条件与边界**

“线程是 CPU 调度的最小单位”更适合描述内核/平台线程，不能原样套到虚拟线程。共享内存提高通信效率，也使共享可变状态需要内存模型与同步规则。

**实际场景（通用工程）**

Web 服务可用平台线程池处理请求；Java 21+ 也可评估每请求一个虚拟线程，尤其适合大量阻塞 I/O，但不能因此取消数据库连接池等下游限流。

**常见追问**

- 平台线程与虚拟线程的区别？——前者通常 1:1 映射内核线程，后者由 JVM 调度且更轻量。
- 线程共享什么？——共享进程内存与资源，但有各自的执行栈和状态。

**易错点**

虚拟线程不是“更快的 CPU 线程”，它主要提高阻塞型任务的可扩展性。

## 496. 进程和线程有什么区别？

**面试回答**

进程强调资源、故障与地址空间隔离；线程强调同一进程内的执行并发。线程共享进程资源、通信直接但需同步，进程隔离更强、通信与切换通常成本更高。

**原理与理解**

一个进程可包含多条线程。线程崩溃若演变为进程级故障可能影响整个服务；独立进程则更容易做权限、资源与故障隔离。

**成立条件与边界**

开销大小取决于操作系统、工作负载与平台/虚拟线程，不能只背“线程一定比进程快”。虚拟线程的创建和切换成本又与平台线程不同。

**实际场景（通用工程）**

同一 JVM 内工作线程可以共享缓存对象；两个服务进程则通过 HTTP、RPC 或消息队列通信，并分别承担 GC 与故障边界。

**常见追问**

- 谁隔离更强？——通常是进程。
- 为什么线程更容易出现数据竞争？——它们可直接访问同一共享变量。

**易错点**

线程共享的是进程内可共享资源，不是“所有状态”；线程栈和执行上下文仍相互独立。

## 497. Java 创建线程有哪些常见方式？

**面试回答**

要区分“定义任务”和“调度线程”：`Runnable` 定义无返回任务，`Callable` 定义可返回并抛异常的任务；可交给 `Thread`、`ExecutorService`、`CompletableFuture` 或虚拟线程执行。继承 Thread 也能定制平台线程，但一般不作为业务任务复用方式。

**原理与理解**

`new Thread(r).start()` 创建并启动平台线程；Java 21+ 可用 `Thread.ofVirtual().start(r)` 或虚拟线程执行器。线程池负责复用有限平台线程，虚拟线程执行器通常每任务新建虚拟线程，两者容量模型不同。

**成立条件与边界**

`FutureTask` 可把 Callable 适配为 Runnable/Future。使用异步工具仍要定义异常传播、取消、超时、关闭与上下文传递；不能只回答三种语法写法。

**实际场景（通用工程）**

少量生命周期明确的后台线程可直接创建；大量独立任务使用受控 Executor；高并发阻塞 I/O 可评估虚拟线程并继续限制数据库、HTTP 等稀缺资源。

**常见追问**

- Runnable 与 Callable？——Callable 有结果且可抛受检异常，通常通过 Future 观察。
- 线程池与虚拟线程冲突吗？——不冲突，但平台线程池用于复用稀缺线程，虚拟线程通常按任务创建。

**易错点**

实现 Runnable/Callable 只是定义任务，本身没有创建或启动线程。

## 498. `start()` 和 `run()` 有什么区别？

**面试回答**

`start()` 把 Thread 安排为可执行，并最终由新线程调用其 `run()`；直接调用 `run()` 只是当前线程的一次普通方法调用，不产生新的并发执行流。

**原理与理解**

start 动作 happens-before 被启动线程中的第一个动作，因此启动前正确发布的数据可被新线程看到。一个 Thread 对象只能成功启动一次，再次 start 会抛 IllegalThreadStateException。

**成立条件与边界**

start 返回不代表新线程已经运行或完成，调度顺序无保证；等待结束应使用 join、Future 或结构化并发工具，而不是 sleep 猜时间。

**实际场景（通用工程）**

测试异步代码时若误调用 `worker.run()`，日志仍显示调用线程；改为 start 后还需显式 join 才能稳定断言结果。

**常见追问**

- start 后立即能拿到结果吗？——不能，需建立完成协调。
- start 与可见性有什么关系？——start 前的动作 happens-before 新线程动作。

**易错点**

不能通过覆盖 start 来替代 run 的任务语义，也不能重复启动同一个 Thread 对象。

## 499. Java 线程有哪些状态？

**面试回答**

`Thread.State` 定义六种：NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING、TERMINATED。它是 JVM 暴露的状态模型，不与操作系统线程状态逐项对应。

**原理与理解**

NEW 尚未启动；RUNNABLE 包含正在 JVM 中执行或等待处理器等资源；BLOCKED 专指等待进入 synchronized 监视器；WAITING/TIMED_WAITING 表示无期限/有期限等待特定动作；TERMINATED 表示执行结束。

**成立条件与边界**

等待 ReentrantLock 通常表现为 WAITING，而不是 BLOCKED；`getState()` 是瞬时诊断快照，不能作为并发控制条件。虚拟线程也使用这组六态。

**实际场景（通用工程）**

线程 dump 中大量 BLOCKED 指向监视器竞争；大量 WAITING 可能只是线程池工作线程正常等待任务，要结合堆栈判断。

**常见追问**

- sleep 对应什么？——正数时长通常是 TIMED_WAITING。
- RUNNABLE 是否一定占用 CPU？——不一定，也可能等待操作系统资源或调度。

**易错点**

Java 没有单独的 READY 和 RUNNING 枚举，两者都落在 RUNNABLE 抽象中。

## 500. `sleep()` 和 `wait()` 有什么区别？

**面试回答**

`Thread.sleep` 让当前线程至少暂停指定时长，不释放已持有的监视器，也没有同步语义；`Object.wait` 用于条件协作，调用者必须持有该对象监视器，等待时释放该对象的全部重入持有次数，返回前重新获得它。

**原理与理解**

wait 可因 notify/notifyAll、超时、中断或伪唤醒而返回，因此必须在 synchronized 中用 `while (!condition) wait()`。notify 只把一个任意等待者移出等待集，线程仍要等通知者释放监视器。

**成立条件与边界**

wait 只释放调用目标对象的监视器，不会释放线程持有的其他锁。sleep 与 wait 都可被中断；超时只是“至少等待到该时刻”，不是精确调度保证。

**实际场景（通用工程）**

生产者消费者优先使用 BlockingQueue；若直接 wait/notify，条件谓词、同一锁对象、循环检查和中断处理缺一不可。

**常见追问**

- wait 为什么必须在循环里？——存在伪唤醒，且唤醒后条件可能已被其他线程改变。
- notify 后等待线程立刻执行吗？——不会，先要重新竞争并获取监视器。

**易错点**

“wait 释放所有锁、sleep 到点立刻运行”都不准确。

## 501. 什么是线程上下文切换？

**面试回答**

平台线程上下文切换是处理器从一条可运行线程切到另一条时保存并恢复寄存器、栈位置和调度状态的过程；会带来调度、缓存与流水线等成本。

**原理与理解**

切换可由时间片、阻塞、抢占或同步触发。虚拟线程从载体线程卸载、再挂载属于 JVM 级调度，不一定发生一对一的内核线程上下文切换。

**成立条件与边界**

线程数多不必然意味着切换一定多，Runnable 数、阻塞模式、CPU 核数和虚拟线程挂载行为更关键。切换也不是多线程唯一成本，锁竞争和缓存一致性同样重要。

**实际场景（通用工程）**

平台线程池过大时，通过 JFR、操作系统调度指标和线程 dump 判断是 CPU 饱和、上下文切换还是 I/O 阻塞，再调整并发度。

**常见追问**

- 为什么切换有开销？——状态保存恢复以及 CPU 缓存局部性受损。
- 虚拟线程是否没有切换成本？——不是，只是调度层次和成本结构不同。

**易错点**

不要把“线程越多越慢”当结论，必须结合可运行线程和任务特性测量。

## 502. 什么叫线程安全？

**面试回答**

线程安全指一个类或组件在其公开并发使用契约下，被多个线程以任意合法交错调用时，仍保持不变量、后置条件和可见性要求，而不依赖未声明的调用时序。

**原理与理解**

实现方式包括不可变对象、线程封闭、消息传递、原子变量、并发容器和锁。线程安全是组合属性：单个方法各自线程安全，不代表多步业务操作自动原子。

**成立条件与边界**

“无需任何额外同步”要看 API 契约；有些类通过外部锁也能安全组合。无状态对象通常易于线程安全，但其依赖或返回的可变对象仍可能泄漏共享状态。

**实际场景（通用工程）**

ConcurrentHashMap 的 get/put 各自线程安全，但“先 get 判断不存在再 put”应改为 putIfAbsent/compute，避免复合检查竞态。

**常见追问**

- synchronized 类就一定线程安全吗？——只有锁覆盖全部共享不变量且对象未逸出时才成立。
- 不可变为何安全？——正确构造和安全发布后，状态不再变化。

**易错点**

线程安全不是“运行时没报错”，而是所有允许的并发执行都满足契约。

## 503. 为什么会出现线程安全问题？

**面试回答**

当多个线程对同一共享可变状态发生冲突访问，且缺少足够的 happens-before 或原子协调时，就可能出现数据竞争、丢失更新、检查后执行竞态和非法发布。

**原理与理解**

`count++` 是读、计算、写的复合动作；两个线程可交错并覆盖结果。即使单次读写原子，仍可能因不可见或跨变量顺序缺失而出错。

**成立条件与边界**

“多线程 + 共享 + 可变”是风险条件，不代表必然错误；正确同步可使其安全。反过来，没有共享字段也可能通过外部资源、静态状态或可变依赖形成共享。

**实际场景（通用工程）**

单例 Service 把请求数据保存到实例字段会被并发覆盖；改用局部变量、不可变参数或明确同步，不要把请求状态留在共享 Bean 中。

**常见追问**

- 数据竞争是什么？——同一变量的冲突访问至少一个是写，且没有 happens-before 排序。
- 如何解决？——减少共享、使用不可变/线程封闭，或通过锁、volatile、原子类和并发容器建立正确关系。

**易错点**

原子性、可见性和有序性是不同问题，只修复其中一个不一定让整体线程安全。
