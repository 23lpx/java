# 中间件与分布式基础

## 606. 什么是消息队列？

**面试回答**

消息队列（MQ）是一种中间件，用于在系统之间异步传递消息：生产者把消息发到队列，消费者从队列取消息处理，两者解耦、不必同时在线，起到缓冲、削峰、解耦的作用。

**理解**

消息队列像一个「中转站」：上游（生产者）把消息放进队列，下游（消费者）从队列取走处理。它让生产者和消费者解耦——生产不用等消费，消费不用和生产者直连。因为中间有队列缓冲，能应对流量高峰（削峰）、异步处理（下单后异步发短信/日志）。

**场景**

项目里用户下单后，把「发送通知、记录日志」等非核心操作通过消息队列异步处理，让主流程快速返回。

**常见追问**

- 消息队列干嘛？（异步传递消息、解耦）
- 核心作用？（解耦、异步、削峰）

**易错点**

消息队列的核心价值是「解耦、异步、削峰」；它是「中转站」，生产者和消费者不直接通信。

## 607. 为什么需要消息队列？

**面试回答**

因为很多场景下系统需要解耦、异步、削峰：消息队列能让上游不依赖下游、把耗时操作异步化、在流量高峰时缓冲请求，避免系统被瞬时高并发压垮。

**理解**

没有 MQ 时：上下游直连，一方挂了影响另一方（耦合）；同步调用耗时操作会让请求变慢（无法异步）；流量高峰可能瞬间压垮下游（无法削峰）。消息队列把「同步的、强耦合的调用」变成「异步的、解耦的消息」，解决了这三类问题。

**场景**

项目里秒杀/大促时，请求先进入消息队列缓冲，后端按自己的处理能力慢慢消费，避免瞬时流量打垮数据库。

**常见追问**

- 三大作用？（解耦、异步、削峰）
- 削峰是什么意思？（流量高峰先进队列缓冲，慢慢消费）

**易错点**

「解耦 + 异步 + 削峰」是消息队列存在的原因；理解「削峰」是应对突发流量、保护系统。

## 608. 消息队列可以解决哪些问题？

**面试回答**

主要解决三类问题：①解耦（系统间不直接依赖）；②异步（耗时操作不阻塞主流程）；③削峰（缓冲高峰流量，保护下游）。此外还能用于顺序处理、分布式解耦等。

**理解**

解耦：A 系统不再直接调 B，而是发消息，B 有变化 A 不用改；异步：主流程发完消息就返回，耗时的下游操作后台慢慢做；削峰：请求先入队，下游按能力消费，避免被流量尖峰压垮。这是 MQ 最经典的三个应用场景。

**场景**

项目里订单系统和库存、通知系统通过 MQ 解耦；下单后异步发通知；秒杀时用 MQ 削峰保护数据库。

**常见追问**

- 三个经典问题？（解耦、异步、削峰）
- 分别举个场景？（下单异步通知=异步，秒杀入队=削峰）

**易错点**

MQ 解决的「解耦、异步、削峰」三个要能分别举例说明，别只背名词。

## 609. Kafka 是什么？

**面试回答**

Kafka 是一个分布式消息队列/流处理平台，以「高吞吐、可持久化、可横向扩展」著称，常用于日志收集、大数据、实时流处理等海量数据场景。

**理解**

Kafka 把消息按「主题（Topic）」分区存储，写入磁盘（顺序写、快），支持多副本保证可靠性，能水平扩展集群。它的特点是吞吐量极高（每秒百万级消息），消息可持久化、可回溯（消费者能重新消费），适合日志、埋点、大数据管道这类「数据量大、允许一定延迟」的场景。

**场景**

项目里用 Kafka 收集用户行为日志、埋点数据，供大数据平台和监控消费，靠它的高吞吐扛住海量日志。

**常见追问**

- Kafka 特点？（高吞吐、持久化、可扩展）
- 适合什么场景？（日志、大数据、海量数据）

**易错点**

Kafka 核心是「高吞吐 + 持久化」，适合海量日志/数据管道；和 RabbitMQ 的定位（业务消息、可靠性）不同。

## 610. RabbitMQ 是什么？

**面试回答**

RabbitMQ 是一个开源的、功能丰富的消息队列，实现了 AMQP 协议，可靠性高、路由灵活，常用于业务系统的异步解耦，是中小型系统常用的 MQ。

**理解**

RabbitMQ 基于 AMQP 协议，提供交换机（Exchange）、队列（Queue）、路由键等灵活的路由机制，支持消息确认、持久化、死信队列等保证可靠性。相比 Kafka，它更侧重「业务消息的可靠投递和灵活路由」，吞吐量中等但功能全、易用，适合订单、通知等业务场景。

**场景**

项目里用 RabbitMQ 做订单异步处理、发送通知等业务消息，靠它的确认机制保证消息不丢。

**常见追问**

- RabbitMQ 基于什么协议？（AMQP）
- 和 Kafka 定位区别？（业务消息可靠 vs 高吞吐大数据）

**易错点**

RabbitMQ 侧重「业务消息 + 可靠投递」，Kafka 侧重「高吞吐 + 大数据」；按场景选，别说反。

## 611. 什么是 RPC？

**面试回答**

RPC（Remote Procedure Call，远程过程调用）是让程序像调用本地方法一样调用「另一台机器上的服务」的技术，屏蔽了网络通信细节，调用方感知不到是远程调用。

**理解**

RPC 解决「跨机器调用」：客户端调一个方法，底层把方法名、参数序列化通过网络发给服务端，服务端执行后把结果序列化返回，客户端收到反序列化得到结果。整个过程对调用方透明，像调本地方法。核心是「序列化 + 网络传输 + 动态代理」。Dubbo、gRPC 都是 RPC 框架。

**场景**

项目里微服务之间调用（如订单服务调用户服务查用户信息），用 Dubbo 等 RPC 框架，像调本地方法一样方便。

**常见追问**

- RPC 是什么？（像本地调用一样调远程服务）
- 核心要素？（序列化、网络传输、代理）

**易错点**

RPC 是「远程调用像本地调用」；关键是屏蔽网络细节，涉及序列化和网络传输。

## 612. Dubbo 是什么？

**面试回答**

Dubbo 是阿里巴巴开源的高性能 Java RPC 框架，提供服务注册发现、负载均衡、远程调用、服务治理等能力，是微服务/分布式系统里服务间通信的常用框架。

**理解**

Dubbo 让分布式服务之间高效通信：服务提供者把服务注册到注册中心（如 Zookeeper、Nacos），消费者从注册中心发现服务地址，再远程调用。它内置负载均衡、容错、监控等治理能力，性能好、生态成熟，是 Java 生态主流 RPC 框架之一。

**场景**

项目里多个微服务用 Dubbo 做 RPC 通信，服务注册到 Nacos，消费者自动发现并调用，配合负载均衡。

**常见追问**

- Dubbo 是什么？（高性能 Java RPC 框架）
- 靠什么发现服务？（注册中心）

**易错点**

Dubbo 是「RPC 框架」，核心是「远程调用 + 服务治理」；它需要注册中心做服务发现。

## 613. 什么是微服务？

**面试回答**

微服务是一种架构风格：把一个大应用拆分成多个小服务，每个服务独立部署、独立开发、围绕单一业务职责，服务之间通过网络（HTTP/RPC）通信，各自可独立扩展和升级。

**理解**

相比「单体应用」（所有功能一个应用），微服务把系统按业务拆成多个小服务（用户服务、订单服务、支付服务等），每个服务有自己的代码库、数据库、部署单元。好处：独立开发部署、技术栈灵活、故障隔离、易扩展；代价：分布式复杂度（网络调用、数据一致性、服务治理）。

**场景**

项目里把外卖系统拆成用户、订单、菜品等多个微服务，各自独立部署、通过 Dubbo/HTTP 通信。

**常见追问**

- 微服务是什么？（拆成多个独立小服务）
- 好处/代价？（独立部署易扩展 vs 分布式复杂度）

**易错点**

微服务是「按业务拆分、独立部署」的架构风格；好处和代价（分布式复杂性）都要答，别只讲好处。

## 614. Spring Cloud 是什么？

**面试回答**

Spring Cloud 是一套基于 Spring Boot 的微服务解决方案/生态，提供了一系列组件（服务注册发现、配置中心、网关、负载均衡、熔断等），帮助快速搭建微服务系统。

**理解**

Spring Cloud 本身不是单一框架，而是一整套微服务工具集，解决微服务落地时的各种问题：服务注册发现（Nacos/Eureka）、配置管理（Spring Cloud Config/Nacos）、网关（Gateway）、负载均衡（Ribbon/LoadBalancer）、熔断降级（Sentinel/Hystrix）、远程调用（Feign/OpenFeign）等。它基于 Spring Boot，让微服务开发有统一、成熟的方案。

**场景**

项目里用 Spring Cloud 全家桶（Nacos 注册发现、Gateway 网关、OpenFeign 远程调用）搭建微服务架构。

**常见追问**

- Spring Cloud 是什么？（微服务解决方案/组件生态）
- 包含哪些组件？（注册发现、网关、配置、熔断等）

**易错点**

Spring Cloud 是「一套微服务组件生态」，不是单个框架；要能举出几个典型组件（Nacos、Gateway、Feign）。

## 615. Nacos 是什么？

**面试回答**

Nacos 是阿里巴巴开源的服务注册与配置中心，提供服务注册与发现、动态配置管理两大核心功能，是微服务架构里常用的基础设施。

**理解**

Nacos 两大作用：①服务注册发现——服务启动时注册到 Nacos，其他服务从 Nacos 获取可用实例地址，实现服务发现；②配置中心——把配置集中管理，支持动态刷新，改配置不用重启服务。它替代了早期 Eureka + Config 的组合，功能更全。

**场景**

项目里各微服务启动后注册到 Nacos，互相通过 Nacos 发现并调用；配置也放 Nacos 统一管理、动态刷新。

**常见追问**

- Nacos 两大功能？（服务注册发现、配置中心）
- 配置中心有什么好处？（集中管理、动态刷新）

**易错点**

Nacos = 「注册中心 + 配置中心」，两个功能都要答到；它常用于微服务的服务发现和配置管理。

## 616. 什么是服务注册与发现？

**面试回答**

服务注册与发现是微服务里的一种机制：服务启动时把自身地址注册到注册中心（注册），调用方从注册中心获取目标服务的可用实例地址（发现），从而在服务实例动态变化时仍能正确调用。

**理解**

微服务实例会动态增删（扩容、下线、故障），IP 和端口不固定，不能写死调用地址。注册与发现解决这个：服务提供者启动时「注册」自己的地址，消费者「发现」并拉取可用实例列表，配合负载均衡选一个调用。注册中心（Nacos、Zookeeper）是关键枢纽。

**场景**

项目里订单服务启动后注册到 Nacos，用户服务调订单服务时先从 Nacos 拉订单服务实例列表，再选一个调用。

**常见追问**

- 为什么需要它？（服务实例地址动态变化）
- 谁做这个？（注册中心，如 Nacos）

**易错点**

服务注册与发现解决「服务地址动态变化、不能写死」的问题；注册中心是核心枢纽。

## 617. 什么是限流？

**面试回答**

限流是控制单位时间内通过的请求数量，防止流量过大压垮系统；超过阈值的请求被拒绝、排队或降级，保护系统稳定。

**理解**

系统处理能力有限，突发流量（秒杀、爬虫、攻击）可能打垮系统。限流设定「每秒最多处理 N 个请求」，超过就拒绝或排队。常见算法：令牌桶、漏桶、滑动窗口、计数器。实现方式有网关限流（如 Gateway + Sentinel）、接口限流、Nginx 限流等。

**场景**

项目里对秒杀接口、开放 API 做限流（如每用户每秒最多 5 次），防止刷接口、保护后端。

**常见追问**

- 限流解决什么？（防止流量过大压垮系统）
- 常见算法？（令牌桶、漏桶、滑动窗口）

**易错点**

限流是「控制单位时间请求量」；它和熔断不同（限流是防流量过大，熔断是防故障扩散）。

## 618. 什么是熔断？

**面试回答**

熔断是一种容错机制：当某个服务调用失败率过高、响应过慢时，暂时「断开」对该服务的调用，直接快速失败（或走降级逻辑），避免故障扩散拖垮整个系统，等它恢复后再尝试。

**理解**

类比「保险丝」：下游服务挂了或超时，如果还一直调它，会堆积大量等待、拖垮上游。熔断器监控调用，失败率达到阈值就「打开」熔断，后续请求直接失败/降级，不再打下游；一段时间后「半开」试探，下游恢复了再「关闭」恢复调用。常见组件：Sentinel、Hystrix、Resilience4j。

**场景**

项目里订单服务调支付服务，支付服务故障时熔断，订单服务快速返回降级结果，不让故障蔓延。

**常见追问**

- 熔断解决什么？（下游故障扩散）
- 状态有哪些？（关闭、打开、半开）

**易错点**

熔断是「防止故障扩散」，典型状态「关闭→打开→半开」；它和限流针对的问题不同。

## 619. 什么是分布式事务？

**面试回答**

分布式事务指一次业务操作涉及多个服务/多个数据库，需要保证这些跨服务的操作「要么都成功、要么都失败」的一致性；由于跨网络和数据库，不能靠单个数据库的事务实现，需要专门方案。

**理解**

单机事务靠数据库 ACID 就能保证；但微服务下，一个下单操作可能涉及订单服务、库存服务、账户服务（各自有自己的库），要保证「一起成功或一起回滚」就难了。分布式事务方案有：两阶段提交（2PC，强一致但复杂）、TCC（Try-Confirm-Cancel）、本地消息表、最终一致性（基于消息队列）等。多数场景追求「最终一致」而非强一致。

**场景**

项目里下单要同时扣库存、扣余额、生成订单，跨多个服务，用分布式事务方案（如消息队列保证最终一致）协调。

**常见追问**

- 分布式事务解决什么？（跨服务/跨库的一致性）
- 为什么难？（跨网络、跨库，不能靠单库事务）

**易错点**

分布式事务核心是「跨服务保证一致性」；方案有 2PC、TCC、最终一致性，实习面试知道概念和常见方案即可。

## 620. CAP 理论是什么？

**面试回答**

CAP 理论指分布式系统在三个特性中最多只能同时满足两个：一致性（C，所有节点数据一致）、可用性（A，请求总能得到响应）、分区容错性（P，网络分区故障时仍能工作）。分布式系统必须选 P，所以实际是在 C 和 A 之间取舍。

**理解**

C 一致性：读任何节点都读到最新数据；A 可用性：每个请求都能得到响应（不保证最新）；P 分区容错：节点间网络断开（分区）时系统仍可用。分布式系统网络分区不可避免，所以 P 必须保证，剩下只能「CP」或「AP」二选一：要强一致（CP）就牺牲部分可用性，要高可用（AP）就允许短暂不一致。如 Zookeeper 偏 CP，Eureka/Nacos 偏 AP。

**场景**

项目里选注册中心时理解 CAP 取舍：Nacos 偏 AP（保证可用，允许短暂不一致），适合大多数业务场景。

**常见追问**

- CAP 三个字母？（一致性、可用性、分区容错）
- 为什么不能三者都满足？（分区容错下，C 和 A 冲突）
- 通常怎么选？（必须 P，在 C/A 之间取舍）

**易错点**

CAP 是「三选二」，且分布式必须保证 P（分区容错），实际是 CP 和 AP 之间选；别以为三个能同时满足。
