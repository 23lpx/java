# 反射

## 172. Java 反射是什么？

**面试回答**

Java 反射是通过 `Class` 及 `java.lang.reflect` API 在运行时检查类型、构造器、方法、字段和注解，并在权限允许时动态创建对象、调用方法或读写字段的机制。

**原理与理解**

类加载后，JVM 用 Class 对象表示运行时类型；Method、Field、Constructor 等对象描述其成员。框架可依据配置和元数据处理编译时未知的用户类型。

**成立条件与边界**

反射不能任意突破访问控制。`setAccessible/trySetAccessible` 受语言访问规则、模块开放和安全策略限制，强封装下可能失败。它也不会绕过类型兼容检查。

**实际场景（通用工程）**

依赖注入、ORM 映射、序列化和测试工具可用反射读取元数据；业务热路径优先显式类型契约。

**常见追问**

- 入口是什么？——运行时 `Class<?>` 对象。
- 能访问 private 吗？——在模块开放且允许取消检查时可能，不能保证。

**易错点**

不要回答“setAccessible(true) 后一定能访问所有 private 成员”。

## 173. 反射可以在运行时做什么？

**面试回答**

可以枚举类型及成员、读取泛型和注解元数据、选择构造器创建实例、调用方法、读写字段，以及检查修饰符、参数和继承关系。

**原理与理解**

`Class` 提供 public/inherited 与 declared 两组查询方式；Constructor、Method、Field 执行操作时会检查目标对象、参数类型、访问权限和模块边界。

**成立条件与边界**

`Class.newInstance()` 已废弃，应使用 `getDeclaredConstructor(...).newInstance()`。反射看到的泛型信息取决于 class 文件中保留的签名，运行时对象仍受类型擦除影响。

**实际场景（通用工程）**

插件系统读取实现类名和注解后创建实例；生产代码应校验允许类型，避免按不可信字符串加载任意类。

**常见追问**

- 如何创建对象？——取得合适 Constructor 后调用 `newInstance`。
- 反射能看到方法参数名吗？——需编译器保留相关元数据，否则不一定。

**易错点**

不要继续推荐已废弃的 `Class.newInstance()`。

## 174. 获取 Class 对象有哪些方式？

**面试回答**

常见方式有类型字面量 `String.class`、已有对象的 `obj.getClass()`、`Class.forName("全限定名")`，以及显式 `ClassLoader.loadClass`；数组和基本类型也有自己的 Class 对象。

**原理与理解**

`Class.forName(String)` 默认使用调用方类加载器并初始化目标类；三参数重载可控制是否初始化和使用哪个 ClassLoader。`loadClass` 通常只加载而不主动初始化。

**成立条件与边界**

同名类由不同类加载器加载会得到不同 Class 对象，因此“三种方式一定得到同一个对象”只在同一运行时类型与类加载器语境成立。对象可能为 null 时也不能调用 `getClass`。

**实际场景（通用工程）**

编译期已知类型使用 class 字面量；插件或驱动加载显式选择类加载器并限制类名来源。

**常见追问**

- class 字面量会初始化类吗？——仅引用类字面量通常不会触发初始化。
- `forName` 可能抛什么？——常见为 `ClassNotFoundException`，初始化还可能失败。

**易错点**

类名相同不等于类型相同，类加载器也是运行时类型身份的一部分。

## 175. Method 对象是什么？

**面试回答**

`Method` 描述类或接口的一个方法声明，包含声明类、名称、参数、返回类型、异常、修饰符、泛型和注解等元数据，并可用于反射调用。

**原理与理解**

`getMethod` 查找 public 方法并包含继承成员；`getDeclaredMethod` 只查当前类声明的方法，可包含非 public，但不自动向父类查找。

**成立条件与边界**

重载方法必须用精确参数类型区分；桥接方法、可变参数和合成方法可能也出现在反射结果中。取得 Method 不代表有权限调用。

**实际场景（项目核验项）**

AutoFill 若按 setter 名称查 Method，应核对参数类型、继承层次和缺失方法的错误策略，避免依赖脆弱字符串。

**常见追问**

- Method 属于实例吗？——它描述声明；调用实例方法时另传接收对象。
- 如何查父类 private 方法？——逐级遍历父类并使用 declared 查询。

**易错点**

`getDeclaredMethod` 不是“能查询全部父类私有方法”的万能接口。

## 176. Field 对象是什么？

**面试回答**

`Field` 描述一个字段声明，可读取名称、类型、泛型、注解和修饰符，并在权限与类型允许时对指定对象执行 get/set。

**原理与理解**

`getField` 查找 public 且包含继承字段；`getDeclaredField` 只查当前类声明。实例字段需要目标对象，static 字段不依赖具体实例。

**成立条件与边界**

final、record 组件对应字段、强封装模块等都有额外限制，`setAccessible` 不保证可写。直接修改 private 字段还可能破坏类的不变量和 Java 内存模型假设。

**实际场景（通用工程）**

框架可读取注解字段元数据，但写入业务对象时优先使用构造器、Bean 属性或明确接口，减少封装破坏。

**常见追问**

- Field 与属性相同吗？——不相同，JavaBean 属性可能由 getter/setter 定义而无同名字段。
- 如何访问继承字段？——根据可见性选择 public 查询或逐级遍历 declared 字段。

**易错点**

不要把字段和 JavaBean 属性混为一谈。

## 177. `Method.invoke()` 有什么作用？

**面试回答**

`Method.invoke(target, args...)` 在运行时调用该 Method 表示的方法；实例方法需要兼容的 target，static 方法可传 null，返回值以 Object 表示，void 返回 null。

**原理与理解**

反射会执行访问、接收者和参数转换检查；目标方法抛出的异常通常封装在 `InvocationTargetException` 中，可通过 `getCause()` 取得原异常。

**成立条件与边界**

调用可能抛出 `IllegalAccessException`、`IllegalArgumentException` 等。反射只执行方法，不会自动进入 Spring AOP；对目标对象直接 invoke 仍可能绕过代理。

**实际场景（项目核验项）**

若 AutoFill 调用 setter，应缓存已验证的 Method，保留原始 cause，并区分字段不存在与业务执行失败。

**常见追问**

- 为什么异常被包装？——反射 API 用 InvocationTargetException 区分调用机制失败与目标方法失败。
- private 方法怎么调用？——先满足访问/模块开放要求，再取消检查；不保证成功。

**易错点**

实例方法 target 不能随意为 null，且捕获 InvocationTargetException 后不能丢掉 cause。

## 178. 反射有什么优点？

**面试回答**

反射让基础设施在编译时不知道具体业务类型的情况下，依据运行时元数据完成插件发现、依赖装配、映射、序列化和测试等通用能力。

**原理与理解**

它降低框架对具体类的静态依赖，并允许通过注解和约定扩展行为。缓存反射元数据后，一套实现可服务大量用户类型。

**成立条件与边界**

反射不是所有框架能力的唯一基础，生成代码、MethodHandle、字节码增强和编译期注解处理也可实现类似目标。AOT/native image 环境还可能要求显式注册反射元数据。

**实际场景（通用工程）**

ORM 根据映射元数据构造结果对象；高频映射也可通过生成访问器或编译期代码降低运行时反射成本。

**常见追问**

- 为什么适合框架？——框架需要处理框架作者未知的应用类型。
- 如何提高可靠性？——启动期预校验、缓存元数据、限制允许成员并提供明确错误。

**易错点**

不要说“没有反射就不可能实现 IoC、ORM 或序列化”。

## 179. 反射有什么缺点？

**面试回答**

主要代价是类型和成员错误延迟到运行期、破坏封装的风险、额外查找与调用开销，以及模块化、AOT 和重构工具支持变复杂。

**原理与理解**

字符串名称和动态参数缺少普通调用的编译期检查；成员查找和适配比直接调用多一层。频繁重复查找可通过缓存缓解，但不能修复脆弱契约。

**成立条件与边界**

现代 JVM 已优化反射调用，不能笼统说“反射非常慢、绝不能用于生产”。应以真实热点基准决定是否改用 MethodHandle、生成代码或直接接口。

**实际场景（通用工程）**

启动阶段扫描和元数据缓存通常可接受；每条大批量记录都重复查 Method 则应缓存或换专用映射器。

**常见追问**

- 怎么降低开销？——缓存元数据、减少动态查找、批量处理并基准验证。
- 最大维护风险？——重命名或签名变化可能直到运行期才暴露。

**易错点**

性能只是代价之一，封装、可诊断性与部署约束同样重要。

## 180. 项目的 AutoFill 为什么需要反射？

**面试回答**

如果 AutoFill 切面只拿到 Object，而多种实体仅通过字段或 setter 命名约定提供审计属性，反射可以按运行时类型查找并赋值；但它是实现选择，不是唯一方案。

**原理与理解**

切面从方法参数取得实体，读取操作类型和当前身份，再调用匹配的 setter。通过缓存 Method 可避免每次查找，缺字段和类型不兼容要有明确策略。

**成立条件与边界**

可以改为统一 Auditable 接口、MyBatis 插件、ORM 审计能力或数据库默认值。反射方案只有在实体约定一致、切点准确、批量参数和代理对象均被处理时才成立。

**实际场景（项目核验项）**

需在仓库确认 `@AutoFill`、操作类型、实体参数位置、setter 名称及当前用户来源；简历未明确的实现细节不作为真实经历扩写。

**常见追问**

- 为什么不直接强转？——切面可能面对多个无共同接口的类型。
- 如何支持批量对象？——明确识别集合/数组并逐项处理，不能只取第一个参数就假设是实体。

**易错点**

不要回答“任意实体字段不同，所以只能反射”；统一接口也能提供类型安全方案。

## 181. 为什么不直接调用实体类 setter？

**面试回答**

通用切面若在编译期只知道 Object，就无法直接调用某个具体实体 setter；反射能按运行时类型调用约定方法。若实体实现共同接口，则直接调用接口方法通常更安全。

**原理与理解**

写 `if (x instanceof Dish)` 等分支会让切面依赖所有实体并随类型增长；反射把依赖转为命名/签名约定，接口则把约定提升为编译期契约。

**成立条件与边界**

反射并不会让新增实体“自动正确”：实体仍必须满足字段、类型、注解和参数位置约定，且切点要命中。setter 还可能包含业务逻辑，切面调用前需确认副作用。

**实际场景（项目核验项）**

面试前核对项目究竟使用 Method.invoke、字段写入还是公共基类/接口，不根据题目标题反推实现。

**常见追问**

- 反射与公共接口怎么选？——类型可控且能修改模型时优先接口；第三方/异构类型才考虑反射。
- 新增实体需要什么？——满足契约并通过切面集成测试。

**易错点**

“新增实体无需任何修改就生效”只有在所有隐含约定都满足时才成立。
