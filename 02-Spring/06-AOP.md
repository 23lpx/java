# AOP

## 158. 什么是 AOP？

**面试回答**

AOP 是面向切面编程，把事务、观测等横跨多个组件的关注点模块化，并按切点规则应用到目标执行点。Spring AOP 采用运行时代理，连接点只支持 Spring Bean 的方法执行。

**原理与理解**

容器为符合 Advisor/Aspect 条件的 Bean 创建代理，调用代理方法时执行拦截器链，再进入目标方法。业务对象关注用例本身，切面集中表达横切策略。

**成立条件与边界**

只有经过代理的外部调用才能触发；`this` 自调用、手工 `new` 的对象、不可代理方法都可能绕过增强。完整 AspectJ 还支持构造器、字段等连接点，不能与 Spring AOP 混为一谈。

**实际场景（通用工程）**

声明式事务、耗时指标和审计可使用 AOP；核心业务判断不应藏在难以发现的切面中。

**常见追问**

- AOP 与 OOP 的关系？——AOP 补充 OOP，模块化横切关注点。
- Spring AOP 如何织入？——主要通过运行时代理和拦截器链。

**易错点**

AOP 不是把任意代码“动态插入任何位置”，Spring AOP 的边界是 Bean 方法代理。

## 159. AOP 解决什么问题？

**面试回答**

AOP 解决横切策略散落、重复和难以统一治理的问题，使同一策略能按规则应用到多个方法，同时保持业务代码聚焦。

**原理与理解**

切点负责选择方法，通知负责执行策略，顺序规则协调多个切面。事务、追踪、指标等因此可以集中配置、测试和演进。

**成立条件与边界**

AOP 只能降低代码重复，不能自动降低认知成本；切点过宽、隐式修改参数或返回值会让行为难追踪。需要领域上下文的业务规则通常应显式调用。

**实际场景（通用工程）**

对服务边界统一记录耗时和失败指标；订单状态迁移仍在业务服务中显式表达。

**常见追问**

- 为什么不直接抽工具类？——工具类仍要每处显式调用，AOP 可按执行点统一应用。
- AOP 最大风险？——隐式控制流、误匹配和代理边界遗漏。

**易错点**

“横切”不等于“与业务无关”，审计等可能有业务语义，仍需清晰契约。

## 160. 哪些场景适合使用 AOP？

**面试回答**

适合跨多个 Bean 方法、规则稳定、可在方法边界表达的关注点，如事务、指标、追踪、审计、重试或声明式缓存；是否采用还要看代理与幂等边界。

**原理与理解**

好的切面输入来自注解、签名或稳定包边界，输出和副作用明确，并可单独测试。应使用能满足需求的最窄通知类型与切点。

**成立条件与边界**

权限校验涉及资源级上下文时不能只靠宽泛切面；重试必须保证操作幂等；缓存、事务的切面顺序会改变语义。`@RestControllerAdvice` 属于 MVC 异常处理机制，不是 Spring AOP 切面。

**实际场景（项目核验项）**

项目中的 `@AutoFill` 若确由切面实现，可描述为方法边界的公共字段填充；具体注解、切点和字段规则需以代码核验。

**常见追问**

- 什么不适合？——核心流程、复杂状态机和依赖隐式顺序的业务逻辑。
- 如何避免误匹配？——使用窄包范围和语义注解，并写切点测试。

**易错点**

不要把所有“公共代码”都塞入 AOP，横切性和可观察性同样重要。

## 161. 什么是横切关注点？

**面试回答**

横切关注点是在多个模块或用例边界重复出现、无法自然归属某个单一业务类的策略，例如事务一致性、追踪、指标与审计。

**原理与理解**

它与纵向业务流程交叉，若每个方法手写会造成策略漂移。AOP 将选择规则和执行逻辑集中，但目标方法仍保持自身职责。

**成立条件与边界**

是否横切取决于架构范围；“更新人”可能是基础审计字段，也可能参与业务规则。抽取前要确认语义一致，不能只因代码长得相似就合并。

**实际场景（通用工程）**

统一记录服务方法的追踪标签属于横切；“订单取消后返还库存”属于业务流程，不应隐藏成通用切面。

**常见追问**

- 常见例子？——事务、日志/指标、审计、缓存。
- 与工具方法区别？——横切关注点还包含应用位置和执行时机。

**易错点**

“非业务代码”不是判定横切关注点的唯一标准。

## 162. 什么是 JoinPoint？

**面试回答**

JoinPoint 是程序执行中可应用通知的位置；在 Spring AOP 中，它始终表示 Spring Bean 的一次方法执行。

**原理与理解**

通知方法可通过 AspectJ 的 `JoinPoint` 参数读取代理、目标、签名和实参；环绕通知使用 `ProceedingJoinPoint` 决定是否及如何继续执行。

**成立条件与边界**

“所有方法都是 JoinPoint”不准确：只有进入 Spring AOP 代理模型的 Bean 方法调用才可能被增强。字段访问、构造器执行等不是 Spring AOP 连接点。

**实际场景（通用工程）**

服务 Bean 的公开方法经代理调用时可成为连接点，切点再从中选择标注特定注解的方法。

**常见追问**

- JoinPoint 与 Pointcut？——前者是执行位置，后者是匹配这些位置的谓词。
- 能修改参数吗？——环绕通知可选择传入 `proceed` 的参数，但应保持契约。

**易错点**

不要把 JoinPoint 对象、连接点概念和 Pointcut 表达式混为一谈。

## 163. 什么是 Pointcut？

**面试回答**

Pointcut 是匹配连接点的谓词，决定哪些 Spring Bean 方法执行应用通知；常见设计器有 `execution`、`within`、`@annotation`、`args` 和 `bean`。

**原理与理解**

`execution` 根据方法签名匹配，`@annotation` 根据执行方法的注解匹配，`args` 依据运行时实参类型。命名切点可被多个通知复用和组合。

**成立条件与边界**

不同设计器语义不同，例如 `args(Serializable)` 与签名声明 `Serializable` 的 `execution` 并不等价。切点过宽会误增强基础设施或增加匹配成本。

**实际场景（项目核验项）**

AutoFill 若使用自定义注解，应核对匹配的是方法注解、类注解还是包表达式，不能仅凭类名猜测。

**常见追问**

- Pointcut 与 Advice 的关系？——一个决定“哪里”，一个决定“做什么”。
- 如何提升可维护性？——范围设计器 + 语义注解，并为正反例写测试。

**易错点**

Pointcut 不是“被切的方法本身”，而是匹配规则。

## 164. 什么是 Advice？

**面试回答**

Advice 是在切点匹配的连接点上执行的动作，包含 before、after returning、after throwing、after finally 和 around 等时机。

**原理与理解**

通知与 Pointcut 关联后形成拦截器链。最窄能力优先：只需前置检查就用 before，需要控制是否执行、参数或返回值时才用 around。

**成立条件与边界**

Before 可以通过抛异常阻止后续执行，但不能正常返回一个替代值；Around 若忘记 `proceed()` 会短路目标方法。通知异常也会改变业务调用结果。

**实际场景（通用工程）**

耗时统计可用 around 并在 `finally` 记录；只记录成功返回结果可用 after returning。

**常见追问**

- Advice 能拿到方法参数吗？——可通过 JoinPoint 或参数绑定获得。
- Around 为什么最强？——它包围连接点并负责是否继续。

**易错点**

不要默认选择 Around，能力越强越容易改变控制流。

## 165. 常见的通知类型有哪些？

**面试回答**

常见五类是 `@Before`、`@AfterReturning`、`@AfterThrowing`、`@After` 和 `@Around`，分别对应执行前、正常返回后、抛出异常后、最终完成后和环绕控制。

**原理与理解**

`@After` 类似 finally，无论正常或异常完成都会运行；`@AfterReturning` 只在正常返回后；`@AfterThrowing` 只在匹配异常传播时；Around 通过 `proceed` 推进链路。

**成立条件与边界**

After 通知不能假设事务已经提交，切面顺序和事务传播会影响最终时机。AfterThrowing 只观察向外传播的异常，被目标内部吞掉的异常不会触发。

**实际场景（通用工程）**

成功审计用 after returning，失败指标用 after throwing，必须收尾的计时用 around 的 finally。

**常见追问**

- `@After` 与 `@AfterReturning`？——前者不区分成功失败，后者仅正常返回。
- Around 能调用多次 proceed 吗？——技术上可能，但会重复执行目标，必须有明确语义。

**易错点**

“方法执行后”太模糊，要说明正常、异常还是 finally 语义。

## 166. 什么是 Aspect？

**面试回答**

Aspect 是模块化的横切关注点，通常组合一个或多个 Pointcut 与 Advice；`@Aspect` 标记类使用 @AspectJ 风格声明切面。

**原理与理解**

Spring 解析 Aspect Bean，生成 Advisor 并为匹配 Bean 创建代理。切面还可声明顺序、参数绑定和可复用切点。

**成立条件与边界**

`@Aspect` 本身不是组件扫描 stereotype，类还需通过 `@Component`、`@Bean` 等注册为 Spring Bean，并启用相应 AOP 基础设施。多个切面顺序应显式且有测试。

**实际场景（项目核验项）**

若仓库存在 AutoFillAspect，应核对它的 Bean 注册方式、通知类型、切点和异常策略后再作为项目答案。

**常见追问**

- Aspect 是否等于 Pointcut + Advice？——这是便于记忆的核心组合，完整模型还包括声明与实例化等。
- 如何控制顺序？——使用 `@Order`/`Ordered`，但跨通知语义仍需验证。

**易错点**

只写 `@Aspect` 不保证切面被 Spring 发现和应用。

## 167. Spring AOP 底层大致如何实现？

**面试回答**

Spring AOP 通过自动代理创建器为匹配的 Bean 包装 JDK 动态代理或基于 CGLIB 的类代理；方法经代理进入 Advisor/MethodInterceptor 链，最后调用目标对象。

**原理与理解**

BeanPostProcessor 在容器生命周期中评估候选 Advisor，必要时返回代理。调用链按顺序执行通知，Around 通知通过 `proceed` 推进到下一个拦截器或目标方法。

**成立条件与边界**

并非“有接口必然 JDK、没接口必然 CGLIB”这一句就够了，`proxyTargetClass` 等配置可强制类代理。自调用使用 `this` 直接进入目标对象，不经过外层代理。

**实际场景（通用工程）**

注入代理 Bean 后调用事务方法能触发增强；手工创建同类实例或在同类内部直接调用则可能绕过代理。

**常见追问**

- 代理何时产生？——通常在 Bean 后处理阶段。
- 为什么代理顺序重要？——事务、缓存和重试的嵌套顺序会改变语义。

**易错点**

Spring AOP 是运行时代理，不是把字节码永久改写进目标类。

## 168. JDK 动态代理和 CGLIB 有什么区别？

**面试回答**

JDK 动态代理生成实现指定接口的代理，客户端以接口视图调用；CGLIB 类代理通过生成目标类子类覆盖可代理方法，可代理没有接口的类。

**原理与理解**

JDK 代理基于 `java.lang.reflect.Proxy` 与 InvocationHandler；Spring 已把 CGLIB 重新打包在 spring-core 中。两者最终都进入 Spring 的拦截器链。

**成立条件与边界**

类代理不能增强 final 类、final/private 方法，也受模块和可见性限制；JDK 代理不会暴露实现类独有方法。性能差异不能靠旧经验定胜负，应按可代理性和类型契约选择。

**实际场景（通用工程）**

面向接口注入适合 JDK 代理；必须按具体类注入且方法可覆盖时可使用类代理。

**常见追问**

- 类代理为什么不能代理 final 方法？——子类无法覆盖它。
- JDK 代理对象能强转实现类吗？——不能，代理类型不是目标实现类的子类。

**易错点**

CGLIB 不是“无需任何限制”，JDK 代理也不等于只能拦截抽象接口方法。

## 169. Spring 什么情况下使用 JDK 动态代理？

**面试回答**

在 Spring Framework 默认代理选择中，目标实现至少一个接口且未强制 `proxyTargetClass` 时，通常使用 JDK 动态代理，代理实现目标暴露的接口。

**原理与理解**

调用方持有接口类型，方法调用由 InvocationHandler 进入 Spring Advisor 链。目标类额外的非接口方法不会通过该代理对外暴露。

**成立条件与边界**

Boot 或项目配置可能默认强制类代理，因此不能把“有接口就一定 JDK”当作运行时结论。可通过代理类型、配置和测试确认。

**实际场景（通用工程）**

Service 以接口作为注入契约且保持默认 Framework 策略时可使用 JDK 代理；若代码按实现类注入则可能出现类型不兼容。

**常见追问**

- 如何确认代理类型？——查看 AOP 配置、运行时类型或使用 Spring AOP 工具判断。
- 自调用能否生效？——无论代理类型，普通 self-invocation 都会绕过外层代理。

**易错点**

不要背“Spring Boot 2.x 永远 CGLIB”作为跨版本、跨配置规则。

## 170. Spring 什么情况下使用 CGLIB？

**面试回答**

目标没有可代理接口时，或配置 `proxyTargetClass=true` 强制类代理时，Spring 使用基于 CGLIB 的子类代理。

**原理与理解**

代理子类覆盖可见、非 final 方法，把调用转入拦截器链后再调用目标。Spring 的类代理支持由容器创建和管理，不需要应用单独声明 CGLIB 依赖。

**成立条件与边界**

final 类不能创建子类代理，final/private 方法不能被覆盖；包可见方法还受类加载器包边界影响。Java 模块系统也可能限制代理非开放包中的类型。

**实际场景（通用工程）**

无接口的组件需要事务或监控时可用类代理，但更应先确认方法可见性、自调用和具体类注入的耦合。

**常见追问**

- 有接口也能用 CGLIB 吗？——可以，强制类代理即可。
- CGLIB 能解决自调用吗？——不能，目标内部的 `this` 调用仍不会经过外部代理。

**易错点**

“没有接口只能 CGLIB”只描述代理选择，不代表所有方法都能增强。

## 171. 为什么 Spring 事务可以通过 AOP 实现？

**面试回答**

事务边界通常围绕服务方法，Spring 可由事务拦截器在调用前获取或加入事务，方法正常完成后提交，按回滚规则异常完成时回滚，因此适合代理式 AOP。

**原理与理解**

`@Transactional` 元数据由事务 Advisor 匹配，`TransactionInterceptor` 结合 `PlatformTransactionManager`/响应式事务管理器执行传播、提交和回滚。参与既有事务时并不会每次创建新事务。

**成立条件与边界**

仅通过 Spring 代理进入的方法才适用；自调用、错误异常捕获、传播行为和线程切换都会影响结果。命令式事务通常绑定当前线程，默认回滚规则也不是“遇到任何异常都回滚”。

**实际场景（真实项目边界）**

项目已确认订单主表与明细批量写入使用声明式事务；面试应描述原子性需求，不虚构具体代理类型或事务管理器实现。

**常见追问**

- 为什么内部调用可能失效？——调用没有穿过代理。
- 提交何时发生？——事务拦截器完成方法调用并满足传播与回滚规则后。

**易错点**

不要把实现简化成“关闭自动提交，异常就回滚”；资源管理和传播由事务管理器决定。
