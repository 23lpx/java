# AOP

## 158. 什么是 AOP？

**面试回答**

AOP 是面向切面编程，把散布在多个方法里的公共逻辑（如日志、事务、权限）抽出来，集中定义，再动态织入到目标方法里，实现业务逻辑与横切逻辑分离。

**理解**

传统做法是每个方法里都写一段相同的日志/事务代码，重复且难维护。AOP 把这些「横切关注点」抽成「切面」，在目标方法执行前后统一插入，业务代码里就不用再写。Spring AOP 通过动态代理实现。

**场景**

项目里 @Transactional 事务、@AutoFill 公共字段填充都是 AOP 的典型应用。

**常见追问**

- AOP 和 OOP 什么关系？（AOP 是 OOP 的补充，解决横切逻辑的复用）
- Spring AOP 怎么实现？（动态代理）

**易错点**

AOP 的核心是「把横切逻辑从业务里抽离」，不是「切业务方法本身」。

## 159. AOP 解决什么问题？

**面试回答**

解决横切关注点（如日志、事务、安全）散落在各业务方法里导致的代码重复、难维护、难统一修改的问题。

**理解**

如果每个 Service 方法都手写「开启事务、打日志、鉴权」，同样的代码复制几十遍，改一处要改几十处。AOP 把这些逻辑集中到切面，一处定义、全局生效，业务方法保持纯粹。本质是「关注点分离 + 复用」。

**场景**

项目里如果没有 AOP，每个增删改方法都要手写事务管理；用了 AOP，一个 @Transactional 注解就搞定。

**常见追问**

- AOP 的核心价值？（减少重复、业务与横切逻辑解耦）
- 不改业务代码怎么加日志？（用切面织入）

**易错点**

AOP 主要解决「横切逻辑的重复和侵入」，不是为了替代业务代码。

## 160. 哪些场景适合使用 AOP？

**面试回答**

适合处理「多个方法都要做的、与业务主逻辑无关」的公共逻辑，如事务管理、日志记录、权限校验、性能监控、缓存、公共字段填充。

**理解**

判断标准：这段逻辑是不是在多个方法里重复、且不属于业务主流程。是，就适合抽成切面。事务是经典场景（Spring 声明式事务就是 AOP），日志、鉴权、耗时统计、公共字段填充（如创建时间、创建人）都很典型。

**场景**

项目里 @Transactional 管事务，@AutoFill + AOP 自动填充创建时间/创建人/更新时间，@RestControllerAdvice 也可看作对异常处理的横切。

**常见追问**

- 日志为什么适合 AOP？（跨方法、非业务、重复）
- 事务为什么适合 AOP？（把事务控制从业务里抽出）

**易错点**

别什么逻辑都塞进 AOP，业务主逻辑不该进切面；只抽「横切、重复、非业务」的部分。

## 161. 什么是横切关注点？

**面试回答**

横切关注点是指「横跨多个业务模块、不属于某个业务本身」的公共关注点，如日志、事务、安全，它们分散在多处，形成交叉。

**理解**

「横切」形象地说：业务逻辑是纵向的（每个业务一条线），而日志、事务等逻辑横向穿过所有业务线。这些逻辑不属于任何一个具体业务，却又处处需要，所以叫横切关注点。AOP 就是专门处理它们的手段。

**场景**

项目里事务、日志、鉴权、公共字段填充都是横切关注点，被 AOP 统一处理。

**常见追问**

- 横切关注点举例？（日志、事务、权限、监控、缓存）
- 为什么不直接写进业务方法？（会导致重复、侵入、难维护）

**易错点**

横切关注点的关键特征是「跨多个模块、非业务核心」，理解这个才能判断什么该进切面。

## 162. 什么是 JoinPoint？

**面试回答**

JoinPoint（连接点）是程序执行过程中能被拦截/增强的点，在 Spring AOP 里通常就是「方法的执行」。

**理解**

可以理解成「候选的切入点」——程序里所有可能被织入增强的位置。Spring AOP 只支持方法级别的连接点（方法执行），不像 AspectJ 支持字段、构造器等。切面最终选择其中一些连接点来增强。

**场景**

项目里 Service 的每个方法都是一个 JoinPoint，AOP 可以选择其中带 @Transactional 的方法做增强。

**常见追问**

- Spring AOP 的 JoinPoint 是什么粒度？（方法级别）
- JoinPoint 和 Pointcut 什么关系？（JoinPoint 是所有候选点，Pointcut 是筛选出来的）

**易错点**

Spring AOP 的连接点只到「方法」这一级，不支持字段、构造器连接点。

## 163. 什么是 Pointcut？

**面试回答**

Pointcut（切入点）是一组规则，用来匹配「哪些连接点（方法）要被增强」，本质是筛选条件。

**理解**

JoinPoint 是「所有可能的位置」，Pointcut 是「从中选出要增强的位置」的表达式。比如 `execution(* com.xx.service.*.*(..))` 匹配 service 包下所有方法。切面 = 切入点（在哪切）+ 通知（切进去做什么）。

**场景**

项目里 @AutoFill 的切点表达式匹配自定义注解标注的方法，或按包路径匹配 service 层方法。

**常见追问**

- 常见切入点表达式？（execution、@annotation 等）
- Pointcut 和 Advice 什么关系？（Pointcut 定位置，Advice 定逻辑）

**易错点**

Pointcut 是「筛选条件/匹配规则」，不是「被切的方法」本身；别和 JoinPoint 混淆。

## 164. 什么是 Advice？

**面试回答**

Advice（通知）是「在切入点做什么」的具体增强逻辑，定义了在方法执行前、后或异常时执行的代码。

**理解**

Advice 和 Pointcut 配合：Pointcut 说「在哪里」，Advice 说「干什么」。通知有多种类型（前置、后置、环绕等）。写切面时，@Before、@After、@Around 标注的方法就是 Advice。

**场景**

项目里 @Around 环绕通知里写公共字段填充的逻辑，就是 Advice。

**常见追问**

- Advice 有哪些类型？（@Before、@After、@Around、@AfterReturning、@AfterThrowing）
- @Around 和 @Before 区别？（@Around 能控制是否继续执行目标方法、能改返回值）

**易错点**

Advice 是「增强逻辑」，Pointcut 是「位置规则」，两者缺一不可。

## 165. 常见的通知类型有哪些？

**面试回答**

有五种：前置通知（@Before）、后置通知（@After）、环绕通知（@Around）、返回后通知（@AfterReturning）、异常通知（@AfterThrowing）。

**理解**

@Before 在方法执行前；@After 在方法执行后（无论成功失败）；@AfterReturning 在正常返回后（能拿返回值）；@AfterThrowing 在抛异常后（能拿异常）；@Around 最强大，包住整个方法，能控制是否执行目标方法、能改参数和返回值。@Around 实际可覆盖其他几种的功能。

**场景**

项目里 @AutoFill 用 @Around 或 @Before 在 insert/update 前填充公共字段；事务、日志常用 @Around 做完整控制。

**常见追问**

- @After 和 @AfterReturning 区别？（@After 无论异常都执行，@AfterReturning 只在正常返回后）
- 哪个最灵活？（@Around，能全控）

**易错点**

@After 不管成功失败都执行；@AfterReturning 只在正常返回时执行，别搞混两者时机。

## 166. 什么是 Aspect？

**面试回答**

Aspect（切面）是「切入点 + 通知」的组合，即把「在哪里切」和「切进去做什么」封装在一起的一个模块，通常是一个标注了 @Aspect 的类。

**理解**

切面是 AOP 的核心组织单元：一个 @Aspect 类里，多个 Advice 方法各带自己的 Pointcut 表达式，形成完整的一段横切逻辑。可以说 Pointcut + Advice = Aspect。

**场景**

项目里 AutoFillAspect 类标注 @Aspect，里面定义切入点和环绕通知，实现公共字段自动填充。

**常见追问**

- Aspect、Pointcut、Advice 三者关系？（Aspect = Pointcut + Advice）
- 怎么声明切面？（类上加 @Aspect，通常再配合 @Component 交给 Spring）

**易错点**

@Aspect 只是「声明这是切面」，还要让类成为 Spring 管理的 Bean（如加 @Component）才能生效。

## 167. Spring AOP 底层大致如何实现？

**面试回答**

Spring AOP 基于动态代理：为目标对象生成一个代理对象，调用目标方法时先经过代理，由代理在方法前后织入通知逻辑。

**理解**

Spring 根据目标对象是否实现接口选择代理方式：实现了接口用 JDK 动态代理（基于接口生成代理类），没实现接口用 CGLIB（基于继承生成子类代理）。调用时，代理拦截方法调用，先执行通知链，再调用真正的目标方法。

**场景**

项目里 Service 有接口时用 JDK 动态代理，没有接口时用 CGLIB；事务、@AutoFill 都是通过代理对象生效的。

**常见追问**

- 动态代理有哪两种？（JDK 动态代理、CGLIB）
- 为什么调用代理对象才能触发增强？（通知逻辑在代理里，绕过代理调用原对象不生效）

**易错点**

Spring AOP 靠「代理对象」实现，所以自己 new 的、或内部 this 调用绕过代理时，增强不生效。

## 168. JDK 动态代理和 CGLIB 有什么区别？

**面试回答**

JDK 动态代理基于接口，用 java.lang.reflect.Proxy 生成一个实现同接口的代理类，要求目标类实现接口；CGLIB 基于继承，通过字节码生成目标类的子类作为代理，不要求接口，但目标类和方法不能是 final。

**理解**

JDK 代理是 JDK 自带，只能代理接口方法；CGLIB 是第三方库，通过继承子类覆盖方法实现代理，能代理没有接口的类。CGLIB 不能代理 final 类/final 方法（无法继承/覆盖）。性能上早期 CGLIB 稍快，现在两者接近。

**场景**

项目里 Service 有接口用 JDK 代理，没有接口的类用 CGLIB。

**常见追问**

- 什么情况只能用 CGLIB？（目标类没实现接口）
- CGLIB 的限制？（不能代理 final 类/final 方法）

**易错点**

JDK 代理「必须有接口」，CGLIB 是「继承子类」所以 final 不行，这个本质区别要记牢。

## 169. Spring 什么情况下使用 JDK 动态代理？

**面试回答**

当目标对象实现了接口时，Spring 默认使用 JDK 动态代理，生成一个实现同接口的代理对象。

**理解**

Spring AOP 的默认策略：目标类实现了接口就用 JDK 代理，因为 JDK 代理更轻量、更原生。这也是「面向接口编程」的体现——你注入的是接口类型，Spring 给你接口的代理实现。

**场景**

项目里 Service 定义了接口（如 DishService 接口 + DishServiceImpl 实现类），Spring 就用 JDK 动态代理生成 DishService 的代理。

**常见追问**

- 注入接口时拿到的是什么？（JDK 生成的代理对象）
- 强制用 CGLIB 怎么配？（spring.aop.proxy-target-class=true）

**易错点**

JDK 代理针对「接口」，所以只能代理接口里声明的方法；实现类自己额外的方法不会被代理。

## 170. Spring 什么情况下使用 CGLIB？

**面试回答**

当目标对象没有实现接口时，Spring 使用 CGLIB 生成目标类的子类作为代理；另外如果配置了强制用 CGLIB（proxy-target-class=true），即使有接口也用 CGLIB。

**理解**

没有接口就无从做 JDK 代理，只能靠 CGLIB 继承子类覆盖方法。Spring Boot 2.x 里默认策略调整为优先 CGLIB（proxy-target-class 默认 true），所以很多场景即使有接口也可能用 CGLIB。要注意 CGLIB 无法代理 final 类/final 方法。

**场景**

项目里没有接口的普通类要做 AOP（如某些工具类、无接口 Service），用 CGLIB。

**常见追问**

- Spring Boot 2.x 默认用哪种？（默认 proxy-target-class=true，倾向 CGLIB）
- CGLIB 有什么限制？（final 类/方法无法代理）

**易错点**

注意版本差异：传统 Spring 默认「有接口用 JDK」，Spring Boot 2.x 默认倾向 CGLIB；final 方法无法被 CGLIB 代理。

## 171. 为什么 Spring 事务可以通过 AOP 实现？

**面试回答**

因为事务管理是典型的横切逻辑：开启事务、提交/回滚这些操作，可以环绕在业务方法执行前后，正好用 AOP 的环绕通知在方法前后统一织入。

**理解**

@Transactional 标注的方法，Spring 生成代理对象，在方法执行前开启事务（获取连接、关闭自动提交），方法正常执行完提交，抛异常则回滚。这套「执行前开事务 + 执行后提交/回滚」的流程就是环绕通知的逻辑，和业务代码完全解耦，所以天然适合 AOP。

**场景**

项目里 Service 方法加 @Transactional 后，Spring 用 AOP 代理在方法前后管理事务，业务代码里不用写任何事务控制。

**常见追问**

- @Transactional 靠什么生效？（AOP 动态代理）
- 为什么自己 new 的对象或内部 this 调用事务不生效？（绕过了代理）

**易错点**

事务靠 AOP 代理实现，所以「代理是否生效」直接决定事务是否生效——这是理解事务失效问题的关键。
