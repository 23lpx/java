# 参数校验

## 142. 为什么后端需要参数校验？

**面试回答**

后端位于信任边界，必须独立验证输入的结构、格式、范围和业务前置条件；前端校验只能改善体验，不能约束绕过页面的客户端。

**原理与理解**

校验应分层：Bean Validation 处理 DTO 的声明式约束，业务层验证库存、状态迁移等规则，数据库约束守住最终一致性。失败应返回稳定错误并避免把无效数据传入更深层。

**成立条件与边界**

参数校验不等于完整安全防护：SQL 注入主要靠参数化查询，越权靠认证授权，竞态靠事务和并发控制。客户端传入的 ID 即使格式合法，也不能证明它有访问权限。

**实际场景（通用工程）**

下单请求先校验数量、地址 ID 和明细集合，再在事务中核验资源存在性、归属、价格状态和库存。

**常见追问**

- 前后端都校验是否重复？——规则可以共享，但后端必须独立执行。
- 数据库约束还需要吗？——需要，应用校验无法覆盖并发和旁路写入。

**易错点**

不要说参数校验能直接“防 SQL 注入和越权”，这是不同控制措施。

## 143. `@Valid` 有什么作用？

**面试回答**

`@Valid` 是 Jakarta Validation 的级联/触发标记。在 Spring MVC 中，把它放在 `@RequestBody`、`@ModelAttribute` 等参数上，可让数据绑定后按对象约束执行校验；放在字段上可递归校验嵌套对象。

**原理与理解**

`@NotNull`、`@Size` 等声明约束，Validator 负责执行。Spring 的 `@Validated` 还支持校验组，并可用于方法级校验场景。

**成立条件与边界**

校验失败不只有 `MethodArgumentNotValidException`：请求体对象、模型绑定、方法参数约束等可能产生不同异常，如 `HandlerMethodValidationException`。是否触发还取决于校验实现和 MVC 配置。

**实际场景（通用工程）**

`@RequestBody @Valid CreateOrderRequest` 校验请求 DTO；DTO 内的明细集合元素还需在相应字段上使用 `@Valid` 才会级联校验。

**常见追问**

- `@Valid` 与 `@Validated` 区别？——前者是 Jakarta 标准；后者是 Spring 注解并支持组提示等。
- 如何校验嵌套对象？——在嵌套属性上标记 `@Valid` 并声明子对象约束。

**易错点**

“字段有约束 + Controller 有 @Valid 就覆盖所有业务规则”不成立。

## 144. `@NotNull`、`@NotBlank`、`@NotEmpty` 有什么区别？

**面试回答**

`@NotNull` 只要求值非 null；`@NotEmpty` 适用于 CharSequence、Collection、Map 或数组，要求非 null 且大小大于 0；`@NotBlank` 适用于 CharSequence，要求非 null 且至少包含一个非空白字符。

**原理与理解**

对字符串而言，`""` 能通过 `@NotNull`，不能通过 `@NotEmpty`；只含空白的字符串能否通过 `@NotEmpty` 取决于长度，因此通常能通过，但不能通过 `@NotBlank`。

**成立条件与边界**

三者不能对所有类型简单理解成严格程度递增。数值范围使用 `@Min`/`@Positive` 等，集合容量使用 `@Size`，并要考虑 Unicode 空白与业务规范化策略。

**实际场景（通用工程）**

名称使用 `@NotBlank`，明细数组使用 `@NotEmpty`，关联对象只要求存在时使用 `@NotNull`；随后仍需校验长度、范围和归属。

**常见追问**

- 集合元素本身如何校验？——使用容器元素约束或配合 `@Valid`。
- `@Size(min=1)` 与 `@NotEmpty`？——都可约束非空大小，前者还能表达上下限。

**易错点**

`@NotBlank` 不是给任意对象用的，也不要把“去掉普通空格”当作完整规范定义。

## 145. 参数校验失败后如何统一处理？

**面试回答**

使用 `@RestControllerAdvice`/`@ExceptionHandler` 或继承 `ResponseEntityExceptionHandler`，针对不同校验异常提取字段、对象或方法参数错误，映射为稳定的 HTTP 状态和错误结构。

**原理与理解**

请求体 Bean 校验常形成 `MethodArgumentNotValidException`；模型绑定可能形成绑定类异常；方法级约束可能形成 `HandlerMethodValidationException`。错误对象中包含字段路径、约束消息和 rejected value 等信息。

**成立条件与边界**

不要假设永远只有一个 `FieldError`，对象级约束也没有简单字段名。错误响应不应回显密码、Token 或完整敏感输入；消息国际化和错误码应与客户端契约分离。

**实际场景（项目核验项）**

项目已确认有统一异常响应能力；需核对当前实际捕获的校验异常类型、是否返回全部错误及 HTTP 状态，不能直接扩写成完整方案。

**常见追问**

- 返回第一个还是全部错误？——由接口契约决定，并考虑客户端体验与响应大小。
- 为什么不在 Controller 手写判断？——声明式约束和集中映射可减少重复，但业务规则仍应在业务层。

**易错点**

统一处理不等于把所有校验失败包装成 HTTP 200，也不等于把框架异常原文直接返回。

## 146. 为什么不能完全依赖前端校验？

**面试回答**

客户端处于不可信边界，用户可修改脚本、重放请求、直接调用接口或使用旧版本客户端；因此后端必须对每个受保护入口执行自己的校验和授权。

**原理与理解**

前端快速提示格式问题并减少无效请求，后端保证系统不接受非法状态。规则可能通过接口 Schema、生成代码或共享规范保持一致，但执行责任不能外包给客户端。

**成立条件与边界**

后端校验也不是单点万能方案：跨字段与资源状态属于业务校验，唯一性与引用完整性还需数据库约束，并发下要依靠原子更新或事务。

**实际场景（通用工程）**

页面限制数量为正数，接口仍校验范围；服务端再核对订单归属和商品状态，数据库保留关键约束。

**常见追问**

- 前端校验还有价值吗？——有，提供即时反馈并节省无效网络请求。
- 多个入口如何避免规则漂移？——把核心规则集中在服务/领域层，并用契约和测试约束各客户端。

**易错点**

“前端可绕过”只是起点，后端还要区分格式校验、业务校验、授权和持久化约束。
