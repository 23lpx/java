# 参数校验

## 142. 为什么后端需要参数校验？

**面试回答**

因为不能信任前端传来的数据，攻击者或异常客户端可以绕过前端直接调用接口传非法数据，后端校验是保证数据合法、安全、符合业务规则的最后一关。

**理解**

前端校验只是体验优化，可以被绕过（改请求、用工具直接调接口）。后端校验才是数据安全的关键：防止空值、越界、非法格式、SQL 注入等。不做后端校验，脏数据会进库、业务会出错甚至出安全问题。

**场景**

项目里新增菜品、下单时，后端用 @Valid + 校验注解校验必填字段、价格范围等，拦截非法输入。

**常见追问**

- 只做前端校验行不行？（不行，前端可被绕过）
- 后端校验主要防什么？（非法/恶意数据、脏数据入库）

**易错点**

前端校验和后端校验「职责不同、缺一不可」，后端校验才是兜底的安全保障。

## 143. `@Valid` 有什么作用？

**面试回答**

@Valid 用于在 Controller 方法参数上触发校验，告诉 Spring 对这个参数对象按类里的校验注解（如 @NotNull）做校验，不通过则抛出异常。

**理解**

@Valid 是 JSR-303/380 的校验触发入口。对象字段上加 @NotNull、@Size 等注解只是「声明规则」，还要在参数上用 @Valid 才能真正触发校验。校验失败会抛出 MethodArgumentNotValidException，通常配合全局异常处理返回友好提示。

**场景**

项目里 `public Result save(@RequestBody @Valid DishDTO dishDTO)`，校验 dishDTO 里的必填字段，失败统一由 @RestControllerAdvice 处理。

**常见追问**

- @Valid 和 @Validated 什么区别？（@Valid 是标准注解；@Validated 是 Spring 的，支持分组校验）
- 校验失败抛什么异常？（MethodArgumentNotValidException）

**易错点**

只加校验注解不加 @Valid 不会触发校验，这两步缺一不可。

## 144. `@NotNull`、`@NotBlank`、`@NotEmpty` 有什么区别？

**面试回答**

@NotNull 只校验「不能为 null」；@NotEmpty 校验「不能为 null 且不能为空」（字符串长度、集合大小 > 0）；@NotBlank 校验「不能为 null 且去掉空格后不能为空」（针对字符串）。

**理解**

三者严格程度递增（针对字符串）：@NotNull 允许空字符串 ""；@NotEmpty 不允许 "" 但允许 " "（纯空格）；@NotBlank 连 " " 都不允许。集合类用 @NotEmpty，字符串「非空且非纯空格」用 @NotBlank，只判 null 用 @NotNull。

**场景**

项目里用户名、菜品名称用 @NotBlank（不能是纯空格），必填列表用 @NotEmpty，可空字段只在需要时用 @NotNull。

**常见追问**

- 空字符串 "" 和 null 一样吗？（不一样，null 是没值，"" 是空字符串）
- 校验集合元素个数用什么？（@Size 或 @NotEmpty）

**易错点**

@NotBlank 只适用于字符串；@NotEmpty 可用于字符串、集合、Map；@NotNull 最宽松，只挡 null。

## 145. 参数校验失败后如何统一处理？

**面试回答**

用全局异常处理器（@RestControllerAdvice + @ExceptionHandler）捕获 MethodArgumentNotValidException，从中取出校验错误信息，统一返回规范的错误响应。

**理解**

校验失败会抛 MethodArgumentNotValidException，里面包含 BindingResult 和所有字段错误。全局异常处理器捕获后，遍历 FieldError 取出字段名和 message，组装成统一的 Result 返回给前端。这样不用在每个接口里写 try-catch。

**场景**

项目里 @RestControllerAdvice 全局异常处理中专门处理 MethodArgumentNotValidException，把「菜品名不能为空」这类信息友好返回。

**常见追问**

- 错误信息从哪取？（从 BindingResult 的 FieldError 里）
- 为什么用全局异常处理？（避免每个接口重复处理，统一返回格式）

**易错点**

校验失败默认返回的是框架的 400 错误，要做「友好提示」得自己用全局异常处理转成统一结构。

## 146. 为什么不能完全依赖前端校验？

**面试回答**

因为前端校验可以被绕过——用户能直接构造 HTTP 请求、改参数、用接口工具调用后端，前端校验根本不会执行；后端校验才是数据安全的最终保障。

**理解**

前端校验只对「正常用户」起提示作用，对恶意用户完全无效。后端必须独立校验，因为后端是数据的最终入口，只有在这里拦截才能保证入库数据合法。正确做法是「前端校验做体验 + 后端校验做安全」。

**场景**

项目里前端虽然也做了表单校验，但后端接口仍用 @Valid 再校验一遍，防止有人绕过页面直接调接口传非法数据。

**常见追问**

- 前端校验的主要价值是什么？（提升用户体验，减少无效请求）
- 后端校验能防什么？（非法数据入库、越权、注入等安全风险）

**易错点**

「前端已经校验了所以后端不用」是危险想法；前后端校验各司其职，后端才是兜底。
