# Spring事务

## 182. 什么是数据库事务？

**面试回答**

数据库事务是一组作为一个逻辑工作单元执行的操作。事务最终只有提交或回滚：提交后整组修改生效，失败时回滚已执行的修改，用于在并发和故障条件下维护数据正确性。

**原理与理解**

事务由数据库提供，通常通过 `BEGIN/START TRANSACTION`、`COMMIT`、`ROLLBACK` 划定边界。Spring 事务不是另一套数据库事务，而是替业务代码管理底层数据库事务的开启、提交和回滚。

**成立条件与边界**

只有同一事务管理器覆盖、且实际参与事务的资源操作才能一起回滚。普通本地事务不能原子回滚已经成功的远程 HTTP 调用、消息发送或另一个独立数据源；这些场景需要幂等、补偿、事务消息等一致性方案。

**实际场景（真实项目）**

项目下单时先写订单主表，利用主键回填得到订单 ID，再批量写入订单明细。两步放在同一个事务中，明细写入失败时主表也回滚。

**常见追问**

- Spring 事务和数据库事务是什么关系？（Spring 管理底层资源事务的边界）
- 一个本地事务能回滚支付宝调用吗？（不能）

**易错点**

“放进一个 Java 方法”不等于“处于同一个数据库事务”，还要确认代理、事务管理器、数据源和异常回滚规则都生效。

## 183. 事务的 ACID 四大特性是什么？

**面试回答**

ACID 分别是原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）和持久性（Durability）：事务要么整体完成要么整体撤销；前后都满足约束；并发影响受隔离级别控制；提交结果在规定的故障模型下能够保留。

**原理与理解**

四个特性关注不同问题：原子性处理部分成功；一致性描述正确状态；隔离性处理并发可见性和冲突；持久性处理提交后的故障恢复。以 InnoDB 为例，事务、锁/MVCC、undo/redo、刷盘配置和恢复机制共同参与实现。

**成立条件与边界**

ACID 不是“数据库自动保证所有业务永远正确”。数据库约束只能保护已表达的规则，跨系统业务约束仍需应用设计；隔离和持久性强度也受隔离级别、数据库配置及硬件条件影响。

**实际场景（通用工程）**

转账既要保证扣款与入账原子完成，也要保证余额规则成立、并发更新不丢失、提交后故障恢复不丢账。

**常见追问**

- 一致性是手段还是目标？（通常理解为事务前后保持合法状态的目标）
- ACID 是否只靠某一类日志实现？（不是，多种机制共同实现）

**易错点**

不要把“隔离性”背成任何级别下都完全串行，也不要把“一致性”简化成“数据没有变化”。

## 184. 什么是原子性？

**面试回答**

原子性指一个事务中的操作作为整体提交或整体回滚，不允许只保留其中一部分修改。

**原理与理解**

数据库记录事务修改，并在回滚或故障恢复时撤销未提交效果。以 InnoDB 为例，undo log 支持回滚和多版本读取，但原子性是事务机制整体提供的，不宜回答成“只靠一份日志”。

**成立条件与边界**

原子性的范围受事务边界限制。数据库回滚只能撤销纳入该事务的数据库修改，不能自动撤回已发送短信、已完成支付或已被消费者处理的消息。

**实际场景（真实项目）**

订单主表插入成功、明细批量插入失败时，整个下单事务回滚，避免留下没有明细的订单。

**常见追问**

- 原子性和幂等有什么区别？（原子性保证一次事务不部分提交；幂等保证重复执行不产生额外副作用）
- 回滚能撤销远程调用吗？（不能）

**易错点**

不要说“事务执行期间其他线程绝对看不到任何变化”，那属于隔离级别讨论，不是原子性的定义。

## 185. 什么是一致性？

**面试回答**

一致性指事务把数据从一个满足约束的合法状态转换到另一个合法状态。数据库约束、正确的业务逻辑以及原子性、隔离性和持久性共同帮助实现它。

**原理与理解**

一致性包含数据库层规则和业务层不变量。例如唯一键、非空约束可以由数据库验证，而“订单总额等于明细金额之和”通常还依赖应用正确计算并在合适的事务与并发控制下写入。

**成立条件与边界**

事务不会修复错误的业务代码。即使所有 SQL 都成功提交，如果金额计算公式写错，事务仍然可以原子地提交一组错误数据。跨服务的一致性也不能仅靠单库本地事务保证。

**实际场景（真实项目）**

创建订单时，主表中的订单 ID 与每条明细的外键关联必须一致；主表和明细应在同一事务内完成写入。

**常见追问**

- 一致性由数据库自动保证吗？（只保证已定义的数据库规则，业务规则还依赖应用设计）
- 一致性与隔离性有什么区别？（前者关注合法状态，后者关注并发影响）

**易错点**

不要把一致性说成“事务前后数据完全一样”；合法的事务本来就会改变数据。

## 186. 什么是隔离性？

**面试回答**

隔离性描述并发事务之间的可见性和相互影响。数据库通过隔离级别、MVCC 和锁等机制控制脏读、不可重复读、幻读以及写冲突。

**原理与理解**

隔离不是只有“有”或“没有”。标准隔离级别从 `READ UNCOMMITTED`、`READ COMMITTED`、`REPEATABLE READ` 到 `SERIALIZABLE` 逐步增强；不同数据库的具体实现和异常现象可能不同。

**成立条件与边界**

较高隔离级别通常减少并发异常，但可能增加锁等待、冲突或重试成本。MVCC 主要优化读写并发，不能自动解决所有业务竞争；库存扣减等写场景仍需要条件更新、锁或其他并发控制。

**实际场景（通用工程）**

两个请求同时领取最后一张优惠券时，仅依赖“先查还有库存、再扣减”可能超发；可使用带库存条件的原子更新并检查受影响行数。

**常见追问**

- 隔离级别越高一定越好吗？（不一定，要权衡正确性和并发成本）
- MVCC 能否解决所有并发写问题？（不能）

**易错点**

“一个事务的中间状态对其他事务永远不可见”并非所有隔离级别都成立，`READ UNCOMMITTED` 就允许脏读。

## 187. 什么是持久性？

**面试回答**

持久性指事务成功提交后，其结果在数据库承诺的故障模型和配置下不会因进程崩溃、重启等故障而丢失。

**原理与理解**

以 InnoDB 为例，redo log、刷盘策略和崩溃恢复共同参与保证已提交修改可恢复。数据页不必在提交瞬间全部落盘，数据库可先持久化日志，再在恢复时重做。

**成立条件与边界**

持久性不是“任何灾难下绝不丢数据”。刷盘参数、操作系统与存储设备缓存、复制策略、硬件故障和备份策略都会影响保障范围。提交成功也不代表远端副本已同步完成，除非系统明确提供这种承诺。

**实际场景（通用工程）**

订单事务提交后数据库进程异常重启，恢复流程应能依据持久化日志还原已提交订单，而清理未提交修改。

**常见追问**

- 持久性是否等于每次提交都把全部数据页直接写盘？（不等于，可依赖日志恢复）
- 备份是否仍有必要？（有，持久性不能替代灾备）

**易错点**

不要把持久性描述成脱离配置和硬件的绝对保证，也不要说未提交事务崩溃后“正常提交”。

## 188. `@Transactional` 有什么作用？

**面试回答**

`@Transactional` 声明类或方法需要事务语义。Spring 在调用进入事务拦截器后，根据传播行为获取或创建事务，方法正常完成时尝试提交；发生匹配回滚规则的异常或事务被标记为 rollback-only 时回滚。

**原理与理解**

注解本身只是事务元数据。默认配置下，传播行为是 `REQUIRED`、隔离级别是数据库默认值、事务为读写，并且 `RuntimeException` 和 `Error` 触发回滚，受检异常默认不触发回滚。

**成立条件与边界**

它必须由 Spring 事务基础设施解析，目标通常应是容器中的 Bean，并且调用要经过代理。事务最终提交也可能因约束冲突、连接故障或 rollback-only 标记而失败，因此“方法正常返回”不等于数据库提交必然成功。

**实际场景（真实项目）**

项目在订单创建的 Service 方法上声明事务，把主表写入、主键回填后的明细组装和批量插入放在同一事务边界内。

**常见追问**

- 注解本身会开启事务吗？（不会，需要事务管理基础设施）
- 默认回滚哪些异常？（`RuntimeException` 和 `Error`）

**易错点**

不要只背“正常提交、异常回滚”；异常类型、是否经过代理、是否被吞掉和传播行为都会改变结果。

## 189. 什么是 Spring 声明式事务？

**面试回答**

声明式事务是通过 `@Transactional` 或 XML 配置描述事务属性，由 Spring 在业务调用外围统一完成事务管理；编程式事务则由业务代码直接使用 `TransactionTemplate` 或事务管理器控制边界。

**原理与理解**

声明式方式把传播行为、隔离级别、超时、只读提示和回滚规则作为元数据，与重复的开启、提交、回滚代码分离。默认代理模式使用 Spring AOP 的事务拦截器应用这些规则。

**成立条件与边界**

声明式事务更简洁，但边界藏在代理和配置中，需要用集成测试验证真实提交/回滚。极细粒度或动态边界可考虑 `TransactionTemplate`，但不应在业务代码里随意混用多套边界。

**实际场景（通用工程）**

一个 Service 用例需要依次写两张表时，可在入口方法声明事务；若批处理要求每 100 条独立提交，则可能更适合显式划分多个事务模板回调。

**常见追问**

- 声明式事务和编程式事务的差别？（元数据驱动 vs 代码显式控制）
- 声明式事务是否完全不需要理解事务边界？（不是）

**易错点**

“代码里没有 `commit`”不代表不需要设计边界；长事务、远程调用和错误传播仍由开发者负责。

## 190. Spring 声明式事务大致是怎么实现的？

**面试回答**

默认 `proxy` 模式下，Spring 为 Bean 创建代理，调用进入事务拦截器后读取事务属性，通过 `PlatformTransactionManager` 获取或创建事务，再执行目标方法并按结果提交或回滚。

**原理与理解**

命令式事务通常与当前执行线程绑定，使同一线程中的数据访问代码取得同一事务资源。传播行为决定复用、挂起还是创建物理事务；事务管理器负责适配 JDBC、JPA 等底层资源。

**成立条件与边界**

只有从代理外部进入的调用才会被默认代理模式拦截。当前线程的事务上下文不会自动传播到方法中新启动的线程；`@Async` 或线程池任务需要重新设计事务边界。响应式事务则使用 Reactor Context，不能套用线程绑定结论。

**实际场景（通用工程）**

Controller 调用注入的 Service 代理，代理开启事务后再执行 Mapper 操作；若 Service 在方法中把第二次写库提交给线程池，该子线程不会自动加入原事务。

**常见追问**

- `PlatformTransactionManager` 做什么？（统一事务获取、提交和回滚协议）
- 新线程会继承当前事务吗？（命令式事务通常不会）

**易错点**

“关闭自动提交并绑定连接”是 JDBC 本地事务的一种典型实现，不应当作所有事务管理器和响应式事务的唯一实现。

## 191. 为什么 `@Transactional` 通常加在 Service 层？

**面试回答**

因为事务边界通常应对应一个完整业务用例。Service 方法负责协调多个数据访问操作，最适合定义“这些修改必须一起提交或回滚”的范围。

**原理与理解**

如果每个 DAO 方法各自提交，一个业务步骤中的多次写入就可能部分成功；如果把事务放到 Controller，又会让传输层承担业务一致性职责，并容易把参数解析、网络等待等无关工作纳入长事务。

**成立条件与边界**

“通常”不是强制规则。事务应尽量短，只覆盖必要的数据一致性操作；不要为了层次形式把耗时远程调用、文件上传或等待用户交互长期包在数据库事务中。

**实际场景（真实项目）**

项目的下单 Service 方法同时完成订单主表和明细表写入，因此事务声明在业务入口，而不是分别声明在每个 Mapper 操作上。

**常见追问**

- Controller 能加事务吗？（技术上可以，但通常不是合适的业务边界）
- 为什么不把远程支付调用放进长事务？（本地事务回滚不了远程结果，还会长期占用连接和锁）

**易错点**

真正原则是“事务边界与一致性边界匹配”，不是机械地认为所有 Service 方法都必须加事务。

## 192. Spring 默认哪些异常会触发回滚？

**面试回答**

在没有自定义回滚规则时，Spring 的 `@Transactional` 默认对 `RuntimeException` 及其子类和 `Error` 回滚，对普通受检异常默认不回滚。

**原理与理解**

事务拦截器在目标方法向外抛出异常后匹配回滚规则。可以用 `rollbackFor`、`noRollbackFor` 及其类名形式覆盖默认行为；规则冲突时采用匹配程度更强的规则。

**成立条件与边界**

这里说的是 Spring 传统默认规则，不是 Java 或数据库的通用规则。Spring 6.2 起可以全局配置对所有异常回滚，但若项目没有显式开启，不能默认认为已经改变。异常还必须到达事务拦截器，吞掉异常不会触发自动判断。

**实际场景（通用工程）**

业务方法写库后抛出 `IllegalStateException`，默认会回滚；若抛出自定义受检异常，则需配置回滚规则或采用项目统一的异常策略。

**常见追问**

- `Exception` 都默认回滚吗？（不是，受检异常默认不回滚）
- 可以全局修改默认规则吗？（Spring 6.2 起支持，但要显式配置）

**易错点**

不要把“运行时异常”误说成“运行期间出现的所有异常”；它特指 `RuntimeException` 类型体系。

## 193. Checked Exception 默认会回滚吗？

**面试回答**

传统默认配置下不会。受检异常从事务方法向外抛出时，Spring 默认仍尝试提交；如需回滚，应配置类型安全的 `rollbackFor`，或统一调整项目默认回滚策略。

**原理与理解**

例如 `@Transactional(rollbackFor = IOException.class)` 会让 `IOException` 及其子类触发回滚。是否声明 `throws` 不决定回滚，真正决定因素是运行时抛出的异常类型和匹配到的事务规则。

**成立条件与边界**

`SQLException` 在 Spring 数据访问体系中通常会被转换为 `DataAccessException`，后者是运行时异常，所以不能用“JDBC 有受检异常”直接推断 Spring 方法一定不回滚。还要看实际抛到代理层的类型。

**实际场景（通用工程）**

订单写库后调用一个声明抛出 `IOException` 的本地文件操作，如果异常需要使数据库回滚，应明确设置 `rollbackFor = IOException.class`；更重要的是评估文件操作与数据库是否真的能形成一致边界。

**常见追问**

- `throws Exception` 会自动让事务回滚吗？（不会）
- `SQLException` 在 Spring 中一定作为受检异常抛出吗？（不一定，常被转换成 `DataAccessException`）

**易错点**

不要只看方法签名判断回滚，要看最终逃逸出事务方法的实际异常类型和配置规则。

## 194. `rollbackFor` 有什么作用？

**面试回答**

`rollbackFor` 用异常 `Class` 指定额外的回滚规则，常用于让受检异常也触发回滚，例如 `@Transactional(rollbackFor = IOException.class)`。

**原理与理解**

类型规则会匹配指定异常及其子类，具有类型安全性。`noRollbackFor` 用于声明某些异常不回滚；`rollbackForClassName` 使用名称模式匹配，可能误匹配相似类名，通常优先使用基于 `Class` 的规则。

**成立条件与边界**

`rollbackFor = Exception.class` 会把范围扩展到大多数异常，但不意味着任何失败信号都会回滚：被捕获的异常、返回错误码、异步线程中的异常仍需单独处理。也不要为了省事掩盖异常分类设计。

**实际场景（通用工程）**

业务约定某个受检异常表示当前用例整体失败时，可将该具体异常配置到 `rollbackFor`，并让它继续抛到代理层。

**常见追问**

- `rollbackFor` 和 `noRollbackFor` 的区别？（指定回滚 vs 指定不回滚）
- 为什么优先写异常 Class？（类型安全，避免字符串模式误匹配）

**易错点**

`rollbackFor` 不是“手动执行回滚”，而是告诉事务拦截器在何种异常逃逸时标记回滚。

## 195. 把异常 catch 住为什么可能导致事务不回滚？

**面试回答**

如果事务方法内部捕获了异常并正常返回，事务拦截器看不到需要回滚的异常，就会按正常路径尝试提交。应当让异常继续抛出，或在确有必要时显式把当前事务标记为 rollback-only。

**原理与理解**

声明式回滚判断发生在代理调用边界。`catch` 本身不会必然导致提交；关键在于捕获后是否重新抛出匹配规则的异常、底层是否已经把事务标记为 rollback-only，以及后续是否又发生异常。

**成立条件与边界**

如果底层参与者已将共享事务标记为 rollback-only，即使外层捕获异常后正常结束，最终提交时也会回滚，并可能抛出 `UnexpectedRollbackException`。因此不能把结论简化为“只要 catch 就一定提交”。

**实际场景（通用工程）**

批量写入失败后仅记录日志并返回“成功”，可能提交之前已经完成的写入；如果业务要求整批失败，应重新抛出异常或明确标记回滚。

**常见追问**

- 捕获后如何保证回滚？（重新抛出，或谨慎调用 `setRollbackOnly()`）
- catch 后一定提交吗？（不一定，还要看 rollback-only 状态和后续结果）

**易错点**

不要为了回滚而在 catch 中丢失原异常；重新抛出时应保留 cause，便于定位真实故障。

## 196. 同一个类内部调用另一个事务方法为什么可能失效？

**面试回答**

默认代理模式只拦截从代理外部进入的方法调用。同类方法通过 `this` 调用另一个带 `@Transactional` 的方法时绕过代理，因此内层方法自己的传播、隔离和回滚配置不会被应用。

**原理与理解**

事务增强位于代理对象，而 `this` 指向目标对象本身。若外层方法没有事务，内层注解不会凭空开启事务；若外层方法已有事务，内层代码通常仍运行在外层事务中，但不是因为内层注解生效。

**成立条件与边界**

这是默认 `proxy` 模式的语义。AspectJ 编织模式可以拦截自调用，但需要额外配置。工程上更清晰的做法通常是重构 Bean 边界，让调用经过另一个受 Spring 管理的 Bean；自注入或 `AopContext` 会增加耦合，应谨慎使用。

**实际场景（通用工程）**

非事务方法 `create()` 直接调用本类中标注 `REQUIRES_NEW` 的 `saveAudit()`，并不会创建新事务；将审计逻辑移动到独立 Bean 后，从代理调用才能应用该传播行为。

**常见追问**

- 外层已有事务时，内层代码完全没有事务吗？（不是，可能参与外层事务，但内层注解未生效）
- 推荐怎么解决？（优先重构到另一个 Bean）

**易错点**

准确说法是“自调用没有触发内层事务拦截”，不是笼统地说“内层所有 SQL 一定无事务”。

## 197. private 方法上的 `@Transactional` 为什么通常不生效？

**面试回答**

在默认代理模式下，`private` 方法不能成为代理可拦截的外部调用，因此其 `@Transactional` 不会建立独立事务边界。事务入口应放在可被代理调用的 Bean 方法上。

**原理与理解**

JDK 接口代理只能代理接口公开方法；类代理也不能通过覆盖拦截 `private` 方法。并且业务代码通常只能从同类内部调用该 private 方法，又会遇到自调用绕过代理。

**成立条件与边界**

“事务方法必须永远是 public”也不完全准确：Spring 6 起，类代理默认可以处理 `protected` 和包可见方法；接口代理要求方法是接口上的 public 方法。为兼容不同代理方式，业务入口使用 public 仍是最稳妥的约定。AspectJ 模式另当别论。

**实际场景（通用工程）**

把 `@Transactional` 写在 Service 的 private 辅助方法上，再由 public 方法直接调用，不会让辅助方法单独开启事务；应把事务声明在 public 业务入口或重构 Bean 边界。

**常见追问**

- protected 方法一定不生效吗？（不一定，Spring 6+ 类代理可支持；接口代理不支持）
- final 方法呢？（类代理无法覆盖 final 方法，应避免作为依赖类代理的事务入口）

**易错点**

回答时要限定“默认代理模式”和 Spring 版本，不要把旧版本的 public-only 经验当成所有场景的绝对规则。

## 198. 什么是事务传播行为？

**面试回答**

事务传播行为规定一个被事务拦截的方法在调用链上遇到已有事务时，是加入、挂起、新建、使用保存点，还是在无事务状态下执行。默认是 `REQUIRED`。

**原理与理解**

常见行为：`REQUIRED` 有则加入、无则新建；`REQUIRES_NEW` 挂起外层并使用独立物理事务；`NESTED` 通常在一个物理事务中使用保存点；`SUPPORTS` 有则加入、无则非事务执行。其余还有 `MANDATORY`、`NOT_SUPPORTED`、`NEVER`。

**成立条件与边界**

传播行为只有在调用经过事务拦截器时才会应用，自调用会绕过。`REQUIRES_NEW` 需要额外连接，使用不当可能耗尽连接池；`NESTED` 依赖事务管理器和底层保存点能力，不能简单等同于独立新事务。

**实际场景（通用工程）**

核心订单写入通常使用 `REQUIRED` 保持同生共死；若审计记录必须独立提交，可评估 `REQUIRES_NEW`，但要接受它可能在外层回滚后仍保留，并评估连接池容量。

**常见追问**

- `REQUIRES_NEW` 和 `NESTED` 的核心区别？（独立物理事务 vs 通常使用同一物理事务的保存点）
- 传播行为能跨远程服务吗？（Spring 本地声明式事务上下文不会自动跨远程调用）

**易错点**

不要只背七个枚举名称；要能说明物理事务、资源占用、提交独立性和代理调用条件。

## 199. `Propagation.REQUIRED` 是什么意思？

**面试回答**

`REQUIRED` 是默认传播行为：当前存在事务就加入，没有事务就创建一个。多个被拦截的 `REQUIRED` 方法通常映射到同一个物理事务，因此整体提交或回滚。

**原理与理解**

每个方法可以形成自己的逻辑事务范围，但加入同一物理事务后共享最终结果。内层范围把事务标记为 rollback-only 时，外层即使捕获异常并尝试提交，也不能把物理事务提交成功。

**成立条件与边界**

外层不知道事务已被标记回滚时，提交阶段会收到 `UnexpectedRollbackException`，避免调用者误以为已经提交。内层声明的隔离级别、超时和只读属性在加入既有事务时通常不会创建新物理事务来重新生效。

**实际场景（真实项目）**

下单业务入口和其调用的数据写入逻辑使用同一个 `REQUIRED` 事务，主表或明细任一步失败都使整个事务无法提交。

**常见追问**

- `REQUIRED` 和 `REQUIRES_NEW` 的区别？（加入既有事务 vs 总是独立新建物理事务）
- 什么情况下出现 `UnexpectedRollbackException`？（共享事务已被内层标记回滚，外层仍尝试提交）

**易错点**

“内层异常被外层 catch 住”不保证外层能提交；要检查共享事务是否已经被标记为 rollback-only。

## 200. 项目中为什么主表和子表写入需要放在同一个事务中？

**面试回答**

订单主表和明细表共同构成一个业务聚合，必须保证同时成功或同时失败。放在同一个本地事务中，可以避免主表已提交而明细缺失等部分成功状态。

**原理与理解**

典型流程是先插入订单主表并回填主键，再把该主键写入每条明细并批量插入。任一步抛出匹配回滚规则的异常，事务都应回滚；数据库外键只能限制部分非法关系，不能代替完整业务事务。

**成立条件与边界**

两次写入必须由同一事务管理器管理并落到同一事务资源，调用也要经过有效的事务入口。批量插入返回值、异常转换和回滚规则需要测试。若主子表分属不同数据库，单库本地事务不能直接保证原子性。

**实际场景（真实项目）**

项目创建订单时完成主键回填和订单明细批量插入，并使用 Spring 事务保证主表、子表写入的原子性。这是可以基于项目真实经历展开的面试场景。

**常见追问**

- 为什么先写主表？（需要取得主键作为明细关联键）
- 外键约束能否替代事务？（不能，外键不保证整组业务操作同时成功）

**易错点**

不要只说“加了注解所以安全”，还应说明代理入口、异常传播、同一数据源/事务管理器以及主键回填是否正确。
