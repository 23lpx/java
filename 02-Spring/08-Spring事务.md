# Spring事务

## 182. 什么是数据库事务？

**面试回答**

事务是一组数据库操作组成的逻辑单元，这组操作要么全部成功，要么全部失败回滚，保证数据的一致性。

**理解**

事务把多个 SQL 操作「打包」成一个整体，具有原子性。比如下单要同时写订单表、明细表、扣库存，任意一步失败，前面已执行的都要回滚，不能出现「订单写了一半」的中间状态。数据库通过事务日志、锁等机制实现。

**场景**

项目里下单流程涉及订单主表、明细表等多张表的写入，必须放在一个事务里，保证要么全成功、要么全回滚。

**常见追问**

- 事务的四大特性？（ACID）
- 事务什么时候回滚？（发生错误或显式调用 rollback）

**易错点**

事务的「要么全成功要么全失败」是针对一组操作的整体，别把单个 SQL 也理解成一定需要事务。

## 183. 事务的 ACID 四大特性是什么？

**面试回答**

原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability），取首字母就是 ACID。

**理解**

原子性：一组操作要么全做要么全不做；一致性：事务执行前后数据都满足业务规则约束；隔离性：并发事务之间互不干扰；持久性：提交后数据永久保存，即使宕机也不丢失。这四者共同保证事务可靠。

**场景**

项目里下单事务要满足 ACID：多表写入原子完成、数据保持一致、并发下单互不干扰、提交后订单持久保存。

**常见追问**

- 四大特性英文是什么？（Atomicity、Consistency、Isolation、Durability）
- 哪个特性靠回滚保证？（原子性）

**易错点**

ACID 四个特性要能分别说清含义，尤其「一致性」和「隔离性」容易混淆。

## 184. 什么是原子性？

**面试回答**

原子性指事务中的多个操作是一个不可分割的整体，要么全部执行成功，要么全部不执行（失败则回滚），不会停留在中间状态。

**理解**

「原子」就是不可再分。事务里任何一步失败，之前已经执行的步骤都要撤销（回滚），就像这组操作从没发生过一样。它靠数据库的回滚日志（undo log）实现。

**场景**

项目里下单要写订单主表 + 明细表，如果写明细表失败，主表已写的订单也要回滚掉，保证不出现「只有订单没有明细」的中间态。

**常见追问**

- 原子性靠什么实现？（undo log 回滚）
- 和一致性的区别？（原子性强调「全或全不」，一致性强调「数据满足规则」）

**易错点**

原子性讲的是「这组操作的执行要么全有要么全无」，别把「原子性」和「数据正确」混为一谈。

## 185. 什么是一致性？

**面试回答**

一致性指事务执行前后，数据都从一个合法状态变到另一个合法状态，满足所有约束（唯一约束、外键、业务规则），不会出现中间态脏数据。

**理解**

一致性是事务的「目标」，其他三个特性（原子性、隔离性、持久性）都是为它服务的。比如转账前后，总金额必须不变；下单后，库存和订单要对应得上。事务保证不管中间怎么操作，最终结果是符合规则的。

**场景**

项目里下单后，订单金额、明细金额、库存扣减要互相吻合，不能出现账对不上的情况。

**常见追问**

- 一致性靠什么保证？（靠原子性、隔离性、持久性共同保证）
- 一致性举例？（转账前后总额不变）

**易错点**

一致性是「目标/结果」，原子性、隔离性、持久性是「手段」，层次要分清。

## 186. 什么是隔离性？

**面试回答**

隔离性指多个事务并发执行时互不干扰，一个事务的中间状态对其他事务不可见，就像各自独立执行一样。

**理解**

并发是数据库常态，隔离性通过锁和 MVCC 等机制，让并发事务之间不会读到彼此未提交的脏数据、不会互相覆盖。数据库提供了不同隔离级别（读未提交、读已提交、可重复读、串行化），隔离越强并发性能越低，需要权衡。

**场景**

项目里并发下单时，两个事务同时扣库存不能互相干扰、不能超卖，隔离性在这里很重要。

**常见追问**

- 隔离级别有哪些？（读未提交、读已提交、可重复读、串行化）
- 隔离性靠什么实现？（锁 + MVCC）

**易错点**

隔离性和一致性容易混：隔离性解决「并发事务互相干扰」，一致性是「数据符合规则」，两个角度不同。

## 187. 什么是持久性？

**面试回答**

持久性指事务一旦提交，对数据的修改就是永久的，即使系统崩溃、断电也不会丢失。

**理解**

提交后数据要落到磁盘（或可靠存储），数据库通过 redo log（重做日志）等机制保证：提交的事务即使还没来得及真正写盘，也能在故障恢复后重做，保证数据不丢。持久性让「已提交」成为一个可靠的承诺。

**场景**

项目里用户下单支付成功后，即使服务器随后宕机，订单数据也不能丢，这就是持久性的要求。

**常见追问**

- 持久性靠什么保证？（redo log 等持久化机制）
- 未提交的事务崩溃会怎样？（回滚，不会生效）

**易错点**

持久性是「提交后不丢」，针对的是已提交事务；未提交的事务崩溃会被回滚。

## 188. `@Transactional` 有什么作用？

**面试回答**

@Transactional 是 Spring 的声明式事务注解，标注在方法或类上，让方法在事务中执行：方法正常执行完自动提交，抛异常则自动回滚。

**理解**

加了它，Spring 会用 AOP 代理在方法执行前开启事务、执行后提交或回滚，业务代码里不用写任何事务控制。默认只在遇到 RuntimeException（运行时异常）和 Error 时回滚，Checked Exception 默认不回滚（可用 rollbackFor 指定）。

**场景**

项目里 Service 层的写操作方法（如新增菜品、下单）加 @Transactional，保证多步数据库操作要么全成功要么全回滚。

**常见追问**

- @Transactional 靠什么生效？（AOP 动态代理）
- 默认哪些异常回滚？（RuntimeException 和 Error）

**易错点**

@Transactional 是「声明式」，靠代理生效；理解它默认的回滚规则（运行时异常回滚、受检异常不回滚）很关键。

## 189. 什么是 Spring 声明式事务？

**面试回答**

声明式事务指通过注解或配置「声明」哪些方法需要事务，而不是手写事务代码；Spring 根据声明自动管理事务的开启、提交和回滚。

**理解**

对比「编程式事务」（手动调 begin/commit/rollback），声明式事务只需加 @Transactional，框架用 AOP 在背后完成事务控制。它让事务逻辑和业务代码解耦，代码更简洁、不易出错，是 Spring 最常用的方式。

**场景**

项目里在 Service 方法上直接加 @Transactional，就是声明式事务，不用写任何 commit/rollback 代码。

**常见追问**

- 编程式和声明式区别？（手写事务代码 vs 注解声明 + 框架管理）
- 声明式事务靠什么实现？（AOP 代理）

**易错点**

声明式事务「省事」但「不透明」，要理解它靠 AOP 代理，否则遇到事务失效问题会懵。

## 190. Spring 声明式事务大致是怎么实现的？

**面试回答**

核心是 AOP 动态代理：Spring 为标注了 @Transactional 的 Bean 生成代理对象，方法执行时由代理在前后织入「开启事务 → 执行业务 → 提交/回滚」的逻辑。

**理解**

调用带 @Transactional 的方法时，实际调用的是代理对象。代理在方法前开启事务（从连接池拿连接、关闭自动提交、绑定到当前线程），方法正常返回则提交，抛出指定异常则回滚，最后释放连接。整个过程业务代码无感知。

**场景**

项目里 Service 的 @Transactional 方法，Spring 生成代理，在方法前后管理事务，出错时自动回滚所有已执行的 SQL。

**常见追问**

- 事务管理器作用？（PlatformTransactionManager，负责 commit/rollback）
- 为什么说事务是 AOP 的典型应用？（因为事务是「方法前后」的横切逻辑）

**易错点**

事务实现依赖「代理」，所以绕过代理（this 内部调用、自己 new）事务会失效，这是理解后续失效问题的关键。

## 191. 为什么 `@Transactional` 通常加在 Service 层？

**面试回答**

因为事务是「业务逻辑」层面的概念：一个业务操作（如下单）往往涉及多次数据库访问、多个 DAO 调用，需要在 Service 层把这些操作作为一个整体控制，而 DAO 层通常是单次操作，不适合做事务边界。

**理解**

Service 方法代表一个完整的业务用例，事务边界应该圈住整个业务逻辑，而不是单个 SQL。如果加在 DAO 层，一次业务里多次 DAO 调用会各自独立提交，无法保证整体原子性。所以事务放在 Service 方法上，把整个业务包裹成一个事务。

**场景**

项目里下单 Service 方法里先后调用订单 Mapper、明细 Mapper，@Transactional 加在这个 Service 方法上，保证两者同生共死。

**常见追问**

- 加在 Controller 层行不行？（技术上能，但事务应属业务层，且 Controller 不该管事务）
- DAO 层能加吗？（能但意义不大，事务边界应该是业务整体）

**易错点**

事务边界 = 业务逻辑边界，所以放 Service；放 DAO 层会破坏「多次操作同事务」的整体性。

## 192. Spring 默认哪些异常会触发回滚？

**面试回答**

默认 RuntimeException（运行时异常）和 Error 会触发回滚；Checked Exception（受检异常）默认不回滚。

**理解**

Spring 事务默认的回滚规则：遇到 RuntimeException 及其子类、Error 时回滚，遇到受检异常（Exception 里非 RuntimeException 的部分）时不回滚，而是照常提交。这是因为受检异常在 Java 语义里往往代表「可预期、可处理」的情况。

**场景**

项目里 Service 抛 NullPointerException、IllegalArgumentException 等运行时异常会自动回滚；但抛一个受检的 SQLException 默认不会回滚，需要额外配置。

**常见追问**

- 为什么受检异常默认不回滚？（受检异常通常被认为是可处理的业务异常）
- 想让受检异常也回滚怎么办？（rollbackFor = Exception.class）

**易错点**

「所有异常都回滚」是常见误解，实际默认只回滚运行时异常和 Error；受检异常要回滚需用 rollbackFor。

## 193. Checked Exception 默认会回滚吗？

**面试回答**

不会。Spring 默认只在遇到 RuntimeException 和 Error 时回滚，Checked Exception（受检异常）默认不回滚，事务照常提交。

**理解**

受检异常（IOException、SQLException 等）在 Spring 的默认语义里被视为「业务上可预期、可能已处理的异常」，所以不自动回滚。如果你希望受检异常也回滚，需要用 @Transactional 的 rollbackFor 属性显式声明。

**场景**

项目里如果某方法声明抛出受检异常且希望失败回滚，需要写 `@Transactional(rollbackFor = Exception.class)`。

**常见追问**

- 怎么让受检异常回滚？（rollbackFor = Exception.class）
- rollbackFor 和 rollbackForClassName 区别？（一个用 Class，一个用字符串类名，作用一样）

**易错点**

这是高频考点：受检异常默认「不回滚」，别想当然认为「抛异常就回滚」。

## 194. `rollbackFor` 有什么作用？

**面试回答**

rollbackFor 用于指定哪些异常类型应该触发事务回滚，用来覆盖默认规则（默认只回滚 RuntimeException 和 Error）。

**理解**

通过 `@Transactional(rollbackFor = Exception.class)`，可以让所有异常（包括受检异常）都回滚；也可以指定具体的异常类型。它是应对「受检异常默认不回滚」这一默认行为的主要手段。

**场景**

项目里对需要「任何异常都回滚」的方法，用 `@Transactional(rollbackFor = Exception.class)`，保证受检异常也能回滚。

**常见追问**

- rollbackFor 和 noRollbackFor 区别？（一个指定要回滚的异常，一个指定不回滚的异常）
- rollbackFor = Exception.class 含义？（所有异常都回滚）

**易错点**

rollbackFor 是「扩大」回滚范围（让默认不回滚的受检异常也回滚），别和「缩小」混淆。

## 195. 把异常 catch 住为什么可能导致事务不回滚？

**面试回答**

因为事务回滚靠「异常抛出到代理层」来触发，如果你在方法内部把异常 try-catch 吞掉了，异常不会抛给代理，Spring 感知不到失败，就会正常提交，导致本应回滚的操作被提交了。

**理解**

声明式事务的原理是：代理捕获到方法抛出的指定异常才回滚。一旦你在业务代码里 catch 住异常且不重新抛出，对代理来说方法「正常返回」，于是提交事务。所以要么别吞异常，要么在 catch 里手动标记回滚（如 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()）或重新抛出。

**场景**

项目里如果 Service 方法内部 try-catch 了数据库异常又不抛出，事务就不会回滚，数据可能写了一半还被提交。

**常见追问**

- catch 后怎么让它回滚？（重新抛出异常，或手动 setRollbackOnly）
- 为什么吞异常危险？（代理感知不到失败，会提交）

**易错点**

「catch 住异常 = 事务没回滚」是事务失效的经典场景，核心是异常没传到代理层。

## 196. 同一个类内部调用另一个事务方法为什么可能失效？

**面试回答**

因为事务靠 AOP 代理实现，类内部用 this 调用另一个方法时，走的是原对象而不是代理对象，绕过了代理，事务增强不生效。

**理解**

@Transactional 的增强逻辑在代理对象上。外部调用 `service.methodA()` 时拿到的是代理，事务生效；但 methodA 内部 `this.methodB()` 调用的是当前原对象（this），没有经过代理，methodB 上的 @Transactional 就不会被拦截，事务失效。

**场景**

项目里如果 Service 的 A 方法直接 this 调用本类的 B 方法（B 有 @Transactional），B 的事务不会生效，这是常见坑。

**常见追问**

- 怎么解决？（把 B 方法移到另一个 Bean，或用 AopContext 获取代理，或注入自身）
- 为什么 this 调用不走代理？（this 是原对象，不是 Spring 生成的代理）

**易错点**

关键是「this 调用绕过代理」；不是 @Transactional 本身失效，是代理没被触发。

## 197. private 方法上的 `@Transactional` 为什么通常不生效？

**面试回答**

因为 Spring 事务靠动态代理实现，代理只能拦截「能被代理的方法」；private 方法无法被 JDK 代理（不在接口里）也无法被 CGLIB 覆盖（CGLIB 不能代理 private 方法），所以注解不生效。

**理解**

JDK 动态代理基于接口，private 方法不在接口里；CGLIB 基于继承子类，private 方法不能被继承覆盖。两者都无法拦截 private 方法，@Transactional 自然失效。所以事务方法必须是 public（或至少能被代理覆盖的方法）。

**场景**

项目里事务方法都声明为 public；如果误把 @Transactional 写在 private 方法上，事务不会生效。

**常见追问**

- 事务方法应该什么访问级别？（public）
- 为什么 private 不行？（代理机制无法拦截 private 方法）

**易错点**

和「内部 this 调用」一样，根因都是「代理机制」；private 方法连被代理的前提都没有。

## 198. 什么是事务传播行为？

**面试回答**

事务传播行为定义了「一个事务方法被另一个事务方法调用时，事务如何处理」：是加入已有事务，还是新开事务，还是不用事务等。

**理解**

当一个事务方法内部调用另一个事务方法，Spring 要决定：新方法是用外层已有的事务，还是自己新开一个，还是挂起外层事务单独跑。这就是传播行为，用 @Transactional 的 propagation 属性指定，默认是 REQUIRED。

**场景**

项目里下单方法（有事务）内部调用另一个有事务的方法，默认 REQUIRED 会让它们共用同一个事务。

**常见追问**

- 常见传播行为有哪些？（REQUIRED、REQUIRES_NEW、NESTED、SUPPORTS 等）
- 默认是什么？（REQUIRED）

**易错点**

传播行为是「事务方法之间的协作规则」，只在「事务方法调用事务方法」时才有意义。

## 199. `Propagation.REQUIRED` 是什么意思？

**面试回答**

REQUIRED 是默认传播行为：如果当前已有事务，就加入这个事务；如果没有，就新建一个事务。

**理解**

这是最常用的传播行为，语义是「我需要一个事务，有就用现成的，没有就开一个」。它让内层方法和外层方法共用同一个事务，内层失败会导致整个事务回滚。这是 Spring 默认行为，满足绝大多数业务场景。

**场景**

项目里下单 Service 方法（REQUIRED）内部调用明细写入方法，两者默认共用一个事务，任一失败整体回滚。

**常见追问**

- REQUIRED 和 REQUIRES_NEW 区别？（REQUIRED 加入已有事务，REQUIRES_NEW 总是新开一个独立事务）
- REQUIRED 下内层回滚会怎样？（整个事务回滚）

**易错点**

REQUIRED = 「有则加入，无则新建」；它会让内层和外层「共生死」，这是默认且最常见的语义。

## 200. 项目中为什么主表和子表写入需要放在同一个事务中？

**面试回答**

因为主表和子表数据有强关联（如订单和订单明细），必须保证「要么同时写入成功、要么同时回滚」，否则会出现只有主表没有子表、或只有子表没有主表的脏数据，破坏数据一致性。

**理解**

订单主表和明细表是一对多关系，明细必须依附主表存在。如果分两个事务，主表提交后写子表失败，就会留下一个没有明细的孤儿订单；反过来先写子表失败回滚、主表却提交了，数据就对不上。放在同一个事务里，任何一步失败都整体回滚，保证一致性。

**场景**

项目里下单时，订单主表和订单明细表在同一个 @Transactional 方法里写入，共用一个事务，确保要么都成功要么都回滚。

**常见追问**

- 分两个事务会怎样？（可能出现孤儿数据或数据不一致）
- 怎么保证同事务？（放在同一个 @Transactional 方法里，用 REQUIRED 传播）

**易错点**

「主从表同事务」的根本原因是「数据强关联 + 一致性要求」，不是简单地把操作放一起就行，还要注意事务传播和异常处理。
