# Redis缓存

## 330. 什么是 Cache Aside 模式？

**面试回答**

Cache Aside（旁路缓存）由应用同时访问缓存和主存储：读取时先查缓存，未命中再查数据库并按需回填；数据更新时先修改作为事实来源的数据库，再使相关缓存失效，是一种常见做法。

**原理与理解**

缓存只保存可丢失、可重建的副本。热点数据在第一次读取后进入 Redis，后续读取直接命中；写操作以数据库结果为准，通过删除缓存让下一次读取重新加载。它与由缓存组件负责同步主存储的 write-through、write-behind 不同。

**成立条件与边界**

“写时先更新数据库再删除缓存”是 Cache Aside 的常见实现，不是无条件的强一致协议。数据库提交、缓存删除和并发回填不是一个原子操作，仍需接受有界陈旧或设计重试、补偿与并发控制。

**实际场景（真实项目边界）**

简历能够确认项目使用过 `RedisTemplate` 和 Spring Cache，但这不足以证明所有缓存都由手写 Cache Aside 实现。面试前应按源码核验哪些查询用了 `@Cacheable`、哪些操作用了 `@CacheEvict` 或手工删除，以及真实 Key 与 TTL。

**常见追问**

- 为什么叫旁路缓存？（应用显式协调缓存与数据库，数据库仍是事实来源）
- 写时为什么常删除而不是更新缓存？（见 [[05-Redis/03-Redis缓存#336. 为什么通常删除缓存而不是更新缓存？]]）

**易错点**

不要把 Cache Aside 说成 Redis 自带的事务协议；Redis 提供读写与过期能力，跨数据库的一致性流程由应用设计。

## 331. 查询 Redis + MySQL 的基本流程是什么？

**面试回答**

先按确定的 Key 查询 Redis；命中则反序列化并返回，未命中则查询 MySQL。数据库查到数据后，根据缓存价值写入 Redis 并设置 TTL，再返回；查不到时还要按业务决定是否短期缓存空值。

**原理与理解**

这个流程把重复读取从数据库转移到缓存。Key 需要稳定且包含数据范围或版本信息；回填值、TTL 和序列化方式要一致。对热点 Key，还要防止同一时刻大量未命中并发回源。

**成立条件与边界**

未命中不等于必然查询 MySQL：数据源也可能是其他服务，布隆过滤器或空值缓存还可能提前结束请求。查库成功也不等于必须回填，低复用、大对象或敏感数据可能不适合缓存。

**实际场景（项目核验项）**

若源码使用 Spring Cache，缓存查询和回填可能由拦截器完成；若使用 `RedisTemplate`，则需要核对空值判断、TTL 和异常降级。不能仅凭依赖声明就描述成手写“Redis → MySQL → SET”流程。

**常见追问**

- 命中和未命中分别是什么？（见 [[05-Redis/03-Redis缓存#332. 什么是 Cache Hit？]] 和 [[05-Redis/03-Redis缓存#333. 什么是 Cache Miss？]]）
- 未命中后为什么可能回填？（见 [[05-Redis/03-Redis缓存#334. Cache Miss 后为什么要把数据库数据写回 Redis？]]）

**易错点**

基本流程不仅是三步口诀，还要说明 Key、空值、TTL、并发回源和 Redis 故障时是否允许直接查库。

## 332. 什么是 Cache Hit？

**面试回答**

Cache Hit（缓存命中）指按当前 Key 和查询语义在缓存中取得了可用结果，请求可以使用该结果而不必为这份数据回源。

**原理与理解**

命中率通常按“命中次数 ÷ 缓存查询总次数”统计。命中能降低回源负载和读取延迟，但还要结合缓存查询耗时、数据大小、请求分布和数据库负载评价收益。

**成立条件与边界**

命中只表示缓存里有值，不保证值一定新鲜或业务上正确。旧版本、错误 Key、错误序列化和缓存空值也可能形成“命中”；TTL 只能限制最长存活时间，不能自动证明与数据库实时一致。

**实际场景（通用工程）**

监控菜品或订单摘要缓存时，应同时观察命中率、P95/P99 延迟、回源 QPS、Key 数量和陈旧数据告警，不能只追求一个很高的命中率。

**常见追问**

- 命中率越高越好吗？（通常有利，但要同时看数据正确性、成本和延迟）
- 缓存命中后一定不访问数据库吗？（这份数据通常不回源，但一次业务请求仍可能访问其他数据）

**易错点**

不要把“Redis 返回非空”直接等同于有效命中；还要判断缓存空值、版本、逻辑过期和反序列化结果。

## 333. 什么是 Cache Miss？

**面试回答**

Cache Miss（缓存未命中）指缓存中没有当前查询可用的结果，常见原因包括首次访问、Key 过期或淘汰、主动失效、Key 设计变化，以及数据本来就不存在。

**原理与理解**

未命中后通常访问事实来源，并决定是否回填。正常的首次读取属于 compulsory miss；容量不足、TTL 到期和写后失效也会产生未命中。大量请求集中未命中会放大数据库压力。

**成立条件与边界**

未命中不是异常，也不能一概归为缓存穿透。对不存在数据的持续查询才可能构成穿透问题；Redis 故障或超时则是缓存不可用，和正常 miss 的监控、降级方式不同。

**实际场景（通用工程）**

上线新 Key 规则或批量失效缓存时，命中率可能暂时下降。发布方案应估算回源容量，并考虑分批预热、限流或请求合并。

**常见追问**

- 未命中一定是缓存穿透吗？（不是，首次访问和过期都属于正常未命中）
- 未命中后一定要回填吗？（不一定，要看数据是否存在、复用概率和对象大小）

**易错点**

要区分“缓存没有该 Key”“缓存服务不可用”和“缓存里存了代表不存在的空值”。

## 334. Cache Miss 后为什么要把数据库数据写回 Redis？

**面试回答**

回填可以让后续相同读取直接命中，摊薄本次回源成本并降低数据库压力。Cache Aside 因此只缓存真正被访问的数据，使缓存逐步形成工作集。

**原理与理解**

若每次未命中都只查库而不回填，同一热点请求会持续访问数据库。回填时一般同时设置 TTL，必要时加入随机抖动；热点 Key 还可通过 single-flight、互斥重建或提前刷新控制并发。

**成立条件与边界**

回填动作可能与写请求竞态：读请求先查到旧数据库值，写请求随后提交并删除缓存，而慢读最后又把旧值写回。回填不能只写 `SET`，还要结合一致性目标考虑版本校验、锁、短 TTL 或再次失效。

**实际场景（通用工程）**

分类菜品列表若读取频繁且生成成本高，适合在未命中后回填；一次性报表、大结果集或高度个性化查询则应先评估缓存复用率和内存成本。

**常见追问**

- 回填时为什么要设置 TTL？（限制陈旧时间与内存占用）
- 如何避免热点 Key 同时回源？（请求合并、互斥重建、提前刷新或限流）

**易错点**

“查库后无脑写回”可能缓存大对象、低价值结果或把并发读到的旧值重新写入。

## 335. 数据库数据发生修改后缓存怎么办？

**面试回答**

若数据库是事实来源，常见策略是在数据库事务成功提交后使相关缓存失效，让后续读取从数据库重建。失效操作需要可重试，并用 TTL 限制删除遗漏造成的陈旧时间。

**原理与理解**

若在事务提交前删除缓存，其他请求可能立即回源并读到旧数据；若数据库最终回滚，缓存还会发生无意义失效。因此应用可在提交后删除，或通过事务消息、Outbox/CDC 等可靠事件异步驱动失效。

**成立条件与边界**

删除缓存不是强一致保证：删除可能失败，提交前开始的慢读也可能在删除后回填旧值。对金额、库存判断、权限等不能容忍陈旧的数据，应考虑不缓存关键判定结果或使用更强的读写协调。

**实际场景（真实项目边界）**

项目确认使用了 Spring Cache，但具体修改操作是否配置 `@CacheEvict`、清理的是单条还是列表缓存、是否在事务提交后生效，需要以源码为准；简历不能证明这些实现细节。

**常见追问**

- 为什么通常删除而不是更新？（见 [[05-Redis/03-Redis缓存#336. 为什么通常删除缓存而不是更新缓存？]]）
- 为什么强调事务提交后？（避免未提交或回滚状态影响缓存）

**易错点**

不能只删除对象详情 Key，却忘记该对象参与的列表、聚合和多级缓存；失效范围也是一致性设计的一部分。

## 336. 为什么通常删除缓存而不是更新缓存？

**面试回答**

删除缓存通常更简单：不必在写路径重复实现缓存值计算，也能避免多个并发写按不同顺序覆盖缓存；真正发生下一次读取时再重建，减少低频数据的无效缓存写入。

**原理与理解**

缓存可能是数据库多行、多个表或复杂计算的结果。数据库更新后精确重算并更新所有相关 Key 容易漏项；使其失效把重建逻辑集中在读路径，更符合缓存“可丢失副本”的定位。

**成立条件与边界**

“删除一定优于更新”不成立。对读极热、重建昂贵且写模型清晰的数据，write-through、事件驱动更新或先计算新值再原子替换可能更合适。删除还会制造一次 miss，并存在删除失败与旧值回填问题。

**实际场景（通用工程）**

商品详情更新少、读取多时，可在提交后删除详情缓存；排行榜、计数器或实时聚合可能更适合增量更新。选择取决于一致性要求、重建成本和写入频率。

**常见追问**

- 更新缓存有什么风险？（漏更新相关 Key、并发覆盖和重复计算）
- 删除缓存有什么代价？（下次读取回源，且删除失败或慢读回填仍需处理）

**易错点**

“这是业界共识，所以永远删除”是绝对化回答；面试要先说明默认选择，再给出不适用条件。

## 337. 为什么 Redis 和 MySQL 可能出现数据不一致？

**面试回答**

因为 Redis 与 MySQL 是两个独立系统，数据库提交、缓存写入或删除不能天然组成同一个原子事务。并发执行、网络超时、进程崩溃、重试和消息乱序都可能让缓存暂时或持续保存旧副本。

**原理与理解**

常见竞态包括：数据库已提交但缓存删除失败；读请求在更新前读到旧值，却在写请求删除缓存后才完成回填；多个写请求提交与失效事件顺序不同。TTL 只能给陈旧时间设置上界，不能消除竞态。

**成立条件与边界**

“两套存储所以完全无法保证一致”也过于笼统。可以通过不缓存、同步串行化、版本号与条件写、可靠事件和读后校验获得更强语义，只是会增加延迟、复杂度或可用性代价。

**实际场景（通用工程）**

缓存中的展示型菜品信息可接受短暂陈旧；支付状态、库存扣减和权限判断则不应只依据可能过期的缓存副本，需要按业务定义一致性等级。

**常见追问**

- 缓存不一致与数据库脏读一样吗？（不一样，前者是跨系统副本同步问题）
- TTL 能保证一致吗？（只能限制 Key 的存活或陈旧窗口，不能保证实时一致）

**易错点**

不要把 Redis `DEL` 成功误解为数据库与缓存已经原子提交；还要分析在途读请求和其他派生 Key。

## 338. 先更新数据库再删除缓存有什么问题？

**面试回答**

这是常见默认顺序，但仍有两个主要风险：数据库提交后缓存删除失败，旧值一直保留到过期；以及更新前开始的慢读在数据库读取旧值，随后写请求提交并删除缓存，慢读最后又回填旧值。

**原理与理解**

第一类问题需要可靠重试或事件补偿；第二类问题来自“读取数据库”和“写入缓存”之间没有版本约束。更新完成到删除成功之间也存在短暂旧缓存窗口，只是通常较小。

**成立条件与边界**

先更新数据库应准确理解为“数据库事务成功提交后再使缓存失效”。消息队列并不会自动解决问题，还必须保证事件持久化、至少一次投递下的幂等、失败重试、顺序处理和监控告警。

**实际场景（通用工程）**

更新菜品后可提交数据库，再投递或执行缓存失效；若删除失败进入重试队列。对于列表与详情多个 Key，需要在同一业务事件中记录完整失效范围。

**常见追问**

- 这个顺序是否完全避免旧值回填？（不能，更新前开始的慢读仍可能在删除后回填）
- 删除失败怎么办？（幂等重试、Outbox/CDC 驱动补偿并配置 TTL）

**易错点**

原笔记把它的问题只归结为“删除失败”，遗漏了在途慢读回填旧值这一小概率但真实的竞态。

## 339. 先删除缓存再更新数据库有什么问题？

**面试回答**

删除缓存后、数据库提交前，读请求可能未命中并从数据库读取旧值，再把旧值写回缓存；若后续数据库更新成功或失败，该旧缓存都可能继续存在，因此这个顺序通常更难控制。

**原理与理解**

时间线可以是：写请求删除 Key；读请求查缓存未命中并读取旧数据库值；写请求更新并提交数据库；读请求回填旧值。若数据库更新失败，提前删除还会造成不必要回源，但主要一致性风险仍是旧值回填。

**成立条件与边界**

这不是说先删一定不可用。若写操作串行、读写使用同一把正确实现的锁，或第二次删除具有可靠保证，可以降低风险；但这些措施会引入吞吐、可用性和运维成本。

**实际场景（通用工程）**

高并发列表查询不应仅靠“先删再更”期待一致；若历史代码采用该顺序，应画出读写时序并验证是否存在可靠的第二次失效与失败补偿。

**常见追问**

- 旧值为什么会被回填？（删缓存后、数据库提交前的读仍可能读到旧库值）
- 常见缓解办法是什么？（延迟双删，见 [[05-Redis/03-Redis缓存#341. 什么是延迟双删？]]）

**易错点**

不能只背线程 A/B 的正常完成顺序，还要考虑数据库回滚、进程崩溃和第二次删除失败。

## 340. 如何降低缓存和数据库不一致的概率？

**面试回答**

先定义可接受的陈旧窗口。常见组合是数据库提交后删除缓存、为删除建立可靠的幂等重试或 Outbox/CDC 补偿、设置合理 TTL，并对热点回填做请求合并或版本控制；强一致判定尽量直接读取事实来源。

**原理与理解**

TTL 限制最坏陈旧时间，可靠事件降低删除丢失概率，版本号或条件写防止旧读覆盖新缓存，请求合并减少并发回填。还应监控删除失败、事件积压、命中率、回源量和数据校验差异。

**成立条件与边界**

没有一套方案同时免费获得强一致、高可用和低延迟。分布式锁也不是自动正确：要处理租约过期、持有者暂停、误删他人锁和故障恢复。若错误缓存会造成资金或权限事故，最安全的方案可能是不缓存该判定。

**实际场景（生产能力）**

可把“更新主数据”和“写入待处理失效事件”放在同一数据库事务中，由消费者幂等删除缓存；积压时告警，失败进入重试或人工处置，并以 TTL 作为最后边界。

**常见追问**

- TTL 为什么只是兜底？（过期前仍可能返回旧值，过期时还可能造成集中回源）
- MQ 能保证一致吗？（不能单独保证，还要有可靠产生、幂等消费、重试、顺序和监控）

**易错点**

不要承诺“先更库后删缓存 + TTL 就完全一致”，也不要把复杂方案包装成项目已经实现的能力。

## 341. 什么是延迟双删？

**面试回答**

延迟双删是为清理并发回填旧值而执行两次缓存失效的策略。常见描述是先删缓存、更新数据库，再等待一个时间窗口后第二次删除；也有在数据库提交后立即删除并安排延迟再删的变体。

**原理与理解**

第一次失效触发后，处于并发窗口的读请求可能把旧值写回；第二次删除尝试在这些读完成后清掉旧值。它针对的是特定时序竞态，而不是让 Redis 与 MySQL 获得原子性。

**成立条件与边界**

延迟时间难以准确选择：太短覆盖不了慢请求，太长扩大陈旧窗口；进程崩溃或第二次删除失败也会失效。若采用，应把第二次删除做成可持久化、可重试任务，并配合 TTL、幂等和监控。

**实际场景（生产能力）**

只有通过压测和链路指标了解数据库读取、网络与回填耗时后，才能选择延迟窗口。多数业务应先评估“提交后失效 + 可靠重试/CDC”是否已经足够。

**常见追问**

- 为什么需要延迟？（等待可能读取旧值的在途请求结束）
- 能完全解决不一致吗？（不能，延迟估计和第二次删除本身都可能失败）

**易错点**

“睡眠固定 500ms 再删一次”不是生产级保证；它只是概率性缓解手段。

## 342. 什么是缓存预热？

**面试回答**

缓存预热是在发布、扩容或活动开始前，主动把确定的热点数据加载到缓存，减少冷启动阶段的集中未命中和回源压力。

**原理与理解**

预热可以由发布任务、离线脚本、热点统计或渐进流量触发。加载时仍应使用与线上一致的 Key、序列化和 TTL，并控制并发，避免预热任务本身把数据库或 Redis 压满。

**成立条件与边界**

不是所有数据都应全量预热。热点判断错误会浪费内存，预热过早可能在上线前已过期，源数据更新还会使预热值变旧。缓存击穿、穿透和雪崩仍需要各自的治理方案。

**实际场景（项目核验项）**

热门菜品或套餐可以作为预热候选，但简历只确认项目使用缓存，没有证明已经实现预热任务。面试时应把它描述为通用优化方案，除非源码和运行流程能够核验。

**常见追问**

- 预热解决什么问题？（降低冷启动阶段的集中回源）
- 怎样安全预热？（只加载热点、限速分批、复用线上编码并验证容量和新鲜度）

**易错点**

缓存预热不是把整张表一次性写入 Redis，也不能代替 TTL、容量规划和热点失效保护。
