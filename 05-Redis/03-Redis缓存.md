# Redis缓存

## 330. 什么是 Cache Aside 模式？

**面试回答**

Cache Aside（旁路缓存）是最常用的缓存读写模式：读时先查缓存，命中直接返回，未命中查数据库并回填缓存；写时先更新数据库，再删除缓存。

**理解**

「旁路」指缓存不参与主数据流，读写逻辑由应用自己控制。读流程：缓存有就返回，没有查库、写回缓存；写流程：更新数据库、删缓存（让下次读重新加载）。它的特点是简单、可控，是绝大多数业务缓存的标准做法。

**场景**

项目里菜品缓存就是 Cache Aside：查菜品先看 Redis，没有查 MySQL 并写回 Redis；改菜品时更新库、删缓存。

**常见追问**

- 为什么叫「旁路」？（应用自己控制缓存读写，缓存不拦截数据流）
- 写时为什么删缓存不更新缓存？（见 [[05-Redis/03-Redis缓存#336. 为什么通常删除缓存而不是更新缓存？]]）

**易错点**

Cache Aside 的核心流程「读：查缓存→查库→回填；写：更新库→删缓存」，要能准确说出，别把顺序搞反。

## 331. 查询 Redis + MySQL 的基本流程是什么？

**面试回答**

先查 Redis 缓存，命中（Cache Hit）直接返回；未命中（Cache Miss）则查 MySQL，查到后把结果写回 Redis（设 TTL），再返回。

**理解**

这是读的完整链路：缓存优先，减少数据库访问。命中就走缓存（快）；未命中才碰数据库，并把结果回填缓存，让后续同样查询能命中。要注意「缓存穿透」（查不到的数据反复打库）等问题，需要配合空值缓存或布隆过滤器等。

**场景**

项目里查菜品列表：先 get Redis，有直接返回；没有就查 MySQL，结果 set 回 Redis（带 TTL）再返回。

**常见追问**

- 命中/未命中是什么？（见 [[05-Redis/03-Redis缓存#332. 什么是 Cache Hit？]] 和 [[05-Redis/03-Redis缓存#333. 什么是 Cache Miss？]]）
- 未命中后为什么要回填？（见 [[05-Redis/03-Redis缓存#334. Cache Miss 后为什么要把数据库数据写回 Redis？]]）

**易错点**

基本流程是「先缓存后库、未命中回填」；这是所有缓存问题讨论的基础，要记牢。

## 332. 什么是 Cache Hit？

**面试回答**

Cache Hit（缓存命中）指请求的数据在缓存里找到了，直接从缓存返回，不用访问数据库。

**理解**

命中率是衡量缓存价值的关键指标：命中率高，说明缓存挡住了大部分请求、数据库压力小、响应快。反之命中率低，缓存没发挥多大作用。

**场景**

项目里高频查询的菜品数据基本都能在 Redis 命中，命中率高，MySQL 压力就小。

**常见追问**

- 命中率高有什么好处？（数据库压力小、响应快）
- 命中率低说明什么？（缓存策略或 Key 设计有问题）

**易错点**

Cache Hit 是「数据在缓存里」，是缓存有效性的核心指标；别和「缓存写回」混为一谈。

## 333. 什么是 Cache Miss？

**面试回答**

Cache Miss（缓存未命中）指请求的数据不在缓存里，需要回源到数据库查询。

**理解**

未命中是「缓存里没找到」，此时要查数据库，并通常把结果回填缓存。未命中分两类：数据从没缓存过（正常未命中），和「查的根本不存在的数据」（会导致缓存穿透）。正常未命中回填后就能命中；穿透类未命中需要特殊处理。

**场景**

项目里首次查某个菜品时缓存没数据，就是 Cache Miss，查库后回填，下次就命中了。

**常见追问**

- 未命中一定查库吗？（一般是的，除非用空值缓存/布隆过滤器拦截）
- 未命中后要做什么？（查库 + 回填缓存）

**易错点**

Cache Miss 是「缓存没有」，正常流程是「查库 + 回填」；但要注意「查不存在的数据」这类异常未命中（缓存穿透）。

## 334. Cache Miss 后为什么要把数据库数据写回 Redis？

**面试回答**

为了下次同样的查询能命中缓存、不再访问数据库，从而降低数据库压力、提高响应速度。

**理解**

缓存的意义就是「挡在数据库前面」。未命中查了库，如果不回填，下次还查库，缓存形同虚设。回填后，后续相同请求直接命中缓存，数据库压力大幅下降。这是缓存「越用越热」的关键动作。

**场景**

项目里第一次查某分类的菜品列表未命中、查库后写回 Redis，之后该分类的查询都直接命中缓存。

**常见追问**

- 不回填会怎样？（每次都查库，缓存没用）
- 回填要注意什么？（设 TTL，避免脏数据长期存在）

**易错点**

「查库后回填」是缓存生效的核心步骤；漏掉回填，缓存就白搭了。

## 335. 数据库数据发生修改后缓存怎么办？

**面试回答**

通常是「删除缓存」（而非更新），让下次读取时重新从数据库加载最新数据回填缓存，保证缓存不长期保存旧数据。

**理解**

数据改了，缓存里的旧值就失效了。主流做法是删缓存：更新数据库后删除对应缓存 Key，下次读未命中、查库回填最新值。这样实现简单、避免「更新缓存」时可能的并发覆盖问题。配合 TTL 兜底，能较好控制不一致。

**场景**

项目里修改菜品后，删除对应的 `dish:info:{id}` 缓存，下次查询重新加载。

**常见追问**

- 为什么删而不是更新？（见 [[05-Redis/03-Redis缓存#336. 为什么通常删除缓存而不是更新缓存？]]）
- 删缓存后第一次读会怎样？（未命中，查库回填最新值）

**易错点**

「改数据 → 删缓存」是主流，核心是「让缓存失效、下次重载」，而不是「同步更新缓存值」。

## 336. 为什么通常删除缓存而不是更新缓存？

**面试回答**

因为更新缓存容易出错且收益低：①更新缓存要多写一次，但缓存数据可能很快过期、根本没人读，白写；②并发更新时容易产生顺序问题导致缓存值错乱；删除缓存让下次读时重新加载，实现简单、不易错。

**理解**

删缓存是「惰性」策略：不主动维护缓存的新值，而是让它失效，等真正被需要时再从库加载。这样避免了「写缓存」的复杂性和并发覆盖风险。缓存是「加速副本」，不需要实时精确同步，删掉最省事也最安全。

**场景**

项目里改菜品后删缓存，而不是去更新缓存里的菜品对象，逻辑简单且不易出错。

**常见追问**

- 更新缓存有什么风险？（并发写覆盖、写了没人读浪费）
- 删缓存的思路？（让缓存失效，读时重建）

**易错点**

核心是「缓存是可有可无的加速层，删掉让读时重建」比「主动更新」更简单可靠，这是业界共识。

## 337. 为什么 Redis 和 MySQL 可能出现数据不一致？

**面试回答**

因为 Redis 缓存是数据库的「副本」，两者更新不是原子操作：当数据库更新和缓存删除之间有时间差，或并发读写交错时，缓存可能还存着旧值，出现短暂或持续的不一致。

**理解**

缓存和数据库是两套存储，没法用同一个事务保证同步。典型场景：更新数据库后、删缓存前，有请求读到旧缓存；或者先删缓存后更新数据库的间隙，有请求回填了旧数据。这些都会造成「缓存和库对不上」。这是缓存架构的固有问题，只能降低概率、不能完全杜绝。

**场景**

项目里菜品价格改了，如果删缓存不及时或并发读，短时间内缓存里可能还是旧价格。

**常见追问**

- 为什么不一致不可避免？（两套存储无法原子同步）
- 怎么降低？（延迟双删、TTL 兜底、消息队列等）

**易错点**

缓存不一致是「缓存副本的固有问题」，不是「数据库脏读」；要理解「无法完全避免，只能降低概率」。

## 338. 先更新数据库再删除缓存有什么问题？

**面试回答**

可能产生「缓存旧值残留」的短暂不一致：更新数据库后、删除缓存前，或删除失败时，请求会读到旧缓存。

**理解**

「先更库、后删缓存」的间隙：更新库完成、还没删缓存时，并发读会命中旧缓存。更严重的是「删缓存失败」——如果删除操作失败，缓存就一直保留旧值，直到 TTL 过期。所以这种顺序虽然避免了「回填旧数据」的问题，但仍有「删缓存失败导致长期不一致」的风险。

**场景**

项目里采用「先更库后删缓存」，如果删缓存因网络抖动失败，旧缓存会残留到过期。

**常见追问**

- 删缓存失败怎么办？（重试、或延迟双删、消息队列保证最终删掉）
- 这个顺序的主要风险？（删缓存失败导致长期旧值）

**易错点**

「先更库后删缓存」的问题是「删缓存失败 → 旧值残留」，不是「读库并发」问题；风险点是删除这步不可靠。

## 339. 先删除缓存再更新数据库有什么问题？

**面试回答**

可能产生「缓存被旧数据回填」的问题：删除缓存后、更新数据库前，有并发读请求查库读到旧数据，又把旧数据写回缓存，导致缓存长期是旧值。

**理解**

「先删缓存、后更库」的间隙里，别的线程来读：缓存已删（未命中），于是查库——此时库还没更新，读到旧值，回填缓存。结果缓存里是旧值，且一直要到下一次删缓存或 TTL 过期才更新。这个时间窗口里，并发读越多，越容易出问题。

**场景**

项目里若先删缓存再更库，高并发读可能把旧数据回填，造成较长的不一致。

**常见追问**

- 为什么旧数据会被回填？（删缓存后、更库前的读会查库回填旧值）
- 怎么缓解？（延迟双删，见 [[05-Redis/03-Redis缓存#341. 什么是延迟双删？]]）

**易错点**

「先删缓存后更库」的问题是「并发读回填旧值」；它的风险窗口在于「删缓存到更库」之间。

## 340. 如何降低缓存和数据库不一致的概率？

**面试回答**

常用手段：采用「先更新数据库再删除缓存」的顺序、删除失败重试、延迟双删、给缓存设合理 TTL 兜底、必要时用消息队列保证最终一致。

**理解**

一致性无法绝对保证，只能尽量降低：①选更安全的顺序（先更库后删缓存，避免回填旧值）；②删缓存失败要重试或异步补偿；③延迟双删覆盖并发窗口；④TTL 作为最终兜底，让旧值必然过期；⑤强一致场景可考虑读写串行或用分布式锁，但代价高。核心是「最终一致」的思路。

**场景**

项目里用「先更库后删缓存 + 缓存设 TTL」的组合，把不一致概率和时间窗口都压到最低。

**常见追问**

- TTL 兜底为什么重要？（即使删缓存失败，旧值也会到期）
- 强一致能保证吗？（缓存架构下很难，通常接受最终一致）

**易错点**

重点是「降低概率 + 最终一致」，别承诺「完全一致」；TTL 是最简单有效的兜底。

## 341. 什么是延迟双删？

**面试回答**

延迟双删是「删除缓存两次」的策略：先删缓存 → 更新数据库 → 延迟一小段时间后再删一次缓存，用来消除「并发读回填旧数据」导致的不一致。

**理解**

针对「先删缓存后更库」时并发读会把旧数据回填的问题：第一次删缓存后更新库，此时可能有读请求把旧值回填进缓存；等一小段时间（让这些读操作完成），再删一次缓存，把可能被回填的旧值清掉，之后读到的就是新数据。第二次删是「补刀」。

**场景**

项目里对一致性要求较高的场景，可用延迟双删兜底，消除并发回填旧值的问题。

**常见追问**

- 为什么要延迟？（等并发读回填旧值的操作完成）
- 延迟双删能完全解决不一致吗？（能大幅降低，但仍非绝对，需配合 TTL）

**易错点**

延迟双删是「删两次」，第二次延迟删是清掉「可能被回填的旧值」；它是缓解手段，不是银弹。

## 342. 什么是缓存预热？

**面试回答**

缓存预热是系统启动或上线前，提前把热点数据加载进缓存，让用户第一次请求就能命中缓存，避免冷启动时大量请求直接打到数据库。

**理解**

刚上线时缓存是空的，大量并发请求会同时未命中、集中打库，可能压垮数据库（类似缓存击穿/雪崩）。预热就是提前跑一遍加载逻辑，把常用数据（如菜品、首页数据）提前塞进 Redis，上线后直接命中。常见于大促、发布前。

**场景**

项目里上线前可预热热门菜品、套餐数据到 Redis，避免启动后瞬间流量全打到 MySQL。

**常见追问**

- 预热解决什么？（避免冷启动瞬间打库）
- 怎么预热？（启动时/上线前批量加载热点数据进缓存）

**易错点**

缓存预热是「提前加载热点数据」，目的是避免「空缓存 + 高并发」瞬间压垮数据库，别和「缓存回填」混淆。
