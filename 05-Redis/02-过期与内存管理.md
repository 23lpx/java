# 过期与内存管理

## 320. Redis 中的数据过期后会立即删除吗？

**面试回答**

不一定立即删除。Redis 采用「惰性删除 + 定期删除」组合策略，过期 Key 可能不会在到期瞬间被删，而是被访问时删或定期批量删。

**理解**

Redis 不维护一个「到期就立即删」的高精度定时器（那样开销大）。而是：①惰性删除——访问某个 Key 时发现它过期了就删；②定期删除——周期性随机抽查一批 Key，删掉其中过期的。两者结合，既不浪费资源，又保证过期 Key 最终被清理。

**场景**

项目里缓存的菜品到期后，可能不会立刻释放内存，而是在被访问或定期扫描时才真正删除。

**常见追问**

- 为什么不一到期就删？（维护大量定时器开销大）
- 那怎么保证删掉？（惰性删除 + 定期删除兜底）

**易错点**

「过期即删」是误解；Redis 是「惰性 + 定期」删除，所以可能出现「过期了但内存还没释放」的情况。

## 321. Redis 有哪些过期删除策略？

**面试回答**

两种主要策略：惰性删除和定期删除（配合使用），另外内存不足时还有内存淘汰策略。

**理解**

惰性删除：访问 Key 时才检查是否过期，过期就删，省资源但可能有「过期 Key 一直没人访问就占内存」。定期删除：每隔一段时间随机抽取一批 Key，检查并删除其中过期的，主动清理但不全量扫。两者互补。内存淘汰策略（maxmemory）是另一种机制，在内存满时淘汰数据。

**场景**

项目里缓存 Key 过期后，靠惰性 + 定期删除逐步清理；内存吃紧时由淘汰策略兜底。

**常见追问**

- 惰性和定期的区别？（访问时删 vs 定时扫描删）
- 过期删除和内存淘汰是一回事吗？（不是，过期删除针对过期 Key，淘汰针对内存满）

**易错点**

「过期删除」（惰性 + 定期）和「内存淘汰」（内存满时）是两套机制，别混淆。

## 322. 什么是惰性删除？

**面试回答**

惰性删除是「访问时才检查」的删除策略：当访问某个 Key 时，Redis 发现它已过期，就顺手删除并返回不存在，而不是主动定时去删。

**理解**

「惰性」体现在不主动花 CPU 去扫描，而是把检查放在读 Key 的路径上。优点是省资源（不访问就不处理）；缺点是如果过期 Key 一直没人访问，就会一直占着内存不释放。所以单独用惰性删除不够，需要配合定期删除。

**场景**

项目里过期的验证码，如果没人再访问，可能还占着内存，直到被访问或定期扫描清理。

**常见追问**

- 惰性删除的优点？（省资源，不主动扫描）
- 缺点？（过期 Key 不被访问就一直占内存）

**易错点**

惰性删除是「被动、访问时才删」，它的短板是「冷门过期 Key 占内存」，所以要配定期删除。

## 323. 什么是定期删除？

**面试回答**

定期删除是 Redis 周期性、随机抽取一批 Key 检查并删除其中过期的 Key 的主动清理策略，用来弥补惰性删除的不足。

**理解**

Redis 每隔一段时间（默认约 100ms 一次）执行过期扫描：随机抽一部分带 TTL 的 Key，检查并删除过期的。它「主动但不全量」——随机抽是为了避免一次性扫描全库阻塞服务。这样既主动清理过期 Key，又不至于卡住主线程。

**场景**

项目里大量缓存 Key 过期时，定期删除会分批随机清理，保证过期 Key 最终被回收。

**常见追问**

- 为什么随机抽不全量扫？（避免长时间阻塞主线程）
- 定期删除解决什么？（惰性删除下冷门过期 Key 不清理的问题）

**易错点**

定期删除是「周期性随机抽查」，不是「定时全量扫描」，目的是在清理和性能间平衡。

## 324. 为什么 Redis 不只使用一种删除策略？

**面试回答**

因为单一策略都有明显缺陷：只惰性删除会让冷门过期 Key 一直占内存；只定期删除要么扫描开销大要么清理不及时，两者结合才能兼顾资源和内存。

**理解**

惰性删除省 CPU 但可能漏掉冷门 Key；定期删除主动清理但不能全量（全量会阻塞），只能随机。两者互补：惰性删除保证「访问到的过期 Key 立刻消失」，定期删除保证「不被访问的过期 Key 也最终被清」。这是一种「性能与内存」的平衡设计。

**场景**

项目里正是靠这两种策略配合，Redis 才能在「不浪费 CPU」和「及时回收内存」之间取得平衡。

**常见追问**

- 只用惰性删除会怎样？（冷门过期 Key 永久占内存）
- 只用定期删除全量扫会怎样？（阻塞主线程，卡顿）

**易错点**

两种策略是「互补」关系，各补对方短板，理解这点就知道为什么不能只用一种。

## 325. Redis 内存满了怎么办？

**面试回答**

Redis 会按配置的内存淘汰策略（maxmemory-policy）自动淘汰一些数据，为新写入腾出空间，而不是直接报错或崩溃。

**理解**

当内存达到 maxmemory 上限，Redis 根据淘汰策略选 Key 删除：可能是淘汰过期 Key、淘汰最近最少用的（LRU）、最不常用的（LFU）、或随机淘汰等。合理配置淘汰策略能保证 Redis 在内存满时依然可用、不 OOM。

**场景**

项目里给 Redis 设了 maxmemory 和淘汰策略（如 allkeys-lru），内存快满时自动淘汰不常用的缓存 Key。

**常见追问**

- maxmemory 是什么？（内存上限配置）
- 淘汰策略怎么定？（看业务，缓存场景常用 allkeys-lru）

**易错点**

内存满时 Redis 靠「淘汰策略」自动腾空间，不是直接崩；但若策略设成 noeviction（不淘汰），写入会报错。

## 326. 什么是内存淘汰策略？

**面试回答**

内存淘汰策略是 Redis 在内存达到上限时，决定「淘汰哪些 Key」的规则，通过 maxmemory-policy 配置。

**理解**

当内存满了要写入新数据，必须有 Key 被删掉腾位置，淘汰策略就是「删谁」的规则。分类：①不淘汰（noeviction，报错）；②针对所有 Key 的（allkeys-lru/lfu/random）；③只针对设置了过期时间的 Key（volatile-lru/lfu/random/ttl）。选哪种看业务是「纯缓存」还是「也存重要数据」。

**场景**

项目里 Redis 主要做缓存，配 allkeys-lru，内存满时优先淘汰最久没用的 Key。

**常见追问**

- allkeys 和 volatile 区别？（allkeys 可淘汰所有 Key，volatile 只淘汰设了 TTL 的）
- 为什么缓存常用 allkeys-lru？（缓存数据都可淘汰，LRU 淘汰冷数据）

**易错点**

淘汰策略分「不淘汰 / 全 Key / 只过期 Key」三大类，要理解 allkeys 和 volatile 的区别。

## 327. Redis 有哪些常见的内存淘汰策略？

**面试回答**

常见的有：noeviction（不淘汰，报错）、allkeys-lru、allkeys-lfu、allkeys-random、volatile-lru、volatile-lfu、volatile-random、volatile-ttl。

**理解**

noeviction 内存满时拒绝写入；allkeys-* 系列可淘汰所有 Key（缓存常用）；volatile-* 系列只淘汰设了过期时间的 Key（保护永久数据）。lru 按「最近最少使用」淘汰，lfu 按「最不常使用」淘汰，random 随机，ttl 优先淘汰剩余时间最短的。

**场景**

项目里纯缓存用 allkeys-lru；如果 Redis 还存了不能丢的数据，用 volatile-lru 保护它们。

**常见追问**

- allkeys-lru 和 volatile-lru 区别？（前者可淘汰所有 Key，后者只淘汰有 TTL 的）
- noeviction 会怎样？（内存满时写入报错）

**易错点**

关键区分「allkeys（可淘汰所有）」和「volatile（只淘汰过期 Key）」；缓存场景一般用 allkeys-lru。

## 328. LRU 是什么？

**面试回答**

LRU（Least Recently Used）是「最近最少使用」淘汰算法：优先淘汰「最久没被访问过」的数据，认为最近没用的数据将来也不太可能用。

**理解**

LRU 基于「时间局部性」——最近访问过的数据更可能再被访问，所以淘汰「最久没碰的」。Redis 的 LRU 是「近似 LRU」，不是精确的（为省开销，随机抽样一部分 Key 找最久未用的），但效果接近。适合「热点数据随时间变化」的缓存场景。

**场景**

项目里缓存用 allkeys-lru，内存满时淘汰最久没被访问的缓存，保留热点数据。

**常见追问**

- LRU 全称？（Least Recently Used）
- Redis 的 LRU 精确吗？（近似 LRU，随机抽样近似）

**易错点**

LRU 看的是「最近是否被访问」，和 LFU 看「访问频率」不同；Redis 实现是近似 LRU，别说是精确的。

## 329. LFU 是什么？

**面试回答**

LFU（Least Frequently Used）是「最不经常使用」淘汰算法：优先淘汰「访问次数最少」的数据，认为用得少的数据价值低。

**理解**

LFU 统计每个 Key 的访问频率，淘汰频率最低的。它和 LRU 的区别：LRU 看「最近用没用」（时间），LFU 看「用了多少次」（频率）。LFU 能避免「偶发访问的热数据被误淘汰」，适合有明确冷热分层、要保护高频数据的场景。

**场景**

项目里如果缓存里有些「偶尔被扫到但长期高频」的数据，用 LFU 能更好保护真正高频的 Key。

**常见追问**

- LFU 全称？（Least Frequently Used）
- LFU 和 LRU 区别？（频率 vs 时间：LFU 淘汰访问次数少的，LRU 淘汰最久没访问的）

**易错点**

LFU 按「访问频率」、LRU 按「最近访问时间」，这是两者核心区别，别混为一谈。
