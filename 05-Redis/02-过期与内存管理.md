# 过期与内存管理

## 320. Redis 中的数据过期后会立即删除吗？

**面试回答**

不保证到期瞬间完成物理删除。TTL 到期后，Key 在命令语义上应当视为不存在；Redis 会在客户端访问它时执行被动过期，并通过后台的主动过期周期抽样清理无人访问的过期 Key。因此“逻辑不可见”与“从 Keyspace 移除、内存完成释放”可能不是同一时刻。

**原理与理解**

如果为每个 Key 建立高精度定时任务，到期事件和调度成本会随 Key 数量快速增长。Redis 采用被动过期与主动过期组合：访问路径发现 Key 已超时就将其过期；后台周期则从带过期时间的 Key 中检查候选并清理。删除大对象时，是否由主线程同步释放内存，还受 `lazyfree-lazy-expire` 等配置影响；异步释放可以先从 Keyspace 解除关联，再由后台线程回收对象内存。

**成立条件与边界**

- 到期 Key 不应继续作为有效业务数据返回，但进程内存不一定在同一微秒下降。
- 主动过期是受 CPU 与延迟预算约束的渐进过程，不承诺在固定时限内清空全部过期 Key。
- 大 Key 同步过期释放可能造成延迟；启用异步释放也会把回收成本转移到后台队列，并非零成本。
- 过期在复制和持久化链路中有专门传播语义，不能从副本瞬时内存状态推导所有节点已同时物理删除。
- Redis 使用绝对时间戳保存过期信息，系统时间异常会影响过期判断。

**实际场景**

**生产能力：** 发现 TTL 已到但 RSS 没有立即下降时，应区分尚待主动清理、异步释放队列、内存分配器未归还操作系统以及内存碎片，结合 `expired_keys`、内存指标和延迟监控判断，不能只据 RSS 认定 Key 仍可读。

**常见追问**

- 过期后还能 `GET` 到吗？正常命令语义下应返回不存在；物理内存是否已释放是另一问题。
- 为什么不为每个 Key 建定时器？大量独立定时事件会增加内存、调度与 CPU 开销。
- 大 Key 过期会不会阻塞？默认同步释放可能产生延迟，可评估异步过期释放，但仍需治理大 Key。

**易错点**

- 把“TTL 到期”直接说成“到期瞬间完成物理删除”。
- 看到内存未下降就认为过期 Key 仍会被正常读取。
- 忽略异步释放、内存碎片和分配器行为对 RSS 的影响。

## 321. Redis 有哪些过期删除策略？

**面试回答**

Redis 官方通常表述为两类过期机制：被动过期（passive expiration）和主动过期（active expiration）。被动过期在访问 Key 时发现超时并处理；主动过期在后台周期性检查带 TTL 的候选 Key，清理即使不再被访问的过期数据。内存淘汰是达到 `maxmemory` 后选择 Key 腾空间的另一套机制，不属于过期策略。

**原理与理解**

被动过期把检查成本放在访问路径上，能保证被访问的已过期 Key 不作为有效数据返回；主动过期负责回收“以后再也没人访问”的 Key。主动周期不会简单全量扫描所有 Key，而是以采样和时间预算控制工作量，在内存回收、CPU 消耗与请求延迟之间折中。

**成立条件与边界**

- “被动 + 主动”描述的是 TTL 到期处理，不等于 `DEL`、`UNLINK` 或 `maxmemory-policy`。
- 两种机制共同工作仍可能让一部分逻辑过期 Key 暂时占用物理内存。
- 主动过期行为会受 Redis 版本、`hz`、动态频率和 `active-expire-effort` 等配置影响。
- Key 从 Keyspace 删除与对象内存同步/异步回收是两个层次。
- 没有 TTL 的 Key 不会因过期机制消失，但可能被 `allkeys-*` 淘汰策略选中。

**实际场景**

**项目核验项：** 项目使用了 Redis 缓存，但现有材料没有服务端版本、`hz`、`active-expire-effort` 或 lazy-free 配置；面试只能说明 Redis 的通用机制，不能声称项目主动调整过这些参数。

**常见追问**

- 被动过期和主动过期分别解决什么？前者保证访问到的过期 Key 不可用，后者回收无人访问的过期 Key。
- 过期与淘汰有什么区别？过期由 TTL 决定；淘汰由内存上限、候选集合和策略决定，Key 可能尚未过期。
- 主动过期会全库扫描吗？不会采用每轮全量扫描，而是渐进检查候选并控制执行预算。

**易错点**

- 把内存淘汰列为第三种“过期删除策略”。
- 把主动过期说成固定间隔的全量扫描。
- 认为两种过期机制可以保证到期后内存立即归还操作系统。

## 322. 什么是惰性删除？

**面试回答**

“惰性删除”更准确可称为被动过期：客户端命令尝试访问某个 Key 时，Redis 检查其过期时间；如果已经超时，就按不存在处理并触发过期删除。它避免主动逐个检查所有 Key，但仅靠它无法及时发现永远不再被访问的过期数据。

**原理与理解**

Redis 在访问 Key 的路径上进行有效性判断，因此过期数据不会因为尚未被后台抽中就正常返回。该机制按实际访问付费：热点过期 Key 很快会被发现，冷门过期 Key 则可能继续占据内存，直到主动过期周期处理。它并不是“访问后先返回旧值，再顺手删除”。

**成立条件与边界**

- “访问”应理解为会触达该 Key 的 Redis 命令路径，不应只局限为应用的 `GET`。
- 被动过期保证的是命令可见性，不承诺对象内存立即同步释放。
- 冷 Key 不再访问时，被动机制不会自行发现它，必须依赖主动过期。
- 主从复制下，过期事件由主节点集中传播，副本处理细节不能简化成每个节点独立被动删除。
- 过期检查有时间和命令语义边界，不能将底层内部结构的存在当作业务可见。

**实际场景**

**通用工程：** 一个短期缓存到期后首次被查询，Redis 会把它当作 Miss；应用按缓存模式决定是否回源和重建。并发回源控制属于缓存层设计，不是被动过期机制自动提供的能力。

**常见追问**

- 被动过期的优点是什么？只在实际访问时付出检查成本，避免为所有 Key 单独调度到期任务。
- 缺点是什么？无人访问的过期 Key 不能靠它及时回收。
- 会先返回过期值吗？正常 Key 命令不会把已判定过期的值作为有效结果返回。

**易错点**

- 回答“惰性删除就是读到旧值后再删”。
- 说冷门过期 Key 会永久占用内存；主动过期还会继续处理它，只是没有瞬时清理保证。
- 把缓存 Miss 后如何回源归到 Redis 过期算法本身。

## 323. 什么是定期删除？

**面试回答**

“定期删除”更准确可称为主动过期：Redis 在后台周期中检查带过期时间的候选 Key，并删除已经超时的 Key，用来处理不会再被客户端访问的数据。它是受时间预算约束的渐进、自适应清理，不是每隔固定 100ms 对整个数据库做一次全量扫描。

**原理与理解**

Redis 的服务器周期会执行过期维护工作，`hz` 是后台任务频率的基线，现代配置还默认启用动态 `hz`；主动过期会根据采样结果决定是否继续投入工作，并受延迟/CPU预算限制。`active-expire-effort` 可提高过期清理力度，但代价是更多 CPU、更长周期以及潜在延迟，因此不能为了“删得干净”无条件调高。

**成立条件与边界**

- 默认 `hz 10` 不能简单翻译成“严格每 100ms 删除一次”，因为任务调度、动态 `hz` 和执行预算都会影响实际行为。
- 主动过期检查的是带 TTL 的候选集合，不是无条件遍历全部 Key。
- 一次集中设置大量相同 TTL 会同时增加过期清理和缓存回源压力；两者需要分别治理。
- 提高 `active-expire-effort` 是内存、CPU 与延迟的权衡，应通过指标和压测决定。
- 主动过期减少残留，不提供严格的物理删除截止时间。

**实际场景**

**生产能力：** 如果 `expired_keys` 快速增长、实例 CPU 与 P99 同时抬升，应检查是否同批 Key 集中过期、大 Key 释放、主动过期力度和回源请求叠加；不能只把 `hz` 调高后结束排查。

**常见追问**

- 默认是不是每 100ms 扫一次？`hz` 默认基线通常为 10，但不能据此描述为严格固定 100ms 的全库扫描。
- 为什么不全量扫描？避免 Key 数量大时长期占用执行时间并制造延迟尖峰。
- `active-expire-effort` 越高越好吗？不是，清理更积极的同时会消耗更多 CPU，并可能增加延迟。

**易错点**

- 背诵“每 100ms 随机扫描”而不说明它只是过度简化。
- 把主动周期理解成精确的定时删除器。
- 只关注过期 Key 数量，不看大 Key 释放与回源流量。

## 324. 为什么 Redis 不只使用一种删除策略？

**面试回答**

因为两种机制解决的约束不同：只用被动过期，永不再访问的过期 Key 会持续占用内存；只靠主动过期，如果要求准时且全量检查，会消耗大量 CPU并产生延迟，而限制预算后又不能立即发现全部过期 Key。组合使用可以同时保证访问语义并渐进回收冷数据，在 CPU、延迟和内存之间取得平衡。

**原理与理解**

被动过期以访问为触发，处理热点最直接；主动过期按后台预算处理冷数据。两者形成互补，但并没有消除所有工程问题：同一时刻过期的大量 Key 仍可能造成回收和回源尖峰，大对象释放仍可能阻塞，内存分配器也可能不立即把空闲页归还操作系统。

**成立条件与边界**

- 组合机制追求折中，不是“保证过期 Key 立即且最终在确定时间内物理释放”。
- TTL 分布、Key 大小、CPU余量和延迟目标会影响清理效果。
- 过期回收解决 Redis 内存生命周期，不解决缓存重建的并发与下游保护。
- lazy-free 可以降低部分同步释放延迟，但会增加后台回收积压与额外内存峰值风险。
- 内存淘汰仍是独立的容量保护机制，不能由主动/被动过期完全替代。

**实际场景**

**通用工程：** 批量预热缓存时，应根据业务允许范围打散 TTL，并限制 Value 大小和重建并发。这样同时减轻主动过期、内存释放和数据库回源压力，而不是指望两种删除机制自动吸收峰值。

**常见追问**

- 只用被动过期会怎样？无人访问的过期数据无法靠访问路径发现，内存回收不及时。
- 只用主动过期为什么不行？若追求全量准时检查会占用大量执行时间；受预算限制又无法保证瞬时清空。
- 组合后还会有过期残留吗？可能暂时存在物理内存残留，但正常命令不应把已过期 Key 作为有效数据返回。

**易错点**

- 说组合后过期 Key 一定“马上”或在固定时间内全部释放。
- 把过期清理与缓存雪崩、回源互斥混成一个机制。
- 忽略异步释放队列也会消耗 CPU 和内存。

## 325. Redis 内存满了怎么办？

**面试回答**

要看是否设置 `maxmemory`、选择了什么 `maxmemory-policy`，以及是否存在可淘汰候选。达到上限后，Redis 可按淘汰策略删除候选 Key；如果使用默认的 `noeviction`，或 volatile 策略下没有带 TTL 的候选，则需要增加内存的命令会返回错误，读取通常仍可继续。配置上限也不等于进程绝不会 OOM，还要为复制/AOF 缓冲、碎片和其他开销预留空间。

**原理与理解**

Redis 在会增加数据占用的命令执行前后检查内存，并根据策略持续选择候选，努力把计入淘汰判断的内存降回上限。一次写入大量数据时可能暂时明显超过 `maxmemory`。此外，复制和 AOF 等部分缓冲内存不会计入用于触发淘汰的统计，操作系统看到的 RSS 也会受分配器和碎片影响，所以 `maxmemory` 应低于机器可用内存而不是顶格配置。

**成立条件与边界**

- 64 位 Redis 的 `maxmemory 0` 通常表示不限制数据集内存，最终可能由系统内存和 OOM Killer 决定。
- `noeviction` 不删除 Key，而是拒绝需要更多内存的命令；只读命令通常仍可工作。
- volatile 策略没有带 TTL 的候选时会表现得像 `noeviction`。
- 淘汰会造成缓存 Miss 和回源压力，不能把“服务仍能写”当成业务无损。
- 复制/AOF缓冲、客户端缓冲、模块、碎片和 fork 写时复制等都可能让实际内存高于 `maxmemory` 口径。

**实际场景**

**项目核验项：** 现有材料不能证明项目设置了 `maxmemory` 或 `allkeys-lru`。应从 Redis 配置和 `CONFIG GET` 核验，并结合 `used_memory`、`used_memory_rss`、`mem_not_counted_for_evict`、`evicted_keys` 与拒绝命令数建立告警。

**常见追问**

- 内存满会直接崩吗？不一定；有合适淘汰候选时可淘汰，`noeviction` 或无候选时相关写命令报错，但系统级内存不足仍可能导致 OOM。
- `maxmemory` 应设成机器全部内存吗？不应，要为进程开销、缓冲、碎片、持久化和操作系统预留空间。
- 淘汰成功就没问题了吗？不是，命中率下降和集中回源可能继续冲击下游。

**易错点**

- 回答“内存满一定自动淘汰，所以不会报错或 OOM”。
- 忽略 `maxmemory 0`、无候选和默认 `noeviction`。
- 只监控 `used_memory`，不看 RSS、碎片、缓冲与淘汰速率。

## 326. 什么是内存淘汰策略？

**面试回答**

内存淘汰策略是 Redis 达到 `maxmemory` 后，用来确定“是否淘汰、从哪些 Key 中选候选、按什么规则选择”的配置，由 `maxmemory-policy` 控制。它可以在所有 Key 或仅带 TTL 的 Key 中采用 LRU、LFU、随机、TTL 等规则，也可以选择 `noeviction` 拒绝增长型写入。

**原理与理解**

淘汰不是 TTL 到期：未过期 Key 也可能因容量不足被移除。`allkeys-*` 的候选范围是所有可淘汰 Key；`volatile-*` 只从设置了过期时间的 Key 中选择；具体算法再决定选哪个。Redis 的 LRU、LFU、TTL 以及新版本 LRM 都采用近似或采样方式，以控制精确维护全局顺序的内存和 CPU 成本。

**成立条件与边界**

- 策略应匹配访问分布和数据角色，不能只因“缓存常用”就机械选择 `allkeys-lru`。
- volatile 策略只是限制候选集合，不会保证永久 Key 对系统级 OOM、误删命令或故障绝对安全。
- 同一实例混放可丢缓存与不可丢数据会使容量、淘汰和恢复目标互相冲突，条件允许时应拆分实例。
- 淘汰算法是概率近似，不能承诺被选中的一定是全局最冷 Key。
- 策略改变后要观察命中率、`evicted_keys`、延迟和下游回源，而不是只看 Redis 写入成功率。

**实际场景**

**生产能力：** 纯缓存且热点符合时间局部性时，可把 `allkeys-lru` 作为候选；热点长期稳定时可对比 `allkeys-lfu`。最终选择应通过真实流量回放或灰度数据验证命中率和回源峰值。

**常见追问**

- `allkeys` 与 `volatile` 有什么区别？前者从所有 Key 中选，后者只从带 TTL 的 Key 中选。
- 淘汰和过期有什么区别？淘汰由容量压力触发，过期由 Key 的时间条件触发。
- volatile 能保护重要数据吗？它不主动选择无 TTL Key，但若无候选会拒绝写入，且仍不能替代持久化、备份与实例隔离。

**易错点**

- 把淘汰策略理解成“Key 到期后怎么删除”。
- 把 volatile 策略称为重要数据的可靠保护机制。
- 修改策略后不验证缓存命中率和数据库回源能力。

## 327. Redis 有哪些常见的内存淘汰策略？

**面试回答**

Redis 7.x 和 Redis 8.0～8.4 常见八种：`noeviction`；`allkeys-lru`、`allkeys-lfu`、`allkeys-random`；`volatile-lru`、`volatile-lfu`、`volatile-random`、`volatile-ttl`。Redis 8.6 起又增加 `allkeys-lrm` 和 `volatile-lrm`，按“最近最少修改”近似淘汰。回答时应先说明版本。

**原理与理解**

- `noeviction`：不淘汰；需要更多内存的命令返回错误。
- `allkeys-lru/lfu/random`：在所有 Key 中按最近使用、访问频率或随机方式选候选。
- `volatile-lru/lfu/random`：只在带 TTL 的 Key 中按相应方式选候选。
- `volatile-ttl`：只在带 TTL 的 Key 中，倾向选择剩余 TTL 更短的候选。
- Redis 8.6+ 的 `allkeys-lrm/volatile-lrm`：按最近修改而不是最近读写访问选候选。

这些近似策略依靠采样做选择；策略名描述的是候选范围和偏好，不是绝对精确排序。

**成立条件与边界**

- `volatile-*` 在没有带 TTL 候选时会像 `noeviction` 一样拒绝需要更多内存的命令。
- `volatile-ttl` 不是“只删除已经过期的 Key”，而是可以提前淘汰尚未到期但剩余 TTL 较短的 Key。
- Redis 8.6 之前没有 LRM 策略，不能把十种策略无版本地套到 Redis 7 面试题中。
- `allkeys-random` 在访问概率大致均匀时可能足够简单，但仍需用命中率验证。
- 所谓“常用”不等于默认；官方示例配置默认策略通常是 `noeviction`。

**实际场景**

**项目核验项：** 面试前应记录项目 Redis 版本、`maxmemory` 和 `maxmemory-policy` 的真实值。若拿不到部署配置，只能讨论策略选择思路，不能声称项目使用 `allkeys-lru`。

**常见追问**

- Redis 7 有多少种常见策略？经典八种；Redis 8.6+ 再增加两种 LRM。
- `volatile-ttl` 会删除过期 Key 吗？过期 Key 由过期机制处理；该策略在内存压力下优先考虑 TTL 更短的未过期候选。
- LRM 与 LRU 区别？LRU 的时间会因读写访问更新，LRM 只关注最近修改时间。

**易错点**

- 无视版本，固定回答“永远只有八种”。
- 把 `volatile-ttl` 解释为清理已经过期的 Key。
- 说默认策略是 `allkeys-lru`，或把项目策略写成未经核验的事实。

## 328. LRU 是什么？

**面试回答**

LRU 是 Least Recently Used，按“最近最少使用”预测未来价值：在内存淘汰候选中，倾向移除距离上次访问时间更久的 Key。Redis 为节省维护精确全局链表的成本，使用近似 LRU——随机采样候选并维护较优候选池，因此不能保证每次都选中全局最久未访问的 Key。

**原理与理解**

LRU 利用时间局部性：最近访问的数据通常更可能再次访问。Redis 记录近似访问时间，淘汰时从样本中比较，`maxmemory-samples` 可以调节近似质量与 CPU 成本。它只在相应 `allkeys-lru` 或 `volatile-lru` 策略触发淘汰时决定候选，不是后台不断主动删除“很久没访问”的 Key。

**成立条件与边界**

- 近似 LRU 可能淘汰并非全局最老的 Key，采样数越大通常越接近精确结果，但 CPU 成本更高。
- LRU 衡量最近一次访问，无法区分一次偶发扫描和长期高频热点。
- 顺序全量扫描可能刷新大量 Key 的访问时间，污染 LRU 判断并挤出真正热点。
- 只有达到内存压力并选择 LRU 策略时才会据此淘汰；“长期未访问”本身不会让无 TTL Key 自动消失。
- 是否适合应看真实访问分布和命中率，而不是只看算法名称。

**实际场景**

**通用工程：** 热点随最近用户行为快速变化的内容缓存通常符合时间局部性，可测试 `allkeys-lru`；如果离线任务周期性扫过全量 Key，要观察扫描是否污染访问热度并导致在线热点被误淘汰。

**常见追问**

- Redis 的 LRU 是精确 LRU 吗？不是，是采样和候选池实现的近似 LRU。
- LRU 和 TTL 有什么关系？TTL 决定时间过期；LRU 只在内存淘汰时按最近访问偏好选候选。
- `maxmemory-samples` 越大越好吗？近似通常更准确，但需要更多 CPU，应以命中率和延迟验证。

**易错点**

- 说 Redis 维护精确 LRU 链表并总能删掉全局最老 Key。
- 认为 Key 一段时间没访问就会被 LRU 自动删除。
- 忽略批量扫描对访问时间和淘汰效果的干扰。

## 329. LFU 是什么？

**面试回答**

LFU 是 Least Frequently Used，按访问频率估计 Key 的长期热度，在淘汰候选中倾向移除频率较低的 Key。Redis LFU 不是保存精确访问次数，而是使用小型概率计数器并配合时间衰减，再通过采样选择淘汰候选，使历史热点在停止访问后能够逐渐降温。

**原理与理解**

如果直接保存无界精确计数，元数据和更新成本会较高，也会让很久以前的高频 Key 永远占优。Redis 使用对数型概率递增计数器：访问越多，继续加一的概率越低；`lfu-decay-time` 让长期未访问 Key 的估计频率逐步下降，`lfu-log-factor` 控制不同访问量区间的分辨率。`allkeys-lfu` 和 `volatile-lfu` 再从相应候选集合中近似选择低频 Key。

**成立条件与边界**

- LFU 计数不是业务访问量统计，不能拿来做计费、排行榜或精确分析。
- LFU 仍是近似算法：概率计数、衰减和采样都可能使选择结果不同于精确全局最小频率。
- 新旧热点切换速度取决于衰减参数；衰减太慢会保留历史热点，太快又可能失去长期热度优势。
- LFU 适合持续热点明显的访问分布，不保证在所有工作负载下比 LRU 命中率高。
- 参数应从默认值开始，通过流量与 `OBJECT FREQ` 等观测验证，不应凭感觉调整。

**实际场景**

**生产能力：** 对“少量 Key 长期承担大部分请求”的缓存，可灰度比较 `allkeys-lfu` 与 LRU 的命中率、淘汰速率和数据库回源；若热点随时间快速轮换，还要确认衰减速度能及时适应。

**常见追问**

- LFU 与 LRU 的核心区别？LFU估计访问频率，LRU关注最近访问时间；两者在 Redis 中都是近似淘汰。
- Redis LFU 是精确计数吗？不是，使用概率计数器、衰减和采样。
- 为什么需要衰减？让过去的热点在停止访问后逐渐降低权重，适应流量变化。

**易错点**

- 把 LFU 元数据当成 Key 的精确累计访问次数。
- 说 LFU 一定比 LRU 更先进、命中率更高。
- 忽略 `lfu-log-factor`、`lfu-decay-time` 与访问模式的匹配。
