# Redis进阶

## 583. Redis 主从复制是什么？

**面试回答**

主从复制是让一个 Redis 主节点（master）的数据自动同步到多个从节点（slave/replica），从节点保存数据副本，实现数据冗余和读写分离。

**理解**

主节点负责写，写操作会通过复制同步给从节点；从节点只读，可以从主节点复制数据。这样一份数据有多份副本，既能做主节点故障时的备份，也能让读请求分摊到从节点。是 Redis 高可用和扩展的基础。

**场景**

项目里 Redis 用主从复制：主节点处理写，从节点承担读流量，并作为主节点故障时的数据备份。

**常见追问**

- 主从复制解决什么？（数据冗余、读写分离）
- 从节点能写吗？（默认只读）

**易错点**

主从复制是「数据副本 + 读写分离」，但不解决「主节点宕机自动切换」（那要靠 Sentinel/Cluster）。

## 584. 为什么需要主从复制？

**面试回答**

①数据冗余：主节点挂了从节点还有数据，降低数据丢失风险；②读写分离：读请求分摊到从节点，提升读吞吐；③为高可用（哨兵/集群）打基础。

**理解**

单机 Redis 有单点风险（宕机全挂、性能有限）。主从复制让数据有多份副本，读压力分散到多个节点，也为后续「故障自动切换」（哨兵）提供数据基础。是 Redis 从「单机」走向「高可用/可扩展」的第一步。

**场景**

项目里数据量大、读多写少时，用主从复制把读分摊到从节点，同时保证数据有备份。

**常见追问**

- 读写分离怎么实现？（主写、从读）
- 主从复制能自动切换主节点吗？（不能，需要哨兵）

**易错点**

主从复制解决「冗余 + 读写分离」，但本身不做「自动故障转移」；别把它和哨兵/集群的功能混淆。

## 585. Redis Sentinel 是什么？

**面试回答**

Sentinel（哨兵）是 Redis 的高可用方案：一组哨兵进程监控主从节点，主节点故障时自动选举一个从节点提升为新主节点，实现故障自动转移。

**理解**

主从复制本身不会自动切换主节点，Sentinel 补上这块：它持续监控 master 状态，发现 master 挂了，多个哨兵投票选出新 master，通知其他从节点跟随新主，并通知客户端新地址。这样主节点宕机后服务能自动恢复，实现高可用。

**场景**

项目里用哨兵监控 Redis 主从，主节点故障时自动切换，保证缓存服务不中断。

**常见追问**

- Sentinel 解决什么？（主节点故障自动切换，高可用）
- 和主从复制什么关系？（主从复制是数据基础，Sentinel 做故障转移）

**易错点**

Sentinel 是「故障自动转移」的高可用方案，不是「分片存储」；数据还在主从里，Sentinel 只负责「盯梢和切换」。

## 586. Redis Cluster 是什么？

**面试回答**

Redis Cluster 是 Redis 的分布式集群方案，把数据按哈希槽（slot）分片存储到多个主节点上，支持水平扩展和部分节点故障时的自动容错。

**理解**

Cluster 解决「单机存不下、写吞吐不够」的问题：把 key 通过 CRC16 哈希到 16384 个 slot，分配到不同主节点，每个节点只存一部分数据。这样数据分散、读写分摊到多节点，可水平扩展。它自带主从和故障转移。适合数据量大、需扩展的场景。

**场景**

项目里 Redis 数据量大到单机存不下时，用 Cluster 分片，水平扩展存储和吞吐。

**常见追问**

- Cluster 解决什么？（数据分片、水平扩展）
- 和哨兵区别？（哨兵是单套数据的高可用，Cluster 是数据分片的分布式）

**易错点**

Cluster「分片 + 扩展」，Sentinel「单套数据的高可用」；两者目标不同，别混淆。

## 587. 什么是 Redis 分布式锁？

**面试回答**

Redis 分布式锁是用 Redis 实现的一种「跨进程/跨机器」的互斥锁：多个服务实例通过争抢同一个 Redis key 来保证同一时刻只有一个实例能执行某段逻辑。

**理解**

在分布式环境下，单机锁（synchronized、Lock）只对同一 JVM 有效，管不住多个服务实例。分布式锁用 Redis 的原子命令（如 SET NX EX）让所有实例争抢同一个 key：谁 set 成功谁拿到锁，执行完删除 key 释放锁。用于防止并发重复操作（如超卖、重复提交）。

**场景**

项目里用 Redis 分布式锁解决缓存击穿（只让一个请求回源）、防止并发下单超卖等。

**常见追问**

- 为什么不用单机锁？（分布式多实例，单机锁管不住）
- 分布式锁关键点？（互斥、释放、防死锁）

**易错点**

分布式锁是「跨实例的互斥」，靠 Redis 原子命令实现；它不是给单机用的，单机场景用普通锁即可。

## 588. 为什么 `SETNX` 可以实现简单分布式锁？

**面试回答**

因为 SETNX（SET if Not eXists）是原子操作：只有在 key 不存在时才设置成功，所以多个实例同时抢同一个 key 时，只有一个能设置成功（拿到锁），其他的失败。

**理解**

分布式锁的核心是「互斥」，即同一时刻只有一个实例能成功。SETNX 保证了「判断 key 不存在 + 设置」是原子的，不会出现两个实例都判断成功。谁 set 成功谁就持有锁，执行完 DEL 删除释放。所以 SETNX 天然适合做「简易互斥锁」。

**场景**

项目里简单场景用 SETNX 抢锁，拿到的执行、执行完释放，实现基本互斥。

**常见追问**

- SETNX 全称？（SET if Not eXists）
- 为什么必须原子？（避免两个实例同时判断成功）

**易错点**

SETNX 能实现「简单」分布式锁，但它有缺陷（不能设过期、可能死锁），生产要用 `SET NX EX` 或 Redisson。

## 589. 简单的 `SETNX` 分布式锁存在哪些问题？

**面试回答**

①没设置过期时间，持锁者崩溃后锁永远不释放（死锁）；②锁和释放不原子，可能误删别人的锁；③没处理「锁过期了但业务还没执行完」的情况。

**理解**

纯 SETNX 只做了「抢锁」，没做「安全和可靠」：如果持锁进程崩溃，key 不删除，其他实例永远拿不到锁（死锁）；释放时直接 DEL 可能删掉「已经过期被别人重新获取」的锁；锁过期时间难定，业务执行超时锁就失效了。所以要用 `SET key value NX EX ttl` + 释放时校验 value（或用 Redisson 的看门狗）。

**场景**

项目里用分布式锁时，不会用裸 SETNX，而是用带过期时间的 SET NX EX 或 Redisson，避免死锁和误删。

**常见追问**

- 怎么避免死锁？（设过期时间 EX）
- 怎么避免误删？（释放时校验 value 是否是自己设置的）

**易错点**

裸 SETNX 的三大坑「死锁、误删、锁超时」要能说清；生产建议 SET NX EX 或 Redisson。

## 590. Redisson 是什么？

**面试回答**

Redisson 是一个基于 Redis 的 Java 客户端/框架，封装了分布式锁、集合、队列等高级功能，尤其提供了可靠、易用的分布式锁实现（含看门狗自动续期）。

**理解**

Redisson 不只是个连接客户端，它在 Redis 之上提供了分布式对象和服务：RLock 分布式锁（支持可重入、自动续期、公平锁等）、RMap、RQueue 等。它的分布式锁解决了裸 SETNX 的问题——用 Lua 脚本保证原子性、用「看门狗」机制给锁自动续期，防止业务没执行完锁就过期。

**场景**

项目里需要可靠分布式锁时用 Redisson 的 RLock，避免自己处理锁的过期、续期、误删等复杂问题。

**常见追问**

- Redisson 和 Lettuce/Jedis 区别？（Redisson 是高级框架，提供分布式锁等；Lettuce/Jedis 是底层客户端）
- Redisson 的看门狗做什么？（自动续期，防止锁提前过期）

**易错点**

Redisson 是「Redis 之上的高级框架」，不是简单客户端；它的分布式锁是可靠方案，核心卖点是「自动续期（看门狗）」。
