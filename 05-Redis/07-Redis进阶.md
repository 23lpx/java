# Redis进阶

## 583. Redis 主从复制是什么？

**面试回答**

Redis 主从复制是由一个主节点把数据变更同步给一个或多个副本节点的机制。Redis 现在通常称 primary/replica，旧资料也写 master/slave；它为数据冗余、只读扩展和后续故障转移提供基础。

**原理与理解**

复制默认是异步的。副本首次同步或无法续接时执行全量同步，主节点生成并传输数据集后再发送期间积累的增量；连接短暂中断且复制 ID、offset 与 backlog 条件满足时，可以通过 `PSYNC` 做部分重同步。

**成立条件与边界**

副本默认只读，但读取可能落后于主节点，不天然满足读己之写或强一致。主节点确认写入时通常不等待副本，所以已确认写入仍可能在故障转移中丢失；仅配置复制也不会自动选举和通知客户端切换新主节点。

**实际场景（项目核验项）**

简历只能确认使用 Redis，不能证明部署了主从复制或做过读写分离。应从拓扑、客户端读策略、复制延迟和故障演练记录核验，不能把通用架构写成项目事实。

**常见追问**

- 全量同步和部分同步有什么区别？（前者传输完整数据集，后者从 replication backlog 补齐缺失增量）
- `WAIT` 能把 Redis 变成强一致系统吗？（不能，只能等待指定副本确认并降低部分故障下的丢写概率）

**易错点**

不要把 replica 叫作独立备份：误删除和错误写入也会复制过去；它是当前状态副本，历史备份仍需单独设计。

## 584. 为什么需要主从复制？

**面试回答**

主从复制主要提供三类能力：保留当前数据副本以降低单点风险，把允许陈旧的读取分摊到副本，以及为 Sentinel 或 Cluster 的副本提升准备候选节点。

**原理与理解**

复制使一个主节点的写入流在其他节点重放。增加副本可以扩展部分读负载，却不会横向扩展单个主节点的写吞吐；当副本提升为新主节点时，复制进度决定它能恢复到多新的状态。

**成立条件与边界**

读写分离只有在业务允许复制延迟时才合适，强一致读取、写后立即读取和会话状态要明确路由策略。副本过多还会增加主节点网络、同步和运维成本，不能只按“副本越多越安全”配置。

**实际场景（通用工程）**

商品展示或统计查询可评估副本读；权限变更、库存扣减后的确认读取通常更谨慎。上线前需要测量复制 lag，并定义副本断链时是返回旧值、切回主节点还是直接失败。

**常见追问**

- 加副本能提高写吞吐吗？（通常不能，写入仍由主节点处理并复制）
- 有副本就能自动故障转移吗？（不能，还需要 Sentinel、Cluster 或托管服务控制面）

**易错点**

不要把“数据有副本”直接等同于“数据不会丢”；异步复制存在窗口，而且逻辑错误会传播到所有副本。

## 585. Redis Sentinel 是什么？

**面试回答**

Redis Sentinel 是面向非分片主从拓扑的高可用控制组件，负责监控、故障通知、自动故障转移，并向支持 Sentinel 的客户端提供当前主节点地址。

**原理与理解**

Sentinel 先由单个实例判断主节点主观下线，再由达到 `quorum` 的 Sentinel 形成客观下线判断；真正授权故障转移还需要 Sentinel 多数派。随后选择合适副本提升为新主节点，重配其他副本与旧主节点，并让客户端发现新配置。

**成立条件与边界**

Sentinel 不做数据分片，也不保证零停机或零丢写。Redis 官方建议至少三个 Sentinel 分布在相互独立的故障域；客户端必须实现 Sentinel 发现和重连。异步复制下，被提升副本可能未收到最新写入。

**实际场景（项目核验项）**

项目是否使用 Sentinel 必须从部署清单、`sentinel monitor` 配置和客户端连接方式核验。即使存在哨兵进程，也要验证 quorum、多数派、故障域和真实切换时间。

**常见追问**

- `quorum` 等于授权切换所需票数吗？（不完全等同，客观下线达到 quorum，故障转移还需要多数 Sentinel 授权）
- Sentinel 和 Cluster 的核心区别是什么？（前者管理一套未分片主从，后者同时负责分片和故障转移）

**易错点**

不要说 Sentinel 能“保证缓存服务不中断”；检测、选举、重配置和客户端重连都有时间窗口，网络分区还可能带来丢写风险。

## 586. Redis Cluster 是什么？

**面试回答**

Redis Cluster 是 Redis 原生的分片与高可用方案。键空间被划分为 16384 个哈希槽并分配给多个主节点，每个主节点可配置副本；客户端根据槽映射访问对应节点，故障时集群可在条件满足时提升副本。

**原理与理解**

普通 Key 使用 `CRC16(key) mod 16384` 计算槽，`{...}` hash tag 可以让多个 Key 落入同一槽。节点不代理普通请求，而是通过 `MOVED`、迁移期间的 `ASK` 等响应引导支持 Cluster 的客户端更新路由。

**成立条件与边界**

多 Key 命令通常要求相关 Key 位于同一槽，Cluster 只支持数据库 0。它使用异步复制，已确认写入仍可能在故障或分区中丢失；少数主节点一侧会停止可用，自动容错还要求多数主节点可达且故障主节点存在可提升副本。

**实际场景（项目核验项）**

不能因为“数据量大”就声称项目采用 Cluster。需要核验槽分布、主从数量、客户端协议支持、hash tag、跨槽命令和故障演练；单个热点 Key 也不会被自动拆到多个主节点。

**常见追问**

- 为什么是 16384 个槽而不是直接对节点数取模？（槽作为稳定的中间层，便于扩缩容时迁移部分槽）
- Cluster 能保证强一致吗？（不能，异步复制存在丢写窗口）

**易错点**

不要把 Cluster 说成“任何节点挂了都不影响”，也不要认为加入更多节点就能自动分散同一个热 Key。

## 587. 什么是 Redis 分布式锁？

**面试回答**

Redis 分布式锁是多个进程共同遵守的一种带租约互斥协议：客户端竞争同一个资源 Key，成功者在有限有效期内获得执行资格，释放时必须证明自己仍是当前持有者。

**原理与理解**

单实例上的基础做法是 `SET lock-key token NX PX ttl`，把“仅不存在时写入”和 TTL 放在一条命令中；释放时校验唯一 token 后删除。Redis 8.4+ 可使用 `DELEX key IFEQ token`，更早版本通常用 Lua 原子完成比较与删除。

**成立条件与边界**

互斥只在租约有效且 Redis 拓扑满足算法假设时成立。客户端暂停超过 TTL 后，即使仍以为自己持锁，也可能与新持有者并发操作；保护高正确性外部资源时，还需要 fencing token、幂等或数据库条件更新。

**实际场景（通用工程）**

热点缓存重建可用每 Key 锁减少并发回源；库存防超卖更应优先依赖数据库条件更新或 Redis 原子库存操作，锁只是协调手段，不能替代最终的数据约束。

**常见追问**

- 为什么要设置唯一 token？（只允许当前持有者释放自己的锁）
- TTL 解决了什么又引入什么？（避免持有者崩溃后永久死锁，但可能让超时旧持有者继续执行）

**易错点**

不要把分布式锁当成跨系统事务，也不要说“拿到锁就绝对只有我能写”；锁是建议性协议，外部资源必须能抵御陈旧持有者。

## 588. 为什么 `SETNX` 可以实现简单分布式锁？

**面试回答**

`SETNX` 的“Key 不存在才设置”由 Redis 原子执行，因此多个客户端竞争同一个 Key 时，只有首先成功设置的客户端获得简单互斥资格，其他客户端得到失败结果。

**原理与理解**

它把“检查不存在”和“创建占位 Key”合并，避免客户端先 `GET` 再 `SET` 的竞态。不过现代实现通常使用带 `NX`、`PX/EX` 的 `SET`，在同一条命令里同时建立互斥标记和租约，而不是裸 `SETNX` 后再设置过期时间。

**成立条件与边界**

原子抢占只解决获取瞬间的互斥，不提供自动续租、安全释放、可重入、公平等待或故障转移安全。TTL 应覆盖预期临界区并设置失败策略，但再大的固定 TTL 也无法消除长暂停和超时任务。

**实际场景（项目核验项）**

面试可以用缓存重建说明竞争过程，但简历不能证明项目实际使用过 `SETNX`。若源码存在锁代码，要核验是否是单条 `SET NX PX`、Value 是否唯一以及失败请求如何退避或降级。

**常见追问**

- 为什么不能先 `SETNX` 再单独 `EXPIRE`？（两条命令之间崩溃会留下无 TTL 的锁）
- 抢锁失败后怎么办？（按业务立即失败、有限等待、带抖动重试或降级，不能无限自旋）

**易错点**

不要再背“`SETNX` 不能设置过期，所以只能死锁”作为完整答案；问题在于裸命令，正确基础写法是单条 `SET ... NX PX/EX ...`。

## 589. 简单的 `SETNX` 分布式锁存在哪些问题？

**面试回答**

裸 `SETNX` 的问题包括：没有原子设置租约会永久占锁，直接 `DEL` 可能误删新持有者的锁，固定 TTL 可能早于业务完成，失败方可能忙等；主从异步复制与故障转移还可能让同一资源出现两个持有者。

**原理与理解**

基础修正是单条 `SET key token NX PX ttl` 获取，释放时原子比较 token 后删除，并限制等待与重试。若旧持有者在暂停后恢复，token 比较只能防止误删，不能阻止它继续写外部资源，因此高正确性场景要让资源校验单调递增的 fencing token。

**成立条件与边界**

续租能降低业务超过 TTL 的概率，却无法覆盖进程长暂停、网络分区和续租线程失效。使用异步复制的主从故障转移时，锁写入可能尚未复制就丢失；选型必须说明允许偶发并发，还是需要更强的协调系统与资源侧防护。

**实际场景（生产能力）**

锁实现要观测获取成功率、等待时间、持有时长、续租失败和超时释放；临界区仍应幂等，库存、余额等写入使用版本号、唯一约束或条件更新抵御重复执行。

**常见追问**

- Lua 安全释放解决全部问题了吗？（没有，只解决比较持有者与删除的原子性）
- 主从切换为什么可能破坏互斥？（锁写入未复制时主节点故障，新主节点上该 Key 不存在）

**易错点**

不要只列“死锁、误删、锁超时”三个口诀；还应说明每个问题的故障时序，以及剩余的故障转移和陈旧持有者风险。

## 590. Redisson 是什么？

**面试回答**

Redisson 是面向 Redis 和 Valkey 的 Java 客户端与分布式数据服务库，除基础访问外，还提供 `RLock`、读写锁、信号量、集合和缓存等高层 API。它能减少自研锁协议的错误，但不是绝对可靠性的代名词。

**原理与理解**

`RLock` 是可重入锁，等待者通常通过 Pub/Sub 获得通知，并按 Java `Lock` 语义绑定持有线程。未显式给定固定 `leaseTime` 时，watchdog 会在持有 Redisson 实例存活期间续期；当前文档默认 watchdog 超时为 30 秒，具体值与行为应按使用版本配置核验。

**成立条件与边界**

watchdog 主要防止正常长任务租约提前到期，不能消除长时间 STW、网络分区和拓扑故障。当前 Redisson 还提供副本同步检查与 `RFencedLock`，但外部资源必须实际校验 fencing token 才能拒绝陈旧写入；只有锁拥有线程可以解锁 `RLock`。

**实际场景（项目核验项）**

简历没有证明项目引入了 Redisson 或 `RLock`。若源码存在依赖，应核验 Redisson 版本、部署模式、`tryLock` 参数、watchdog、异常路径与 `finally` 解锁，而不是直接声称已用它解决超卖。

**常见追问**

- Redisson 与 Lettuce/Jedis 有什么区别？（都是 Java 客户端，但 Redisson 还提供大量分布式对象和服务抽象）
- 显式传入 `leaseTime` 与 watchdog 有什么关系？（固定租约到期自动释放；自动续期行为应按调用方式和版本确认）

**易错点**

不要说“用了 Redisson 就没有锁问题”，也不要在未成功获取锁时执行 `unlock()`；通常先判断 `tryLock` 结果，并只在当前线程确实持锁时于 `finally` 释放。
