# 持久化

## 374. Redis 为什么需要持久化？

**面试回答**

Redis 主要在内存中提供数据服务，进程退出或机器故障后，未写入持久介质的数据可能丢失。持久化把数据以 RDB 快照、AOF 日志或两者组合写入磁盘，使实例重启后能够恢复到某个已持久化状态。

**原理与理解**

是否开启以及采用哪种方式，取决于恢复点目标 RPO、恢复时间目标 RTO、写入压力和数据能否从事实来源重建。Redis 也允许完全关闭持久化，这对可安全重建的纯缓存是合法选择。

**成立条件与边界**

持久化不等于零丢失，也不等于高可用和备份：故障时仍有未刷盘窗口，磁盘与文件也可能损坏。复制、自动故障转移、异地备份和恢复演练解决的是不同问题，不能由 RDB/AOF 单独替代。

**实际场景（项目核验项）**

简历只能确认使用 Redis，不能证明项目开启了 RDB、AOF 或两者组合。应从 Redis 配置、托管服务控制台和 `INFO persistence` 核验；若它只是缓存，还要准备冷启动限流与预热方案。

**常见追问**

- Redis 可以不做持久化吗？（可以，前提是数据可丢失或可从其他来源重建）
- 持久化能替代主从复制吗？（不能，前者侧重重启恢复，后者侧重副本与可用性）

**易错点**

不要说“Redis 在内存里，所以一宕机必然全丢”；实际丢失范围取决于持久化、复制和故障类型，也不要把锁等临时协调状态当作必须靠持久化保存的数据。

## 375. RDB 是什么？

**面试回答**

RDB 是 Redis 对某一时点数据集生成的紧凑二进制快照，默认文件名通常是 `dump.rdb`。它可由 `save N M` 条件自动触发，也可通过 `BGSAVE` 或 `SAVE` 等方式产生。

**原理与理解**

常见的 `BGSAVE` 会 fork 子进程，子进程把快照写入临时文件，完成后原子替换旧 RDB；父进程继续服务客户端，并依靠操作系统的写时复制保持快照视图。`SAVE` 则由主进程同步保存，会阻塞服务，生产中通常更谨慎使用。

**成立条件与边界**

RDB 只能恢复到最近一次成功快照，之后的写入可能丢失。fork 本身可能造成停顿，快照期间大量写入会增加写时复制内存，磁盘空间不足或后台保存失败也会使恢复点长期不更新。

**实际场景（项目核验项）**

不能直接声称项目“每五分钟生成一次 RDB”。应核验真实 `save` 规则、最近成功时间、`rdb_last_bgsave_status`、数据规模及容器或云盘是否持久化挂载。

**常见追问**

- `BGSAVE` 如何尽量不阻塞主进程？（fork 子进程保存，父子通过写时复制共享初始内存页）
- RDB 何时会丢数据？（故障发生在最新成功快照之后时）

**易错点**

不要说 RDB 只会“定时触发”，也不要说 fork 后完全没有性能影响；fork 停顿、写时复制和后台 I/O 都需要容量评估。

## 376. AOF 是什么？

**面试回答**

AOF 持久化记录会改变数据集的操作，并在启动时据此重建状态。Redis 7.0 起使用 multi-part AOF：由至多一个 base 文件、一个或多个增量 AOF 文件和 manifest 共同描述有效文件集合。

**原理与理解**

增量内容使用 Redis 协议格式追加；base 文件在重写后可采用 RDB 或 AOF 格式。`appendfsync` 决定数据何时要求操作系统刷入稳定存储：`always`、默认建议的 `everysec` 和由操作系统决定刷盘的 `no`，对应不同延迟与丢失窗口。

**成立条件与边界**

收到写命令、追加到缓冲区和真正 `fsync` 到磁盘不是同一时刻。`everysec` 在灾难故障下通常可能损失约一秒写入；`always` 成本更高，也不能把硬件、文件系统和运维故障简化成绝对零丢失。

**实际场景（项目核验项）**

项目是否开启 AOF、使用哪种 `appendfsync`、AOF 目录是否落在持久卷，都必须核验。不能只看到 Redis 依赖就声称使用 `everysec` 或具备特定 RPO。

**常见追问**

- AOF 为什么需要重写？（用能表达当前状态的更短操作集合替代历史冗余，控制文件增长）
- 和 RDB 有什么区别？（见 [[05-Redis/06-持久化#377. RDB 和 AOF 有什么区别？]]）

**易错点**

不要把现代 AOF 简化成单个 `appendonly.aof` 文本文件，也不要把 AOF 重写说成普通压缩；它生成的是等价的最小化重建表示。

## 377. RDB 和 AOF 有什么区别？

**面试回答**

RDB 保存时点快照，通常文件更紧凑、启动加载更快，但故障时可能丢失最近一次快照后的写入；AOF 记录增量变更，可通过刷盘策略获得更小的丢失窗口，但会增加持续写盘和重写成本。两者可以单独使用、组合使用或全部关闭。

**原理与理解**

| 维度 | RDB | AOF |
| --- | --- | --- |
| 记录内容 | 某一时点的数据集快照 | base 状态与之后的增量写入 |
| RPO | 取决于快照间隔 | 取决于 `appendfsync` 策略 |
| 启动恢复 | 通常直接加载快照，较快 | 加载 base 并应用增量，通常更久 |
| 持续成本 | 生成快照时集中消耗 fork、内存与 I/O | 持续追加、fsync，并周期性重写 |
| 备份特性 | 单个不可变快照易归档 | Redis 7+ 需按 manifest 管理整组文件 |

**成立条件与边界**

“AOF 一定更大、更慢”不是严格定律，数据形态、重写、磁盘和 Redis 7+ 的 RDB base 都会改变结果；“AOF 更安全”也必须附带刷盘策略。两者同时开启时，Redis 正常启动会选择 AOF 恢复，因为它被视为更完整。

**实际场景（通用工程）**

纯缓存可选择无持久化并强化回源保护；可接受分钟级丢失且重视备份与快速恢复时可评估 RDB；需要更小 RPO 时再评估 AOF 或组合方案，并用压测验证延迟与恢复时间。

**常见追问**

- 哪一种数据一定不丢？（都不能无条件保证，必须结合配置和故障模型）
- 为什么可以同时开启？（AOF用于更细恢复，RDB便于快照备份和快速恢复场景）

**易错点**

不要只背“RDB 小快会丢、AOF 大慢安全”，答案必须带上触发/刷盘策略、现代 multi-part AOF 和实际 RPO/RTO。

## 378. RDB 有什么优缺点？

**面试回答**

RDB 的优点是快照紧凑、单文件便于复制归档，通常能较快加载大数据集；缺点是恢复点较粗，而且生成快照需要 fork、写时复制内存和集中磁盘 I/O。

**原理与理解**

RDB 完成后不再修改，生成过程先写临时文件再原子替换，因此适合作为版本化备份。父进程不负责快照磁盘写入，但 fork 和快照期间被修改的内存页会带来延迟与额外内存占用。

**成立条件与边界**

“恢复快”是相对 AOF 重放的常见结论，不是所有环境的固定结果；压缩、CPU、磁盘吞吐和数据规模都会影响。快照留在同一磁盘也不等于备份，磁盘或机房故障仍可能同时丢失数据和 RDB。

**实际场景（生产能力）**

生产中应监控最近成功快照、fork 耗时、写时复制内存、磁盘空间和后台保存失败，并把验证过的 RDB 复制到独立故障域，定期执行恢复演练。

**常见追问**

- 为什么 RDB 适合备份？（文件紧凑且生成后不可变，便于按时间归档）
- 大数据集做 RDB 有什么风险？（fork 停顿、写时复制内存和磁盘压力）

**易错点**

不要把“子进程保存”说成零性能影响，也不要只配置快照却不监控是否成功；失败的快照不会提供新的恢复点。

## 379. AOF 有什么优缺点？

**面试回答**

AOF 的主要优点是可通过 `appendfsync` 获得比周期快照更细的恢复点，并能在后台重写冗余历史；主要代价是持续追加与刷盘开销、通常更大的存储占用，以及启动加载和重写的资源成本。

**原理与理解**

`everysec` 通常在性能与持久性之间折中，`always` 更频繁刷盘但延迟成本更高，`no` 则把刷盘时机交给操作系统。重写会基于当前数据集生成新的 base，同时继续记录增量；Redis 7+ 用 manifest 原子切换有效文件集合。

**成立条件与边界**

AOF 不是完整审计日志：重写会消除历史冗余，base 还可能是 RDB 格式。重写同样涉及 fork、写时复制、磁盘空间和 I/O；尾部截断可按配置处理，但中部损坏可能导致启动失败或修复时丢弃后续数据。

**实际场景（生产能力）**

需要监控 AOF 当前大小、重写状态与结果、fsync 延迟、磁盘余量和加载耗时；备份 Redis 7+ AOF 时应按 manifest 复制完整文件集合，不能只拿某一个增量文件。

**常见追问**

- `everysec` 最多只会丢一秒吗？（是常见预期，不是跨所有硬件和故障类型的绝对保证）
- AOF 重写会阻塞业务吗？（后台执行，但 fork、写时复制和磁盘竞争仍可能影响延迟）

**易错点**

不要说 AOF 文件始终可直接阅读，也不要把 `appendfsync no` 解释成完全不写磁盘；它只是由操作系统决定刷盘时机。

## 380. Redis 重启后如何恢复数据？

**面试回答**

正常启动时，如果 AOF 已开启，Redis 使用 AOF 恢复；Redis 7+ 会按 manifest 加载 base，再应用有效的增量 AOF。若未开启 AOF，Redis 会尝试加载配置路径中的 RDB；没有可加载的持久化文件时，实例才以空数据集启动。

**原理与理解**

同时开启 RDB 和 AOF 时选择 AOF，是因为它通常包含更完整的变更。恢复不是永远“逐条重放一个文本文件”：multi-part AOF 的 base 可以是 RDB 格式，之后再加载增量。数据加载完成前，实例通常不能正常提供完整数据服务。

**成立条件与边界**

配置开启不代表文件一定可用。文件缺失、权限错误、磁盘损坏、manifest 不一致或 AOF 中部损坏都可能使启动失败；不能假设 AOF 损坏时 Redis 会自动安全回退到旧 RDB。关闭自动 `save` 规则也不等于忽略已有 RDB，尾部截断是否容忍还受配置和版本影响。

**实际场景（生产能力）**

重启前后应保存文件副本，检查 `INFO persistence` 和日志，核对 Key 数量与关键业务数据，并演练损坏文件的隔离和恢复流程；项目是否真正执行过这些流程需要运维记录证明。

**常见追问**

- RDB 和 AOF 都开启时加载谁？（正常情况下加载 AOF）
- 为什么启动时间可能很长？（需要读取 base、应用增量并重建内存数据集）

**易错点**

不要只背“AOF 优先”而忽略版本、manifest 和文件完整性，也不要把 `save ""` 简化成“下次一定空启动”；修改持久化配置前必须备份并验证切换流程。
