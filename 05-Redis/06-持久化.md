# 持久化

## 374. Redis 为什么需要持久化？

**面试回答**

因为 Redis 数据主要存在内存里，断电或重启后内存数据会丢失；持久化把内存数据保存到磁盘，让 Redis 重启后能恢复数据，保证数据不因宕机而全丢。

**理解**

内存是易失的，Redis 光靠内存存数据，一重启就「清零」。持久化把数据落到磁盘（RDB 快照或 AOF 日志），重启时加载恢复。虽然 Redis 常用作缓存（丢了可重建），但有些数据（如分布式锁、计数器、重要中间态）不想丢，就需要持久化。

**场景**

项目里 Redis 主要做缓存，但配置了持久化，避免重启后缓存全空、瞬间打库，也保护一些不能轻易丢的数据。

**常见追问**

- 持久化有哪两种？（RDB 和 AOF）
- 不持久化会怎样？（重启数据全丢）

**易错点**

持久化是「内存数据 → 磁盘」的保障；即使做缓存，也常配持久化避免重启后冷启动打库。

## 375. RDB 是什么？

**面试回答**

RDB 是 Redis 的一种持久化方式，定期把某一时刻的内存数据快照保存成二进制文件（dump.rdb），是「数据快照」。

**理解**

RDB 相当于「给内存数据拍照片」：Redis 在满足条件（如指定时间间隔内有多少次写操作）时，fork 子进程把当前内存数据写成快照文件。它的特点是文件紧凑、恢复快，但两次快照之间的数据（最后一次快照后的写入）可能丢失。

**场景**

项目里 Redis 配置 RDB 定期快照，重启时加载快照快速恢复。

**常见追问**

- RDB 本质是什么？（某时刻的内存数据快照）
- 会丢数据吗？（会丢两次快照之间的写入）

**易错点**

RDB 是「快照」，优点是恢复快，缺点是「两次快照之间的数据可能丢」；理解它的「快照」本质。

## 376. AOF 是什么？

**面试回答**

AOF 是 Redis 的另一种持久化方式，把「每条写命令」追加记录到日志文件（appendonly.aof），重启时重放这些命令恢复数据。

**理解**

AOF 记录的是「操作日志」而不是「数据快照」：每次写操作都追加到 AOF 文件末尾。重启时按顺序重放命令，重建数据。它比 RDB 丢数据更少（可配置每条/每秒刷盘），但文件更大、恢复更慢。通常「AOF 保证数据完整，RDB 保证恢复快」。

**场景**

项目里对数据完整性要求高时用 AOF，重启后能更完整地恢复数据。

**常见追问**

- AOF 记录什么？（写命令日志）
- 和 RDB 区别？（见 [[05-Redis/06-持久化#377. RDB 和 AOF 有什么区别？]]）

**易错点**

AOF 是「命令日志」不是「数据快照」，它靠重放命令恢复；优点是丢数据少，缺点是文件大、恢复慢。

## 377. RDB 和 AOF 有什么区别？

**面试回答**

RDB 是「定时快照」，存某一时刻的数据，文件小、恢复快，但两次快照之间可能丢数据；AOF 是「命令日志」，记录每条写命令，丢数据少（更安全），但文件大、恢复慢。

**理解**

几个维度：①内容：RDB 存数据快照，AOF 存写命令；②数据安全：AOF 更安全（丢数据少），RDB 可能丢快照后写入；③恢复速度：RDB 快，AOF 慢（要重放命令）；④文件大小：RDB 紧凑，AOF 大且会重写压缩。生产常「两者结合」：RDB 用于快速恢复，AOF 用于减少丢失。

**场景**

项目里 Redis 可同时开启 RDB + AOF，兼顾恢复速度和数据完整性。

**常见追问**

- 谁恢复快？（RDB）
- 谁丢数据少？（AOF）

**易错点**

RDB「快照、快恢复、可能丢」vs AOF「日志、安全、慢恢复」，要能分维度对比，并知道常配合使用。

## 378. RDB 有什么优缺点？

**面试回答**

优点：文件紧凑、恢复速度快、对性能影响相对小（fork 子进程写）。缺点：两次快照之间可能丢失数据；fork 子进程在大数据量下可能短暂影响性能。

**理解**

RDB 是「定期快照」：优点是快照文件小、加载恢复快，适合做冷备份、快速恢复；缺点是它是「定时」的，最后一次快照之后到宕机之间的写入会丢，数据完整性不如 AOF。fork 子进程写快照时，数据量大可能短暂卡顿。

**场景**

项目里用 RDB 做定期备份、快速恢复；若对丢数据敏感，配合 AOF。

**常见追问**

- RDB 最大的缺点？（可能丢两次快照之间的数据）
- 为什么恢复快？（加载二进制快照比重放命令快）

**易错点**

RDB 的「丢数据」是核心缺点（快照间隔内的写入）；优点主要是「小 + 快」，别只说快。

## 379. AOF 有什么优缺点？

**面试回答**

优点：数据更安全（可做到每条命令都落盘，丢数据少）；文件可读（是命令记录）。缺点：文件比 RDB 大、恢复速度慢、写命令有额外 IO 开销。

**理解**

AOF 是「命令日志」：优点是完整性好（取决于刷盘策略，可几乎不丢），缺点是文件持续增长（需 AOF 重写压缩）、重启要重放命令所以慢、每次写都要记日志有开销。适合「数据完整性优先」的场景。

**场景**

项目里对数据安全要求高时用 AOF（配 everysec 刷盘），接受一定恢复时间和文件大小代价。

**常见追问**

- AOF 最大的优点？（丢数据少，更安全）
- 缺点？（文件大、恢复慢）

**易错点**

AOF 的「安全」和「慢/大」是一体两面；要能说清刷盘策略（always/everysec/no）对丢数据程度的影响。

## 380. Redis 重启后如何恢复数据？

**面试回答**

Redis 重启时会根据持久化配置加载数据：如果 AOF 开启，优先加载 AOF 文件（重放命令）；否则加载 RDB 快照文件恢复数据。

**理解**

恢复优先级：AOF 通常优先于 RDB，因为 AOF 数据更完整（丢得少）。只开 AOF 就重放 AOF；只开 RDB 就加载 RDB 快照；两者都开则优先 AOF。加载过程是阻塞的，加载完才对外服务。

**场景**

项目里 Redis 重启后，按配置优先用 AOF（若开启）恢复，否则用 RDB 快照恢复，避免缓存全空。

**常见追问**

- AOF 和 RDB 都开，优先谁？（优先 AOF）
- 为什么优先 AOF？（数据更完整）

**易错点**

恢复时「AOF 优先于 RDB」，因为 AOF 丢数据更少；这是常见考点。
