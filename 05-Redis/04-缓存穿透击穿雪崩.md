# 缓存穿透击穿雪崩

## 343. 什么是缓存穿透？

**面试回答**

缓存穿透指查询一个「根本不存在的数据」，缓存里没有、数据库里也没有，导致每次请求都绕过缓存直接打数据库，恶意或异常请求反复查询不存在的 key，数据库压力剧增。

**理解**

正常情况下，查不到的数据不会写进缓存（缓存里没这个 key），于是每次查这个不存在的 id，都会「缓存未命中 → 查库 → 查不到 → 不回填」，形成每次都打库。攻击者可以利用这点，用大量不存在的 id 疯狂请求，把数据库打挂。

**场景**

项目里如果有人恶意请求 `id = -1` 或随机不存在的菜品 id，缓存拦不住，每次都打数据库，就是缓存穿透。

**常见追问**

- 穿透的关键特征？（查的数据缓存和数据库都没有）
- 怎么解决？（缓存空值、布隆过滤器，见 [[05-Redis/04-缓存穿透击穿雪崩#346. 如何解决缓存穿透？]]）

**易错点**

穿透是「查不存在的 key」，特点是「缓存和库都没有」，和击穿（热点 key 失效）、雪崩（大量 key 同时失效）要区分。

## 344. 缓存穿透是如何产生的？

**面试回答**

因为查询不存在的数据时，缓存里没有、数据库也没有，系统不会缓存「空结果」，于是每次请求都重复「查缓存未命中 → 查库也查不到」的过程，形成每次都打库。

**理解**

穿透的产生有两个条件：①被查的数据在库里不存在；②系统没有对这种「空结果」做缓存或拦截。攻击者或程序 bug 反复用不同（或不存在的）id 请求，每次都穿透缓存直达数据库，数据库压力越来越大。

**场景**

项目里若接口用不存在的 id 查询，且没有空值缓存/布隆过滤，恶意请求就能持续穿透打库。

**常见追问**

- 为什么空结果不缓存会穿透？（每次都要重新查库确认不存在）
- 攻击者怎么利用？（构造大量不存在的 key 高频请求）

**易错点**

穿透的根因是「不存在的数据无法被缓存挡住」，所以每次都要查库；理解这点就知道解决方案方向。

## 345. 缓存穿透为什么会给数据库造成压力？

**面试回答**

因为穿透让每个请求都「绕过缓存直达数据库」，缓存完全失效；当大量不存在的 key 高频请求时，数据库要反复执行无效查询，CPU/连接被耗尽，甚至被打垮。

**理解**

缓存的作用是「挡住大部分请求」，穿透时这个保护失效了——请求不命中缓存、又查不到库、又不缓存结果，于是每个请求都实实在在打一次数据库。高频 + 大量 = 数据库压力骤增，轻则变慢、重则崩溃。

**场景**

项目里如果穿透没防护，几千几万个不存在的 id 并发请求，数据库会被无效查询拖垮。

**常见追问**

- 穿透为什么让缓存失效？（不存在的 key 缓存永远拦不住）
- 压力大在哪？（每个请求都打库，无效查询堆积）

**易错点**

穿透的压力来自「缓存失效 + 每次都打库」；要理解它不是「一次查询慢」，而是「海量无效查询压垮库」。

## 346. 如何解决缓存穿透？

**面试回答**

常用方法：①缓存空值（把「不存在」也缓存起来，设短 TTL）；②布隆过滤器（先判断 key 是否可能存在，不存在直接拦截）；③接口层校验（拦截非法 id）。

**理解**

缓存空值：查不到时也缓存一个空标记，下次直接命中空值不查库；布隆过滤器：用位图快速判断「key 一定不存在」（有误判但不会漏判），不存在的直接返回，不进库；参数校验：对明显非法的 id（负数、超范围）直接拒绝。三者可组合使用。

**场景**

项目里对查不存在的菜品 id，用缓存空值（短 TTL）+ 参数校验来防穿透。

**常见追问**

- 缓存空值注意什么？（短 TTL，避免占用空间）
- 布隆过滤器特点？（省空间、有误判、不会漏判）

**易错点**

三种方案思路不同：空值缓存「缓存不存在」、布隆过滤器「提前判断存在性」、参数校验「入口拦截」；要能说出各自适用场景。

## 347. 缓存空值如何解决缓存穿透？

**面试回答**

查数据库发现数据不存在时，也往缓存里写一个「空值/空标记」（设较短 TTL），下次再查这个 key 就能命中缓存（返回空），不再查数据库。

**理解**

把「不存在」也当作一种结果缓存起来，就打破了「每次都查库确认不存在」的循环。因为不存在的 key 现在也能命中缓存了，数据库不再被打。设短 TTL 是因为「不存在」这个结论可能变化（数据可能被补录），且避免缓存里塞满空值占内存。

**场景**

项目里查不存在的菜品 id，缓存一个空标记（如空对象或特定占位符）设 1~5 分钟 TTL，挡住后续重复请求。

**常见追问**

- 为什么要短 TTL？（数据可能被补录，且避免空值占内存）
- 空值缓存占用大吗？（用短 TTL 控制）

**易错点**

缓存空值是把「空」也缓存，核心是「短 TTL」；要理解短 TTL 的用意（数据可能变化 + 省内存）。

## 348. 什么是布隆过滤器？

**面试回答**

布隆过滤器是一种省空间的数据结构，用来快速判断「一个元素是否可能存在」：它可能误判「不存在的说成存在」，但绝不会漏判「存在的说成不存在」。

**理解**

它用位数组 + 多个哈希函数：插入时把元素哈希到多个位置置 1；查询时看这些位置是否都为 1。都 1 说明「可能存在」（可能误判），有 0 说明「一定不存在」。用它挡缓存穿透：查询前先判断，若「一定不存在」直接返回，不用查库。优点是极省内存，缺点是存在误判、且删除困难。

**场景**

项目里可把菜品 id 全量放进布隆过滤器，查询前先判断 id 是否存在，不存在的直接拦截，防穿透。

**常见追问**

- 布隆过滤器会漏判吗？（不会漏判，只会误判）
- 优点和缺点？（省内存、快；有误判、难删除）

**易错点**

布隆过滤器的特性是「不会漏判、可能误判」，即「说没有就真没有，说有却不一定有」；方向别记反。

## 349. 布隆过滤器为什么存在误判？

**面试回答**

因为布隆过滤器把元素映射到位数组的多个位置，不同元素的哈希位置可能重叠，查询时「所有位置都是 1」可能是别的元素置的位，而不是这个元素真的存在，所以会误判。

**理解**

多个哈希函数把元素映射到若干位，随着插入元素增多，位数组里越来越多的位被置 1，位与位之间互相「污染」。判断某元素时，它的几个哈希位置可能恰好都被别的元素置过 1，于是误以为存在。反过来，只要有一个位置是 0，就能确定它一定没插入过（不会漏判）。误判率由位数组大小和哈希函数个数决定。

**场景**

项目里布隆过滤器误判会导致「不存在的 id 被放过去查一次库」，但概率可控、影响小，仍能挡住绝大部分穿透。

**常见追问**

- 为什么不会漏判？（只要有 0 位就一定没插入过）
- 怎么降低误判率？（增大位数组、调整哈希函数个数）

**易错点**

误判是「哈希冲突 + 位共享」导致的，只可能「误存在」，不可能「误不存在」；要理解这个不对称性。

## 350. 什么是缓存击穿？

**面试回答**

缓存击穿指某个「热点 key」在过期失效的瞬间，大量并发请求同时打到这个 key，由于缓存失效，全部穿透到数据库，给数据库造成瞬间巨大压力。

**理解**

击穿针对「单个热点 key」：平时它命中缓存挡着，一旦过期，正好赶上大量并发访问，所有请求都未命中、同时查库。和穿透（查不存在数据）、雪崩（大量 key 同时失效）不同，击穿是「一个热点 key 失效 + 高并发」。

**场景**

项目里某个爆款菜品详情缓存过期，恰好大量用户同时访问，瞬间全部打库，就是缓存击穿。

**常见追问**

- 击穿的对象是什么？（单个热点 key）
- 怎么解决？（互斥锁、逻辑过期，见 [[05-Redis/04-缓存穿透击穿雪崩#353. 如何解决缓存击穿？]]）

**易错点**

击穿 = 「单个热点 key 失效 + 并发打库」，要抓住「热点」和「单个」两个特征，和雪崩「大量」区分。

## 351. 缓存击穿通常发生在什么场景？

**面试回答**

通常发生在「某个热点数据（如爆款商品、热门菜品）的缓存过期瞬间，正好有大量并发请求访问它」的场景，比如秒杀、大促、热点新闻。

**理解**

击穿的三个要素：①数据是热点（访问量极大）；②缓存过期（失效）；③高并发同时访问。三者凑齐，缓存这层「闸门」在关键时刻失效，海量请求涌向数据库。日常的低频数据过期不会击穿，因为并发量不够大。

**场景**

项目里爆款菜品详情缓存到期，正值高峰期大量用户查看，就会击穿。

**常见追问**

- 为什么低频数据不会击穿？（并发量不够，打库压力小）
- 典型场景？（秒杀、热点商品、大促）

**易错点**

击穿必须「热点 + 过期 + 高并发」三者同时满足；不是所有缓存过期都会击穿。

## 352. 什么是热点 Key？

**面试回答**

热点 Key 是访问频率极高、被大量请求集中访问的缓存 Key，通常是爆款商品、热门内容等，是缓存系统的关键保护对象。

**理解**

热点 Key 承载了大部分流量，一旦它出问题（过期、失效），影响面极大。热点 Key 可能还需要特别处理：避免集中在单节点（热 key 倾斜）、防止击穿（互斥锁/逻辑过期）、必要时本地缓存兜底。

**场景**

项目里爆款菜品、首页推荐数据就是热点 Key，访问量远超普通数据。

**常见追问**

- 热点 Key 有什么风险？（击穿、单节点压力大）
- 怎么识别热点 Key？（监控访问频率、统计命中）

**易错点**

热点 Key 是「高频访问的 key」，是击穿、热 key 倾斜等问题的主角；要理解它为什么特殊。

## 353. 如何解决缓存击穿？

**面试回答**

常用方法：①互斥锁（重建缓存时只让一个请求查库，其他等待）；②逻辑过期（缓存不设物理 TTL，用逻辑过期时间，过期后异步重建）；③热点数据永不过期 + 定时刷新。

**理解**

击穿的本质是「大量请求同时去查库重建缓存」。解决思路是「只让一个请求查库、其他复用结果」：互斥锁让第一个请求锁住、查库回填，其他请求等待或重试；逻辑过期让缓存值带逻辑过期时间，物理不过期，发现过期就返回旧值并异步重建。两者都是避免「并发打库」。

**场景**

项目里对热点菜品缓存用互斥锁或逻辑过期，防止过期瞬间大量请求同时打库。

**常见追问**

- 互斥锁思路？（只让一个请求查库，其余等待）
- 逻辑过期思路？（物理不过期，逻辑过期后异步重建）

**易错点**

解决击穿的核心是「防止并发重建缓存」，即「只让一个请求回源」，互斥锁和逻辑过期是两种实现。

## 354. 互斥锁如何解决缓存击穿？

**面试回答**

当缓存失效时，请求先去抢一把锁（如用 Redis 的 SETNX），抢到的那个请求负责查库并重建缓存，其他没抢到的请求等待/重试，避免所有请求同时打库。

**理解**

缓存未命中后，不是所有请求都去查库，而是先尝试加锁：只有第一个拿到锁的请求去查库、回填缓存、释放锁；其余请求拿到锁失败，就短暂等待后重试（此时缓存可能已回填，直接命中）。这样把「并发打库」变成「一个查库 + 其余等待」，保护数据库。

**场景**

项目里热点菜品缓存过期，用 Redis 分布式锁保证只有一个请求去查 MySQL 重建缓存，其余等待命中。

**常见追问**

- 锁用什么实现？（Redis 的 SETNX，或 Redisson）
- 没抢到锁的请求怎么办？（等待重试，或返回旧值）

**易错点**

互斥锁的核心是「只让一个请求回源」，把并发查询「串行化」到一次；要注意锁的粒度和释放（避免死锁）。

## 355. 什么是逻辑过期？

**面试回答**

逻辑过期是给缓存值额外存一个「逻辑过期时间」，但 key 物理上不过期；读取时发现逻辑时间已过期，就返回旧值并异步重建缓存，而不是让请求阻塞等查库。

**理解**

做法：缓存 value 里带上过期时间字段，Redis 的 key 不设 TTL（或设很长）。读时判断：逻辑没过期直接返回；逻辑过期了，先返回旧值（保证响应快），同时后台开线程去查库更新缓存。好处是「永不过期」避免了击穿，且读请求不用等待；代价是实现稍复杂、可能短暂返回旧值。

**场景**

项目里对热点数据用逻辑过期：过期后用户仍能立刻拿到旧数据，同时后台异步刷新，避免击穿和阻塞。

**常见追问**

- 逻辑过期和物理 TTL 区别？（物理 TTL 到期 key 没了；逻辑过期 key 还在，靠字段判断）
- 优点？（读不阻塞，避免击穿）

**易错点**

逻辑过期的关键是「物理不过期 + 逻辑时间判断 + 异步重建」，它用「返回旧值」换取「不阻塞、不击穿」。

## 356. 什么是缓存雪崩？

**面试回答**

缓存雪崩指大量缓存 key 在同一时间集中失效（或 Redis 宕机），导致海量请求同时穿透到数据库，瞬间把数据库压垮。

**理解**

雪崩和击穿的区别在「范围」：击穿是单个热点 key 失效，雪崩是「一大批 key 同时失效」。原因通常是大量 key 设了相同或相近的 TTL，到点一起过期，缓存集体失效，请求全部打库；或 Redis 本身挂掉，缓存整体不可用。

**场景**

项目里如果大量菜品缓存都设了 30 分钟 TTL 且同时写入，到点一起过期，就可能引发雪崩。

**常见追问**

- 雪崩和击穿区别？（雪崩是大批量 key 失效，击穿是单个热点 key）
- 怎么解决？（TTL 加随机值、多级缓存、限流降级等，见 [[05-Redis/04-缓存穿透击穿雪崩#358. 如何解决缓存雪崩？]]）

**易错点**

雪崩 = 「大量 key 同时失效」或「Redis 宕机」，核心是「范围大」，和击穿「单点」区分。

## 357. 缓存雪崩通常是怎么产生的？

**面试回答**

两个主要原因：①大量缓存 key 设置了相同（或相近）的 TTL，到时间点集中过期；②Redis 服务本身宕机或不可用，缓存整体失效。

**理解**

第一种是「人为的时间集中」：如果缓存写入时都设一样的过期时间，它们就会在同一时刻集体过期，缓存「瞬间清空」，请求全打库。第二种是「基础设施故障」：Redis 挂掉，所有缓存都不可用，等于缓存整体失效。两者都会造成数据库瞬时压力暴涨。

**场景**

项目里批量写入缓存时若 TTL 都一样，到期时会出现「集体过期」；Redis 宕机则更彻底。

**常见追问**

- 为什么 TTL 相同会雪崩？（同时过期，缓存集体失效）
- Redis 宕机怎么应对？（集群、多级缓存、降级）

**易错点**

雪崩的产生要么是「TTL 集中过期」，要么是「Redis 故障」；要能分清这两类原因。

## 358. 如何解决缓存雪崩？

**面试回答**

①给 TTL 加随机值（打散过期时间）；②Redis 集群/高可用（避免单点宕机）；③多级缓存（本地缓存兜底）；④限流降级、熔断（保护数据库）。

**理解**

针对「TTL 集中过期」，给每个 key 的 TTL 加个随机偏移，让它们错开过期时间，避免集体失效；针对「Redis 宕机」，用主从/集群保证高可用；再加本地缓存、限流降级作为兜底，即使缓存全挂，也不至于瞬间打垮数据库。

**场景**

项目里缓存 TTL 用「基础时间 + 随机值」，Redis 用主从/哨兵保证可用，必要时限流降级。

**常见追问**

- 为什么 TTL 加随机值有效？（错开过期时间，避免集中失效）
- 降级是什么意思？（缓存挂了时，直接返回兜底数据或限流，保护库）

**易错点**

解决雪崩要「多管齐下」：打散 TTL、保证 Redis 高可用、加兜底；别只答「加随机值」一点。

## 359. TTL 加随机值有什么作用？

**面试回答**

给每个缓存 key 的 TTL 加上一个随机偏移量，让它们的过期时间错开，避免大量 key 在同一时刻集中过期，从而防止缓存雪崩。

**理解**

如果所有 key 都设 30 分钟 TTL 且同时写入，30 分钟后一起过期。加随机值后，有的 30 分钟过期、有的 35、有的 28 分钟，过期时间分散在不同时刻，缓存是「分批」失效而非「一次性清空」，数据库压力被摊平，不会瞬间被打垮。

**场景**

项目里缓存菜品时 TTL 设「30 分钟 + 随机几分钟」，避免集体过期引发雪崩。

**常见追问**

- 随机值加多少合适？（根据业务，比如基础时间 ± 一个范围）
- 它防的是哪种问题？（缓存雪崩，TTL 集中过期）

**易错点**

TTL 加随机值是「打散过期时间」防雪崩的手段，针对的是「集中过期」这一类雪崩原因，不是万能解。

## 360. 缓存穿透、击穿、雪崩有什么区别？

**面试回答**

穿透是「查不存在的数据」每次都打库；击穿是「单个热点 key 过期瞬间」并发打库；雪崩是「大量 key 同时失效或 Redis 宕机」导致大面积打库。三者都是缓存失效导致数据库压力过大，但触发原因和范围不同。

**理解**

用一句话区分：穿透——数据本身不存在；击穿——一个热点 key 过期；雪崩——一大批 key 一起失效（或 Redis 挂了）。范围上：穿透是「恶意/异常请求」、击穿是「单点」、雪崩是「大面积」。解法也对应不同（空值/布隆、互斥锁/逻辑过期、TTL 随机/高可用）。

**场景**

项目里三者的防护各不同：防穿透用空值缓存，防击穿用互斥锁/逻辑过期，防雪崩用 TTL 随机 + 高可用。

**常见追问**

- 三个概念各自关键词？（穿透「不存在」、击穿「单热点」、雪崩「大批量」）
- 会不会同时发生？（可能，要分别防护）

**易错点**

这是高频对比题，关键是抓住各自「触发条件」：不存在 / 单点热点过期 / 大批量失效，别把三个混为一谈。
