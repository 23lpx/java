# 缓存穿透击穿雪崩

## 343. 什么是缓存穿透？

**面试回答**

缓存穿透通常指请求持续查询事实来源中不存在的数据，缓存每次都未命中，结果反复回源到数据库。攻击流量、参数错误或高基数随机 Key 都可能让缓存无法有效拦截请求。

**原理与理解**

Cache Aside 默认只回填查到的数据；不存在结果若不缓存，同一个无效 Key 每次都要由数据库重新确认。若请求不断使用新的随机 Key，即使对单个空结果做缓存，也可能继续制造大量 miss。

**成立条件与边界**

一次正常未命中不是缓存穿透。需要关注的是不存在数据被重复或大规模查询并形成持续回源。它也不是“绕过了 Redis”，请求通常仍然访问 Redis，只是 Redis 没有可用结果。

**实际场景（项目核验项）**

随机菜品 ID、越权访问其他租户 ID 或已删除数据都可能成为穿透输入，但简历不能证明项目已经遭遇或治理过该问题；应从接口校验、鉴权、空值缓存和限流代码核验。

**常见追问**

- 穿透的关键特征是什么？（请求不存在数据并持续回源）
- 常见治理手段是什么？（空值缓存、布隆过滤器、校验和限流，见 [[05-Redis/04-缓存穿透击穿雪崩#346. 如何解决缓存穿透？]]）

**易错点**

不要把所有 Cache Miss 都叫穿透，也不要承诺“缓存一个空值”就能挡住不断变化的随机 Key。

## 344. 缓存穿透是如何产生的？

**面试回答**

常见形成条件是：请求的数据在事实来源中不存在，系统没有保存短期的“不存在”结果，也没有在入口或数据库之前拒绝明显无效请求，于是每次缓存未命中都继续回源。

**原理与理解**

来源包括恶意枚举随机 ID、客户端参数错误、代码生成错误 Key、数据删除后仍有旧链接，以及布隆过滤器未及时加入新数据等。问题由“无效请求数量 × 每次回源成本”共同决定。

**成立条件与边界**

数据库中不存在只是必要背景，不代表一定造成事故；若请求量低、查询走高效索引且数据库有余量，影响可能有限。反之，即使单次查询很快，足够高的请求率仍能耗尽连接池和 CPU。

**实际场景（通用工程）**

接口接收 ID 后先完成格式、范围、租户和权限校验；数据库确认不存在时，按业务短期缓存缺失标记，并监控同一来源的大量不同 Key 请求。

**常见追问**

- 为什么不缓存空结果会反复查库？（系统每次都要重新确认数据仍不存在）
- 只有攻击才会产生吗？（不是，客户端 Bug、过期链接和数据同步问题也可能产生）

**易错点**

不要只校验 `id > 0` 就认为已经解决；大量格式合法但不存在的 ID 仍可能穿透。

## 345. 缓存穿透为什么会给数据库造成压力？

**面试回答**

因为缓存无法吸收这类请求，每次都要占用数据库连接、解析和执行查询、读取索引页并返回结果。大量无效请求会与正常业务争夺连接池、CPU、I/O 和线程资源。

**原理与理解**

缓存价值来自复用已有结果；不存在结果若不复用，命中率对这部分流量始终为零。压力不仅在数据库，应用线程池、网络、连接池和日志系统也可能先达到瓶颈。

**成立条件与边界**

“一次不存在查询就很慢”不是重点。主键未命中可能成本较低，但高 QPS、随机 Key 导致的缓存污染和下游排队仍会放大影响；是否危险需要结合容量和限流阈值判断。

**实际场景（通用工程）**

排查穿透时同时观察无效 ID 比例、Redis miss、数据库 QPS/连接池等待、接口来源和 Key 基数，不能只看单条 SQL 的执行时间。

**常见追问**

- 为什么索引查询也可能压垮数据库？（单次便宜不代表海量并发的总成本低）
- 除数据库外还会影响什么？（应用线程池、连接池、网络和日志）

**易错点**

不要把问题描述成“缓存完全失效”；正常 Key 仍可能命中，只是异常流量没有被缓存层吸收。

## 346. 如何解决缓存穿透？

**面试回答**

通常分层治理：入口做参数校验、鉴权、限流和风控；对重复查询的不存在结果缓存短 TTL 的缺失标记；对大规模合法 ID 集合可使用布隆过滤器预判；数据库和应用仍需保留容量保护与降级。

**原理与理解**

空值缓存适合重复无效 Key，布隆过滤器适合用较小内存过滤大集合中的明显不存在项，限流用于控制随机高基数攻击。多个措施针对的流量形态不同，组合使用比单一方案可靠。

**成立条件与边界**

布隆过滤器的“可能存在”仍要查库；空值缓存会占内存，并可能短暂遮蔽刚创建的数据。安全场景不能把布隆过滤器当作鉴权，因为误判、同步延迟和过滤器丢失都需要回退路径。

**实际场景（生产能力）**

可采用“校验与鉴权 → 频率限制 → Bloom 预判 → Cache Aside → 缺失标记短 TTL”的链路，并监控空值 Key 数量、误判回源和过滤器同步失败。

**常见追问**

- 空值缓存适合什么情况？（同一不存在 Key 被重复查询）
- 布隆过滤器适合什么情况？（元素集合大、允许少量误判并能维护成员同步）

**易错点**

治理缓存穿透不能替代鉴权；“ID 可能存在”不等于当前用户有权访问。

## 347. 缓存空值如何解决缓存穿透？

**面试回答**

数据库确认数据不存在后，在 Redis 写入专门的缺失标记并设置较短 TTL。后续相同 Key 命中该标记即可返回“未找到”，不再重复访问数据库。

**原理与理解**

缺失标记应与 Redis 故障、序列化失败和真实空字段区分。创建该数据时还要删除或覆盖对应负缓存，否则在 TTL 到期前，新数据可能仍被误判为不存在。

**成立条件与边界**

它只对重复 Key 有效。攻击者持续生成不同 Key 时，会造成大量空值写入和内存污染，仍需限流或布隆过滤器。TTL 太长影响新数据可见性，太短则降低保护效果。

**实际场景（通用工程）**

查询菜品 ID 不存在时可以写入轻量 sentinel，TTL 根据补录概率和攻击流量确定；创建或恢复菜品时同步失效该 sentinel，并统计负缓存命中率。

**常见追问**

- 为什么使用专门标记而不是普通 `null`？（便于区分 miss、真实空值和反序列化异常）
- 为什么通常设置较短 TTL？（平衡回源保护、新数据可见性和内存占用）

**易错点**

不要把“1～5 分钟”当作固定正确答案；TTL 应由业务可见性要求、请求量和容量决定。

## 348. 什么是布隆过滤器？

**面试回答**

布隆过滤器是基于位数组和多个哈希函数的概率型成员结构。查询返回“不存在”时，在标准模型下可以确定元素未被加入；返回“可能存在”时仍可能是假阳性，需要访问数据库确认。

**原理与理解**

插入元素时，把多个哈希位置设为 1；查询时只要有一个对应位为 0，就判定未加入，全部为 1 则判定可能存在。它不存完整元素，因此比集合节省空间，但不能返回元素本身。

**成立条件与边界**

“不会漏判”成立的前提是元素成功加入、过滤器未丢失且没有不安全删除。若新数据先写库却未及时写入 Bloom，应用层仍可能把真实存在数据挡掉。标准 Bloom 不支持删除，删除需求可评估计数 Bloom 或 Cuckoo Filter。

**实际场景（项目核验项）**

把所有菜品 ID 放入 Bloom 只是候选方案，不是已确认项目实现。若采用，需要设计初始化、增量添加、重建、容量、目标误判率和故障时回退到数据库的流程。

**常见追问**

- Bloom 会出现哪种误判？（未加入的元素可能被判断为“可能存在”）
- 什么时候可能出现业务层面的漏放行？（过滤器未同步新元素、数据丢失或错误删除）

**易错点**

口诀“说没有就没有”只适用于正确维护的标准 Bloom；工程系统还存在同步与持久化故障。

## 349. 布隆过滤器为什么存在误判？

**面试回答**

不同元素可能把相同的位设为 1。查询一个从未加入的元素时，它对应的多个位置可能恰好都被其他元素置为 1，于是过滤器返回“可能存在”，形成假阳性。

**原理与理解**

误判率与位数组大小、已插入元素数和哈希函数个数有关。容量不足或填充度过高会增加假阳性；Redis Bloom 可按预期容量和 `error_rate` 预留过滤器，扩展为多个子过滤器也会增加查询与内存成本。

**成立条件与边界**

目标 `error_rate` 是概率参数，不代表每固定 N 次查询必然误判一次。Bloom 只能减少明显无效查询，不能作为数据库存在性的最终证据，也不能保证恶意流量完全不回源。

**实际场景（通用工程）**

容量评估应基于预计 ID 数量和可接受回源比例；上线后监控过滤器容量、子过滤器数量、实际误判回源和构建失败，而不是只使用默认参数。

**常见追问**

- 怎样降低误判率？（增加位空间并按容量选择合适哈希函数数量）
- 误判会造成什么？（不存在数据被放行去查库，但不应直接返回“存在”）

**易错点**

误判来自位共享，不是哈希函数“算错”；过低的目标误判率也会增加内存和计算成本。

## 350. 什么是缓存击穿？

**面试回答**

缓存击穿指一个高热 Key 过期、被删除或尚未建立时，大量并发请求同时 miss 并回源，造成事实来源瞬时负载激增。英文资料也常称 cache stampede 或 thundering herd。

**原理与理解**

问题不只是 Key 消失，而是该 Key 热度高、回源成本高且多个请求同时重建。若每个请求都独立查询数据库并回填，就会把一个逻辑请求放大成大量下游操作。

**成立条件与边界**

普通低频 Key 过期通常只是一次 miss，不构成击穿。单个热 Key 也可能只压垮一个 Redis 分片或下游接口，而不一定首先压垮 MySQL，必须按实际依赖分析。

**实际场景（项目核验项）**

热门菜品详情可用来解释击穿时序，但简历没有证明项目存在爆款流量或已经使用防击穿锁；面试应明确这是通用高并发场景。

**常见追问**

- 击穿关注什么对象？（单个或少量高热 Key）
- 常见解决办法是什么？（请求合并、互斥重建、逻辑过期，见 [[05-Redis/04-缓存穿透击穿雪崩#353. 如何解决缓存击穿？]]）

**易错点**

不要说“只要热点 Key 过期就一定击穿”；还需要同时存在足够并发和昂贵回源。

## 351. 缓存击穿通常发生在什么场景？

**面试回答**

典型场景是秒杀商品、热点新闻、首页配置或大客户数据在访问高峰时过期或被主动失效，许多实例同时发现 miss，并发执行同一个昂贵查询或远程调用。

**原理与理解**

触发因素也可能是应用发布后冷启动、缓存节点故障导致热 Key 丢失、批量失效，或回填本身耗时过长。回填窗口越长，同时进入的请求越多，放大效应越明显。

**成立条件与边界**

“热点 + 过期 + 高并发”是常见口诀，但过期不是唯一原因；Key 被删除、淘汰或从未预热也能触发。反之，高并发读取一个始终可用的 Key 不属于击穿，而是热 Key 负载问题。

**实际场景（通用工程）**

活动前根据历史 QPS、Key 访问分布、回源 P99 和数据库安全容量，估算同一回填窗口内可能积累多少请求，再决定是否预热或合并请求。

**常见追问**

- 冷启动会击穿吗？（高热 Key 尚未建立且大量请求同时到达时会）
- 热 Key 未过期却很慢属于击穿吗？（不一定，可能是 Redis 分片或网络热点）

**易错点**

不要把击穿限制为“TTL 正好到零”这一种触发方式。

## 352. 什么是热点 Key？

**面试回答**

热点 Key 是在一段时间内承载显著高于普通 Key 的请求量、带宽或写入量的 Key。它可能成为单分片 CPU、网络、内存访问或下游回源的瓶颈。

**原理与理解**

Redis Cluster 按 Key 分片，一个超热 Key 仍由单个分片处理，不能自动拆到所有节点。大 Value 与普通小 Value 即使 QPS 相同，带宽成本也不同，因此识别热度要同时看频率和数据大小。

**成立条件与边界**

没有通用的固定 QPS 阈值。热点取决于实例容量、请求类型、Value 大小、流水线使用和延迟目标。读热点可用本地多级缓存或副本分担读，写热点通常更难拆分。

**实际场景（生产能力）**

通过客户端埋点、代理/服务端监控、采样和业务榜单识别热点，并为突发热点准备 Key 拆分、本地短缓存、限流和降级；所有方案都要评估一致性代价。

**常见追问**

- Redis Cluster 能自动解决单个热 Key 吗？（不能，单个 Key 通常仍落在一个分片）
- 大 Key 和热 Key 是一回事吗？（不是，但大 Value 会放大热 Key 的带宽与阻塞影响）

**易错点**

热点 Key 不只指“爆款商品”，也可能是全局配置、计数器、锁或集合。

## 353. 如何解决缓存击穿？

**面试回答**

核心是减少同一 Key 的并发回源：使用 single-flight 或每 Key 互斥锁，只让一个请求重建；采用逻辑过期加异步刷新，在允许陈旧读取时先返回旧值；还可配合提前刷新、预热、限流和降级。

**原理与理解**

互斥重建牺牲部分等待时间换取数据库保护；逻辑过期是 stale-while-revalidate，用短暂陈旧换取低延迟和可用性；主动刷新把重建移到到期前。三者针对不同的一致性和延迟要求。

**成立条件与边界**

“热点永不过期”不是完整方案：数据仍会更新，Key 也可能被淘汰、删除或因 Redis 故障丢失。逻辑过期不适合权限、库存或价格结算等不能接受旧值的判定。

**实际场景（通用工程）**

展示型菜品详情可考虑逻辑过期；需要读取最新状态的下单校验更适合互斥回源或直接读取事实来源。选择前先明确是否允许返回旧值和最长等待时间。

**常见追问**

- 互斥锁和逻辑过期怎么选？（前者等新值，后者允许旧值并异步刷新）
- 还需要 TTL 吗？（逻辑过期 Key 也可配置更长物理 TTL 作为内存与故障兜底）

**易错点**

解决击穿不是简单“加一把全局锁”；锁粒度应按 Key，并配置超时、回退和观测。

## 354. 互斥锁如何解决缓存击穿？

**面试回答**

缓存 miss 后先竞争该数据对应的锁；获取锁的请求再次检查缓存，仍未命中才查询事实来源并回填。其他请求等待、退避重试或按策略降级，使同一时刻通常只有一个加载者回源。

**原理与理解**

Redis 简单锁通常用 `SET lock-key token NX PX ttl` 一次完成“仅不存在时写入”和租约设置；释放时用 Lua 比较 token 后再删除，避免误删租约过期后由其他请求获得的锁。

**成立条件与边界**

锁 TTL 要覆盖最坏回源时间，但请求暂停或回源超时仍可能使租约提前失效，产生多个加载者。没拿到锁的请求不能无限自旋；还要处理 Redis 故障、锁服务不可用和加载者崩溃。

**实际场景（生产能力）**

按缓存 Key 建细粒度锁，获取失败采用带抖动的短退避并设置总超时；加载完成、失败和锁竞争均打指标。若业务允许，也可在超时后返回旧值或降级数据。

**常见追问**

- 为什么获取锁后还要再查一次缓存？（等待期间其他请求可能已完成回填）
- 为什么不能直接 `DEL` 释放？（锁可能已过期并被其他请求重新获得）

**易错点**

只回答 `SETNX` 不够；正确性还依赖租约、唯一 token、条件释放、双重检查和失败策略。

## 355. 什么是逻辑过期？

**面试回答**

逻辑过期是在缓存值中保存业务过期时间。读取发现逻辑过期后，可以先返回仍可接受的旧值，并由一个后台任务异步刷新，这是一种 stale-while-revalidate 策略。

**原理与理解**

Key 在逻辑到期时仍存在，因此大量请求不会同时变成物理 miss。第一个成功获得刷新资格的请求重建缓存，其他请求继续读取旧值或按业务等待，刷新完成后替换数据和新的逻辑时间。

**成立条件与边界**

物理 Key 不必真的“永不过期”，通常可设置更长 TTL 作为内存泄漏和长期刷新失败的兜底。该方案明确允许短暂陈旧，必须定义最大陈旧时间、刷新失败重试和旧值不可用时的降级。

**实际场景（通用工程）**

首页展示、推荐或商品描述可接受短暂旧值时适合逻辑过期；支付状态、权限和库存判断不应未经评估就返回旧值。

**常见追问**

- 与物理 TTL 有什么区别？（逻辑到期由应用判断，Key 不会立刻因该时间消失）
- 如何避免多个线程同时刷新？（每 Key single-flight、互斥锁或原子刷新标记）

**易错点**

逻辑过期不是“后台随便开一个线程”；要使用受管理的线程池或任务系统，并处理失败、积压和应用重启。

## 356. 什么是缓存雪崩？

**面试回答**

缓存雪崩指大量不同 Key 在相近时间失效、被淘汰或无法访问，导致大范围请求同时回源，超过数据库或下游服务容量并引发连锁故障。

**原理与理解**

它可能由同步 TTL、批量删除、内存淘汰、冷启动、Redis 整体故障或网络隔离触发。与击穿相比，雪崩影响的是一批 Key 或整个缓存层，回源查询类型和业务范围更广。

**成立条件与边界**

大量 Key 过期不一定造成雪崩，还要看是否同时有请求、是否能快速重建以及下游余量。Redis 故障也不必然压垮数据库，如果应用有断路、限流和降级而不是无条件回源。

**实际场景（项目核验项）**

批量缓存菜品列表可以作为雪崩示例，但没有源码和监控证据时，不能声称项目曾经同时写入、统一 30 分钟过期或发生过数据库事故。

**常见追问**

- 雪崩与击穿有什么区别？（前者涉及大量 Key 或整个缓存层，后者集中在单个或少量热 Key）
- 常见治理入口是什么？（TTL 打散、高可用、限流降级等，见 [[05-Redis/04-缓存穿透击穿雪崩#358. 如何解决缓存雪崩？]]）

**易错点**

“Redis 宕机就是雪崩”是便于记忆的说法；更准确地说，缓存不可用后无保护回源并造成级联过载才形成雪崩。

## 357. 缓存雪崩通常是怎么产生的？

**面试回答**

常见原因包括批量写入的 Key 使用相同 TTL 而集中过期、批量失效或淘汰、发布后冷缓存、大面积 Redis/网络故障，以及应用在缓存异常时无上限地回源数据库。

**原理与理解**

真正的放大链路是“缓存容量骤降 → miss 激增 → 下游排队与超时 → 重试增加 → 更多资源耗尽”。没有退避的客户端重试会进一步加速级联故障。

**成立条件与边界**

主从复制本身不等于自动高可用，客户端必须能发现新主节点；Redis Cluster 还要求分片有副本和足够多数节点。异步复制与故障转移存在短暂不可用或写丢失窗口。

**实际场景（通用工程）**

演练 Redis 超时、节点切换和批量过期，验证客户端超时、连接池、熔断、数据库限流和降级响应，而不是只验证 Sentinel 或 Cluster 能否完成选主。

**常见追问**

- 为什么客户端重试会放大雪崩？（超时请求叠加重试，进一步占用缓存和下游资源）
- 有 Sentinel 就不会雪崩吗？（不能保证，仍有检测、切换、客户端重连和容量边界）

**易错点**

不要把雪崩原因只背成“TTL 相同或 Redis 宕机”，容量淘汰、批量失效和错误回退策略同样常见。

## 358. 如何解决缓存雪崩？

**面试回答**

按原因分层处理：用 TTL 抖动和分批预热避免集中失效；用 Sentinel 或带副本的 Cluster、容量规划和故障演练提升缓存可用性；应用侧用超时、请求合并、限流、熔断和降级保护数据库。

**原理与理解**

TTL 抖动摊平过期时间，预热降低冷启动 miss；高可用减少单点故障，但不能消除切换窗口；限流、舱壁和断路器保证缓存故障时回源流量不超过数据库安全容量。

**成立条件与边界**

本地多级缓存可以兜底读取，但会引入多副本失效问题。直接“Redis 挂了就全部查库”通常最危险；降级数据是否可用、能丢弃哪些请求必须由业务预先定义。

**实际场景（生产能力）**

建立缓存故障预算：配置短连接/命令超时和有限重试，按接口限制最大回源并发，非核心接口返回兜底或稍后重试，核心链路保留数据库容量并设置告警。

**常见追问**

- TTL 随机值解决哪一类问题？（同步过期，不解决 Redis 整体不可用）
- Cluster 和 Sentinel 的作用一样吗？（Sentinel 面向非分片主从故障转移；Cluster 同时提供分片，并在有副本时支持故障转移）

**易错点**

“部署集群”不是完整答案；高可用拓扑、客户端支持、超时重试和数据库保护缺一不可。

## 359. TTL 加随机值有什么作用？

**面试回答**

在符合业务陈旧容忍度的基础 TTL 上加入随机抖动，可以把一批 Key 的预计过期时刻分散开，减少同一瞬间集中 miss 和回源的概率。

**原理与理解**

例如批量加载时，不让所有 Key 都精确在 30 分钟到期，而是在合理区间内分布。随机范围应与 Key 数量、访问分布、回源能力和业务 TTL 要求匹配。

**成立条件与边界**

随机抖动只处理同步过期，不能解决 Redis 故障、批量删除、内存淘汰或单个热点 Key 击穿。它也不保证过期绝对均匀；如果大量流量只访问少数 Key，仍需热点保护。

**实际场景（项目核验项）**

“30 分钟加随机几分钟”只能作为示例。项目是否配置 TTL、基础时长和抖动范围，应从 Spring Cache 配置或 `RedisTemplate` 写入代码核验。

**常见追问**

- 随机范围如何确定？（在新鲜度约束内，根据批量规模和下游安全回源能力评估）
- 可以使用负抖动吗？（可以，但必须保证最终 TTL 为正且不违反最短缓存收益）

**易错点**

不要为了打散过期而破坏业务允许的最大陈旧时间，也不要把 TTL 抖动当成万能防雪崩方案。

## 360. 缓存穿透、击穿、雪崩有什么区别？

**面试回答**

穿透是不存在数据持续 miss 并回源；击穿是单个或少量热点 Key 失效后并发回源；雪崩是大量 Key 或整个缓存层同时失去服务能力，引发大范围回源和级联过载。

**原理与理解**

三者可按“数据是否存在、影响 Key 范围、并发形态”区分：穿透关注无效 Key，击穿关注热点的并发重建，雪崩关注缓存能力大面积骤降。对应治理分别偏向负缓存/Bloom/限流、single-flight/逻辑过期、TTL 打散/高可用/系统降级。

**成立条件与边界**

这些是面试中的故障模型，不是互斥的 Redis 错误码。随机无效 Key、热点过期和缓存节点故障可能同时发生，应通过指标和时序定位真正的流量放大点。

**实际场景（通用工程）**

告警后先看 miss 的 Key 基数和分布：大量不存在且分散的 Key 偏向穿透；单个热 Key 回源峰值偏向击穿；全局命中率骤降并伴随缓存故障偏向雪崩。

**常见追问**

- 三个关键词是什么？（不存在、热点并发重建、大面积缓存能力下降）
- 它们能否同时发生？（可以，防护也需要分层组合）

**易错点**

不要只背“单个/多个”的数量差异；穿透的核心是不存在数据，击穿的核心是热点并发回源，雪崩的核心是大面积能力下降与级联过载。
