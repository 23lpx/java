# Redis基础

## 305. Redis 是什么？

**面试回答**

Redis 是一个基于内存的、高性能的键值存储数据库（NoSQL），数据存在内存里所以读写很快，支持丰富的数据类型（String、Hash、List、Set、ZSet 等），常用作缓存、分布式锁、消息队列等。

**理解**

Redis 数据主要放内存，所以比磁盘数据库快几个数量级；它支持持久化（RDB/AOF）避免重启丢数据；提供多种数据结构和原子操作，能做很多事。定位是「高性能的内存数据库」，不只是「缓存」。

**场景**

项目里用 Redis 做菜品/套餐缓存、验证码存储、分布式锁，利用它的高性能和 TTL 过期能力。

**常见追问**

- Redis 是关系型数据库吗？（不是，是 NoSQL 键值数据库）
- Redis 数据存哪？（主要内存，可选持久化到磁盘）

**易错点**

Redis 是「内存数据库」，不只是「缓存」；它能做缓存、锁、队列等多种事，别窄化理解。

## 306. Redis 为什么适合做缓存？

**面试回答**

因为 Redis 数据存在内存、读写极快（微秒级），支持 TTL 自动过期、丰富的数据结构，能显著降低数据库压力、提高响应速度，所以非常适合做缓存。

**理解**

缓存的核心诉求是「快 + 能过期 + 好管理」。Redis 内存存储满足「快」；TTL 满足「自动过期」；多种数据结构满足不同缓存形态（String 存对象、Hash 存字段、ZSet 做排行榜）。相比把缓存放应用内存或数据库，Redis 独立、共享、性能好。

**场景**

项目里把高频查询的菜品、套餐数据缓存到 Redis，查询先走缓存，减轻 MySQL 压力、加快响应。

**常见追问**

- 缓存一般放什么数据？（高频读、不常变的数据）
- Redis 相比其他缓存优势？（内存快、数据结构丰富、持久化）

**易错点**

Redis 适合做缓存的核心是「内存快 + TTL 过期 + 结构丰富」，不是「是数据库所以能做缓存」。

## 307. Redis 为什么快？

**面试回答**

主要有几点：①数据存在内存，读写不经过磁盘 IO；②单线程执行命令，避免线程切换和锁竞争开销；③基于 IO 多路复用，一个线程高效处理大量并发连接；④高效的数据结构。

**理解**

「快」是多个因素叠加：内存访问天然比磁盘快几个数量级；单线程避免了多线程的上下文切换和加锁；IO 多路复用让单线程能同时监听大量连接，不必为每个连接开线程；数据结构的实现也经过优化。这些共同造就了 Redis 的高性能。

**场景**

项目里缓存查询能到微秒级，即使并发很高，单线程 + IO 多路复用也能高效应对。

**常见追问**

- 内存和磁盘速度差多少？（内存纳秒级，磁盘毫秒级，差几个数量级）
- 单线程为什么反而快？（省去线程切换和锁竞争）

**易错点**

Redis 快是「内存 + 单线程 + IO 多路复用 + 数据结构」综合结果，别只归因于「单线程」或「内存」一点。

## 308. Redis 是完全单线程的吗？

**面试回答**

不是完全单线程。Redis 的核心「命令执行」是单线程的（一个主线程串行处理命令），但 Redis 6.0 之后引入了多线程来处理网络 IO（读写 socket），其他一些后台任务（如持久化、内存回收）也用别的线程。

**理解**

要区分「执行命令」和「网络 IO」：命令的执行、对数据的操作始终是单线程串行的（这也是它数据操作无并发竞争的原因）；但网络数据的读取、发送在 Redis 6.0+ 可以用多线程加速。所以「Redis 单线程」准确说是「命令执行单线程」，不是整个进程只有一个线程。

**场景**

理解这点，面试就不会说错「Redis 完全单线程」；实际性能上 Redis 6 的多线程 IO 进一步提升了高并发吞吐。

**常见追问**

- 哪个部分是单线程？（命令执行/数据操作）
- Redis 6.0 多线程做了什么？（网络 IO 读写）

**易错点**

「Redis 完全单线程」是常见错误；准确表述是「命令执行单线程，6.0 起网络 IO 可多线程」。

## 309. Redis 单线程为什么还能这么快？

**面试回答**

因为单线程执行的是内存操作（本身就快），又避免了多线程的上下文切换和锁竞争开销，配合 IO 多路复用高效处理并发连接，所以即使单线程也能达到很高的吞吐。

**理解**

关键在「单线程做的是内存操作」——CPU 处理一条内存命令极快，瓶颈往往在网络 IO 而非 CPU。单线程省掉了线程切换、锁竞争这些额外开销，把 CPU 充分用在执行命令上；IO 多路复用让一个线程同时服务大量连接，不阻塞在单个连接上。所以「单线程」在这里反而是优势。

**场景**

项目里 Redis 单线程处理命令，但因为都是内存操作且无锁竞争，高并发下依然能保持高吞吐。

**常见追问**

- 单线程的优势？（无上下文切换、无锁竞争）
- 瓶颈在哪？（单线程下，大 Key 或慢命令会阻塞其他命令）

**易错点**

单线程快的前提是「内存操作 + 无锁」；同时要知道它的副作用——单个慢命令（如大 Key 删除）会阻塞整个 Redis。

## 310. 什么是 IO 多路复用？

**面试回答**

IO 多路复用是一种「一个线程同时监听多个网络连接」的技术：通过系统调用（如 epoll）监控多个 socket，哪个就绪就处理哪个，避免为每个连接开一个线程、也避免阻塞等待单个连接。

**理解**

传统做法一个连接一个线程，连接多了线程爆炸；或者一个线程阻塞在一个连接上，其他连接干等。IO 多路复用让一个线程注册多个 socket，用 epoll 等机制「谁有数据就处理谁」，单线程就能高效处理成千上万个并发连接。Redis 正是靠它实现高并发。

**场景**

项目里 Redis 同时面对大量客户端连接，靠 IO 多路复用在一个线程里高效轮询处理，支撑高并发。

**常见追问**

- Linux 上用什么？（epoll）
- 它解决什么问题？（单线程高效处理大量并发连接）

**易错点**

IO 多路复用是「一个线程监听多个连接、谁就绪处理谁」，是 Redis 单线程能高并发的关键，别理解成「多线程并行处理」。

## 311. Redis 常见的五种基本数据类型是什么？

**面试回答**

String（字符串）、Hash（哈希）、List（列表）、Set（集合）、ZSet（有序集合），每种对应不同场景。

**理解**

String 是最基础的 key-value，存字符串/数字/序列化对象；Hash 存「字段-值」集合，适合对象；List 是有序列表，可做队列栈；Set 是无序不重复集合，适合去重、交并集；ZSet 是带分数的有序集合，适合排行榜。理解各自特性才能选对类型。

**场景**

项目里 String 存验证码和对象缓存，Hash 存对象字段，ZSet 做排行榜，Set 做去重。

**常见追问**

- 五种类型分别是？（String、Hash、List、Set、ZSet）
- 存对象用哪种？（String 存序列化对象，或 Hash 存字段）

**易错点**

五种类型要能说清各自特征和适用场景，尤其 ZSet（有序集合）和 List（有序列表）别混淆。

## 312. String 适合哪些场景？

**面试回答**

String 是最通用类型，适合存简单值、序列化对象、计数器、验证码、缓存 JSON 字符串、分布式锁的 key 等。

**理解**

String 能存字符串、数字、二进制（如序列化后的对象）。常见场景：缓存「对象序列化成的 JSON」、验证码（带 TTL）、计数器（INCR 原子自增）、token 存储、分布式锁（SET NX EX）。它是使用最广泛的类型。

**场景**

项目里用 String 存验证码（带过期时间）、缓存菜品的 JSON 字符串、存 JWT token 等。

**常见追问**

- String 能存数字吗？（能，且支持 INCR/DECR 原子自增）
- 缓存对象用 String 怎么做？（序列化成 JSON 存，取出再反序列化）

**易错点**

String 是最基础类型，但「存对象」要序列化（JSON），取出要反序列化，别以为能直接存对象。

## 313. Hash 适合哪些场景？

**面试回答**

Hash 适合存「一个对象的多字段」或「一组相关的键值对」，比如用户信息、购物车（商品 id → 数量），可以按字段单独读写，比整体序列化更灵活。

**理解**

Hash 内部是一个「字段-值」映射，相当于「Redis 里的一个小 map」。适合对象属性较多、且需要按字段单独访问/更新的场景。相比把整个对象序列化成 String，Hash 能只改一个字段而不动其他字段。

**场景**

项目里可用 Hash 存购物车（field 是商品 id，value 是数量），或存对象的某些可独立更新的字段。

**常见追问**

- Hash 和 String 存对象区别？（Hash 可按字段操作，String 整体序列化）
- Hash 适合什么？（对象多字段、按字段更新）

**易错点**

Hash 的价值是「按字段独立读写」，适合需要部分更新对象的场景；如果总是整体读，String 序列化更简单。

## 314. List 适合哪些场景？

**面试回答**

List 是有序列表，适合做消息队列（先进先出）、最新消息列表、时间线、栈等，支持从两端插入和范围读取。

**理解**

List 底层是链表（或压缩列表），支持 LPUSH/RPUSH 在两端插入，LPOP/RPOP 从两端弹出，天然适合队列（FIFO）和栈（LIFO）。还支持按范围取（LRANGE）做「最近 N 条」列表。

**场景**

项目里可用 List 做简单的异步任务队列、最新评论/消息列表。

**常见追问**

- List 做队列用什么命令？（LPUSH + RPOP 或 BRPOP）
- List 适合做什么？（队列、栈、最新列表）

**易错点**

List 是「有序、可两端操作」的列表，适合队列栈；做可靠消息队列还是建议用专门的消息中间件，List 是简化方案。

## 315. Set 适合哪些场景？

**面试回答**

Set 是无序、不重复的集合，适合去重、共同好友、标签、抽奖去重、以及集合间的交并差运算。

**理解**

Set 保证元素唯一，且支持 SINTER（交集）、SUNION（并集）、SDIFF（差集）等集合运算。适合「唯一性」和「集合关系」场景：点赞去重、共同关注、标签系统、抽奖不重复等。

**场景**

项目里可用 Set 存点赞用户集合（去重）、用户标签、抽奖中奖名单去重。

**常见追问**

- Set 有什么特点？（无序、不重复）
- 共同好友怎么算？（SINTER 交集）

**易错点**

Set 核心是「无序 + 唯一 + 集合运算」，去重和交集是它的典型用途，别和 List（有序可重复）混淆。

## 316. ZSet 适合哪些场景？

**面试回答**

ZSet 是带分数的有序集合，适合排行榜、按权重排序、延迟队列、按时间/分数排序的场景，每个元素带一个 score 用于排序。

**理解**

ZSet 每个元素有个 score，按 score 从小到大排序，支持 ZADD 添加、ZRANGE 按排名取、ZREVRANGE 倒序取、ZINCRBY 增减分数。score 相同时按元素字典序。它天然适合「需要按某个数值排序」的场景。

**场景**

项目里可用 ZSet 做销量排行榜、热点菜品榜（score 是销量/热度）、延迟任务（score 是执行时间）。

**常见追问**

- ZSet 和 List 都是有序，区别？（ZSet 按 score 排序、元素唯一；List 按插入顺序、可重复）
- 排行榜用什么？（ZSet）

**易错点**

ZSet 的「有序」是按 score 排序，不是按插入顺序；且元素唯一，这是它和 List 的本质区别。

## 317. 什么是 TTL？

**面试回答**

TTL（Time To Live）是键的生存时间，即一个 Key 在 Redis 里能存活多久，到期后自动过期删除。

**理解**

通过 EXPIRE 或 SET 时带 EX 参数给 Key 设置过期时间，TTL 会倒计时，归零后 Key 自动失效。TTL 是缓存的关键能力——让缓存数据「用旧了自动淘汰」，避免缓存无限增长、也避免长期不一致。

**场景**

项目里缓存菜品数据设 TTL（如 30 分钟），验证码设 TTL（如 5 分钟），到期自动删除。

**常见追问**

- 怎么设 TTL？（EXPIRE key seconds，或 SET key value EX seconds）
- TTL 到期会怎样？（Key 自动过期删除）

**易错点**

TTL 是「过期时间」，缓存「必须设 TTL」是共识；不设 TTL 的缓存会一直存在，可能造成脏数据和内存浪费。

## 318. 为什么缓存通常要设置 TTL？

**面试回答**

因为缓存数据会「变旧」，设 TTL 让它到期自动失效，既能避免缓存长期与数据库不一致（脏数据），又能防止缓存无限增长占满内存。

**理解**

缓存存的是数据库的副本，数据库更新后缓存可能过时。设 TTL 能「兜底」：即使删除缓存的操作漏了，数据到期也会自动失效、下次重新从库加载，把不一致的时间窗口限制住。同时 TTL 保证缓存不会只增不减，控制内存。

**场景**

项目里菜品/套餐缓存都设了合理的 TTL，避免数据长期不一致，也防止内存被占满。

**常见追问**

- 不设 TTL 有什么问题？（可能长期脏数据 + 内存无限增长）
- TTL 设多长合适？（看业务容忍的不一致时长和更新频率）

**易错点**

TTL 的两个作用「防脏数据 + 控内存」都要答到，别只说「自动删除」。

## 319. Redis 中 Key 应该如何设计？

**面试回答**

用「业务前缀 + 冒号分隔 + 唯一标识」的形式，如 `dish:info:{id}`，做到可读、不冲突、便于批量管理，同时避免过长和含义不明。

**理解**

好的 Key 设计要点：①加业务前缀区分模块（如 dish:、order:、user:）；②用冒号分层；③包含唯一标识；④长度适中（太长占内存、太短无意义）；⑤避免特殊字符。这样既能一眼看懂、避免不同业务 Key 撞名，又能用前缀批量删除/统计。

**场景**

项目里缓存 Key 设计为 `dish:info:{id}`、`setmeal:list:category:{id}` 等，清晰且可按前缀管理。

**常见追问**

- 为什么加前缀？（区分业务、避免冲突、方便批量操作）
- Key 能太长吗？（不建议，占内存且影响性能）

**易错点**

Key 设计核心是「前缀 + 冒号 + 唯一标识」，目的是可读、不冲突、可批量管理；别用含义不明的随机 Key。
