# Redis基础

## 305. Redis 是什么？

**面试回答**

Redis 是以内存数据集为核心的数据结构服务器。它以 Key 访问数据，提供 String、Hash、List、Set、Sorted Set 等结构和原子命令，并支持过期、持久化、复制与集群能力。它既可用作共享缓存，也可按需求承担数据库、计数、限流或消息等职责，但角色要由一致性、持久性和可用性要求决定，不能把它简单等同于“缓存”或关系型数据库。

**原理与理解**

Redis 的价值不仅是把字节放进内存，还在于由服务端直接提供面向数据结构的操作。例如计数可用 `INCR`，集合去重可用 `SADD`，排行榜可用 `ZADD`。单条命令通常具有原子执行语义，应用可以减少“读出—修改—写回”的竞争窗口。数据主要在内存中，但可通过 RDB、AOF 等机制落盘；是否能承受数据丢失仍取决于持久化、复制、故障转移和备份方案。

**成立条件与边界**

- Redis 不是关系型数据库：没有传统关系模型、外键和通用 SQL 事务语义。
- “在内存中”不等于“永不落盘”，也不等于“开启持久化后绝不丢数据”。
- 能否作为主存储，要评估数据规模、查询模型、持久性、恢复目标和运维能力；不能只因它快就替代数据库。
- “分布式锁”“消息队列”等是基于特定命令和协议构建的能力，需要额外处理租约、确认、重试与故障边界。

**实际场景**

**真实项目边界：** 简历可确认项目使用了 Redis，并通过 `RedisTemplate`、Spring Cache 访问缓存；但现有材料不能证明具体缓存对象、Key、TTL、分布式锁或消息实现，面试时只陈述能够由代码和配置核验的内容。

**常见追问**

- Redis 只能做缓存吗？不能，还可用于计数、集合运算、排序、流式消息等，但每种用途都要单独评估可靠性。
- Redis 的值只是字符串吗？Key 是二进制安全的字符串，Value 则有多种数据类型；各类型中的元素最终也以字节序列表达。
- Redis 开了持久化就能当数据库吗？不能直接推出，还要看刷盘策略、复制、备份、恢复演练和业务容错目标。

**易错点**

- 把 Redis 只定义成“缓存”，忽略其数据结构服务器定位。
- 把“原子命令”扩大成任意多条命令、跨 Key 操作都天然具有事务性。
- 未核验代码就把锁、验证码、排行榜等通用用法说成真实项目实现。

## 306. Redis 为什么适合做缓存？

**面试回答**

Redis 适合做共享缓存，主要因为工作集在内存中、访问延迟通常较低，多个应用实例可以共享数据；同时它提供 TTL、内存淘汰、原子命令和多种数据结构，便于控制数据生命周期并承载不同访问模式。是否真正提升性能仍取决于命中率、网络往返、序列化成本、Key 分布和回源代价。

**原理与理解**

应用内本地缓存省去网络往返，但每个实例各有副本，容量和一致性管理更复杂；Redis 是独立服务，增加了一次网络访问，却能让多个实例共享缓存并集中控制 TTL、容量和高可用。缓存收益来自“命中 Redis 的总成本显著小于回源成本”，而不是“用了 Redis 就一定更快”。批量读取或 Pipeline 可以减少多次 RTT，但也要限制批次，避免服务端积压大量响应。

**成立条件与边界**

- 热点数据应有足够命中率，且 Redis 的网络、连接池、序列化与反序列化成本低于回源成本。
- Redis 失效、超时或大面积未命中时，下游必须有隔离、限流、降级或重建保护。
- TTL 只限制缓存存活时间，不自动保证缓存与数据库强一致。
- 持久化不是 Redis 适合做缓存的必要条件；是否开启取决于重建成本和恢复目标。
- 本地缓存、Redis 和数据库可以分层组合，没有一种方案在所有场景中都更优。

**实际场景**

**真实项目边界：** 可确认项目使用 Redis/Spring Cache 降低重复查询成本；具体缓存了哪些对象、命中率、TTL 和失效策略仍需根据缓存注解、Key 生成逻辑和配置核验，不能预设为菜品或套餐缓存。

**常见追问**

- Redis 与本地缓存怎么选？极低延迟、少量实例可优先本地缓存；需要跨实例共享与集中管理时可用 Redis，也可组成两级缓存。
- 什么数据适合缓存？读取频繁、回源昂贵、可接受一定过期或有可靠失效机制的数据。
- Redis 有持久化为什么仍需数据库？缓存通常不是权威数据源，持久性、查询能力和一致性模型也与数据库不同。

**易错点**

- 说 Redis 访问“一定是微秒级”，忽略网络、排队、序列化和长尾延迟。
- 只回答“内存快”，遗漏共享、过期、淘汰和原子操作等工程价值。
- 把 Redis 与本地缓存简单比较为绝对优劣。

## 307. Redis 为什么快？

**面试回答**

Redis 的低延迟来自一组条件：主要工作集位于内存；核心路径和数据结构实现经过优化；事件循环配合 I/O 多路复用处理大量连接；多数核心命令按顺序执行，减少共享数据上的锁竞争；客户端还能用批量命令或 Pipeline 摊薄网络往返。最终性能仍受命令复杂度、数据大小、网络、持久化、复制、硬件和客户端实现影响。

**原理与理解**

内存访问避免了每次请求都等待随机磁盘 I/O，但一次 Redis 调用仍包含客户端排队、网络 RTT、协议解析、命令执行、序列化和返回传输。I/O 多路复用解决的是等待大量连接的问题；顺序执行让核心状态变更更简单；Pipeline 通过批量发送命令减少逐条 RTT 和系统调用开销。这些因素共同生效，不能用“因为单线程”一个原因概括。

**成立条件与边界**

- O(1) 只是算法复杂度，不代表固定耗时；Value 很大、网络慢或实例繁忙时仍可能高延迟。
- O(N) 命令、大 Key、长 Lua/Function、阻塞式模块命令会占用执行线程并影响其他客户端。
- 开启 AOF、生成快照、复制积压、内存换页或系统抖动都会影响长尾延迟。
- Pipeline 提升吞吐但不会让一条命令本身更快；批次过大会占用客户端和服务端内存。
- 性能数字必须在给定版本、配置、数据分布、并发模型和硬件上压测，不能背固定 QPS。

**实际场景**

**生产能力：** 排查“Redis 变慢”时，应分别测客户端总耗时、网络 RTT 和服务端命令耗时，并结合 Slow Log、延迟监控、命令复杂度、大 Key、CPU、内存与持久化指标定位，不能先认定是 Redis 主线程或网络。

**常见追问**

- 内存访问为什么不等于请求无 I/O？Redis 调用仍有网络 I/O，持久化和复制也可能涉及磁盘与网络。
- Pipeline 为什么能提高吞吐？它减少逐条命令的往返和系统调用开销，但响应仍需排队和读取。
- Redis 快是否意味着可以执行任意 O(N) 命令？不是，单个慢命令会扩大同实例其他请求的排队时间。

**易错点**

- 把快完全归因于内存或单线程。
- 用“内存纳秒、Redis 微秒”直接推导端到端接口耗时。
- 只看平均延迟，不看 P99、超时、批次大小和慢命令。

## 308. Redis 是完全单线程的吗？

**面试回答**

不是。准确说法是：Redis 多数核心命令的执行路径以主线程顺序处理，因此同一实例上不靠多个命令线程并行修改核心数据集；但进程还会用后台线程或子进程处理异步释放、部分慢 I/O、RDB/AOF 等工作。现代 Redis 还可配置 I/O 线程协助客户端套接字读写和协议解析，所以“Redis 完全单线程”不准确。

**原理与理解**

需要把“命令执行”“网络 I/O”和“后台任务”分开。核心命令顺序执行降低了共享状态同步复杂度；持久化快照、AOF 重写可能使用子进程，后台 I/O 和异步删除可由后台线程完成；Redis 6.0 起引入的线程化 I/O 属于网络路径优化，且是否启用与具体行为受版本和配置影响。它没有把任意数据命令都改成多线程并行执行。

**成立条件与边界**

- “多数核心命令顺序执行”不表示所有模块、查询引擎或未来版本都遵循同一内部实现。
- 单条命令原子执行不等于多条独立命令构成原子事务。
- 不同客户端之间谁先到达主线程不应由业务代码猜测；需要顺序时应使用事务、脚本或业务协议。
- I/O 线程默认配置和职责会随版本演进，面试应说明所讨论的 Redis 版本。

**实际场景**

**通用工程：** 当 CPU 已成为瓶颈时，先确认消耗来自套接字 I/O 还是命令执行。只有网络读写占比较高且版本、CPU 核数适合时，才评估 I/O 线程；若瓶颈是慢命令或大 Key，增加 I/O 线程不能解决根因。

**常见追问**

- 哪部分通常是单线程？多数核心命令的解析后执行与数据结构操作在主执行路径上顺序完成。
- Redis 6.0+ 的 I/O 线程做什么？可协助客户端套接字读写和协议解析，具体以版本和配置为准。
- RDB 后台保存也是线程吗？常见实现是 `fork` 子进程，不应把进程和线程混为一谈。

**易错点**

- 回答“Redis 整个进程只有一个线程”。
- 回答“Redis 6 以后命令都能多线程并行执行”。
- 忽略子进程、后台线程、模块和版本差异。

## 309. Redis 单线程为什么还能这么快？

**面试回答**

因为主执行路径主要处理短小的内存命令，事件循环在连接就绪时才处理 I/O，多数命令顺序执行又减少了共享状态上的锁与线程切换；再配合高效数据结构和客户端批处理，单个核心也能提供较高吞吐。但单线程不是性能来源本身，而是一种在特定工作负载下有效的设计，也构成 CPU 密集和慢命令场景的上限。

**原理与理解**

如果每条命令很快，顺序执行可以把时间集中在真正的数据操作上，并让单条命令天然具有清晰的原子边界。大量客户端连接不会各自占一个执行线程，而是由事件循环处理已就绪连接。另一方面，只要某条命令长时间占住执行线程，后续请求就会排队；因此 Redis 的高性能依赖命令短、Value 有界和内存工作集健康。

**成立条件与边界**

- 优势成立于短命令和内存可承载的工作集；CPU 密集脚本、大范围集合运算或大 Key 会破坏此前提。
- “无锁”只能用于概括核心命令串行修改数据的主要路径，不能推导 Redis 内部完全不存在锁。
- 瓶颈不总在网络，也可能在单核 CPU、内存带宽、持久化、复制或客户端。
- 要利用多核处理命令，通常需要分片、Cluster 或多个实例，并同时处理跨 Key 操作与热点分布问题。

**实际场景**

**生产能力：** 对热点接口压测时，把普通 `GET/SET` 与大范围 `SMEMBERS`、`HGETALL` 或长脚本分开观察。若慢命令使同实例 P99 同步上升，应缩小数据结构、改成渐进遍历/异步任务或拆分实例，而不是只扩客户端线程池。

**常见追问**

- 单线程的主要好处是什么？核心状态变更模型简单，减少锁竞争和线程切换，但不是无条件更快。
- 单线程的主要缺点是什么？长命令会阻塞同一执行路径，单实例命令执行能力受单核约束。
- 如何利用多核？先优化命令与数据模型，再按容量和吞吐需要分片或部署多个实例。

**易错点**

- 把“单线程”说成 Redis 快的充分条件。
- 断言 Redis 的瓶颈一定只在网络。
- 认为 I/O 线程能让慢命令并行执行，从而消除阻塞。

## 310. 什么是 IO 多路复用？

**面试回答**

I/O 多路复用是让一个线程通过操作系统的就绪通知机制同时关注多个文件描述符：线程把多个 socket 注册给 `select`、`poll`、`epoll` 或 `kqueue` 一类机制，等待“哪些连接已经可读或可写”，再处理就绪连接。它减少了一个连接一个线程以及阻塞等待单个连接的成本，但不等于命令被多核并行执行。

**原理与理解**

网络连接的大量时间处于等待状态。如果每个连接都绑定一个线程，连接数增长会带来线程栈、调度和上下文切换开销。多路复用把“等待哪些连接就绪”交给操作系统，事件循环只处理已就绪事件。Redis 在不同平台选择适配的事件通知实现，不能把 `epoll` 当成所有系统上的唯一答案。

**成立条件与边界**

- 多路复用优化的是 I/O 等待与连接管理，不会降低命令本身的算法复杂度。
- “一个线程监听多个连接”是概念模型；现代 Redis 可配置 I/O 线程协助读写，不能据此断言网络路径永远只有一个线程。
- socket 就绪只表示当前可进行某类 I/O，不保证一次就能读完完整请求或写完全部响应。
- 事件循环中执行长任务仍会推迟其他就绪连接的处理。

**实际场景**

**通用工程：** 高连接数但单请求很轻时，多路复用能避免为每条连接长期占用一个工作线程；如果业务执行本身耗时很长，则还需要把耗时任务移出事件循环或限制命令规模。

**常见追问**

- Linux 上常见实现是什么？`epoll`，但 Redis 还会按平台使用其他实现。
- I/O 多路复用是轮询所有连接吗？应用获取的是就绪事件；具体内核实现和调用语义因机制而异，不能简单理解为应用逐个忙轮询。
- 它与多线程是什么关系？两者是不同维度；多路复用管理多连接，多线程可以分担工作，但不自动改变命令执行模型。

**易错点**

- 把多路复用解释为“多个线程同时做 I/O”。
- 说 `epoll` 会替应用完成业务数据处理。
- 认为有了多路复用，CPU 密集或阻塞命令就不会影响其他请求。

## 311. Redis 常见的五种基本数据类型是什么？

**面试回答**

面试中常说的五种经典基本类型是 String、Hash、List、Set 和 Sorted Set（常简称 ZSet）：分别对应字节序列、字段映射、按插入次序排列的序列、无序唯一集合、按 score 排序的唯一成员集合。选型应按访问模式、顺序、唯一性、排序和复杂度决定，而不是只看业务对象名称。

**原理与理解**

- String：二进制安全的字节序列，可用于值、计数和位操作。
- Hash：一个 Key 下的 field-value 记录，可按字段访问。
- List：元素按插入顺序排列，可从两端操作。
- Set：成员无序且唯一，支持成员判断和集合运算。
- Sorted Set：成员唯一，每个成员关联 score，并按 score 排序。

这“五种”是经典面试分类，不是 Redis 的全部类型。Redis 还提供 Streams、位图/位域、HyperLogLog、地理空间等能力，现代产品版本还可能包含 JSON、搜索、向量等扩展。

**成立条件与边界**

- 逻辑类型与底层编码不是一回事；内部编码会随版本、元素大小和数量变化，不应死记为固定实现。
- 同一种业务可能有多种建模方式，例如对象既能整体序列化为 String，也能拆成 Hash。
- 命令复杂度与返回数据量同样重要；类型匹配不代表可以无界增长。
- Sorted Set 的“有序”来自 score，List 的“有序”来自元素位置，语义不同。

**实际场景**

**项目核验项：** 应从 `RedisTemplate` 的序列化器、实际命令或 Spring Cache 的 Value 格式判断项目使用了哪些类型；现有材料只能确认使用 Redis，不能把验证码、Hash 对象、Set 去重或 ZSet 排行榜写成既有实现。

**常见追问**

- Redis 只有五种类型吗？不是，这是经典核心类型的面试归纳。
- 存对象选 String 还是 Hash？整体读写可用序列化 String，需要字段级操作可考虑 Hash，并比较 TTL、内存和演进成本。
- List 和 Sorted Set 的顺序有什么不同？List 由位置/插入操作决定，Sorted Set 由 score 决定。

**易错点**

- 把 ZSet 当成官方命令中的完整类型名；更准确的名称是 Sorted Set，ZSet 是常用简称。
- 把底层编码写死为链表、跳表或压缩列表，忽略版本与阈值变化。
- 看到“对象、队列、排行”就机械套类型，不分析访问和可靠性需求。

## 312. String 适合哪些场景？

**面试回答**

String 适合整体读写的文本、二进制或序列化对象，也适合用 `INCR/DECR` 做计数、用位操作表达紧凑状态，以及存放短期令牌、标志或带唯一随机值的租约记录。Redis String 是二进制安全的字节序列；JSON 只是常见序列化格式，不代表普通 String 能按 JSON 字段直接查询更新。

**原理与理解**

String 接口简单，`GET/SET` 适合把一个值作为整体管理；数值字符串可使用原子计数命令，避免客户端读改写竞争；位图场景可在一个 String 的位偏移上记录布尔状态。对象序列化后写入 String，可以保持应用对象结构，但字段级更新通常要先取出、反序列化、修改并整体写回。

**成立条件与边界**

- “能存对象”实际是客户端把对象序列化成字节；序列化格式、类型信息与兼容性必须明确。
- `INCR` 的原子性只覆盖该命令本身；计数与其他业务写入的一致性需额外设计。
- `SET key value NX EX/PX` 可作为锁记录的基础，但完整分布式锁还要唯一持有者、条件释放、续期和故障分析。
- 保存 JWT 或验证码只是通用方案；是否需要服务端保存 JWT 取决于撤销和会话模型，不能默认项目如此实现。
- 大对象会增加网络、复制、持久化和删除成本。

**实际场景**

**项目核验项：** 若项目通过 Spring Cache 将查询结果整体序列化到 Redis，底层常表现为 String 类 Value；应根据序列化配置、实际 `TYPE` 命令和缓存内容确认，不能仅凭使用 `RedisTemplate` 推断项目保存了验证码、JWT 或分布式锁。

**常见追问**

- String 能存数字吗？能，数字以字符串形式存储并可由数值命令解析操作。
- String 存对象和 Hash 有何差别？String 偏整体读写，Hash 支持字段级访问；还要比较序列化、TTL、内存和演进成本。
- 为什么锁 Value 要随机且唯一？释放时必须验证所有者，避免误删已经由其他客户端重新获得的锁。

**易错点**

- 说 Redis 能直接存 Java 对象，忽略客户端序列化。
- 把普通 String 与 RedisJSON 的字段操作能力混为一谈。
- 把 `SET NX EX` 一条命令等同于在所有故障模型下可靠的分布式锁。

## 313. Hash 适合哪些场景？

**面试回答**

Hash 适合把一组相关 field-value 放在同一个 Key 下，例如需要按字段读取或更新的记录、配置项或计数分组。它避免每次为了修改一个字段而整体反序列化对象，但并不等同于支持嵌套对象和关系查询；是否优于 String 要看实际读写粒度、TTL、内存和模式演进需求。

**原理与理解**

Hash 的字段和值都是字节序列，`HGET/HSET/HMGET/HINCRBY` 等命令提供字段级访问与原子更新。若请求经常只取少量字段，Hash 可以减少应用侧整体编解码；若总是整对象读取，序列化 String 可能更简单。Hash 的内部编码可能因版本、字段数量和大小变化，业务不应依赖具体编码。

**成立条件与边界**

- Redis 7.4 之前，过期时间通常只能设置在整个 Hash Key 上；Redis 7.4+ 才提供 Hash 字段级过期命令，使用前要确认服务端和客户端支持。
- `HGETALL` 会随字段数量和返回体增长；大 Hash 可能形成大 Key 并阻塞网络和执行路径。
- Hash 不提供多层嵌套对象语义，复杂对象仍需要展平或序列化字段。
- 多个字段分别更新可能暴露中间状态；需要整体原子变更时应使用合适的多字段命令、事务或脚本。

**实际场景**

**通用工程：** 购物车可建模为 `cart:{userId}`，field 为商品标识、value 为数量，以字段命令独立增删；但如果每个商品需要不同 TTL、复杂属性或可靠审计，应重新评估拆 Key、字段过期版本要求或数据库建模。

**常见追问**

- Hash 与 String 存对象怎么选？按字段访问/更新频繁时偏向 Hash，整对象读写和版本化简单时偏向 String，并用真实数据压测内存与网络。
- Hash 的 field 能单独设置 TTL 吗？Redis 7.4+ 提供字段级过期；旧版本通常只有 Key 级 TTL。
- Hash 适合无限放字段吗？不适合，无界增长会形成大 Key，遍历和迁移成本升高。

**易错点**

- 不说明版本就断言 Hash 字段永远不能或都能单独过期。
- 认为 `HGETALL` 永远是轻量操作。
- 把 Hash 当作能嵌套、索引和查询的文档数据库。

## 314. List 适合哪些场景？

**面试回答**

List 是按元素位置保持顺序的字符串序列，擅长从两端插入、弹出和阻塞等待，适合栈、队列、双端队列以及有界的最近 N 条记录。若消息需要消费组、确认、重放、待处理列表和更完整的可靠性语义，应优先评估 Redis Streams 或专用消息中间件。

**原理与理解**

通过 `LPUSH/RPUSH` 和 `LPOP/RPOP` 可以组合 FIFO 或 LIFO；阻塞式弹出可减少空轮询；`LTRIM` 可把列表控制在最近 N 条。List 的顺序由插入和位置操作决定，允许重复元素。Redis 会根据版本和数据形态选择内部编码，回答时不应固定说“底层就是链表”。

**成立条件与边界**

- 两端操作通常高效，但按索引访问、在中部插入/删除以及大范围返回可能随距离或元素数量增长。
- 简单弹出后消费者崩溃可能造成消息丢失；要可靠消费需设计转移、确认、重试、幂等和死信。
- List 没有 Streams 的消费者组、消息 ID 和待确认消息等完整语义。
- 最近列表必须限制长度；无界增长会造成大 Key、内存和迁移问题。

**实际场景**

**通用工程：** 对允许偶发丢失、只需单消费者或简单 FIFO 的内部轻量任务，可用阻塞式 List 并限制长度；订单、支付等必须可追踪和重放的消息，不应只凭 `LPUSH/BRPOP` 就宣称可靠。

**常见追问**

- List 怎么做 FIFO？例如一端 `LPUSH`、另一端 `RPOP`，或采用方向一致的其他组合。
- List 和 Streams 怎么选？只需简单两端队列可用 List；需要消费组、确认、重放和消息追踪时考虑 Streams。
- List 适合随机访问吗？不擅长，靠近两端的索引较好，中间位置与大范围读取成本更高。

**易错点**

- 把 List 的底层实现永远写成链表或压缩列表。
- 说 List 天然就是可靠消息队列。
- 忽略阻塞命令的连接占用、消费幂等和列表长度上限。

## 315. Set 适合哪些场景？

**面试回答**

Set 是无序且成员唯一的字符串集合，适合去重、成员存在性判断、随机抽样，以及交集、并集、差集等集合关系计算，例如标签成员、已处理 ID 或共同关注候选。它不提供稳定顺序，且大集合运算可能成为慢命令。

**原理与理解**

`SADD` 利用成员唯一性完成去重，`SISMEMBER` 判断是否存在，`SINTER/SUNION/SDIFF` 计算集合关系，`SPOP/SRANDMEMBER` 支持随机取值。成员的返回顺序不是业务契约；需要按时间或分值排序时，应考虑 Sorted Set 或另建索引。

**成立条件与边界**

- 唯一性只在同一个 Set Key 内成立，不能直接替代数据库全局唯一约束。
- `SMEMBERS` 和大规模交并差会处理或返回大量元素，可能阻塞实例；应限制集合规模或使用渐进扫描、离线计算。
- Redis Cluster 中多 Key 集合运算要求相关 Key 可在同一槽位，或由应用改写计算方式。
- Set 无稳定顺序，不能依赖某次遍历结果作为分页顺序。

**实际场景**

**通用工程：** 可用 Set 记录一次任务已处理的业务 ID，`SADD` 返回值帮助判断是否首次加入；但涉及最终业务唯一性时，数据库唯一约束或幂等表仍应作为权威保障，Set 只能承担快速前置判断。

**常见追问**

- 共同好友怎么求？数据量有界且 Key 同槽时可用 `SINTER`；大集合需评估复杂度、网络和分片边界。
- Set 与 List 的区别？Set 无序且唯一，List 有位置顺序且可重复。
- 如何遍历大 Set？使用 `SSCAN` 渐进遍历并容忍扫描期间的重复或变化，避免一次返回全部成员。

**易错点**

- 把 Set 的无序误解成每次都“真正随机”。
- 在生产高峰直接对大集合执行全量交并差或 `SMEMBERS`。
- 把缓存层去重当成永久、强一致的业务唯一性保证。

## 316. ZSet 适合哪些场景？

**面试回答**

Sorted Set（常简称 ZSet）保存唯一成员，并为每个成员关联一个浮点 score，按 score 排序，score 相同再按成员字典序确定顺序。它适合排行榜、优先级、按时间索引、滑动窗口计数等需要“成员唯一 + 数值排序/范围查询”的场景。

**原理与理解**

`ZADD` 写入或更新 score，`ZRANGE/ZRANK` 按顺序和排名查询，`ZRANGEBYSCORE` 类能力按分值范围读取，`ZINCRBY` 原子调整分值。同一个成员在一个 Sorted Set 中只有一个 score，再次写入通常更新该成员的分值，而不是新增重复成员。

**成立条件与边界**

- score 使用双精度浮点数；特别大的整数、精细小数与比较边界要考虑精度，必要时设计可精确表示的单位。
- score 相同按成员字典序排序，不等于按写入先后顺序。
- 大范围查询、删除或高频热点更新仍有 CPU 和网络成本，排行榜应限制返回区间。
- 用执行时间作 score 只能形成“到期任务索引”；还需轮询/唤醒、原子领取、确认、重试、幂等和多消费者竞争处理，不能直接等同于完整延迟队列。

**实际场景**

**通用工程：** 活跃度排行榜可把用户 ID 作为 member、积分作为 score，并只读取 Top N；若同分时业务要求按达成时间排序，需要把时间纳入可比较编码或另存字段，而不能默认 Sorted Set 保留先到顺序。

**常见追问**

- Sorted Set 与 List 都有序，有何区别？前者按 score 排序且成员唯一，后者按位置顺序且允许重复。
- score 相同如何排序？按 member 的字典序排序。
- ZSet 能直接做延迟队列吗？它能做到期索引，但可靠消费协议需要应用额外实现，复杂场景应评估专业消息系统。

**易错点**

- 说同分成员按插入顺序排列。
- 忽略 member 唯一，再次 `ZADD` 可能更新 score。
- 把 ZSet 存时间戳称为已经完成“可靠延迟队列”。

## 317. 什么是 TTL？

**面试回答**

TTL 是 Key 的剩余生存时间。可以用 `EXPIRE` 或写入命令的过期选项为 Key 设置超时，`TTL` 返回秒级剩余时间，`PTTL` 返回毫秒级。到期后 Key 在语义上应视为不存在，但 Redis 通过访问时被动过期和周期性主动抽样共同清理，不保证恰好在到期瞬间完成物理删除。

**原理与理解**

过期时间是附着在 Key 上的元数据。客户端访问已超时 Key 时，Redis 会被动删除；对从未再访问的过期 Key，Redis 会周期性抽样并主动清理。`TTL` 返回 `-1` 表示 Key 存在但没有过期时间，返回 `-2` 表示 Key 不存在。覆盖整个 Key 的命令（如普通 `SET`）通常会清除原 TTL，而 `INCR`、`HSET`、`LPUSH` 这类原地修改通常保留 Key 的 TTL；具体命令仍应查文档。

**成立条件与边界**

- TTL 的单位和 API 映射必须核对，避免秒、毫秒混用。
- 到期后“不可读”与内存“已立即回收”不是同一时刻。
- 对 Key 重新赋值可能丢失原 TTL；需要保留时应使用明确支持保留过期时间的选项并核验版本。
- Key 级 TTL 与 Redis 7.4+ 的 Hash field 级过期不是同一能力。
- 过期时间依赖时钟，部署环境应保持时间同步。

**实际场景**

**项目核验项：** 应从 Spring Cache 配置、`RedisCacheManager`、写入代码和运行时 `TTL/PTTL` 结果确认每类缓存的期限；现有材料没有给出“30 分钟缓存”或“5 分钟验证码”等具体数值，不能作为项目事实。

**常见追问**

- `TTL` 的 `-1` 和 `-2` 分别是什么？`-1` 是存在但无过期时间，`-2` 是 Key 不存在。
- TTL 到期会立即删除吗？逻辑上过期，物理清理由被动访问和主动抽样完成。
- 更新 Value 后 TTL 一定还在吗？不一定，覆盖 Key 的命令通常会清除 TTL，原地修改通常保留，应按具体命令核验。

**易错点**

- 说 TTL 归零时必然立即完成物理删除。
- 混淆 `TTL`、`PTTL` 及客户端 `Duration` 的单位。
- 更新缓存时只写 Value，意外把原过期时间变成永久。

## 318. 为什么缓存通常要设置 TTL？

**面试回答**

缓存通常设置 TTL，是为了给数据新鲜度和生命周期设上限：即使主动失效遗漏，旧值也不会无限期保留；冷数据也能逐步退出缓存。TTL 是一致性与容量治理的兜底，不是强一致保证。期限应根据业务可容忍陈旧时间、更新频率、回源成本和流量分布确定。

**原理与理解**

Cache Aside 中通常在数据库变更后使缓存失效，但进程崩溃、网络异常或遗漏路径仍可能留下旧值。TTL 限制这种旧值可能存在的最长时间，也促使长期不访问的数据释放空间。不过 Redis 的 `maxmemory` 淘汰与 TTL 是两个机制：有 TTL 的热 Key 也可能因内存策略提前被淘汰，没有 TTL 的 Key 也可能受所选淘汰策略影响。

**成立条件与边界**

- TTL 不能解决过期前的不一致窗口，也不能替代更新/失效、重试、消息补偿和监控。
- TTL 太短会降低命中率、放大回源和重建；太长会扩大陈旧窗口并占用更多内存。
- 大量 Key 同时到期可能造成集中回源，可在允许范围内加入随机抖动、分批预热或互斥重建。
- 并非所有缓存都必须有固定 TTL：少量稳定配置可采用事件驱动失效或版本切换，但必须有容量和变更治理。
- 安全令牌、验证码等业务有效期是业务规则，不能仅依赖缓存淘汰策略表达。

**实际场景**

**真实项目边界：** 项目可确认使用缓存，但每个缓存区的 TTL、是否加抖动和失效机制需要以配置与代码为准。面试可说明“会按允许陈旧时间和回源压力设计”，不要虚构项目中所有缓存都使用同一个期限。

**常见追问**

- TTL 设多长？没有通用值，要结合新鲜度目标、命中率、重建成本和峰值流量压测。
- 设置 TTL 就不会内存不足吗？不会，还要设置容量上限、淘汰策略并监控 Key 数量、Value 大小和命中率。
- 为什么给 TTL 加随机值？用于打散同批 Key 的到期时间，降低同一时刻集中回源风险。

**易错点**

- 说“缓存必须设置 TTL”，忽略事件失效、版本化缓存等受控方案。
- 把 TTL 当成缓存一致性的唯一或充分保障。
- 只考虑过期删除，不考虑集中失效、提前淘汰和重建压力。

## 319. Redis 中 Key 应该如何设计？

**面试回答**

Key 设计要稳定、唯一、可读且长度有界，通常采用 `服务:环境:租户:实体:标识:版本` 一类命名规范，并明确每段含义、TTL、Value 类型和序列化版本。例如 `order:prod:tenant42:detail:123:v1`。冒号只是常用约定，不是 Redis 语法要求；Key 中也不应放密码、Token、手机号等敏感明文。

**原理与理解**

统一命名空间可以避免不同服务、环境和租户碰撞，实体 ID 保证定位，版本段帮助灰度升级 Value 结构。Key 也是内存和网络开销的一部分，过长会放大海量 Key 的成本，过短又会失去可维护性。Redis Cluster 通过完整 Key 计算槽位；`{...}` Hash Tag 可以让相关 Key 同槽以执行有限的多 Key 操作，但过度集中会形成热点。

**成立条件与边界**

- 冒号、字段顺序和大小写是团队约定，应形成文档和构造器，Redis 不会自动理解业务层级。
- 不能把 `KEYS prefix:*` 当作生产批量管理方案，它会遍历当前 Key 空间并可能阻塞；`SCAN` 是渐进遍历，也不是事务快照，扫描期间可能重复或反映变更。
- Redis Cluster 下扫描和批处理要考虑各分片；多 Key 原子命令通常还要求 Key 位于同槽。
- 仅靠前缀删除可能误删其他版本或租户数据；大规模失效可采用版本号切换、索引集合或受控后台任务。
- Key 应避免敏感明文和无界用户输入，并对租户、权限和注入式拼接做校验。

**实际场景**

**项目核验项：** 可先从 Spring Cache 的 `cacheNames`、Key 表达式和 `RedisTemplate` 常量整理“缓存区—Key 模式—Value 类型—TTL—失效入口”清单；在看到源码前，不把 `dish:info:{id}`、`setmeal:list:*` 等示例写成项目既有 Key。

**常见追问**

- 为什么常用冒号分隔？便于人和工具阅读命名层次，是约定而非强制语法。
- 如何按前缀批量删除？避免在线执行 `KEYS`；按规模选择分片 `SCAN` + 有界批次 `UNLINK`、维护索引，或切换命名空间版本，并评估重复扫描和并发变化。
- Cluster 中 `{}` 有什么用？花括号中的 Hash Tag 参与槽位计算，可让相关 Key 同槽；设计不当会导致数据与流量倾斜。

**易错点**

- 把“前缀可管理”写成可以放心用 `KEYS` 在线批量删除。
- 把 `dish:info:{id}` 中的 `{id}` 示例直接当成项目事实，或误以为花括号只是装饰。
- Key 拼入敏感信息、超长 JSON、随机不可追踪片段，或缺少环境/租户隔离。
