# 事务

## 277. MySQL 有哪些事务隔离级别？

**面试回答**

InnoDB 支持 SQL 标准描述的四种隔离级别：`READ UNCOMMITTED`、`READ COMMITTED`、`REPEATABLE READ` 和 `SERIALIZABLE`。隔离级别用于权衡并发性能、结果可重复性和一致性要求，InnoDB 默认是 `REPEATABLE READ`。

**原理与理解**

`READ UNCOMMITTED` 允许脏读；`READ COMMITTED` 的每次一致性读使用新快照；`REPEATABLE READ` 的普通一致性读复用第一次一致性读建立的快照；`SERIALIZABLE` 规则更严格，在关闭自动提交时会把普通 `SELECT` 隐式转换为共享锁定读。

**成立条件与边界**

“级别越高，性能一定越差”只是常见趋势，不是可以脱离工作负载的定律。隔离级别还会影响锁范围和死锁概率，实际行为要结合存储引擎、SQL 类型、索引和是否为锁定读判断。

**实际场景（通用工程）**

报表业务可能更关注读取较新的已提交数据，而订单状态迁移更关注并发正确性；选择级别前应先明确允许哪些并发现象，而不是机械修改全局默认值。

**常见追问**

- InnoDB 默认隔离级别是什么？（`REPEATABLE READ`）
- 隔离级别只影响普通查询吗？（不是，也会影响锁定读和 DML 的加锁行为）

**易错点**

不要只背四个名称和一张现象表；同一隔离级别下，普通快照读、锁定读和写操作的行为并不相同。

## 278. 什么是脏读？

**面试回答**

脏读指一个事务读到了另一个事务尚未提交的修改；如果后者回滚，前者曾经读到的值就从未成为已提交状态。

**原理与理解**

例如事务 A 修改订单金额但未提交，事务 B 此时读到新金额，随后 A 回滚，这就是脏读。InnoDB 的 `READ UNCOMMITTED` 可能发生脏读；`READ COMMITTED` 及以上级别的普通读取不会读取其他事务未提交的数据。

**成立条件与边界**

脏读描述数据库事务可见性，不等同于缓存脏数据、读写分离延迟或应用对象未刷新。数据库外部的数据副本是否新鲜，需要单独分析。

**实际场景（通用工程）**

若风控计算读取了另一事务尚未提交的账户余额，而该修改随后回滚，风控结论就建立在无效数据上。

**常见追问**

- 哪个级别可能发生脏读？（`READ UNCOMMITTED`）
- `READ COMMITTED` 能否避免脏读？（能，但仍可能出现不可重复读）

**易错点**

关键是“读到其他事务未提交的数据”，不是泛指读到了错误、过期或不一致的数据。

## 279. 什么是不可重复读？

**面试回答**

不可重复读指同一事务对同一行进行多次读取时，因为其他事务在两次读取之间提交了更新或删除，导致读取结果不一致。

**原理与理解**

在 `READ COMMITTED` 下，每次普通一致性读都会建立新快照，因此第二次查询可以看到期间已经提交的修改；在 `REPEATABLE READ` 下，同一事务的普通一致性读通常复用第一次一致性读建立的快照。

**成立条件与边界**

可重复读保证的是快照语义，不代表当前事务看不到自己的写入，也不代表锁定读和 DML 永远读取旧快照。InnoDB 的锁定读和写操作需要基于较新的状态加锁处理。

**实际场景（通用工程）**

事务 A 两次读取同一个订单状态，事务 B 在中间把状态从待支付改为已支付并提交；若 A 两次普通读取结果不同，就是不可重复读。

**常见追问**

- 它和脏读有什么区别？（读到的都是已提交版本，但同一事务两次结果不同）
- RR 的快照何时建立？（通常在第一次普通一致性读时）

**易错点**

不要说 RR 的 Read View 必然在 `BEGIN` 时创建；除非显式使用一致性快照，通常要等第一次一致性读。

## 280. 什么是幻读？

**面试回答**

幻读指同一事务按同一查询条件再次读取时，因为其他事务提交了会进入或离开该条件范围的行，结果集合发生变化，仿佛出现了“幻影行”。

**原理与理解**

面试中常用“第一次查 5 行，第二次查 6 行”解释，但本质是谓词范围内的集合变化，不只看行数，也可能由插入、删除或使记录进入查询范围的更新造成。它与“同一已定位行的值变化”侧重点不同。

**成立条件与边界**

在 InnoDB RR 下，普通一致性读复用快照，因此不会看到其他事务后来提交的插入；RR 下的范围锁定读和 DML 通常使用 gap/next-key locks 阻止扫描范围内插入。若混用快照读与当前读，两种可见性状态可能产生看似矛盾的结果，不能笼统回答“RR 绝对没有幻读”或“RR 一定有幻读”。

**实际场景（通用工程）**

事务按“金额大于 100”查询订单集合，另一个事务插入满足条件的订单并提交；该新行是否能在第二次查询中出现，要结合隔离级别和查询是快照读还是锁定读判断。

**常见追问**

- 幻读和不可重复读怎么区分？（前者关注查询谓词对应的记录集合，后者侧重同一行重复读取）
- InnoDB RR 如何处理？（快照读使用一致快照；范围锁定读使用 gap/next-key locks）

**易错点**

“幻读就是行数变化”是便于记忆的简化，不是严格边界；更准确的关键词是“同一查询条件对应的记录集合变化”。

## 281. READ COMMITTED 和 REPEATABLE READ 有什么区别？

**面试回答**

在 InnoDB 中，RC 的每次普通一致性读都读取一个新快照，能看到查询前已经提交的数据；RR 的同一事务普通一致性读复用第一次一致性读建立的快照。两者的 DML 和锁定读加锁范围也不同。

**原理与理解**

因此 RC 可能发生不可重复读，RR 的普通一致性读可保持重复读取结果。加锁方面，RC 通常只锁索引记录并允许在间隙插入，gap lock 主要保留给外键和重复键检查；RR 的范围锁定读通常会使用 gap/next-key locks。

**成立条件与边界**

快照差异只针对一致性非锁定读。`SELECT ... FOR UPDATE`、`SELECT ... FOR SHARE`、`UPDATE`、`DELETE` 需要读取可用于加锁或修改的较新状态，不能套用“RR 永远只读旧快照”。

**实际场景（通用工程）**

长事务内需要多次生成同一口径报表时，RR 快照更容易保持口径；需要每次查询都看到最新已提交结果时，可评估 RC，但仍要处理并发写竞争。

**常见追问**

- RC 和 RR 的 Read View 差异？（RC 每次一致性读新建，RR 复用第一次一致性读的快照）
- RC 一定比 RR 性能好吗？（不一定，取决于锁冲突、SQL 和负载）

**易错点**

不要把 RC/RR 的区别只说成“有没有不可重复读”，还应说明快照时机和锁范围差异。

## 282. InnoDB 默认事务隔离级别是什么？

**面试回答**

InnoDB 的默认事务隔离级别是 `REPEATABLE READ`，可以按全局、会话或下一事务的范围进行配置。

**原理与理解**

RR 下，同一事务中的普通一致性读使用第一次一致性读建立的快照；锁定读和写操作则按索引扫描范围加锁，范围条件通常会涉及 gap/next-key locks。

**成立条件与边界**

“默认是 RR”不等于项目运行时一定是 RR。连接池初始化、数据库参数、会话设置和云数据库配置都可能修改实际隔离级别，应通过配置或查询确认。

**实际场景（项目核验项）**

面试前应在项目数据库中查询实际隔离级别，并检查连接池与框架配置；可以回答 InnoDB 默认值，但不能未经检查就声称项目实际配置必然是 RR。

**常见追问**

- 默认级别能修改吗？（能，可以设置全局、会话或单个事务）
- 如何确认项目实际级别？（查询数据库变量并检查连接池/框架配置）

**易错点**

数据库产品默认值、存储引擎能力和项目实际配置是三个层次，不要混为一谈。

## 283. 什么是 MVCC？

**面试回答**

MVCC 是多版本并发控制。InnoDB 保留被修改记录的历史信息，让一致性非锁定读根据快照选择可见版本，从而减少普通读与写之间的锁冲突。

**原理与理解**

InnoDB 聚簇索引记录包含最近修改事务标识和指向 undo 记录的回滚指针。当前版本不满足快照可见性时，可以沿 undo 信息重建更早版本。Read View/快照规则决定哪个版本可见。

**成立条件与边界**

MVCC 主要服务于 RC 和 RR 下的普通一致性读。锁定读、`UPDATE`、`DELETE` 和写写冲突仍然需要锁；DDL、元数据锁或资源压力也可能使读取等待。因此“MVCC 下所有读都不加锁、永不阻塞”是错误的。

**实际场景（通用工程）**

后台正在修改商品价格时，前台普通查询可以读取符合其快照的已提交版本，而不必为了读取同一行等待写事务结束。

**常见追问**

- MVCC 的关键组成是什么？（记录版本信息、undo 历史版本和可见性快照）
- `SELECT ... FOR UPDATE` 是否走普通快照读？（不是，它是锁定读）

**易错点**

MVCC 不是一种锁，也不是完全替代锁；它优化的是符合条件的一致性读取路径。

## 284. MVCC 主要解决什么问题？

**面试回答**

MVCC 主要减少一致性读与写操作之间的相互阻塞，让查询读取合适的已提交历史版本，同时实现 RC 或 RR 所需的可见性语义。

**原理与理解**

如果普通查询都必须对记录加共享锁，写事务可能被大量读取阻塞。MVCC 让查询依据快照读取当前或历史版本，写事务继续生成新版本，从而提高读写并发。

**成立条件与边界**

MVCC 不能解决丢失更新、超卖、唯一性竞争或死锁等全部并发问题。需要基于最新状态做决策时，应使用条件更新、锁定读、乐观锁或其他原子并发控制。

**实际场景（通用工程）**

订单列表查询可以使用一致性读；支付回调把订单从未支付更新为已支付时，则应使用带旧状态条件的原子更新，不能只依赖 MVCC。

**常见追问**

- MVCC 能避免写写冲突吗？（不能，写操作仍需锁和冲突处理）
- 为什么它有利于读多写少场景？（大量普通读减少了锁等待）

**易错点**

“读写不冲突”只是在合适的一致性读语境下的概括，不能扩展成所有 SQL 都互不影响。

## 285. MVCC 为什么能提高数据库并发性能？

**面试回答**

因为普通一致性读不必等待最新写入完成，而是可以根据快照读取一个可见的已提交版本，从而减少读写锁竞争，让更多事务并发推进。

**原理与理解**

写事务修改聚簇索引记录并留下可重建旧版本的 undo 信息；读事务发现当前版本不可见时沿版本信息找到可见版本。这样读取与写入不必都争用同一份最新记录的共享/排他锁。

**成立条件与边界**

多版本也有成本：长事务会让旧快照长期存活，阻碍 purge 清理 update undo，增加 undo 表空间和版本链回溯开销。高并发系统应避免无必要的长事务，包括长时间不提交的只读事务。

**实际场景（通用工程）**

高频商品查询与少量价格更新并发时，普通查询可以读取快照版本；但如果查询要求锁住商品用于随后扣减，则会转为锁定读并产生等待。

**常见追问**

- MVCC 是否没有额外成本？（不是，会维护 undo 和版本信息）
- 长事务为什么危险？（旧快照阻碍 purge，版本链和空间持续增长）

**易错点**

不要回答成“复制整行数据到很多张表”；InnoDB 通过记录中的事务信息、回滚指针和 undo 记录重建历史版本。

## 286. 什么是 Read View？

**面试回答**

Read View 可以理解为一致性读使用的事务可见性快照。它记录创建快照时的事务边界信息，用来判断当前记录版本是否可见；不可见时再沿 undo 历史寻找更早版本。

**原理与理解**

判断核心是区分：创建快照前已提交的版本、创建时仍活跃的事务版本、快照之后启动的事务版本，以及当前事务自己的修改。面试可以说明活跃事务集合和事务 ID 边界，但不必把内部字段名背成跨版本不变的 API。

**成立条件与边界**

RC 下每次一致性读使用新快照；RR 下同一事务复用第一次一致性读建立的快照。当前事务自己的先前修改对自己可见。锁定读和 DML 不按普通一致性读的旧快照执行。

**实际场景（通用工程）**

RR 事务第一次普通查询后，另一个事务提交了新订单；前者再次执行普通查询时仍按原快照判断可见性，但之后执行锁定读时可能接触较新的数据库状态。

**常见追问**

- Read View 决定什么？（某个记录版本对一致性读是否可见）
- RR 在 `BEGIN` 时立即创建 Read View 吗？（通常不是，第一次一致性读才创建）

**易错点**

Read View 不是数据的完整物理副本，而是版本可见性的判断依据。

## 287. 什么是 undo log？

**面试回答**

undo log 是 InnoDB 在回滚段中保存的撤销信息，用于回滚事务修改，并为一致性读重建记录的早期版本。

**原理与理解**

记录中的回滚指针可以指向相关 undo 记录。需要撤销时，InnoDB 使用这些信息执行相反操作；需要读取旧版本时，update undo 可用于重建修改前的记录内容。

**成立条件与边界**

insert undo 只用于插入事务自身的回滚，提交后即可丢弃；update undo 还可能被其他事务的一致性快照需要，只有不再有快照依赖时才能由 purge 清理。删除记录也通常先标记，随后再 purge。

**实际场景（真实项目）**

订单主表已经插入、明细批量写入失败时，本地事务需要回滚主表修改；底层撤销能力由 InnoDB 的事务与 undo 机制支持。

**常见追问**

- undo log 的两个主要用途？（事务回滚、构造一致性读旧版本）
- 提交后 undo 一定立即删除吗？（不一定，update undo 可能仍被旧快照需要）

**易错点**

不要笼统说“undo 保存整行修改前副本并在提交后立刻删除”，不同操作的 undo 内容和生命周期并不相同。

## 288. undo log 有什么作用？

**面试回答**

第一，为事务回滚提供撤销信息；第二，为 MVCC 的一致性读提供重建历史版本所需的信息；第三，配合 purge 在旧版本不再被需要时完成清理。

**原理与理解**

回滚和一致性读都依赖“如何从当前记录得到更早状态”这一能力，但用途不同：回滚要撤销当前事务的修改，一致性读只是为查询构造可见版本，不会把数据库真的改回旧状态。

**成立条件与边界**

undo log 不能替代 redo log。undo 处理逻辑撤销和历史版本，redo 用于崩溃恢复中重放尚未反映到数据文件的修改；恢复过程通常需要两类信息协同。

**实际场景（通用工程）**

事务失败时数据库用 undo 撤销已执行修改；另一个 RR 事务读取同一记录时，则可能利用 update undo 构造其快照可见的旧版本。

**常见追问**

- 用 undo 构造旧版本会修改真实数据吗？（不会，只服务于读取可见版本）
- 为什么长事务会影响 undo 清理？（旧快照可能仍需历史版本）

**易错点**

undo log 记录的是撤销所需信息，不宜简单等同于业务 SQL 的完整反向文本。

## 289. 什么是 redo log？

**面试回答**

redo log 是 InnoDB 的磁盘日志结构，记录对表数据进行修改所产生的底层变更请求。异常关机后，InnoDB 在恢复阶段重放尚未完整反映到数据文件的修改。

**原理与理解**

数据页先在内存缓冲池修改，redo 信息按 LSN 推进并追加到日志，checkpoint 推进后较旧的 redo 可被截断或复用。恢复时利用 redo 把数据文件推进到一致状态，再结合事务状态处理未提交影响。

**成立条件与边界**

redo 不是业务 SQL 历史，也不是备份和复制日志。事务持久性还取决于 `innodb_flush_log_at_trx_commit`、操作系统与存储设备是否真正完成刷盘等条件，不能脱离配置承诺“绝不丢失”。

**实际场景（通用工程）**

订单事务提交后数据页尚未全部刷新到表空间时数据库进程崩溃，重启恢复可利用已持久化的 redo 把相关修改重新应用到数据文件。

**常见追问**

- redo log 的核心用途？（崩溃恢复和持久性基础）
- redo 能否做按时间点业务恢复？（通常使用备份加 binlog，不靠 redo 代替）

**易错点**

不要把 redo 简化成“记录修改后的完整数据”或“保存每条 SQL”；它记录的是 InnoDB 恢复所需的底层变更信息。

## 290. redo log 有什么作用？

**面试回答**

redo log 使数据页可以延后刷新，同时保留崩溃后重放修改的能力，从而兼顾写入性能和事务持久性。

**原理与理解**

这体现了 WAL 思想：相关 redo 必须在对应脏数据页写回持久存储之前先写入日志。提交阶段是否把 redo log buffer 写入并刷到磁盘，受 `innodb_flush_log_at_trx_commit` 等配置控制。

**成立条件与边界**

默认高持久性配置下，每次提交会写出并刷盘 redo；修改该参数可减少同步 I/O，但会改变崩溃时的数据丢失窗口。即使设置为 1，硬件或操作系统错误报告刷盘完成仍可能破坏绝对保证。

**实际场景（通用工程）**

批量写入先修改缓冲池页面，不必在每次提交时随机刷新全部数据页；只要满足日志先行和提交持久化要求，checkpoint 可在之后推进数据页落盘。

**常见追问**

- WAL 的“先”指什么？（脏数据页落盘前，相关 redo 必须先持久化）
- redo 越大越好吗？（不一定，会影响 checkpoint、恢复时间和资源占用）

**易错点**

“顺序写一定比随机写快”只能解释常见性能优势，不能取代对刷盘策略、组提交和存储设备行为的分析。

## 291. 什么是 binlog？

**面试回答**

binlog 是 MySQL Server 的二进制事件日志，记录数据库变更事件，主要用于复制和基于备份的时间点恢复。普通 `SELECT`、`SHOW` 等不修改数据的语句不会写入 binlog。

**原理与理解**

binlog 支持 `STATEMENT`、`ROW` 和 `MIXED` 格式：分别记录语句、行变更事件，或按规则混合使用。MySQL 8.4 默认使用 ROW，并且修改 `binlog_format` 的能力已在 MySQL 8.0 中标记为弃用，应注意版本差异。

**成立条件与边界**

binlog 是否启用、刷盘策略和保留时间取决于服务配置。它不是通用查询审计日志，也不单独构成完整备份；时间点恢复通常需要先恢复全量备份，再重放之后的 binlog 事件。

**实际场景（生产能力，非简历项目声明）**

生产系统可把源库 binlog 发送给副本重放，或在误删后利用备份加 binlog 恢复到指定时间点；简历未证明项目搭建过主从复制，不能表述为真实实现。

**常见追问**

- binlog 的两大主要用途？（复制、时间点恢复）
- 三种格式是什么？（`STATEMENT`、`ROW`、`MIXED`）

**易错点**

不要笼统说 binlog “记录所有 SQL”；普通查询不记录，ROW 格式记录的是行变更事件而不是原始业务 SQL。

## 292. redo log 和 binlog 有什么区别？

**面试回答**

redo log 属于 InnoDB，服务于数据文件的崩溃恢复与持久性；binlog 属于 MySQL Server，服务于复制和时间点恢复。两者的记录内容、生命周期和消费者都不同。

**原理与理解**

redo 记录 InnoDB 恢复所需的底层变更，按 LSN 追加并随 checkpoint 截断旧内容；binlog 记录数据库变更事件，按编号文件追加并按保留策略清理。binlog 的内容取决于 STATEMENT/ROW/MIXED 格式，不能一概叫作“SQL 逻辑日志”。

**成立条件与边界**

启用 binlog 的事务提交需要协调 InnoDB 事务状态与 binlog 事件，避免崩溃后两份日志对“是否提交”的判断不一致，这正是内部两阶段提交讨论的背景（见 [[04-MySQL/06-MySQL进阶#605. 什么是两阶段提交？]]）。它不是跨微服务的业务两阶段提交。

**实际场景（通用工程）**

数据库进程异常重启时，InnoDB 使用 redo 做本机恢复；搭建副本或做误删后的时间点恢复时，则消费 binlog。两者不能互相替代。

**常见追问**

- 哪个用于主从复制？（binlog）
- 哪个用于 InnoDB 崩溃恢复？（redo log）
- 详细对比入口？（见 [[04-MySQL/04-事务#291. 什么是 binlog？]]）

**易错点**

不要只背“物理日志 vs 逻辑日志”；ROW binlog、redo 的底层记录方式以及版本实现都更复杂，面试应优先按所属层次、用途和生命周期区分。
