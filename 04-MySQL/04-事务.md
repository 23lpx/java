# 事务

## 277. MySQL 有哪些事务隔离级别？

**面试回答**

四种：读未提交（READ UNCOMMITTED）、读已提交（READ COMMITTED）、可重复读（REPEATABLE READ）、串行化（SERIALIZABLE），隔离级别从低到高，隔离越强并发性能越低。

**理解**

读未提交：能读到别人未提交的数据（脏读）；读已提交：只能读已提交数据，但同一事务多次读可能结果不同（不可重复读）；可重复读：同一事务多次读结果一致，但可能出现幻读；串行化：事务串行执行，完全隔离但性能最差。默认可重复读。

**场景**

项目里一般用 InnoDB 默认的可重复读；理解级别差异能解释「为什么读不到别的事务没提交的数据」等现象。

**常见追问**

- InnoDB 默认哪个级别？（可重复读 REPEATABLE READ）
- 四种级别分别解决/产生什么问题？（见脏读、不可重复读、幻读题）

**易错点**

隔离级别是「并发性能 vs 隔离性」的权衡；四个级别要能对号入座它们解决/引入的并发问题。

## 278. 什么是脏读？

**面试回答**

脏读指一个事务读到了另一个事务「未提交」的数据，如果那个事务回滚了，读到的就是无效的「脏数据」。

**理解**

事务 A 修改数据但还没提交，事务 B 读到了这个未提交的修改，这就是脏读。若 A 回滚，B 读到的数据就「不存在」了。脏读只在「读未提交」级别发生，读已提交及以上级别通过「只读已提交数据」避免了脏读。

**场景**

项目里两个事务操作同一订单，如果允许脏读，可能读到还没提交、即将回滚的库存/金额，导致错误判断。

**常见追问**

- 哪个级别会脏读？（读未提交）
- 怎么避免脏读？（提升到读已提交及以上）

**易错点**

脏读的关键是「读到未提交数据」；别把它和「缓存/数据库不一致」混为一谈（那是另一个问题）。

## 279. 什么是不可重复读？

**面试回答**

不可重复读指同一事务内多次读取同一行数据，结果不一致（中间被别的事务修改并提交了），表现为两次读到的值不同。

**理解**

事务 A 第一次读某行得值 X；事务 B 修改这行并提交；A 再读同一行得到 Y。A 的两次读结果不同，就是不可重复读。它强调的是「同一行数据的值被改了」。读已提交级别会有不可重复读，可重复读级别通过 MVCC 保证同一事务读一致。

**场景**

项目里在一个事务里多次读同一订单金额，若中间被别的提交事务改掉，就出现不可重复读（在可重复读级别下不会）。

**常见追问**

- 不可重复读和脏读区别？（脏读读未提交，不可重复读读的是已提交但两次不一致）
- 哪个级别解决不可重复读？（可重复读）

**易错点**

不可重复读针对「同一行值被改」，是「已提交数据」的两次不一致，和脏读（未提交）要分清。

## 280. 什么是幻读？

**面试回答**

幻读指同一事务内多次查询，结果「行数」不一致——中间被别的事务插入或删除了符合条件的行，导致第二次查询多出或少了「幻影」行。

**理解**

幻读关注的是「结果集的行数变化」（新增/删除），而不是某行的值变化（那是不可重复读）。事务 A 查 `count>100 的订单` 得 5 行；事务 B 插入一条新订单并提交；A 再查得 6 行，多出的就是「幻影」。InnoDB 用 MVCC + 间隙锁（Next-Key Lock）在可重复读级别缓解幻读。

**场景**

项目里统计查询若在事务内多次执行，幻读会导致两次统计数量对不上；InnoDB 可重复读 + 间隙锁能在很大程度上避免。

**常见追问**

- 幻读和不可重复读区别？（幻读是「行数」变化，不可重复读是「某行值」变化）
- InnoDB 怎么处理幻读？（MVCC + 间隙锁/Next-Key Lock）

**易错点**

幻读 = 「多出/少了行」，不可重复读 = 「某行的值变了」，两者针对对象不同，别混。

## 281. READ COMMITTED 和 REPEATABLE READ 有什么区别？

**面试回答**

READ COMMITTED 同一事务内每次读都可能读到已提交的最新数据，会产生不可重复读；REPEATABLE READ 同一事务内多次读结果一致，通过 MVCC 避免不可重复读，是 InnoDB 默认级别。

**理解**

两者的核心差异在「快照怎么建立」：READ COMMITTED 每次读都生成新快照（能看到别的事务已提交的修改）；REPEATABLE READ 在事务第一次读时建立快照，之后一直用这个快照（看不到后续提交的修改）。所以前者有不可重复读，后者没有。幻读方面 RR 也通过间隙锁进一步缓解。

**场景**

项目里默认可重复读：一个事务里多次读同一数据结果一致，即使中途别的提交了修改也看不到。

**常见追问**

- 为什么 RR 能避免不可重复读？（快照在事务开始就固定）
- RC 和 RR 谁并发更好？（RC 快照更「新」，锁也更少，并发通常更好）

**易错点**

区别根源是「快照建立时机」：RC 每次读新快照，RR 事务内固定快照；由此导出不可重复读的有无。

## 282. InnoDB 默认事务隔离级别是什么？

**面试回答**

可重复读（REPEATABLE READ）。

**理解**

InnoDB 默认 REPEATABLE READ，它通过 MVCC 保证同一事务内多次读一致，避免不可重复读，并通过间隙锁（Next-Key Lock）在很大程度上避免幻读。注意 MySQL 的默认级别是 InnoDB 的 RR，与 SQL 标准中 RR 的定义略有差异（标准 RR 仍允许幻读，InnoDB 额外用锁缓解了幻读）。

**场景**

项目里事务默认就是可重复读，所以同一事务里重复读同一数据结果稳定。

**常见追问**

- RR 下还会幻读吗？（InnoDB 用间隙锁大幅缓解，但极端场景下仍可能）
- 默认级别能改吗？（能，通过事务隔离级别参数/命令修改）

**易错点**

InnoDB 默认「可重复读」，且它用锁额外缓解了幻读，这点比 SQL 标准的 RR 更强，别按标准笼统说「RR 一定幻读」。

## 283. 什么是 MVCC？

**面试回答**

MVCC 是多版本并发控制，通过为每行数据保留多个版本，让读操作不用加锁就能读到「一致性快照」，从而在读多写少的场景下提高并发。

**理解**

MVCC 的核心是「读不加锁、读写不冲突」。它靠 undo log（保存旧版本）和 Read View（快照）实现：每个事务看到的是一个「历史快照」而非最新数据，读操作直接读快照，不阻塞写，写操作写新版本也不阻塞读。这样读写并发大幅提升。

**场景**

项目里并发查询订单列表时，读操作靠 MVCC 不加锁，不被写操作阻塞，系统吞吐更高。

**常见追问**

- MVCC 解决什么问题？（读不加锁、读写并发）
- MVCC 靠什么实现？（undo log + Read View）

**易错点**

MVCC 是「读不阻塞写、写不阻塞读」的多版本机制，不是「锁」；要理解它靠 undo log 和快照实现。

## 284. MVCC 主要解决什么问题？

**面试回答**

主要解决「读写冲突」问题：让读操作不加锁也能读，读不阻塞写、写不阻塞读，从而提高并发性能，同时保证读到一致的快照。

**理解**

传统做法读要加锁，写要等读完，并发差。MVCC 让读直接读快照（历史版本），写直接写新版本，两者互不阻塞。它主要服务于「读已提交」和「可重复读」这两个隔离级别下的「一致性读」，是数据库高并发的关键。

**场景**

项目里大量读请求（查菜品、查订单）和写请求（下单）并发时，MVCC 让读不被写阻塞，用户体验和吞吐都更好。

**常见追问**

- MVCC 主要优化什么？（读写并发，读不加锁）
- 它对写有帮助吗？（主要是读的并发，写仍需锁）

**易错点**

MVCC 解决的是「读写互相阻塞」的问题，重点是「读不加锁」；别理解成它能解决所有并发问题。

## 285. MVCC 为什么能提高数据库并发性能？

**面试回答**

因为 MVCC 让读操作不用加锁，读读不冲突、读写也不冲突，读不会被写阻塞，多个事务能同时进行，并发度大幅提高。

**理解**

没有 MVCC 时，为了保证一致性，读可能要加共享锁，写要排他锁，读写互斥，一个写会阻塞所有读。MVCC 通过多版本让读直接访问旧版本快照，完全不加锁，于是写和读可以并行。这对「读多写少」的互联网场景收益巨大。

**场景**

项目里商品/菜品详情页大量读请求，MVCC 让这些读不被后台的写操作（改价格、改库存）阻塞。

**常见追问**

- MVCC 下读还加锁吗？（普通一致性读不加锁）
- 什么场景收益最大？（读多写少）

**易错点**

MVCC 提高并发靠的是「读不加锁 + 读写不互斥」，要能说清它省掉了「读写之间的锁等待」。

## 286. 什么是 Read View？

**面试回答**

Read View 是 MVCC 中用来判断「当前事务能看到哪些版本」的快照，它记录事务开启时活跃事务列表等信息，据此决定某行数据的某个版本是否可见。

**理解**

Read View 里包含：当前活跃（未提交）事务集合、最小/最大事务 id 等。读一行时，用它判断这行的版本是否由已提交的事务产生、是否可见，从而选出「当前事务应该看到」的版本。RC 每次读生成新 Read View，RR 事务内复用同一个。

**场景**

项目里可重复读级别下，事务第一次读建立 Read View，之后一直用它，所以多次读结果一致。

**常见追问**

- Read View 决定什么？（哪些数据版本对当前事务可见）
- RC 和 RR 的 Read View 区别？（RC 每次读新建，RR 事务内复用）

**易错点**

Read View 是「可见性判断的依据」，是 MVCC 实现「一致性读」的核心，别只背名词要懂它的作用。

## 287. 什么是 undo log？

**面试回答**

undo log 是回滚日志，记录数据被修改前的旧版本，用于事务回滚和 MVCC 的多版本读取。

**理解**

每次修改数据前，InnoDB 先把旧值写进 undo log。事务回滚时按 undo log 把数据改回去；MVCC 读快照时，也靠 undo log 里的旧版本链找到「事务开启时的历史版本」。所以 undo log 既管「回滚」也管「读旧版本」。

**场景**

项目里事务回滚（如下单失败撤销已插入的数据）、可重复读（读到旧版本）背后都有 undo log 在支撑。

**常见追问**

- undo log 两个作用？（事务回滚、MVCC 多版本）
- undo log 存什么？（修改前的旧数据）

**易错点**

undo log 不只是「回滚」，还支撑 MVCC 的「读历史版本」，两个作用都要记住。

## 288. undo log 有什么作用？

**面试回答**

两个作用：①事务回滚——把已修改的数据恢复到修改前；②MVCC——保存数据旧版本，供一致性读（快照读）使用。

**理解**

回滚靠 undo log 记录「改之前长什么样」，出错了按它还原；MVCC 靠 undo log 的版本链，让读事务能回溯到「自己应该看到的那个历史版本」。两者都源于「undo log 保存旧版本」这个本质。

**场景**

项目里事务失败回滚，以及可重复读下读到事务开始时的旧值，都依赖 undo log。

**常见追问**

- 没有 undo log 会怎样？（无法回滚，也无法实现 MVCC 快照读）
- undo log 会被删除吗？（事务提交后，不再需要的旧版本会被清理/purge）

**易错点**

undo log 的「回滚」和「MVCC」两个作用要一起说，别只答回滚。

## 289. 什么是 redo log？

**面试回答**

redo log 是重做日志，记录「数据做了什么修改」，用于崩溃恢复：事务提交后即使数据没来得及写盘，也能靠 redo log 重做，保证持久性。

**理解**

redo log 是物理层面的「修改记录」。为避免每次修改都直接随机写磁盘（慢），InnoDB 先把修改记到 redo log（顺序写，快），再慢慢刷盘。即使宕机，重启后按 redo log 重放，把没落盘的修改补上，保证已提交事务不丢。这是 WAL（Write-Ahead Logging，先写日志）思想。

**场景**

项目里订单提交后即使服务器宕机，redo log 能保证已提交的订单在恢复后依然存在。

**常见追问**

- redo log 解决什么？（持久性、崩溃恢复）
- 为什么先写 redo log？（顺序写快，且保证不丢数据）

**易错点**

redo log 管「持久性/崩溃恢复」，是「重做」；undo log 管「回滚/旧版本」，是「撤销」，两者方向相反。

## 290. redo log 有什么作用？

**面试回答**

保证事务的持久性：通过先写 redo log（WAL），让已提交事务的修改在崩溃后能被重做恢复，数据不丢失，同时提升写入性能。

**理解**

redo log 记录「改后的结果」，事务提交前先把修改写进 redo log（顺序写），数据页可以稍后异步刷盘。这样既快（顺序写 vs 随机写）又安全（崩溃后按 redo log 重放恢复）。它是「持久性」特性的实现基础。

**场景**

项目里下单事务 commit 后，即使数据页还没刷盘就宕机，恢复时 redo log 会把订单数据补上。

**常见追问**

- redo log 为什么快？（顺序追加写，比随机写数据页快）
- 提交和 redo log 关系？（提交前会刷 redo log，保证不丢）

**易错点**

redo log 的作用是「持久性 + 崩溃恢复」，核心是「先记日志再刷盘」的 WAL 思想。

## 291. 什么是 binlog？

**面试回答**

binlog 是 MySQL Server 层的二进制日志，记录所有「修改数据」的逻辑操作（SQL 语句或行变更），用于主从复制、数据恢复、审计等。

**理解**

binlog 是 MySQL 层面的逻辑日志（区别于 InnoDB 的 redo log），记录「执行了什么修改语句」。主从复制靠它：主库的 binlog 同步给从库重放，实现数据一致。也能用于「基于时间点恢复数据」。binlog 有三种格式：statement、row、mixed。

**场景**

项目里若做读写分离、主从复制，就靠 binlog 把主库的写操作同步到从库。

**常见追问**

- binlog 有什么用？（主从复制、数据恢复）
- binlog 和 redo log 区别？（见 [[04-MySQL/04-事务#292. redo log 和 binlog 有什么区别？]]）

**易错点**

binlog 是「Server 层逻辑日志」，redo log 是「InnoDB 引擎层物理日志」，层级和用途都不同。

## 292. redo log 和 binlog 有什么区别？

**面试回答**

层级不同：redo log 是 InnoDB 引擎层日志，记录物理修改，用于崩溃恢复保证持久性；binlog 是 MySQL Server 层日志，记录逻辑操作，用于主从复制和数据恢复。

**理解**

几个维度对比：①产生者：redo log 是 InnoDB，binlog 是 Server 层；②内容：redo 记录「页怎么改」（物理），binlog 记录「执行了什么语句/行变化」（逻辑）；③用途：redo 管崩溃恢复，binlog 管复制/恢复；④写入：redo 循环写、固定大小，binlog 追加写、可切分。两者通过两阶段提交保证一致性（见 [[04-MySQL/06-MySQL进阶#605. 什么是两阶段提交？]]）。

**场景**

项目里 redo log 保证单机崩溃不丢数据，binlog 用于主从复制/备份恢复。

**常见追问**

- 谁产生 redo log？（InnoDB 引擎）
- 主从复制靠哪个日志？（binlog）

**易错点**

redo log「引擎层、物理、崩溃恢复」vs binlog「Server 层、逻辑、复制」，这是高频对比题，要能分维度说清。
