# 表设计

## 239. 什么是主键？

**面试回答**

主键是表中用来唯一标识每一行记录的字段（或字段组合），不能重复、不能为 NULL，一张表只能有一个主键。

**理解**

主键保证每一行都能被唯一找到。它通常是自增整数或业务唯一编号。主键是「实体唯一性」的基石，InnoDB 表还会把主键作为聚簇索引的存储结构（见索引部分），所以主键很重要。

**场景**

项目里每张表都有 id 主键（自增），用来唯一标识一条菜品、订单、用户记录。

**常见追问**

- 主键能是多个字段吗？（能，叫联合主键，但一般不推荐）
- 主键能为 NULL 吗？（不能）

**易错点**

主键「唯一 + 非空 + 一张表一个」，别和唯一索引（可多个、可空）混淆。

## 240. 什么是唯一索引？

**面试回答**

唯一索引是保证某一列（或几列组合）的值在表中不重复的索引，可以为 NULL（且 MySQL 允许唯一索引列有多个 NULL）。

**理解**

唯一索引既能加速查询，又能约束数据不重复。和主键的区别在于：唯一索引一张表可以有多个，且允许 NULL。它常用于用户名、手机号、订单号这类需要唯一的字段。

**场景**

项目里用户名、手机号、订单号加唯一索引，防止重复注册、重复下单。

**常见追问**

- 唯一索引能多个吗？（能，一张表可多个）
- 唯一索引能为 NULL 吗？（能，且多个 NULL 不冲突）

**易错点**

唯一索引「可多个、允许 NULL」，主键「唯一、非空、仅一个」，这是两者的关键差异。

## 241. 主键和唯一索引有什么区别？

**面试回答**

主键一张表只能有一个，不能为 NULL；唯一索引一张表可以有多个，允许 NULL。两者都保证值唯一，但主键是记录的唯一标识，唯一索引只是约束某列不重复。

**理解**

主键是「行标识」，语义更强，通常也是聚簇索引；唯一索引是「列约束 + 索引」，可以多个。主键不能为空，唯一索引列可以为空（多个 NULL 不算重复）。设计上：标识一条记录用主键，保证业务字段唯一（如手机号）用唯一索引。

**场景**

项目里 id 是主键，手机号、订单号等业务唯一字段用唯一索引。

**常见追问**

- 唯一索引能当主键用吗？（语义上不同，主键还有行标识和聚簇索引的作用）
- 两者数量限制？（主键 1 个，唯一索引可多个）

**易错点**

核心区别是「数量（1 vs 多）」和「NULL（不允许 vs 允许）」，别只说「都唯一」。

## 242. 为什么一张表通常需要主键？

**面试回答**

因为主键是唯一标识每行记录的基础，没有主键就无法高效定位某一行；而且 InnoDB 存储引擎需要主键来组织聚簇索引（B+Tree），没有显式主键会选一个唯一索引或生成隐藏的 rowid。

**理解**

主键保证数据唯一、可定位。对 InnoDB 来说，表数据就是按主键聚簇存储的，主键是行数据的「物理组织依据」。没有主键，InnoDB 会找唯一非空索引代替，都找不到就生成隐藏自增 rowid，既浪费空间又不稳定。所以显式建主键是良好实践。

**场景**

项目里每张表都显式建自增 id 主键，保证数据有序、可高效定位。

**常见追问**

- InnoDB 没有主键会怎样？（选唯一索引或生成隐藏 rowid）
- 主键为什么影响存储？（InnoDB 按主键聚簇存储数据）

**易错点**

InnoDB 下主键不只是「约束」，还是「数据存储组织方式」，所以每张表都该有显式主键。

## 243. 为什么很多业务表使用自增主键？

**面试回答**

因为自增主键能保证插入有序、递增，符合 InnoDB 聚簇索引「顺序插入」的特性，能减少页分裂、提高插入和查询性能，且实现简单、无业务含义。

**理解**

InnoDB 按主键顺序存数据。自增主键每次新记录都插在末尾，不需要在中间插入，避免了 B+Tree 页分裂带来的开销；而随机主键（如 UUID）插入位置随机，容易引起页分裂、降低性能、增加碎片。自增主键还简单、无业务耦合。

**场景**

项目里的 id 主键都是自增整数，插入有序高效。

**常见追问**

- UUID 做主键有什么问题？（随机，导致页分裂、性能差、占空间）
- 自增主键缺点？（不适合分布式全局唯一，可考虑雪花算法）

**易错点**

自增主键的好处核心是「顺序插入 + 减少页分裂」，要联系 InnoDB 聚簇索引理解，别只说「简单」。

## 244. `char` 和 `varchar` 有什么区别？

**面试回答**

char 是定长字符串，固定占用声明长度，存取快但浪费空间；varchar 是变长字符串，按实际长度存（加少量长度字节），省空间但存取略慢。

**理解**

char(n) 不管存几个字符都占 n 的长度（不足补空格），适合长度固定的字段（如手机号、状态码）；varchar(n) 按实际内容长度存，最多 n，适合长度不定的字段（如名称、备注）。varchar 需要额外的长度信息，且更新导致变长时可能有额外开销。

**场景**

项目里手机号、身份证号用 char，菜品名、地址、备注用 varchar。

**常见追问**

- 定长 vs 变长怎么选？（长度固定用 char，不定用 varchar）
- varchar 最大长度？（受行大小和字符集限制，常用 varchar(255) 等）

**易错点**

char 是「定长」、varchar 是「变长」；别把 varchar(n) 理解成「总是占 n」。

## 245. NULL 和空字符串有什么区别？

**面试回答**

NULL 表示「没有值/未知」，空字符串 '' 表示「值为空文本」，两者是不同的概念，比较、存储、索引处理都不同。

**理解**

NULL 是「值缺失」，`= NULL` 判断不了，要用 `IS NULL`；空字符串是一个真实存在的字符串，能用 `= ''` 判断。NULL 参与运算结果还是 NULL，聚合函数会忽略 NULL。设计上通常建议用「非空 + 默认值」而不是 NULL，避免判断麻烦。

**场景**

项目里字段尽量设 NOT NULL 并给默认值；比如「备注」没填就存空字符串或默认值，而不是 NULL。

**常见追问**

- 判断 NULL 用什么？（IS NULL / IS NOT NULL，不能用 = NULL）
- COUNT 会数 NULL 吗？（COUNT(column) 不会数 NULL）

**易错点**

NULL 是「无值」不是「空字符串」，判断必须用 IS NULL；这是新手最常踩的坑。

## 246. 数据库三大范式是什么？

**面试回答**

第一范式（1NF）：列不可再分（原子性）；第二范式（2NF）：在 1NF 基础上，非主键字段完全依赖主键（消除部分依赖）；第三范式（3NF）：在 2NF 基础上，非主键字段只依赖主键（消除传递依赖）。

**理解**

范式是「减少数据冗余和异常」的设计规范。1NF 要求每列是最小原子单位；2NF 消除「非主键字段只依赖联合主键的一部分」；3NF 消除「非主键字段通过另一个非主键字段间接依赖主键」。范式越高冗余越少，但查询可能要更多 JOIN。

**场景**

项目里表设计基本满足 3NF：订单表存用户 id 而不是用户完整信息，用户详情在用户表里，避免冗余。

**常见追问**

- 范式是为了什么？（减少冗余、避免更新/插入/删除异常）
- 一定要满足 3NF 吗？（不一定，实际常做反范式冗余换性能）

**易错点**

三大范式要能说清「消除什么依赖」；同时要知道实际业务不一定死守范式，会适当反范式。

## 247. 为什么实际业务中有时会适当冗余字段？

**面试回答**

为了减少 JOIN、提高查询性能：把常用但不常变的字段冗余到主表，查询时一次取出，避免频繁联表，用「存储冗余」换「查询性能」。

**理解**

严格范式要求不冗余，但那样查订单列表时每次都要 JOIN 用户表取用户名，订单量大时 JOIN 开销大。把用户名等字段冗余到订单表，查询一次搞定。代价是冗余数据要维护一致性（更新用户名时要同步）。这是典型的「性能 vs 规范」权衡。

**场景**

项目里订单表冗余了用户昵称、菜品名称快照等字段（订单地址快照也是这个思路），避免下单后用户改名、菜品改名影响历史订单展示，也减少 JOIN。

**常见追问**

- 冗余的代价？（数据一致性要维护，更新要同步）
- 什么字段适合冗余？（不常变、常被一起查的字段）

**易错点**

冗余是「有代价的优化」，要能说清「用冗余换性能 + 需维护一致性」，不是无脑冗余。

## 248. 什么是反范式设计？

**面试回答**

反范式设计是故意违反范式规范，通过增加冗余字段、合并表等手段，用空间换时间，提高查询性能、减少 JOIN。

**理解**

范式追求「少冗余」，反范式追求「高性能」，两者是权衡关系。当查询频繁、JOIN 昂贵时，适当冗余能显著提速。反范式不是「乱设计」，而是「有意识地用冗余换性能」，并接受相应的一致性维护成本。

**场景**

项目里订单快照（下单时保存地址、菜品名快照）就是反范式设计：冗余了本可关联查询的数据，换来了历史订单稳定展示 + 少 JOIN。

**常见追问**

- 反范式和范式矛盾吗？（是权衡，不是对立，实际设计常在两者间平衡）
- 反范式典型手段？（冗余字段、合并表、存汇总值）

**易错点**

反范式是「用冗余换性能」的主动设计，不是「不会设计」；要能说出它带来的维护成本。
