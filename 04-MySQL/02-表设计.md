# 表设计

## 239. 什么是主键？

**面试回答**

主键是表中唯一标识一行的约束，可以由一列或多列组成；MySQL 要求主键列非 NULL，一张表只有一个 PRIMARY KEY 约束，但联合主键可包含多个列。

**原理与理解**

主键同时表达实体身份并创建唯一索引。在 InnoDB 中，主键索引是聚簇索引，叶子页保存整行数据；其他二级索引记录会携带主键值用于回表。

**成立条件与边界**

主键只保证标识唯一，不自动保证业务字段唯一。主键可用自增数、应用生成 ID 或稳定自然键，需综合长度、写入局部性、分布式生成和外部暴露风险。

**实际场景（真实项目边界）**

项目已确认订单主表插入后回填主键，再把该 ID 写入订单明细关联列；具体每张表的键策略仍以 DDL 为准。

**常见追问**

- 联合主键合法吗？——合法，但每个二级索引都要携带完整主键，宽度成本更高。
- 主键就是业务编号吗？——不一定，可分离内部代理键和受唯一约束的业务编号。

**易错点**

“一张表只能有一个主键”指一个主键约束，不代表主键只能有一列。

## 240. 什么是唯一索引？

**面试回答**

唯一索引既提供索引访问，又要求索引键组合不重复。MySQL 中可建立多个唯一索引；若列允许 NULL，多个含 NULL 的键通常不会被视为彼此相等。

**原理与理解**

插入或更新时，存储引擎检查唯一键冲突，数据库约束能抵御并发竞态，比“先查再插”的应用判断更可靠。联合唯一约束按所有键列的组合判断。

**成立条件与边界**

唯一索引不自动等于业务全局唯一：软删除、租户隔离、大小写/重音规则和 NULL 语义都会改变约束范围。是否允许 NULL 由列定义决定，而非唯一索引必然允许。

**实际场景（项目核验项）**

简历确认统一处理数据库约束异常，但未列出手机号、订单号等具体唯一索引；面试前应从建表脚本核验索引列和异常映射。

**常见追问**

- 为什么不能只在代码里查重？——并发请求可能同时通过检查，数据库唯一约束才是最终防线。
- 联合唯一索引中有 NULL 呢？——MySQL 的 NULL 不按普通相等值处理，需专项测试业务期望。

**易错点**

不要背“唯一索引可以为 NULL”，准确说法是列可声明为 NULL，且 MySQL 的唯一性检查对 NULL 有特殊语义。

## 241. 主键和唯一索引有什么区别？

**面试回答**

主键用于定义行身份，列必须非 NULL且每表一个约束；唯一索引用于约束一个或多个候选键，可有多个，并可建立在允许 NULL 的列上。InnoDB 优先以主键组织聚簇数据。

**原理与理解**

若 InnoDB 没有主键，会寻找第一个所有列均 NOT NULL 的唯一索引作为聚簇索引；仍找不到则生成隐藏聚簇键。其他唯一索引一般仍属于二级索引。

**成立条件与边界**

“唯一索引可以替代主键”只在唯一性层面部分成立，行身份、外键引用、ORM映射和聚簇存储仍有区别。可空唯一键还不能表达所有候选键约束。

**实际场景（通用工程）**

内部 `id` 作为主键，业务订单号另建唯一索引：前者稳定关联明细，后者防止业务标识重复并支持查询。

**常见追问**

- 主键与唯一索引都能加速查询吗？——能，但结构位置、键宽和覆盖能力不同。
- 没有主键会怎样？——InnoDB 选择合适的唯一非空索引，否则创建隐藏键。

**易错点**

不要把“PRIMARY KEY 是一种唯一索引”推导成两者设计语义完全相同。

## 242. 为什么一张表通常需要主键？

**面试回答**

显式主键为每行提供稳定身份，方便更新、删除、关联、复制和 ORM 映射；对 InnoDB，它还决定聚簇索引，并被二级索引用作行定位信息。

**原理与理解**

没有显式主键时，InnoDB 仍要选择或生成内部聚簇键，但业务无法直接引用隐藏键。合理的窄主键还能控制二级索引体积和回表成本。

**成立条件与边界**

主键不必自增，也不保证物理文件中的永久连续顺序。选择主键时要避免频繁变化、过宽和随机写放大，同时考虑跨系统唯一性。

**实际场景（真实项目边界）**

订单与明细是一对多关系，稳定主键是关联和主键回填链路的基础；事务则负责主子写入的原子性，两者职责不同。

**常见追问**

- InnoDB 隐藏键能否由应用查询？——不能把它当业务可见主键使用。
- 为什么主键尽量短？——其值会进入每个二级索引记录，过宽会放大空间和缓存成本。

**易错点**

“没有主键就不能存数据”不准确；能存，但 InnoDB 会自行选择或生成聚簇键。

## 243. 为什么很多业务表使用自增主键？

**面试回答**

自增整数键较短、生成简单，通常近似递增写入 InnoDB 聚簇索引，局部性好且二级索引携带成本低，适合单库或可控分片的内部标识。

**原理与理解**

AUTO_INCREMENT 由数据库分配值；不同锁模式、批量插入、事务回滚和并发会产生间隙，所以它保证的是唯一生成能力，不是连续无洞的业务序号。

**成立条件与边界**

高并发集中写入可能形成热点；多库合并、跨区域生成和离线写入需要额外方案。自增 ID 可被枚举，不能承担权限控制或保密作用。

**实际场景（真实项目边界）**

简历确认项目使用数据库生成主键并回填订单 ID；是否所有表均为自增以及具体类型需从 DDL 核验。

**常见追问**

- 自增 ID 会连续吗？——不保证，失败、回滚和预分配都可能留洞。
- 分布式系统还能用吗？——可以配合分片步长或中心服务，但通常会评估雪花 ID 等方案。

**易错点**

“递增主键永不页分裂、永无竞争”都是绝对化说法。

## 244. `char` 和 `varchar` 有什么区别？

**面试回答**

`CHAR(M)` 表达固定字符长度语义，值不足时按规则补尾随空格；`VARCHAR(M)` 存可变长度字符串，并额外保存 1 或 2 字节长度信息。M 表示字符数，不是固定字节数。

**原理与理解**

实际字节数由字符集决定，例如 utf8mb4 一个字符最多可占多字节。VARCHAR 只保存实际内容及长度前缀；CHAR 的存储和尾随空格比较行为还受行格式、SQL 模式与 collation 影响。

**成立条件与边界**

不能简单断言 CHAR 查询一定更快或总占 M 个字节。定长、短小且语义上固定的数据可考虑 CHAR；长度差异明显的文本通常用 VARCHAR，并核对索引长度与最大行大小。

**实际场景（通用工程）**

固定长度状态码或摘要片段可评估 CHAR；姓名、地址、备注等长度变化明显的数据更适合 VARCHAR/TEXT，并按业务设上限。

**常见追问**

- VARCHAR(20) 是 20 字节吗？——不是，是最多 20 个字符，字节受字符集影响。
- 尾随空格会怎样？——存储、返回和比较受类型与 collation 规则影响，不能只靠经验判断。

**易错点**

不要把 CHAR/VARCHAR 的差异概括为“固定字节与可变字节”，MySQL 的单位和字符集必须一起说明。

## 245. NULL 和空字符串有什么区别？

**面试回答**

NULL 表示未知或缺失，空字符串 `''` 是长度为 0 的已知字符串。判断 NULL 要用 `IS NULL`/`IS NOT NULL`；`= NULL` 的结果不是 TRUE。

**原理与理解**

SQL 使用三值逻辑，含 NULL 的普通比较常得到 UNKNOWN。COUNT(column) 忽略 NULL但会统计空字符串；空字符串可以参与等值比较和唯一性判断。

**成立条件与边界**

是否允许 NULL 是数据模型选择。NOT NULL 配合合理默认值可简化逻辑，但用空字符串冒充“未知”会混淆语义；对日期、数字等更不能用空字符串统一代替缺失。

**实际场景（通用工程）**

用户备注“尚未填写”可建模为 NULL，“明确填写为空”是否有业务意义要先定义；查询和序列化层需保持同一约定。

**常见追问**

- `NULL = NULL` 是 TRUE 吗？——不是，应使用 IS NULL；需要空值安全比较可了解 MySQL `<=>`。
- COUNT 会怎样？——COUNT(*) 数行，COUNT(column) 跳过 NULL。

**易错点**

NULL 不是 0、false 或空字符串，也不能用普通等号判断。

## 246. 数据库三大范式是什么？

**面试回答**

第一范式要求属性值在当前关系模型下保持原子；第二范式要求在 1NF 基础上，非主属性完全依赖每个候选键，消除对组合键一部分的依赖；第三范式要求在 2NF 基础上，非主属性不通过另一个非主属性传递依赖候选键。

**原理与理解**

范式依据函数依赖识别重复事实和更新异常。2NF 问“是否只依赖组合键的一部分”，3NF 问“是否依赖另一个非主属性”，因此只背“依赖主键”不够严谨。

**成立条件与边界**

2NF 问题主要出现在复合候选键场景；原子性取决于业务查询和约束需求。范式是设计分析工具，不是表越拆越多越好，最终还要满足一致性和访问模式。

**实际场景（通用工程）**

订单主表保存订单级字段，订单明细保存商品项，避免把多个商品 ID 拼进一个字符串，也避免每条明细重复完整的订单级事实。

**常见追问**

- 2NF 与 3NF 的核心差异？——部分依赖与传递依赖。
- 范式越高越好吗？——不一定，要平衡一致性、查询复杂度和性能。

**易错点**

“第一范式就是每格只能放一个值”是简化说法，必须结合字段的业务语义判断原子性。

## 247. 为什么实际业务中有时会适当冗余字段？

**面试回答**

为减少高频连接、保存历史快照、隔离上下游变化或提高读可用性，业务会有意识地复制少量字段；前提是明确权威数据源、同步时机和不一致处理。

**原理与理解**

冗余用写入和一致性成本换取查询简单、性能或历史语义。快照字段不是“缓存一份当前值”，而是记录事件发生时的事实，之后通常不随源数据改变。

**成立条件与边界**

必须区分可重新生成的派生值、最终一致副本和不可变历史快照。双写要有事务、事件、补偿或对账策略；不能靠“每次都记得改两处”。

**实际场景（真实项目边界）**

项目下单时固化收货人信息作为地址快照，后续地址簿修改不影响历史订单；这是历史语义需要，而不只是为了少一次 JOIN。

**常见追问**

- 冗余字段如何保持一致？——先定义是否应同步，再选择同事务、事件驱动、重试与对账。
- 快照为何不更新？——它表达过去时点的事实，更新反而破坏历史。

**易错点**

不要把所有重复字段都叫缓存，也不要默认冗余字段必须与源表实时一致。

## 248. 什么是反范式设计？

**面试回答**

反范式是在理解规范化模型后，为特定读性能、历史快照或可用性目标，有控制地合并表或冗余数据，并接受额外写入与一致性成本。

**原理与理解**

常见方式包括冗余展示字段、维护汇总值、宽表或预计算读模型。它不是否定范式，而是针对明确瓶颈做局部权衡，并建立数据血缘和修复能力。

**成立条件与边界**

应先用执行计划、索引和真实负载确认问题；反范式后要处理并发更新、回滚、补偿、重算和迁移。读多写少并不自动意味着应该宽表。

**实际场景（真实项目边界）**

地址快照可视为有业务语义的反范式：订单保存下单时地址字段。项目未证明使用统计宽表或冗余计数，不能扩写为相关经验。

**常见追问**

- 与普通缓存有什么区别？——反范式数据进入持久化模型并承担业务语义，缓存通常可失效和重建。
- 什么时候考虑？——规范化查询已成为经验证的瓶颈，或历史事实必须独立保存时。

**易错点**

反范式不是“为了快就复制字段”，没有同步和修复方案只是在制造数据债务。
