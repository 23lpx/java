# 锁

## 293. 为什么数据库需要锁？

**面试回答**

数据库使用锁协调并发事务对共享数据的访问，防止写写覆盖、违反唯一性或业务状态机等问题，并为不同隔离级别提供相应的并发控制能力。

**原理与理解**

多个事务访问同一记录或索引范围时，数据库根据锁类型和兼容关系决定立即执行还是等待。锁与 MVCC 是互补机制：普通一致性读可以读取快照，锁定读和写操作则需要锁住相关索引记录或范围。

**成立条件与边界**

锁只能保护被同一数据库并发控制机制覆盖的资源，不能自动协调 Redis、消息队列或远程支付平台。锁也不等于业务一定正确：错误的查询条件、过大的锁范围或缺少状态条件仍可能产生错误结果。

**实际场景（通用工程）**

两个支付回调并发把订单从未支付改为已支付时，可以使用带旧状态条件的 `UPDATE`，由数据库锁和原子条件保证只有一次状态迁移成功。

**常见追问**

- 锁和 MVCC 是什么关系？（MVCC 优化一致性读，写和锁定读仍需要锁）
- 数据库锁能保护远程接口吗？（不能）

**易错点**

锁不是“牺牲并发就自动获得正确性”，还要有正确的事务边界、索引、状态条件和失败处理。

## 294. 什么是共享锁？

**面试回答**

共享锁（S 锁）允许持锁事务读取记录；多个事务可以对同一索引记录持有 S 锁，但其他事务不能同时取得冲突的 X 锁来修改该记录。

**原理与理解**

在 InnoDB 中，`SELECT ... FOR SHARE` 会对读取到的索引记录申请共享模式锁。S 与 S 兼容，S 与 X 冲突，锁通常持有到事务提交或回滚。

**成立条件与边界**

“S 锁挡住写”针对需要取得冲突锁的操作。普通一致性 `SELECT` 通常不申请 S 锁，可以通过 MVCC 忽略当前记录锁并读取快照中的可见版本。`FOR SHARE` 只有在有效事务中才有持续保护意义。

**实际场景（通用工程）**

创建子记录前需要确保父记录在本事务完成前不被删除，可以在事务内使用 `SELECT ... FOR SHARE` 读取父记录，再插入子记录。

**常见追问**

- S 锁与 S 锁兼容吗？（兼容）
- 持有 S 锁时普通快照读会被阻塞吗？（通常不会，快照读可读可见版本）

**易错点**

不要把“共享锁允许读”理解成所有读操作默认都会加共享锁；RC/RR 下普通 `SELECT` 通常是一致性非锁定读。

## 295. 什么是排他锁？

**面试回答**

排他锁（X 锁）允许持锁事务更新或删除相关索引记录，并与其他事务对同一记录申请的 S 锁、X 锁冲突。

**原理与理解**

`UPDATE`、`DELETE` 以及 `SELECT ... FOR UPDATE` 会根据执行时扫描的索引记录申请 X 类型锁。其他事务若要修改相同记录或进行冲突的锁定读，必须等待锁释放。

**成立条件与边界**

X 锁不等于“其他事务完全不能读取”。普通一致性读可以利用 MVCC 读取其快照可见的旧版本。实际锁范围还取决于隔离级别、使用的索引、唯一等值查询还是范围扫描。

**实际场景（通用工程）**

事务先用 `SELECT ... FOR UPDATE` 锁定待处理任务，再更新任务状态，可防止另一个锁定消费者同时修改同一记录；但应设计好超时和并发领取策略。

**常见追问**

- X 锁会阻塞哪些操作？（冲突的锁定读与写）
- 普通 `SELECT` 一定被 X 锁阻塞吗？（不一定，RC/RR 的一致性读通常读取快照）

**易错点**

“X 锁阻塞所有读写”过于绝对，必须区分快照读和锁定读。

## 296. 什么是行锁？

**面试回答**

InnoDB 所说的行级锁实际加在索引记录及其索引间隙上，主要包括 record lock、gap lock 和 next-key lock。粒度通常比表锁细，但锁住多少数据取决于 SQL 扫描了多少索引范围。

**原理与理解**

record lock 锁一个索引记录；gap lock 只阻止在两个索引记录之间的间隙插入；next-key lock 是“记录锁 + 该记录之前的间隙锁”。RR 下范围锁定读常用 next-key lock 防止扫描范围出现新记录；唯一索引完整等值查询通常只需记录锁。

**成立条件与边界**

表没有显式索引时，InnoDB 会创建隐藏聚簇索引用于记录锁。查询没有合适索引时，锁定读或 DML 可能扫描并锁住大量索引记录和间隙，产生近似锁全表的效果，但这不叫“自动升级成表锁”。RC 下普通搜索的 gap locking 通常关闭，但外键和重复键检查仍可能使用。

**实际场景（通用工程）**

`UPDATE orders SET status = ? WHERE id = ?` 使用主键精确定位时通常只锁目标索引记录；若按无合适索引的条件更新，可能扫描和锁住大量记录，显著放大阻塞范围。

**常见追问**

- InnoDB 行锁锁的是什么？（索引记录，而不是抽象的物理行编号）
- 什么是 next-key lock？（记录锁与其前方 gap lock 的组合）

**易错点**

“走索引才是行锁、不走索引就退化表锁”不准确；正确说法是锁跟随实际索引扫描范围，可能锁住大量记录但不会因此自动升级为表锁。

## 297. 什么是表锁？

**面试回答**

表锁以整张表为粒度协调访问，例如显式 `LOCK TABLES` 取得的读写锁。InnoDB 还使用表级意向锁来表示事务准备在表内取得行级 S/X 锁。

**原理与理解**

意向共享锁 IS 和意向排他锁 IX 主要用于让行锁与整表锁共存：取得行级 S 锁前先取得 IS，取得行级 X 锁前先取得 IX。意向锁通常只与真正的整表锁请求发生关键冲突，不会把所有行操作互相阻塞。

**成立条件与边界**

InnoDB 还存在 AUTO-INC 等特殊表级锁，具体行为受配置和插入方式影响。表锁、意向锁、元数据锁不是同一个概念；DDL 阻塞也不能一律归因于普通表级读写锁。

**实际场景（通用工程）**

事务更新某行前持有表级 IX，显式整表写锁请求会通过意向锁快速发现表内已有行锁活动，而不必逐行检查。

**常见追问**

- IX 是不是已经锁住整张表不能读写？（不是，它主要表示将取得或已取得行级 X 锁）
- InnoDB 是否只有行锁？（不是，也有意向锁、AUTO-INC 锁及显式表锁等）

**易错点**

不要把“表级锁对象”都理解为“整表完全不可访问”；必须结合具体锁模式和兼容矩阵判断。

## 298. 行锁和表锁有什么区别？

**面试回答**

行级锁作用于索引记录或范围，通常并发度更高但锁管理更复杂；表锁覆盖整张表，管理成本相对简单，但冲突时影响范围更大。

**原理与理解**

InnoDB 通过意向锁协调两种粒度。事务操作不同记录时，行锁可以并行；整表锁会与不兼容的表级意向或读写锁冲突。是否出现阻塞不能只看“行锁/表锁”标签，还要看锁模式、扫描范围和持有时间。

**成立条件与边界**

InnoDB 一般不会因为行锁数量多或 SQL 没用到合适索引而自动锁升级。没有合适索引会导致扫描并锁住大量索引记录，效果可能很像表被锁住，但诊断和优化方式仍是检查执行计划与锁范围。

**实际场景（通用工程）**

两个事务按主键更新不同订单通常可并行；一个缺少合适索引的范围更新扫描了大部分表时，可能阻塞大量订单操作，即使底层仍是一组记录/间隙锁。

**常见追问**

- InnoDB 会自动把大量行锁升级成表锁吗？（通常不会）
- 如何减少锁范围？（合适索引、精确条件、短事务，并用执行计划验证）

**易错点**

“行锁一定只锁一行”同样错误；范围扫描可能取得许多 record/next-key locks。

## 299. 什么是悲观锁？

**面试回答**

悲观锁是一种并发控制思路：先取得会阻止冲突操作的锁，再读取和修改数据。MySQL 中常通过事务内的 `SELECT ... FOR UPDATE` 或 `FOR SHARE` 实现锁定读。

**原理与理解**

`FOR UPDATE` 按类似 `UPDATE` 的方式锁住查询扫描到的索引记录和相关范围，使其他事务的冲突写入等待。它适合冲突概率高、读取后必须基于同一状态继续修改的业务。

**成立条件与边界**

锁定读需要在有效事务中使用，并尽快提交或回滚。查询条件和索引设计决定锁范围；范围过大可能造成严重阻塞与死锁。数据库本地悲观锁也不能锁住远程服务或缓存。

**实际场景（通用工程）**

从任务表领取一条待处理任务时，可以在事务中锁定候选记录并立即改为处理中；高并发任务队列还可评估 `SKIP LOCKED`，但它返回的是不一致视图，不适合一般事务读取。

**常见追问**

- `FOR UPDATE` 什么时候释放锁？（事务提交或回滚时）
- 加了 `FOR UPDATE` 就只锁结果行吗？（不一定，取决于扫描的索引记录和范围）

**易错点**

不要在自动提交、长事务或无合适索引的条件下机械使用 `FOR UPDATE`，否则锁的保护时间或范围可能与预期不同。

## 300. 什么是乐观锁？

**面试回答**

乐观锁是一种应用层并发控制思路：读取时不长期占用业务排他锁，更新时携带旧版本或旧状态作为条件，通过原子更新的受影响行数检测并发冲突。

**原理与理解**

典型 SQL 是 `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`。只有仍满足旧版本条件的请求更新成功，其余请求需要重新读取、放弃或按业务规则重试。

**成立条件与边界**

乐观锁不等于数据库完全不加锁；执行 `UPDATE` 时 InnoDB 仍会取得必要的 X 锁。它只是不在“先读后思考”的整个期间持有悲观业务锁。冲突频繁时反复重试可能比悲观方案成本更高。

**实际场景（通用工程）**

后台编辑同一商品资料时，可以使用版本号阻止后提交者静默覆盖前一个管理员的修改，并把冲突明确返回给用户处理。

**常见追问**

- 乐观锁是否完全不用数据库锁？（不是，最终 UPDATE 仍需数据库锁）
- 通常如何实现？（版本号或旧状态条件，见 [[04-MySQL/05-锁#301. 乐观锁通常如何实现？]]）

**易错点**

“先操作、提交时检查”容易让人误以为检查和更新是两条独立 SQL；正确实现必须把条件检查和更新放在同一条原子 SQL 中。

## 301. 乐观锁通常如何实现？

**面试回答**

常用版本号或旧状态条件实现：更新时把旧版本写入 `WHERE`，成功后递增版本号，再根据受影响行数判断本次是否取得更新权。

**原理与理解**

例如：

```sql
UPDATE product
SET price = ?, version = version + 1
WHERE id = ? AND version = ?;
```

受影响行数为 1 表示条件匹配并更新成功；为 0 表示当前条件没有匹配，需要进一步区分记录不存在、版本冲突或状态已经变化。

**成立条件与边界**

失败后不能无限无脑重试。应重新读取最新数据，确认操作是否仍有意义，并设置重试上限；涉及付款、发消息等外部副作用时，还必须保证整体幂等。只使用更新时间戳时还要考虑精度和并发更新碰撞。

**实际场景（通用工程）**

订单状态可以使用 `WHERE id = ? AND status = 'UNPAID'` 做状态型乐观并发控制；影响 0 行时不能直接认定“重复成功”，还可能是订单不存在或状态非法。

**常见追问**

- 影响 0 行一定是版本冲突吗？（不一定，也可能记录不存在或状态不满足）
- 版本号为什么要在同一条 SQL 中递增？（保证比较和更新原子完成）

**易错点**

只写 version 字段却不检查受影响行数，等于没有真正处理并发冲突。

## 302. 什么是数据库死锁？

**面试回答**

死锁指多个事务各自持有锁，又等待其他事务持有的锁，形成等待环，使这些事务无法自行继续。InnoDB 默认启用死锁检测，并选择一个或多个事务作为受害者回滚来打破环路。

**原理与理解**

典型情况是事务 A 持有记录 1 等待记录 2，事务 B 持有记录 2 等待记录 1。死锁与普通锁等待不同：普通等待可能在持锁事务提交后继续，死锁形成环后若不干预就无法推进。

**成立条件与边界**

InnoDB 倾向回滚较小的事务，但应用不能依赖某个固定事务一定成为受害者。关闭 `innodb_deadlock_detect` 后，系统依赖锁等待超时处理；死锁检测也不一定覆盖其他存储引擎或某些 MySQL 层表锁组合。

**实际场景（通用工程）**

两个批量更新事务以相反顺序修改订单 1 和订单 2，可能各锁住一条后等待另一条，从而形成死锁。

**常见追问**

- 死锁与锁等待的区别？（死锁存在等待环，普通等待可能自然解除）
- InnoDB 默认如何处理？（检测后回滚受害事务）

**易错点**

数据库回滚一个事务只是解除当前死锁，业务仍必须捕获错误并决定是否重试整个事务。

## 303. MySQL 为什么会产生死锁？

**面试回答**

常见原因是并发事务以不同顺序取得多个索引记录或范围锁，形成循环等待；扫描范围过大、gap/next-key locks、多个二级索引、外键检查和重复键处理都会增加锁交叉机会。

**原理与理解**

一条看似只操作一行的 SQL 也可能涉及聚簇索引、二级索引和间隙，因此死锁不只发生在“显式锁两行”的代码中。官方文档明确指出，即使事务只插入或删除一行也可能死锁。

**成立条件与边界**

“加锁顺序不一致”是常见诱因，不是唯一原因；数据分布、执行计划和并发时序都会影响实际锁集合。不能仅凭 SQL 文本猜测，应结合 `SHOW ENGINE INNODB STATUS` 和执行计划分析。

**实际场景（通用工程）**

两个请求都批量更新多条明细，但输入 ID 顺序不同，可能按不同顺序取得锁；先统一排序通常能减少这种交叉等待。

**常见追问**

- 单行 INSERT 可能死锁吗？（可能，可能涉及多个索引记录或重复键锁）
- 如何查看最近一次 InnoDB 死锁？（`SHOW ENGINE INNODB STATUS`）

**易错点**

死锁不是简单等同于“事务太慢”；长事务扩大死锁窗口，但真正特征是锁等待图形成环。

## 304. 如何降低死锁发生概率？

**面试回答**

让事务按一致顺序访问表和记录，保持事务小而短，为锁定读和更新条件建立合适索引，减少不必要的锁定读，并在应用层准备好安全重试被回滚的完整事务。

**原理与理解**

一致加锁顺序减少等待环；短事务缩短持锁时间；合适索引减少扫描和加锁记录；普通快照读能满足需求时不使用 `FOR UPDATE/FOR SHARE`。诊断时查看最近死锁，频繁问题可临时开启全量死锁日志。

**成立条件与边界**

死锁只能降低概率，不能保证彻底消除。重试应有次数上限、短暂退避并重新执行整个事务；若事务夹杂远程调用或其他不可回滚副作用，必须先做幂等与边界重构，不能直接重复执行。

**实际场景（通用工程）**

批量更新前按主键排序，事务中不执行耗时网络请求，发生死锁后回滚并有限重试；若同类死锁频繁出现，再依据死锁日志调整索引和访问顺序。

**常见追问**

- 为什么统一顺序能降低死锁？（减少形成循环等待的机会）
- 死锁重试应重试哪一部分？（通常重新执行整个已回滚事务）

**易错点**

不要把无限重试当成修复；频繁死锁说明事务设计、索引或访问顺序需要进一步治理。
