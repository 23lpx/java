# 锁

## 293. 为什么数据库需要锁？

**面试回答**

为了在并发访问时保证数据的一致性和正确性：多个事务同时读写同一数据时，用锁控制访问顺序，避免数据被覆盖、读到中间态。

**理解**

并发是数据库常态，没有锁的话，两个事务同时改同一行可能互相覆盖，读也可能读到未提交或半成品数据。锁通过「限制同时访问」来保证并发下数据正确。锁的代价是降低并发度，所以要「按需加锁」，在一致性和性能间权衡。

**场景**

项目里并发下单扣库存时，用锁保证库存不会超卖、数据不错乱。

**常见追问**

- 锁解决什么？（并发下数据一致性）
- 锁有代价吗？（有，降低并发性能）

**易错点**

锁是「用并发换正确性」；理解它为什么必要，也要理解它为什么不能滥用。

## 294. 什么是共享锁？

**面试回答**

共享锁（S 锁，读锁）允许多个事务同时持有，用于读取数据；持有共享锁时，其他事务也能读，但不能写。

**理解**

共享锁的规则是「读读共享、读写互斥」：多个事务都能加 S 锁读同一数据，但只要有 S 锁在，别人就不能加排他锁（X 锁）去写。它保证读期间数据不被改。`SELECT ... LOCK IN SHARE MODE`（MySQL 8 用 `FOR SHARE`）可显式加共享锁。

**场景**

项目里一般查询用 MVCC 不加锁；特殊场景需要「读时不让别人改」才显式加共享锁。

**常见追问**

- 共享锁和排他锁兼容吗？（不兼容，读写互斥）
- 共享锁之间呢？（兼容，可多个事务同时读）

**易错点**

共享锁「读读共享、读写互斥」；多个读可以共存，但读会挡住写。

## 295. 什么是排他锁？

**面试回答**

排他锁（X 锁，写锁）只能被一个事务持有，用于修改数据；持有排他锁时，其他事务既不能读（加共享锁）也不能写（加排他锁）。

**理解**

排他锁是「独占」的：一个事务加了 X 锁，别人连读（需加 S 锁）都不行，更不能写。增删改操作会自动加排他锁。`SELECT ... FOR UPDATE` 可显式加排他锁。它保证修改期间数据不被他人读写干扰。

**场景**

项目里更新库存、修改订单状态时，InnoDB 自动给对应行加排他锁，保证并发修改安全。

**常见追问**

- 排他锁和共享锁兼容吗？（不兼容）
- 哪些操作会加排他锁？（INSERT/UPDATE/DELETE，以及 SELECT ... FOR UPDATE）

**易错点**

排他锁「独占」，写操作会加它，且它会阻塞别人的读写；和共享锁的「共享」形成对比。

## 296. 什么是行锁？

**面试回答**

行锁是锁定「一行数据」的锁，粒度细，并发度高，只阻塞访问同一行的其他事务，是 InnoDB 默认的锁粒度。

**理解**

行锁按「行」加锁，不同行之间不冲突，所以并发性能好，适合写操作较多的场景。但行锁只在「走索引」时才能精确锁行，如果没走索引会退化成锁表（InnoDB 里实际是锁所有行/间隙）。InnoDB 默认支持行锁。

**场景**

项目里并发更新不同订单时，行锁让它们互不阻塞（不同行），只有改同一行才等待。

**常见追问**

- 行锁有什么优势？（粒度细、并发高）
- 什么时候行锁退化为表锁？（查询没走索引时）

**易错点**

行锁粒度细、并发好，但要「走索引」才生效；没走索引可能退化成锁表，这是关键细节。

## 297. 什么是表锁？

**面试回答**

表锁是锁定「整张表」的锁，粒度粗，一个事务锁表后其他事务对该表的读写都要等待，并发度低但开销小。

**理解**

表锁一次锁住整张表，实现简单、加锁快，但会严重降低并发。MyISAM 主要用表锁；InnoDB 一般用行锁，但在某些情况（如没走索引的更新）也可能锁表。表锁适合「大量读、少量写」或需要整表操作的场景。

**场景**

项目里一般用 InnoDB 行锁；对整表做维护、备份等批量操作时可能涉及表锁。

**常见追问**

- 表锁和行锁谁并发好？（行锁并发好，表锁粒度粗）
- 什么引擎用表锁？（MyISAM，InnoDB 一般行锁）

**易错点**

表锁「锁整表、并发低」；InnoDB 主要是行锁，但没走索引时会退化成锁表，别以为 InnoDB 永远行锁。

## 298. 行锁和表锁有什么区别？

**面试回答**

粒度不同：行锁锁一行，粒度细、并发高，但开销较大；表锁锁整表，粒度粗、并发低，但开销小、实现简单。

**理解**

行锁允许不同事务同时操作不同行，适合高并发写入；表锁一次锁全表，任何操作都要等，适合并发低或整表操作的场景。InnoDB 默认行锁（走索引时），MyISAM 用表锁。行锁虽然并发好，但锁数量多时内存开销也大。

**场景**

项目里订单并发更新用行锁（不同订单互不阻塞）；整表统计、备份等才考虑表锁。

**常见追问**

- 高并发写入用哪种？（行锁）
- InnoDB 什么时候会退化成锁表？（没走索引）

**易错点**

核心对比是「粒度 → 并发/开销」；行锁细而高并发，表锁粗而低并发，要根据场景选。

## 299. 什么是悲观锁？

**面试回答**

悲观锁是「先加锁再操作」的并发控制策略：认为并发冲突很可能发生，操作数据前先获取锁，确保独占，操作完再释放。

**理解**

悲观锁假设「别人会来改」，所以主动加锁（如 `SELECT ... FOR UPDATE` 排他锁）。它的优点是简单可靠、能保证强一致；缺点是锁持有期间阻塞其他事务，并发性能差。适合写多、冲突概率高的场景。

**场景**

项目里扣库存这类「高冲突、要强一致」的操作，可用悲观锁（FOR UPDATE 锁住库存行再扣）。

**常见追问**

- 悲观锁怎么实现？（数据库锁，如 SELECT ... FOR UPDATE）
- 悲观锁缺点？（阻塞、并发低）

**易错点**

悲观锁 = 「先加锁，防冲突」；核心是「用锁阻塞来保证一致」，代价是并发差。

## 300. 什么是乐观锁？

**面试回答**

乐观锁是「先操作、提交时检查」的并发控制策略：认为冲突很少发生，操作时不加锁，提交时校验数据是否被改过，被改过则重试或放弃。

**理解**

乐观锁假设「别人一般不会来改」，所以不阻塞，靠「提交时比对」发现冲突。常用版本号或时间戳实现：更新时 `WHERE version = 旧值`，更新成功说明没被改，失败说明被改了要重试。优点是不阻塞、并发好；缺点是要处理冲突重试。

**场景**

项目里更新菜品价格、用户信息这类「冲突少」的操作，用乐观锁（版本号）实现，读多写少时性能更好。

**常见追问**

- 乐观锁怎么实现？（版本号/CAS，见 [[04-MySQL/05-锁#301. 乐观锁通常如何实现？]]）
- 乐观锁什么时候用？（冲突少、读多写少）

**易错点**

乐观锁 = 「不加锁 + 提交时校验」；和悲观锁的「先加锁」思路相反，核心是「版本号/CAS 检测冲突」。

## 301. 乐观锁通常如何实现？

**面试回答**

通常用「版本号」或「时间戳」：表里加 version 字段，更新时 `UPDATE ... SET version = version + 1 WHERE id = ? AND version = 旧值`，根据影响行数判断是否成功。

**理解**

更新前先读出当前 version，更新时把 version 作为条件：如果没人改过，version 还是旧值，更新成功并把 version+1；如果期间别人改了，version 变了，条件不成立、影响行数为 0，说明发生冲突，需要重试或提示。本质是「CAS（比较并交换）」思想。

**场景**

项目里对菜品做编辑时，用 version 字段做乐观锁，防止两个管理员同时编辑互相覆盖。

**常见追问**

- 影响行数为 0 说明什么？（数据被改过，冲突，需重试）
- 乐观锁的 CAS 是什么思想？（比较并交换，先比对再更新）

**易错点**

乐观锁实现的关键是「更新时带上版本号/旧值做条件，用影响行数判断冲突」，别漏了「判断影响行数」这一步。

## 302. 什么是数据库死锁？

**面试回答**

死锁是两个或多个事务互相持有对方需要的锁，又都在等待对方释放，形成循环等待，谁都无法继续，导致事务卡死。

**理解**

比如事务 A 锁了行 1 想锁行 2，事务 B 锁了行 2 想锁行 1，两者互相等待对方释放，形成环，谁也不能推进。死锁是并发编程的经典问题，数据库会自动检测死锁并回滚其中一个事务来打破僵局。

**场景**

项目里两个事务以不同顺序更新多行数据时，可能产生死锁，需要合理设计加锁顺序来避免。

**常见追问**

- 死锁产生的条件？（循环等待资源）
- 数据库怎么处理死锁？（自动检测，回滚其中一个事务）

**易错点**

死锁是「互相等待形成环」；数据库会检测并回滚一个事务解决，但业务上要尽量从设计上避免。

## 303. MySQL 为什么会产生死锁？

**面试回答**

因为并发事务以不同顺序申请多个锁，形成「互相持有并等待对方锁」的循环等待，比如 A 锁行1等行2、B 锁行2等行1。

**理解**

死锁的根源是「加锁顺序不一致 + 交叉等待」。常见诱因：①多个事务以不同顺序更新多行；②间隙锁（Gap Lock）在并发插入时也可能产生死锁；③大事务持有锁时间过长。理解了「循环等待」就能从「统一加锁顺序」等方向预防。

**场景**

项目里批量更新订单明细时，若不同事务处理的明细 id 顺序不同，容易死锁；统一按 id 排序处理可降低概率。

**常见追问**

- 怎么预防？（统一加锁顺序、缩短事务、减少锁粒度）
- 间隙锁会导致死锁吗？（会，并发插入场景可能）

**易错点**

死锁根本原因是「循环等待」，而「加锁顺序不一致」是最常见诱因，预防也从这入手。

## 304. 如何降低死锁发生概率？

**面试回答**

统一加锁顺序、缩短事务、减少锁粒度、合理使用索引、避免大事务长时间持锁、及时处理冲突重试。

**理解**

①统一顺序：多个事务访问多行时按相同顺序（如按 id 排序）加锁，避免交叉；②缩短事务：事务越小持锁越短，死锁窗口越小；③减少锁范围：尽量用行锁、走索引，别锁表；④避免在一个事务里既读又写多张表且顺序乱。数据库会自动回滚死锁事务，业务侧要能捕获并重试。

**场景**

项目里批量更新时先按 id 排序，事务内操作尽量精简，减少持锁时间，降低死锁概率。

**常见追问**

- 为什么统一顺序能减少死锁？（打破循环等待）
- 死锁发生了怎么办？（数据库会回滚一个，业务捕获后重试）

**易错点**

降低死锁的核心是「打破循环等待 + 缩短持锁时间」；同时要知道死锁无法完全避免，业务要有重试兜底。
