# SQL基础

## 225. SQL 的执行顺序是什么？

**面试回答**

书写顺序是 SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT，但数据库实际执行顺序是 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT。

**理解**

先确定数据来源（FROM，含 JOIN），再过滤（WHERE），再分组（GROUP BY）、过滤分组（HAVING），然后才做 SELECT 里的字段计算、去重，最后排序（ORDER BY）和分页（LIMIT）。理解执行顺序能解释很多现象，比如「WHERE 里不能用 SELECT 里的别名」。

**场景**

项目里写复杂的菜品统计查询时，按这个顺序思考：先想从哪张表取、怎么过滤、怎么分组，再想查什么字段、怎么排。

**常见追问**

- 为什么 WHERE 不能用聚合函数？（WHERE 在 GROUP BY 之前，聚合还没算出来）
- HAVING 和 WHERE 顺序？（WHERE 先，HAVING 后，见 [[04-MySQL/01-SQL基础#226. `WHERE` 和 `HAVING` 有什么区别？]]）

**易错点**

书写顺序 ≠ 执行顺序；执行顺序里 SELECT 在 WHERE/GROUP BY 之后，所以 WHERE 里不能引用 SELECT 的别名。

## 226. `WHERE` 和 `HAVING` 有什么区别？

**面试回答**

WHERE 在分组前过滤行，作用于原始数据，不能用聚合函数；HAVING 在分组后过滤分组，作用于分组结果，可以用聚合函数。

**理解**

WHERE 针对每一行记录做筛选，发生在 GROUP BY 之前；HAVING 针对分组后的每组做筛选，发生在 GROUP BY 之后，所以能对 `COUNT(*)`、`SUM()` 等聚合结果做条件判断。能用 WHERE 过滤的就先用 WHERE，减少参与分组的行数，性能更好。

**场景**

项目里统计各分类菜品数量时，先 `WHERE status = 1` 过滤有效数据，再 `GROUP BY category`，最后 `HAVING COUNT(*) > 5` 筛出数量大于 5 的分类。

**常见追问**

- 为什么 WHERE 不能接聚合函数？（聚合在分组时才计算，WHERE 在分组前）
- 什么时候必须用 HAVING？（对聚合结果做条件时）

**易错点**

WHERE 过滤「行」、HAVING 过滤「组」；对聚合函数的结果做条件必须用 HAVING。

## 227. `GROUP BY` 有什么作用？

**面试回答**

GROUP BY 按指定列对数据进行分组，把相同值的行归为一组，通常配合聚合函数（COUNT、SUM、AVG 等）对每组做统计。

**理解**

它把「明细数据」聚合成「分组统计」。分组后 SELECT 里一般只能出现「分组列」和「聚合函数」，否则语义不明确。常用于分类统计、去重计数等场景。

**场景**

项目里统计每个菜品分类下的菜品数量：`SELECT category_id, COUNT(*) FROM dish GROUP BY category_id`。

**常见追问**

- GROUP BY 必须和聚合函数一起吗？（不一定，但常配合使用；单独用可去重）
- SELECT 里能随便写非分组列吗？（不能，只能写分组列和聚合函数）

**易错点**

GROUP BY 后 SELECT 的非聚合列必须是分组列，否则可能报错或结果无意义。

## 228. `ORDER BY` 有什么作用？

**面试回答**

ORDER BY 对查询结果按指定列排序，ASC 升序（默认）、DESC 降序，可对多列排序。

**理解**

它是在结果集确定后做排序，排在 SELECT、WHERE 等之后。多列排序时先按第一列排，相同时再按第二列排。排序可能用到索引（如果排序列有索引且顺序匹配）或临时文件排序。

**场景**

项目里菜品列表按价格降序、销量降序排列，分页查询按更新时间倒序，都是 ORDER BY。

**常见追问**

- 默认排序是什么？（ASC 升序）
- ORDER BY 能用别名吗？（能，因为它在 SELECT 之后执行）

**易错点**

ORDER BY 在 SELECT 之后执行，所以能用 SELECT 里的别名；注意排序可能造成额外开销（filesort）。

## 229. `LIMIT` 如何实现分页？

**面试回答**

用 `LIMIT offset, size` 或 `LIMIT size OFFSET offset`：offset 是跳过的记录数，size 是每页条数，配合页码计算实现分页。

**理解**

第 n 页（从 1 开始）的 offset = (n-1) × size。`LIMIT 0,10` 取前 10 条，`LIMIT 10,10` 取第 11 到 20 条。LIMIT 在 ORDER BY 之后执行，所以分页前要先排序。深分页（offset 很大）会慢（见 [[04-MySQL/01-SQL基础#238. 深分页为什么可能比较慢？]]）。

**场景**

项目里菜品分页查询 `LIMIT #{offset}, #{pageSize}`，offset 由页码和每页条数算出。

**常见追问**

- offset 怎么算？（(页码-1) × 每页条数）
- LIMIT 在什么之后执行？（ORDER BY 之后）

**易错点**

LIMIT 是「跳过 offset 条再取 size 条」；深分页 offset 大时性能差，要知道原因。

## 230. INNER JOIN 是什么？

**面试回答**

INNER JOIN 是内连接，只返回两个表中满足连接条件的匹配行，不匹配的行不会出现在结果里。

**理解**

它取两张表的「交集」。连接条件（ON）匹配上的记录才返回，任何一边没有匹配就丢弃。这是最常用的连接类型。

**场景**

项目里查询订单并带出用户信息时，用 INNER JOIN 连接订单表和用户表，只返回有对应用户的订单。

**常见追问**

- INNER JOIN 返回什么？（两表匹配的行）
- 和 LEFT JOIN 区别？（见 [[04-MySQL/01-SQL基础#232. INNER JOIN 和 LEFT JOIN 有什么区别？]]）

**易错点**

INNER JOIN 只保留「匹配成功」的行，不匹配的会丢掉；别以为它会保留某一侧的全部行。

## 231. LEFT JOIN 是什么？

**面试回答**

LEFT JOIN 是左连接，返回左表的所有行，右表匹配不上的用 NULL 填充。

**理解**

它以左表为主，左表每行都会出现；右表有匹配就带上，没有匹配则对应列是 NULL。适合「保留主表全部记录 + 补充关联信息」的场景。

**场景**

项目里查询所有菜品并带出分类名称时，用 LEFT JOIN 连接分类表，菜品即使没分类也能显示（分类名为 NULL）。

**常见追问**

- 左表没匹配右表会怎样？（右表列填 NULL）
- 和 RIGHT JOIN 区别？（主表不同，LEFT 以左表为主）

**易错点**

LEFT JOIN 保证「左表全保留」，右表没匹配补 NULL；这是它和内连接的本质区别。

## 232. INNER JOIN 和 LEFT JOIN 有什么区别？

**面试回答**

INNER JOIN 只返回两表都匹配的行（交集）；LEFT JOIN 返回左表所有行，右表不匹配的补 NULL。

**理解**

关键是「不匹配的行去哪」：内连接丢弃不匹配的行，左连接保留左表不匹配的行（右表补 NULL）。所以 LEFT JOIN 的结果行数 ≥ 左表行数（除非连接条件产生重复），而 INNER JOIN 结果行数 ≤ 两表各自行数。

**场景**

项目里「必须有关联数据」用 INNER JOIN（如订单必须有用户）；「主表记录都要、关联可空」用 LEFT JOIN（如菜品可选分类）。

**常见追问**

- 左表有、右表没有的记录，两者分别怎么处理？（内连接丢弃，左连接保留补 NULL）
- 怎么把 LEFT JOIN 变 INNER JOIN？（加 WHERE 右表字段 IS NOT NULL）

**易错点**

记住核心：内连接取交集，左连接保左表；别搞混「不匹配记录」的去留。

## 233. 什么是子查询？

**面试回答**

子查询是嵌套在另一个 SQL 里的查询，作为外层查询的条件或数据来源，先用内层查询的结果参与外层计算。

**理解**

子查询可以出现在 WHERE（如 `id IN (SELECT ...)`）、FROM（作为临时表）、SELECT 等位置。它让复杂查询能拆成「先查一部分、再查整体」的步骤。但子查询有时性能不如 JOIN，要看具体场景和优化器。

**场景**

项目里查「销量最高的分类」这类需求时，可能用子查询先算分类销量，再筛最大值。

**常见追问**

- 子查询能放哪些位置？（WHERE、FROM、SELECT）
- 子查询和 JOIN 怎么选？（数据量大时 JOIN 常更高效，看优化器）

**易错点**

子查询是「嵌套查询」，不是所有场景都最优；有时 MySQL 会优化，有时 JOIN 更快，别迷信子查询。

## 234. `COUNT(*)` 和 `COUNT(column)` 有什么区别？

**面试回答**

COUNT(*) 统计所有行数（包括 NULL 列的行）；COUNT(column) 只统计该列不为 NULL 的行数。

**理解**

COUNT(column) 会跳过该列为 NULL 的记录，所以结果 ≤ COUNT(*)。COUNT(*) 不关心具体列，统计的是「行数」。要统计总行数用 COUNT(*)，要统计某列非空值个数用 COUNT(column)。

**场景**

项目里统计菜品总数用 COUNT(*)，统计「已填写备注的订单数」用 COUNT(remark)。

**常见追问**

- COUNT(column) 会数 NULL 吗？（不会，跳过 NULL）
- 统计总行数用哪个？（COUNT(*)）

**易错点**

COUNT(column) 不数 NULL 值，COUNT(*) 数所有行，这是两者唯一的本质区别。

## 235. `COUNT(*)` 和 `COUNT(1)` 有什么区别？

**面试回答**

在 MySQL 的 InnoDB 下基本没有区别，都统计总行数，性能几乎一样，COUNT(1) 不会更快。

**理解**

COUNT(1) 是统计「1」这个非空表达式出现的次数，等价于统计行数；COUNT(*) 也是统计行数。现代 MySQL 对两者做了优化，性能差异可忽略。所以不必纠结用哪个，语义上都是「数总行数」，用 COUNT(*) 更直观。

**场景**

项目里统计总行数统一用 COUNT(*)，不必刻意用 COUNT(1)「优化」性能。

**常见追问**

- COUNT(1) 更快吗？（现代 MySQL 下没有明显差别）
- COUNT(主键) 呢？（语义和 COUNT(*) 一样，但可能因读主键略有差异）

**易错点**

「COUNT(1) 比 COUNT(*) 快」是老说法，现代 MySQL 里两者基本等价，别当优化手段去背。

## 236. `DELETE`、`TRUNCATE`、`DROP` 有什么区别？

**面试回答**

DELETE 删除表中数据（可带 WHERE 删部分行），保留表结构，可回滚、有日志；TRUNCATE 清空整表数据，保留表结构，不可回滚、速度快；DROP 直接删除整张表（结构和数据都没了）。

**理解**

三者删除的层级和后果不同：DELETE 是「删行」，最灵活但慢；TRUNCATE 是「清空表」，快但不可恢复；DROP 是「删表」，最彻底。它们对事务、自增计数的影响也不同（TRUNCATE 会重置自增，DELETE 不会）。

**场景**

项目里删单个菜品用 DELETE（带 WHERE）；清空测试数据可用 TRUNCATE；删除废弃表用 DROP。

**常见追问**

- 哪个能回滚？（DELETE 能，TRUNCATE/DROP 通常不能）
- 哪个重置自增主键？（TRUNCATE 会重置，DELETE 不会）

**易错点**

DELETE/TRUNCATE 删「数据」保留表，DROP 删「整张表」；TRUNCATE 不可回滚且重置自增，别误用。

## 237. UNION 和 UNION ALL 有什么区别？

**面试回答**

UNION 合并两个查询结果并去重；UNION ALL 直接合并不去重，保留所有行（包括重复行）。

**理解**

UNION 会对结果做去重（可能涉及排序/哈希），有额外开销；UNION ALL 只是简单拼接，性能更好。如果确定结果不会重复或允许重复，用 UNION ALL。两者都要求各查询的列数和类型一致。

**场景**

项目里合并不同条件查出的列表时，允许重复用 UNION ALL；需要去重用 UNION。

**常见追问**

- 哪个快？（UNION ALL 快，因为不去重）
- 两者对列的要求？（列数、类型要一致）

**易错点**

UNION 去重、UNION ALL 不去重；性能上 UNION ALL 更好，别默认都用 UNION。

## 238. 深分页为什么可能比较慢？

**面试回答**

因为 `LIMIT offset, size` 的 offset 很大时，数据库要先取出并丢弃前面的 offset 条记录，扫描的数据量很大，offset 越大越慢。

**理解**

比如 `LIMIT 1000000, 10`，数据库不是直接跳到第 100 万条，而是要把前 100 万条都扫描/排序后丢掉，再返回 10 条，IO 和 CPU 开销巨大。深分页优化常用「延迟关联」或「记录上次查询的游标/主键」的方式。

**场景**

项目里订单列表翻到很后面时，如果还用 `LIMIT offset, size` 会越来越慢，可用「记录上一页最后一条 id，用 `WHERE id > lastId LIMIT size`」来优化。

**常见追问**

- 深分页优化方法？（延迟关联、基于主键游标 WHERE id > lastId）
- 为什么游标方式快？（能用索引定位，不用扫前面大量数据）

**易错点**

深分页慢的本质是「要扫描并丢弃大量前面的数据」，不是 LIMIT 本身慢；优化思路是避免扫描前面数据。
