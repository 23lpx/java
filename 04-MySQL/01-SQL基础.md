# SQL基础

## 225. SQL 的执行顺序是什么？

**面试回答**

面试常说的逻辑处理顺序是 `FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT`。它用于理解名称可见性和结果语义，不等于 MySQL 真实的物理执行顺序；优化器可以重写查询、调整连接顺序并选择不同执行计划。

**原理与理解**

先形成数据源并按行过滤，再分组和过滤组，之后计算选择列表，最后排序和截取。MySQL 允许 SELECT 别名用于 `GROUP BY`、`HAVING`、`ORDER BY`，但 WHERE 判断时选择列表的值尚未形成。

**成立条件与边界**

该口诀会省略窗口函数、CTE、子查询和集合操作，也不能用来推断索引访问顺序。真实性能必须看 `EXPLAIN`/`EXPLAIN ANALYZE` 和实际执行指标。

**实际场景（通用工程）**

排查“WHERE 为什么不能引用 SELECT 别名”时用逻辑顺序解释；排查慢 SQL 时改看执行计划，不能把逻辑顺序当执行计划。

**常见追问**

- WHERE 与 HAVING 的阶段差异？——见 [[04-MySQL/01-SQL基础#226. `WHERE` 和 `HAVING` 有什么区别？]]。
- JOIN 一定先按书写顺序执行吗？——不一定，优化器可在语义等价前提下重排。

**易错点**

不要回答“数据库一定严格按这条链执行”，它只是逻辑语义模型。

## 226. `WHERE` 和 `HAVING` 有什么区别？

**面试回答**

`WHERE` 在分组和聚合前过滤输入行，不能直接使用聚合函数；`HAVING` 在分组后过滤分组结果，可以判断 `COUNT`、`SUM` 等聚合值。MySQL 中 HAVING 也可以在没有 GROUP BY 时使用。

**原理与理解**

能提前用 WHERE 排除的行通常应先排除，以减少后续连接或聚合的数据量。HAVING 面向聚合后的组，并可引用选择列表别名，这是 MySQL 支持的名称解析规则。

**成立条件与边界**

“WHERE 一定比 HAVING 快”不严谨，优化器可能下推等价条件；包含聚合、别名或语义不等价的条件不能随意移动。NULL 还遵循三值逻辑。

**实际场景（通用工程）**

统计有效菜品分类数量时先用 WHERE 过滤状态，再 GROUP BY 分类，最后用 HAVING 筛选数量达到阈值的分类。

**常见追问**

- HAVING 能过滤普通列吗？——语法上可能，但应先判断能否语义等价地下推到 WHERE。
- WHERE 为什么不能写 `COUNT(*) > 5`？——此时分组聚合尚未形成。

**易错点**

不要只背“WHERE 过滤行、HAVING 过滤组”而忽略无 GROUP BY 的 HAVING 和优化器下推。

## 227. `GROUP BY` 有什么作用？

**面试回答**

`GROUP BY` 按一个或多个表达式把输入行划分为组，通常与聚合函数一起把明细转换为每组一行的统计结果。

**原理与理解**

开启 MySQL 默认的 `ONLY_FULL_GROUP_BY` 时，SELECT、HAVING、ORDER BY 中的非聚合表达式必须是分组列，或能被 MySQL判定为函数依赖于分组列；因此并非机械地“SELECT 只能写分组列和聚合函数”。

**成立条件与边界**

GROUP BY 本身不保证结果顺序，想稳定排序必须显式 ORDER BY。仅为去重时通常用 DISTINCT 更能表达意图；复杂聚合还要关注临时表、排序和索引。

**实际场景（通用工程）**

按订单状态统计数量时，以状态分组并 COUNT；若还选择其他字段，要确认它由分组键唯一决定。

**常见追问**

- GROUP BY 后能选非分组列吗？——只有满足聚合或函数依赖等规则时才合法。
- GROUP BY 会自动排序吗？——不能依赖，排序必须写 ORDER BY。

**易错点**

关闭 `ONLY_FULL_GROUP_BY` 后拿到某组“任意一行”的非聚合值，不代表 SQL 语义正确。

## 228. `ORDER BY` 有什么作用？

**面试回答**

`ORDER BY` 按一个或多个表达式对最终结果排序，`ASC` 为默认升序，`DESC` 为降序；多列排序按从左到右的优先级依次比较。

**原理与理解**

MySQL 可能利用顺序匹配的索引直接产出有序结果，也可能执行 filesort。filesort 是额外排序算法的统称，不等于一定写磁盘。

**成立条件与边界**

没有 ORDER BY 时行顺序没有契约；分页若排序键不唯一，同值行之间仍可能漂移。NULL、字符排序和大小写行为受方向与 collation 影响。

**实际场景（通用工程）**

订单列表可按 `create_time DESC, id DESC` 排序，用唯一 ID 作为最终 tie-breaker，保证分页顺序确定。

**常见追问**

- ORDER BY 能使用 SELECT 别名吗？——MySQL 可以。
- 出现 filesort 就一定慢吗？——不一定，要看行数、内存、排序键和 LIMIT。

**易错点**

不要把主键或当前执行计划呈现的顺序当作无 ORDER BY 时的稳定结果。

## 229. `LIMIT` 如何实现分页？

**面试回答**

MySQL 支持 `LIMIT offset, row_count` 或 `LIMIT row_count OFFSET offset`；第 n 页、每页 s 条时，常用偏移量为 `(n - 1) × s`。

**原理与理解**

ORDER BY 先确定逻辑顺序，LIMIT 再截取其中一段。应用还应返回总数、是否有下一页或游标信息，具体取决于产品分页契约。

**成立条件与边界**

页码必须校验为正数并限制 pageSize；没有确定性 ORDER BY 会导致重复或遗漏。OFFSET 越大通常需要读取并丢弃越多候选行，见 [[04-MySQL/01-SQL基础#238. 深分页为什么可能比较慢？]]。

**实际场景（真实项目边界）**

简历确认项目完成了分页查询，但未确认是手写 LIMIT 还是 PageHelper；面试时只陈述已核验的具体实现。

**常见追问**

- OFFSET 从几开始？——从 0 开始。
- 为什么分页必须排序？——否则每次返回的行集合和顺序没有稳定保证。

**易错点**

`LIMIT 10, 20` 表示跳过 10 条、取 20 条，不是第 10 页取 20 条。

## 230. INNER JOIN 是什么？

**面试回答**

INNER JOIN 组合两侧满足 ON 条件的行；任一侧没有匹配就不产生该组合。`JOIN`、`INNER JOIN` 和 `CROSS JOIN` 在 MySQL 语法上可有重叠，但工程上应显式写 ON 表达连接关系。

**原理与理解**

连接不是简单“取两个表的交集”，而是按连接谓词生成匹配的行组合。一对多、多对多关系会使一行匹配多行，结果数可能超过任一输入表。

**成立条件与边界**

连接条件缺失或过宽会造成笛卡尔积；ON 与 WHERE 对内连接常可等价改写，但对外连接不一定。优化器可选择嵌套循环、哈希连接等实现。

**实际场景（通用工程）**

查询订单及其明细时，订单主键与明细关联列匹配；一个订单有多条明细，因此结果会展开为多行。

**常见追问**

- INNER JOIN 与 LEFT JOIN 的结果差异？——见 [[04-MySQL/01-SQL基础#232. INNER JOIN 和 LEFT JOIN 有什么区别？]]。
- 结果行数一定小于两张表吗？——不一定，多对多连接可明显放大。

**易错点**

“内连接就是集合交集”只能帮助入门，不能解释重复键和结果基数。

## 231. LEFT JOIN 是什么？

**面试回答**

LEFT JOIN 返回左侧每一行与右侧所有匹配行的组合；若右侧没有匹配，则仍保留左侧行，并把右侧列补为 NULL。

**原理与理解**

外连接先按 ON 判断匹配，再为未匹配的左行补 NULL。右表一对多时，同一左行会产生多条结果，LEFT JOIN 不保证“一条左行只返回一次”。

**成立条件与边界**

把右表过滤条件放进 WHERE，可能过滤掉补 NULL 的行，使结果表现得像内连接；若希望保留左表未匹配行，通常把右表匹配条件写在 ON 中并核对语义。

**实际场景（通用工程）**

查询所有分类及其菜品数量时，可 LEFT JOIN 菜品；没有菜品的分类仍保留，但 COUNT 时要统计右表非空主键而非 COUNT(*)。

**常见追问**

- ON 与 WHERE 对 LEFT JOIN 有何差异？——ON 决定匹配，WHERE 再过滤连接结果。
- 右表多行匹配怎么办？——结果会展开，需要聚合或业务层按关系处理。

**易错点**

“左表全部保留”只在没有后续 WHERE、HAVING、DISTINCT 等再次改变结果的前提下成立。

## 232. INNER JOIN 和 LEFT JOIN 有什么区别？

**面试回答**

INNER JOIN 只保留满足连接条件的组合；LEFT JOIN 还保留没有右侧匹配的左行，并将右侧列置为 NULL。选择依据是业务是否允许关联缺失，而不是性能口诀。

**原理与理解**

两者的核心差异发生在未匹配行。对于只引用右表的过滤条件，写在 LEFT JOIN 的 ON 中与写在 WHERE 中可能得到不同结果。

**成立条件与边界**

不能声称 INNER JOIN 结果数一定不超过输入表：重复键可放大结果。优化器能否把外连接化简为内连接，也取决于后续条件是否拒绝 NULL。

**实际场景（通用工程）**

“只看有明细的订单”可用 INNER JOIN；“订单都展示，即使明细暂缺”才适合 LEFT JOIN，并处理 NULL。

**常见追问**

- LEFT JOIN 后 WHERE `right.id IS NOT NULL` 会怎样？——通常排除未匹配行，语义接近内连接。
- 哪个一定更快？——没有固定答案，要看基数、索引、选择性和执行计划。

**易错点**

JOIN 类型首先表达数据语义，不能为所谓性能随意互换。

## 233. 什么是子查询？

**面试回答**

子查询是嵌入其他语句的查询，可作为标量值、行值、`IN/EXISTS` 条件或 FROM 中的派生表；引用外层列的叫关联子查询。

**原理与理解**

MySQL 优化器可能把子查询转换为半连接、物化结果或其他等价计划，因此“子查询一定先执行”或“JOIN 一定更快”都不成立。

**成立条件与边界**

标量子查询必须最多返回一行；`NOT IN` 遇到 NULL 可能产生 UNKNOWN，反连接场景常需明确 NULL 语义。关联子查询是否逐行执行要看最终计划。

**实际场景（通用工程）**

筛选“存在未支付明细的订单”可使用 EXISTS；若改 JOIN，要避免一对多导致订单重复。

**常见追问**

- EXISTS 与 IN 怎么选？——先保证 NULL 和重复语义正确，再用执行计划与数据验证。
- 派生表是什么？——FROM 中的子查询结果，可被合并或物化。

**易错点**

不要用固定口诀判断子查询性能，优化器转换和数据分布才决定计划。

## 234. `COUNT(*)` 和 `COUNT(column)` 有什么区别？

**面试回答**

`COUNT(*)` 统计结果中的行数；`COUNT(column)` 统计该表达式非 NULL 的行数。因此后者可能更小，区别是 NULL 语义，不是“星号会读取所有列”。

**原理与理解**

COUNT 是聚合函数。对 LEFT JOIN 结果，COUNT(*) 会把补 NULL 的外连接行也算入，而 `COUNT(right.id)` 只统计确实匹配且该列非 NULL 的右行。

**成立条件与边界**

`COUNT(DISTINCT expr)` 还会去重并忽略 NULL。性能依赖引擎、可用索引、过滤条件和统计信息，不能仅凭写法判断。

**实际场景（通用工程）**

统计每个分类的菜品数时，LEFT JOIN 后应 COUNT 非空的菜品主键；否则没有菜品的分类也会被 COUNT(*) 统计为 1。

**常见追问**

- COUNT 可空列会怎样？——NULL 行不计入。
- COUNT(*) 会展开所有列吗？——不会，它表达计数行。

**易错点**

`COUNT(column)` 统计的不是“这一列共有多少行”，而是这一表达式有多少个非 NULL 结果。

## 235. `COUNT(*)` 和 `COUNT(1)` 有什么区别？

**面试回答**

在 MySQL 中两者都统计行数：`1` 是恒为非 NULL 的常量，因此结果相同；通常没有值得依赖的性能差异，语义上优先使用 COUNT(*)。

**原理与理解**

优化器和存储引擎会选择合适的访问方式。InnoDB 对无条件 COUNT(*) 不保存精确总行数，通常仍需扫描可见记录，可选择较小的二级索引降低读取量。

**成立条件与边界**

带 WHERE、事务可见性、索引覆盖和并发版本都会影响成本。COUNT(可空列) 才与 COUNT(*) 有结果差异；COUNT(非空主键) 结果相同但不保证计划完全相同。

**实际场景（通用工程）**

分页总数查询统一写 COUNT(*)，然后通过 EXPLAIN、索引和是否确实需要精确总数来优化。

**常见追问**

- COUNT(1) 会少读一列所以更快吗？——这种解释不成立。
- InnoDB 能 O(1) 返回精确行数吗？——通常不能，MVCC 下各事务可见行数可能不同。

**易错点**

不要把 COUNT(1) 当“性能优化技巧”，先优化过滤和访问路径。

## 236. `DELETE`、`TRUNCATE`、`DROP` 有什么区别？

**面试回答**

DELETE 是删除行的 DML，可带 WHERE；InnoDB 事务内通常可回滚。TRUNCATE TABLE 是快速清空整表的 DDL，会隐式提交、不能像 DELETE 那样回滚，并重置 AUTO_INCREMENT。DROP TABLE 删除表定义及其数据，也属于会隐式提交的 DDL。

**原理与理解**

DELETE 逐行产生事务性修改、锁和日志；TRUNCATE 通常丢弃并重建表空间/表对象，MySQL 将其视为 DDL；DROP 直接移除对象。

**成立条件与边界**

“DELETE 一定可回滚”只适用于支持事务的引擎且尚未提交；TRUNCATE 会受外键引用限制。MySQL 8 的原子 DDL强调崩溃后的原子性，不等于用户事务中可 ROLLBACK。

**实际场景（通用工程）**

业务删除必须带明确条件并走事务；清理测试环境整表数据可评估 TRUNCATE；DROP 只用于确认废弃的对象和受控迁移。

**常见追问**

- TRUNCATE 能触发 DELETE 触发器吗？——不能按 DELETE 语句理解，应查具体 DDL行为。
- 哪些会隐式提交？——TRUNCATE、DROP 等 DDL 会。

**易错点**

不要笼统回答“TRUNCATE/DROP 不写日志”，它们仍有 DDL、redo/binlog 等持久化行为。

## 237. UNION 和 UNION ALL 有什么区别？

**面试回答**

`UNION` 默认等同 `UNION DISTINCT`，合并各查询结果后去重；`UNION ALL` 保留重复行，通常少一步去重工作。

**原理与理解**

各分支必须返回相同列数，结果列类型由对应位置协商；最终列名通常取自第一个查询。整个集合结果的 ORDER BY/LIMIT 应放在集合表达式外层。

**成立条件与边界**

是否使用 UNION ALL 由重复语义决定，不能只因更快就替换 UNION。混用 DISTINCT 与 ALL、分支内排序和 LIMIT 时要用括号明确作用域。

**实际场景（通用工程）**

合并“堂食订单”和“外卖订单”且两集合业务上互斥时可用 UNION ALL；若来源可能重叠且结果要求唯一，再用 UNION 或显式去重。

**常见追问**

- UNION 为什么通常更贵？——需要识别并移除重复行。
- 两个分支列名不同怎么办？——按位置合并，最终名称通常来自首个查询。

**易错点**

UNION 去重的是整行组合，不是只按某一列去重。

## 238. 深分页为什么可能比较慢？

**面试回答**

`LIMIT offset, size` 的 offset 很大时，MySQL 通常仍要沿访问路径找到、排序或读取前 offset + size 个候选，再丢弃前 offset 个；偏移越深，CPU、I/O 和回表成本往往越高。

**原理与理解**

若 ORDER BY 能用覆盖索引，成本可下降但仍需跨过大量索引项。Seek/Keyset 分页把上一页最后的排序键作为边界，让索引从边界继续扫描。

**成立条件与边界**

Seek 分页要求稳定、可比较且最好唯一的排序键，复合排序要写词典序边界；它不支持任意跳页，数据并发变化时也需定义一致性。延迟关联不是所有 SQL 都更快。

**实际场景（项目核验项）**

简历只确认项目实现分页查询，未确认存在深分页优化；若订单量增长，可按 `create_time DESC, id DESC` 设计复合游标并用真实数据压测。

**常见追问**

- 为什么 `id > lastId` 不总正确？——只有排序方向、过滤条件和 ID 语义与查询一致时才成立。
- 如何确认瓶颈？——看 EXPLAIN ANALYZE、扫描行数、回表和排序指标。

**易错点**

深分页慢不是 LIMIT 关键字本身慢，而是访问并丢弃大量前置结果。
