# 索引

## 249. 什么是数据库索引？

**面试回答**

索引是数据库为加速查询而建立的一种数据结构，类似书的目录，能帮数据库快速定位数据，而不必全表扫描。

**理解**

索引存储了「索引列的值 → 对应数据位置」的映射，通常用 B+Tree 等结构组织，让查询能按值快速查找。它是有序的，所以能加速等值、范围、排序查询。索引本质是「用额外的存储和维护开销，换取查询速度」。

**场景**

项目里在常用查询字段（主键、外键、状态、分类等）上建索引，加速菜品、订单的查询。

**常见追问**

- 索引本质是什么？（一种有序的数据结构，加速查找）
- 索引是越多越好吗？（不是，见 [[04-MySQL/03-索引#252. 索引是不是越多越好？]]）

**易错点**

索引是「空间换时间」，有维护成本；不是「有了索引就一定快」，要看是否命中。

## 250. 索引为什么能提高查询速度？

**面试回答**

因为索引是「有序的数据结构」，查询时能按值快速定位（如 B+Tree 的二分查找），把全表扫描的 O(n) 降为接近 O(log n)，大幅减少需要扫描的数据量。

**理解**

没有索引，查一条记录要逐行比对（全表扫描）。有索引，数据库按索引树从根到叶子快速定位到目标值的位置，只访问少量节点。索引的有序性还支持范围查询和排序，不用临时排序。

**场景**

项目里按主键查菜品 O(log n) 直接定位；按加了索引的状态字段过滤，不用扫全表。

**常见追问**

- 索引为什么快？（有序结构 + 快速定位，避免全表扫描）
- B+Tree 查找复杂度？（接近 O(log n)，且树很矮、磁盘 IO 少）

**易错点**

索引快的前提是「查询能用上索引」；用不上索引（索引失效）就还是全表扫描。

## 251. 索引有什么缺点？

**面试回答**

①占用额外存储空间；②增删改数据时索引也要同步维护，写操作变慢；③索引太多会增加优化器选择和内存负担。

**理解**

索引是「空间换时间」：存储要占磁盘，插入/更新/删除时每维护一个索引就多一份开销。索引越多，写入越慢、占空间越多。所以建索引要克制，只为高频查询字段建，避免为不常用或低区分度的字段建无用索引。

**场景**

项目里只对高频查询字段建索引，不会给每列都建，避免拖慢写入、浪费空间。

**常见追问**

- 为什么索引会让写变慢？（每次增删改都要维护索引树）
- 低区分度字段（如性别）适合建索引吗？（不适合，区分度低，索引收益小）

**易错点**

索引的代价是「空间 + 写性能」，所以不是越多越好，要权衡查询和写入。

## 252. 索引是不是越多越好？

**面试回答**

不是。索引越多，占用空间越大，写入（增删改）越慢，还增加优化器选择负担，所以只为高频、高区分度的查询字段建索引即可。

**理解**

每个索引都要占磁盘、都要在数据变更时维护。索引太多，写操作退化明显，还可能让优化器选错索引。正确做法是分析实际查询，为 WHERE、JOIN、ORDER BY 里常用的、区分度高的字段建索引，避免冗余和低效索引。

**场景**

项目里根据真实查询场景建索引（如菜品按分类、状态查询），不会盲目给每列都建。

**常见追问**

- 什么字段适合建索引？（高频查询、高区分度、常用于 WHERE/JOIN/ORDER BY）
- 冗余索引问题？（浪费空间、拖慢写入）

**易错点**

索引「按需建、克制建」，多了反而有害；别以为索引越多查询越快。

## 253. InnoDB 为什么使用 B+Tree？

**面试回答**

因为 B+Tree 树很矮（多层节点、每层能存很多键），磁盘 IO 次数少；且叶子节点用链表相连，天然支持范围查询和顺序遍历，非常适合磁盘存储和范围检索。

**理解**

数据库数据在磁盘上，性能瓶颈主要是磁盘 IO。B+Tree 每个节点能存大量键（高扇出），3~4 层就能支撑千万级数据，查一条数据只需几次 IO。叶子节点之间还有双向链表，范围查询（如 `id > 100`）直接顺着链表走，高效。所以 InnoDB 选它。

**场景**

项目里按主键、范围（如分页、按时间区间查订单）查询时，B+Tree 都能高效支持。

**常见追问**

- B+Tree 为什么矮？（每个节点存很多键，扇出大）
- 叶子节点链表有什么用？（支持范围查询和顺序遍历）

**易错点**

InnoDB 用 B+Tree 的核心原因是「减少磁盘 IO + 支持范围查询」，要能联系磁盘存储来理解。

## 254. 为什么不用普通二叉树？

**面试回答**

普通二叉树每个节点只存一个键、只有两个子节点，数据量大时树会非常高，导致查找需要大量磁盘 IO，性能很差。

**理解**

二叉树高度是 O(log₂n)，但基数小，n 很大时高度依然很高（比如 100 万数据高度约 20），而每个节点可能在不同磁盘页，20 次 IO 太慢。B+Tree 每个节点存很多键（比如几百个），同样的数据量树高只有 3~4 层，IO 次数大幅减少。这是「为磁盘优化」的设计。

**场景**

理解这个对比，就能明白为什么数据库索引不用二叉树、红黑树，而用 B+Tree。

**常见追问**

- 二叉树高有什么问题？（IO 次数多，慢）
- 为什么数据库关心树高？（每层访问可能就是一次磁盘 IO）

**易错点**

核心是「树高 → 磁盘 IO 次数」；二叉树太高导致 IO 多，所以不适合磁盘索引。

## 255. 为什么不用 Hash 作为主要索引结构？

**面试回答**

Hash 索引等值查询很快（O(1)），但不支持范围查询、排序，也无法用于最左前缀匹配等场景，所以不能作为主要索引结构。

**理解**

Hash 索引把键算成哈希值直接定位，等值查询极快；但哈希无序，`id > 100`、`ORDER BY`、`LIKE` 这类范围/排序/模糊查询都用不了。而实际业务里范围查询很常见，所以 InnoDB 主要用 B+Tree，Hash 只在特定场景（如自适应哈希、MEMORY 引擎）作为补充。

**场景**

项目里订单按时间范围、金额区间查询很常见，B+Tree 能支持；Hash 索引做不到。

**常见追问**

- Hash 索引擅长什么？（等值查询）
- Hash 索引不能做什么？（范围、排序、前缀匹配）

**易错点**

Hash 不是「慢」，是「只擅长等值、不支持范围」；别把 Hash 说成一无是处，也别认为它能替代 B+Tree。

## 256. B+Tree 为什么能减少磁盘 IO？

**面试回答**

因为 B+Tree 每个节点能存大量键（高扇出），树的高度很低，查找时只需访问少数几个节点（几次磁盘 IO），就能定位到数据。

**理解**

磁盘 IO 是性能瓶颈。B+Tree 一个节点通常占一页（16KB），能存几百上千个键和指针，所以几层就能索引千万级数据。查一条数据从根到叶子只访问 3~4 个节点，即 3~4 次 IO。相比二叉树几十层几十次 IO，IO 次数大幅减少。

**场景**

项目里百万级菜品、订单表，主键查询只需几次磁盘 IO 就能返回，这就是 B+Tree 的价值。

**常见追问**

- 一个节点能存多少键？（取决于页大小和键大小，通常几百个）
- 为什么节点大反而 IO 少？（一页读出更多键，树更矮）

**易错点**

B+Tree 减 IO 的本质是「高扇出 → 矮树 → 少访问节点」，要联系「一页一个节点」理解。

## 257. B+Tree 为什么适合范围查询？

**面试回答**

因为 B+Tree 的所有数据都在叶子节点，且叶子节点之间用双向链表按顺序相连，找到起点后顺着链表就能顺序取出一个范围内的所有数据。

**理解**

范围查询如 `id BETWEEN 100 AND 200`：先在 B+Tree 里定位到 100 的位置，然后沿叶子链表向后遍历到 200，一次遍历取出一整段，效率高。这种「有序叶子 + 链表」的结构是 B+Tree 相对 B-Tree、Hash 的独特优势。

**场景**

项目里分页查询、按时间区间查订单、按价格区间查菜品，都是 B+Tree 范围查询的典型应用。

**常见追问**

- 叶子链表方向？（双向链表，可正序也可倒序）
- 为什么 Hash 不能范围查询？（哈希无序）

**易错点**

B+Tree 范围查询靠「有序叶子 + 链表」，这是它区别于 B-Tree（数据分散在非叶节点）和 Hash 的关键。

## 258. 什么是聚簇索引？

**面试回答**

聚簇索引是一种「索引和数据存一起」的存储方式：表数据按聚簇索引（主键）的顺序物理存储，叶子节点直接保存整行数据。InnoDB 的主键索引就是聚簇索引。

**理解**

「聚簇」指数据行和索引「聚」在一起。InnoDB 把表数据按主键组织成一棵 B+Tree，叶子节点存的就是完整行记录。所以主键决定了数据的物理顺序，主键查找能直接拿到整行数据，不用再回表。每张 InnoDB 表只能有一个聚簇索引（因为数据只能按一种顺序存）。

**场景**

项目里按主键 id 查菜品，走聚簇索引，叶子节点直接就是整行数据，一次定位即得。

**常见追问**

- 聚簇索引的叶子存什么？（整行数据）
- 一张表能有几个聚簇索引？（一个，通常是主键）

**易错点**

聚簇索引「索引即数据」；主键索引 = 聚簇索引，数据就存在它的叶子节点里，这是 InnoDB 的核心特点。

## 259. InnoDB 主键索引叶子节点保存什么？

**面试回答**

保存整行的数据记录（所有列的值），因为主键索引就是聚簇索引，数据就存在主键 B+Tree 的叶子节点里。

**理解**

InnoDB 表数据按主键聚簇存储，主键索引树（聚簇索引）的叶子节点直接就是完整的数据行，包含该行的所有列。所以通过主键查询，定位到叶子节点就同时拿到了整行数据，无需额外回表。

**场景**

项目里 `SELECT * FROM dish WHERE id = 5` 走主键索引，叶子节点直接返回整行菜品数据。

**常见追问**

- 主键索引叶子是数据还是指针？（是完整数据行）
- 和二级索引叶子有什么不同？（二级索引叶子存主键值，见 [[04-MySQL/03-索引#261. 二级索引叶子节点保存什么？]]）

**易错点**

主键索引（聚簇索引）叶子存「整行数据」，二级索引叶子存「主键值」，这是理解回表的关键区别。

## 260. 什么是二级索引？

**面试回答**

二级索引（辅助索引/非聚簇索引）是主键索引之外建立的索引，叶子节点存的是「索引列的值 + 对应主键值」，而不是整行数据。

**理解**

InnoDB 里除了主键索引（聚簇索引），其他索引都是二级索引。它们也按 B+Tree 组织，但叶子只存「索引列 + 主键」。通过二级索引查到主键后，如果还需要其他列，就要拿主键再去主键索引里查完整数据（回表）。

**场景**

项目里给菜品表的 category_id 建二级索引，查某分类的菜品时先通过它定位主键，再回表拿完整数据。

**常见追问**

- 二级索引叶子存什么？（索引列值 + 主键值）
- 二级索引查询一定回表吗？（不一定，覆盖索引可避免，见 [[04-MySQL/03-索引#263. 什么是覆盖索引？]]）

**易错点**

二级索引 = 非主键索引，叶子存「索引值 + 主键」，是「回表」现象的来源。

## 261. 二级索引叶子节点保存什么？

**面试回答**

保存「索引列的值」和「该行对应的主键值」，不保存整行其他列的数据。

**理解**

二级索引叶子只记录：这个索引值对应哪条记录（用主键标识）。所以通过二级索引查询时，只能直接拿到「索引列」和「主键」，如果 SELECT 还需要其他列，就必须用主键回表查聚簇索引。这也是「覆盖索引能避免回表」的原因。

**场景**

项目里 category_id 二级索引的叶子存 (category_id, id)，查分类下的菜品 id 时能直接取到，但取菜名等其他字段要回表。

**常见追问**

- 为什么叶子存主键不存数据？（避免数据冗余，数据只存一份在聚簇索引）
- 存主键有什么好处？（数据变更时不用更新所有索引）

**易错点**

二级索引叶子「存主键」是 InnoDB 的设计，既省空间又让数据只有一份，代价就是可能需要回表。

## 262. 什么是回表？

**面试回答**

回表指通过二级索引查到主键后，还需要再回到主键索引（聚簇索引）里查一次，才能拿到完整的行数据。

**理解**

二级索引叶子只存「索引列 + 主键」。如果查询需要的列不都在二级索引里，就要拿主键再去聚簇索引查一次完整数据，这多出来的一次查找就是「回表」。回表会增加 IO，所以有时用覆盖索引来避免。

**场景**

项目里 `SELECT name, price FROM dish WHERE category_id = 3`，category_id 索引只能拿到主键，还要回表查 name、price。

**常见追问**

- 回表有什么代价？（多一次索引查找，增加 IO）
- 怎么避免回表？（覆盖索引，见 [[04-MySQL/03-索引#263. 什么是覆盖索引？]]）

**易错点**

回表是「二级索引 → 主键索引」的额外查找；不是所有二级索引查询都回表，覆盖索引就不用。

## 263. 什么是覆盖索引？

**面试回答**

覆盖索引指查询需要的列全部包含在索引里，通过索引就能直接拿到所需数据，不需要再回表。

**理解**

如果 `SELECT` 的列都在某个索引的「索引列 + 主键」范围内，那么这个索引就「覆盖」了查询，直接从二级索引叶子取数据即可，省去回表。这是常见的查询优化手段。

**场景**

项目里 `SELECT id, category_id FROM dish WHERE category_id = 3`，category_id 索引就覆盖了（叶子有 category_id 和 id），不用回表。

**常见追问**

- 覆盖索引为什么快？（不用回表，少一次 IO）
- 怎么构造覆盖索引？（把查询所需列建进联合索引）

**易错点**

覆盖索引的前提是「查询列都在索引里」；它能避免回表，是索引优化的常见手段。

## 264. 覆盖索引为什么可以提高查询效率？

**面试回答**

因为它避免了回表：查询所需数据都在索引里，直接读索引叶子就能返回，少了一次「二级索引 → 主键索引」的额外查找和磁盘 IO。

**理解**

回表是多一次索引遍历。覆盖索引让查询「只访问一个索引」就完成，IO 次数更少，速度更快。尤其当回表代价高（数据量大、行分散）时，覆盖索引的收益明显。所以设计索引时尽量让索引覆盖常用查询的字段。

**场景**

项目里为高频查询设计联合索引，把 SELECT 需要的字段都放进索引，避免回表，提升查询性能。

**常见追问**

- 覆盖索引省的是什么？（省掉回表那次查找）
- 联合索引和覆盖索引关系？（常通过联合索引实现覆盖）

**易错点**

覆盖索引的收益来自「免回表」，本质是减少磁盘 IO；要理解它和回表的关系。

## 265. 什么是联合索引？

**面试回答**

联合索引（复合索引）是在多个列上建立的索引，如 `(a, b, c)`，按列顺序组成一个索引，查询时需遵循最左匹配原则。

**理解**

联合索引把多列按顺序组织成一个 B+Tree：先按 a 排，a 相同再按 b 排，以此类推。它能同时优化「a 单独查」和「a+b」「a+b+c」的查询，但单独查 b 或 c 通常用不上。联合索引是覆盖索引、多条件查询优化的基础。

**场景**

项目里常按「状态 + 分类」查菜品，就建 (status, category_id) 联合索引。

**常见追问**

- 联合索引能优化哪些查询？（最左前缀：a、a+b、a+b+c）
- 单独查 b 能用联合索引吗？（通常不能，见 [[04-MySQL/03-索引#266. 什么是最左匹配原则？]]）

**易错点**

联合索引的「列顺序」很重要，决定了哪些查询能命中，要理解最左匹配。

## 266. 什么是最左匹配原则？

**面试回答**

最左匹配指联合索引 `(a,b,c)` 使用时，查询条件必须从最左边的列 a 开始连续匹配，才能用到索引；跳过 a 直接查 b、c 通常用不上这个索引。

**理解**

联合索引是按 (a, b, c) 的顺序组织的，只有提供了 a 才能确定在索引中的大致位置，再进一步用 b、c 缩小范围。所以 `a`、`a+b`、`a+b+c` 能命中，`b`、`c`、`b+c` 通常不命中。范围查询会中断后续列的匹配（如 a 用范围后，b 可能失效）。

**场景**

项目里 (status, category_id, price) 联合索引：查 status 命中，查 status+category_id 命中，但单独查 category_id 不命中。

**常见追问**

- 为什么必须从最左开始？（索引按最左列优先排序）
- 范围查询对最左匹配有什么影响？（范围列之后的列通常失效）

**易错点**

最左匹配是「从最左列连续匹配」；不是「只要包含最左列就行」，中间跳列会导致后面列失效。

## 267. 联合索引 `(a,b,c)` 哪些查询可以使用索引？

**面试回答**

能命中：`a`、`a + b`、`a + b + c`；通常不能命中（或只能部分命中）：单独 `b`、单独 `c`、`b + c`；范围查询会中断后续列。

**理解**

最左匹配原则下，查询条件必须从 a 开始连续匹配。`WHERE a=1` 能命中；`WHERE a=1 AND b=2` 命中 a、b；`WHERE a=1 AND b=2 AND c=3` 全部命中。而 `WHERE b=2` 因为跳过了 a，用不上索引（除非覆盖索引走扫描）。注意 `WHERE a=1 AND c=3` 只能用上 a，c 用不上（中间缺 b）。范围：`a>1 AND b=2` 只有 a 能用，b 失效。

**场景**

项目里设计 (status, category_id, price) 联合索引时，查询尽量带上 status 才能命中索引，避免单独按 category_id 或 price 查询。

**常见追问**

- `a=1 AND c=3` 能用上哪些？（只有 a，c 因缺 b 而失效）
- 等值和范围混合会怎样？（范围列之后的列失效）

**易错点**

能命中的前提是「从 a 开始、连续、不跳列」；范围查询会切断后面的列，这是最易错的点。

## 268. 常见的索引失效场景有哪些？

**面试回答**

常见有：①对索引列使用函数或运算；②隐式类型转换；③`like '%xxx'` 前缀模糊；④联合索引不满足最左匹配；⑤对索引列用 `!=`/`<>`、`NOT IN` 等（可能失效）；⑥索引列参与 OR（部分情况）。

**理解**

索引失效的本质是「数据库无法利用索引的有序结构定位，只能退化为全表扫描」。对列做函数/运算会让值变形，无法按索引值匹配；类型转换同理；前导模糊无法确定前缀位置；不满足最左匹配无法定位。理解这些场景，写 SQL 时就能避免。

**场景**

项目里写查询时避免 `WHERE DATE(create_time) = '2024-01-01'` 这种对索引列用函数，改为范围条件 `create_time >= ... AND create_time < ...`。

**常见追问**

- 为什么对列用函数会失效？（索引存的是原始值，函数后无法匹配）
- 怎么避免？（把函数放等号另一边，或用范围条件）

**易错点**

索引失效「不是绝对的」，要结合优化器和数据分布判断；但上述场景是高频失效点，写 SQL 要主动避免。

## 269. `like '%xxx'` 为什么可能导致索引失效？

**面试回答**

因为 `%` 在开头时，无法确定字符串的前缀，B+Tree 索引是按前缀有序的，无法利用索引定位，只能全表扫描；而 `xxx%` 前缀匹配能走索引。

**理解**

B+Tree 索引对字符串按字典序有序存储，`like 'abc%'` 能确定「以 abc 开头」这个范围，所以能走索引；但 `like '%abc'` 不知道开头是什么，整个索引范围都可能是，无法定位，就退化成全表扫描。

**场景**

项目里模糊搜索菜品名时，尽量用 `name like '关键词%'`（前缀匹配）才能走索引，避免 `%关键词%` 或 `%关键词`。

**常见追问**

- `like 'abc%'` 走索引吗？（走，前缀匹配可定位）
- 一定要中间模糊怎么办？（考虑全文索引、搜索引擎，或接受全表扫描）

**易错点**

关键是「前缀能不能确定」：`%` 在开头就废了；`%` 在末尾（`abc%`）还能走索引。

## 270. 对索引列使用函数为什么可能导致索引失效？

**面试回答**

因为索引里存的是列的「原始值」，对列套函数后值被计算变形，数据库无法直接用索引按原始值匹配，只能全表扫描。

**理解**

比如 `WHERE DATE(create_time) = '2024-01-01'`，索引按 create_time 原始值排序，但查询条件是「对 create_time 取日期后的结果」，两者对不上，优化器没法走索引，只能把每行都算一遍 DATE 再比对。解决方法是把函数移到另一边，或改成范围查询。

**场景**

项目里查某天订单，避免 `DATE(create_time) = ?`，改用 `create_time >= '当天0点' AND create_time < '次日0点'`。

**常见追问**

- 怎么改写避免失效？（函数放常量一边，或转成范围查询）
- 隐式类型转换也算函数吗？（算，本质类似，见 [[04-MySQL/03-索引#271. 隐式类型转换为什么可能导致索引失效？]]）

**易错点**

核心是「索引存原始值，函数让它对不上」；改写思路是「让索引列保持原样参与比较」。

## 271. 隐式类型转换为什么可能导致索引失效？

**面试回答**

因为当列的类型和比较值类型不一致时，MySQL 可能对索引列做隐式转换（相当于对列用了函数），导致索引按原始值匹配不上，退化为全表扫描。

**理解**

比如 `phone` 是字符串列，写 `WHERE phone = 13800000000`（数字），MySQL 可能把列转成数字再比较（`CAST(phone AS signed)`），等价于对索引列用了函数，索引失效。反过来如果转换发生在常量上，则不影响索引。要避免，就保证比较时类型一致。

**场景**

项目里字符串字段（如订单号、手机号）查询时，参数传字符串 `phone = '13800000000'`，避免传数字触发隐式转换。

**常见追问**

- 什么方向转换会导致失效？（列被转换会失效，常量转换一般不影响）
- 怎么避免？（保持字段和参数类型一致，字符串就传字符串）

**易错点**

隐式转换失效的根源是「列被转换 = 对列用函数」；注意是「列转常量」才容易失效。

## 272. 什么是 EXPLAIN？

**面试回答**

EXPLAIN 是 MySQL 用来分析一条 SQL 执行计划的命令，在 SQL 前加 EXPLAIN，就能看到优化器打算怎么执行这条语句（用了哪个索引、扫描多少行、连接方式等）。

**理解**

EXPLAIN 输出很多列，关键的：type（访问类型）、key（实际用的索引）、rows（预估扫描行数）、Extra（额外信息如是否回表、是否 filesort）。它是排查慢查询、判断索引是否命中的核心工具。

**场景**

项目里发现某查询慢，用 EXPLAIN 看它有没有走索引、扫描了多少行，再决定怎么优化。

**常见追问**

- EXPLAIN 看什么？（type、key、rows、Extra）
- 怎么判断走了索引？（看 key 列有值、type 不是 ALL）

**易错点**

EXPLAIN 是「预估执行计划」，不是真实执行；用它判断「是否走索引、扫描行数」是优化 SQL 的第一步。

## 273. EXPLAIN 中 `type` 表示什么？

**面试回答**

type 表示访问类型，即 MySQL 用哪种方式访问数据，从好到差大致是：system/const、eq_ref、ref、range、index、ALL，它反映查询效率的高低。

**理解**

type 越靠前越好。const（按主键/唯一索引等值查一行）、eq_ref（连接时按唯一键匹配）、ref（普通索引等值查）、range（索引范围扫描）、index（全索引扫描）、ALL（全表扫描）。一般要避免 ALL，尽量达到 range 及以上。

**场景**

项目里用 EXPLAIN 看查询 type，如果出现 ALL（全表扫描）就要考虑加索引或改写 SQL。

**常见追问**

- ALL 表示什么？（全表扫描，最差）
- const 什么时候出现？（主键或唯一索引的等值查询）

**易错点**

type 是「访问方式」的优劣等级，ALL 最差、const 最好；目标是尽量走索引，避免 ALL。

## 274. EXPLAIN 中 `key` 表示什么？

**面试回答**

key 表示这条 SQL 实际使用的索引名；如果为 NULL，说明没用到索引（可能全表扫描）。

**理解**

key 列告诉你优化器最终选择了哪个索引。配合 possible_keys（候选索引）一起看：possible_keys 是可能用到的索引，key 是实际选的。key 为 NULL 通常意味着没走索引，需要优化。

**场景**

项目里 EXPLAIN 查询时，看 key 是否为空判断索引有没有命中；key 为空且 type 是 ALL，说明在扫全表。

**常见追问**

- key 为 NULL 说明什么？（没用到索引）
- possible_keys 和 key 区别？（候选 vs 实际使用）

**易错点**

key 是「实际使用的索引」；要结合 possible_keys 判断是不是「有索引但没用上」。

## 275. EXPLAIN 中 `rows` 表示什么？

**面试回答**

rows 表示 MySQL 预估需要扫描的行数（估算值），行数越大通常说明扫描范围越大、查询越慢。

**理解**

rows 是优化器根据统计信息估算的「要读多少行」，不是精确值，但能反映查询代价。rows 很大（接近全表）说明可能要扫描大量数据，值得优化。对比加索引前后的 rows 能直观看到优化效果。

**场景**

项目里优化查询前后用 EXPLAIN 对比 rows，加索引后 rows 从几十万降到几十，说明优化有效。

**常见追问**

- rows 是精确的吗？（不是，是估算）
- rows 很大说明什么？（扫描范围大，可能需要优化）

**易错点**

rows 是「估算」不是精确值，但它能判断扫描量级，是判断查询代价的重要参考。

## 276. EXPLAIN 中 `Extra` 有哪些常见信息？

**面试回答**

常见的有：Using index（覆盖索引，不用回表）、Using where（用 where 过滤）、Using index condition（索引下推）、Using filesort（额外排序）、Using temporary（用了临时表，通常是排序/分组导致）。

**理解**

Extra 是补充信息，能发现隐藏问题：Using filesort 说明排序没走索引、要额外排序；Using temporary 说明用了临时表（常见于 GROUP BY/DISTINCT），性能较差；Using index 是好消息（覆盖索引）；Using index condition 是索引下推（见 [[04-MySQL/06-MySQL进阶#603. 什么是索引下推？]]）。

**场景**

项目里看到 Using filesort 或 Using temporary 时，说明 ORDER BY/GROUP BY 没利用好索引，需要优化。

**常见追问**

- Using filesort 是什么问题？（排序没走索引，额外排序，慢）
- Using index 是好事吗？（是，表示覆盖索引，不用回表）

**易错点**

Extra 里的 filesort、temporary 是「性能隐患」信号，index 是「优化到位」信号，要学会看这些信息定位问题。
