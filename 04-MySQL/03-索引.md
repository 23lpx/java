# 索引

## 249. 什么是数据库索引？

**面试回答**

索引是数据库为提高数据访问效率而维护的辅助数据结构。它按照一个或多个列的值组织索引记录，使优化器有机会避免扫描整张表，也可能直接支持排序、分组或覆盖查询。代价是额外空间和写入维护成本。

**原理与理解**

以 InnoDB 常见的 B-tree 索引为例，索引项按键值有序组织。查询可先在树中定位键值范围，再访问匹配的索引记录；主键聚簇索引的叶子记录包含行数据，二级索引的叶子记录包含索引列和主键列。

**成立条件与边界**

“建了索引”不等于“执行时一定用索引”，更不等于“一定更快”。优化器会根据统计信息、选择性、返回行数、排序需求和成本选择访问路径；预计访问大部分数据时，全表扫描可能更便宜。

**实际场景（项目核验项）**

为订单或菜品查询设计索引前，先从真实 SQL 核验过滤条件、连接条件、排序与返回列，再用执行计划验证，而不是仅凭“状态、分类经常出现”就声明项目已经建立某个索引。

**常见追问**

- 索引的本质是什么？（以额外存储和维护成本换取更高效的访问路径）
- 索引越多越好吗？（不是，见 [[04-MySQL/03-索引#252. 索引是不是越多越好？]]）

**易错点**

不要把索引只说成“值到磁盘地址的映射”；不同存储引擎、聚簇索引和二级索引保存的内容并不相同。

## 250. 索引为什么能提高查询速度？

**面试回答**

索引通过有序结构缩小需要检查的数据范围，并可能减少数据页读取、回表和排序。例如等值查询可定位到特定键值，范围查询可从边界开始顺序扫描，覆盖查询还可以只读取索引。

**原理与理解**

没有合适访问路径时，数据库可能逐页扫描表并过滤；有合适索引时，可以沿树定位起点，只扫描满足范围的索引项。性能收益最终来自“少读页、少处理行、少做额外工作”，而不只是抽象算法复杂度。

**成立条件与边界**

把查询从 O(n) 降为接近 O(log n) 只能作为数据结构层面的近似理解。真实成本还受树高、缓存命中、随机与顺序 I/O、匹配行数、回表次数和并发负载影响；低选择性查询也可能不用索引。

**实际场景（通用工程）**

优化分页列表时，应比较索引前后的访问类型、预估扫描行数、是否额外排序以及实际耗时，确认收益来自扫描量下降，而不是只看到 `key` 非空就结束分析。

**常见追问**

- 索引为什么快？（减少需要读取的页和处理的行）
- 有索引为什么仍可能慢？（返回行多、回表多、统计信息不准或访问路径不合适）

**易错点**

“B+Tree 查询就是几次磁盘 I/O”过于绝对：根页和中间页通常可能在 Buffer Pool 中，叶子范围也可能跨很多页。

## 251. 索引有什么缺点？

**面试回答**

索引会占用磁盘和缓存空间；插入、删除以及修改索引列时需要维护索引记录，增加写放大、页分裂概率和日志量；索引过多还会增加 DDL、备份与优化器评估成本。

**原理与理解**

一行发生变化时，所有受影响的索引都要保持一致。联合索引键较宽、主键较长或重复索引较多时，索引体积和维护成本都会上升，更多索引页也会挤占 Buffer Pool。

**成立条件与边界**

“低区分度字段绝对不能建索引”不准确。低基数字段单独过滤时收益常较小，但放在符合查询模式的联合索引中，或用于覆盖、排序且数据分布倾斜时，仍可能有价值，必须以工作负载验证。

**实际场景（通用工程）**

新增列表查询索引时，同时评估线上读收益、写入频率、索引大小、是否与现有联合索引重复，并在发布后观察执行计划和写入延迟。

**常见追问**

- 为什么索引影响写入？（受影响的索引记录也要插入、删除或更新）
- 长主键有什么影响？（InnoDB 二级索引会保存主键列，主键越长通常占用越大）

**易错点**

并不是每次更新都会修改所有索引；只有相关索引项需要变化，但额外索引仍会增加总体维护与存储成本。

## 252. 索引是不是越多越好？

**面试回答**

不是。索引设计应服务于稳定且重要的查询模式，在查询收益与空间、写入、运维成本之间取舍。通常优先消除重复索引，并让一个合理的联合索引覆盖多个高频访问模式。

**原理与理解**

优化器会在可选访问路径中估算成本，但更多候选索引不会自动产生更优计划。相似前缀的单列与联合索引可能冗余，宽索引则会降低单页可容纳的记录数并增加缓存压力。

**成立条件与边界**

不能仅凭“字段高频”或“区分度高”建索引。还要核对谓词组合、列顺序、排序、返回列、数据分布和写比例；外键相关索引、唯一约束等还承担正确性或约束检查职责，不能只按查询收益删除。

**实际场景（项目核验项）**

对菜品或订单表做索引治理时，应先导出实际表结构与高频 SQL，检查重复、未使用和缺失索引；在没有这些证据前，只能把建议标记为核验项。

**常见追问**

- 哪些列适合进入索引？（常用于选择性过滤、连接、排序或覆盖查询的列）
- 怎样判断索引冗余？（比较索引列、顺序、前缀、唯一性和实际使用情况）

**易错点**

不要用“WHERE 中出现的每一列都建单列索引”代替联合索引设计，多个单列索引也不必然能被高效合并。

## 253. InnoDB 为什么使用 B+Tree？

**面试回答**

InnoDB 的普通索引采用 B-tree 家族的页式有序结构，面试中通常称为 B+Tree。它具有高扇出、树高低、等值与范围访问兼顾等特点，适合以页为单位的磁盘与缓存系统。

**原理与理解**

内部节点主要用于导航，叶子层保存索引记录并按键值顺序组织。一个页能容纳多个键和子页引用，因此从根到叶通常只需经过少量层级；定位起点后还能在叶子层继续顺序扫描。

**成立条件与边界**

MySQL 官方文档通常使用 “B-tree index” 这一名称；“B+Tree”是面试中对 InnoDB 实现特征的常用概括。树的具体高度、每页键数和 I/O 次数由页大小、键宽、行数、填充度及缓存状态决定，不能固定说成 3～4 次。

**实际场景（通用工程）**

订单按主键等值查询、按创建时间区间查询、按联合索引前缀筛选，都是有序树索引适合处理的访问模式；是否选择该索引仍由优化器成本决定。

**常见追问**

- 为什么高扇出重要？（相同数据规模下通常能降低树高）
- 为什么适合范围查询？（叶子记录有序，可从边界继续扫描）

**易错点**

核心不只是“树矮”，还包括页式存储、有序访问和范围扫描；也不要把一个树层机械等同于一次物理磁盘 I/O。

## 254. 为什么不用普通二叉树？

**面试回答**

普通二叉搜索树每个节点最多两个子节点，扇出低；若将节点映射到数据库页，相同数据规模下通常比多路树更高，需要访问更多页，而且普通二叉树还可能退化为链表。

**原理与理解**

数据库索引关心的是页访问成本。B-tree 家族让一个页存放大量键和子页指针，用更高扇出换取更低树高；平衡二叉树虽然能避免退化，但仍只有两个分支，更适合内存中的细粒度节点操作。

**成立条件与边界**

“一百万行二叉树一定要 20 次磁盘 I/O”只是理想平衡树的层数示意，实际节点布局和缓存会改变 I/O。比较重点应是页模型和扇出，而不是死记一个层数。

**实际场景（通用工程）**

在解释数据库索引与 Java `TreeMap` 的结构差异时，可指出两者都保持有序，但数据库需要优先减少页访问，数据结构选择的成本模型不同。

**常见追问**

- 红黑树不会退化，为什么仍不常用于磁盘索引？（二叉分支使树高通常更高）
- 数据库为什么特别关注树高？（树高影响需要访问的索引页数量）

**易错点**

不要回答“二叉树查询慢、B+Tree 查询快”而不说明磁盘页、高扇出和树高之间的关系。

## 255. 为什么不用 Hash 作为主要索引结构？

**面试回答**

Hash 索引适合完整键的等值查询，但键值无序，不能直接支持范围扫描、按索引顺序排序或最左前缀查找。通用 OLTP 查询需要兼顾等值、范围和排序，因此 InnoDB 的用户索引以 B-tree 为主。

**原理与理解**

Hash 根据哈希值定位桶，对 `=`、`<=>` 很合适；但不能从某个键自然找到“下一个键”，所以无法像 B-tree 那样处理 `<`、`BETWEEN` 或有序遍历。哈希冲突也需要额外处理。

**成立条件与边界**

InnoDB 的自适应哈希索引是引擎根据访问模式自动构建的内部优化，不是用户可用 `CREATE INDEX ... USING HASH` 代替 B-tree 的通用索引。MEMORY 等引擎的索引能力也不能直接套到 InnoDB。

**实际场景（通用工程）**

用户既要按订单号等值查找，也要按创建时间范围检索并排序时，有序树索引能覆盖更普遍的需求；若只是纯键值访问，还应结合缓存或专用 KV 系统评估。

**常见追问**

- Hash 索引擅长什么？（完整键等值查询）
- 自适应哈希索引能手工创建吗？（不能，它是 InnoDB 内部机制）

**易错点**

不要笼统说 Hash 查询恒为 O(1)；冲突、桶分布、缓存和实现都会影响真实成本。

## 256. B+Tree 为什么能减少磁盘 IO？

**面试回答**

B+Tree 以页为节点并具有较高扇出，在相同记录规模下通常保持较低树高，因此定位目标所需访问的索引页较少；叶子层顺序扫描还能提高范围访问的局部性。

**原理与理解**

内部页保存多组分隔键和子页引用，一次读页可以获得大量导航信息。根页和高层页又常驻或容易命中 Buffer Pool，真正触发的物理 I/O 往往少于逻辑访问的树层数。

**成立条件与边界**

“一个节点固定 16KB、能放几百上千个键、查询固定 3 次 I/O”都不是通用结论。InnoDB 默认页大小通常是 16KB，但可配置；键宽、记录格式、页利用率和缓存命中都会改变结果。

**实际场景（通用工程）**

缩短 InnoDB 主键不仅影响聚簇索引，还能缩小每个二级索引中的主键部分，使更多索引记录装入一页，间接改善缓存和 I/O。

**常见追问**

- 树高和 I/O 是一一对应吗？（不是，页可能已在 Buffer Pool）
- 键很宽有什么影响？（单页记录数减少，索引体积和树高可能增加）

**易错点**

索引减少的是“通常需要访问的数据页”，不是保证每次查询都只发生固定次数的物理磁盘读取。

## 257. B+Tree 为什么适合范围查询？

**面试回答**

B+Tree 的键值有序。执行范围查询时，可以先定位下界，再沿叶子层按键顺序扫描，直到越过上界，无需为范围中的每个值都从根节点重新查找。

**原理与理解**

例如 `created_at >= t1 AND created_at < t2`，索引可构造一个键值区间；存储引擎定位起点后连续读取后续索引记录。这也可能为 `ORDER BY` 提供有序结果，减少额外排序。

**成立条件与边界**

范围扫描仍可能读取大量记录和数据页。若范围覆盖表中大部分数据、需要频繁回表或排序方向与索引不匹配，优化器可能选择其他计划；是否高效必须结合选择性与执行计划。

**实际场景（通用工程）**

按时间段查询订单时，可使用半开区间并让索引列参与直接比较；同时核对是否还需要状态过滤、排序和返回大量列，再决定联合索引顺序。

**常见追问**

- 为什么 Hash 不适合范围查询？（哈希桶不保持键值顺序）
- 范围查询一定快吗？（不一定，范围过大或回表过多仍会慢）

**易错点**

不必把实现背成“叶子节点一定是双向链表”才算回答完整；面试核心是叶子记录有序且可连续扫描。

## 258. 什么是聚簇索引？

**面试回答**

聚簇索引是 InnoDB 中直接保存行数据的特殊索引，每张表只有一个。定义主键时，主键就是聚簇索引；没有主键时，InnoDB 依次选择第一个所有列均 `NOT NULL` 的唯一索引，或生成隐藏的 `GEN_CLUST_INDEX`。

**原理与理解**

通过聚簇索引查找时，叶子记录已经包含完整行，不需要再从另一份堆文件取行。其他索引是二级索引，其中保存主键列，用主键再次定位聚簇记录。

**成立条件与边界**

“数据文件严格按主键物理连续排列”是过度简化。更准确地说，聚簇索引决定行记录在 B-tree 叶子页中的组织方式；页分裂、空洞和物理文件布局不保证全表磁盘空间连续。

**实际场景（通用工程）**

设计主键时通常偏向短、稳定且单调增长的值，以降低二级索引体积和随机插入带来的页维护；但是否使用自增主键还要结合分库分表与业务标识需求。

**常见追问**

- 没有主键会怎样？（使用合适的唯一非空索引，否则生成隐藏 6 字节行 ID）
- 一张 InnoDB 表有几个聚簇索引？（一个）

**易错点**

主键约束与聚簇组织是相关但不同的概念；“主键索引”在 InnoDB 中通常是聚簇索引，在其他存储引擎中不一定如此。

## 259. InnoDB 主键索引叶子节点保存什么？

**面试回答**

InnoDB 主键聚簇索引的叶子记录保存该行的全部列数据，并包含 InnoDB 为事务与回滚等机制维护的隐藏系统字段。

**原理与理解**

沿主键树找到叶子记录后即可取得整行，因此主键查询通常不需要“回表”。这也是 InnoDB 把聚簇索引称为行数据存储位置的原因。

**成立条件与边界**

大字段可能采用页外存储，叶子记录保存前缀和指针等信息，不能理解为所有字节都固定塞在一个叶子页内。`SELECT` 也可能只读取需要的列，而不是把整行所有内容都返回给应用。

**实际场景（通用工程）**

按订单主键查询详情时，聚簇索引能直接定位行；若先按用户 ID 的二级索引查询并需要其他列，则可能还要用叶子记录中的主键查聚簇索引。

**常见追问**

- 主键查询需要回表吗？（通常不需要）
- 与二级索引叶子有什么不同？（二级索引叶子保存二级索引列和主键列，见 [[04-MySQL/03-索引#261. 二级索引叶子节点保存什么？]]）

**易错点**

“保存整行”描述的是逻辑组织；不要由此推导出大字段必然完整内联在同一个 16KB 页中。

## 260. 什么是二级索引？

**面试回答**

在 InnoDB 中，除聚簇索引以外的索引都叫二级索引，也常称非聚簇索引。它按二级索引键组织记录，并携带主键列，用于找到对应的聚簇索引记录。

**原理与理解**

查询先在二级索引中定位候选记录。如果所需信息已被二级索引覆盖，可以直接返回；否则使用其中的主键值再次查聚簇索引，这一步通常称为回表。

**成立条件与边界**

二级索引不等于“单列普通索引”，唯一索引和联合索引只要不是聚簇索引，也属于二级索引。二级索引查询也不必然回表，是否回表取决于查询所需列和执行计划。

**实际场景（通用工程）**

为 `(user_id, status, create_time)` 建立联合索引后，它仍是二级索引；查询只返回这些列和主键时可能形成覆盖查询，返回订单全部详情时通常需要回表。

**常见追问**

- 二级索引为什么保存主键？（用来定位聚簇索引中的行）
- 二级索引查询一定回表吗？（不一定，覆盖索引可避免，见 [[04-MySQL/03-索引#263. 什么是覆盖索引？]]）

**易错点**

不要把“二级索引”与“联合索引”“唯一索引”放在同一维度互斥分类，它们描述的是不同属性。

## 261. 二级索引叶子节点保存什么？

**面试回答**

InnoDB 二级索引叶子记录保存二级索引定义中的列，以及对应行的主键列。主键列既用于定位聚簇记录，也帮助唯一标识二级索引中的记录。

**原理与理解**

例如表的主键为 `id`，二级索引为 `(user_id, status)`，叶子记录逻辑上包含 `user_id`、`status` 和 `id`。查询其他列时，存储引擎可根据 `id` 再访问聚簇索引。

**成立条件与边界**

具体物理编码还涉及索引扩展、隐藏列和记录格式，不必把它简化为固定三元组。若主键很长，每条二级索引记录都会受影响，所以短主键通常更节省空间。

**实际场景（通用工程）**

只查询 `user_id`、`status` 和 `id` 时，上述二级索引可能已经覆盖；若还查询收货地址快照或金额等未包含列，则通常需要访问聚簇记录。

**常见追问**

- 二级索引为什么不直接保存磁盘地址？（InnoDB 通过稳定的主键定位聚簇记录）
- 修改主键代价为什么大？（所有二级索引中的主键部分也可能需要维护）

**易错点**

“二级索引保存主键，所以更新数据不用维护二级索引”是错误的；修改索引列或主键仍会引起相关索引记录变化。

## 262. 什么是回表？

**面试回答**

回表是先通过 InnoDB 二级索引找到主键，再用主键访问聚簇索引以取得二级索引未覆盖的列。一次二级索引范围扫描可能产生多次聚簇索引查找。

**原理与理解**

二级索引记录不保存完整行。若查询 `SELECT *`，存储引擎通常需要对候选主键逐个取得聚簇记录；随机且大量的回表会增加数据页访问，优化器也可能因此放弃二级索引而选择全表扫描。

**成立条件与边界**

回表不是任何二级索引查询的必经步骤。覆盖索引可以避免取完整行；ICP 可以先在二级索引层过滤候选项、减少回表，但 `Using index condition` 本身不表示完全不回表。

**实际场景（通用工程）**

订单列表先按 `(user_id, status)` 找到大量主键，又返回很多详情列时，可能出现大量回表；可从缩小范围、减少返回列或设计合适覆盖索引等方向优化。

**常见追问**

- 回表为什么可能慢？（需要额外访问聚簇索引，且可能是大量离散页）
- 怎么避免回表？（让查询需要的列被索引覆盖，见 [[04-MySQL/03-索引#263. 什么是覆盖索引？]]）

**易错点**

不要把一次 SQL 的回表理解成固定“再查一次”；范围扫描匹配多少个候选记录，就可能发生相应数量的聚簇访问。

## 263. 什么是覆盖索引？

**面试回答**

覆盖索引不是一种独立索引类型，而是某个索引包含一条查询所需的全部列，使 MySQL 可以仅从索引记录取得结果，无需再读取完整行。

**原理与理解**

二级索引包含索引列和主键列，因此 `SELECT id, user_id, status ...` 可能被 `(user_id, status)` 覆盖。传统 `EXPLAIN` 的 `Extra` 出现 `Using index`，通常表示仅使用索引树取得列信息。

**成立条件与边界**

覆盖关系取决于具体查询；同一索引对查询 A 是覆盖索引，对 `SELECT *` 的查询 B 可能不是。覆盖也不保证计划最佳，扫描大量索引记录仍可能很慢，过度扩宽索引还会增加写入和空间成本。

**实际场景（通用工程）**

高频订单摘要列表只返回主键、状态与创建时间时，可评估让过滤、排序和返回列落在同一联合索引中；详情接口不应为了覆盖所有大字段而建立超宽索引。

**常见追问**

- 覆盖索引必须是联合索引吗？（不一定，单列索引也可能覆盖只需该列和主键的查询）
- `Using index condition` 是覆盖索引吗？（不是，它表示 ICP，通常仍需读取完整行）

**易错点**

“索引中有 WHERE 列”不等于覆盖，还必须覆盖 `SELECT`、连接、排序等执行中需要从该表读取的列。

## 264. 覆盖索引为什么可以提高查询效率？

**面试回答**

覆盖索引可以省去从二级索引到聚簇索引的额外访问，减少随机 I/O 和数据页读取；索引记录通常也比完整行窄，同样缓存空间能容纳更多记录。

**原理与理解**

普通二级索引查询要先扫描索引，再按主键取行；覆盖查询直接在索引叶子层过滤并返回所需值。对匹配行多、完整行较宽的查询，减少回表的收益尤其明显。

**成立条件与边界**

覆盖索引不是越宽越好。把大量低频列或大字段加入索引会增加索引体积、维护成本和树页访问，甚至抵消查询收益；应只服务于明确的高频查询。

**实际场景（通用工程）**

列表页只展示订单 ID、状态、时间时，优先限制返回列，再评估覆盖索引；这通常比直接用 `SELECT *` 并尝试把所有字段都塞入索引更合理。

**常见追问**

- 覆盖索引主要省掉什么？（回表和完整行页读取）
- 怎样确认覆盖？（核对查询所需列，并查看执行计划中的 `Using index` 等信息）

**易错点**

覆盖索引提升的是特定查询的访问效率，不代表索引本身没有维护代价，也不代表 `rows` 很大时查询一定快。

## 265. 什么是联合索引？

**面试回答**

联合索引是在多个列上按既定顺序建立的一个索引，例如 `(a,b,c)`。索引记录先按 `a` 排序，`a` 相同时再按 `b`，最后按 `c`，因此列顺序直接影响可支持的查找、排序和覆盖能力。

**原理与理解**

联合索引可利用列组合的相关性，一次访问同时处理多个条件，并可能替代部分前缀相同的单列索引。设计时通常综合等值条件、范围条件、排序、选择性和覆盖需求决定顺序。

**成立条件与边界**

“区分度最高的列永远放最左边”不是通用规则。若业务必须先按租户或用户等值隔离，再按时间范围查询，查询模式和排序需求可能比单列区分度更重要。

**实际场景（项目核验项）**

为订单列表提出 `(user_id, status, create_time)` 只是候选方案；必须核对真实 SQL、字段分布、排序方向与现有索引，再用 `EXPLAIN ANALYZE` 或压测验证。

**常见追问**

- 联合索引列顺序为什么重要？（索引按键元组的字典序排列）
- 单独查 `b` 能用 `(a,b,c)` 吗？（通常不能做普通左前缀定位，见 [[04-MySQL/03-索引#266. 什么是最左匹配原则？]]）

**易错点**

联合索引不是多个单列索引的简单拼接，`(a,b)` 与 `(b,a)` 的有序访问能力不同。

## 266. 什么是最左匹配原则？

**面试回答**

最左匹配指 B-tree 联合索引通常从最左列开始构造连续的查找前缀。例如 `(a,b,c)` 可直接支持按 `(a)`、`(a,b)`、`(a,b,c)` 定位；缺少 `a` 时通常不能用普通范围查找直接定位 `b`。

**原理与理解**

联合索引按完整键元组排序。只有先确定前面的列，后面的列才形成连续有序区间。SQL 中条件书写顺序不影响这一原则，优化器会分析表达式，关键是索引列和谓词能否形成连续前缀。

**成立条件与边界**

最左匹配描述的是高效查找和范围边界，不等于“非最左列完全没有作用”。后续列仍可能参与 ICP、覆盖或排序；MySQL 8.4 在满足限制时还可能使用 Skip Scan，不能把口诀当成绝对执行规则。

**实际场景（通用工程）**

索引 `(user_id, status, create_time)` 很适合先限定用户，再按状态和时间访问；仅按 `status` 查询全体订单时，应由执行计划判断 Skip Scan、全索引扫描、其他索引或全表扫描哪种成本更低。

**常见追问**

- WHERE 条件必须按索引顺序写吗？（不必，条件书写顺序不是关键）
- 缺少最左列一定完全不用索引吗？（普通左前缀定位不行，但可能出现 Skip Scan 或索引扫描等计划）

**易错点**

不要把“能否用索引定位”“能否在索引层过滤”“能否覆盖返回列”混成一个简单的“索引是否失效”。

## 267. 联合索引 \`(a,b,c)\` 哪些查询可以使用索引？

**面试回答**

典型可高效定位的条件包括 `a=?`、`a=? AND b=?`、`a=? AND b=? AND c=?`，以及在连续等值前缀后对下一列做范围查询。`b=?` 或 `b=? AND c=?` 通常不能按普通左前缀直接定位。

**原理与理解**

`a=? AND c=?` 可以先用 `a` 确定索引范围，`c` 可能在索引层过滤，但它不能像连续的 `(a,b,c)` 条件那样进一步形成同一个精确查找前缀。`a>? AND b=?` 中，`a` 可构造范围，`b` 是否减少回表或扫描要看 ICP、覆盖和具体计划。

**成立条件与边界**

“遇到范围条件，后面的列全部失效”不准确：后列通常不能继续缩小传统范围边界，但仍可能参与索引条件下推、覆盖或其他优化。MySQL 8.4 的 Skip Scan 还可能在严格条件下处理缺少前导列的查询。

**实际场景（通用工程）**

评审联合索引时，应分别记录“用于访问边界的列”“用于索引层过滤的列”“用于覆盖的列”，再通过 `key_len`、`Extra` 和实际执行数据验证，避免只画一张绝对的命中表。

**常见追问**

- `WHERE c=3 AND a=1 AND b=2` 能用吗？（能，SQL 条件书写顺序不决定索引前缀）
- `a>1 AND b=2` 中 `b` 完全没用吗？（不一定，可能用于 ICP 或覆盖，但通常不能继续缩小 `a` 的范围边界）

**易错点**

“使用了某个联合索引”不表示其中每一列都用于定位；要区分访问键、索引过滤和覆盖。

## 268. 常见的索引失效场景有哪些？

**面试回答**

更准确的说法是“索引不能用于高效定位，或优化器选择不用”。常见原因包括缺少联合索引左前缀、对索引列做未匹配函数运算、前导通配符、类型或字符集转换、返回行过多，以及排序或谓词与索引顺序不匹配。

**原理与理解**

索引需要从谓词中推导出可搜索的键值或区间。如果表达式改变了索引列的比较形式、无法确定起点，或预计回表成本高，优化器可能选择全表扫描、全索引扫描、Index Merge 等其他访问路径。

**成立条件与边界**

`!=`、`NOT IN`、`OR`、`IS NULL` 和低基数列都不是自动“失效”。MySQL 的范围优化、Index Merge、函数索引、Skip Scan 和成本模型可能仍选择索引；必须看数据分布和执行计划。

**实际场景（通用工程）**

发现慢 SQL 时先保存 SQL、参数类型、表结构、索引与统计信息，再看 `EXPLAIN ANALYZE`；不要只根据代码表面出现函数或 `OR` 就直接下结论。

**常见追问**

- `OR` 一定不走索引吗？（不一定，可能使用单一范围或 Index Merge）
- 优化器为什么放弃可用索引？（估计访问大量行时，全表扫描可能成本更低）

**易错点**

“索引失效”是面试口语，不是统一执行状态；应具体说明是不能构造范围、只做索引扫描，还是成本选择不用。

## 269. \`like '%xxx'\` 为什么可能导致索引失效？

**面试回答**

普通 B-tree 索引按字符串从左到右有序。模式以 `%` 或 `_` 开头时，没有确定的左侧前缀，无法据此构造连续的索引起止范围，所以通常不能进行前缀定位。

**原理与理解**

`LIKE 'abc%'` 可把 `abc` 当作范围前缀；`LIKE '%abc'` 的匹配值可能散布在整个索引中，只能检查大量记录。若索引覆盖查询，执行计划仍可能选择全索引扫描，但这不等于利用索引完成了高选择性的定位。

**成立条件与边界**

是否使用索引还受数据类型、排序规则、模式是否为常量和成本影响。后缀或任意位置搜索可考虑全文索引、搜索引擎、反向列或业务允许的其他结构，不能只靠普通 B-tree 前缀。

**实际场景（通用工程）**

商品名称搜索若要求任意位置包含，应把它当成搜索需求设计，而不是给名称列加普通索引后仍执行 `LIKE '%关键词%'` 并期待稳定的范围查找。

**常见追问**

- `LIKE 'abc%'` 一定走索引吗？（具备范围条件，但最终仍由优化器按成本选择）
- 前导 `%` 是否绝对不读索引？（不能用普通 B-tree 前缀定位，但可能因覆盖等原因做全索引扫描）

**易错点**

“没走高效范围查找”和“执行计划中完全没有索引”不是同一件事。

## 270. 对索引列使用函数为什么可能导致索引失效？

**面试回答**

普通索引保存的是原始列值的有序结果。若条件比较的是 `FUNCTION(column)`，优化器通常无法直接把函数结果还原为原列的连续索引范围，因此不能用原索引高效定位。

**原理与理解**

例如 `DATE(create_time) = '2026-08-22'` 对每个值计算日期；改写为 `create_time >= '2026-08-22' AND create_time < '2026-08-23'`，可以直接在原始时间列上构造范围。

**成立条件与边界**

并非任何函数都必然失效。MySQL 8.4 支持函数索引，也可通过生成列建立匹配索引；优化器还可能做特定表达式变换。关键是是否存在与查询表达式匹配、可用于定位的索引。

**实际场景（通用工程）**

按天查询订单时，优先使用时间半开区间；若业务大量按同一表达式查询，再评估函数索引或生成列，并验证写入成本和执行计划。

**常见追问**

- 怎样改写 `DATE(create_time)=?`？（改成原列上的左闭右开时间范围）
- 必须保留表达式怎么办？（评估匹配的函数索引或生成列索引）

**易错点**

不要把函数与隐式转换完全画等号；二者都可能改变比较方式，但触发条件和可修复方案需要分别分析（见 [[04-MySQL/03-索引#271. 隐式类型转换为什么可能导致索引失效？]]）。

## 271. 隐式类型转换为什么可能导致索引失效？

**面试回答**

当比较两侧类型、字符集或排序规则不一致时，MySQL 可能对索引列做隐式转换；一旦比较变成对转换结果求值，原列索引就可能无法用于高效范围定位。

**原理与理解**

例如字符串列与数值参数比较时，MySQL 可能按数值规则转换字符串列，导致必须计算许多索引值；同时 `'1'`、`'01'` 等值在数值转换后还可能产生不同于字符串比较的语义。

**成立条件与边界**

不是所有类型不一致都会让索引失效，转换方向、列类型、常量形式、字符集与排序规则都会影响结果。最稳妥的做法是让表字段、关联列和绑定参数类型一致，并通过执行计划验证。

**实际场景（通用工程）**

Java/MyBatis 传参时，数据库字段若为 `VARCHAR`，DTO、Mapper 参数和 JDBC 绑定也应保持字符串语义；跨表 JOIN 的两列还应核对类型、长度、字符集和排序规则。

**常见追问**

- 为什么字符串列用数字参数风险较大？（可能把列转成数值后逐项比较）
- 怎么排查？（检查 DDL、参数绑定类型、字符集/排序规则和执行计划）

**易错点**

不要只看 SQL 文本中的引号；预编译参数的实际 JDBC 类型也会影响数据库如何比较。

## 272. 什么是 EXPLAIN？

**面试回答**

`EXPLAIN` 用于查看优化器为语句选择的执行计划，包括表访问顺序、访问类型、候选与实际索引、预估行数和附加操作。传统 `EXPLAIN` 主要展示估算计划，不代表语句已按该计划完整执行。

**原理与理解**

优化器根据统计信息和成本模型生成计划。MySQL 8.4 还支持 `EXPLAIN ANALYZE`，它会实际执行语句并返回迭代器的估算成本、实际时间、实际行数和循环次数，用于比较估算与现实。

**成立条件与边界**

`EXPLAIN ANALYZE` 会执行语句，不能像普通 `EXPLAIN` 一样随意用于有副作用或线上高成本的语句；分析结果也只代表当前参数、数据分布、缓存和负载环境。

**实际场景（通用工程）**

慢查询治理先用 `EXPLAIN` 检查访问路径，再在安全的测试环境或受控条件下用 `EXPLAIN ANALYZE` 观察实际行数与耗时，最后结合慢日志和业务负载验证。

**常见追问**

- `EXPLAIN` 会给出真实耗时吗？（传统格式不会；`EXPLAIN ANALYZE` 会实际执行并给出运行数据）
- 只看 `key` 够吗？（不够，要结合访问类型、行数、过滤、排序和实际耗时）

**易错点**

执行计划是诊断证据，不是性能结论；统计信息过期、参数不同或数据变化都可能导致计划和实际成本改变。

## 273. EXPLAIN 中 \`type\` 表示什么？

**面试回答**

传统 `EXPLAIN` 的 `type` 表示该表的访问类型，即 MySQL 用什么方式找到行。常见值有 `system`、`const`、`eq_ref`、`ref`、`range`、`index`、`ALL` 等。

**原理与理解**

`const` 常见于主键或唯一索引等值且最多一行；`eq_ref` 常见于连接中每个前表组合最多匹配一行；`ref` 是非唯一等值；`range` 扫描索引区间；`index` 是全索引扫描；`ALL` 是全表扫描。

**成立条件与边界**

从 `const` 到 `ALL` 的顺序只能作入门参考，不能断言“type 越靠前一定越快”。小表全表扫描可能很便宜，`range` 也可能扫描大量行，`index` 只是扫描整棵索引，并不天然优秀。

**实际场景（通用工程）**

看到 `ALL` 时，先看表规模、过滤率和实际耗时；看到 `ref` 或 `range` 时，也要检查 `rows`、回表和 `Extra`，避免只为了把访问类型“调得更好看”而加索引。

**常见追问**

- `index` 和 `ALL` 有什么区别？（前者扫描整个索引，后者扫描整表）
- `range` 一定快吗？（不一定，取决于范围大小和后续访问成本）

**易错点**

`type` 不是字段类型，也不是 SQL 类型；它描述每张表的访问方法。

## 274. EXPLAIN 中 \`key\` 表示什么？

**面试回答**

`key` 表示优化器实际选择的索引；`possible_keys` 表示当前查询可能考虑的索引。`key` 为 `NULL` 通常表示该表没有选择索引访问路径。

**原理与理解**

优化器会综合统计信息和成本，从候选索引或其他路径中选择计划。应同时查看 `key_len` 判断使用了多长的索引键，并结合 `type`、`rows`、`filtered` 和 `Extra` 理解索引承担的作用。

**成立条件与边界**

`key` 非空不等于查询高效，可能是全索引扫描或低选择性范围；`possible_keys` 为空也不必然说明需要加索引，例如小表扫描可能合理，或索引仅用于排序而未列为过滤候选。

**实际场景（通用工程）**

验证联合索引时，不只确认 `key` 名称，还要检查访问条件实际使用的键长度、预估与实际扫描行数，以及是否发生额外排序和大量回表。

**常见追问**

- `possible_keys` 和 `key` 的区别？（候选索引与最终选用索引）
- `key` 非空就算优化完成吗？（不是，还要检查扫描量与额外工作）

**易错点**

不要用“`key` 为 NULL 就盲目加索引”作为固定流程；先确认查询模式、表规模和成本瓶颈。

## 275. EXPLAIN 中 \`rows\` 表示什么？

**面试回答**

传统 `EXPLAIN` 的 `rows` 是优化器估计为执行该表访问需要检查的行数，不是实际扫描行数。连接查询中，每一行表示对应表在其循环中的估算，整体工作量还与前序表输出和循环次数相关。

**原理与理解**

估算来自索引统计信息、直方图和选择性推断，用于比较候选计划。估算偏差过大可能导致优化器选择次优计划；`EXPLAIN ANALYZE` 可以提供实际行数和循环次数用于对照。

**成立条件与边界**

`rows` 小不保证响应快，还可能受排序、回表、锁等待、网络和返回数据量影响；`rows` 大也不必然异常，例如本来就要做全量报表。不同 EXPLAIN 格式的字段名称和含义呈现也有所不同。

**实际场景（通用工程）**

若估算只扫描几十行而实际读取数十万行，应检查统计信息、数据倾斜和谓词相关性，而不是只继续增加索引。

**常见追问**

- `rows` 是实际值吗？（不是，传统 `EXPLAIN` 中是估算值）
- 怎样看实际扫描情况？（使用 `EXPLAIN ANALYZE` 并结合性能监控）

**易错点**

多表连接的总成本不能只把每行 `rows` 独立看待；后表可能被前表输出循环访问多次。

## 276. EXPLAIN 中 \`Extra\` 有哪些常见信息？

**面试回答**

常见值包括：`Using index` 表示可仅从索引取得列信息；`Using where` 表示读取后还要应用条件过滤；`Using index condition` 表示使用 ICP；`Using filesort` 表示需要额外排序过程；`Using temporary` 表示使用内部临时表。

**原理与理解**

ICP 会先用二级索引中的列过滤，满足条件后才读取完整行，从而减少回表（见 [[04-MySQL/06-MySQL进阶#603. 什么是索引下推？]]）。`Using filesort` 的 “file” 是算法名称的一部分，排序不一定落盘；内部临时表也可能在内存中。

**成立条件与边界**

这些标志不是简单的红绿灯。`Using where` 很常见且不必然有问题；`Using filesort`、`Using temporary` 在小结果集上可能成本很低；`Using index` 虽避免读取完整行，但全索引扫描仍可能处理大量记录。

**实际场景（通用工程）**

列表查询出现 `Using filesort` 时，先检查实际排序行数、`LIMIT`、索引顺序与内存使用；只有确认排序是主要瓶颈后，才针对查询设计索引。

**常见追问**

- `Using index condition` 是否表示覆盖索引？（不是，它表示 ICP，并且通常仍需读取完整行）
- `Using filesort` 是否一定写磁盘？（不一定，它表示额外排序过程）

**易错点**

不要看到 `Using temporary` 或 `Using filesort` 就断言 SQL 很慢，也不要看到 `Using index` 就断言已经最优。
