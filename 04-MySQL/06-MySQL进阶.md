# MySQL进阶

## 600. 什么是 Gap Lock？

**面试回答**

Gap Lock（间隙锁）锁定的是索引记录之间的「间隙」（不存在的区间），防止其他事务在这个区间内插入新记录，用于解决幻读。

**理解**

间隙锁锁的不是某一行，而是「行与行之间的空隙」。比如索引值有 10 和 20，间隙锁可以锁住 (10, 20) 这个区间，其他事务就不能往这里插入值 15，从而避免幻读（多出新行）。它在可重复读隔离级别下生效。

**场景**

项目里可重复读级别下，范围查询会加间隙锁，防止并发插入导致统计行数变化（幻读）。

**常见追问**

- 间隙锁解决什么？（防止插入，解决幻读）
- 间隙锁锁的是什么？（索引记录之间的区间，不是具体行）

**易错点**

间隙锁锁「区间」不锁「行」，目的是阻止插入；它是在可重复读下为防幻读而存在的。

## 601. 什么是 Next-Key Lock？

**面试回答**

Next-Key Lock 是「行锁 + 间隙锁」的组合，既锁定某条索引记录，又锁定它前面的间隙，能同时防止「修改已有行」和「插入新行」，是 InnoDB 在可重复读下防幻读的核心机制。

**理解**

Next-Key Lock = 记录锁（锁行）+ 间隙锁（锁前一个间隙）。它锁住「一个左开右闭的区间」，既不让别人改这条记录，也不让别人在这个间隙插入新记录，从而同时防不可重复读和幻读。

**场景**

项目里可重复读级别下，`SELECT ... FOR UPDATE` 或范围更新会加 Next-Key Lock，防止并发插入导致幻读。

**常见追问**

- Next-Key Lock 由什么组成？（行锁 + 间隙锁）
- 它主要防什么？（幻读，见 [[04-MySQL/06-MySQL进阶#602. MySQL 如何处理幻读？]]）

**易错点**

Next-Key Lock 是「行锁 + 间隙锁」的组合，是 InnoDB 防幻读的关键；要理解它锁的是「记录 + 前间隙」。

## 602. MySQL 如何处理幻读？

**面试回答**

InnoDB 通过 MVCC 和 Next-Key Lock（行锁 + 间隙锁）共同处理幻读：快照读靠 MVCC 读一致性快照，当前读靠 Next-Key Lock 锁住间隙阻止插入。

**理解**

幻读是「多次查询行数不一致」（有人插入了新行）。InnoDB 两条路：普通 SELECT 是快照读，用 MVCC 读事务开始时的快照，后续插入看不见；而 `SELECT ... FOR UPDATE`、更新等是当前读，用 Next-Key Lock 锁住间隙，让其他事务无法插入，从而防幻读。这样可重复读级别下幻读被大幅缓解。

**场景**

项目里可重复读级别下，普通的统计查询（快照读）和加锁的范围查询（当前读）都不会因为并发插入而出现行数不一致。

**常见追问**

- 快照读怎么防幻读？（MVCC 读固定快照）
- 当前读怎么防幻读？（Next-Key Lock 锁间隙）

**易错点**

防幻读是「MVCC + Next-Key Lock」双管齐下，分别对应快照读和当前读，别只说其中一个。

## 603. 什么是索引下推？

**面试回答**

索引下推（Index Condition Pushdown，ICP）是 MySQL 的优化手段：把 WHERE 里「能用在索引上」的条件，尽量在存储引擎层先过滤，减少回表次数和返回给 Server 层的数据量。

**理解**

没有 ICP 时，二级索引查到主键就回表，拿到整行再在 Server 层过滤其他条件。有了 ICP，一些条件可以「下推」到存储引擎，在遍历索引时就先判断过滤，不满足的连回表都省了。尤其在联合索引场景，能显著减少回表。

**场景**

项目里联合索引查询、部分条件过滤时，MySQL 用索引下推减少回表，提升查询性能。

**常见追问**

- 索引下推优化了什么？（减少回表次数）
- EXPLAIN 里怎么体现？（Extra 显示 Using index condition）

**易错点**

索引下推是「把过滤提前到存储引擎层，减少回表」，不是「用索引查得更准」；它是性能优化而非功能变化。

## 604. 什么是 Buffer Pool？

**面试回答**

Buffer Pool 是 InnoDB 的内存缓冲池，用来缓存数据页和索引页，让大部分读写直接命中内存，减少磁盘 IO，是 InnoDB 性能的关键。

**理解**

磁盘 IO 很慢，InnoDB 把经常访问的数据页、索引页加载到 Buffer Pool 里，后续读写先在内存里找，命中就不用读盘。修改也先在 Buffer Pool 里改（配合 redo log 保证持久），再异步刷盘。它的大小由 innodb_buffer_pool_size 配置，通常设得较大。

**场景**

项目里 MySQL 配置较大的 Buffer Pool，热数据（常查的菜品、订单）缓存在内存，查询更快。

**常见追问**

- Buffer Pool 缓存什么？（数据页、索引页）
- 为什么能提速？（减少磁盘 IO，内存读写快）

**易错点**

Buffer Pool 是「内存缓存页」的缓冲池，本质是「用内存换 IO」；它和 redo log 配合，改内存也保证持久性。

## 605. 什么是两阶段提交？

**面试回答**

两阶段提交是 MySQL 保证 redo log 和 binlog 一致性的机制：事务提交时，先写 redo log（prepare 阶段），再写 binlog，最后把 redo log 置为 commit 阶段，确保两者要么都成功要么都失败。

**理解**

redo log（引擎层）和 binlog（Server 层）是两个日志，要保证它们在崩溃后一致，就用两阶段提交：①prepare：写 redo log 并标记 prepare；②写 binlog；③commit：把 redo log 标记为 commit。这样崩溃恢复时能判断：binlog 写没写、redo 是否 commit，据此决定提交还是回滚，保证主从复制数据一致。

**场景**

项目里做主从复制时，两阶段提交保证主库的 redo log 和 binlog 一致，从库同步的数据才正确。

**常见追问**

- 两阶段提交解决什么？（redo log 和 binlog 一致性）
- 为什么需要它？（两个日志各自独立写，需要协调）

**易错点**

两阶段提交是「redo log 和 binlog 的协调机制」，目的是崩溃后两者一致、主从数据不错；不是「事务的 prepare/commit」那种两阶段提交协议。
