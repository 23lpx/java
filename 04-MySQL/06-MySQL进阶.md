# MySQL进阶

## 600. 什么是 Gap Lock？

**面试回答**

Gap Lock（间隙锁）是 InnoDB 对索引记录之间、首条记录之前或末条记录之后区间施加的锁，主要禁止其他事务向该间隙插入记录。它不锁住某个已存在行的数据内容，是范围加锁防止插入的一部分。

**原理与理解**

在可重复读下，加锁读、UPDATE、DELETE 扫描索引范围时通常会产生 next-key lock，其中包含 gap lock。间隙锁是“纯抑制插入”的：不同事务可以持有看似冲突的间隙锁，但插入该区间仍需等待。

**成立条件与边界**

不是所有范围条件都会锁相同区间，实际范围取决于隔离级别、执行计划、使用的索引和扫描到的记录。唯一索引等值命中通常只需记录锁；READ COMMITTED 下搜索与扫描通常关闭 gap locking，但外键约束检查和重复键检查等仍可能使用。

**实际场景（通用工程）**

事务用 `SELECT ... FOR UPDATE` 锁定待处理编号范围时，要根据实际索引判断阻塞区间；若条件未有效使用索引，锁范围可能远大于业务想象并阻塞并发插入。

**常见追问**

- Gap Lock 锁的是行吗？——主要锁索引间隙，禁止插入，不等同于修改已有记录的记录锁。
- 为什么两个事务能同时持有 gap lock？——它主要是抑制插入，gap lock 之间可共存。
- 如何确认锁范围？——结合索引、执行计划、隔离级别和 performance_schema 锁信息分析。

**易错点**

不要背成“可重复读的范围查询一定加间隙锁”；普通一致性读通常不加锁，加锁范围也由实际索引扫描决定。

## 601. 什么是 Next-Key Lock？

**面试回答**

Next-Key Lock 是索引记录锁与该记录之前间隙锁的组合。它既保护已存在的索引记录，也阻止在相邻间隙插入新记录，是 InnoDB 在可重复读下进行范围加锁时的常见形式。

**原理与理解**

若索引值为 10、20、30，next-key 区间可概念化为左开右闭的 `(10,20]`、`(20,30]` 等；还存在首端和 supremum 伪记录对应的边界区间。真正的区间以索引顺序为准，而不是表的物理行位置。

**成立条件与边界**

Next-key lock 是常见默认，不代表每次都保留组合形态：唯一索引精确命中可能退化为记录锁，未命中或范围边界也可能表现为纯 gap lock。READ COMMITTED 与特定优化会改变加锁行为。

**实际场景（通用工程）**

用唯一订单号等值 `FOR UPDATE` 与用非唯一状态索引做范围 `FOR UPDATE`，锁范围可能完全不同；设计并发控制前应验证执行计划与实测锁信息。

**常见追问**

- Next-Key Lock 由什么组成？——记录锁加记录之前的间隙锁。
- 它主要处理什么？——锁定范围并阻止符合范围的新记录插入，参见 [[04-MySQL/06-MySQL进阶#602. MySQL 如何处理幻读？]]。
- 是否固定锁“当前记录后面的间隙”？——官方定义是记录锁加该记录之前的 gap，区间常写成左开右闭。

**易错点**

不要把“行锁”当成精确术语代替 record lock，也不要脱离所用索引直接画锁区间。

## 602. MySQL 如何处理幻读？

**面试回答**

在 InnoDB 可重复读下，普通一致性读通过 MVCC 复用同一 Read View，使同一事务的多次快照读通常看不到之后提交的新行；需要读取最新版本并锁定范围时，加锁读通过 next-key/gap locking 阻止其他事务向扫描范围插入。

**原理与理解**

幻读是再次执行同一谓词查询时出现新增或消失的结果行。快照读解决的是“观察到一致快照”，加锁读解决的是“对当前范围进行并发约束”，二者机制和使用目的不同。

**成立条件与边界**

READ COMMITTED 通常每次一致性读建立新快照，因此可能看到新提交行；可重复读中的快照由第一次一致性读建立，不应机械说成事务开始即生成。若先做快照读、再做当前读，后者读取的是最新可见并加锁的记录，结果可能不同；锁范围仍取决于索引扫描。

**实际场景（通用工程）**

统计报表只需事务内一致视图时使用普通 SELECT；若业务要检查某编号区间为空并阻止并发插入，则应在正确索引和事务边界内使用加锁读或唯一约束，而不是把快照读当互斥锁。

**常见追问**

- MVCC 是否阻止别人插入？——不会，它提供一致快照；阻止插入靠范围锁或约束。
- 当前读有哪些？——`SELECT ... FOR UPDATE/SHARE`、UPDATE、DELETE 等会读取较新版本并加锁。
- 可重复读绝对没有幻读吗？——要区分快照读、当前读及混用情形，不能只给一句绝对结论。

**易错点**

“MVCC + Next-Key Lock 防幻读”必须分别对应快照观察与当前范围加锁，不能说两者总在同一次 SELECT 中共同工作。

## 603. 什么是索引下推？

**面试回答**

索引条件下推（ICP）是在使用索引访问表时，把只依赖该索引列的部分 WHERE 条件交给存储引擎先判断；不满足的索引项无需再读取完整基表记录，从而减少回表和 Server 层处理。

**原理与理解**

没有 ICP 时，引擎定位索引项后通常先取完整行，再由 Server 判断剩余条件；有 ICP 时，Server 把可由索引字段判断的条件下推，引擎遍历索引时先过滤。EXPLAIN 的 Extra 常显示 `Using index condition`。

**成立条件与边界**

ICP 只在优化器认为可用时生效，不是手工保证；InnoDB 的主要收益来自二级索引，因为聚簇索引记录已包含整行。并非所有表达式都可下推，例如依赖子查询、存储函数或非索引列的条件不能仅凭索引项判断。

**实际场景（通用工程）**

联合索引 `(name, age)` 只能用 name 确定扫描范围时，age 条件若可由索引项判断，ICP 能先过滤再回表；是否真的减少 I/O 应结合 EXPLAIN ANALYZE 与访问量验证。

**常见追问**

- ICP 改变查询结果吗？——不改变语义，只改变条件判断位置和访问成本。
- 它是否等于覆盖索引？——不是；覆盖索引无需回表，ICP 仍可能对通过过滤的记录回表。
- 如何观察？——查看 EXPLAIN 的 `Using index condition`，再用执行统计验证收益。

**易错点**

ICP 不是“把所有 WHERE 都推到索引”，也不代表使用了 ICP 的计划一定最优。

## 604. 什么是 Buffer Pool？

**面试回答**

Buffer Pool 是 InnoDB 管理的主要内存区域，以页为单位缓存表和索引数据及相关内部结构。读请求命中缓存可减少磁盘访问，写请求先修改内存页形成 dirty page，再由后台机制按策略刷盘。

**原理与理解**

Buffer Pool 通过改进的 LRU 等结构管理热页、空闲页和脏页。事务提交时通常不要求把所有数据页立刻写回表空间；redo log 记录恢复所需变化，崩溃恢复可重做尚未落到数据页的已提交修改。

**成立条件与边界**

Buffer Pool 不是“整张表放进内存”，命中率高也不等于没有 I/O。大小设置要考虑数据库专用或共享主机、容器限制、连接内存和操作系统余量，不能机械套固定百分比；扩大后还需观察工作集、脏页刷新和 checkpoint 压力。

**实际场景（生产能力）**

查询延迟升高时同时检查 Buffer Pool 命中、物理读、脏页比例和磁盘延迟；若工作集超出内存，优先确认索引与扫描量，再评估扩容，而不是只把 Buffer Pool 调大。

**常见追问**

- 缓存哪些内容？——主要是 InnoDB 表和索引页，也包含相关辅助结构。
- 脏页为什么可以晚刷？——redo log 支持崩溃恢复，但持久性仍受日志刷盘配置影响。
- 命中率越高一定越好吗？——它只是一个信号，还要看访问模式、延迟和写回压力。

**易错点**

不要把 Buffer Pool 与 Query Cache 混淆，也不要说“修改只在内存、redo 已经等于数据页落盘”。

## 605. 什么是两阶段提交？

**面试回答**

“两阶段提交”有两层常见语境：分布式 XA 中是 prepare 后再由协调者决定 commit/rollback；MySQL 开启 binary log 且使用事务型引擎时，也通过内部两阶段提交协调 InnoDB 事务状态与 binlog，使崩溃恢复后两者对同一事务作一致判断。

**原理与理解**

面试常问的 MySQL 内部流程可概括为：InnoDB 进入 prepare 并持久化恢复信息，Server 写事务的 binlog，随后提交存储引擎事务。若中途崩溃，恢复逻辑结合 prepared transaction 与 binlog 是否存在来决定提交或回滚，而不是简单依赖最后一个“commit 标记”。

**成立条件与边界**

它不是保证任意两个数据库业务一起成功的魔法，也不能保证异步副本零延迟或零数据损失；durability 还受 `innodb_flush_log_at_trx_commit`、`sync_binlog`、存储与复制配置影响。具体刷盘与 group commit 顺序存在版本实现细节，面试不应把简图说成所有场景固定的物理写盘顺序。

**实际场景（通用工程）**

使用 binlog 做复制或时间点恢复时，需要保证“引擎已提交但 binlog 缺失”与“binlog 已记录但引擎回滚”不会成为正常恢复结果；内部两阶段提交正是协调这个一致性边界。

**常见追问**

- 内部 2PC 协调什么？——MySQL Server 的 binlog 与事务型存储引擎的提交状态。
- 与业务分布式事务一样吗？——都含 prepare/decision 思想，但参与者、接口和故障边界不同。
- 两阶段提交能保证副本实时一致吗？——不能，复制模式与确认策略另行决定。

**易错点**

不要说“redo 和 binlog 要么都写成功要么都没写”；故障点可能留下 prepared redo 或已写 binlog，关键是恢复时能作一致决定。
