# 统一响应与异常处理

## 429. 为什么后端需要统一响应结构？

**面试回答**

统一响应结构是应用层契约，用稳定字段表达业务结果、提示和数据，便于客户端统一解析、错误展示和链路定位。但它不是 HTTP 标准，也不能替代正确的 HTTP 状态码；文件下载、流式响应、重定向和 204 等接口还可能不适合套普通 JSON 包装。

**原理与理解**

若接口成功和失败各自返回任意结构，客户端需要编写大量分支。约定响应模型后，业务码、消息和数据的位置稳定，全局异常处理也能产出同类错误结构。同时 HTTP 状态负责协议层语义，业务码负责应用内细分，两层应协同而非把所有响应都伪装成 `200 OK`。

**成立条件与边界**

- 统一的是契约和语义，不是强迫所有接口拥有完全相同的内容。
- HTTP 状态码应反映请求结果；业务失败不应一律返回 200。
- 响应包装会增加一层结构，应通过 OpenAPI、接口文档或类型定义固定契约。
- 文件、SSE、流式内容、重定向和无响应体接口可采用专门返回方式。
- 统一响应不能替代鉴权、异常分类、日志和监控。

**实际场景**

**真实项目边界：** 简历确认苍穹外卖封装了统一响应模型并配合全局异常处理，能够说明“成功与业务失败遵循统一 JSON 契约”；具体类名和字段仍应以代码为准。

**常见追问**

- 统一响应与 HTTP 状态码冲突吗？不冲突，分别表达协议层和业务层语义。
- 所有接口都要包装吗？不必，文件、流式或 204 响应可例外。
- 为什么还要业务码？用于在同一 HTTP 状态下稳定区分具体业务错误。

**易错点**

- 把统一响应说成行业强制标准。
- 无论成功失败都返回 HTTP 200，只在 `code` 里区分。
- 为了统一 JSON 破坏文件下载、缓存或流式响应语义。

## 430. 统一响应体一般包含哪些字段？

**面试回答**

常见最小集合是业务码 `code`、面向调用方的消息 `message` 和业务数据 `data`；生产系统还可按需要增加 `traceId`、错误明细或分页元数据。字段名称没有统一标准，关键是语义稳定、类型明确，并且不把堆栈、SQL、密钥等内部信息返回客户端。

**原理与理解**

`code` 适合机器判断，`message` 便于人理解，`data` 承载成功结果。`traceId` 能帮助把用户报错与服务端日志关联。校验错误有时需要结构化字段列表，而不是把多个错误拼成不可解析的长字符串。

**成立条件与边界**

- 业务码与 HTTP 状态码是两个维度，命名和取值需在接口文档中定义。
- `message` 不应成为客户端业务分支依据，也不宜暴露内部异常原文。
- `data` 是否为 `null`、缺省或空对象要保持一致约定。
- `timestamp`、`path`、分页信息等是可选字段，不应为了“齐全”机械添加。
- 多语言提示可由稳定错误码配合客户端或服务端国际化实现。

**实际场景**

**真实项目边界：** 简历只能确认项目存在统一响应模型，不能单凭简历断言一定是 `Result<T>{code,msg,data}`；面试前需要打开代码确认字段名、成功码和失败码。

**常见追问**

- 前端应该判断 HTTP 状态还是业务码？两者都要按契约处理，HTTP 状态先表达协议结果，业务码再细分。
- 为什么需要 traceId？方便从用户侧错误定位到对应服务端日志和调用链。
- message 能直接展示吗？要看是否经过安全和用户体验设计，不能直接展示内部异常。

**易错点**

- 把 `code=200` 与 HTTP 200 混为同一个字段。
- 客户端根据中文 message 写逻辑。
- 把异常堆栈或数据库原文放入统一响应。

## 431. 什么是全局异常处理？

**面试回答**

全局异常处理是在 Web 边界集中把 Controller 处理过程中传播出的异常分类、记录并转换为稳定 HTTP 响应。Spring MVC 常用 `@ControllerAdvice` 或 `@RestControllerAdvice` 配合 `@ExceptionHandler`，从而减少重复代码并统一错误契约。

**原理与理解**

业务层抛出异常后，Spring MVC 的异常解析链会查找局部和全局处理方法，再生成状态、响应头和响应体。处理器应把已知业务错误、参数错误、资源冲突和未知系统错误分开；未知异常要保留内部日志，但对外只返回安全信息。

**成立条件与边界**

- Controller 内的局部 `@ExceptionHandler` 通常优先于全局 advice。
- MVC 全局处理器不天然覆盖在进入 Controller 前失败的 Filter、容器错误、定时任务或另一个异步线程。
- 异常被错误吞掉后，全局处理器无法看见，事务回滚语义也可能改变。
- 全局处理是异常到响应的边界，不承担所有恢复、补偿或重试逻辑。
- 日志应避免同一异常在多层重复打印。

**实际场景**

**真实项目边界：** 苍穹外卖使用 `@RestControllerAdvice` 集中捕获业务异常和数据库约束异常，再转换为统一响应；简历未声明 Filter 异常或异步异常如何处理，这些不能扩展成既有能力。

**常见追问**

- 能处理 Filter 抛出的异常吗？通常不能直接依赖 MVC advice，需要在过滤器链或容器错误机制中处理。
- 局部和全局处理器谁优先？Controller 局部处理通常先匹配。
- 未知异常怎么返回？记录完整内部信息并返回通用错误和 traceId，避免泄露细节。

**易错点**

- 把 ControllerAdvice 简单说成 AOP 切面。
- 宣称它可以捕获应用里的任何线程、任何异常。
- 捕获未知异常后既不记录也不告警。

## 432. `@RestControllerAdvice` 有什么作用？

**面试回答**

`@RestControllerAdvice` 是 `@ControllerAdvice` 与 `@ResponseBody` 的组合注解。它把其中的 `@ExceptionHandler`、`@InitBinder` 和 `@ModelAttribute` 方法应用到匹配的 Controller，并让处理方法返回值写入响应体，适合 REST JSON 接口。

**原理与理解**

Spring 在启动时发现 advice Bean，运行时由 MVC 的处理器和异常解析器应用。默认可作用于所有 Controller，也可以用包、注解或类型条件缩小范围。`@ResponseBody` 表示返回值经消息转换器写入响应体，并不保证内容一定是 JSON，实际格式还取决于协商和转换器。

**成立条件与边界**

- 它是组合注解，不等于只能做异常处理；还支持全局绑定和模型增强。
- 默认范围较广，但选择器、Bean 顺序及局部处理器会影响实际匹配。
- 返回响应体不等于固定返回 JSON，媒体类型由内容协商和 `HttpMessageConverter` 决定。
- 对 WebFlux 应使用对应的响应式 Web 栈语义，不能机械套用 MVC 线程模型。
- advice 本身也应避免抛出未受控异常或泄露原始信息。

**实际场景**

**真实项目边界：** 简历明确写明苍穹外卖通过 `@RestControllerAdvice` 捕获业务异常和数据库约束异常，并封装统一响应；可以作为该注解的真实项目回答。

**常见追问**

- 它由哪两个注解组合？`@ControllerAdvice` 和 `@ResponseBody`。
- 能限制作用范围吗？可以按包、注解或可赋值类型筛选 Controller。
- 返回值一定是 JSON 吗？不一定，取决于内容协商和消息转换器。

**易错点**

- 只会回答“全局异常注解”，忽略它的组合关系和其他能力。
- 说它无条件作用于系统全部类。
- 把 `@ResponseBody` 等同于固定 JSON。

## 433. `@ExceptionHandler` 有什么作用？

**面试回答**

`@ExceptionHandler` 声明某个 Controller 或 Advice 方法能够处理哪些异常，并将匹配异常转换成响应。异常类型可以在注解中指定，也可从方法参数推断；通常应为不同错误类别设置合适的 HTTP 状态和稳定错误体。

**原理与理解**

异常从处理方法传播后，Spring MVC 在局部 Controller 和全局 Advice 中寻找最匹配的处理方法。处理方法可以接收异常、请求等参数，并返回响应对象或 `ResponseEntity`。更具体的异常处理应避免被宽泛的 `Exception.class` 处理提前吞掉。

**成立条件与边界**

- 局部处理方法仅作用于所在 Controller 层次；放在 Advice 中才形成跨 Controller 能力。
- 异常匹配存在类型层次，宽泛兜底应放在明确分类之后并谨慎排序。
- 处理方法不是恢复事务的魔法；数据库操作已回滚或已部分完成要结合事务边界判断。
- 参数校验在不同 Spring MVC 方法签名下可能抛出不同异常，需要覆盖真实版本行为。
- 返回错误前要记录或关联必要上下文，但避免重复日志和敏感信息。

**实际场景**

**真实项目边界：** 项目可用不同 `@ExceptionHandler` 方法区分业务异常和数据库约束异常；具体捕获的异常类、响应状态及方法签名需要以仓库代码核验。

**常见追问**

- 不写异常类型可以吗？可以从异常参数推断，但显式声明有时更清晰。
- 可以处理多个异常类型吗？可以，但返回语义相近时再合并。
- 处理后事务还会回滚吗？取决于异常传播到事务拦截器的时机及回滚规则，不能只看 Controller 处理结果。

**易错点**

- 认为注解会在异常发生处立即捕获。
- 用一个 `Exception.class` 把所有错误映射成同一提示。
- 忽略异常处理与事务、日志、HTTP 状态的配合。

## 434. `@ControllerAdvice` 和 `@RestControllerAdvice` 有什么区别？

**面试回答**

两者都提供跨 Controller 的增强；`@RestControllerAdvice` 额外组合了 `@ResponseBody`，所以其方法返回值默认写入响应体。`@ControllerAdvice` 本身没有这个默认行为，返回字符串等值时可能按 MVC 视图规则解析，也可以在具体方法上单独添加 `@ResponseBody`。

**原理与理解**

选择取决于应用输出形态：服务端页面可能需要返回视图，REST API 通常直接返回 JSON 或其他表示。两者的全局范围、筛选方式和异常处理能力相同，差别主要在返回值处理方式，而不是一个能全局、另一个不能全局。

**成立条件与边界**

- `@RestControllerAdvice` 适合响应体接口，但实际媒体类型仍由内容协商决定。
- `@ControllerAdvice` 方法添加 `@ResponseBody` 后也能直接写响应体。
- 两者都可通过属性缩小适用 Controller 范围。
- 两者都不自动覆盖 Filter、Servlet 容器外或任意异步线程异常。
- 项目若同时有页面和 API，可以按包或注解拆分多个 Advice。

**实际场景**

**真实项目边界：** 苍穹外卖属于前后端分离接口，并在简历中明确使用 `@RestControllerAdvice` 封装统一响应，因此选择它符合直接返回响应体的需求。

**常见追问**

- `@ControllerAdvice` 能返回 JSON 吗？可以，在类或方法上配合 `@ResponseBody`。
- 两者异常匹配能力不同吗？核心能力相同，主要区别是默认返回值处理。
- 能同时使用多个 Advice 吗？可以，需要管理范围、顺序和异常分类。

**易错点**

- 说 `@ControllerAdvice` 不能处理异常。
- 说 `@RestControllerAdvice` 必然返回 JSON。
- 忽略页面渲染和 REST API 的不同输出需求。

## 435. 为什么不在每个 Controller 里写 try-catch？

**面试回答**

通用的异常到响应转换如果散落在每个 Controller，会重复、易漏且难以保持状态码和错误体一致，因此应让业务异常向边界传播并集中处理。但当局部代码能够恢复、补偿、释放非自动资源、增加必要上下文或转换异常时，局部 `catch` 仍然合理。

**原理与理解**

Controller 应主要负责协议适配和调用应用服务。集中处理把横切的错误契约放在一个位置；局部处理则负责真正与该业务步骤相关的恢复。捕获异常却继续返回成功，会让事务拦截器和监控误判，因此无法恢复时应保留 cause 并重新抛出合适异常。

**成立条件与边界**

- 不是“绝对不写 try-catch”，而是不要重复做通用响应包装。
- 可以恢复时才继续执行；不能恢复时应重新抛出或返回明确失败。
- 吞掉运行时异常可能导致声明式事务未按预期回滚。
- try-with-resources、finally 与全局异常处理职责不同，仍需正确释放资源。
- 外部调用的重试和补偿要评估幂等性，不能在 catch 中盲目重试。

**实际场景**

**通用工程：** Controller 不为每个数据库错误重复构造响应；服务层若调用外部系统失败且具备明确补偿策略，可在局部捕获、补偿后抛出业务失败，再由 Advice 转换响应。

**常见追问**

- 什么情况应局部 catch？能恢复、补偿、转换或补充上下文时。
- catch 后能直接返回成功吗？只有业务确实恢复成功；否则会隐藏失败。
- 为什么吞异常会影响事务？事务代理可能看不到原异常，从而无法按异常规则回滚。

**易错点**

- 把“集中处理”背成“项目中绝不能写 catch”。
- catch 后只打印日志、不重新抛出。
- 同一个异常在服务层和全局处理器重复打印完整堆栈。

## 436. 什么是业务异常？

**面试回答**

业务异常表示请求在技术上被处理，但违反了业务规则或当前状态不允许执行，例如资源状态冲突、额度不足或重复操作。项目通常用带稳定错误码的自定义异常向上表达，再由边界层转换成适当 HTTP 状态和安全提示。

**原理与理解**

业务失败与程序缺陷不同：前者是可预期的规则分支，后者通常是空指针、配置错误或基础设施故障。自定义异常可以减少层层返回错误码的样板，但高频正常分支也可使用显式结果类型，不能为了“统一”把所有判断都异常化。

**成立条件与边界**

- 业务异常是否 checked/unchecked 是设计选择；在 Spring 事务中会影响默认回滚边界。
- 错误码应稳定，提示可变化，客户端不应解析异常类名或文本。
- 业务异常也不能暴露敏感规则，例如账户是否存在等可被枚举的信息。
- 不是所有业务失败都映射 HTTP 500；可根据语义使用 400、404、409、422 等。
- 异常不能替代数据库约束和并发控制。

**实际场景**

**真实项目边界：** 简历确认项目全局捕获业务异常，但没有列出具体异常类、错误码和案例；面试时可说明整体机制，具体例子需从代码中选取真实的一项。

**常见追问**

- 业务异常和系统异常怎么区分？前者是可预期规则不满足，后者通常是代码或基础设施失败。
- 业务异常一定返回 200 吗？不应如此，HTTP 状态应反映失败语义。
- 为什么常用运行时异常？可减少签名传播并配合默认事务回滚，但仍需规范分类。

**易错点**

- 把所有异常都包装成业务异常。
- 业务失败统一返回 500 或 200。
- 编造简历未出现的具体业务异常案例。

## 437. 数据库异常为什么不应该直接返回前端？

**面试回答**

原始数据库异常可能包含 SQL、表列名、约束名、连接信息和数据片段，既不稳定也可能泄露内部结构。正确做法是服务端记录受控的诊断信息和 traceId，把异常分类为冲突、暂时故障或未知错误，再向客户端返回稳定且安全的响应。

**原理与理解**

Spring 数据访问层可把部分厂商异常翻译为统一的 `DataAccessException` 层次，例如完整性约束失败对应 `DataIntegrityViolationException`。应用应依赖可识别的异常类别和业务约束，而不是把厂商错误原文当作 API 契约。

**成立条件与边界**

- 日志也要脱敏，不能因“不返回前端”就记录密码、Token 或完整个人信息。
- 已知唯一约束冲突可转换为 409 等业务可理解响应；连接中断等不应伪装成“字段重复”。
- 未知异常对外可返回通用提示，对内必须保留 cause、堆栈和请求关联信息。
- 生产错误响应不应包含堆栈，开发环境调试信息也要控制访问范围。
- 异常翻译的具体类型取决于数据访问框架和配置。

**实际场景**

**真实项目边界：** 苍穹外卖简历明确处理数据库约束异常并封装统一响应；能够说明“内部保留诊断信息、外部返回友好错误”，但日志字段和状态码仍需代码核验。

**常见追问**

- 数据库异常都返回系统繁忙吗？不应；可识别的约束冲突应给出稳定业务语义，未知故障再使用通用错误。
- 日志要记录什么？traceId、异常类别、必要上下文和堆栈，同时脱敏。
- Spring 如何统一数据库异常？通过数据访问异常翻译形成 `DataAccessException` 层次，具体依赖集成方式。

**易错点**

- 把 SQL 异常原文直接放进 message。
- 所有数据库异常都映射成“重复数据”。
- 对外隐藏细节后，对内也不记录 cause，导致无法排查。

## 438. 唯一约束异常如何转换成友好提示？

**面试回答**

数据库唯一约束应作为并发下的最终唯一性防线。应用捕获经框架翻译的完整性或重复键异常，根据稳定的约束名映射为业务错误码和友好提示，并返回合适的冲突状态；不要依赖本地化的数据库错误整句，也不要把重复值原样返回。

**原理与理解**

“先查后插”只能优化用户体验，两个并发请求仍可能同时通过检查。唯一索引让最终写入原子地只成功一次；失败请求再由异常处理器翻译。如果多个唯一约束对应不同业务语义，最好为约束设置稳定名称并维护显式映射。

**成立条件与边界**

- Spring 的 `DuplicateKeyException` 属于数据完整性异常层次，但实际抛出类型取决于框架、驱动和异常翻译配置。
- 解析厂商错误消息脆弱，优先读取结构化错误信息或稳定约束名；无法可靠识别时返回通用冲突。
- 并非所有 `DataIntegrityViolationException` 都是唯一键冲突，也可能是非空、外键或长度等约束。
- 对重复注册等场景要防用户枚举，提示详细度需要结合安全策略。
- 约束异常发生后，当前事务通常应回滚，不能在同一失败事务里继续正常写入。

**实际场景**

**真实项目边界：** 简历确认苍穹外卖会处理数据库约束异常，但没有指定是用户名、菜品名还是其他唯一键；可以回答“约束异常被全局翻译”，不能编造具体冲突字段。

**常见追问**

- 为什么不能只先查再插？存在并发竞态，数据库唯一约束才是最终保证。
- 如何区分不同唯一约束？使用稳定约束名或结构化厂商错误码做映射，并保留通用回退。
- 为什么常返回 409？它表达当前资源状态与请求冲突；具体仍服从项目 API 契约。

**易错点**

- 把 `DataIntegrityViolationException` 一律当重复键。
- 用字符串切割完整数据库错误作为唯一识别方案。
- 把冲突值、SQL 或索引内部细节回传前端。
