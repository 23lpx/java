# 统一响应与异常处理

## 429. 为什么后端需要统一响应结构？

**面试回答**

为了让所有接口返回格式一致（统一的状态码、消息、数据），前端能按统一规则解析处理，避免每个接口返回结构各不相同、前端要写一堆兼容逻辑。

**理解**

如果每个接口各返回各的（有的直接返回数据、有的返回对象、错误时又是另一种），前端要针对每个接口写不同解析逻辑，非常痛苦且易错。统一响应结构（如 `{code, msg, data}`）让前端一套代码处理所有成功/失败情况，也方便全局异常处理和日志规范。

**场景**

项目里定义了统一的 `Result<T>` 结构，所有接口都返回它，前端统一解析 code 判断成功失败、取 data。

**常见追问**

- 统一响应一般含什么？（code、msg、data）
- 有什么好处？（前端易解析、错误处理统一）

**易错点**

统一响应的核心是「约定一致的返回格式」，让前后端协作简单；不是「所有接口返回一模一样的内容」。

## 430. 统一响应体一般包含哪些字段？

**面试回答**

一般包含：状态码（code，标识成功/失败及错误类型）、消息（msg，给用户的提示）、数据（data，业务数据，可能为空）。

**理解**

典型结构 `Result<T>{ Integer code; String msg; T data; }`：code 区分成功（如 1/200）和各种失败；msg 是给前端/用户的描述（如「操作成功」「用户名已存在」）；data 承载实际返回数据。这样的三要素能满足绝大多数接口。

**场景**

项目里 Result 就是 code + msg + data 三字段，成功时 data 有值，失败时 msg 说明原因。

**常见追问**

- 三个字段分别干嘛？（code 状态、msg 提示、data 数据）
- code 一般怎么设计？（成功一个值，各种错误各一个值）

**易错点**

统一响应体核心三要素「code、msg、data」；code 和 HTTP 状态码是两回事，别混淆。

## 431. 什么是全局异常处理？

**面试回答**

全局异常处理是集中处理整个应用抛出的异常：用一个（或几个）处理器拦截所有 Controller 层抛出的异常，统一转成规范响应，而不是在每个接口里写 try-catch。

**理解**

业务里到处可能抛异常（业务异常、参数校验异常、数据库异常），如果每个方法都 try-catch，代码重复且易漏。全局异常处理用 @RestControllerAdvice + @ExceptionHandler，在一个地方「兜底」所有异常，按异常类型返回对应的统一响应。这样异常处理集中、规范。

**场景**

项目里用 @RestControllerAdvice 全局异常处理器，统一捕获业务异常、参数校验异常等，返回规范的 Result。

**常见追问**

- 为什么集中处理？（避免每个接口重复 try-catch，统一返回）
- 怎么实现？（@RestControllerAdvice + @ExceptionHandler）

**易错点**

全局异常处理是「集中兜底」，靠 AOP/ControllerAdvice 拦截异常；它让异常处理从「分散」变「统一」。

## 432. `@RestControllerAdvice` 有什么作用？

**面试回答**

@RestControllerAdvice 是 Spring 的全局异常处理（和全局数据绑定）注解，标记一个类为全局增强，让里面的 @ExceptionHandler 能拦截所有 Controller 抛出的异常，并把处理结果直接作为响应体返回。

**理解**

它 = @ControllerAdvice + @ResponseBody：既能全局拦截 Controller 的异常，又能把返回值直接序列化成 JSON 响应（不用返回视图）。通常配合 @ExceptionHandler 方法，定义「遇到某异常返回什么」。

**场景**

项目里 GlobalExceptionHandler 类标 @RestControllerAdvice，集中处理所有接口的异常并返回统一 Result。

**常见追问**

- 它 = 哪两个注解的组合？（@ControllerAdvice + @ResponseBody）
- 作用范围？（全局，所有 Controller）

**易错点**

@RestControllerAdvice 是「全局 + 返回 JSON」，是全局异常处理的载体；要记住它 = ControllerAdvice + ResponseBody。

## 433. `@ExceptionHandler` 有什么作用？

**面试回答**

@ExceptionHandler 用在方法上，指定「处理哪种异常」：当 Controller 抛出该类型异常时，就由这个方法捕获处理，返回自定义的响应。

**理解**

在 @RestControllerAdvice 类里，多个方法各标 @ExceptionHandler(XxxException.class)，分别处理不同异常。比如 @ExceptionHandler(BusinessException.class) 处理业务异常，@ExceptionHandler(MethodArgumentNotValidException.class) 处理参数校验异常。它把「异常类型」和「处理逻辑」对应起来。

**场景**

项目里全局异常处理器用多个 @ExceptionHandler 方法，分别处理业务异常、参数校验异常、数据库唯一约束异常等。

**常见追问**

- 它指定什么？（要处理的异常类型）
- 能处理多个类型吗？（能，value 里可写多个 class）

**易错点**

@ExceptionHandler 是「异常类型 → 处理方法」的映射，配合 @RestControllerAdvice 实现全局捕获。

## 434. `@ControllerAdvice` 和 `@RestControllerAdvice` 有什么区别？

**面试回答**

@RestControllerAdvice 是 @ControllerAdvice + @ResponseBody 的组合：两者都能全局处理异常，但 @RestControllerAdvice 的方法返回值会直接序列化成响应体（JSON），@ControllerAdvice 的方法返回值默认可能被当视图名处理。

**理解**

@ControllerAdvice 只做「全局增强」，方法返回值按普通 Controller 处理（可能解析为视图）；@RestControllerAdvice 在此基础上加了 @ResponseBody，返回值直接写进响应体，适合前后端分离返回 JSON。所以做统一异常返回 JSON，用 @RestControllerAdvice 更方便。

**场景**

项目里前后端分离、统一返回 JSON，所以用 @RestControllerAdvice，异常处理结果直接作为 JSON 响应。

**常见追问**

- 两者关系？（RestControllerAdvice = ControllerAdvice + ResponseBody）
- 返回 JSON 用哪个？（@RestControllerAdvice）

**易错点**

区别就在「@ResponseBody」：RestControllerAdvice 返回 JSON，ControllerAdvice 返回视图；选对能少写 @ResponseBody。

## 435. 为什么不在每个 Controller 里写 try-catch？

**面试回答**

因为会导致代码重复、容易遗漏、异常处理逻辑散落各处难维护；用全局异常处理集中处理，一处定义、全局生效，代码更简洁统一。

**理解**

如果每个接口都 try-catch，几十个接口就有几十段重复的异常处理，改了规则要改几十处，还容易漏。全局异常处理把「异常 → 响应」的映射集中到一个类，所有接口自动生效，新增异常类型也只需加一个方法。这是「关注点分离」——业务方法专注业务，异常处理交给全局。

**场景**

项目里 Controller 方法都很干净，不写 try-catch，异常统一抛给全局异常处理器兜底。

**常见追问**

- 全局处理的好处？（集中、不重复、易维护）
- 业务方法该不该 catch？（不该吞异常，交全局处理，特殊场景才局部处理）

**易错点**

「全局 vs 局部」是设计取舍：通用异常全局处理，特殊补偿逻辑才局部 catch；不是「绝对不能 catch」。

## 436. 什么是业务异常？

**面试回答**

业务异常是「业务规则不满足」时主动抛出的自定义异常，比如用户名已存在、库存不足、状态不允许操作等，用来向调用方/用户传达业务层面的失败。

**理解**

业务异常不是程序 bug，而是「程序正常运行，但业务规则不通过」——比如用户重复注册、密码错误。我们定义一个 BusinessException（含错误码、提示信息），在业务逻辑里校验不通过就抛出，全局异常处理器捕获后返回对应提示。它让「业务失败」和「系统错误」区分开。

**场景**

项目里定义 BusinessException，比如菜品已关联套餐不能删、登录密码错误，就抛业务异常并返回友好提示。

**常见追问**

- 业务异常和系统异常区别？（业务异常是规则不满足，系统异常是程序出错）
- 为什么自定义？（带上业务错误码和提示信息，区分处理）

**易错点**

业务异常是「主动抛出的规则失败」，不是「程序崩溃」；它让业务错误能友好返回、统一处理。

## 437. 数据库异常为什么不应该直接返回前端？

**面试回答**

因为数据库异常信息包含内部实现细节（表名、SQL、字段名等），直接返回会泄露系统内部结构、存在安全风险，而且对用户也不友好；应转换成通用的友好提示。

**理解**

数据库异常（如 SQL 语法错误、约束冲突）的原始信息很技术化，可能暴露表结构、字段名等敏感信息，攻击者可借此摸清数据库。同时用户看不懂「Duplicate entry xxx」这种信息。正确做法是全局异常处理器捕获后，记日志（供排查），返回给用户一句友好、不泄露细节的提示。

**场景**

项目里数据库异常被全局处理器捕获，记录详细日志，但前端只返回「系统繁忙，请稍后重试」这类友好提示。

**常见追问**

- 直接返回有什么风险？（泄露内部结构、安全风险）
- 正确做法？（记日志 + 返回友好提示）

**易错点**

数据库异常「日志里详细、前端友好」是原则；既不能裸奔给前端，也不能啥都不记导致难排查。

## 438. 唯一约束异常如何转换成友好提示？

**面试回答**

在全局异常处理器里，捕获数据库唯一约束冲突异常（如 MySQL 的 DuplicateKeyException），判断冲突的字段，转换成「用户名已存在」「该字段已重复」等友好提示返回。

**理解**

唯一约束冲突（如重复注册用户名）在 MySQL 层抛 DuplicateKeyException，原始信息是「Duplicate entry ... for key ...」，看不懂。全局异常处理器捕获后，可以解析是哪个唯一索引冲突，映射成对应业务提示（「用户名已被注册」）。这样用户在界面上看到的是友好提示，而不是数据库报错。

**场景**

项目里用户重复注册时，数据库抛唯一约束异常，全局处理器捕获并返回「该用户名已存在」。

**常见追问**

- 为什么不能在业务里先查再插？（并发下「先查后插」仍有竞态，唯一约束是最终兜底）
- 异常信息从哪知道冲突字段？（解析异常里的 key 名，或预先约定）

**易错点**

唯一约束是「数据库层兜底」，靠它保证唯一，再在异常处理里「翻译」成友好提示；光靠先查后插并发下不可靠。
