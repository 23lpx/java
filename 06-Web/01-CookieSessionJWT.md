# CookieSessionJWT

## 381. Cookie 是什么？

**面试回答**

Cookie 是用户代理为某个站点保存的一小段状态数据。服务器通常通过 `Set-Cookie` 响应头创建 Cookie；后续请求满足域、路径、有效期、`Secure` 和 `SameSite` 等发送条件时，浏览器才会在 `Cookie` 请求头中携带它。Cookie 常用于会话标识、偏好设置，但它本身不是认证机制。

**原理与理解**

Cookie 由名称、值和属性组成。`Domain`、`Path` 控制作用范围，`Expires`/`Max-Age` 控制生命周期；`Secure` 限制经安全通道发送，`HttpOnly` 阻止脚本通过非 HTTP API 读取，`SameSite` 限制跨站请求携带。浏览器按规则存储、匹配和淘汰 Cookie，并非“该浏览器的每次请求都会带上全部 Cookie”。

**成立条件与边界**

- RFC 6265 要求通用用户代理至少具备每个 Cookie 4096 字节等最低处理能力，这不是所有浏览器、属性组合下都严格相同的业务可用上限；Cookie 应保持小而少。
- `HttpOnly` 降低脚本直接读取 Cookie 的风险，但不能修复 XSS，也不阻止浏览器自动发送 Cookie。
- `Secure` 保护发送通道的选择，不等于 Cookie 内容已加密；仍应使用 HTTPS 并防止泄露。
- `SameSite` 是 CSRF 防线之一，不应替代来源校验、CSRF Token 等完整防护。
- `Path` 主要用于发送范围匹配，不是可靠的安全隔离边界。

**实际场景**

**通用工程：** 使用服务端 Session 时，可让浏览器保存随机 Session ID Cookie，并配置 `HttpOnly`、`Secure`、合理的 `SameSite`、作用域和有效期；服务端保存真实会话状态并在退出时失效会话。

**常见追问**

- 浏览器什么时候携带 Cookie？满足域、路径、有效期、安全通道和同站策略等条件时。
- `HttpOnly` 和 `Secure` 分别解决什么？前者限制脚本读取，后者限制通过安全通道发送，二者作用不同。
- Cookie 一定是持久化文件吗？不一定；未设置持久化生命周期的会话 Cookie 通常随当前会话结束处理，具体恢复行为受浏览器实现影响。

**易错点**

- 说浏览器“每次请求都会带上 Cookie”，忽略匹配和安全属性。
- 把约 4KB 背成所有实现都完全一致的硬上限。
- 把 Cookie、Session 或登录认证当成同一个概念。

## 382. Session 是什么？

**面试回答**

Session 是服务端把多次 HTTP 请求关联为同一会话的一种状态管理机制。以 Servlet 为例，`HttpSession` 保存会话属性，客户端通常只携带一个难以预测的 Session ID；服务器据此定位会话。Cookie 是最常见的 ID 传递方式，必要时也可能使用 URL 重写。

**原理与理解**

HTTP 本身不替业务保存登录上下文。登录成功后，服务器可以建立“Session ID → 会话数据”的映射，并把 ID 交给客户端；后续请求携带 ID，容器或应用恢复对应的 `HttpSession`。会话数据可位于单机内存、共享存储或容器提供的复制机制中，不能一概说成只在 JVM 内存。

**成立条件与边界**

- Session ID 本质上是持有者凭证；即使会话数据在服务端，ID 被窃取仍可能导致会话劫持。
- 认证前后应更新 Session ID，退出、超时、改密等事件应按策略失效会话，以降低固定会话和长期盗用风险。
- URL 重写会让 ID 出现在地址栏、日志、书签、Referer 或缓存中，有可用 Cookie 时不宜采用。
- 分布式部署可使用共享 Session、复制、粘性会话等方案，各自有一致性、可用性和运维成本。
- Session 只解决会话关联；每个请求仍需做权限和资源归属校验。

**实际场景**

**通用工程：** 管理后台使用 Session 登录时，认证成功后创建会话并更新 ID；请求根据 Session ID 恢复管理员身份，退出时服务端失效会话，而不是只删除浏览器 Cookie。

**常见追问**

- Session 一定存在内存吗？不一定，可由容器放在内存，也可共享、复制或持久化。
- 客户端一定通过 Cookie 传 ID 吗？Cookie 最常见；Servlet 还支持 URL 重写，但安全暴露面更大。
- Session 数据在服务端就绝对安全吗？不是，Session ID 泄露、固定会话和服务端越权仍会破坏安全。

**易错点**

- 把 Session 定义成“服务器内存里的用户对象”，忽略实现方式。
- 认为客户端不能改会话内容，所以 Session ID 无需保护。
- 退出时只删 Cookie，不失效服务端会话。

## 383. Cookie 和 Session 有什么区别？

**面试回答**

Cookie 是浏览器保存并按规则随请求发送的数据载体；Session 是服务器关联多次请求并保存会话状态的机制。二者不是二选一：常见 Session 方案正是用 Cookie 携带 Session ID，服务端再通过 ID 找到会话数据。

**原理与理解**

可从职责区分：Cookie 解决客户端状态的存储和传输，Session 解决服务端会话状态的关联。Cookie 值会到达客户端，容量和发送范围受浏览器规则限制；Session 状态由服务端管理，会消耗存储并涉及过期、共享和容灾。安全性不能只用“Cookie 不安全、Session 安全”概括，因为 Session ID 也常放在 Cookie 中且必须像密码一样保护。

**成立条件与边界**

- Cookie 可单独保存非敏感偏好，也可只保存会话 ID；不能默认其中一定有完整用户信息。
- Session 可通过 Cookie 之外的机制关联，但 URL 携带 ID 通常风险更高。
- Cookie 可被篡改不代表服务端必须信任；服务端应签名、校验或把它仅作为不透明标识。
- Session 的扩展难点取决于架构；共享存储、粘性会话和复制都能支持多实例，但会引入不同代价。
- Cookie 的安全属性与服务端 Session 生命周期都要配置，任何一边缺失都可能形成漏洞。

**实际场景**

**通用工程：** 登录态采用 Session 时，Cookie 只保存随机 ID，身份、权限快照和失效状态留在服务端；服务端不能因为 ID 格式合法就跳过会话存在性、超时和权限检查。

**常见追问**

- 为什么说二者常配合？Cookie 负责传 Session ID，Session 负责保存服务端状态。
- 哪个更安全？不能脱离威胁模型；关键在 HTTPS、Cookie 属性、ID 随机性、会话轮换和服务端校验。
- 分布式 Session 怎么做？常见有共享存储、会话复制或粘性路由，需要结合一致性与可用性选择。

**易错点**

- 简化为“Cookie 客户端不安全，Session 服务端绝对安全”。
- 认为 Cookie 存的一定是业务数据，或 Session 一定只存内存。
- 把 Cookie 与 Session 描述成互斥认证方案。

## 384. Token 是什么？

**面试回答**

Token 是客户端访问资源时提交的一种凭证或标识。它可以是不透明随机串，也可以是 JWT 这类自包含令牌；可以依赖服务端查询状态，也可以本地验签。`Bearer Token` 表示“持有即可使用”，因此谁拿到它谁就可能冒用，必须保护存储和传输。

**原理与理解**

不透明 Token 通常只负责索引服务端状态，资源服务器需要查库或调用内省服务；自包含 Token 可携带声明并通过签名在本地验证。Token 的格式、签发者、接收者、作用域、有效期和撤销策略共同决定其安全语义，不能从“叫 Token”推导它一定有签名、一定无状态或一定是 JWT。

**成立条件与边界**

- Token 是上位概念，JWT 只是可能的格式之一；Session ID 也可视为一种不透明会话 Token。
- Bearer Token 不能证明请求者就是最初领取者，除非额外采用发送者约束等机制。
- Token 不应放在 URL 查询参数中作为常规方案，URL 容易进入日志、历史记录和 Referer。
- 使用 `Authorization: Bearer <token>` 是标准常见方式，但具体项目也可能使用安全 Cookie；二者的 XSS、CSRF 边界不同。
- 身份认证通过不等于有权操作当前资源，仍要执行授权。

**实际场景**

**真实项目边界：** 简历确认项目登录认证使用 JWT。现有材料没有确认 Token 存储位置、请求头名称或刷新机制，这些只能作为项目核验项，不能在面试中临时补造。

**常见追问**

- Token 都是无状态的吗？不是，不透明 Token 通常依赖服务端状态，JWT 也可能配合撤销状态。
- Token 和 JWT 是什么关系？Token 是凭证概念，JWT 是一种标准化令牌格式。
- 为什么不建议放 URL？容易被日志、浏览器历史、Referer 等记录并泄露。

**易错点**

- 把 Token 直接定义成“签名后的无状态字符串”。
- 把 Bearer Token 当成只有原用户才能使用的身份证明。
- 认证成功后跳过权限和数据归属检查。

## 385. JWT 是什么？

**面试回答**

JWT（JSON Web Token，RFC 7519）是一种紧凑、URL 安全的声明表示格式。声明可被封装为 JWS 以签名或 MAC，也可封装为 JWE 以加密；登录认证中最常见的是三段式签名 JWT。它经常用于自包含访问令牌，但“JWT”本身不等于登录协议或完整认证方案。

**原理与理解**

JWT 的核心是传递一组 JSON Claims，并借助 JOSE 规范提供完整性、来源验证或机密性。资源服务器只有在信任签发者、使用允许的算法和密钥、验证时间及受众等声明后，才能把它当作凭证。RFC 7519 将 JWT 的英文读音说明为类似 `jot`；面试中直接读字母 J-W-T 也便于沟通。

**成立条件与边界**

- 常见签名 JWT 是 JWS，防篡改但不隐藏 Payload；需要机密性时应使用适合的加密机制或 JWE。
- JWT 可以减少逐请求会话查询，但系统仍可能维护密钥、撤销、用户状态和刷新令牌等状态。
- JWT 不天然解决跨域、CSRF、XSS、注销或权限更新问题。
- 标准允许多种表示和可选声明，具体认证协议必须规定必需算法与 Claims。
- 不应接受未签名 JWT 或由输入任意选择的算法作为认证凭证。

**实际场景**

**真实项目边界：** 项目使用 JWT 传递登录身份，并通过拦截链恢复请求上下文；其算法、密钥管理、Claims 和有效期需要回到代码与配置核验。

**常见追问**

- JWT 一定是三段吗？常见紧凑 JWS 是三段；紧凑 JWE 是五段，不能把 JWT 标准只等同于三段签名形式。
- JWT 一定无状态吗？格式本身不决定系统是否保存撤销或会话状态。
- JWT 与 JWS/JWE 什么关系？JWT Claims 可以作为 JWS 的载荷或 JWE 的明文。

**易错点**

- 回答“JWT 就是 Header、Payload、Signature 三段”，不说明这是常见 JWS 形式。
- 把 JWT 说成加密算法或完整登录协议。
- 认为采用 JWT 后系统天然安全、无状态且可立即注销。

## 386. JWT 由哪三个部分组成？

**面试回答**

面试通常问的是紧凑序列化的签名 JWT，也就是 JWS：`protected-header.payload.signature`，三段均使用 Base64URL 表示并以 `.` 分隔。第一段是受保护头，第二段承载 Claims，第三段是签名或 MAC。边界是：JWT 也可使用五段式 JWE，因此“三段”不是所有 JWT 的普遍定义。

**原理与理解**

验签输入通常是前两段编码值以点号连接后的字节序列。服务端按预先允许的算法与可信密钥验证第三段，再解析和验证 Claims。Base64URL 只是适合 URL 的编码，不提供机密性；任何拿到常见 JWS Token 的人通常都能还原头和 Payload。

**成立条件与边界**

- 三段结论仅针对紧凑 JWS；紧凑 JWE 包含受保护头、加密密钥、初始化向量、密文和认证标签五段。
- Payload 可为空或包含不同内容，认证应用通常放 JWT Claims，但必须按协议校验。
- 不能只解码前两段就认为 Token 有效，必须先完成正确的密码学验证。
- 解码库成功解析不等于算法、密钥、签发者、受众和有效期都通过。
- 令牌长度受 Claims、算法和密钥类型影响，不宜在 Header 中塞入冗余数据。

**实际场景**

**通用工程：** 排查三段式 Token 时，可以解码前两段观察非敏感元数据，但线上日志应脱敏；认证判断必须走统一验证组件，不能让调试解码结果替代验签。

**常见追问**

- 三段分别是什么？受保护头、载荷、签名或 MAC。
- 为什么用 Base64URL？便于在 URL 和 HTTP 等文本环境中安全表示二进制数据。
- 五段 JWT 是什么？通常是紧凑序列化的 JWE，用于加密保护内容。

**易错点**

- 把 Base64URL 说成加密。
- 只要能拆成三段就当作合法 JWT。
- 忘记“三段式”是常见签名 JWT 的上下文结论。

## 387. Header 中通常保存什么？

**面试回答**

签名 JWT 的受保护 Header 通常包含 `alg`，可选包含 `typ`、`kid` 等参数：`alg` 标识密码算法，`typ` 可标识对象类型，`kid` 可帮助选择密钥。但这些字段来自不可信 Token，验证端必须预先配置允许算法和可信密钥，不能盲目按 `alg` 或 `kid` 执行。

**原理与理解**

Header 参与 JWS 签名输入，因此验签成功后能检测其是否被修改；但在验证完成前，它仍只是攻击者可控的选择提示。安全实现会按令牌用途固定或白名单化算法，限定签发者对应的密钥集合，并安全处理 `kid` 等查找参数，防止算法混淆、路径或 SQL 注入、恶意远程密钥引用。

**成立条件与边界**

- `typ` 是可选参数，不能因为缺少它就一概断言不合法；新设计可使用显式类型帮助隔离不同 JWT 用途。
- `alg` 声明不等于服务端授权该算法，允许集合必须来自可信配置。
- `kid` 只是密钥选择提示，不是密钥本身，也不应未经校验拼接文件路径或查询语句。
- HMAC 与非对称签名的密钥角色不同，不能因名称相似而混用验证逻辑。
- Header 一般可被解码查看，不应放密码、密钥或其他秘密。

**实际场景**

**项目核验项：** 简历未确认项目使用 HS256、RS256 或 `kid`。面试前应从 JWT 工具类和配置核验“允许算法、密钥来源、轮换方式”，不能直接沿用第一版中的 HS256 说法。

**常见追问**

- 服务端能否直接相信 `alg`？不能，只能接受可信配置允许的算法。
- `kid` 有什么用？在受控密钥集合中提示选择哪把密钥，但其输入仍需安全处理。
- `typ` 必须是 `JWT` 吗？标准中通常可选，应用 Profile 可另行要求。

**易错点**

- 根据 Token 自报的 `alg` 动态开放算法。
- 把 `kid` 当成已验证的可信路径或地址。
- 未核验代码就声称项目使用 HS256。

## 388. Payload 中通常保存什么？

**面试回答**

Payload 保存 Claims。常见注册声明有 `iss`（签发者）、`sub`（主体）、`aud`（受众）、`exp`（过期时间）、`nbf`（生效时间）、`iat`（签发时间）和 `jti`（唯一标识）；还可放最小化的业务声明。具体哪些必需由应用协议决定，RFC 7519 并未要求所有 JWT 都包含这些字段。

**原理与理解**

Claims 不只是“把 userId 放进去”。验证方应使用 `iss` 建立信任边界，用 `aud` 防止令牌被投递到错误服务，用时间声明控制生命周期，并按业务需要使用 `jti` 做追踪或撤销。权限、角色等变化频繁的数据放入长效 Token 会形成陈旧授权，因此应最小化并在高风险操作时查询权威状态。

**成立条件与边界**

- 常见签名 JWT 的 Payload 可被任何持有者解码，不应存密码、密钥、身份证号等秘密或不必要个人数据。
- `exp` 等注册声明在基础标准中是可选的，但认证 Profile 通常应强制短生命周期并校验相关字段。
- `iat` 不是过期时间，`sub` 也不一定等同数据库用户主键，必须按协议解释。
- `aud` 可能是单个值或数组，验证端要判断自己是否为预期接收者。
- Claims 验证通过只建立 Token 语义，不替代数据库中的实时封禁、权限和对象归属判断。

**实际场景**

**项目核验项：** 简历只能确认解析 Token 并传递用户上下文，不能确认 Payload 必然包含 `userId`、用户类型或哪些时间声明；需要读取签发与解析代码后再形成项目话术。

**常见追问**

- `exp`、`nbf`、`iat` 有何区别？分别是过期、生效前不可接受、签发时间。
- Payload 能放角色吗？可以，但要考虑权限变更后的陈旧数据和最小化原则。
- `jti` 有什么用？提供令牌唯一标识，可辅助防重放、审计或撤销，但需要配套服务端状态。

**易错点**

- 把所有注册声明都说成 JWT 强制字段。
- 在 Payload 放敏感信息，误以为签名能保密。
- 把 Token 内角色当成永久可信的实时权限。

## 389. Signature 有什么作用？

**面试回答**

签名或 MAC 用于验证令牌的完整性，并在密钥信任模型成立时确认其来源：攻击者修改受保护 Header 或 Payload 后，通常无法生成有效结果。它不提供内容机密性，也不自动阻止合法 Token 被复制重放。

**原理与理解**

JWS 会对受保护头编码值和 Payload 编码值组成的签名输入执行密码算法。HMAC 使用同一秘密做 MAC 和验证，任何持有秘密的一方都能签发；RSA、ECDSA 等通常由私钥签名、公钥验证。验证端还必须限定算法、选择与签发者和用途绑定的密钥，并验证 Claims，不能只调用“解析”接口。

**成立条件与边界**

- 签名有效只能说明相对于所用密钥内容未变且来源满足该密钥模型，不代表该用户仍启用或请求已获授权。
- HMAC 密钥必须高熵并严格保管，不能使用人类可记密码充当弱秘密。
- 公钥验证者通常不能伪造非对称签名；HMAC 验证者因为共享秘密也具备生成能力。
- 算法混淆、接受 `none`、错误选钥或跳过 `iss`/`aud` 等校验都会破坏整体安全。
- 合法 Token 被窃取后签名仍然有效，需要 TLS、短有效期和撤销/发送者约束等降低风险。

**实际场景**

**通用工程：** 统一 JWT 验证组件应先按可信配置限定算法和密钥，再验证签名、签发者、受众、时间及用途；业务代码只接收验证后的身份对象，避免各接口自行解码。

**常见追问**

- 签名和加密区别？签名主要保证完整性和来源，JWE 等加密才提供机密性。
- HMAC 与 RSA 验签差异？HMAC 共享同一秘密；RSA 通常私钥签、公钥验。
- 签名有效能防重放吗？不能，攻击者复制完整有效 Token 仍可能使用。

**易错点**

- 说签名能让 Payload 不可见。
- 只验签，不验签发者、受众、有效期和用途。
- 直接接受 Token 指定的任意算法或密钥位置。

## 390. JWT 为什么可以实现无状态认证？

**面试回答**

自包含签名 JWT 可把身份与时间等声明随请求带来，资源服务器依靠本地可信密钥和验证规则完成校验，不必每次按 Session ID 查询中心会话。因此“请求认证路径”可以无会话状态并易于多实例扩展，但不能说整个认证系统完全没有状态。

**原理与理解**

Session 方案通常通过不透明 ID 查找服务端会话；JWT 方案可在每台资源服务器本地验证签名、`iss`、`aud`、`exp` 等并提取主体。省去中心查询换来的是 Token 生命周期内 Claims 可能陈旧，以及单个 Token 难以立即撤销。密钥发布和轮换、用户禁用、Token 版本、拒绝列表、刷新令牌仍可能依赖服务端状态。

**成立条件与边界**

- 只有资源服务器具备可信密钥且不依赖逐请求会话查询时，才能称该认证路径相对无状态。
- 引入拒绝列表、内省或用户状态查询后会重新产生状态与网络依赖，这是可接受的安全权衡。
- 多实例能本地验签不等于自动完成密钥轮换、权限同步和故障隔离。
- 自包含 Claims 不应承载长期不变假设；重要权限变更需要缩短过期时间或查询权威源。
- 无状态与跨域是不同问题，浏览器 CORS 和凭证发送规则仍需独立配置。

**实际场景**

**真实项目边界：** 项目由拦截器解析 JWT 后写入 ThreadLocal 供当前请求使用，这说明请求上下文可由 Token 恢复；现有材料不足以证明系统完全不查用户状态或没有任何撤销状态。

**常见追问**

- “无状态”具体指什么？通常指服务端不按每个访问 Token 保存并查询中心会话。
- 为什么适合多实例？各实例拿到可信验证材料后可独立校验，但仍要同步密钥和策略。
- 无状态的代价是什么？撤销困难、声明陈旧、Token 较大和安全配置更复杂。

**易错点**

- 回答“用了 JWT，服务端完全没有任何状态”。
- 认为每台机器能验签就不需要密钥轮换和用户状态策略。
- 把 JWT 无状态等同于无跨域限制。

## 391. JWT 中的数据是加密的吗？

**面试回答**

要区分表示形式：常见三段式签名 JWT（JWS）通常没有加密，Header 和 Payload 只是 Base64URL 表示，持有者可以读取；签名只保护完整性。JWT 标准也允许使用 JWE 对 Claims 加密，所以“JWT 永远不加密”和“JWT 默认能保密”都不准确。

**原理与理解**

Base64URL 是可逆编码。JWS 的第三段让验证方发现前两段被修改，却不会隐藏其内容；JWE 才通过加密密钥、初始化向量、密文和认证标签提供机密性与完整性。即便采用 JWE，也应遵守数据最小化，避免把不必要的密码和秘密长期放进客户端持有的令牌。

**成立条件与边界**

- 看到三段式 JWT 时通常按“可读、不可随意篡改”理解，但仍需核验使用的具体序列化和算法。
- TLS 保护传输链路，不会让已经泄露到日志或前端脚本的 Token 自动安全。
- 加密不等于完成身份认证；仍需验证发行者、受众、时间和算法等语义。
- JWE 增加密钥管理、长度和计算成本，是否使用取决于机密性需求。
- 即使 Payload 不敏感，完整 Token 作为 Bearer 凭证仍是秘密，不能公开记录。

**实际场景**

**通用工程：** 调试 JWT 时只记录摘要、`jti` 或脱敏字段，不打印完整 Token。不要因为 Payload 看起来只是 userId，就忽略完整 Token 泄露后可被重放的风险。

**常见追问**

- Base64URL 是加密吗？不是，只是编码。
- 什么形式能让 JWT 内容不可读？可使用 JWE，但仍要做完整的令牌语义校验。
- Payload 可见，为什么完整 Token 仍不能泄露？因为签名有效的 Bearer Token 可被持有者直接重放。

**易错点**

- 绝对回答“JWT 的数据都没有加密”，忽略 JWE。
- 认为只要不放密码，完整 Token 就可以写日志或发到群里。
- 把 HTTPS 与令牌内容加密混为一谈。

## 392. 为什么 JWT 中不能存密码等敏感信息？

**面试回答**

因为常见签名 JWT 的 Payload 只是 Base64URL 编码，任何拿到 Token 的人都能读取；Token 还可能经过浏览器存储、代理、日志和监控系统，扩大暴露面。签名防篡改而不保密，所以不应放密码、密钥和不必要的个人敏感信息。

**原理与理解**

密码应只在认证瞬间通过受保护通道提交，服务端保存适当的慢哈希结果，而不是复制到可反复携带的令牌中。即使对 JWT 使用 JWE，也会增加密钥生命周期和泄露后的数据影响；令牌应遵循最小披露，只携带授权判断真正需要且生命周期适配的声明。

**成立条件与边界**

- “不放密码”不等于其他所有数据都可以放，应评估隐私、日志传播、客户端可见性和陈旧风险。
- 哈希后的密码也不应放 Token，它仍可能成为离线攻击材料或内部认证实现信息。
- JWE 能提高机密性，但不能成为塞入大量敏感数据的理由。
- Token 中的用户 ID 也可能属于可关联信息，公开程度和合规要求要结合业务判断。
- 完整 Token 本身是认证秘密，即便内部 Claims 都不敏感也必须保护。

**实际场景**

**生产能力：** 定义 Claims 白名单，只放主体标识、必要受众和时间等最小信息；网关、异常日志、链路追踪和前端监控统一对 `Authorization`、Cookie 及 Token 参数脱敏。

**常见追问**

- 加密后的密码能不能放？没有必要且增加风险；认证凭证不应在每次请求中反复携带。
- 角色能不能放？可以按设计放，但要考虑权限变更后的陈旧和越权风险。
- JWE 后就能随便放吗？不能，仍要遵循最小化、生命周期和密钥管理原则。

**易错点**

- 只说“Base64 能解码”，不说明 Token 在多系统传播造成的暴露面。
- 把密码哈希误当成适合公开携带的数据。
- 忽略完整 Token 自身就是需要保密的 Bearer 凭证。

## 393. JWT 被修改以后服务端怎么发现？

**面试回答**

对于正确配置的签名 JWT，服务端使用预先信任的算法和密钥重新验证 JWS。Header 或 Payload 任一受保护字节被修改，攻击者若没有相应签名能力，验证就会失败。但只有同时限定算法、正确选钥并校验必要 Claims，才能把“发现修改”转化为安全的认证结论。

**原理与理解**

JWS 的签名输入覆盖受保护 Header 与 Payload。修改 userId 后，即使攻击者重新 Base64URL 编码，旧签名也不再匹配；若他使用自己的密钥重新签名，服务端也应因该密钥不在可信集合而拒绝。验证库需要固定安全 API 和失败关闭策略，不能在异常时退回“仅解码”。

**成立条件与边界**

- 验证端必须白名单化算法，拒绝未签名 Token，防止 `none` 或算法混淆类错误。
- HMAC 密钥太弱可能被离线猜测，攻击者一旦获得秘密就能生成看似有效的 Token。
- `kid`、`jku`、`x5u` 等头参数来自不可信输入，错误处理会导致选中攻击者控制的密钥。
- 签名只能发现被保护内容的变化，不能发现完整合法 Token 的复制重放。
- 验签成功后仍要校验 `iss`、`aud`、`exp`、`nbf`、类型和业务授权。

**实际场景**

**通用工程：** 验证失败统一返回未认证并记录不含完整 Token 的审计信息；不要为了兼容旧客户端，在验签异常时继续解析 Claims 或切换到更弱算法。

**常见追问**

- 攻击者改完 Payload 再编码为什么不行？他无法用可信密钥生成匹配的新签名。
- 攻击者自己签一个行不行？不行，服务端只信任预配置的签发者、算法和密钥。
- 签名正确就一定能用吗？不一定，还可能过期、受众错误、已撤销或无业务权限。

**易错点**

- 说“只要 JWT 被改，服务端一定发现”，不列正确验证的前提。
- 把解码成功当成验签成功。
- 验完签名就直接信任所有 Claims。

## 394. JWT 如何判断是否过期？

**面试回答**

验证端读取并校验 `exp` 声明。`exp` 是 NumericDate，表示自 Unix Epoch 起的秒数；当前时间达到或超过该时间时不得接受 Token。生产验证还应校验签名、`nbf`、`iss`、`aud` 等，并只允许很小的时钟偏差，不能只解码后比较一个时间字段。

**原理与理解**

签发端根据安全与体验要求设置生命周期，资源服务器用可信时钟进行验证。`nbf` 表示在某个时间前不能接受，`iat` 只表示签发时间，不能替代 `exp`。RFC 7519 基础标准将这些声明定义为可选，但用于登录访问令牌的应用规范应明确要求哪些时间字段存在以及缺失时如何拒绝。

**成立条件与边界**

- `exp` 的单位是秒，不应与 Java 毫秒时间戳混用。
- 可允许少量 clock skew 处理机器时钟偏差，但偏差过大会实质延长令牌寿命。
- 过期只决定时间有效性；签名、发行者、受众、用途和撤销状态仍需独立验证。
- 客户端可以预判刷新时间，但服务端验证结果才是访问资源的权威结论。
- 长期 Token 会放大泄露和权限陈旧影响；有效期应按风险设计，而不是固定套用“7 天”。

**实际场景**

**项目核验项：** 现有简历没有记录 JWT 的有效期、续签或刷新设计。应检查签发配置、验证库时钟偏差、前端过期处理和服务端失败码，再描述项目流程。

**常见追问**

- `exp` 是秒还是毫秒？标准 NumericDate 使用自 Epoch 起的秒数。
- `iat` 能判断过期吗？不能，它是签发时间，需要结合 `exp` 或协议定义的最大年龄。
- 为什么允许时钟偏差？分布式机器时钟可能存在小误差，但容忍值应很小且受控。

**易错点**

- 只比较 `exp`，不验签名和其他必需声明。
- 把秒误作毫秒，或把客户端时间当成权威。
- 未核验项目就说 Token 固定七天过期。

## 395. JWT 和 Session 有什么区别？

**面试回答**

JWT 是一种令牌格式，Session 是一种服务端会话状态机制，二者并非严格同层级的替代品。常见比较是“自包含 JWT 访问令牌”与“Cookie 携带不透明 Session ID”：前者可本地验签，后者需按 ID 查会话；前者撤销和声明更新更难，后者需要维护会话存储。

**原理与理解**

Session ID 本身也是一种不透明 Token，Cookie 只是常见传输载体；JWT 也可能配合数据库、拒绝列表或刷新会话而变得有状态。真正的取舍应看验证链路、撤销时效、权限实时性、跨服务信任、密钥管理、容量与故障模型，而不是简单背“JWT 存客户端，Session 存服务端”。

**成立条件与边界**

- JWT Claims 通常由客户端携带，但服务端也可能保存其哈希、`jti` 或刷新会话状态。
- Session 可通过共享存储支持集群，不能说它天然无法分布式。
- JWT 本地验签可减少中心查询，但 Token 更大，并可能携带陈旧权限。
- Cookie 和 `Authorization` 的安全边界不同：自动发送的 Cookie 要重点防 CSRF，脚本可读存储要重点防 XSS 窃取；两者都需 HTTPS。
- 两种方案都必须处理过期、退出、改密、封禁、密钥或 ID 泄露和授权校验。

**实际场景**

**通用工程：** 内部管理系统若要求立即踢下线和强实时权限，可偏向中心会话或内省；多服务低耦合读接口可使用短期自包含访问令牌。实际系统也常采用短期 JWT + 有状态刷新会话的组合。

**常见追问**

- JWT 一定比 Session 快吗？不一定，要比较密码学开销、网络查询、缓存命中、Token 大小和系统架构。
- Session 能做集群吗？能，可用共享存储、复制或粘性会话，但各有代价。
- 二者能组合吗？能，例如服务端保存刷新会话，签发短期 JWT 访问令牌。

**易错点**

- 把 JWT 格式与 Session 机制当作完全对称概念。
- 回答“JWT 无状态、Session 有状态”后忽略撤销和刷新设计。
- 认为 JWT 天然解决跨域，或 Session 天然更安全。

## 396. JWT 有什么优点？

**面试回答**

在合适场景下，JWT 的主要优点是标准化、可携带经签名的声明，并允许资源服务器本地验证，从而减少每次请求对中心会话存储的依赖；多个服务也可依据统一签发者、受众和密钥规则验证。它适合短期、边界清晰的服务间身份传递，但优势都有前提。

**原理与理解**

JWT 定义了注册 Claims 和 JOSE 封装方式，不同技术栈可按同一协议互操作。非对称签名下，签发方保管私钥，多个资源方只持公钥即可验证，降低签发能力扩散。自包含声明还能减少一次远程查询，但会把一致性和撤销问题转移到生命周期设计。

**成立条件与边界**

- 本地验证只有在密钥分发、轮换和算法策略正确时才是优势。
- 减少中心查询不代表端到端一定更快；大 Token、密码运算和网关转发也有成本。
- “跨服务可用”必须由 `iss`、`aud`、权限范围和信任关系约束，不能让一个 Token 通吃所有系统。
- JWT 不天然支持跨域；CORS、Cookie 与浏览器凭证策略属于另一层问题。
- 声明越多，Token 越大、隐私与陈旧风险越高，应坚持最小化。

**实际场景**

**真实项目边界：** 项目用 JWT 配合不同拦截链恢复管理端和用户端上下文，体现了统一令牌解析和请求内身份传递的便利；是否减少中心查询、是否使用非对称签名仍需代码核验。

**常见追问**

- JWT 为什么适合多服务？在明确的信任和受众边界内，各服务可使用可信验证材料独立验签。
- JWT 一定更轻量吗？不一定，JWT 通常比随机 Session ID 更长。
- 自包含最大的交换是什么？少查中心状态，但撤销和实时权限更新更困难。

**易错点**

- 把“可本地验签”说成任何 JWT 都无需网络或状态。
- 声称 JWT 天然更快、更小、可跨域。
- 为了自包含把大量用户资料和权限塞进 Claims。

## 397. JWT 有什么缺点？

**面试回答**

JWT 的主要缺点包括：Bearer Token 泄露后可被重放；离线验签模式没有内建的单 Token 立即撤销；Claims 在有效期内可能陈旧；令牌通常比随机 Session ID 大；算法、密钥、签发者、受众和刷新流程配置复杂。它不是“签名以后就安全”的免维护方案。

**原理与理解**

自包含带来的独立验证，也意味着服务端若不查状态，就无法立即知道用户已退出、被封禁或权限刚变化。要缩短风险窗口通常使用短期访问令牌，并用有状态刷新令牌、拒绝列表、版本号或内省补足，这又增加存储与运维成本。令牌经多层代理传输还会增加带宽和日志泄露面。

**成立条件与边界**

- 撤销困难主要针对“长效且完全离线验证”的自包含 Token；引入状态后可以提高撤销能力。
- JWT 不是天然易受 XSS 或 CSRF，风险取决于存储和发送方式；脚本可读存储暴露给 XSS，自动发送 Cookie 需要 CSRF 防护。
- Token 太大可能触及代理或服务器 Header 限制，也会增加每次请求开销。
- 密钥泄露可能影响大量 Token，轮换和隔离必须预先设计。
- 把实时、高频变化的权限塞入长效 Claims 会放大越权窗口。

**实际场景**

**生产能力：** 对高风险业务采用短期 Access Token、有状态且可轮换的 Refresh Token，并在改密、封禁、退出等事件撤销相关会话；日志只记录令牌摘要，同时监控异常刷新和重放迹象。

**常见追问**

- JWT 最大问题是什么？取决于场景，常见核心是 Bearer 泄露和离线验证下的撤销/陈旧状态。
- 放 localStorage 还是 Cookie？没有统一答案；需在 XSS、CSRF、前端架构和跨站需求间设计，不能只背一种位置。
- Token 越短越好吗？生命周期越短通常缩小泄露窗口，但会增加刷新频率和可用性复杂度。

**易错点**

- 把 JWT 缺点只回答成“Token 比较长”。
- 认为使用 `HttpOnly` Cookie 后不再需要 CSRF 防护。
- 用超长有效期换取“永不掉线”，却没有撤销和刷新保护。

## 398. 如何让 JWT 主动失效？

**面试回答**

JWT 没有单一的“主动删除”按钮，常见做法是组合：缩短 Access Token 有效期；按 `jti` 或 Token 哈希建立带 TTL 的拒绝列表；维护用户/会话的 `tokenVersion` 或最早有效时间；高风险请求使用内省；Refresh Token 则服务端保存、撤销并轮换。选择取决于撤销粒度和时效要求。

**原理与理解**

离线验签只看令牌自身和密钥，所以要在到期前否决它，就必须增加可查询状态或让验证材料失效。拒绝列表适合单 Token，版本号或“not-before”适合某用户全部旧 Token，内省适合强实时控制。刷新令牌轮换时，旧令牌用过即失效，并可在检测到重放时撤销整条授权链。

**成立条件与边界**

- 拒绝列表项应至少保留到原 Token 的 `exp`，并优先存 `jti` 或哈希，避免保存和记录完整 Bearer Token。
- `tokenVersion` 需要每次查询权威状态或通过短缓存传播，撤销时效取决于缓存一致性。
- 改签名密钥会让同一密钥下大量 Token 一起失效，适用于密钥泄露或大范围处置，不适合普通单用户退出。
- 只删除客户端 Token 不能保证已复制的 Token 失效。
- OAuth 刷新令牌轮换是成熟生产方案，但自研登录是否采用必须由实际协议和代码确认。

**实际场景**

**项目核验项：** 简历未证明项目存在 Redis 黑名单、Refresh Token、`jti`、版本号或密钥轮换。当前只能说明生产可选方案；面试前应确认退出接口究竟是仅客户端删除，还是服务端也维护撤销状态。

**常见追问**

- 退出登录只删前端 Token 够吗？只能阻止该副本继续使用，泄露或复制的 Token 仍可能在过期前有效。
- 黑名单存什么？优先存不可逆 Token 哈希或 `jti`，TTL 覆盖剩余有效期。
- 为什么不每次都换密钥？影响范围过大，还增加多实例轮换和旧密钥过渡复杂度。

**易错点**

- 回答“JWT 无法主动失效”，忽略引入状态后的方案。
- 把完整 Token 明文放入日志或黑名单键值。
- 把全局换密钥当成日常退出手段。

## 399. 项目中用户登录后的 JWT 完整流程是什么？

**面试回答**

简历能确认的项目流程是：项目基于 JWT、双拦截器和 ThreadLocal，分离管理端与用户端认证链路；登录后由服务端签发 Token，后续受保护请求进入对应拦截器，完成 Token 解析与校验后把当前身份写入 ThreadLocal，业务代码在本请求内读取，上下文最终必须清理。认证只确认“是谁”，接口权限和数据归属还要另行授权。

**原理与理解**

完整的通用安全链路应是：①登录接口校验凭据；②按可信算法、密钥、签发者、受众和生命周期签发 JWT；③客户端安全保存并在请求中提交；④管理端或用户端拦截器按各自规则验证签名、时间、发行者、受众和令牌用途；⑤只把已验证的最小身份写入 ThreadLocal；⑥业务执行认证后的授权；⑦在 `finally` 或请求完成回调中 `remove()`，避免线程池复用造成身份串请求。

**成立条件与边界**

- “双拦截器”必须具有清晰且互斥或可解释的路径、Token 类型与受众规则，不能只凭 URL 不同就信任同一类 Claims。
- ThreadLocal 只适用于同一线程内传递；异步任务、线程切换和消息消费不能默认继承，需要显式传递并清理。
- Token 解析不等于验证，必须失败关闭并统一处理缺失、格式错误、验签失败、未生效和过期。
- 身份上下文不能替代角色权限、资源所有权和管理端/用户端隔离校验。
- 请求头名称、Claims、算法、密钥来源、有效期、刷新与注销机制在简历中均未确认，必须以代码和配置为准。

**实际场景**

**真实项目边界：** 可准确表达“项目用 JWT + 双拦截器区分管理端和用户端，解析 Token 后通过 ThreadLocal 传递当前用户上下文”。**项目核验项：** 补查登录接口、签发工具类、两条拦截器注册路径、Header/Cookie 取值、Claims、异常码、`ThreadLocal.remove()`、权限校验以及退出/续签实现后，再形成可逐行对应代码的项目话术。

**常见追问**

- 为什么需要两个拦截器？用于隔离管理端与用户端认证链路，但还应由独立受众、类型或权限规则形成真实安全边界。
- ThreadLocal 为什么必须清理？Servlet 工作线程会复用，不清理可能导致内存滞留或下一请求读到旧身份。
- 拦截器验过 JWT 后还要做什么？继续做角色、接口权限、数据归属和用户实时状态校验。

**易错点**

- 把简历未披露的 HS256、`userId` Claim、自定义 Header 或七天有效期说成真实实现。
- 只解码 Token 就写入 ThreadLocal，或在异常路径忘记清理。
- 把“已经登录”当成“有权操作任意订单、用户或管理接口”。
