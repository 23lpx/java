# CookieSessionJWT

## 381. Cookie 是什么？

**面试回答**

Cookie 是服务器发给浏览器、由浏览器保存在本地的一小段数据（键值对），之后浏览器每次请求都会自动带上它，用于记住用户状态（如登录、偏好）。

**理解**

Cookie 是「存在客户端的小数据」，由服务器通过 Set-Cookie 响应头下发，浏览器存储后，后续请求自动附加在 Cookie 请求头里。它常用于保存 session id、记住登录状态等。Cookie 有大小限制（约 4KB）、可设有效期、可设 HttpOnly/Secure 等属性。

**场景**

项目里若用 Session 方案，登录后服务器把 session id 写进 Cookie，浏览器后续请求带上它标识用户。

**常见追问**

- Cookie 存在哪？（浏览器/客户端本地）
- Cookie 大小限制？（约 4KB）

**易错点**

Cookie 是「存客户端的小数据」，本身不是认证方式，常配合 Session 存 session id；别把 Cookie 和 Session/JWT 混为一谈。

## 382. Session 是什么？

**面试回答**

Session 是「存在服务器端」的会话数据，用于记录某个用户在一段时间内的状态（如已登录、用户信息），客户端通过 Cookie 里的 session id 来对应到这份服务器数据。

**理解**

Session 数据存在服务器内存/存储里，客户端只持有 session id（通常放 Cookie）。请求来时，服务器根据 session id 找到对应的 Session，就知道这个用户是谁。它的状态在服务器端，客户端无法直接篡改，但服务器要存储所有在线用户的 Session，占用服务端资源。

**场景**

项目里传统的登录认证：登录成功后服务器创建 Session 存用户信息，客户端 Cookie 存 session id，后续请求据此识别用户。

**常见追问**

- Session 存在哪？（服务器端）
- 客户端怎么关联 Session？（通过 Cookie 里的 session id）

**易错点**

Session 是「服务端状态」，Cookie 是「客户端小数据」，两者常配合（Cookie 存 session id）但本质不同。

## 383. Cookie 和 Session 有什么区别？

**面试回答**

Cookie 存在客户端（浏览器），Session 存在服务器端；Cookie 存的是数据本身（如 session id），Session 存的是会话状态（如用户信息）；Cookie 可被用户看到/修改，Session 更安全但占用服务器资源。

**理解**

几个维度：①位置：Cookie 客户端、Session 服务端；②内容：Cookie 是键值小数据，Session 是会话对象；③安全：Cookie 可被篡改，Session 数据在服务端更安全；④资源：Session 占服务器内存/存储，Cookie 占客户端；⑤关联：通常用 Cookie 存 session id 来定位 Session。

**场景**

项目里登录用 Session 存用户信息（服务端），Cookie 只存 session id（客户端），两者配合完成认证。

**常见追问**

- 为什么 Cookie 不如 Session 安全？（Cookie 在客户端可被改）
- Session 的缺点？（占服务端资源，分布式下要共享）

**易错点**

Cookie 和 Session 不是「二选一」的关系，常见是「配合使用」：Cookie 存 session id，Session 存真实状态。

## 384. Token 是什么？

**面试回答**

Token 是服务器签发的一串「令牌/凭证」，客户端拿到后每次请求携带它，服务器校验通过就认为身份合法，用于无状态认证。

**理解**

Token 是「服务端签发的身份凭证」，通常是一串经过签名/编码的字符串，包含用户信息、有效期等。客户端请求时放请求头（如 Authorization），服务器校验 token 的签名和有效期来确认身份。和 Session 不同，Token 让服务器不必保存每个用户的会话状态（无状态）。

**场景**

项目里登录后服务器签发 JWT 作为 token，客户端存下并每次请求带上，服务器校验后识别用户。

**常见追问**

- Token 和 Session 区别？（Token 无状态、可跨服务；Session 服务端存状态）
- Token 一般放哪？（请求头 Authorization，或自定义头）

**易错点**

Token 是「无状态凭证」，JWT 是 Token 的一种实现；别把 Token 和 JWT 完全等同，也别和 Session 混淆。

## 385. JWT 是什么？

**面试回答**

JWT（JSON Web Token）是一种基于 JSON 的开放标准（RFC 7519），用于在各方之间安全传递信息的紧凑令牌，由 Header、Payload、Signature 三部分组成，常用于无状态登录认证。

**理解**

JWT 是一个「自包含」的令牌：把用户信息和元数据编码进 token，服务器用签名验证它没被篡改、用过期时间验证它是否有效，不需要在服务端存会话状态。它适合分布式、前后端分离场景。

**场景**

项目里用 JWT 做登录认证：登录成功签发 JWT，客户端存下来，后续请求带上，服务器用拦截器校验。

**常见追问**

- JWT 全称？（JSON Web Token）
- 三部分组成？（Header、Payload、Signature）

**易错点**

JWT 是「编码 + 签名」的令牌，不是「加密」；内容（Payload）可被解码看到，别当成加密数据。

## 386. JWT 由哪三个部分组成？

**面试回答**

三部分：Header（头部）、Payload（载荷）、Signature（签名），用点号 `.` 分隔，形如 `header.payload.signature`。

**理解**

Header 描述令牌类型和签名算法；Payload 存放声明（用户信息、过期时间等）；Signature 用「Header + Payload + 密钥」按指定算法算出的签名，用于防篡改。三部分各自 Base64Url 编码后拼接。

**场景**

项目里的 JWT 拆开看就是三段，前两段 Base64Url 解码可见内容，第三段是签名。

**常见追问**

- 三部分用什么连接？（点号 `.`）
- 哪部分是防篡改的？（Signature）

**易错点**

三部分是「Base64Url 编码」不是「加密」，所以 Header 和 Payload 能被解码看到内容。

## 387. Header 中通常保存什么？

**面试回答**

Header 保存令牌的元信息，主要是两部分：类型（typ，如 JWT）和签名算法（alg，如 HS256、RS256）。

**理解**

Header 是 JSON，典型如 `{"alg": "HS256", "typ": "JWT"}`，说明「这是 JWT、用 HS256 算法签名」。它被 Base64Url 编码后作为 JWT 第一部分。服务器校验签名时，会根据这里的 alg 用对应算法验签。

**场景**

项目里 JWT 的 Header 声明 alg 为 HS256（HMAC-SHA256），服务端用同一密钥验签。

**常见追问**

- alg 表示什么？（签名算法）
- Header 会被编码吗？（会，Base64Url 编码）

**易错点**

Header 是「明文可解码」的元信息，不是机密；它声明签名算法，服务端据此验签。

## 388. Payload 中通常保存什么？

**面试回答**

Payload 保存「声明（claims）」，即要传递的信息，如用户 id、用户名、签发时间、过期时间等，其中过期时间（exp）等是标准声明。

**理解**

Payload 是 JWT 的「数据部分」，包含标准声明（如 exp 过期时间、iat 签发时间、sub 主题）和自定义声明（如 userId、role）。它是 Base64Url 编码，任何人都能解码看到，所以不能放敏感信息（密码等）。

**场景**

项目里 JWT 的 Payload 存 userId、用户类型（管理端/用户端）、过期时间等非敏感信息。

**常见追问**

- 常见标准声明？（exp 过期时间、iat 签发时间、sub 主体）
- Payload 能存密码吗？（不能，可被解码看到）

**易错点**

Payload 是「编码」不是「加密」，内容可见，只能放不敏感信息；这是理解「JWT 不能存密码」的基础。

## 389. Signature 有什么作用？

**面试回答**

Signature 是签名，用来验证 JWT 在传输过程中没有被篡改：服务器用约定的密钥和算法重新计算签名，与令牌里的签名比对，不一致说明被改过。

**理解**

签名的计算：把「Base64Url(Header) + "." + Base64Url(Payload)」作为输入，用 Header 声明的算法和密钥（HMAC 用同一密钥，RSA 用私钥签、公钥验）算出签名。攻击者改了 Payload 但不知道密钥，就算不出正确的签名，服务器一比对就发现。所以签名保证「完整性」，不是「机密性」。

**场景**

项目里服务器用密钥对 JWT 重新计算签名并比对，防止用户篡改 token 里的 userId 等信息。

**常见追问**

- 签名防的是什么？（篡改，保证完整性）
- 签名是加密吗？（不是，是防篡改的校验值）

**易错点**

签名保证「没被篡改」，不代表「内容加密」；篡改后签名对不上会被识别。

## 390. JWT 为什么可以实现无状态认证？

**面试回答**

因为 JWT 把用户信息「自包含」在 token 里，服务器校验签名和过期时间就能确认身份，不需要在服务端保存会话状态，所以叫无状态。

**理解**

Session 方案里，服务器要存「session id → 用户信息」的映射；而 JWT 把用户信息（如 userId）直接放进 token，服务器只需「验签 + 看过期」就能确定用户是谁，不用查存储。这样任何服务器实例都能独立校验，天然适合分布式、水平扩展。

**场景**

项目里用 JWT 后，服务器不存登录态，拦截器验签即可识别用户，多个实例也能共享校验。

**常见追问**

- 「无状态」指什么？（服务器不保存会话状态）
- 为什么适合分布式？（每台机器都能独立验签，不用共享 Session）

**易错点**

无状态 = 「服务器不存会话」，靠 token 自包含信息 + 验签；代价是难以主动失效（见 JWT 缺点）。

## 391. JWT 中的数据是加密的吗？

**面试回答**

不是。JWT 只是 Base64Url 编码 + 签名，Header 和 Payload 都能被解码直接看到内容，它保证的是「没被篡改」，不是「内容加密」。

**理解**

Base64 是「编码」不是「加密」，可以轻易解码还原。JWT 的 Payload 里存了什么，任何拿到 token 的人都能解码看到。签名只保证「改了就发现」，不保证「别人看不到」。所以 JWT 里绝不能放密码等敏感信息。

**场景**

项目里的 JWT 只存 userId 这类不敏感信息，因为 Payload 可被解码看到。

**常见追问**

- Base64 是加密吗？（不是，是编码，可逆）
- JWT 保证什么？（完整性/防篡改，不是机密性）

**易错点**

这是必须纠正的高频错误：「JWT 是加密的」是错的；它是「编码 + 签名」，不加密。

## 392. 为什么 JWT 中不能存密码等敏感信息？

**面试回答**

因为 JWT 的 Payload 只是 Base64Url 编码，任何人都能解码看到内容，存密码等于把密码明文暴露出去，所以不能放敏感信息。

**理解**

Base64Url 编码可逆，解码后就是原始 JSON，毫无机密性。如果 Payload 里放密码，任何人拿到 token 解码就能看到密码。所以 JWT 只能放「不敏感、且服务端需要」的信息（如 userId、角色、过期时间），密码、身份证等敏感数据绝不能放。

**场景**

项目里 JWT 的 Payload 只放 userId、用户类型等非敏感信息，密码等绝不放进去。

**常见追问**

- 那敏感数据放哪？（放服务端存储，token 里只放标识）
- 怎么让 Payload 内容保密？（JWT 本身做不到，要么不放，要么额外加密）

**易错点**

根本原因是「Payload 可解码、不加密」；所以敏感信息不能放 JWT，这是安全常识。

## 393. JWT 被修改以后服务端怎么发现？

**面试回答**

通过校验签名发现：服务端用密钥和 Header 声明的算法，对「Header + Payload」重新计算签名，与 token 里的 Signature 比对，不一致就说明被篡改过。

**理解**

攻击者改了 Payload（比如把 userId 改大），但不知道密钥，无法生成匹配的签名。服务端验签时重新算一遍，发现签名对不上，就判定 token 被篡改，拒绝请求。所以「修改」一定会被签名校验抓住。

**场景**

项目里拦截器验签：用户篡改 token 里的 userId，签名对不上，服务器直接返回未授权。

**常见追问**

- 为什么改了会被发现？（没有密钥，算不出正确签名）
- 密钥泄露会怎样？（攻击者能伪造合法 token）

**易错点**

JWT 防篡改靠「签名校验」，核心是「密钥保密」；密钥一泄露，签名就形同虚设。

## 394. JWT 如何判断是否过期？

**面试回答**

通过 Payload 里的 `exp`（过期时间）声明：服务端校验时取出 exp，和当前时间比较，当前时间已超过 exp 就认为 token 过期，拒绝请求。

**理解**

签发 JWT 时在 Payload 里写入 exp（Unix 时间戳），表示「这个 token 有效期到什么时候」。服务端验签通过后，再检查 `exp < 当前时间`，若已过期则判定失效。过期判断是服务端逻辑，不是 JWT 自动失效。

**场景**

项目里签发 JWT 时设 exp（如 7 天），拦截器校验时判断是否过期，过期返回「登录已过期」。

**常见追问**

- exp 是什么？（过期时间戳）
- 过期判断在哪做？（服务端校验逻辑）

**易错点**

JWT 过期靠「exp + 服务端比对」，不是 token 到点自动作废；服务端必须主动检查 exp。

## 395. JWT 和 Session 有什么区别？

**面试回答**

Session 是服务端存会话状态，客户端只持 session id，服务器要维护状态、可主动失效但占用资源；JWT 是客户端存 token、服务端无状态，靠验签识别用户，易扩展但难主动失效。

**理解**

几个维度：①状态存储：Session 在服务端，JWT 在客户端（token 自包含）；②扩展性：JWT 无状态、任何实例可验签，适合分布式；Session 要共享（如存 Redis）；③主动失效：Session 服务端删除即可，JWT 难（除非加黑名单等）；④安全：JWT 内容可见（不能存敏感），Session 数据在服务端更安全。

**场景**

项目里选 JWT 是因为前后端分离、无状态易扩展；代价是难以主动踢人下线。

**常见追问**

- 哪个可扩展性好？（JWT，无状态）
- 哪个能主动失效？（Session 更方便，JWT 要额外机制）

**易错点**

核心区别是「状态存哪」：Session 服务端、JWT 客户端；由此导出扩展性、失效、安全等一系列差异。

## 396. JWT 有什么优点？

**面试回答**

①无状态，服务器不存会话，易水平扩展；②自包含，信息在 token 里，校验快；③适合前后端分离和跨域；④支持跨服务/跨域认证。

**理解**

无状态让每个服务实例都能独立验签，不用共享 Session，方便微服务/分布式；自包含减少查库查存储；前端把 token 放请求头，天然适合前后端分离和跨域；一套 token 可在多个服务间通用。这些是 JWT 流行的原因。

**场景**

项目里用 JWT 让认证逻辑简单、无状态、易扩展，适配前后端分离架构。

**常见追问**

- 无状态有什么好处？（易扩展、不用共享 Session）
- 为什么适合前后端分离？（token 放请求头，不依赖 Cookie）

**易错点**

JWT 的优点集中在「无状态、自包含、易扩展」，要能对应到「分布式/前后端分离」的落地价值。

## 397. JWT 有什么缺点？

**面试回答**

①内容不加密，不能存敏感信息；②难以主动失效（签发了就无法简单作废）；③token 比 session id 大，占用更多带宽；④一旦泄露，在过期前都能被冒用。

**理解**

JWT 的缺点和它的设计绑定：Payload 可解码（不加密）；无状态导致「服务器不能简单删掉它」让它失效；自包含意味着 token 较大；泄露后由于服务器不存状态，无法立刻吊销，只能在到期前靠黑名单等补偿。这些是选型时要权衡的。

**场景**

项目里用 JWT 就得接受「难以主动踢人下线」，所以重要操作要配合其他机制（如改密后强制重登、黑名单）。

**常见追问**

- 为什么难主动失效？（无状态，服务器不存 token）
- 泄露了怎么办？（尽快改密钥/加黑名单，缩短有效期）

**易错点**

JWT 的缺点「不加密、难失效、较大、泄露风险」要能说全，尤其「难主动失效」是核心短板。

## 398. 如何让 JWT 主动失效？

**面试回答**

常见方法：①缩短有效期；②维护黑名单（把要失效的 token 或用户加入黑名单，校验时拦截）；③改密钥（让所有旧 token 失效）；④结合 Redis 存「已注销」标记。

**理解**

JWT 无状态，无法直接「删掉」一个已签发的 token。主动失效只能靠「补偿」：让 token 本身短命（缩短 exp），或在校验时多查一层「是否已失效」（黑名单/Redis 标记），或换密钥让旧 token 全部作废。这些都是在「无状态」上叠加一点「状态」来实现可控。

**场景**

项目里用户修改密码后，可把该用户加入黑名单或更新密钥版本，使旧 JWT 失效，强制重新登录。

**常见追问**

- 黑名单怎么做？（存已失效 token 的标识，校验时查询）
- 改密钥影响？（所有旧 token 立即失效）

**易错点**

JWT 主动失效要「额外加机制」（黑名单/短时效/换密钥），因为它本身无状态；别以为能像 Session 那样直接删。

## 399. 项目中用户登录后的 JWT 完整流程是什么？

**面试回答**

大致：①用户登录，服务器校验账号密码；②校验通过，服务器签发 JWT（含 userId、用户类型、过期时间）返回给前端；③前端保存 token，后续请求在请求头带上；④服务器用拦截器校验 token（验签、查过期），通过则把 userId 存进 ThreadLocal 供业务使用；⑤拦截器在请求结束后清理 ThreadLocal。

**理解**

这是项目认证的完整链路：登录发 token → 前端携带 → 拦截器校验 → ThreadLocal 传递用户信息 → 请求结束清理。双拦截器（用户端/管理端）分别校验各自路径，登录接口放行。核心是「签发 → 携带 → 校验 → 传递 → 清理」五步。

**场景**

项目里用户登录成功后，前端把 JWT 存起来，每次请求带在 header 里，后端 JwtTokenInterceptor 校验并往 ThreadLocal 塞 userId，业务代码从 ThreadLocal 取当前用户。

**常见追问**

- 拦截器里做什么？（验签、查过期、存 ThreadLocal）
- 为什么请求结束要清 ThreadLocal？（避免线程复用数据残留）

**易错点**

完整流程要串起来讲：签发、携带、拦截校验、ThreadLocal 传递、清理，缺一环都不完整。
