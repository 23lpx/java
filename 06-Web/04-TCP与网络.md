# TCP与网络

## 523. TCP 和 UDP 有什么区别？

**面试回答**

TCP 提供面向连接、可靠、有序的双向字节流，并包含流量控制和拥塞控制；UDP 提供最小化的无连接数据报服务，保留报文边界，但本身不保证送达、顺序、去重或拥塞控制。UDP 头部和建连成本更低，不等于任何场景都更快；应用可在 UDP 之上补充可靠性，例如 QUIC。

**原理与理解**

TCP 建立连接状态，对每个字节编号，通过确认、重传、接收窗口和拥塞控制管理连续字节流；应用必须自行定义消息边界。UDP 以一个 Datagram 为交付单位，应用一次发送的报文边界会被保留，但网络可能丢失、重复、乱序，应用还要控制速率并处理超过路径 MTU 的风险。

**成立条件与边界**

- “UDP 不可靠”表示协议不内建可靠交付，不表示基于 UDP 的应用协议不能实现可靠性、拥塞控制和加密。
- “TCP 可靠”不等于永不失败；连接可能超时、重置，应用仍需处理交付结果不确定和业务重试。
- TCP 是字节流，没有粘包/拆包意义上的消息边界；UDP 保留数据报边界，但大报文可能分片或被丢弃。
- UDP 少一次传统 TCP 建连且头部更小，但真实延迟取决于网络、拥塞算法、加密、重传和应用设计。
- HTTP/1.1、HTTP/2 通常运行于 TCP；HTTP/3 使用 QUIC，而 QUIC 通常封装在 UDP 上。

**实际场景**

**通用工程：** 数据库连接和传统 HTTP/2 需要可靠字节流，常使用 TCP；实时音视频可基于 UDP 有选择地容忍丢包并在应用层做拥塞控制；HTTP/3 则展示了“UDP 承载也能提供可靠流”的组合。

**常见追问**

- TCP 保留消息边界吗？不保留，应用要用长度字段、分隔符或固定长度等方式分帧。
- UDP 一定比 TCP 快吗？不一定，只是协议机制更少；应用补齐可靠性后成本也会增加。
- HTTP 都走 TCP 吗？不是，HTTP/3 运行在 QUIC 上，QUIC 通常使用 UDP。

**易错点**

- 简化成“TCP 慢但绝不丢，UDP 快但一定丢”。
- 忽略 TCP 的字节流与 UDP 的数据报边界。
- 因 HTTP/1.1/2 常用 TCP，就断言所有 HTTP 都使用 TCP。

## 524. TCP 为什么是可靠协议？

**面试回答**

TCP 的可靠性来自一组协同机制：字节序号和累计确认识别已收到数据，重传处理丢失，校验和检测传输损坏，接收窗口进行流量控制，拥塞控制约束向网络注入的数据量，接收端按序交付并丢弃重复数据。三次握手只是建立连接与同步序号，不是可靠性的全部。

**原理与理解**

TCP 为字节流中的每个字节分配序号，ACK 表示某序号之前的字节已被接收；发送端依据重传超时和重复 ACK 等信号重发缺失数据。接收窗口避免压垮对端缓冲，拥塞窗口与算法适应网络容量。最终应用看到按序字节流，而不是到达顺序混乱的独立报文。

**成立条件与边界**

- ACK 通常说明远端 TCP 已接收相关字节，不等于远端业务已处理、写库或落盘成功。
- 连接在确认前后都可能断开，应用层仍需超时、幂等、事务状态查询和错误恢复。
- TCP 校验和用于检测随机传输错误，不提供加密、来源认证或防恶意篡改；敏感通信需要 TLS 等机制。
- 流量控制保护接收端，拥塞控制保护网络，两者目的不同。
- TCP 保证有序字节流，不恢复应用消息边界；协议解析仍需正确分帧。

**实际场景**

**通用工程：** 客户端发出下单请求并收到 TCP ACK，只能说明字节到达远端协议栈，不能认定订单创建成功；必须以 HTTP/业务响应或后续状态查询作为业务结果依据。

**常见追问**

- 靠什么发现丢失？序号、ACK、重传计时器和重复 ACK 等反馈共同作用。
- 流量控制与拥塞控制区别？前者适配接收端能力，后者适配网络承载能力。
- TCP 可靠是否还需要业务幂等？需要，网络中断可能让客户端不知道服务端是否已经执行。

**易错点**

- 只回答“三次握手保证可靠”。
- 把 TCP ACK 当成业务成功回执。
- 认为 TCP 自带加密和防攻击能力。

## 525. TCP 三次握手过程是什么？

**面试回答**

典型主动建立过程是：①客户端发送 `SYN`，携带初始序号 x；②服务器返回 `SYN+ACK`，携带自己的初始序号 y，并确认 `x+1`；③客户端返回 `ACK`，确认 `y+1`。双方同步并确认彼此的初始序号后进入 ESTABLISHED，SYN 本身占用一个序号。

**原理与理解**

客户端从 CLOSED 进入 SYN-SENT；服务端 LISTEN 收到 SYN 后进入 SYN-RECEIVED；客户端收到合法 SYN+ACK 后可进入 ESTABLISHED，服务端收到最终 ACK 后也进入 ESTABLISHED。SYN 报文还常用于协商 MSS、窗口扩大、SACK Permitted、时间戳等 TCP 选项。

**成立条件与边界**

- 第三个 ACK 可以携带应用数据，不能把它固定理解成只能发送空报文。
- TCP 支持双方同时主动打开，此时状态和报文序列比典型客户端—服务端图更复杂。
- 第一次 SYN 或 SYN+ACK 丢失会重传，握手并非每步只发送一次。
- 建立的是传输连接，不会自动完成 TLS、HTTP、用户登录或业务会话。
- SYN 队列、accept 队列和 SYN Cookie 属于具体协议栈与系统实现，不能从三报文图直接推导所有内核行为。

**实际场景**

**通用工程：** 抓包定位连接慢时，可检查 SYN 是否重传、SYN+ACK 是否返回、第三个 ACK 是否到达，并区分 TCP 建连耗时与随后 TLS、HTTP 请求处理耗时。

**常见追问**

- 为什么 ACK 是 x+1？SYN 占用一个序号，接收方期待的下一个序号是 x+1。
- 第三次握手能带数据吗？协议允许，接收端按连接状态确保数据有效后交付。
- 握手协商哪些信息？核心是 ISN，同步报文还可携带 MSS、窗口扩大、SACK、时间戳等选项。

**易错点**

- 只背 `SYN → SYN+ACK → ACK`，说不出序号确认关系。
- 认为三次握手已经完成 HTTPS 或登录认证。
- 断言第三次 ACK 一定没有数据。

## 526. 为什么 TCP 建立连接需要三次握手？

**面试回答**

核心原因是双方都要发送自己的初始序号，并收到对方对该序号的确认。第二个报文可合并“确认客户端 ISN”和“发送服务器 ISN”，第三个 ACK 再确认服务器 ISN；这样双方才能建立同步状态，并降低旧重复 SYN 被误认为新连接的风险。用“确认双方收发能力”概括可以，但不够精确。

**原理与理解**

两次消息后，客户端已确认服务器收到了客户端 ISN，也收到了服务器 ISN；但服务器还不知道客户端是否接受了服务器当前 ISN，旧重复连接请求也需要发起方最终确认。第三个 ACK 补齐这个确认。第四个独立报文没有必要，因为服务器的 SYN 与对客户端的 ACK 可以合并。

**成立条件与边界**

- 三次握手的规范重点是 ISN 同步与防旧重复连接，不是证明网络今后不会丢包。
- 握手只能验证当前路径上完成了必要报文交换，不能证明应用、数据库或远端进程业务健康。
- 三次握手不是身份认证，攻击者仍可发 SYN；SYN Flood 需要队列管理、SYN Cookie、限速等防护。
- 旧报文处理还依赖序号选择、TIME-WAIT、时间戳等机制，不能把全部安全归功于第三次 ACK。
- 同时打开场景仍遵循双方同步/确认 ISN 的原则，但不呈现简单的一发一收三行图。

**实际场景**

**通用工程：** 服务端收到大量 SYN 但最终 ACK 很少时，连接大量停留在 SYN-RECEIVED；这说明握手未完成，需要区分网络丢包、客户端异常与 SYN Flood，而不是排查 HTTP Controller。

**常见追问**

- 两次为什么不够？服务器尚未收到客户端对服务器 ISN 的确认，也难以排除旧重复请求。
- 为什么不是四次？服务器可把自己的 SYN 与对客户端 SYN 的 ACK 合并。
- 三次握手能防 SYN Flood 吗？不能，只建立正常连接协议；防护依赖额外实现和网络策略。

**易错点**

- 只回答“双方确认收发能力正常”，没有 ISN 和旧重复报文。
- 说三次握手能保证后续数据永不丢失。
- 把握手次数解释为越多越安全。

## 527. TCP 四次挥手过程是什么？

**面试回答**

典型正常关闭可描述为四个报文：主动方发 `FIN` 表示该方向不再发送；被动方回 `ACK`，连接进入半关闭；被动应用完成剩余发送后发自己的 `FIN`；主动方回最终 `ACK` 并进入 TIME-WAIT，被动方收到 ACK 后关闭。FIN 与 SYN 一样会占用一个序号。

**原理与理解**

主动方常经历 FIN-WAIT-1、FIN-WAIT-2、TIME-WAIT；被动方常经历 CLOSE-WAIT、LAST-ACK。收到 FIN 只表示对端不会再发送新数据，本端仍可发送剩余数据，因此两个方向独立关闭。正常 FIN 关闭会尽力交付已排队数据，而 RST 是中止式关闭，语义不同。

**成立条件与边界**

- “四次挥手”是典型报文序列，不是每次抓包都恰好四个包；ACK 与本端 FIN 可以合并，表现为三个报文。
- 双方同时关闭会进入 CLOSING 等状态，并可能双方都经历 TIME-WAIT。
- FIN 可能重传，延迟 ACK、丢包和数据报文会让抓包数量超过四个。
- 应用调用 `close()`、`shutdownOutput()` 或异常触发 RST，会产生不同关闭行为。
- TLS 连接通常还应处理 `close_notify` 等上层安全关闭语义，不能只看 TCP FIN 判断 TLS 数据完整结束。

**实际场景**

**通用工程：** 排查连接未释放时，服务端大量 CLOSE-WAIT 往往表示已收到对端 FIN，但本地应用迟迟没有关闭；应检查资源生命周期，而不是把所有关闭问题归为 TIME-WAIT。

**常见追问**

- 谁进入 TIME-WAIT？典型主动关闭方；同时关闭时双方都可能进入。
- ACK 和 FIN 能合并吗？可以，如果接收 FIN 时本端也已准备关闭。
- FIN 与 RST 区别？FIN 是有序半关闭，RST 是中止连接并可能丢弃未交付数据。

**易错点**

- 断言关闭连接在线路上永远恰好四个报文。
- 说 ACK 与 FIN 不能合并。
- 混淆 CLOSE-WAIT 与 TIME-WAIT 的责任方和成因。

## 528. 为什么关闭连接通常需要四次挥手？

**面试回答**

因为 TCP 是全双工字节流，两个发送方向要独立结束。收到对端 FIN 后必须确认，但本端应用可能还有数据要发，不能立刻发送自己的 FIN；所以 ACK 与本端 FIN通常分开发出，形成四个报文。若本端已无数据，它们可以合并，关闭也可能只看到三个报文。

**原理与理解**

一端发 FIN 只关闭“本端发送 → 对端接收”方向，对端仍可在另一方向继续发送。只有对端应用也执行关闭，TCP 才发第二个 FIN。相比建立连接时 SYN 与 ACK 通常可直接合并，关闭时是否能合并取决于应用何时完成输出，因此常见四次而非强制四次。

**成立条件与边界**

- 全双工独立关闭是根因，“ACK 和 FIN 绝对不能合并”是错误解释。
- 半关闭可让一方发送完请求后继续读取对端响应，应用协议必须知道何时以 EOF 作为边界。
- 如果应用不关闭已收到 FIN 的 socket，会长期停在 CLOSE-WAIT，最终耗尽文件描述符等资源。
- 中止式 RST 不遵循正常 FIN 关闭流程，也不提供相同的数据交付语义。
- 四次只是逻辑阶段，重传、同时关闭和 ACK 合并会改变实际报文数量。

**实际场景**

**生产能力：** 监控中 CLOSE-WAIT 持续增长时，重点检查应用是否遗漏响应体关闭、socket close 或异常路径释放；TIME-WAIT 增长则更多关联主动关闭与连接创建速率，两者不能用同一参数处理。

**常见追问**

- 为什么握手常三次、关闭常四次？握手中 SYN 与 ACK 通常可合并；关闭时收到 FIN 的一方可能尚未完成发送。
- 能否三次关闭？可以，第二个 ACK 与本端 FIN 合并时可呈现三段。
- 收到 FIN 后还能发送数据吗？可以，FIN 只关闭对端的发送方向，本端方向仍可开放。

**易错点**

- 把“四次”当作不可变化的报文数量。
- 认为收到 FIN 后整个连接立即不能再传数据。
- 用调 TIME-WAIT 参数解决 CLOSE-WAIT 泄漏。

## 529. 什么是 TIME_WAIT？

**面试回答**

TIME-WAIT 是正常主动关闭后的等待状态，标准状态机要求停留 2×MSL。它让端点能够再次确认重传的 FIN，并避免旧连接延迟报文干扰相同连接标识的新实例。典型主动关闭方进入 TIME-WAIT；双方同时关闭时双方都可能进入。

**原理与理解**

主动方发送最终 ACK 后，如果 ACK 丢失，对端会重传 FIN；TIME-WAIT 中仍保留必要状态，可再次回复 ACK。等待足够时间也让旧序号空间中的报文在网络中失效，减少新旧连接混淆。RFC 9293 用 2×MSL 描述协议要求，但具体系统的 MSL 与优化实现可能不同。

**成立条件与边界**

- TIME-WAIT 是 TCP 正确性机制，不是看到数量大就认定故障。
- 大量短连接且本机主动关闭时，可能消耗临时端口和连接控制状态；监听端口本身不会因每个 TIME-WAIT 就无法继续接受所有新连接。
- 连接由源/目的 IP 和端口等标识，端口复用是否安全由协议栈规则、时间戳和配置共同决定。
- 盲目缩短等待或启用激进复用可能引入旧报文混淆、NAT/负载均衡兼容等问题。
- 优先通过 HTTP 长连接、连接池、合理关闭方和容量规划降低无意义连接 churn，再评估内核参数。

**实际场景**

**生产能力：** 调用大量上游 API 的客户端出现临时端口不足时，应同时看新建连接速率、连接池命中、目标四元组分布和 TIME-WAIT 数量；先修复未复用连接，再基于操作系统文档和压测调整参数。

**常见追问**

- 为什么等待 2MSL？覆盖旧报文最大生存窗口，并允许对端 FIN 重传后再次确认。
- 谁进入 TIME-WAIT？通常是主动关闭方；同时关闭时双方都可能进入。
- TIME-WAIT 越少越好吗？不是，它承担协议正确性；目标是减少不必要连接 churn，而非清零。

**易错点**

- 把 TIME-WAIT 一律当成内存泄漏或系统 Bug。
- 说只有服务器或只有客户端会进入，忽略谁主动关闭。
- 未理解网络拓扑和内核语义就直接缩短等待时间。

## 530. DNS 是什么？

**面试回答**

DNS 是层次化、分布式的命名系统，用域名查询资源记录。A/AAAA 可把名称关联到 IPv4/IPv6 地址，但 DNS 不只做“域名转 IP”，还包含 NS、MX、CNAME、TXT、SRV、SOA 等记录，并通过权威服务器、递归解析器和缓存共同工作。

**原理与理解**

主机通常把问题交给递归解析器；若缓存未命中，解析器依据根、顶级域和目标域权威信息逐步查询，得到结果后按 TTL 缓存。真实流程可能被本机缓存、hosts、浏览器缓存、递归缓存或 CNAME 链提前/延长，不能背成每次都完整访问根服务器。

**成立条件与边界**

- DNS 记录变更不会全球瞬时生效，旧答案可在各级缓存中保留到 TTL 等策略允许的时间。
- DNS 传统查询常用 UDP，也必须支持 TCP 场景；还可使用 DNS over TLS、DNS over HTTPS 等加密传输。
- 返回多个地址可辅助流量分配，但 DNS 本身不保证实时健康检查、会话保持或端到端负载均衡正确。
- CNAME 是别名关系，不是直接等价于“另一个 IP”；解析还要继续取得目标地址记录。
- DNSSEC 提供来源认证和完整性验证，不提供查询内容机密性；DoT/DoH 保护传输隐私，也不自动等于 DNSSEC 验证。

**实际场景**

**通用工程：** 服务迁移前应降低 TTL 并等待旧缓存窗口，再切换 A/AAAA 或别名记录；发布后同时检查权威记录、多个递归解析器和客户端缓存，不能只在一台机器 `ping` 成功就认为全球完成。

**常见追问**

- DNS 只返回 IP 吗？不是，查询返回指定类型的资源记录。
- 递归查询与迭代查询区别？客户端通常要求递归解析器给最终答案；解析器再按委派关系向不同服务器逐步查询。
- DNS 一定使用 UDP 53 吗？不是，也使用 TCP，并有 DoT、DoH 等传输方式。

**易错点**

- 把 DNS 定义成单一“域名 → IP 电话簿”。
- 认为每次访问都从根服务器开始查。
- 把 DNS 缓存误认为记录变更立即全球一致。

## 531. 浏览器输入 URL 后大致发生了什么？

**面试回答**

这是分支很多的综合流程：浏览器先把输入解释为 URL 或搜索，执行安全和导航策略；若不能由 Service Worker、缓存或现有连接满足，才进行名称解析和建连。随后可能建立 TCP+TLS 的 HTTP/1.1/2 连接，或建立 QUIC 的 HTTP/3 连接，发送 HTTP 请求、处理重定向与响应，最后解析文档、加载子资源、执行脚本并完成布局、绘制与合成。

**原理与理解**

典型网络路径可展开为：①解析 URL、检查 HSTS/代理/缓存/Service Worker；②通过本机与递归 DNS 等取得候选地址；③选择路由和地址，复用已有连接或新建连接；④HTTPS 下验证服务身份并协商 TLS/ALPN，HTTP/3 则由 QUIC 集成 TLS；⑤发送带 Header、Cookie 等的请求；⑥处理缓存验证、重定向、认证和内容编码；⑦HTML 解析生成 DOM，CSS 形成样式规则，JS 可能阻塞或改变页面，同时并行获取图片、字体等；⑧布局、绘制、合成并持续响应后续任务。

**成立条件与边界**

- DNS 不一定是第一步，也不一定发生：输入可能是搜索词，页面可能命中缓存/Service Worker，域名和连接也可能已缓存或复用。
- HTTPS 不总是“TCP 后再 TLS”：HTTP/3 使用 QUIC，TLS 1.3 能力集成其中。
- 一个页面会产生多个资源请求，并可能跨多个域名、连接和协议版本；不是单个请求返回后才一次性渲染。
- HTTP 重定向、CSP、混合内容、Cookie SameSite、缓存策略和证书错误都会改变流程。
- 浏览器渲染流程与普通后端 API 客户端不同，API 客户端通常解析 JSON 而不构建 DOM/CSSOM。

**实际场景**

**生产能力：** 页面慢时按阶段定位：DNS、建连、TLS、TTFB、下载、主线程脚本、布局与绘制分别看指标；如果连接已复用，就不能把每次接口耗时都加上一遍 DNS 和三次握手。

**常见追问**

- 输入 URL 后一定先 DNS 吗？不一定，URL/搜索判定、策略、缓存和连接复用可能先发生或直接避免 DNS。
- HTTPS 建连顺序是什么？HTTP/1.1/2 常为 TCP 后 TLS；HTTP/3 为 QUIC 握手并集成 TLS 1.3。
- 收到 HTML 就结束了吗？没有，还要解析、请求子资源、执行脚本并进行渲染流水线。

**易错点**

- 固定背诵“DNS → TCP → TLS → HTTP”，不说明缓存、连接复用和 HTTP/3 分支。
- 把页面加载当成只有一个 HTTP 请求。
- 将后端接口返回 JSON 与浏览器页面渲染过程混为一谈。
