# TCP与网络

## 523. TCP 和 UDP 有什么区别？

**面试回答**

TCP 是面向连接、可靠的传输协议，需要建立连接、保证数据有序不丢失；UDP 是无连接、不可靠的协议，直接发送、不保证到达，但更快速、开销小。

**理解**

TCP 像「打电话」：先建立连接（三次握手），保证数据按序、完整到达，适合对可靠性要求高的场景（网页、文件、邮件）；UDP 像「发短信/广播」：不建连接、直接发，不保证到达、不保证顺序，但快、开销小，适合实时性优先的场景（视频通话、直播、游戏）。

**场景**

项目里 HTTP 走 TCP（要可靠）；实时语音、视频、游戏用 UDP（要快、能容忍少量丢包）。

**常见追问**

- 谁可靠？（TCP）
- 谁快？（UDP，无连接、无重传）

**易错点**

TCP「可靠但有连接开销」、UDP「快但不可靠」，核心是「可靠性 vs 速度」的取舍。

## 524. TCP 为什么是可靠协议？

**面试回答**

因为 TCP 通过确认应答、超时重传、序号与排序、流量控制、拥塞控制等机制，保证数据不丢失、不重复、按序到达。

**理解**

可靠性体现在：①确认应答（ACK）——收到就确认；②超时重传——没收到确认就重发；③序号——数据分片编号，接收方按序重组、去重；④流量控制——根据接收方能力调整发送速度；⑤拥塞控制——避免网络拥塞。这些机制共同保证可靠传输。

**场景**

项目里 HTTP 请求走 TCP，靠这些机制保证请求/响应数据完整有序到达，不会丢包错序。

**常见追问**

- 靠什么保证不丢？（确认 + 重传）
- 靠什么保证有序？（序号）

**易错点**

TCP 可靠是「多机制共同保证」（确认、重传、序号、流量/拥塞控制），别只说「握手」。

## 525. TCP 三次握手过程是什么？

**面试回答**

①客户端发 SYN 请求建立连接；②服务器回 SYN + ACK 确认；③客户端再发 ACK 确认，双方建立连接。

**理解**

三步：客户端 SYN（我要连你）→ 服务器 SYN+ACK（好，我准备好了）→ 客户端 ACK（我知道了，开始传数据）。握手是为了双方确认「彼此的收发能力都正常」，并为后续通信约定初始序号。完成三次握手，连接建立，可以传数据。

**场景**

项目里前端每次建立 HTTP 连接（复用 TCP 时可能省略）都要经过 TCP 三次握手，这是网络通信的基础。

**常见追问**

- SYN 和 ACK 分别表示？（同步/建立连接、确认）
- 三次握手后处于什么状态？（连接已建立）

**易错点**

三次握手是「SYN → SYN+ACK → ACK」三步，别记成两次；它的目的是双方确认收发能力。

## 526. 为什么 TCP 建立连接需要三次握手？

**面试回答**

为了确认双方的收发能力都正常，并同步初始序号，同时防止「已失效的连接请求」突然到达服务器造成错误连接。

**理解**

两次握手的问题：客户端发 SYN 后，如果网络延迟导致旧的 SYN 晚到服务器，服务器以为客户端要连，回 ACK 就建了连接，但客户端其实没这个意图，造成资源浪费。三次握手让客户端最后再确认一次，避免这种「旧请求误建连接」。同时也让双方都确认「我的发送、对方接收」没问题。

**场景**

理解三次握手的目的，就明白为什么不是两次也不是四次——两次无法可靠确认，三次刚好。

**常见追问**

- 两次为什么不够？（无法确认双方收发能力，且旧请求会误建连接）
- 三次握手的核心？（双方确认 + 防旧请求）

**易错点**

三次握手的关键是「双方确认收发能力 + 防失效请求」，不是「越多次越安全」；三次是权衡后的最优。

## 527. TCP 四次挥手过程是什么？

**面试回答**

①主动方发 FIN 请求关闭；②被动方回 ACK；③被动方再发 FIN；④主动方回 ACK，连接关闭。

**理解**

关闭要四次是因为 TCP 是「全双工」，两个方向要分别关闭：主动方 FIN（我不发了）→ 被动方 ACK（知道了）→ 被动方 FIN（我也不发了）→ 主动方 ACK（好，关闭）。被动方的 ACK 和 FIN 分开（不能合并），所以是四次。挥手后主动方还要等一段时间（TIME_WAIT）。

**场景**

项目里 HTTP 连接关闭时，走 TCP 四次挥手，这是连接断开的流程。

**常见追问**

- 为什么四次？（全双工，两个方向分别关）
- 谁先发 FIN？（主动关闭的一方）

**易错点**

四次挥手 = 「两方向各一次 FIN+ACK」，比握手多一次是因为「ACK 和 FIN 不能合并」；理解全双工是关键。

## 528. 为什么关闭连接通常需要四次挥手？

**面试回答**

因为 TCP 是「全双工」通信，每个方向都要独立关闭：一方发 FIN 表示「我不发了」，对方 ACK 后可能还有数据要发，等它发完再发自己的 FIN 关闭另一个方向，所以需要四次。

**理解**

关闭连接时，主动方说「我不发了」（FIN），被动方确认（ACK），但被动方可能还有数据没发完，不能立刻关。等被动方发完，它再发 FIN 说「我也不发了」，主动方 ACK。两个方向各需要一次「FIN + ACK」，所以是四次。握手时 SYN 和 ACK 能合并（三次），挥手时 ACK 和 FIN 常常不能合并（四次）。

**场景**

项目里连接关闭时，理解「全双工要分两个方向关」，就明白为什么是四次。

**常见追问**

- 为什么不能像握手一样三次？（关闭时 ACK 和 FIN 可能分开，全双工）
- 全双工是什么意思？（双方可同时收发）

**易错点**

核心是「全双工，两方向独立关闭」；握手 SYN 能合并成三次，挥手 ACK/FIN 分开所以四次。

## 529. 什么是 TIME_WAIT？

**面试回答**

TIME_WAIT 是主动关闭连接的一方在发送最后一个 ACK 后，需要等待一段时间（约 2 个 MSL）才能完全释放连接的状态，用来确保对方收到最后的 ACK、并让旧连接的数据包在网络中消散。

**理解**

主动关闭方发完最后 ACK 后，怕这个 ACK 丢了对方重发 FIN，所以要等一会儿；同时让之前该连接的所有数据包（可能还在网络中）都过期消失，避免干扰「相同四元组」的新连接。TIME_WAIT 过多会占用端口，是高并发服务器要注意的问题。

**场景**

项目里高并发 HTTP 短连接下，若服务器频繁主动关闭，会产生大量 TIME_WAIT，需要合理配置连接复用或调优。

**常见追问**

- 谁会有 TIME_WAIT？（主动关闭的一方）
- TIME_WAIT 过多有什么问题？（占用端口/资源）

**易错点**

TIME_WAIT 是「主动关闭方」的状态，目的是「确保最后 ACK 送达 + 旧包消散」；它多会导致端口占用。

## 530. DNS 是什么？

**面试回答**

DNS（域名系统）是把域名（如 www.baidu.com）解析成 IP 地址的服务，像「电话簿」一样，让用户能用好记的域名访问服务器，而不必记 IP。

**理解**

网络通信实际靠 IP 地址，但 IP 难记。DNS 提供「域名 → IP」的映射：浏览器访问域名时，先向 DNS 服务器查询得到 IP，再用 IP 建立连接。DNS 是分层的、分布式的，有缓存机制加速解析。

**场景**

项目里前端访问后端域名，先经 DNS 解析出服务器 IP，再走 HTTP 请求。

**常见追问**

- DNS 解决什么？（域名到 IP 的解析）
- 为什么用域名不用 IP？（域名好记、可变更）

**易错点**

DNS 是「域名 → IP」的解析系统，是访问网站的第一步；它是「名字服务」，不是「数据传输协议」。

## 531. 浏览器输入 URL 后大致发生了什么？

**面试回答**

大致流程：DNS 解析域名得到 IP → 建立 TCP 连接（三次握手）→ 若是 HTTPS 再 TLS 握手 → 发送 HTTP 请求 → 服务器处理并返回响应 → 浏览器渲染页面 → 连接关闭。

**理解**

完整链路：①DNS 把域名换成 IP；②TCP 三次握手建立连接；③HTTPS 则做 TLS 加密握手；④发 HTTP 请求；⑤服务器处理（可能查库、调缓存）返回响应；⑥浏览器解析渲染；⑦连接关闭（或复用）。这是「从输入网址到看到页面」的全过程，覆盖了 DNS、TCP、HTTP 等知识点。

**场景**

项目里前端请求后端接口也是类似流程：DNS → TCP → HTTP → 服务器处理 → 返回 JSON。

**常见追问**

- 第一步是什么？（DNS 解析）
- HTTPS 在哪一步加密？（TCP 之后 TLS 握手）

**易错点**

这是「网络综合题」，要按顺序串起来：DNS → TCP → (TLS) → HTTP → 处理 → 渲染/返回，别漏环节。
