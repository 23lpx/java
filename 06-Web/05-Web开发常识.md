# Web开发常识

## 532. Entity 是什么？

**面试回答**

Entity（实体）是对应数据库表结构的对象，字段和表的列一一对应，用于和数据库交互（ORM 映射）。

**理解**

Entity 是「数据层」的对象，代表一张表的一行记录。MyBatis 等 ORM 框架把查询结果映射成 Entity，把 Entity 持久化到表。它的字段和数据库列对应，可能包含数据库相关的字段（如主键、创建时间）。

**场景**

项目里的 Dish、Order、User 就是 Entity，和对应的数据库表一一映射，用于 MyBatis 的增删改查。

**常见追问**

- Entity 对应什么？（数据库表）
- 谁来映射？（ORM 框架如 MyBatis）

**易错点**

Entity 是「数据库映射对象」，和表结构对应；它偏数据层，一般不该直接暴露给前端。

## 533. DTO 是什么？

**面试回答**

DTO（Data Transfer Object，数据传输对象）是用于「层与层之间传输数据」的对象，尤其是接收前端请求参数或在不同服务间传递数据，字段按传输需要定义，不一定和表结构一致。

**理解**

DTO 服务于「数据传输」，不绑定数据库。比如接收前端提交的菜品数据，可能包含分类 id、多个口味选项等，字段和 Entity 不完全一样。用它接收参数、封装传输数据，避免直接用 Entity 接收导致字段不匹配或过度暴露。

**场景**

项目里 DishDTO 接收前端提交的菜品数据（含口味、分类等），字段和 Dish 实体不完全一致。

**常见追问**

- DTO 用来干什么？（数据传输，接收请求/跨层传数据）
- 和 Entity 区别？（DTO 按传输需要，Entity 按表结构）

**易错点**

DTO 是「传输对象」，字段按「传输/请求需要」定，不一定要和表一致；别把它和 Entity 等同。

## 534. VO 是什么？

**面试回答**

VO（View Object，视图对象）是「返回给前端展示」的对象，字段按页面展示需要组织，可能聚合多个实体的字段，或只暴露部分字段。

**理解**

VO 面向「展示层」，为前端量身定制：比如订单详情 VO 可能聚合订单信息 + 用户昵称 + 菜品列表，或只返回前端需要的几个字段（隐藏敏感字段）。它让返回结构符合前端需要，避免把 Entity 的敏感/冗余字段直接暴露。

**场景**

项目里 DishVO 返回给前端的菜品数据，可能带上分类名称、状态描述等展示用字段。

**常见追问**

- VO 面向谁？（前端展示）
- 和 DTO 区别？（DTO 侧重传输/接收，VO 侧重返回展示）

**易错点**

VO 是「展示对象」，为前端展示定制（聚合、裁剪字段）；和 DTO（传输）、Entity（表映射）定位不同。

## 535. DTO、VO、Entity 有什么区别？

**面试回答**

Entity 对应数据库表，用于数据持久化；DTO 用于传输数据（尤其接收请求），字段按传输需要；VO 用于返回给前端展示，字段按展示需要。三者定位分别是「数据层、传输层、展示层」。

**理解**

核心是「各层用各层的对象，避免一个对象打天下」：Entity 绑定表结构，不应直接暴露前端；DTO 负责接收和传输，字段灵活；VO 负责返回展示，按页面裁剪/聚合。这样分层清晰、各层解耦，也能隐藏内部字段。

**场景**

项目里：Dish（Entity）对应表，DishDTO 接收新增/修改请求，DishVO 返回列表/详情给前端，三者字段各有侧重。

**常见追问**

- 为什么不一个对象通用？（各层需求不同，混用会暴露内部结构、难维护）
- 三者分别在哪层？（Entity 数据层、DTO 传输层、VO 展示层）

**易错点**

三者区别在「定位/用途」：Entity 表映射、DTO 传输、VO 展示；这是后端分层设计的基础。

## 536. 为什么不建议直接把 Entity 返回给前端？

**面试回答**

因为 Entity 绑定数据库表结构，直接返回会：①暴露内部字段（如密码、删除标记等敏感信息）；②前端拿到不需要的冗余字段；③数据库结构变化会直接冲击前端接口，耦合严重；④某些字段序列化可能有坑（如懒加载、循环引用）。

**理解**

Entity 是「数据层」的对象，包含表的全部列，其中可能有敏感字段（密码）、内部字段（状态码、删除标记）不该给前端。直接返回还会让接口和表结构强耦合，表一改接口就变。用 VO 按前端需要裁剪、隐藏敏感字段，是更安全、更解耦的做法。

**场景**

项目里 User 实体含密码，绝不能不处理就返回；用 UserVO 只返回昵称、头像等安全字段。

**常见追问**

- 直接返回有什么风险？（泄露敏感字段、过度暴露）
- 怎么做？（转成 VO/DTO 返回）

**易错点**

核心风险是「敏感字段泄露 + 表结构耦合」；用 VO/DTO 隔离是标准做法。

## 537. 为什么需要参数校验？

**面试回答**

因为不能信任客户端传来的数据，后端必须校验参数的合法性（非空、格式、范围），防止非法数据入库、引发业务错误或安全问题。

**理解**

前端校验可被绕过（直接调接口），后端校验才是数据安全的兜底。校验能拦截：空值、格式错误、越界、非法值等，避免脏数据、防注入、保证业务规则。这是「防御式编程」的基本要求。

**场景**

项目里用 @Valid + 校验注解对 DTO 做校验，非法输入直接拦截，返回友好错误。

**常见追问**

- 只做前端校验行不行？（不行，可被绕过）
- 校验主要防什么？（非法数据、脏数据、安全问题）

**易错点**

参数校验是「后端兜底」，和前端校验各司其职；不校验会导致脏数据和安全漏洞。

## 538. 分页接口通常需要哪些参数？

**面试回答**

通常需要：页码（page/pageNum）、每页条数（pageSize/size），可选：查询条件、排序字段和方式。

**理解**

分页接口的核心参数是「第几页 + 每页多少条」，后端据此算 offset（(page-1)*size）用 LIMIT 查询。还常带过滤条件（关键字、状态等）和排序（按时间/价格）。返回一般包含：当前页数据列表、总条数、总页数等。

**场景**

项目里菜品分页接口接收 page、pageSize 和查询条件（菜名、分类、状态），返回 PageResult（列表 + 总数）。

**常见追问**

- offset 怎么算？（(page-1) × pageSize）
- 返回什么？（列表 + 总数/总页数）

**易错点**

分页核心参数是「页码 + 每页条数」；后端要返回「列表 + 总数」，前端才能渲染分页条。

## 539. 什么是接口幂等？

**面试回答**

接口幂等指同一个请求重复执行多次，产生的效果和执行一次相同，不会因为重复调用而产生额外副作用。

**理解**

幂等是接口的重要属性，保证「重复请求安全」。查询天然幂等；更新成固定值也幂等；但「下单、支付、扣款」这类创建/扣减操作不幂等，重复执行会出问题。幂等对网络重试、用户重复点击、消息重复消费都至关重要。

**场景**

项目里支付、下单接口要保证幂等，防止用户重复点击或网络重试导致重复扣款、重复下单。

**常见追问**

- 幂等和重复提交什么关系？（幂等接口能天然防重复提交）
- 怎么保证幂等？（唯一约束、token、状态判断等）

**易错点**

幂等是「重复执行结果相同、无额外副作用」，不是「响应内容相同」；它是设计接口时必须考虑的属性。

## 540. 哪些接口需要考虑幂等？

**面试回答**

有「副作用」的接口都要考虑，尤其是：下单、支付、扣款、扣库存、转账、创建资源、消息消费等，这些重复执行会产生严重后果。

**理解**

凡是「改变了状态、且重复执行会叠加副作用」的操作都要幂等保护：下单重复=多订单，支付重复=多扣钱，扣库存重复=超卖。而查询、删除（删已删的）、按固定值更新天然幂等或影响小。设计时对「非幂等且高敏感」的接口要重点做幂等。

**场景**

项目里支付宝支付、下单、扣库存接口必须幂等，防止重复提交导致多扣款/超卖。

**常见追问**

- 哪些天然幂等？（查询、删除、固定值更新）
- 哪些必须做幂等？（支付、扣款、下单）

**易错点**

有「副作用的写操作」是幂等重点关注对象，尤其「支付/扣款/下单」这类，重复会出大事。

## 541. 重复提交订单可能产生什么问题？

**面试回答**

可能产生：重复下单（生成多笔重复订单）、重复扣款、库存重复扣减（超卖）、数据不一致等，造成经济损失和用户体验问题。

**理解**

用户快速点两次「提交」，或网络重试，导致同一个下单请求执行两次：可能生成两笔相同订单、扣两次钱、库存扣两次。尤其是支付环节，重复提交可能多扣钱。所以下单/支付接口要做幂等（如用唯一订单号、token 防重、数据库唯一约束）。

**场景**

项目里下单接口用幂等设计（如订单号唯一、提交 token），防止用户重复点击产生重复订单。

**常见追问**

- 为什么会重复提交？（用户连点、网络重试）
- 怎么防？（幂等：唯一订单号、防重 token、唯一约束）

**易错点**

重复下单的后果是「多订单 + 多扣款 + 超卖」，本质是接口不幂等；解决靠「幂等设计」，是下单接口的必考题。
