# Web开发常识

## 532. Entity 是什么？

**面试回答**

在常见 Java 后端分层中，Entity 通常表示具有业务身份、并可能映射到持久化数据的对象；很多 CRUD 项目会让它与数据库表字段大体对应。但 `Entity` 不是 MyBatis 强制的类型名，在领域驱动设计中它更强调“由标识区分、生命周期内保持身份”，不等于必须与一张表一一对应。

**原理与理解**

MyBatis 实际映射的是普通 Java 对象，类名可以是 Entity、PO、DO 或其他约定。数据表与对象也未必严格一一对应：字段可通过 SQL 别名或 `resultMap` 映射，查询对象还可能来自多表结果。面试时应先说明团队语境，再描述其职责。

**成立条件与边界**

- 在本知识库的 CRUD 语境中，可把 Entity 理解为靠近持久化层的数据对象。
- 不能把“字段与表列完全一致”当作定义；对象可忽略列、增加非持久化字段或组合映射。
- JPA 的 `@Entity` 有框架规范语义，MyBatis 中的 Entity 通常只是命名约定，两者不要混同。
- DDD Entity 与“数据库映射对象”存在交集，但关注点不同。

**实际场景**

**项目核验项：** 苍穹外卖简历确认使用 MyBatis，但没有列出具体实体类及其映射关系；面试前应从代码确认订单、菜品等类的真实命名，以及是否存在 `resultMap`、驼峰映射或非表字段。

**常见追问**

- MyBatis 要求类名必须叫 Entity 吗？不要求，它映射普通 Java 对象。
- Entity 必须对应一张表吗？不必须，要看项目分层和映射方式。
- JPA Entity 与 MyBatis 实体有什么区别？前者受 JPA 映射规范约束，后者通常是项目约定。

**易错点**

- 把 Entity 绝对定义为“与表一一对应的类”。
- 混淆 DDD Entity、JPA Entity 与普通持久化对象。
- 认为 MyBatis 会根据 `Entity` 这个类名自动完成映射。

## 533. DTO 是什么？

**面试回答**

DTO（Data Transfer Object）是按一次数据传输契约组织字段的对象，用于跨层、跨进程或接口边界传递数据。它不应被数据库表结构支配，可以分别设计请求 DTO 和响应 DTO，并承载参数校验注解。

**原理与理解**

接口所需字段通常不同于持久化字段。DTO 把外部输入或服务调用契约与内部模型隔离，使接口字段、校验规则和版本演进不必直接改变 Entity。转换可手写，也可使用映射工具，但关键是明确字段来源和信任边界。

**成立条件与边界**

- DTO 不只用于接收前端参数，也可用于服务间传输和应用层命令/查询结果。
- DTO 本身只是数据载体；是否允许业务方法取决于团队规范。
- 使用 DTO 不会自动阻止越权或恶意赋值，服务端仍要做权限、字段白名单和业务校验。
- 简单内部接口可以少建对象，但要接受耦合和字段暴露风险。

**实际场景**

**项目核验项：** 简历没有列出 DTO 类名和字段；可从苍穹外卖代码核验新增菜品、套餐或下单请求是否使用独立 DTO，以及嵌套集合是否配合 `@Valid` 做级联校验。

**常见追问**

- DTO 必须和 Entity 字段相同吗？不必，应以传输契约为准。
- DTO 能作为响应对象吗？可以，DTO 是广义传输对象；有些团队另用 VO 区分响应。
- DTO 如何转 Entity？可手写、构造器或映射工具，关键字段需显式审查。

**易错点**

- 把 DTO 仅限定为 Controller 的请求参数。
- 用属性全量复制覆盖服务端维护字段，如 ownerId、状态或审计字段。
- 认为拆出 DTO 后就天然安全、无需授权校验。

## 534. VO 是什么？

**面试回答**

在国内常见 Web 项目语境中，VO 通常指 View Object，即按前端展示需要组织的响应对象，可以裁剪或聚合多个来源的数据。不过 VO 也常被用作 Value Object（值对象）的缩写，因此面试时要先说明本项目采用哪种含义。

**原理与理解**

View Object 让 API 响应契约独立于数据表：例如把状态码转换为展示字段，或聚合订单与明细。它的核心价值是边界隔离，而不是给 Entity 换一个名字。若团队使用“Response DTO”而不用 VO，也同样合理。

**成立条件与边界**

- VO 是团队命名习惯，不是 Spring 或 MyBatis 的强制分层。
- View Object 不应携带密码、内部审计字段等不该暴露的信息。
- 聚合字段可能来自多表、缓存或计算结果，不代表必须先加载多个 Entity 再拼装。
- 在 DDD 讨论中，VO 往往指 Value Object，含义与展示对象不同。

**实际场景**

**项目核验项：** 简历未声明 DishVO、OrderVO 等具体类型；面试前需要通过 Controller 返回类型确认项目究竟使用 VO、DTO 还是直接返回分页结果，避免背出代码里不存在的类名。

**常见追问**

- VO 一定是 View Object 吗？不一定，也可能表示 Value Object，要结合上下文。
- VO 可以包含多个表的数据吗？可以，它面向响应契约而非表结构。
- VO 和响应 DTO 有本质差别吗？通常没有统一标准，主要是团队命名和职责约定。

**易错点**

- 不说明语境就断言 VO 只有一种含义。
- 把 VO 理解为 Entity 的机械复制品。
- 为了“分层”创建大量完全相同且没有边界价值的对象。

## 535. DTO、VO、Entity 有什么区别？

**面试回答**

在本知识库采用的 Web 分层语境中：Entity 靠近领域或持久化模型，DTO 面向数据传输契约，VO 面向页面或接口响应展示。区别主要在职责和变化原因，而不是后缀；这些名称是项目约定，并非 Java、Spring 或 MyBatis 的统一标准。

**原理与理解**

数据库结构、请求契约和响应展示的变化节奏不同。分别建模可以避免表字段变化直接传到 API，也能控制可写字段和可见字段。转换代码增加了一定成本，因此是否拆分应依据安全性、复杂度和维护收益决定。

**成立条件与边界**

- 常见流向是请求 DTO → 业务处理 → Entity/持久化对象 → VO/响应 DTO，但不是唯一架构。
- 同一对象在小型、低风险内部系统中可以复用；不能把拆三层当成绝对规则。
- 分层不能代替字段授权、数据脱敏、参数校验和版本管理。
- 类名不能证明职责，应以代码依赖方向和字段所有权判断。

**实际场景**

**通用工程：** 创建订单时，请求对象只接收用户可提交字段；用户身份、订单状态和审计字段由服务端生成；查询响应再按页面需要返回订单与明细，避免客户端直接控制持久化对象的所有属性。

**常见追问**

- 为什么不使用一个对象到底？会增加接口与表结构耦合，并扩大可写、可见字段范围。
- 三种对象必须全部存在吗？不必须，按复杂度和风险选择。
- 主要转换放在哪里？通常在应用/服务边界或专用转换器中，避免散落在各层。

**易错点**

- 把三者说成框架规定的固定层级。
- 只会背“Entity 对表、DTO 入参、VO 出参”，说不出隔离了什么变化。
- 认为对象越多架构一定越好。

## 536. 为什么不建议直接把 Entity 返回给前端？

**面试回答**

主要是为了控制数据暴露并隔离 API 与持久化模型。Entity 可能包含密码摘要、内部状态、逻辑删除和审计字段；直接序列化还会让表结构变化影响接口契约。通常应返回明确的 VO 或响应 DTO，但简单、受控且字段完全合适的场景并非绝对禁止。

**原理与理解**

响应模型是一份对外契约，应明确哪些字段可见。直接返回 Entity 容易出现过度暴露，也可能遭遇关联对象递归、懒加载或序列化行为变化。显式转换能形成字段白名单，并允许接口字段与数据库字段独立演进。

**成立条件与边界**

- “不建议”不是“任何情况下都错误”，要结合接口受众、字段敏感度和维护成本。
- 仅靠 `@JsonIgnore` 可以缓解个别字段暴露，但会把 API 规则耦合回持久化类型。
- 返回 DTO 仍可能泄露数据，安全来自正确选择和授权字段，而不是类名。
- 下载、流式响应、204 等接口不适合强行套普通 JSON 对象。

**实际场景**

**通用工程：** 用户查询接口应显式返回昵称、头像等允许字段，而不直接序列化包含密码摘要、内部状态或审计信息的用户持久化对象。

**常见追问**

- 最大风险是什么？敏感或内部字段泄露，以及接口与表结构强耦合。
- 使用 VO 就一定安全吗？不一定，仍需字段审查、权限校验和脱敏。
- 什么时候可直接返回？字段简单、边界受控、契约稳定并经过明确审查时可以权衡。

**易错点**

- 说“Entity 永远不能返回”。
- 只提代码整洁，不提字段授权和契约稳定性。
- 把换成 VO 当作自动脱敏。

## 537. 为什么需要参数校验？

**面试回答**

因为客户端输入不可信，服务端必须在进入核心业务前验证结构约束和业务规则，尽早拒绝缺失、格式错误、越界或不允许的数据。Jakarta Validation 适合声明字段、对象和方法参数约束，但权限、状态转换、唯一性等业务规则仍需业务层和数据库共同保证。

**原理与理解**

Spring MVC 可对带 `@Valid` 或 `@Validated` 的请求对象执行 Bean Validation；不同方法签名可能抛出 `MethodArgumentNotValidException` 或 `HandlerMethodValidationException`。结构校验只是第一层，后续还要做身份授权、业务状态校验和数据库约束。

**成立条件与边界**

- 前端校验改善体验，但可被绕过，不能替代后端校验。
- `@Valid` 主要触发级联校验，本身不是“非空”等约束；嵌套对象需要正确标注。
- 参数校验不能防 SQL 注入；SQL 注入主要依靠参数化查询和安全的动态 SQL 构造。
- “先查是否重复”不能替代数据库唯一约束，并发下仍可能竞态。
- 校验错误应返回稳定、可定位但不过度暴露内部实现的信息。

**实际场景**

**项目核验项：** 简历确认苍穹外卖使用 Spring MVC，但未声明 `@Valid`、校验分组或异常类型；需要从 Controller 签名与依赖版本核验真实实现后，才能作为项目经验回答。

**常见追问**

- `@Valid` 与 `@Validated` 有什么区别？前者属于 Jakarta Validation 并支持级联；后者是 Spring 扩展，可指定校验组，具体方法校验行为还与 Spring 版本和声明位置有关。
- 参数校验放在哪层？接口层做结构约束，业务层做业务不变量，数据库做最终约束。
- 校验能防注入吗？不能，需使用参数绑定并限制动态标识符。

**易错点**

- 把校验注解当成完整安全方案。
- 认为只做前端校验即可。
- 忘记集合元素、嵌套对象和方法级校验的触发条件。

## 538. 分页接口通常需要哪些参数？

**面试回答**

页码分页通常接收 `page`、`pageSize`，再加过滤条件和受控的排序字段；响应可包含数据列表、总数、当前页等。数据量大或翻页频繁时可改用游标分页，使用稳定排序键和下一页游标，避免大 OFFSET 的成本与并发变化造成的重复或遗漏。

**原理与理解**

OFFSET 分页将页码转换为偏移量，易理解且适合后台列表；但深分页需要扫描或跳过更多记录。游标分页从上次的稳定排序位置继续查询，通常性能和一致性更好，但不便随机跳页，也不一定提供精确总数。

**成立条件与边界**

- `page` 通常从 1 开始，但必须以接口契约为准；要校验最小值和 `pageSize` 上限。
- 排序必须稳定，常在时间字段后补唯一主键，避免同值导致跨页重复或遗漏。
- 排序字段和方向应使用白名单，不能把客户端字符串直接拼入 SQL。
- 总数查询可能很贵，不是所有分页响应都必须返回 `total`。
- `(page-1)*pageSize` 只适用于约定从 1 开始的 OFFSET 分页。

**实际场景**

**项目核验项：** 简历没有描述分页方案；应从苍穹外卖代码核验是否使用 PageHelper、MyBatis 分页插件或手写 `LIMIT`，以及返回对象是否确实包含 `total`，不能仅凭教程印象作答。

**常见追问**

- OFFSET 分页有什么问题？深分页成本高，数据并发变化时可能重复或漏项。
- 游标分页需要什么？稳定且可比较的排序键，以及服务端生成或校验的游标。
- 为什么限制 pageSize？控制数据库、内存、网络和序列化成本。

**易错点**

- 认为分页一定要查精确总数。
- 只按非唯一时间排序，忽略稳定性。
- 允许客户端任意拼接排序字段。

## 539. 什么是接口幂等？

**面试回答**

接口幂等是指对同一目标重复执行语义相同的请求，其在服务端产生的预期效果与执行一次相同。幂等关注业务效果，不要求每次响应字节、日志、时间戳完全相同。

**原理与理解**

RFC 9110 将安全方法以及 PUT、DELETE 定义为幂等方法语义；但服务端实现仍可能写多条访问日志。POST 默认不具备幂等语义，业务可以通过幂等键、唯一约束和状态机把具体 POST 操作设计成可安全重试。

**成立条件与边界**

- 幂等请求的响应可能不同，例如首次 DELETE 返回成功，重复删除返回已不存在，但目标状态一致。
- HTTP 方法语义不能替代正确实现；错误的 PUT 或 DELETE 代码仍可能产生累加副作用。
- 幂等键应绑定调用方、业务操作和请求摘要，并定义有效期与冲突处理。
- 数据库唯一约束只能解决某类重复写入，不能自动处理所有外部调用和部分成功。
- 幂等不等于并发安全，也不等于事务原子性。

**实际场景**

**真实项目边界：** 简历确认支付宝异步回调通过状态校验和重复通知过滤实现幂等；这是“同一支付结果重复通知，不重复迁移订单状态”的项目证据，不应扩展成所有下单接口都已实现幂等。

**常见追问**

- 幂等要求响应完全一样吗？不要求，核心是预期业务效果相同。
- POST 能幂等吗？规范默认不保证，但具体业务可以通过设计实现。
- 幂等与去重一样吗？去重是常用手段，幂等是最终效果属性。

**易错点**

- 把幂等定义成“返回结果完全一致”。
- 只根据 GET/POST 名称判断实际接口是否安全重试。
- 有唯一索引就宣称整个跨系统流程绝对幂等。

## 540. 哪些接口需要考虑幂等？

**面试回答**

凡是可能因用户连点、客户端重试、消息重复投递或超时重放而重复执行，并且重复会造成不可接受副作用的操作，都要评估幂等，尤其是创建订单、支付状态迁移、扣款、发券、库存变更和消息消费。保护强度应按业务风险设计，而不是给所有写接口套同一种锁。

**原理与理解**

是否需要额外机制取决于 HTTP 语义、业务不变量和失败模型。读取通常安全；按确定目标状态执行的 PUT/DELETE 具有幂等语义；创建或累加类 POST 风险更高。常见手段包括客户端幂等键、业务唯一键、条件更新、状态机、去重记录和事务。

**成立条件与边界**

- “写操作”不等于一定非幂等，“读操作”也不能偷偷产生扣费等业务副作用。
- 自动重试非幂等请求前，调用方必须知道它已通过业务设计变为可安全重试，或确认原请求未执行。
- 防重复点击只能减少请求，不能替代服务端幂等。
- 分布式锁不是默认答案；锁过期、故障和重复消息仍需业务唯一性兜底。
- 外部支付、消息和数据库组合流程需要状态查询、补偿或对账，不能只依赖单库事务。

**实际场景**

**真实项目边界：** 苍穹外卖简历能够支撑“支付回调需要状态校验和重复通知过滤”；订单提交、库存扣减是否具有独立幂等键或唯一约束仍属于项目核验项。

**常见追问**

- 常见幂等手段怎么选？优先找业务唯一标识和合法状态迁移，再结合唯一约束、条件更新或幂等记录。
- 查询接口都安全吗？按 HTTP 语义应只读，但实现若产生业务副作用就不安全。
- 为什么不能只禁用按钮？请求可能来自重试、脚本或消息，不只来自页面连点。

**易错点**

- 说所有有副作用的接口都天然非幂等。
- 用前端按钮防抖代替服务端保证。
- 不分析失败窗口就机械使用 Redis 锁。

## 541. 重复提交订单可能产生什么问题？

**面试回答**

重复提交可能创建多笔订单，并进一步触发重复优惠占用、库存预留、支付单创建或通知发送；是否会重复扣款取决于支付链路自身是否也失去幂等保护。治理时要先定义“同一次业务提交”的唯一身份，再用唯一约束、幂等记录或条件状态迁移保证原子判定。

**原理与理解**

用户连点、代理重试、客户端超时重试都可能让相同意图到达多次。如果服务端采用“先查后插”，并发请求仍可能同时查不到并各自创建。可靠方案通常让判定与写入在数据库约束或原子操作中完成，并对相同幂等键返回原处理结果或当前状态。

**成立条件与边界**

- 业务订单号只有在服务端复用同一标识并受唯一约束时才能防重；每次重试生成新号没有作用。
- 唯一约束冲突要转换为“已受理/参数冲突”等明确语义，不能一律当系统错误。
- 幂等键相同但请求内容不同应拒绝，防止误把不同订单合并。
- 订单创建幂等不自动保证支付、库存和消息链路幂等。
- 幂等记录需要考虑过期时间、存储容量、并发和故障恢复。

**实际场景**

**项目核验项：** 简历没有声明下单接口使用提交 Token、订单幂等键或订单号唯一约束，因此只能把重复下单作为应掌握的设计场景；现阶段不能说苍穹外卖已经采用某一种方案。

**常见追问**

- “先查订单是否存在”够吗？不够，并发下存在检查与插入之间的竞态窗口。
- 幂等键重复时应该返回什么？通常返回原结果或当前处理状态；若请求摘要不同则返回冲突。
- 订单防重后还会重复扣款吗？仍需支付侧使用商户订单号、状态机和回调幂等独立保证。

**易错点**

- 直接断言重复下单一定造成重复扣款或超卖。
- 给每次重试生成新的业务唯一号。
- 把数据库唯一约束错误裸露给前端。
