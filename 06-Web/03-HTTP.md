# HTTP

## 411. HTTP 是什么？

**面试回答**

HTTP（超文本传输协议）是客户端和服务器之间传输数据（如网页、JSON、图片）的应用层协议，基于请求-响应模型，是无状态的。

**理解**

HTTP 定义「客户端怎么发请求、服务器怎么回响应」的格式和规则。它是 Web 的基石，浏览器、App 都通过 HTTP 和服务器通信。它基于 TCP，无状态（每次请求独立，不记住上次）。前端发请求、后端返数据，都遵循 HTTP 规范。

**场景**

项目里前端调用后端接口、提交 JSON 数据、接收响应，都是通过 HTTP 协议完成。

**常见追问**

- HTTP 是什么层协议？（应用层）
- 「无状态」什么意思？（见 [[06-Web/03-HTTP#421. HTTP 为什么是无状态协议？]]）

**易错点**

HTTP 是「应用层协议」、基于 TCP、无状态；它是「协议/规范」，不是「数据本身」。

## 412. HTTP 请求由哪些部分组成？

**面试回答**

主要由四部分：请求行（方法 + URL + 协议版本）、请求头（Headers）、空行、请求体（Body，可选）。

**理解**

请求行说明「做什么操作、访问哪个资源」，如 `POST /api/login HTTP/1.1`；请求头是键值对，携带元信息（Content-Type、Authorization 等）；空行分隔头和体；请求体携带数据（如 POST 提交的 JSON）。GET 通常没有请求体，POST 有。

**场景**

项目里前端 POST 登录请求：请求行是 POST /user/login，头带 Content-Type: application/json，体里是账号密码 JSON。

**常见追问**

- 请求行包含什么？（方法、URL、协议版本）
- 请求头和请求体的区别？（头是元信息，体是数据）

**易错点**

请求的四个部分「行、头、空行、体」要能说清；GET 一般无请求体、POST 有。

## 413. HTTP 响应由哪些部分组成？

**面试回答**

主要由四部分：状态行（协议版本 + 状态码 + 状态描述）、响应头（Headers）、空行、响应体（Body）。

**理解**

状态行说明「结果如何」，如 `HTTP/1.1 200 OK`；响应头是元信息（Content-Type、Content-Length 等）；响应体是返回的数据（HTML、JSON 等）。状态码标识成功/失败（200 成功、404 未找到等）。

**场景**

项目里后端返回 JSON：状态行 200 OK，响应头 Content-Type: application/json，响应体是 Result 对象的 JSON。

**常见追问**

- 状态行包含什么？（协议版本、状态码、状态描述）
- 状态码在哪？（状态行）

**易错点**

响应的四个部分「状态行、头、空行、体」；状态码在状态行里，是判断结果的关键。

## 414. HTTP Header 是什么？

**面试回答**

HTTP Header（请求头/响应头）是键值对形式的元信息，描述请求或响应本身的属性，如内容类型、长度、认证信息、缓存控制等，不直接是业务数据。

**理解**

Header 是「关于数据的说明」：请求头里常见 Content-Type（数据格式）、Authorization（认证）、User-Agent（客户端）；响应头里常见 Content-Type、Content-Length、Set-Cookie。它让双方知道「怎么处理 Body」。

**场景**

项目里前端请求带 Authorization 头放 JWT，后端响应带 Content-Type 标明返回 JSON。

**常见追问**

- Header 是什么形式？（键值对）
- 常见请求头？（Content-Type、Authorization、User-Agent）

**易错点**

Header 是「元信息/关于数据的说明」，和 Body（实际数据）要区分；别把两者混为一谈。

## 415. HTTP Body 是什么？

**面试回答**

HTTP Body 是请求或响应里实际传输的数据内容，如 POST 提交的 JSON、服务器返回的 HTML/JSON 数据。

**理解**

Body 是「真正要传的数据」。请求体：POST/PUT 提交的数据（JSON、表单等）；响应体：服务器返回的内容（页面、JSON、图片）。它和 Header 分工：Header 说明「怎么解析」，Body 是「内容本身」。GET 请求通常没有请求体。

**场景**

项目里 POST 下单请求，Body 是订单 JSON；响应 Body 是返回的 Result JSON。

**常见追问**

- Body 存什么？（实际数据内容）
- GET 有 Body 吗？（通常没有）

**易错点**

Body 是「数据本身」，Header 是「数据说明」；POST 的数据在 Body 里，GET 参数在 URL 里。

## 416. GET 和 POST 有什么区别？

**面试回答**

GET 用于获取资源，参数放在 URL 里，可缓存、幂等；POST 用于提交数据，数据放在请求体里，通常不幂等、不缓存。

**理解**

语义上 GET 是「查」、POST 是「提交/新增」。GET 参数在 URL（有长度限制、可见），适合查询；POST 数据在 Body（无明确长度限制、相对隐蔽），适合提交大或敏感数据。GET 幂等可缓存，POST 一般有副作用不幂等。但从技术上都只是 HTTP 方法，语义要遵循约定。

**场景**

项目里查询菜品列表用 GET（参数在 URL），新增菜品、下单用 POST（数据在 Body）。

**常见追问**

- 谁的数据在 URL？（GET）
- 谁更安全？（都不安全，POST 只是不显示在 URL，传输层面要 HTTPS 保护）

**易错点**

GET/POST 是「语义和用法」区别（查询 vs 提交、URL vs Body、幂等性）；别误以为「POST 就一定安全」，安全要靠 HTTPS。

## 417. PUT 和 POST 有什么区别？

**面试回答**

语义上 PUT 用于「更新整个资源」（幂等，重复请求结果相同），POST 用于「创建资源或提交操作」（通常不幂等）。

**理解**

PUT 是「替换/更新指定资源」，要求指定完整资源标识，重复执行结果一样（幂等）；POST 是「创建/提交」，常产生新资源，重复执行可能产生多个（不幂等）。RESTful 风格里：POST 创建、PUT 整体更新。但实际很多项目用 POST 同时做增改，PUT 用得少。

**场景**

项目里更新接口通常用 PUT（RESTful）或 POST（更常见），取决于团队的接口规范。

**常见追问**

- 谁幂等？（PUT 幂等，POST 不幂等）
- PUT 更新什么？（整个资源，或指定字段）

**易错点**

PUT「更新 + 幂等」、POST「创建 + 不幂等」是核心区别；但实际使用要看项目约定，别绝对化。

## 418. PUT 和 PATCH 有什么区别？

**面试回答**

PUT 用于「整体替换」资源（要传完整数据，幂等）；PATCH 用于「部分更新」资源（只传要改的字段，不保证幂等）。

**理解**

PUT 语义是「用新数据替换整个资源」，没传的字段可能被置空；PATCH 语义是「只修改指定字段」，其他字段保持不变。比如改用户信息：PUT 要传完整用户对象，PATCH 只传要改的昵称。PATCH 更细粒度。

**场景**

项目里部分更新字段（如只改状态）用 PATCH 更贴切，但很多项目统一用 PUT/POST 简化。

**常见追问**

- 谁适合部分更新？（PATCH）
- PUT 的「整体替换」意味着什么？（没传的字段可能被覆盖）

**易错点**

PUT「整体替换」、PATCH「部分更新」，是两者核心区别；但实际很多接口没严格区分。

## 419. 什么是 HTTP 方法幂等？

**面试回答**

幂等指同一个请求执行一次和执行多次，产生的效果/结果相同，重复请求不会造成额外副作用。

**理解**

「幂等」是接口的重要属性：GET 查数据，查十次结果一样、无副作用，幂等；PUT 更新成同一个值，重复更新结果一样，幂等；POST 创建资源，重复调用可能创建多条，不幂等。幂等对「重试安全」「防重复提交」很重要。

**场景**

项目里查询接口幂等（随便重试）；下单接口不幂等，重复提交会产生重复订单，所以要防重。

**常见追问**

- 幂等有什么意义？（重试安全、防重复）
- 哪些方法幂等？（GET、PUT、DELETE，POST 不幂等）

**易错点**

幂等是「重复执行结果相同、无额外副作用」，不是「响应内容一模一样」；它是设计接口要考虑的重要属性。

## 420. 哪些 HTTP 方法通常具有幂等性？

**面试回答**

GET、PUT、DELETE、HEAD 通常具有幂等性；POST 通常不幂等。

**理解**

GET 查询无副作用，幂等；PUT 更新为同一状态，重复结果一致，幂等；DELETE 删除，删一次和删多次（第二次返回不存在）结果都是「资源已删除」，幂等；POST 创建，重复可能创建多条，不幂等。注意「幂等」看的是服务端资源状态，不是返回码完全相同。

**场景**

项目里查询、更新、删除接口应尽量设计成幂等，便于重试；下单等创建接口要额外做幂等保护。

**常见追问**

- DELETE 为什么幂等？（删多次结果都是已删除）
- POST 为什么不幂等？（重复创建可能多资源）

**易错点**

GET/PUT/DELETE 幂等、POST 不幂等是常规结论；但「幂等」取决于具体实现，方法本身只是约定。

## 421. HTTP 为什么是无状态协议？

**面试回答**

因为 HTTP 协议本身不保存客户端的状态：每次请求都是独立的，服务器不记得之前请求的任何信息，两个请求之间没有关联。

**理解**

「无状态」指协议层面不维护「会话记忆」——服务器处理每个请求时，不依赖也不保存上一个请求的上下文。这样服务器更简单、易扩展。但实际业务需要「记住用户」，于是用 Cookie/Session、Token 等机制在应用层补上「状态」，这就是「协议无状态、应用有状态」。

**场景**

项目里 HTTP 本身无状态，所以用 JWT 让客户端携带身份信息，服务器靠它识别用户。

**常见追问**

- 无状态有什么好处？（服务器简单、易扩展）
- 怎么记住用户？（Cookie/Session/Token 在应用层补充）

**易错点**

「无状态」是「协议不保存会话」，不是「不能实现登录」；登录靠上层机制补状态，别混淆。

## 422. 200 表示什么？

**面试回答**

200 OK，表示请求成功，服务器正常处理并返回了结果。

**理解**

200 是 2xx 成功类的代表，表示「请求被成功处理」。响应体里通常就是业务数据。2xx 还有 201 Created（创建成功）等，但 200 是最通用的成功码。

**场景**

项目里接口正常返回数据时状态码就是 200，响应体是 Result 对象。

**常见追问**

- 2xx 代表什么？（成功）
- 201 表示什么？（创建成功）

**易错点**

200 是「成功」的通用码；但要注意「HTTP 200 + 业务失败」的情况（业务错误码在响应体里，HTTP 层仍是 200），这是接口设计常见约定。

## 423. 400 表示什么？

**面试回答**

400 Bad Request，表示客户端请求有错误（如参数格式不对、缺少必填参数），服务器无法或拒绝处理。

**理解**

400 属于 4xx 客户端错误，表示「请求本身有问题」，责任在客户端。比如参数校验失败、JSON 格式错误。项目里参数校验失败可能返回 400，也可能统一返回 200 + 错误码，取决于接口规范。

**场景**

项目里请求体 JSON 格式错误、必填参数缺失时，可能返回 400。

**常见追问**

- 4xx 代表什么？（客户端错误）
- 400 和 401/403 区别？（400 是请求格式问题，401 未认证，403 无权限）

**易错点**

400 是「请求本身有问题」（客户端责任），和 401（未登录）、403（无权限）要区分。

## 424. 401 和 403 有什么区别？

**面试回答**

401 Unauthorized 表示「未认证/未登录」——用户没提供身份凭证或凭证无效；403 Forbidden 表示「已认证但无权限」——用户知道是谁，但不被允许访问该资源。

**理解**

401 是「你是谁都没证明」，需要先登录/提供有效 token；403 是「知道你是谁，但你没权限」，比如普通用户访问管理端接口。顺序上通常是「先认证（401）再授权（403）」。

**场景**

项目里没带 token 或 token 无效返回 401；普通用户访问管理员接口返回 403。

**常见追问**

- 401 的「未认证」指什么？（没登录/凭证无效）
- 403 的「无权限」指什么？（登录了但权限不够）

**易错点**

401「未认证」、403「已认证但无权限」，这是高频考点；核心区别在「是否已经认证」。

## 425. 404 表示什么？

**面试回答**

404 Not Found，表示服务器找不到请求的资源（路径不存在或资源不存在）。

**理解**

404 是最常见的 4xx 之一，表示「你要访问的东西不存在」。可能是 URL 写错、接口路径不对，或查询的资源 id 不存在。前端最常见的就是「页面/接口 404」。

**场景**

项目里请求一个不存在的接口路径，或查询不存在的资源，可能返回 404。

**常见追问**

- 404 是什么类错误？（客户端错误，资源不存在）
- 和 400 区别？（400 请求格式错，404 资源找不到）

**易错点**

404 是「资源/路径不存在」；别和「服务器错误 500」搞混——404 是客户端找错地方，500 是服务器出错。

## 426. 500 表示什么？

**面试回答**

500 Internal Server Error，表示服务器内部出错（如代码异常、未捕获异常），无法正常处理请求。

**理解**

500 是 5xx 服务器错误类的代表，表示「责任在服务器」——请求可能没问题，但服务器处理时崩了。比如空指针、数据库异常没处理。项目里通常用全局异常处理器兜底，把异常转成友好响应，避免直接暴露 500。

**场景**

项目里若 Service 抛未捕获异常，默认会 500；用 @RestControllerAdvice 兜底后返回统一错误结构。

**常见追问**

- 5xx 代表什么？（服务器错误）
- 怎么避免暴露 500？（全局异常处理兜底）

**易错点**

500 是「服务器内部错误」，责任在服务端；和 4xx（客户端责任）区分，别把参数错误也当 500。

## 427. HTTP 和 HTTPS 有什么区别？

**面试回答**

HTTPS 是 HTTP 加上 TLS/SSL 加密层：HTTP 明文传输、默认 80 端口；HTTPS 数据加密传输、默认 443 端口，需要 CA 证书，能防窃听、防篡改、防伪装。

**理解**

HTTP 数据明文，传输途中可被窃听、篡改。HTTPS 在 HTTP 和 TCP 之间加了一层 TLS/SSL，对数据加密，并用证书验证服务器身份。所以 HTTPS 更安全，代价是握手更复杂、略慢、要证书。现代网站基本都上 HTTPS。

**场景**

项目里生产环境用 HTTPS，保证前端和后端传输的 token、密码等数据不被窃听。

**常见追问**

- HTTPS 默认端口？（443）
- HTTPS 多了一层什么？（TLS/SSL 加密层）

**易错点**

HTTPS = HTTP + TLS/SSL，核心是「加密 + 证书验证」；端口 443 vs 80，别记混。

## 428. HTTPS 为什么更安全？

**面试回答**

因为 HTTPS 通过 TLS/SSL 对数据进行加密传输，并用证书验证服务器身份，实现「防窃听、防篡改、防伪装」三重保护，而 HTTP 是明文传输、无身份验证。

**理解**

①加密：数据在传输中被加密，窃听者拿到也看不懂（防窃听）；②完整性校验：能发现数据是否被篡改（防篡改）；③证书：验证服务器身份，防止「中间人」冒充（防伪装）。这三者让 HTTPS 比 HTTP 安全得多。

**场景**

项目里登录、支付等敏感接口走 HTTPS，防止密码、token 在传输中被截获。

**常见追问**

- HTTPS 防哪三件事？（窃听、篡改、伪装）
- 证书的作用？（验证服务器身份）

**易错点**

HTTPS 安全的核心是「TLS/SSL 加密 + 证书验证」；它保证「传输安全」，不等于「应用绝对安全」，别过度解读。
