# HTTP

## 411. HTTP 是什么？

**面试回答**

HTTP 是一族无状态、应用层、请求—响应协议，为资源访问定义统一的方法、状态码、字段和消息语义。它不只传“超文本”，也可传 JSON、图片、流等表示。HTTP/1.1、HTTP/2、HTTP/3 共享核心语义，但线路编码和底层传输不同。

**原理与理解**

客户端针对目标资源发送带方法的请求，服务器返回状态码、字段和可选内容；代理、网关和缓存也能按统一语义参与。HTTP/1.1 通常映射在 TCP 上，HTTP/2 常使用一条 TCP 连接承载多路流，HTTP/3 则把 HTTP 语义映射到 QUIC，不能再把整个 HTTP 家族定义成“基于 TCP”。

**成立条件与边界**

- “无状态”指请求可独立理解，不等于服务器不能保存业务数据、会话或缓存；详见 [[06-Web/03-HTTP#421. HTTP 为什么是无状态协议？]]。
- HTTP 定义应用语义，连接、多路复用和帧格式由具体版本决定。
- `http` 与 `https` URI 的访问安全属性不同，但请求方法和状态码等 HTTP 语义基本一致。
- 请求—响应模型不代表一个连接只能顺序处理一对消息；HTTP/2、HTTP/3 支持多路复用。
- HTTP 不保证业务接口设计正确，幂等、认证、授权和数据一致性仍需应用实现。

**实际场景**

**通用工程：** 前端调用 JSON API、服务间请求和文件下载都可使用 HTTP；排障时要同时区分“HTTP 语义错误”“具体版本的消息/帧错误”和“底层连接错误”。

**常见追问**

- HTTP 属于哪一层？应用层。
- HTTP 一定运行在 TCP 上吗？HTTP/1.1、HTTP/2 通常使用 TCP，HTTP/3 使用基于 UDP 的 QUIC。
- HTTP 与 REST 是什么关系？HTTP 是协议；REST 是架构风格，可利用 HTTP 方法、URI 和状态码表达资源语义。

**易错点**

- 把所有 HTTP 版本都回答成“基于 TCP”。
- 把 HTTP 只理解为浏览器传网页。
- 认为无状态意味着服务端不能保存任何状态。

## 412. HTTP 请求由哪些部分组成？

**面试回答**

若面试按 HTTP/1.1 线路格式回答，请求由请求行、Header 区、结束 Header 的空行和可选消息体组成；请求行是 `method request-target HTTP-version`。更通用地说，请求包含方法、目标、字段和可选内容。HTTP/2、HTTP/3 用二进制帧和伪 Header 表达控制数据，没有字面上的请求行与空行。

**原理与理解**

请求行示例为 `POST /orders HTTP/1.1`，其中是 request-target，不保证总是完整 URL；Header 描述主机、内容格式、认证、条件请求等上下文；可选消息体承载请求内容。HTTP/2 使用 `:method`、`:scheme`、`:authority`、`:path` 等伪 Header，HTTP/3 采用相似语义但映射到 QUIC 流。

**成立条件与边界**

- “四部分”是 HTTP/1.1 文本消息的教学模型，不能直接推广为 HTTP/2、HTTP/3 的线路格式。
- 请求体是否存在由消息分帧决定，与方法语义是两个层次；不能只看 GET/POST 就判断线路上一定有无 Body。
- GET 请求内容没有通用语义，客户端不应随意发送，部分服务器或中间件可能拒绝。
- HTTP/1.1 请求体长度可由 `Content-Length` 或 `Transfer-Encoding` 等机制确定；错误分帧会引发请求走私风险。
- Trailer 是消息的另一类字段，简单“四段式”通常不会展开，但生产解析不能忽略版本规范。

**实际场景**

**通用工程：** 抓包排查 HTTP/1.1 登录请求时，可依次核对请求行、`Host`/`Content-Type` 等 Header 和 JSON Body；若链路已协商 HTTP/2，应查看伪 Header 与帧，而不是搜索文本请求行。

**常见追问**

- 请求行包含什么？方法、request-target 和 HTTP 版本，仅针对 HTTP/1.x 文本格式。
- request-target 一定是完整 URL 吗？不是，常见是路径和查询，也可因代理或 CONNECT 等使用其他形式。
- GET 能不能有 Body？线路格式没有按方法禁止，但内容没有通用 GET 语义且互操作性差，不应作为常规设计。

**易错点**

- 把 HTTP/1.1 的四段结构说成所有版本都一样。
- 将 request-target 一律称为完整 URL。
- 回答“GET 协议上绝对不能有 Body”。

## 413. HTTP 响应由哪些部分组成？

**面试回答**

按 HTTP/1.1 线路格式，响应由状态行、Header 区、结束 Header 的空行和可选消息体组成；状态行包含 HTTP 版本、状态码和可选 reason phrase。HTTP/2、HTTP/3 没有文本状态行，使用 `:status` 伪 Header 与二进制帧表达相同响应语义。

**原理与理解**

状态码是机器处理的核心，reason phrase 只是历史上的人类可读说明，客户端不能依赖它决定逻辑。Header 描述响应上下文和表示元数据，Body/内容承载资源表示或处理结果。是否允许响应内容还取决于请求方法和状态码，而不是“响应一定有 Body”。

**成立条件与边界**

- HEAD 响应不能传输表示数据；1xx、204、304 也没有消息内容，成功 CONNECT 则切换为隧道。
- `Content-Length` 并非所有响应都必须有；HTTP 版本、状态码和分帧方式会影响消息边界。
- HTTP/2 的响应包含 `:status`，没有 HTTP/1.1 的版本文本和 reason phrase。
- 业务响应 JSON 与 HTTP 状态码是两个层次，应保持一致而非互相替代。
- 中间代理可能增加或转换部分字段，端到端逻辑不应依赖未经规范保证的字段顺序。

**实际场景**

**通用工程：** 调试接口时先看 HTTP 状态码和 `Content-Type`，再解析 Body；若响应为 204 或 HEAD，就不应因为没有 JSON Body 而误判为网络截断。

**常见追问**

- 状态行有哪些元素？HTTP/1.x 中为版本、状态码和可选原因短语。
- reason phrase 能否作为程序判断条件？不能，它可为空且不承载规范语义。
- 200 一定有 Body 吗？通常有方法相关内容，但仍可能显式为零长度；需要无内容成功时更适合 204。

**易错点**

- 说 HTTP/2 响应也有 `HTTP/2 200 OK` 文本状态行。
- 认为所有响应都必须有 Body。
- 用 `OK` 文本而不是状态码做程序判断。

## 414. HTTP Header 是什么？

**面试回答**

HTTP Header 更准确称为 HTTP 字段，用“字段名 + 字段值”携带请求或响应的元数据与控制信息，例如内容类型、认证、缓存、条件请求和 Cookie。字段名大小写不敏感；字段值如何解析由各字段规范决定，不能统一当作普通字符串键值对。

**原理与理解**

`Content-Type` 描述表示的媒体类型，`Authorization` 携带认证凭证，`Cache-Control` 指示缓存行为，`Set-Cookie` 创建 Cookie。字段可能作用于消息、内容、请求上下文或响应控制；部分字段可合并为列表，`Set-Cookie` 等字段则有特殊组合规则。

**成立条件与边界**

- Header 不只是“解释 Body”；Host/`:authority`、认证、条件请求和路由字段即使无 Body 也有意义。
- 字段名大小写不敏感，但字段值是否大小写敏感取决于具体定义。
- HTTP/1.1 有连接特定字段；HTTP/2 禁止发送 `Connection`、`Keep-Alive`、`Transfer-Encoding` 等连接特定字段。
- Header 也受代理、服务器和客户端大小限制，不适合塞入大对象或无限增长的 JWT。
- Header 可能包含凭证和 Cookie，日志、链路追踪与错误页面必须脱敏。

**实际场景**

**项目核验项：** 简历确认项目使用 JWT，但没有确认通过标准 `Authorization: Bearer`、Cookie 还是自定义 Header 传输；面试前应从前后端请求代码与拦截器核验。

**常见追问**

- Header 名大小写敏感吗？不敏感。
- `Content-Type` 与 `Accept` 区别？前者描述当前消息内容的媒体类型，后者表达客户端可接受的响应媒体类型。
- Header 顺序重要吗？通常不能依赖字段名之间的顺序；同名字段值的组合语义要看具体字段定义。

**易错点**

- 把 Header 只定义为 Body 的格式说明。
- 认为所有同名 Header 都能随意用逗号合并。
- 未核验就声称项目 JWT 放在 `Authorization` 中。

## 415. HTTP Body 是什么？

**面试回答**

HTTP Body 是具体消息在线路上承载内容的部分，可包含 JSON、表单、文件、HTML 或二进制流。它是可选的；Header 描述内容类型、编码等元数据。严格区分时，HTTP/1.1 的 message body 还可能经过 Transfer-Encoding，而内容本身可再由 Content-Encoding 转换。

**原理与理解**

请求内容由目标资源按方法语义处理，响应内容则表达资源表示、操作结果或错误说明。`Content-Type` 决定媒体类型，`Content-Encoding` 表示 gzip 等内容编码；HTTP/1.1 的 `Transfer-Encoding: chunked` 解决线路分帧，不等同于压缩格式。

**成立条件与边界**

- Body 是否存在不能只由方法名称判断；消息分帧与方法语义必须分别考虑。
- GET/HEAD 请求内容没有通用语义；TRACE 请求禁止内容，其他方法按各自规范与接口约定处理。
- HEAD、1xx、204、304 响应不传输消息内容，不能强制所有接口返回统一 JSON Body。
- POST 数据不一定只在 Body，URL 仍可带查询参数；PUT/PATCH 的 Body 也要由媒体类型定义含义。
- Body 在 HTTPS 下受传输保护，但仍可能被应用日志、代理或终端代码读取。

**实际场景**

**通用工程：** 文件上传可使用 `multipart/form-data` Body，JSON API 可用 `application/json`；服务端同时校验 `Content-Type`、大小上限和内容本身，不能只信任 Header 声明。

**常见追问**

- Body 与 Content 有什么区别？日常可近似理解；在 HTTP/1.1 中 message body 是线路承载，Transfer-Encoding 解码后才得到内容。
- GET 参数只能放 URL 吗？查询通常放 URI；GET 内容没有通用语义，不应依赖 Body 传查询条件。
- Body 大小有协议固定上限吗？HTTP 没有统一小上限，实际由客户端、代理、容器和应用配置限制。

**易错点**

- 回答“GET 绝对没有 Body、POST 一定有 Body”。
- 把 `Transfer-Encoding` 和 `Content-Encoding` 混为一谈。
- 认为 POST Body 不会被记录所以天然适合明文敏感数据。

## 416. GET 和 POST 有什么区别？

**面试回答**

核心区别是标准语义：GET 请求获取目标资源当前选定表示，是 safe 且幂等；POST 请求目标资源按自身语义处理所附内容，通常会改变状态，标准没有把 POST 定义为 safe 或幂等。参数位置、安全性和缓存并不是简单的“URL 对 Body、危险对安全”二分。

**原理与理解**

GET 便于链接、书签、预取和缓存，因此不得把删除等副作用藏在 GET 中。POST 可用于创建子资源、提交表单、触发操作或追加数据，不只等于“新增”。GET 响应默认可缓存，除非缓存控制禁止；POST 响应在规范上存在可缓存条件，但多数缓存实现主要支持 GET/HEAD。

**成立条件与边界**

- HTTP 没规定统一的 URL 长度上限，浏览器、代理和服务器都有实现限制；POST Body 也有各层大小限制。
- GET 请求内容没有通用语义且可能被拒绝，因此查询条件通常放 URI，但不是因为线路语法绝对禁止 Body。
- POST 数据可同时出现在查询与 Body；位置由接口设计和媒体类型决定。
- POST 不比 GET 天然安全；两者都要 HTTPS，URI 更容易进入历史、日志和 Referer，但 Body 也可能被记录。
- 具体 POST 操作可以通过业务设计做到幂等，但这不会改变 HTTP 对 POST 方法的默认幂等属性。

**实际场景**

**通用工程：** 获取商品列表使用 GET 并让筛选条件进入查询参数；创建订单使用 POST，并用业务幂等键防止超时重试造成重复创建，而不是仅凭“POST 不幂等”放弃保护。

**常见追问**

- GET 是否可以修改数据？规范把 GET 定义为 safe；实现若用 GET 删除数据就是违反方法语义，会被预取和爬虫放大风险。
- POST 能缓存吗？规范定义了缓存可能性，但需显式条件且实现支持有限，不能简单回答永远不能。
- 哪个更安全？方法本身不提供机密性，安全依赖 TLS、认证授权、日志与输入处理。

**易错点**

- 背诵“GET 参数只能在 URL，POST 参数只能在 Body”。
- 说 POST 无长度限制或天然安全。
- 把 POST 只等同于创建资源。

## 417. PUT 和 POST 有什么区别？

**面试回答**

PUT 请求用所附表示创建或替换“客户端已确定 URI”的目标资源状态，方法语义是幂等；POST 则让目标资源按自身规则处理内容，创建资源时常由服务器决定新 URI，方法默认不幂等。二者都可能创建资源，差异不只是“更新对新增”。

**原理与理解**

`PUT /users/123` 表示客户端知道目标标识并希望该表示成为资源 123 的新状态；重复相同请求的预期效果相同。`POST /users` 可让集合资源创建新成员并返回 `201 Created` 与 `Location`。POST 还可以触发动作、处理表单或追加内容，因此语义由目标资源定义。

**成立条件与边界**

- PUT 的幂等指预期服务器效果相同，重复响应状态可能从 201 变为 200/204。
- “整体替换”是常见 PUT 表达；没提交字段如何处理取决于表示模型与接口契约，不能机械断言一律置空。
- POST 接口可通过幂等键设计成业务幂等，但客户端不能仅凭方法名安全地自动重试。
- PUT 也需要并发控制；可使用 ETag 与 `If-Match` 防止覆盖他人更新。
- 团队即使全部使用 POST，也应在接口文档中明确语义、幂等和重试规则。

**实际场景**

**通用工程：** 客户端指定头像资源 URI 并重复上传同一表示可用 PUT；向订单集合申请创建新订单可用 POST，并以请求幂等键和唯一约束处理网络重试。

**常见追问**

- PUT 能创建吗？能，若目标资源不存在且服务器允许，PUT 可在客户端指定的 URI 创建。
- POST 一定创建新资源吗？不一定，也可触发操作或处理内容。
- PUT 重复请求响应一定相同吗？不一定，幂等比较的是预期效果，不是每次状态码和 Body 完全相同。

**易错点**

- 简化为“POST 新增、PUT 更新”。
- 把幂等理解为响应字节完全相同。
- 认为 PUT 天然解决并发覆盖。

## 418. PUT 和 PATCH 有什么区别？

**面试回答**

PUT 通常提交目标资源的新完整表示并创建或替换其状态，定义为幂等；PATCH 提交“如何修改资源”的 Patch Document，应用一组部分变更。PATCH 没有被标准定义为天然幂等，但具体 Patch 格式与操作可以设计成幂等。

**原理与理解**

PATCH 的 Body 不是随意的“几个字段”，而应由媒体类型说明补丁语义，例如 JSON Patch 表达操作序列，JSON Merge Patch 表达合并规则。某些补丁依赖明确的基线版本；并发修改时应通过强 ETag 和 `If-Match` 等条件请求避免基于错误版本应用。

**成立条件与边界**

- 重复“把状态设置为 PAID”可能幂等，重复“余额加 10”通常不幂等；不能只看 PATCH 方法名。
- PUT 不必等同数据库全字段 UPDATE，它表达资源表示替换，字段映射由接口契约决定。
- PATCH 服务器应声明和校验支持的补丁媒体类型，可通过 `Accept-Patch` 告知客户端。
- 并发冲突可返回 412（条件失败）或按场景返回 409，不能静默覆盖。
- 部分更新也必须重新做认证、字段级授权、校验和审计。

**实际场景**

**通用工程：** 修改用户昵称可采用 Merge Patch；对有版本号的配置资源发送 PATCH 时同时带 `If-Match`，版本不符拒绝，让客户端重新获取后计算补丁。

**常见追问**

- PATCH 一定不幂等吗？标准不保证；具体补丁操作可以幂等，也可能不幂等。
- PUT 能否只更新部分字段？私有接口可以约定，但会偏离常见替换语义，应清楚文档化或改用 PATCH。
- JSON Patch 与 Merge Patch 一样吗？不一样，前者是操作序列，后者按对象合并规则更新。

**易错点**

- 回答“PUT 必须传数据库全部列，少一列就置 null”。
- 把 PATCH Body 当成没有媒体类型和操作语义的任意 JSON。
- 忽略条件请求导致并发丢失更新。

## 419. 什么是 HTTP 方法幂等？

**面试回答**

幂等指对同一目标发送多个相同请求，其“用户期望的服务器效果”与发送一次相同。它不要求每次响应、时间戳和日志完全一致，也不表示没有任何副作用。幂等性让客户端在未拿到响应时更有依据进行安全重试。

**原理与理解**

例如把资源状态 PUT 为固定值，执行一次或多次最终目标状态相同；DELETE 第一次可能返回 204，之后返回 404，但目标仍是“资源不存在”。服务器仍可为每次请求记录日志、版本历史或指标，这些实现副作用不改变方法的幂等语义。

**成立条件与边界**

- 必须比较多个“相同请求”的预期效果；不同参数、不同前置状态或不同目标不能直接比较。
- 幂等不等于 safe：DELETE 和 PUT 可以改变状态，但仍是幂等方法。
- 网络超时时客户端不知道首个请求是否已执行；幂等方法通常可重试，非幂等方法需幂等键、状态查询或确认未执行。
- HTTP 方法给出语义契约，服务端若让 GET 扣库存就是违反契约，不能简单说“幂等完全看实现”。
- 业务幂等仍要考虑并发、唯一约束、事务和幂等记录的原子性。

**实际场景**

**生产能力：** 创建订单时客户端生成唯一请求号；服务端用唯一约束或幂等表把“校验请求号、创建订单、记录结果”放入可靠的一致性边界，使超时重试返回同一业务结果而不重复下单。

**常见追问**

- 幂等要求响应相同吗？不要求，比较的是用户期望的服务器效果。
- 幂等等于没有副作用吗？不是，PUT/DELETE 会改变资源，日志也可每次新增。
- POST 能做到幂等吗？具体接口可以借助幂等键做到，但 POST 方法本身没有标准幂等保证。

**易错点**

- 把幂等定义为“返回结果完全相同”。
- 把幂等与 safe 混为一谈。
- 只在应用代码先查后写，忽略并发下仍会重复执行。

## 420. 哪些 HTTP 方法通常具有幂等性？

**面试回答**

RFC 9110 定义的 safe 方法——GET、HEAD、OPTIONS、TRACE——都是幂等的；此外 PUT 和 DELETE 也是幂等方法。POST 和 PATCH 没有被标准定义为幂等，CONNECT 也不是。方法语义是客户端和中间件的重试契约，具体接口可以在此基础上提供更强的业务幂等保证。

**原理与理解**

safe 表示客户端请求只读语义，不期望改变服务器状态；safe 一定幂等，但幂等不一定 safe。PUT 重复设置相同资源状态，DELETE 重复保持资源不存在，因此幂等。POST/PATCH 的效果由目标资源或补丁定义，可能追加或累加，客户端不能默认重试安全。

**成立条件与边界**

- DELETE 重复响应可不同，第一次 204、之后 404 并不破坏幂等性。
- GET 若被实现成删除或计费写操作，是接口违反 safe/幂等语义，不应据此否定标准定义。
- PATCH 可被设计为幂等，但需要根据补丁操作判断；“追加一项”和“设为固定值”不同。
- 代理不得自动重试非幂等请求；客户端只有确认实际语义幂等或原请求未执行时才应自动重试。
- 即使方法幂等，也要限制无限重试并处理超时、退避、熔断和版本冲突。

**实际场景**

**通用工程：** SDK 可对连接中断的 GET 或 PUT 做有上限的重试；对支付、下单等 POST，应先确认服务端幂等键协议，不能仅因“没收到响应”就盲目重发。

**常见追问**

- safe 方法有哪些？GET、HEAD、OPTIONS、TRACE。
- DELETE 第二次返回 404 为什么仍幂等？资源最终仍为不存在，预期效果未增加。
- PATCH 是否幂等？标准不保证，取决于具体 Patch Document 的操作语义。

**易错点**

- 漏掉 OPTIONS、TRACE，或把 CONNECT 列为幂等。
- 说 POST/PATCH 永远不可能做成业务幂等。
- 把标准方法语义完全归结为“看服务端心情”。

## 421. HTTP 为什么是无状态协议？

**面试回答**

HTTP 被称为无状态，是因为协议允许每个请求独立理解，不要求服务器记住该客户端之前的请求步骤才能解释当前消息。它不等于服务端完全不保存状态；业务会话可通过 Cookie/Session、Token 或数据库补充，连接和缓存也有各自的协议状态。

**原理与理解**

请求应携带处理它所需的目标、方法、字段和可选内容，使代理和服务器能在统一语义下处理。应用若要“记住用户”，可以让客户端带 Session ID 并查询服务端会话，或携带 JWT 等凭证。此时 HTTP 语义仍是无状态的，应用层则有明确状态与身份关系。

**成立条件与边界**

- 无状态不意味着每次都必须新建连接；HTTP/1.1 可复用连接，HTTP/2、HTTP/3 可多路复用。
- HPACK/QPACK 动态表、流控制和 TLS 会话等连接状态不等于应用登录会话。
- JWT 自包含认证可减少会话查询，但密钥、撤销和用户状态仍可能存在，不能据此说系统绝对无状态。
- Cookie 只是状态传递机制，Session 与 Token 的安全边界仍需独立设计。
- 请求独立不代表可以忽略业务流程状态，订单状态机等仍由应用维护。

**实际场景**

**真实项目边界：** 项目使用 JWT 在 HTTP 请求间携带身份，并由双拦截器解析后建立用户上下文；这补充了应用认证信息，但不改变 HTTP 协议自身的无状态语义。

**常见追问**

- 无状态有什么好处？降低请求之间的协议耦合，便于代理、扩展和故障恢复，但实际收益取决于应用状态设计。
- 为什么还能保持登录？通过 Cookie/Session、Token 等应用机制在每次请求中关联身份。
- 长连接是否让 HTTP 变成有状态协议？不会，连接状态和应用会话状态不是同一概念。

**易错点**

- 回答“服务器绝对不保存任何东西”。
- 把连接复用误认为 HTTP 变成有状态。
- 把 JWT 认证直接说成整个系统没有状态。

## 422. 200 表示什么？

**面试回答**

`200 OK` 表示该 HTTP 请求已成功。响应内容的语义取决于请求方法：GET 通常返回目标资源表示，POST 可返回操作状态或结果，PUT/DELETE 可返回操作结果。200 不是所有成功场景的唯一选择，创建、异步受理、成功无内容可分别考虑 201、202、204。

**原理与理解**

HTTP 状态码供客户端、代理、监控和重试机制表达通用结果，业务 Body 再提供领域代码和细节。新资源创建通常用 `201 Created` 并通过 `Location` 指示资源；`202 Accepted` 只说明已接收、尚未完成；无响应内容的成功可用 204。

**成立条件与边界**

- 200 只说明 HTTP 层请求成功处理，不能由此断言 Body 中每个业务条件都成功。
- 所有错误都返回 200 + 业务码会削弱通用客户端、代理、告警和可观测性语义，应由统一 API 规范权衡。
- 200 可以是零长度内容，但若明确无需返回内容，204 通常表达更直接。
- HEAD 的 200 不发送表示数据，不能据“没有 Body”判断失败。
- 健康检查返回 200 也只代表该检查定义的健康程度，不能自动证明全部依赖正常。

**实际场景**

**项目核验项：** 简历没有说明项目是规范使用 2xx/4xx/5xx，还是统一 200 + 业务码；应从全局异常处理、统一 Result 和前端拦截器核验后再描述。

**常见追问**

- 创建成功该用什么？通常使用 201，并可返回 `Location`。
- 202 是否表示后台任务成功完成？不表示，只代表请求已被接受处理。
- 200 与业务码如何配合？HTTP 状态表达通用协议结果，业务码细化领域原因，两者应一致。

**易错点**

- 把 200 解释成所有业务步骤都必然成功。
- 创建、异步受理和无内容成功一律回答 200。
- 认为 HTTP 状态码与统一响应体只能二选一。

## 423. 400 表示什么？

**面试回答**

`400 Bad Request` 表示服务器因其认为是客户端错误而不能或不愿处理请求，例如语法错误、无效消息分帧或欺骗性路由。业务参数校验失败常可使用 400，但若内容类型不支持、语法正确而语义无法处理或存在资源冲突，可分别考虑 415、422、409。

**原理与理解**

400 是较宽泛的客户端错误，不应吞掉所有 4xx 语义。JSON 无法解析可返回 400；媒体类型不受支持是 415；JSON 语法正确但字段组合无法执行可用 422；当前资源版本冲突可用 409 或条件请求失败的 412。精确状态码有利于客户端采取正确补救动作。

**成立条件与边界**

- 缺少有效认证凭证通常是 401，服务器理解请求但拒绝履行通常是 403，不应都塞进 400。
- URI 太长、内容太大分别有 414、413，实际还要结合网关和容器限制。
- 400 不意味着必须关闭连接；但 HTTP/1.1 消息分帧错误可能使连接无法安全复用。
- 返回 Body 可给出安全、可定位的字段错误，但不能暴露堆栈、SQL 或内部路径。
- 参数校验状态码需要全项目一致，否则客户端会形成大量特判。

**实际场景**

**通用工程：** 请求 JSON 少了逗号返回 400；JSON 可解析但状态枚举不允许可按 API 规范返回 400 或 422；无论选择哪种，都保持错误结构、字段定位和文档一致。

**常见追问**

- 400 和 422 区别？400 更宽泛且可表示语法/分帧问题；422 表示内容类型和语法可理解，但所含指令在语义上无法处理。
- 400 与 415 区别？415 针对当前资源/方法不支持请求内容格式。
- 4xx 都是客户端代码 Bug 吗？不一定，也可能是凭证过期、资源状态冲突或用户输入无效。

**易错点**

- 把所有客户端失败都返回 400。
- 参数错误返回 500，误导监控和重试。
- 在 400 Body 中直接暴露内部异常详情。

## 424. 401 和 403 有什么区别？

**面试回答**

`401 Unauthorized` 更准确是“缺少目标资源所需的有效认证凭证”，响应必须携带适用的 `WWW-Authenticate` challenge；`403 Forbidden` 表示服务器理解请求但拒绝履行。面试可用“401 未通过认证、403 通常是权限不足”快速区分，但 403 并不严格要求请求者已认证。

**原理与理解**

未带凭证、凭证失效或凭证不被接受通常对应 401，客户端可用新凭证重试。403 可能因为已认证主体权限不足，也可能与凭证无关；相同凭证不应被自动重复提交。为隐藏敏感资源是否存在，服务器还可对禁止访问的目标返回 404。

**成立条件与边界**

- 401 的英文 reason phrase 容易误导，规范核心是 lack of valid authentication credentials。
- 生成 401 时应包含 `WWW-Authenticate`，自定义 JSON 错误体不能替代该 Header 语义。
- 403 不能绝对翻译为“已登录但没权限”，虽然这是业务 API 中最常见用法。
- 资源归属不足、账号受策略限制等可返回 403；是否用 404 隐藏存在性要统一设计。
- 认证和授权失败响应不能暴露过多信息，避免帮助枚举账号或资源。

**实际场景**

**项目核验项：** 项目有管理端与用户端认证链路，但简历未确认无 Token、Token 过期、角色不足分别返回 401、403 还是业务码；需核验拦截器和全局异常映射。

**常见追问**

- 401 为什么要 `WWW-Authenticate`？它向客户端给出适用于目标资源的认证 challenge。
- 403 能否发生在未认证请求？规范允许拒绝原因与凭证无关，因此不能把“已认证”作为硬前提。
- 为什么有时越权返回 404？避免向无权主体披露资源存在性。

**易错点**

- 只背“401 未登录、403 已登录”，不说明这是常用简化。
- 返回 401 却完全没有认证 challenge 设计。
- 把对象级越权误返回 200 或仅依赖前端隐藏按钮。

## 425. 404 表示什么？

**面试回答**

`404 Not Found` 表示源服务器没有找到目标资源的当前表示，或不愿披露该表示存在。它既可能是路由不存在，也可能是具体资源不存在；404 本身不说明缺失是临时还是永久，明确永久消失时更适合 410 Gone。

**原理与理解**

HTTP 关注目标资源对当前请求是否有可提供的表示。服务端可用 404 隐藏一个实际存在但当前主体无权获知的资源。404 响应在没有其他限制时具有启发式可缓存性，因此资源刚创建或权限变化后出现“仍然 404”时还要检查缓存控制。

**成立条件与边界**

- 路由不存在与数据库 ID 不存在都可返回 404，但日志和业务错误码可进一步区分。
- 无权访问时选 403 还是 404 取决于是否允许披露资源存在性，应保持一致。
- 404 不是 DNS 解析失败、连接拒绝或超时；那些通常还没得到 HTTP 响应。
- 单页应用前端路由 404 与后端 API 404 的处理层次不同。
- 资源永久删除且服务器明确知道时可返回 410，而不是永远只用 404。

**实际场景**

**通用工程：** 查询 `/orders/{id}` 时，如果订单不存在或当前用户无权知道它存在，可按安全规范返回 404；服务端日志仍记录真实原因和关联 ID，但响应不泄露他人资源信息。

**常见追问**

- 404 一定表示 URL 写错吗？不一定，也可能是目标资源没有当前表示或服务端刻意隐藏。
- 404 和 410 区别？404 不说明临时/永久，410 表示服务器知道资源很可能永久消失。
- 404 能缓存吗？在未被方法或显式缓存控制禁止时具有启发式可缓存性。

**易错点**

- 把网络层连接失败说成 HTTP 404。
- 认为 404 只能由错误路由产生。
- 忽略缓存造成的负面结果残留。

## 426. 500 表示什么？

**面试回答**

`500 Internal Server Error` 表示服务器遇到未预期条件，导致无法完成请求。它是通用兜底 5xx，但不应替代更具体的 502、503、504。正确做法不是把 500 隐藏成 200，而是返回准确状态、对外脱敏、对内记录可关联诊断信息。

**原理与理解**

未处理异常、违反内部不变量或无法归类的服务端故障可落到 500。网关收到上游无效响应是 502，服务临时过载/维护是 503，上游未及时响应是 504。全局异常处理器应把已知业务/客户端异常映射为合适 4xx，把未知故障保留为脱敏 500。

**成立条件与边界**

- 500 不等于“所有数据库异常”；唯一约束冲突可能映射 409，连接故障则可能是 500 或 503，需看是否临时和可恢复。
- 不应把堆栈、SQL、密钥和内部路径返回给客户端。
- 对外消息可统一，对内必须保留异常栈、Trace ID、请求上下文和告警。
- 客户端不应无条件重试所有 500，尤其非幂等请求；需要按方法、错误和幂等协议判断。
- 全局异常处理不是为了“避免 500”，而是为了准确分类、脱敏和可观测。

**实际场景**

**生产能力：** 未知空指针由异常处理器返回 500 + Trace ID，日志记录完整堆栈并触发告警；如果识别为上游超时则由网关/服务返回 504 或明确错误，客户端仅在安全条件下退避重试。

**常见追问**

- 500、502、503、504 如何区分？分别是未知内部异常、网关收到上游无效响应、服务暂时不可用、网关等待上游超时。
- 怎么“避免暴露 500”？不能篡改状态，应隐藏内部细节并提供可追踪错误标识。
- 参数校验失败是否返回 500？通常不是，应映射合适 4xx。

**易错点**

- 为了统一响应把所有异常都返回 HTTP 200。
- 把所有 5xx 都叫服务器代码 Bug。
- 返回脱敏消息后却不记录完整内部诊断信息。

## 427. HTTP 和 HTTPS 有什么区别？

**面试回答**

HTTPS 是通过受保护连接访问 HTTP 资源：HTTP 语义基本不变，但 TLS/QUIC 提供传输机密性、完整性和服务身份验证。`http` 默认端口通常是 80，`https` 通常是 443，但都可显式使用其他端口；“HTTPS = HTTP 与 TCP 之间加 SSL 层”只适合过度简化的 HTTP/1.x/2 图示，不适用于 HTTP/3。

**原理与理解**

对 HTTP/1.1、HTTP/2，HTTPS 常先建立 TCP，再完成 TLS 握手和 HTTP 协商；HTTP/3 使用 QUIC，TLS 1.3 握手能力集成在 QUIC 中。客户端验证证书信任链和服务身份，协商密钥后保护应用数据。SSL 已被淘汰，现代准确称呼是 TLS。

**成立条件与边界**

- 默认端口是约定，不是协议强制；`https://example.com:8443` 仍是 HTTPS。
- HTTPS 保护传输中的内容，不修复 XSS、SQL 注入、越权、弱密码或终端被攻陷。
- 只有客户端正确验证证书、主机名和信任锚，才能抵抗常见中间人冒充。
- TLS 会增加握手和密码运算，但连接复用、会话恢复和现代硬件会降低成本，不能简单说 HTTPS 一定明显更慢。
- HTTPS 仍可能暴露 IP、端口、流量大小和时序等元数据，并不等于完全匿名。

**实际场景**

**项目核验项：** 简历未确认生产域名、TLS 终止位置、证书来源和 HTTP 版本；只能说明登录 Token 等敏感请求在生产中应使用 HTTPS，不能声称项目已部署某种证书或网关方案。

**常见追问**

- HTTPS 默认端口是什么？通常 443；HTTP 通常 80，但均可显式改端口。
- HTTPS 使用 SSL 还是 TLS？现代实现使用 TLS，“SSL”多是历史或口语称呼。
- HTTP/3 还基于 TCP 吗？不，HTTP/3 映射到 QUIC，QUIC 通常封装在 UDP 上并集成 TLS 1.3。

**易错点**

- 把默认端口说成不可改变的硬规则。
- 用“HTTP + TCP 中间加 SSL”解释所有版本。
- 认为上了 HTTPS 就不存在应用安全漏洞。

## 428. HTTPS 为什么更安全？

**面试回答**

HTTPS 的安全性来自 TLS：加密提供传输机密性，认证加密/完整性校验让篡改可被发现，证书验证帮助客户端确认所连接服务的身份，从而降低窃听、篡改和冒充风险。默认 Web 场景主要认证服务器，只有配置双向 TLS 时才同时以证书认证客户端。

**原理与理解**

握手阶段协商协议版本与密码参数、验证服务证书并建立共享密钥；随后记录层或 QUIC 使用协商密钥保护应用数据。TLS 1.3 的目标是防窃听、篡改和消息伪造，但安全结论依赖算法配置、私钥保护、证书验证、随机数和实现均正确。

**成立条件与边界**

- 用户忽略证书告警、客户端关闭主机名校验或信任恶意根证书时，服务身份保证会失效。
- HTTPS 只保护两个 TLS 端点之间的链路；TLS 在反向代理终止后，内部链路是否继续加密要另行设计。
- 浏览器混合内容、错误跳转和首次 HTTP 访问仍会形成降级面，可结合全站 HTTPS、Secure Cookie 与 HSTS。
- 证书过期、私钥泄露和旧协议/弱算法会破坏安全，需要自动续期、轮换、监控与安全配置。
- HTTPS 不隐藏合法端点看到的数据，也不能阻止端点把密码或 Token 写入日志。

**实际场景**

**生产能力：** 登录和支付入口强制 HTTPS，HTTP 重定向到 HTTPS，Cookie 设置 `Secure`，证书到期提前告警；明确 TLS 在 CDN、网关还是应用终止，并评估终止点到后端的链路保护。

**常见追问**

- HTTPS 防哪三类风险？降低传输窃听、篡改和服务冒充风险，前提是 TLS 与证书验证正确。
- 证书的作用是什么？把服务身份与公钥材料绑定到受信任验证链，客户端还要核对目标主机。
- HTTPS 是否认证客户端？普通网站通常不使用客户端证书；mTLS 才提供双向证书认证。

**易错点**

- 把 HTTPS 说成对服务器数据库中的数据也自动加密。
- 认为只要有证书就无需验证主机名和信任链。
- 忽略 TLS 终止后的内部明文链路与日志泄露。
