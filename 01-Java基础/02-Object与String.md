# Object 与 String

## 18. `==` 和 `equals()` 有什么区别？

**面试回答**

`==` 是语言运算符：比较基本类型时比较经过数值提升或相应转换后的值，比较引用类型时判断两个引用是否指向同一对象。`equals()` 是实例方法，其语义由类的契约决定；Object 默认仍是身份相等，String 等类重写后比较内容。

**原理与理解**

引用的身份相同一定能通过合理实现的 equals，但内容相等不要求是同一对象。调用 `a.equals(b)` 还存在 a 为 null 的风险，空值安全比较可用 `Objects.equals(a, b)`。

**成立条件与边界**

“`equals` 都比较内容”不成立，取决于具体类是否重写及如何定义。数组继承 Object 的 `equals`，默认仍比较身份；内容比较应使用 `Arrays.equals/deepEquals`。

**实际场景（通用工程）**

比较订单号、状态字符串使用 `equals`，比较枚举可用 `==`。字符串字面量与显式构造对象的区别见 [[02-Object与String#29. `"abc"` 和 `new String("abc")` 有什么区别？]]。

**常见追问**

- String 能否用 `==` 比值？（不能依赖，`==` 比身份）
- 空值如何安全比较？（`Objects.equals` 或让确定非空的对象调用 equals）

**易错点**

不要把引用值解释成可见的物理地址，也不要把 `equals` 的语义脱离具体类型。

## 19. Object 默认的 `equals()` 比较什么？

**面试回答**

Object 的默认 `equals` 当且仅当两个引用指向同一个对象时返回 true，效果等同于引用身份比较。子类可在满足 equals 契约的前提下重写为值相等。

**原理与理解**

默认实现适合以对象身份区分实例的类型。值对象通常根据组成业务值的字段定义相等性，并同步设计 `hashCode`。

**成立条件与边界**

代理类、继承层次和可变字段会让相等性设计变复杂；如果无法保证对称、传递和一致性，组合或限制继承往往更稳妥。

**实际场景（通用工程）**

两个分别查询得到、但业务字段相同的 DTO，若未重写 equals，放入 Set 仍可能被视为两个元素；是否应值相等取决于类型语义。

**常见追问**

- Object 默认 equals 与 `==` 有何区别？（对引用身份判断的结果相同）
- 所有实体都要重写 equals 吗？（不一定，要先明确身份语义和值语义）

**易错点**

不要默认 Lombok 生成的 equals 一定符合领域语义；应核对包含字段、继承策略以及代理影响。

## 20. 为什么重写 `equals()` 通常要重写 `hashCode()`？

**面试回答**

因为 Object 契约要求：两个对象只要 equals 相等，在同一次程序执行中就必须有相同 hashCode。哈希集合先按哈希值定位桶，再用 equals 区分键；只重写 equals 会破坏查找、去重等行为。

**原理与理解**

hashCode 用于缩小候选范围，equals 决定逻辑相等。两者应基于同一组相等性字段；相等字段变化时，对象在哈希容器中的位置可能失效。

**成立条件与边界**

反向不成立：hashCode 相同的对象可以不 equals。契约只要求一致性，不要求哈希值唯一，也不规定具体算法。

**实际场景（通用工程）**

值对象作为 HashMap key 或放入 HashSet 前，统一生成和审查 equals/hashCode，并用碰撞样例验证两阶段比较逻辑。

**常见追问**

- equals 不同，hashCode 能相同吗？（能，允许碰撞）
- hashCode 能否包含可变字段？（风险很高，入表后变化会导致查找异常）

**易错点**

“通常要一起重写”在对象进入哈希容器时是正确性要求，不只是性能建议。

## 21. `equals()` 相同，`hashCode()` 一定相同吗？

**面试回答**

按照 Object 契约一定要相同。如果 `a.equals(b)` 为 true，而两者 hashCode 不同，说明类的实现违反契约，HashMap、HashSet 等容器可能无法正确查找或去重。

**原理与理解**

哈希容器不会遍历所有元素做 equals；它先用 hash 定位候选位置。因此逻辑相等对象必须进入一致的哈希定位流程。

**成立条件与边界**

这里说的是“正确实现必须保证”，不是 JVM 自动替开发者修复。对象参与 equals 的字段改变后，相应 hashCode 通常也会改变，所以可变 key 仍可能失效。

**实际场景（生产能力）**

为业务键编写单元测试时同时验证自反、对称、传递，以及 equals 相等必有相同 hashCode；再覆盖 HashSet 去重行为。

**常见追问**

- 反过来成立吗？（不成立，参见 [[02-Object与String#22. `hashCode()` 相同，`equals()` 一定相同吗？]]）
- hashCode 每次都必须固定吗？（对象用于 equals 的信息未变且同一程序执行期间应保持一致）

**易错点**

不要说“Java 会自动保证”；自定义类若实现错误，编译器和 JVM 通常不会替你兜底。

## 22. `hashCode()` 相同，`equals()` 一定相同吗？

**面试回答**

不一定。hashCode 是有限范围的 int，不同对象完全可能发生碰撞；哈希相同只表示进入同一候选集合，最终仍由 equals 判断逻辑相等。

**原理与理解**

对象取值空间通常远大于 32 位哈希空间，根据抽屉原理碰撞不可避免。好的散列函数追求均匀分布和稳定契约，而不是保证唯一。

**成立条件与边界**

hashCode 不能用作数据库唯一键、幂等键、签名或安全摘要。即使当前样本未碰撞，也不构成唯一性保证。

**实际场景（通用工程）**

HashMap 桶内可能存在多个 hash 相同但 key 不相等的节点，容器会继续比较 key；equals/hashCode 关系见 [[02-Object与String#20. 为什么重写 `equals()` 通常要重写 `hashCode()`？]]。

**常见追问**

- 碰撞是否代表实现错误？（不代表，碰撞允许；分布极差才会影响性能）
- hashCode 能否当唯一 ID？（不能）

**易错点**

不要把“相同对象同 hash”错误反推成“同 hash 就是同对象”。

## 23. `hashCode()` 有什么作用？

**面试回答**

hashCode 为对象提供一个 int 散列值，主要帮助 HashMap、HashSet 等结构快速缩小 equals 比较范围。它是散列定位的输入，不是对象地址、全局唯一标识或安全哈希。

**原理与理解**

容器通常会对 hashCode 再做扰动和索引计算，然后在候选桶内比较 hash 与 equals。合理分布能降低候选数量，但正确性最终依赖 equals 契约。

**成立条件与边界**

Object 不要求 hashCode 在不同 JVM 进程间稳定；自定义算法升级后也可能改变。不要持久化它后用于跨版本分片或协议兼容。

**实际场景（通用工程）**

设计缓存键与集合元素时核对 [[05-HashMap]] 的定位流程；分布式分片应使用版本明确、跨进程稳定的专用哈希算法。

**常见追问**

- 默认 hashCode 是内存地址吗？（规范不保证）
- hashCode 越大越好吗？（不是，关键是契约和分布）

**易错点**

hashCode 不是唯一性证明；日志中看到相同哈希值也不能断言两个对象相等。

## 24. `toString()` 有什么作用？

**面试回答**

toString 返回对象的字符串表示，常用于日志、调试和展示。Object 默认格式是运行时类名、`@` 和该对象 hashCode 的无符号十六进制表示；业务类通常重写为更有意义的摘要。

**原理与理解**

字符串拼接、`String.valueOf` 和很多日志输出路径会间接使用 toString。好的实现应便于定位问题，同时保持稳定、简洁并避免昂贵计算。

**成立条件与边界**

默认尾部不是“内存地址”，也不一定是身份哈希，因为它调用可被重写的 hashCode。自动生成 toString 还可能泄露密码、令牌、手机号或递归打印双向关联。

**实际场景（生产能力）**

订单日志只输出订单号、状态和必要追踪字段，对敏感数据脱敏；大集合、懒加载关联和密钥字段不直接展开。

**常见追问**

- 默认格式是什么？（类名 + `@` + hashCode 的十六进制）
- println 对 null 会怎样？（通常经 `String.valueOf` 输出 `null`，不是调用 null 的实例方法）

**易错点**

不要把 toString 当序列化协议；其格式通常不承诺可逆或跨版本稳定。

## 25. String 为什么是不可变的？

**面试回答**

String 的公开契约规定其值创建后不能改变；看似修改的操作返回新 String。实现上 String 是 final 类并封装内部存储，不向调用方暴露可修改入口，但“某个 final 数组”本身不足以证明不可变。

**原理与理解**

不可变需要同时控制继承、内部状态别名和所有修改路径。JDK 8 常见实现使用 char 数组，JDK 9 起 OpenJDK 使用紧凑字符串的 byte 数组；这些是实现选择，不是 String 不可变的定义。

**成立条件与边界**

final 引用只限制重新赋值，不能阻止数组元素变化。反射、Unsafe 或本地代码破坏封装不属于普通 API 契约；也不应据此否定日常语义下的不可变性。

**实际场景（通用工程）**

配置名、协议字段和映射键可以安全共享 String 值；不可变对象还需在构造时避免泄露可变引用。

**常见追问**

- substring 会修改原字符串吗？（不会，返回结果字符串）
- String 底层永远是 char[] 吗？（不是，属于 JDK 版本实现细节）

**易错点**

“private final 数组 + 没有 setter”只是部分实现理由；还要防止数组引用泄露和内部可变状态被修改。

## 26. String 不可变有什么好处？

**面试回答**

不可变让 String 可以安全共享和驻留，内容与 hashCode 保持稳定，适合作为哈希键；只读状态也降低并发共享的同步需求，并避免字符串参数在校验后被普通 API 意外修改。

**原理与理解**

当对象状态不会变化，多个持有者无需协调“谁改了内容”，缓存的哈希值也不会因内容改变而失效。字符串字面量和 intern 结果因此可复用同一规范化实例。

**成立条件与边界**

String 自身不可变不等于“使用 String 的业务逻辑线程安全”；复合操作、引用发布和周边可变对象仍需同步。频繁生成新字符串也会带来分配成本。

**实际场景（通用工程）**

Map key、Redis key 前缀和状态码可以稳定复用；循环构造大文本时改用构建器，避免反复复制。

**常见追问**

- 不可变为什么适合做 key？（相等性和哈希在生命周期内稳定）
- 不可变对象是否绝对无并发问题？（对象状态只读，但复合业务操作仍可能竞争）

**易错点**

不要把“String 不可变”扩大成“所有字符串相关代码都线程安全”。

## 27. String、StringBuilder、StringBuffer 有什么区别？

**面试回答**

String 不可变；StringBuilder 和 StringBuffer 是可变字符序列。StringBuffer 的公开方法带同步语义，适合共享实例的单次操作；StringBuilder 不提供同步，通常用于线程封闭的构建过程，开销更低。

**原理与理解**

Builder/Buffer 通过可增长的内部存储追加内容，最终 `toString()` 生成 String。StringBuffer 的同步保证单个方法调用互斥，并不自动保证多步“检查再追加”整体原子。

**成立条件与边界**

“StringBuffer 线程安全”应限定到其方法契约；复合序列仍可能需要外部锁。StringBuilder 可在多线程程序中使用，只要实例不被并发修改。

**实际场景（通用工程）**

请求内拼接 SQL 片段或响应摘要用局部 StringBuilder；若确需跨线程共享可变缓冲区，先确认是否应改为线程封闭，再决定同步方案。

**常见追问**

- 单线程为何优先 StringBuilder？（无需同步）
- StringBuffer 能否保证多次调用整体原子？（不能自动保证）

**易错点**

不要只背性能排序；对象是否共享、拼接规模和编译器优化才决定选择。

## 28. 为什么循环拼接字符串推荐 StringBuilder？

**面试回答**

循环中的 `s = s + part` 通常需要反复构造新结果并复制已有内容，可能形成接近平方级的字符复制和大量临时分配；StringBuilder 可复用可变缓冲区连续追加，最后生成一次结果。

**原理与理解**

编译器能折叠编译期常量；Java 9 起 javac 还可通过 `invokedynamic` 选择单次拼接策略。但跨循环迭代不断把旧 String 作为下一次输入，通常无法等价为自动复用同一个 Builder。

**成立条件与边界**

少量、直观的单次 `+` 不必手工改写。Builder 仍会创建自身、可能多次扩容并在 `toString()` 时创建结果 String，不能说“绝对只有一个对象”。

**实际场景（生产能力）**

批量生成文本时可按预估长度初始化 StringBuilder，并用基准测试或分配分析确认热点；日志参数优先使用占位符，避免未启用日志级别时仍拼接。

**常见追问**

- `"a" + "b"` 会怎样？（通常编译期折叠为常量）
- Java 9 之后 `+` 是否仍用 StringBuilder？（不能一概而论，javac 使用 indy 拼接机制）

**易错点**

“`+` 一定慢”与“编译器一定能优化整个循环”都是绝对化误区。

## 29. `"abc"` 和 `new String("abc")` 有什么区别？

**面试回答**

`"abc"` 是字符串字面量，指向该字面量对应的驻留实例；每次实际求值 `new String("abc")` 都显式创建一个新的 String 对象，其内容相同但身份与字面量对象不同。

**原理与理解**

因此内容比较 `"abc".equals(new String("abc"))` 为 true，而身份比较通常为 false。对新对象调用 `intern()` 会返回与其内容相等的规范化驻留字符串引用，不保证返回调用者本身。

**成立条件与边界**

语言保证字面量和常量表达式字符串被 intern，但不要求用“常量池在堆的某区域”解释语义。JIT 可以消除不可观察的分配，但不改变程序可观察到的身份行为。

**实际场景（通用工程）**

业务字符串始终按内容比较；关于驻留机制可继续看 [[02-Object与String#31. 什么是字符串常量池？]]。

**常见追问**

- 两者 equals 和 `==` 的结果？（equals 为 true；引用身份不同）
- `intern()` 返回什么？（内容相同的规范化池中引用）

**易错点**

不要用对象所处“堆/池”的口号代替身份与内容语义；现代实现中这些物理位置说法容易过时。

## 30. `new String("abc")` 会创建几个对象？

**面试回答**

不能脱离执行阶段固定回答“一个或两个”。每次可观察地执行 `new String(...)` 都产生一个显式新 String；`"abc"` 对应的驻留实例可能早已在类加载或初始化相关过程中存在，也可能此前尚未物化，因此不应把它机械计入当前表达式的固定创建数。

**原理与理解**

源码包含一个字面量常量和一次构造调用，但“源代码涉及几个概念对象”与“运行这一行新分配几个对象”不是同一个问题。优化编译还可能在不改变可观察语义时消除实际分配。

**成立条件与边界**

若面试官明确限定“类尚未加载、池中不存在、忽略 JIT，并统计为准备字面量而创建的对象”，才可在该模型下回答两个；必须先说明假设。表达式区别见 [[02-Object与String#29. `"abc"` 和 `new String("abc")` 有什么区别？]]。

**实际场景（通用工程）**

排查内存分配应使用 JFR、分配剖析或基准工具，而不是用这道题的简化计数估算生产对象数。

**常见追问**

- 为什么经典答案是两个？（把字面量首次物化和显式 new 同时计入，并忽略运行阶段差异）
- JIT 能否消除 new？（在对象身份等行为不可观察时可能）

**易错点**

“固定两个”与“固定一个”都缺少前提；准确回答应先定义统计范围和运行状态。

## 31. 什么是字符串常量池？

**面试回答**

通常所说字符串常量池，是运行时维护的规范化字符串集合。相同内容的字符串字面量和常量表达式引用同一驻留实例；`String.intern()` 可取得内容相同的规范化引用。

**原理与理解**

JLS 规定字面量字符串以及常量表达式产生的字符串会被 intern，String API 定义 intern 的返回规则。这允许编译期常量在身份上复用，但业务代码仍应使用 equals 比内容。

**成立条件与边界**

池的物理位置、表结构、扩容和回收策略属于 JVM 实现与版本细节，不是 Java 语言保证。“JDK 7 前永久代、之后堆”只能作为特定 HotSpot 历史说明，不能当通用定义。

**实际场景（生产能力）**

对海量动态字符串盲目调用 intern 可能增加全局表压力，应先测量重复率和生命周期；String 可复用的基础见 [[02-Object与String#25. String 为什么是不可变的？]]。

**常见追问**

- 哪些字符串会自动驻留？（字面量和常量表达式结果）
- intern 是否总返回原对象？（不是，已有等内容驻留对象时返回已有对象）

**易错点**

不要混淆 class 文件常量池、运行时常量池和字符串驻留表，它们是相关但不同的概念。

## 32. String 的 `equals()` 是怎么比较的？

**面试回答**

String 的 equals 按字符序列内容进行大小写敏感比较；当参数也是 String 且表示相同字符序列时返回 true。它比较的是值，不是对象身份。

**原理与理解**

实现通常会先做快速判断，再比较长度、编码标记和内容，但调用方应依赖 API 语义而非某个 JDK 版本的 char 数组或 byte 数组循环。

**成立条件与边界**

equals 不做大小写折叠、Unicode 规范化或本地化排序。`equalsIgnoreCase` 也不是所有语言环境下文本匹配的完整解决方案。

**实际场景（生产能力）**

用户输入、文件名或业务编码比较前，先明确是否需要 trim、大小写规则和 Unicode 规范化；协议固定值可使用精确 equals。

**常见追问**

- 如何避免变量为 null 时 NPE？（`Objects.equals` 或常量在前）
- String equals 是否比较内部数组引用？（API 保证比较字符序列内容，不应依赖内部表示）

**易错点**

不要把“逐个 char 比较”写成跨版本实现保证；紧凑字符串已说明内部表示会变化。

## 33. String 为什么适合作为 HashMap 的 Key？

**面试回答**

String 不可变，参与相等性的内容和 hashCode 在生命周期内稳定；同时它正确实现 equals/hashCode，因此放入 HashMap 后不会因正常 API 修改而丢失定位。

**原理与理解**

Map 先按哈希定位，再按 equals 区分键。不可变还允许 String 缓存哈希计算结果，重复查询时减少计算，但具体缓存字段属于实现细节。

**成立条件与边界**

“适合”不等于所有字符串都自动代表同一业务键。大小写、空白、Unicode 规范化和前缀拼接规则不同，仍会形成不同 key；恶意输入还需考虑哈希碰撞防护。

**实际场景（通用工程）**

生成缓存键时统一命名空间、分隔符和编码规范；契约基础见 [[02-Object与String#20. 为什么重写 `equals()` 通常要重写 `hashCode()`？]]。

**常见追问**

- 可变对象做 key 有何风险？（相等字段变化后可能无法从原桶找到）
- String hashCode 是否唯一？（不唯一，允许碰撞）

**易错点**

不要只答“不可变”，还应说明稳定的 equals/hashCode；也不要把字符串规范化问题交给 HashMap 自动解决。

## 34. StringBuilder 为什么比 String 频繁拼接效率高？

**面试回答**

StringBuilder 把多次 append 聚合到同一可变序列中，减少每一步创建完整 String 和复制全部前缀的成本；最终通过 `toString()` 生成不可变结果，通常更适合频繁或循环拼接。

**原理与理解**

内部容量不足时需要扩容并复制，预估容量可减少次数。具体存储类型和增长公式是 JDK 实现细节，API 不保证“每次翻倍”。

**成立条件与边界**

Builder 不是零分配：会有 Builder、内部存储扩容以及结果 String；少量单次拼接可能已被编译器优化，手工改写未必更快。并发共享同一 Builder 也不安全。

**实际场景（生产能力）**

构建较大 SQL、CSV 行或摘要时，使用局部 Builder、合理初始容量并限制最终长度，避免内存放大和无界输出。

**常见追问**

- toString 是否返回 Builder 自身？（不是，返回 String）
- 初始容量越大越好吗？（不是，过大会浪费内存，应按数据规模估计）

**易错点**

“只创建一个对象”“容量固定翻倍”都不是 API 保证；性能结论要带场景和实现边界。
