# HashMap

## 61. HashMap 的底层数据结构是什么？

**面试回答**

HashMap 的公开契约是基于哈希表的 Map 实现。OpenJDK 8 及之后常用“数组桶 + 单链表 + 红黑树树桶”组织节点：哈希定位桶，冲突节点先形成链表，满足实现阈值后可树化。

**原理与理解**

每个映射节点保存 hash、key、value 和 next；树桶节点增加树结构链接。正常分布下 get/put 具有预期常数时间，树桶用于缓解极端冲突。

**成立条件与边界**

数组、链表、红黑树及字段布局是 OpenJDK 实现，不是 Map 接口或所有 JVM 的永久保证。HashMap API 只承诺在哈希分布合理等前提下的性能特征，并且不保证迭代顺序。

**实际场景（通用工程）**

按订单 ID 建立进程内临时索引时可用 HashMap；如果需要稳定插入顺序、排序或并发更新，应分别考虑 LinkedHashMap、TreeMap 或 ConcurrentHashMap。

**常见追问**

- Java 7 与 Java 8 的典型实现差异？（OpenJDK 8 引入树桶）
- HashMap 是否保证 O(1)？（只是在哈希分布合理前提下的预期性能）

**易错点**

把“数组+链表+红黑树”说成 Java 语言规范，会把某个 JDK 实现误当成跨版本契约。

## 62. Java 8 中 HashMap 为什么使用数组 + 链表 + 红黑树？

**面试回答**

数组桶用于快速缩小候选范围；链表以较低结构成本容纳少量桶冲突；红黑树在单桶节点过多时改善查找增长趋势。三者是在常见小桶、极端冲突和实现复杂度之间的折中。

**原理与理解**

多数桶为空或只有少量节点，链表比树更省节点和维护成本。若冲突集中，线性遍历成本升高，树化可以把桶内查找从线性趋势改善到对数趋势。

**成立条件与边界**

树化不是 HashMap API 承诺，也不是“链表一长就必然转树”；还受 table 容量和具体阈值影响。树节点比较还会利用 Comparable 或实现内部 tie-break，不能把它等同于普通 TreeMap 排序。

**实际场景（通用工程）**

安全敏感入口仍应限制攻击者可控 key 数量和资源占用；树化只是缓解冲突，不替代输入限制、容量管理与监控。

**常见追问**

- 为什么不一开始都用红黑树？（小桶下链表更简单、空间成本更低）
- 红黑树是否让整个 Map 有序？（不会，只处理单个桶内部）

**易错点**

红黑树是冲突桶的防退化结构，不会让 HashMap 变成排序 Map。

## 63. HashMap 的 `put()` 流程是什么？

**面试回答**

OpenJDK 会计算并扩散 key 的 hash，必要时初始化 table，再用掩码定位桶。桶空则插入；桶非空则比较首节点并遍历链表或树：等价 key 更新 value，不同 key 新增节点。新增后可能树化，并在 size 超过阈值时扩容。

**原理与理解**

key 等价判断会先利用已算出的 hash，再判断引用身份或 equals。覆盖已有 value 通常不是结构修改，不增加 size；新增映射才改变结构，`put` 返回该 key 之前的 value 或 null。

**成立条件与边界**

null 返回值既可能表示原来没有映射，也可能表示旧 value 就是 null。put 的具体分支、尾插和钩子方法属于 OpenJDK 实现，不能作为 Map 接口通用流程。

**实际场景（通用工程）**

聚合计数若存在“读旧值再 put”逻辑，单线程可用 `merge`；并发场景不能把 HashMap 的多步 put 当原子操作。

**常见追问**

- 如何判断同一个 key？（Map 相等语义配合一致的 hashCode）
- 覆盖 value 会增加 size 吗？（不会）

**易错点**

“只要 hash 相同就覆盖”错误；hash 只是候选筛选，最终还需 key 相等判断。

## 64. HashMap 的 `get()` 流程是什么？

**面试回答**

OpenJDK 对查询 key 计算扩散 hash 并定位桶；先检查首节点，再按链表或树桶规则寻找 hash 与 key 相等的节点，找到返回 value，否则返回 null。

**原理与理解**

平均速度来自哈希把候选缩小到少量桶内节点。若哈希分布差或容量设置不合理，候选增多，实际成本就会上升。

**成立条件与边界**

HashMap 允许 null value，因此 get 返回 null 不能区分“无此 key”与“映射到 null”，需要 `containsKey`。并发修改期间调用 get 没有 HashMap 线程安全保证。

**实际场景（通用工程）**

业务逻辑若必须区分“未缓存”和“缓存了空结果”，应使用 containsKey、哨兵值或明确缓存模型，不凭 get 的 null 猜测。

**常见追问**

- get 为什么通常快？（哈希定位后只查少量候选）
- null key 如何查询？（HashMap 支持，OpenJDK 将其 hash 处理为 0）

**易错点**

“命中就是绝对 O(1)”与“返回 null 就不存在”都是忽略前提的答案。

## 65. 什么是 Hash 冲突？

**面试回答**

日常语境常把两种情况都叫哈希冲突：不同 key 得到相同 hashCode；或者扩散后的 hash 不同但经过 table 掩码后落入同一桶。对 HashMap 性能直接相关的是“多个映射进入同一桶”。

**原理与理解**

key 空间远大于有限的 int hash 和有限桶数，冲突不可避免。好的 hashCode 与扩散函数只能让分布更均匀，不能保证零冲突。

**成立条件与边界**

相同 hashCode 一定会进入同一桶；不同 hashCode 在当前容量下也可能同桶，扩容后可能分开。哈希冲突不等于 key 相等，仍需 equals 确认。

**实际场景（通用工程）**

自定义业务键应让相等字段与 hashCode 一致，并检查分布；不能使用常量 hashCode，虽可能保持正确性，却会严重损害性能。

**常见追问**

- 冲突可以完全避免吗？（不能）
- 不同 hashCode 能落同一桶吗？（能，桶数有限）

**易错点**

把“hashCode 相同”“扩散 hash 相同”和“桶下标相同”混为一谈，会导致扩容解释错误。

## 66. HashMap 如何解决 Hash 冲突？

**面试回答**

OpenJDK HashMap 采用链地址思路：同一桶保存节点链；节点过多且 table 足够大时转为树桶。它还扩散 hash 高低位，并通过扩容增加桶数，降低可被分散的桶冲突。

**原理与理解**

查找时先定位桶，再用 hash 与 key 相等性筛选节点。扩容后，OpenJDK 的 2 次幂容量让旧桶节点按新增的一个掩码位拆成两组，而不必重新调用 key.hashCode。

**成立条件与边界**

扩容无法拆开 hash 完全相同且 key 不等的节点；树化也会增加内存和维护成本。开放定址等是其他哈希表方案，不是此实现的路径。

**实际场景（生产能力）**

若单桶异常变长，优先排查 key 的 hashCode、输入分布与恶意数据，而不是只通过扩大初始容量掩盖问题。

**常见追问**

- 扩容能消除所有冲突吗？（不能）
- 扰动函数作用是什么？（让高位信息参与低位掩码定位）

**易错点**

“链地址法”“hash 扩散”“扩容”和“树化”解决的是不同层面的问题，不能互相替代。

## 67. HashMap 为什么同时需要 `hashCode()` 和 `equals()`？

**面试回答**

hashCode 用来快速缩小候选桶；equals 用来确认候选 key 是否逻辑相等。只做 equals 需要线性扫描大量键，只做 hashCode 又无法区分碰撞对象，所以两者共同保证效率和正确性。

**原理与理解**

Object 契约要求 equals 相等的对象具有相同 hashCode，这使逻辑相等 key 能到达同一查找路径；同 hash 不要求 equals，桶内仍可保存多个映射。

**成立条件与边界**

若只重写 equals 而 hashCode 不一致，逻辑相等对象可能进入不同桶，get/remove 失败。若只重写 hashCode，通常只是冲突增多，不会让 equals 不同的 key 自动变成同一映射。详见 [[02-Object与String#20. 为什么重写 `equals()` 通常要重写 `hashCode()`？]]。

**实际场景（通用工程）**

自定义 key 应使用不可变业务标识实现 equals/hashCode，并用相等 key 的 put/get、HashSet 去重和字段变更测试验证契约。

**常见追问**

- hashCode 相同是否 key 相同？（不是）
- equals 相等但 hashCode 不同会怎样？（违反契约，哈希容器行为异常）

**易错点**

“只重写 hashCode 会误判为重复”不准确，最终 key 判等仍依赖 equals。

## 68. HashMap 默认初始容量是多少？

**面试回答**

Java SE 25 HashMap API 描述无参构造的默认初始容量为 16、默认负载因子为 0.75。OpenJDK 通常延迟到首次需要时才分配 table，因此“逻辑默认容量 16”不等于构造瞬间已有 16 个桶。

**原理与理解**

OpenJDK table 容量采用 2 的幂。传入 initialCapacity 表达桶容量需求，不等于“可无扩容存放同数量映射”；预计映射数还要考虑负载因子。

**成立条件与边界**

Java 19+ 提供 `HashMap.newHashMap(expectedMappings)`，可按预计映射数创建更合适的容量。指定容量过大不仅浪费空间，HashMap 迭代还与 capacity + size 相关。

**实际场景（生产能力）**

已知预计存 N 个映射时优先使用 `newHashMap(N)`（版本允许）或按负载因子估算，而不是直接 `new HashMap<>(N)` 后声称绝不扩容。

**常见追问**

- 为什么容量使用 2 的幂？（见 [[05-HashMap#72. HashMap 为什么把容量设计成 2 的幂？]]）
- 默认构造是否立刻分配数组？（OpenJDK 通常懒分配）

**易错点**

初始容量、预计映射数和扩容阈值是三个概念，数字相同不代表含义相同。

## 69. HashMap 默认负载因子是多少？

**面试回答**

默认负载因子是 0.75。它控制 table 允许达到的密度，并参与计算扩容阈值；API 将其描述为空间成本和查找成本之间的良好折中。

**原理与理解**

在典型状态下，threshold 近似 capacity × loadFactor。更高负载因子减少空桶但可能增加桶内候选，更低值增加空间和扩容频率。

**成立条件与边界**

负载因子不是“当前 size/capacity 的实时统计字段”，而是构造配置；树化与首次 table 创建等实现路径也可能引起扩容，不能把所有 resize 都归结为一个固定公式。

**实际场景（通用工程）**

大多数业务保持默认值；只有容量、内存和访问分布有可靠测量时才调整，并同时观察迭代成本和冲突情况。

**常见追问**

- 为什么默认 0.75？（见 [[05-HashMap#70. 为什么负载因子默认是 0.75？]]）
- 能否传 0 或负数？（不能，构造器会拒绝）

**易错点**

0.75 是配置参数，不是“数组已有 75% 槽位都非空”的精确描述，因为一个桶可包含多个映射。

## 70. 为什么负载因子默认是 0.75？

**面试回答**

HashMap API 将 0.75 定义为时间与空间成本的良好折中：值高可降低空间开销，但增加查找成本；值低可减少桶密度，却需要更多桶并更早扩容。

**原理与理解**

哈希表设计同时受 key 分布、内存、缓存局部性和扩容成本影响，不存在脱离负载的普适最优值。0.75 是默认工程选择，方便覆盖常见用途。

**成立条件与边界**

不要把 0.75 宣称为由泊松分布严格证明的数学最优值；OpenJDK 源码中的分布分析用于解释树化概率，不等于为所有业务推导出唯一负载因子。

**实际场景（生产能力）**

只有通过基准与生产指标发现内存或碰撞瓶颈时才调整；盲目设为 1 可能增加查找成本，盲目设为 0.5 可能放大空间与迭代成本。

**常见追问**

- 更高一定更省总内存吗？（不一定，冲突节点与性能代价也要计算）
- 0.75 是否所有 Map 都相同？（不是，具体实现各有契约）

**易错点**

“0.75 是精确最优”与“0.5 一定更快”都缺少真实分布和测量前提。

## 71. HashMap 什么时候扩容？

**面试回答**

API 层面，当映射数超过 load factor 与当前 capacity 的乘积时会 rehash，桶数约增至两倍。OpenJDK 还会在首次 put 时创建 table；小 table 的某个桶达到树化条件时，也可能优先扩容而不是树化。

**原理与理解**

常规新增后若 `++size > threshold` 就 resize。2 次幂 table 扩大后，旧桶节点根据旧容量对应的 hash 位留在原下标或移动到“原下标 + 旧容量”。

**成立条件与边界**

“默认第 13 个元素必扩容”只适用于默认 table 已为 16、此前都是新增映射且没有其他实现路径等条件。覆盖已有 key 不增加 size，通常不会因 size 触发扩容。

**实际场景（生产能力）**

大量装载前按预计映射数预设容量，避免多次 resize 的 CPU、瞬时内存和延迟峰值；仍需防止严重 hash 冲突。

**常见追问**

- 扩容后是否重新调用每个 key.hashCode？（OpenJDK 迁移利用已保存 hash，不必逐个重新调用）
- 容量是否永远翻倍？（OpenJDK 常规路径如此，API 表述为大约两倍）

**易错点**

扩容不只是“size 到 12”，还包括首次分配与小 table 冲突集中时的实现路径。

## 72. HashMap 为什么把容量设计成 2 的幂？

**面试回答**

这是 OpenJDK HashMap 的实现选择。容量为 2 的幂时，可用 `(n - 1) & hash` 选择桶；扩容翻倍只增加一个有效掩码位，旧桶节点可高低分组迁移，逻辑简单且高效。

**原理与理解**

`n - 1` 的低位为连续 1，hash 扩散后的低位都能参与索引。扩容后检查 `hash & oldCap`，为 0 则留原位，否则移动 oldCap 距离。

**成立条件与边界**

“位运算一定比取模快很多”不是现代 JIT 下的通用证明，编译器可优化常量或幂次取模。真正稳定的实现收益还包括掩码规则、容量归一化和迁移拆分。

**实际场景（通用工程）**

调用方不应依赖具体桶下标或遍历顺序；理解 2 的幂用于解释内部实现，而不是手工预测 Map 输出。

**常见追问**

- 为什么还要 hash 扩散？（避免只用低位时丢失高位差异）
- 指定非 2 次幂容量会怎样？（OpenJDK 会归一到可用的 2 次幂 table 大小）

**易错点**

2 的幂不会自动保证分布均匀，key 的 hashCode 质量仍然重要。

## 73. HashMap 链表什么时候转换成红黑树？

**面试回答**

在 OpenJDK 8+ 中，新增节点使某桶达到树化阈值 8，并且 table 容量至少为 64 时，会尝试把该桶转为树；容量小于 64 时通常先扩容，希望把节点分散。

**原理与理解**

源码常量为 `TREEIFY_THRESHOLD = 8`、`MIN_TREEIFY_CAPACITY = 64`。put 内部计数有实现上的前后顺序，面试可表述为“插入后桶节点达到 8 且 table 至少 64”。

**成立条件与边界**

这些数字是 OpenJDK 实现常量，不是 HashMap API 保证。反树化涉及 `UNTREEIFY_THRESHOLD = 6` 以及 resize/remove 路径，不能简单说“删除到 6 就在所有情况下立刻变链表”。

**实际场景（生产能力）**

出现树桶应视为检查 hash 分布的信号；不能把树化当作允许低质量或攻击者可控 hashCode 的理由。

**常见追问**

- 到 8 一定树化吗？（不一定，还要 table 至少 64）
- 为什么小 table 先扩容？（扩容可能把桶冲突分散）

**易错点**

只背 8 和 6、不知道 64 以及转化路径，是典型的碎片化记忆。

## 74. 为什么链表过长后要转换成红黑树？

**面试回答**

链表查找随桶节点数线性增长；红黑树保持近似平衡，可把树桶查找增长趋势改善为对数级，降低严重冲突或恶意 hash 分布导致的性能退化。

**原理与理解**

树化不是为了让正常 HashMap 比数组更快，而是为异常长桶设置上限更好的数据结构。小桶继续用链表，避免树节点空间和旋转维护成本。

**成立条件与边界**

这是 OpenJDK 的实现防护，不是 HashMap 对最坏复杂度的跨实现 API 承诺。若 key 不可比较，树桶还需类名与身份哈希等 tie-break 维持结构，不代表 key 获得业务排序。

**实际场景（生产能力）**

对公网可控 key 仍要限制请求规模和资源使用；树化改善单桶查找，却不能阻止内存耗尽或高成本 equals。

**常见追问**

- 红黑树一定比链表快吗？（节点少时未必）
- 树化后 Map 是否按 key 排序？（不是）

**易错点**

树桶只优化单桶候选查找，不改变 HashMap 整体无序和非线程安全的性质。

## 75. HashMap 为什么线程不安全？

**面试回答**

HashMap 没有为并发读写建立同步与 happens-before 保证。多个线程共享同一实例并至少有一个结构修改时，可能出现丢更新、可见性问题、瞬态结构或遍历异常；API 要求外部同步。

**原理与理解**

put、resize、size 更新由多步操作组成，不是一个原子事务。fail-fast 迭代器也只是尽力检测错误，不能阻止或修复并发修改。

**成立条件与边界**

历史 OpenJDK 7 的并发 resize 环链是著名案例，但不应把“JDK 8 不再复现该具体环路”误写成线程安全。并发只读也需要对象先被正确构造和安全发布。

**实际场景（生产能力）**

本地共享缓存使用 ConcurrentHashMap 或更完整的缓存组件；若用 `Collections.synchronizedMap`，复合操作和遍历还要遵守其锁规则。比较见 [[05-HashMap#78. HashMap 和 ConcurrentHashMap 有什么区别？]]。

**常见追问**

- CME 能保证检测并发写吗？（不能，best-effort）
- 单线程局部 HashMap 需要换 CHM 吗？（不需要）

**易错点**

“JDK 8 只会丢数据、绝不会出现其他异常行为”仍是无依据保证；未同步并发修改的结果不应依赖。

## 76. HashMap 可以存 null Key 和 null Value 吗？

**面试回答**

可以。HashMap 允许一个 null key 对应的映射，并允许任意多个 key 映射到 null value。同一个 null key 再 put 会替换原映射，而不是增加第二个 null key。

**原理与理解**

OpenJDK 将 null key 的扩散 hash 处理为 0，因此进入第 0 桶；null value 与普通 value 一样存储。get 的 null 结果因此具有两种含义。

**成立条件与边界**

是否允许 null 是具体 Map 实现的契约，不是 Map 接口统一规定。Hashtable 和 ConcurrentHashMap 都拒绝 null；差异见 [[05-HashMap#77. HashMap 和 Hashtable 有什么区别？]]。

**实际场景（通用工程）**

若 null 表达“未命中”“计算失败”和“合法空值”中的不同语义，应使用显式状态或 Optional/哨兵模型，避免 Map API 歧义扩散到业务层。

**常见追问**

- 如何判断 null value 的 key 是否存在？（`containsKey`）
- ConcurrentHashMap 支持 null 吗？（不支持 key 或 value 为 null）

**易错点**

“null key 存在数组下标 0”是 OpenJDK 实现说明；公开契约只要求 HashMap 允许 null key。

## 77. HashMap 和 Hashtable 有什么区别？

**面试回答**

HashMap 不同步并允许 null key/value；Hashtable 的公开方法提供同步语义，并拒绝 null key/value。Hashtable 是早期遗留类，现代并发映射通常优先 ConcurrentHashMap，但不能仅以“老”断言它在所有场景都错误。

**原理与理解**

Hashtable 对单个方法使用同步，ConcurrentHashMap 则允许 retrieval 与更新高并发重叠，并提供 ConcurrentMap 的原子复合操作。HashMap 适合线程封闭或有外部同步的场景。

**成立条件与边界**

“Hashtable 锁整张表所以必然很慢”是简化实现描述，性能必须测量；它的方法线程安全也不让多次调用自动组成原子事务。三者都不保证按插入顺序迭代。

**实际场景（通用工程）**

新代码单线程映射用 HashMap；共享并发状态优先根据原子操作需求使用 ConcurrentHashMap；维护旧 API 时再评估 Hashtable 兼容性。

**常见追问**

- Hashtable 允许 null 吗？（不允许）
- synchronized 方法能保证“先检查再插入”原子吗？（跨多次调用不能自动保证）

**易错点**

“线程安全就选 Hashtable”忽略了并发语义和原子 API；“Hashtable 已废弃”也不准确，它并未被标记为 Deprecated。

## 78. HashMap 和 ConcurrentHashMap 有什么区别？

**面试回答**

HashMap 不提供线程安全保证；ConcurrentHashMap 支持高并发 retrieval 和更新，并提供 `putIfAbsent`、条件 remove/replace、compute/merge 等原子复合操作。ConcurrentHashMap 不允许 null key/value，迭代器是弱一致的且不抛 CME。

**原理与理解**

Java SE 25 契约说明 get 等 retrieval 通常不阻塞，并可与更新重叠；对某 key 的已完成更新与读到该值的非 null retrieval 存在 happens-before。size 等聚合结果在并发更新时可能只是瞬态估计，不能直接做控制条件。

**成立条件与边界**

“JDK 8 就是 CAS + synchronized 锁桶头”只是对 OpenJDK 部分写路径的概括：空桶插入、非空桶更新、树桶和协作扩容路径不同。JDK 7 Segment 也是历史实现，不是 ConcurrentHashMap API 身份。

**实际场景（生产能力）**

并发缓存初始化使用 `computeIfAbsent` 或 `putIfAbsent`，避免 `containsKey + put` 竞态；复杂跨 key 不变量仍可能需要外部锁、事务或重新建模。

**常见追问**

- 为什么迭代不抛 CME？（提供弱一致视图，可反映创建后某时刻的状态）
- size 能否用于“等于 N 就执行一次”？（并发更新时不适合作程序控制）
- 为什么不支持 null？（API 明确保留 null 表示无映射，key/value 均拒绝 null）

**易错点**

ConcurrentHashMap 保证单次和规定的复合操作线程安全，不代表任意多步业务逻辑自动原子，也不代表整个表存在可供用户锁住的全局互斥锁。
