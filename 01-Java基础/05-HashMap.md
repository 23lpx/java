# HashMap

## 61. HashMap 的底层数据结构是什么？

**面试回答**

Java 8 的 HashMap 是「数组 + 链表 + 红黑树」。数组每个位置是一个桶，桶里挂链表；链表长度超过阈值后转成红黑树。

**理解**

数组下标由 key 的 hash 决定，元素落在哪个桶。同一个桶里的多个元素（哈希冲突）用链表串起来；链表太长查询退化成 O(n)，就升级成红黑树把查找降到 O(log n)。这是 JDK8 相对 JDK7 的重要优化（JDK7 只有数组 + 链表）。

**场景**

存菜品缓存、id 映射时用 HashMap，理解它的结构能解释「为什么查找快」「为什么无序」。

**常见追问**

- JDK7 和 JDK8 的 HashMap 结构有什么不同？（JDK8 加了红黑树）
- 数组长度会变吗？（会，扩容时翻倍）

**易错点**

说 HashMap 底层只说「数组 + 链表」是 JDK7 的答案，JDK8 要补上「红黑树」。

## 62. Java 8 中 HashMap 为什么使用数组 + 链表 + 红黑树？

**面试回答**

数组保证 O(1) 定位，链表解决哈希冲突，红黑树解决链表过长导致的查询退化问题，让最坏情况从 O(n) 降到 O(log n)。

**理解**

数组寻址快但不能直接存所有冲突元素；链表能存冲突但查询要遍历；当链表太长（比如恶意构造相同 hash 的 key），查询就退化。引入红黑树作为「升级版链表」，在元素多时保证查询效率。三者各司其职，是性能与实现的平衡。

**场景**

这解释了为什么 HashMap 在极端情况下（大量 hash 冲突）依然能保持可接受的查询性能。

**常见追问**

- 为什么不用二叉搜索树而用红黑树？（普通 BST 可能退化成链表，红黑树自平衡）
- 红黑树会再变回链表吗？（会，节点少时退化成链表省空间）

**易错点**

红黑树是为了「防退化」而不是「更快」，小数据量下链表反而更简单高效。

## 63. HashMap 的 `put()` 流程是什么？

**面试回答**

先计算 key 的 hash 定位数组下标；该位置为空就直接放入；不为空就遍历链表或红黑树，遇到相同 key 就覆盖 value，否则挂到末尾；最后判断是否超过阈值，超过就扩容。

**理解**

大致步骤：1. 算 `hash(key)` 得到下标；2. 若桶为空，新建节点放入；3. 桶里已有元素，按链表或红黑树查找 key：相同则替换 value，不同则插入；4. 插入后元素总数超过「容量 × 负载因子」就扩容 resize。JDK8 插入用尾插法，JDK7 是头插法。

**场景**

`map.put("orderId", order)` 时就是这套流程，key 相同会覆盖旧值，不同才新增。

**常见追问**

- 怎么判断 key 相同？（hashCode 相同且 equals 为 true）
- 覆盖和新增有什么区别？（覆盖改 value 不动结构，新增才可能触发扩容）

**易错点**

put 时「先判断 key 是否相同」，判断标准是 hashCode + equals 两个条件，不是只看 hash。

## 64. HashMap 的 `get()` 流程是什么？

**面试回答**

先算 key 的 hash 定位数组下标；该位置为空直接返回 null；不为空就遍历链表或红黑树，用 equals 找到相同 key 返回它的 value，找不到返回 null。

**理解**

get 和 put 的定位逻辑一致：`hash(key)` → 下标 → 桶内查找。桶里是链表就顺序遍历逐个 equals 比较，是红黑树就按树查找。找不到返回 null（但要注意，value 本身也可能是 null，所以不能用 null 判断 key 是否存在，要用 `containsKey`）。

**场景**

`map.get(orderId)` 取订单，命中就 O(1)（无冲突时），这就是 HashMap 快的原因。

**常见追问**

- 为什么 get 快？（hash 定位 + 桶内少量比较，平均 O(1)）
- 怎么区分「key 不存在」和「value 是 null」？（用 containsKey）

**易错点**

get 返回 null 不代表 key 一定不存在，因为 value 可能存的就是 null。

## 65. 什么是 Hash 冲突？

**面试回答**

不同 key 经过哈希计算后，映射到了同一个数组下标（同一个桶），就叫哈希冲突。

**理解**

数组长度有限，而 key 无限多，把任意 key 映射到有限下标必然会有多个 key 落到同一位置，这是哈希表固有的问题。好的哈希函数能减少冲突，但无法完全避免。

**场景**

HashMap 里两个不同的订单 id 算出的下标恰好相同，就发生了 hash 冲突，它们会挂在同一个桶的链表上。

**常见追问**

- 冲突能避免吗？（不能完全避免，只能降低概率）
- 冲突多会怎样？（链表变长、查询变慢，触发转红黑树）

**易错点**

hash 冲突是「下标相同」不是「hashCode 值一定相同」，即便 hashCode 不同，经过 (n-1)&hash 后也可能落到同一桶。

## 66. HashMap 如何解决 Hash 冲突？

**面试回答**

用「链地址法」（拉链法）：同一桶的多个元素用链表串起来；链表过长时转成红黑树。

**理解**

冲突元素都放在同一个桶的链表里，插入时挂到链表尾部，查找时沿链表逐个 equals 比较。JDK8 进一步优化：链表长度到阈值后转红黑树，避免查找退化。此外，HashMap 的扰动函数（hash 高 16 位异或低 16 位）让下标分布更均匀，从源头减少冲突。

**场景**

理解这点就能解释：为什么 HashMap 平均 O(1)，但最坏（全冲突）会退化到 O(n) 或 O(log n)。

**常见追问**

- 还有别的解决冲突方法吗？（开放定址法、再哈希法；Java 用的是链地址法）
- 扰动函数干嘛的？（让高位参与运算，分布更均匀）

**易错点**

「拉链法」是 HashMap 的冲突解决方式，别和「扩容」混淆，扩容是容量不够时的事。

## 67. HashMap 为什么同时需要 `hashCode()` 和 `equals()`？

**面试回答**

hashCode 负责「定位到哪个桶」做粗筛，equals 负责「桶内确认是不是同一个 key」做精判，两者缺一不可。

**理解**

如果只有 hashCode，两个不同对象可能 hash 相同（冲突），无法区分谁是谁；如果只有 equals，就要拿 key 和所有已有 key 逐个比，退化成 O(n)。所以先用 hashCode 缩小范围，再用 equals 精确判断，配合起来才高效又准确（详见 [[02-Object与String#20. 为什么重写 `equals()` 通常要重写 `hashCode()`？]]）。

**场景**

自定义对象作为 HashMap 的 key 时，必须同时正确重写 hashCode 和 equals，否则 put 进去 get 不出来。

**常见追问**

- 只重写一个会怎样？（equals 相等但 hashCode 不同，get 找不到；hashCode 相同但 equals 不等，误判重复）
- hashCode 的作用是什么？（快速定位桶）

**易错点**

「hashCode 定位、equals 精判」是理解 HashMap 的核心，面试说反或漏掉一个都算没答到点上。

## 68. HashMap 默认初始容量是多少？

**面试回答**

默认初始容量是 16，且必须是 2 的幂。

**理解**

`new HashMap<>()` 时容量默认 16（`DEFAULT_INITIAL_CAPACITY = 16`）。JDK8 是懒加载的，第一次 put 才真正创建数组。容量设计成 2 的幂是为了位运算定位（见 [[05-HashMap#72. HashMap 为什么把容量设计成 2 的幂？]]）。

**场景**

如果知道大概要存多少元素，new 时指定容量（如 `new HashMap<>(64)`）能减少扩容次数。

**常见追问**

- 为什么是 16 不是别的？（2 的幂，配合位运算，且是个合理的初始大小）
- 能指定初始容量吗？（能，构造器传参，内部会调整为 2 的幂）

**易错点**

16 是「默认」值，实际会懒加载；指定非 2 的幂容量，HashMap 内部会帮你向上取整到 2 的幂。

## 69. HashMap 默认负载因子是多少？

**面试回答**

默认负载因子是 0.75。

**理解**

负载因子 = 元素个数 / 数组容量，表示「装到多满就扩容」。0.75 意味着数组用到 75% 就扩容。它是空间和时间的折中：太低空间浪费、扩容频繁，太高冲突变多、查询变慢。

**场景**

面试常连着问「为什么是 0.75」，见 [[05-HashMap#70. 为什么负载因子默认是 0.75？]]。

**常见追问**

- 负载因子能改吗？（构造器可传，但一般用默认值）

**易错点**

负载因子 0.75 和初始容量 16 别记混；0.75 是「比例阈值」，16 是「容量大小」。

## 70. 为什么负载因子默认是 0.75？

**面试回答**

0.75 是空间利用率和查询效率的折中：太小空间浪费、扩容太频繁，太大冲突变多、查询退化。

**理解**

负载因子接近 1，数组塞得很满，空间利用率高，但 hash 冲突概率大增，链表变长，查询变慢；负载因子接近 0，冲突少、查询快，但大部分空间空着，而且频繁扩容（扩容有拷贝开销）。0.75 是经验上的平衡点，兼顾两者。这是权衡的结果，不是精确算出来的最优值。

**场景**

面试答到这里能体现「理解权衡」，而不是死记数字。

**常见追问**

- 为什么不是 1 或 0.5？（1 冲突太多，0.5 太浪费 + 频繁扩容）
- 0.75 是算出来的吗？（是工程经验值，结合泊松分布对冲突概率的考量）

**易错点**

0.75 是「折中值」不是「精确最优值」，别把它说成数学上严格推导的结果。

## 71. HashMap 什么时候扩容？

**面试回答**

当元素个数超过「容量 × 负载因子」（即超过阈值，默认 16 × 0.75 = 12）时，就会触发扩容。

**理解**

扩容会创建一个容量翻倍的新数组，把旧数组的元素重新计算下标搬到新数组（rehash）。因为容量是 2 的幂，扩容后元素要么留在原下标，要么移到「原下标 + 旧容量」，所以 rehash 相对高效。扩容是较重的操作，会短暂占用更多内存和 CPU。

**场景**

项目里如果能预估 HashMap 要存的元素数量，提前指定容量能避免多次扩容带来的性能抖动。

**常见追问**

- 扩容后容量变成多少？（翻倍，16 → 32 → 64）
- 扩容时元素怎么搬？（重新算下标，要么原位要么 +旧容量）

**易错点**

「元素个数超过 12」这个 12 是「容量 × 负载因子」算出来的，不是固定死的；扩容是翻倍，不是加固定值。

## 72. HashMap 为什么把容量设计成 2 的幂？

**面试回答**

为了用位运算 `(n-1) & hash` 代替取模 `hash % n`，更快；同时让下标分布更均匀，扩容时元素迁移更简单。

**理解**

当 n 是 2 的幂时，`hash % n` 等价于 `hash & (n-1)`，位运算比取模快。而且 n-1 的二进制全是 1，和 hash 做与运算时，结果只由 hash 的低位决定，配合扰动函数（高 16 位异或低 16 位）能让各下标被均匀命中。扩容时也方便：元素要么留在原位，要么平移到「原位 + 旧容量」。

**场景**

理解这一点能解释 HashMap 为什么高效，以及为什么它要保证容量始终是 2 的幂。

**常见追问**

- `&` 比 `%` 快多少？（位运算是 CPU 原生指令，比取模快）
- 为什么要扰动函数？（只取低位会分布不均，扰动让高位也参与）

**易错点**

2 的幂带来的核心好处是「位运算定位 + 分布均匀 + 迁移简单」，别只答「取模快」一个点。

## 73. HashMap 链表什么时候转换成红黑树？

**面试回答**

两个条件：链表长度达到 8，且数组容量（table 长度）达到 64。满足这两个才转红黑树；数组不够大时会先扩容而不是转树。

**理解**

转树的阈值是「链表长度 ≥ 8」（TREEIFY_THRESHOLD），但这有个前提「数组长度 ≥ 64」（MIN_TREEIFY_CAPACITY）。因为如果数组还很小，说明是数组容量不足导致冲突集中，这时扩容就能让元素分散开，比转树更划算。所以两个条件都要满足才会真正树化。

**场景**

面试追问「链表到 8 一定转树吗」时，答「不一定，还要看数组长度是否到 64」。

**常见追问**

- 为什么阈值是 8？（结合泊松分布，链表到 8 的概率已经很低，说明冲突异常，需要树化）
- 红黑树什么时候退化成链表？（元素少时，阈值 6，避免频繁转换）

**易错点**

「链表长度 ≥ 8 就转红黑树」漏了「数组容量 ≥ 64」这个前提，是不完整的。

## 74. 为什么链表过长后要转换成红黑树？

**面试回答**

因为链表查询要逐个遍历，时间复杂度 O(n)，过长会让 HashMap 的查找从接近 O(1) 退化到 O(n)；红黑树是自平衡二叉查找树，查询 O(log n)，能防止性能退化。

**理解**

正常情况下冲突少、链表短，遍历几个节点无所谓。但如果大量 key 落到同一桶（比如恶意构造相同 hash 的 key），链表会非常长，查一个 key 要遍历整条链。红黑树通过自平衡保证高度不超过约 2log(n)，把最坏情况压到 O(log n)。这是防御性设计。

**场景**

理解这点能回答「HashMap 为什么在大冲突场景下依然可用」，以及它和普通 BST 的区别（BST 会退化成链）。

**常见追问**

- 为什么用红黑树不用平衡二叉树？（红黑树旋转次数少，插入删除更高效，性能更均衡）
- 红黑树查找一定比链表快吗？（数据少时链表更快，红黑树有维护成本）

**易错点**

红黑树是「防最坏退化」，不是「任何情况都更快」；链表短时用链表反而更好。

## 75. HashMap 为什么线程不安全？

**面试回答**

因为 HashMap 的读写操作没有加锁或同步，多线程并发 put 会出现数据覆盖、size 计数不准，甚至 JDK7 扩容时形成环形链表导致死循环。

**理解**

JDK7 扩容用头插法，多线程同时 resize 可能形成环形链表，get 时死循环（CPU 100%）；JDK8 改成尾插法解决了死循环，但并发 put 仍会互相覆盖、丢失更新，size 也不是原子的。所以 HashMap 多线程共享时必须换 ConcurrentHashMap 或加锁。

**场景**

项目里多线程共享缓存 Map 时，不能直接用 HashMap，要用 ConcurrentHashMap（见 [[05-HashMap#78. HashMap 和 ConcurrentHashMap 有什么区别？]]）。

**常见追问**

- JDK7 死循环是怎么来的？（头插法 + 并发 resize 形成环）
- JDK8 还有死循环吗？（没有，但仍会丢数据、数据不一致）

**易错点**

JDK8 的 HashMap 线程不安全主要体现在「数据覆盖、不一致」，死循环是 JDK7 的问题，别把版本搞混。

## 76. HashMap 可以存 null Key 和 null Value 吗？

**面试回答**

可以，HashMap 允许一个 null key 和任意多个 null value。

**理解**

HashMap 对 null key 做了特殊处理：null key 的 hash 记为 0，存在数组下标 0 的位置，所以 null key 只能有一个（第二次 put null key 会覆盖）。null value 没有任何限制，随便存。

**场景**

用 HashMap 存「可能为 null 的 key/value」时 HashMap 能容纳；而 Hashtable、ConcurrentHashMap 不允许 null，见 [[05-HashMap#77. HashMap 和 Hashtable 有什么区别？]]。

**常见追问**

- 为什么 null key 只能有一个？（hash 固定为 0，同一位置，重复会覆盖）
- ConcurrentHashMap 允许 null 吗？（不允许，会抛 NPE）

**易错点**

「HashMap 允许 null」但「ConcurrentHashMap 不允许 null」，这两个结论别混淆，面试常拿来对比。

## 77. HashMap 和 Hashtable 有什么区别？

**面试回答**

主要区别：HashMap 线程不安全，Hashtable 线程安全（方法加 synchronized）；HashMap 允许 null key/value，Hashtable 不允许；HashMap 效率高、是主流选择，Hashtable 已基本废弃。

**理解**

Hashtable 用 `synchronized` 锁整个方法，任何操作都串行化，性能差，所以即便要线程安全也不推荐它，而是用 ConcurrentHashMap（分段锁/CAS，并发性能好得多）。HashMap 是 Hashtable 的现代替代，API 也更符合集合框架设计。

**场景**

项目里日常用 HashMap；需要线程安全时用 ConcurrentHashMap，而不是 Hashtable。

**常见追问**

- Hashtable 为什么性能差？（锁整个表，并发度低）
- 线程安全的 Map 有哪些？（Hashtable、ConcurrentHashMap、Collections.synchronizedMap）

**易错点**

Hashtable 是 `t` 小写（`Hashtable`），HashMap 的 M 大写，拼写别错；「线程安全用 Hashtable」是过时答案。

## 78. HashMap 和 ConcurrentHashMap 有什么区别？

**面试回答**

HashMap 线程不安全，ConcurrentHashMap 线程安全。JDK8 的 ConcurrentHashMap 用 CAS + synchronized（只锁桶头节点）保证并发安全，效率远高于整个加锁的方案，且不允许 null key/value。

**理解**

JDK8 ConcurrentHashMap 放弃了 JDK7 的分段锁（Segment），改为对每个桶的头节点加锁 + CAS 写，读操作不加锁，并发粒度更细，多线程读写性能接近 HashMap。它不允许 null，是为了避免并发下「null 是没找到还是存了 null」的歧义。要线程安全就选它。

**场景**

项目里本地缓存、多线程共享的 Map 用 ConcurrentHashMap；单线程或线程隔离的 Map 用 HashMap 即可。

**常见追问**

- JDK7 和 JDK8 的 ConcurrentHashMap 实现有何不同？（JDK7 分段锁 Segment，JDK8 CAS + synchronized 锁桶）
- 为什么 ConcurrentHashMap 不允许 null？（并发下 null 语义歧义）

**易错点**

ConcurrentHashMap 不是「整个 Map 加一把锁」，JDK8 是「锁桶头节点 + CAS」，并发粒度细，这是和 Hashtable 的本质区别。
