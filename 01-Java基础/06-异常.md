# 异常

## 79. Java 异常体系是怎样的？

**面试回答**

Java 中可被抛出和捕获的对象都继承 `Throwable`。它主要有两条分支：`Error` 表示通常不应由普通业务流程恢复的严重问题；`Exception` 表示应用层可能处理的异常。`Exception` 中，`RuntimeException` 及其子类属于非受检异常，其余通常属于受检异常。

**原理与理解**

编译器按类型决定是否强制“捕获或声明”：`RuntimeException`、`Error` 及其子类不强制，其余可抛异常通常必须处理。这个分类描述的是编译期契约，不等于严重程度或是否一定能恢复。

**成立条件与边界**

`Error` 语法上也能捕获，只是应用通常不应宽泛地捕获它；在任务隔离边界记录某个特定 `Error` 也可能有工程价值，但不能据此假设 JVM 状态仍可靠。

**实际场景（通用工程）**

业务入口通常统一处理预期的业务异常与未知 `Exception`；`OutOfMemoryError` 等严重问题更多依赖监控、隔离、限流和进程恢复，而不是继续执行业务。

**常见追问**

- 常见运行时异常有哪些？——`NullPointerException`、`IllegalArgumentException`、`ClassCastException` 等。
- `Throwable` 下只有两个直接子类吗？——面试通常按 `Error` 与 `Exception` 两大体系回答，具体类层次以 JDK API 为准。

**易错点**

不要说“`Error` 不能 catch”或“受检异常一定可恢复”；前者是工程建议，不是语法限制，后者也不是分类依据。

## 80. Error 和 Exception 有什么区别？

**面试回答**

两者都继承 `Throwable`。`Error` 通常表示虚拟机、链接或资源耗尽等严重问题，应用一般不把它当作正常恢复路径；`Exception` 更常用于描述应用可以传播、转换或处理的异常情况。

**原理与理解**

`Error` 和 `RuntimeException` 都是非受检异常，编译器不强制捕获或声明；`Exception` 还包含 `IOException`、`SQLException` 等受检异常。因此它们的差异不只是“能不能捕获”，还包括语义和类型体系。

**成立条件与边界**

“`Exception` 应该全部捕获”同样不准确。能在当前层真正恢复、补偿或转换时再捕获；否则保留 `cause` 并向上抛，避免吞异常。某些特定 `Error` 可在隔离边界记录后终止该任务，但不应使用 `catch (Throwable)` 让进程假装正常。

**实际场景（通用工程）**

接口层将已知业务异常映射为稳定响应；数据库、网络等异常可转换或上抛；严重 `Error` 交给监控和运行平台拉起实例。

**常见追问**

- `OutOfMemoryError` 能捕获吗？——语法上能，但通常无法保证后续业务安全。
- `StackOverflowError` 属于哪一支？——`Error`。

**易错点**

不要把 `Error` 简化成“JVM 专属且绝对不可处理”，也不要把 `Exception` 等同于“都应该就地 catch”。

## 81. Checked Exception 和 RuntimeException 有什么区别？

**面试回答**

受检异常在编译期必须捕获或在方法签名中声明；`RuntimeException` 及其子类不受这个强制要求。区别是编译期契约，不代表哪一类一定更严重或一定可恢复。

**原理与理解**

`IOException`、`SQLException`、`InterruptedException` 等通常是受检异常；`IllegalArgumentException`、`IllegalStateException`、`NullPointerException` 等是运行时异常。运行时异常不全是程序 bug，也可以用于表达调用契约或业务前置条件不满足。

**成立条件与边界**

框架可能转换异常类型，例如 Spring 常把持久化异常转换为非受检的 `DataAccessException`。Spring 声明式事务的默认回滚规则也不是“所有异常都回滚”，详见 [[02-Spring/08-Spring事务]]。

**实际场景（通用工程）**

可由调用方采取明确恢复动作的 I/O 失败可以保留受检契约；需要跨多层统一处理的业务失败常使用运行时异常，但应由团队的错误模型决定。

**常见追问**

- 受检异常必须怎么处理？——`try-catch`，或通过 `throws` 继续声明。
- `InterruptedException` 能直接吞掉吗？——不能；通常应恢复中断标记或继续抛出。

**易错点**

不要回答“受检异常可恢复、运行时异常都是编码错误”；Java 只强制前者参与编译期检查。

## 82. `throw` 和 `throws` 有什么区别？

**面试回答**

`throw` 是语句，用于抛出一个类型可赋给 `Throwable` 的表达式；`throws` 写在方法或构造器签名中，声明该可执行体可能传播的异常类型。

**原理与理解**

`throw new IllegalStateException(...)` 会让当前控制流异常完成；`throws IOException, SQLException` 是调用契约，尤其用于传播受检异常。非受检异常即使未写在 `throws` 中也能传播。

**成立条件与边界**

`throws` 不会主动创建或抛出异常，也不保证运行时一定发生；`throw` 一次抛出一个异常对象，但该对象可通过 `cause` 或 suppressed exceptions 保留关联异常。

**实际场景（通用工程）**

校验失败时主动 `throw` 业务异常；底层文件读取方法可 `throws IOException`，由更了解恢复策略的上层决定重试、转换还是终止。

**常见追问**

- `throw null` 会怎样？——运行时抛出 `NullPointerException`。
- 子类重写方法能扩大受检异常范围吗？——不能声明比父方法更宽的新受检异常。

**易错点**

不要说“`throws` 后列出的异常一定由内部 `throw` 语句产生”；被调用方法、表达式和运行时也可能抛出。

## 83. `try-catch-finally` 的执行顺序是什么？

**面试回答**

先执行 `try`。若正常完成则跳过 `catch`；若抛出异常，则执行从上到下第一个类型匹配的 `catch`。之后只要控制流能到达，都会先执行 `finally`，再完成返回或继续传播异常。

**原理与理解**

`return` 时会先计算待返回结果，再执行 `finally`。如果 `finally` 正常结束，原返回或异常继续；如果 `finally` 自己以 `return`、`throw` 等方式异常结束，它会替换之前的完成原因。

**成立条件与边界**

`finally` 并非进程级可靠性机制，未进入或未离开 `try`、虚拟机终止、进程崩溃等情况都可能使它不执行，详见 [[06-异常#84. finally 一定会执行吗？]]。

**实际场景（通用工程）**

实现 `AutoCloseable` 的资源优先使用 try-with-resources；资源按声明的逆序关闭，若主体和关闭都抛异常，关闭异常会成为 suppressed exception。

**常见追问**

- 多个 `catch` 如何匹配？——第一个与运行时异常类型兼容的分支。
- `finally` 在返回值计算前还是后？——返回表达式先求值，方法真正返回前执行 `finally`。

**易错点**

“无论如何都会执行 finally”过于绝对；也不要在 `finally` 中改变控制流。

## 84. finally 一定会执行吗？

**面试回答**

不一定。正常返回、匹配或未匹配异常时，只要线程能够离开对应 `try`，`finally` 通常都会执行；虚拟机或进程直接终止、崩溃、断电，或者线程一直阻塞在 `try` 中时，它就可能没有机会执行。

**原理与理解**

`finally` 是 Java 控制流规则的一部分，不是持久化或进程存活保证。`System.exit` 正常终止 JVM、`Runtime.halt` 立即终止、操作系统强杀进程等都不能依赖 `finally` 做收尾。

**成立条件与边界**

不要把“线程被强制停止”笼统列为必不执行：过时的 `Thread.stop` 会异步抛出 `ThreadDeath`，栈展开时仍可能执行 `finally`，但这种停止方式本身不安全且不应使用。

**实际场景（通用工程）**

释放进程内锁或连接可使用 `finally`/try-with-resources；关键状态还应依赖事务、幂等、租约或外部协调，不能把一致性只押在收尾代码上。

**常见追问**

- `return` 会跳过 `finally` 吗？——不会，方法返回前仍执行。
- `kill -9` 后会执行吗？——不会，进程没有机会继续执行 Java 代码。

**易错点**

`finally` 只能保证可达控制流中的清理，不能保证面对进程级故障时执行。

## 85. finally 中存在 return 会怎样？

**面试回答**

`finally` 中的 `return` 会以新的返回原因结束方法，覆盖 `try`/`catch` 已计算的返回值，也会丢弃正在传播的异常，因此应避免。

**原理与理解**

Java 规范把 `return`、`throw` 等视为 abrupt completion。若 `try` 因原因 R 结束，而 `finally` 又因原因 S 结束，最终保留 S，R 被丢弃。

**成立条件与边界**

即使 `finally` 不写 `return`，它重新抛出另一个异常也会覆盖原异常；需要同时保留时，应建立 cause 链或使用 try-with-resources 的 suppressed exception 机制。

**实际场景（通用工程）**

代码审查和静态检查应禁止 `finally` 中的 `return`。清理失败时记录或传播策略要明确，不能让业务异常悄悄消失。

**常见追问**

- `try` 返回对象引用后，`finally` 修改对象会怎样？——返回的是同一引用，修改可能对调用方可见；但重新给局部变量赋值不等于改对象。
- `finally` 抛异常会怎样？——会替换之前待返回值或待传播异常。

**易错点**

不要只记“覆盖返回值”，更危险的是它可能吞掉故障证据。

## 86. 如何自定义业务异常？

**面试回答**

先定义稳定的错误模型，再选择继承 `RuntimeException` 或受检异常。常见做法是提供错误码、安全提示以及保留 `cause` 的构造器，并在业务规则不满足时抛出，由边界层统一映射。

**原理与理解**

运行时业务异常可减少跨层 `throws` 声明，适合由统一异常处理器集中转换；受检异常适合强制直接调用者明确处理。是否携带 `code`、哪些构造器可见，取决于系统协议，并非语言强制。

**成立条件与边界**

异常消息不能泄露 SQL、密钥或内部路径；包装底层异常时应传入 `cause`。不要用异常代替普通分支，也不要为每一句提示创建没有稳定语义的新类型。

**实际场景（通用工程）**

库存不足可抛出带 `OUT_OF_STOCK` 错误码的业务异常；数据库连接失败仍保留原始 cause，并按系统异常处理。

**常见追问**

- 为什么常继承 `RuntimeException`？——便于跨层传播和统一处理，但要结合事务回滚与接口契约。
- 需要无参构造器吗？——只有序列化、框架实例化或团队规范确实需要时再提供。

**易错点**

“自定义异常都继承 RuntimeException、都必须带 code”不是通用定律。

## 87. 项目中为什么通常要定义统一业务异常？

**面试回答**

统一业务异常用于标识可预期的业务失败，让入口层稳定映射业务码、HTTP 状态和安全提示，同时把它与程序缺陷、依赖故障等未知异常区分开。

**原理与理解**

业务层只表达失败语义，`@RestControllerAdvice`/`@ExceptionHandler` 等边界组件负责协议转换，Controller 无需重复 `try-catch`。未知异常保留追踪标识并记录完整上下文，客户端只接收安全的通用提示，详见 [[07-项目/01-统一响应与异常处理]]。

**成立条件与边界**

统一不等于所有失败都返回 HTTP 200，也不等于所有业务异常都记录 ERROR。状态码、业务码和日志级别应按可预期程度、告警价值和客户端契约制定；同一异常也不能被多层重复记录。

**实际场景（项目核验项）**

可核对项目是否已有统一异常基类、稳定错误码、全局处理器和响应结构；若实际只统一了部分数据库约束异常，应如实描述，不能扩写成完整生产方案。

**常见追问**

- 业务异常要不要记录日志？——按可预期性和排障价值选择 INFO/WARN，未知系统异常通常记录 ERROR。
- 为什么不在每个 Controller 捕获？——会重复协议转换、遗漏分支并增加耦合。

**易错点**

不要把异常堆栈直接返回前端，也不要用统一响应包装掩盖真实的 HTTP 语义。
