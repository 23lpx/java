# 异常

## 79. Java 异常体系是怎样的？

**面试回答**

所有异常类的根是 `Throwable`，下面分两大分支：`Error`（严重错误，程序处理不了）和 `Exception`（程序能处理的异常）。Exception 又分为 Checked Exception（受检异常）和 RuntimeException（运行时异常）。

**理解**

`Throwable` 是根类；`Error` 如 OOM、StackOverflowError，属于 JVM 层面的问题，不该被 catch；`Exception` 是业务能处理的异常。其中 RuntimeException 及其子类（如 NPE、数组越界、ClassCastException）是运行时异常，编译期不强制处理；其余 Exception 是受检异常，编译期必须处理。

**场景**

项目里的异常处理针对的是 Exception，尤其是 RuntimeException 和自定义业务异常，Error 不用管也管不了。

**常见追问**

- Throwable 下还有别的分支吗？（主要是 Error 和 Exception 两个）
- RuntimeException 常见子类有哪些？（NullPointerException、IndexOutOfBoundsException、ClassCastException、IllegalArgumentException）

**易错点**

「异常」和「错误」在 Java 里是两个不同分支（Exception 和 Error），别混用术语。

## 80. Error 和 Exception 有什么区别？

**面试回答**

Error 是 JVM 层面的严重错误，如内存溢出、栈溢出，程序通常无法恢复，不应该捕获；Exception 是程序运行中可以预判和处理的异常，应该被捕获处理。

**理解**

Error 表示「系统/虚拟机出问题了」，比如 `OutOfMemoryError`、`StackOverflowError`，捕获了也救不回来，硬 catch 反而掩盖问题。Exception 是「程序逻辑可以处理的问题」，如空指针、SQL 异常、网络异常。面试重点：Error 不该 catch，Exception 应该 catch。

**场景**

项目里 `try-catch` 捕获的都是 Exception（尤其是业务异常），不会去 catch Error。

**常见追问**

- OutOfMemoryError 能被 catch 吗？（语法上能，但不推荐，因为 JVM 状态已不可靠）
- Error 和 Exception 都是 Throwable 的子类吗？（是）

**易错点**

Error 也是 Throwable 的子类，但「能 catch」不等于「应该 catch」，别把「语法上可以」说成「推荐这么做」。

## 81. Checked Exception 和 RuntimeException 有什么区别？

**面试回答**

Checked Exception（受检异常）在编译期强制处理，必须 try-catch 或 throws 声明，否则编译不过；RuntimeException（运行时异常）编译期不强制，运行时才暴露。

**理解**

受检异常代表「可预期、必须处理的异常」，如 `IOException`、`SQLException`、`ClassNotFoundException`，编译器强制你处理；运行时异常代表「程序 bug」，如 `NullPointerException`、`ArrayIndexOutOfBoundsException`，通常是编码错误，编译器不强制。Spring 事务里默认只回滚 RuntimeException（见 [[02-Spring/08-Spring事务]]）。

**场景**

项目里自定义业务异常都继承 RuntimeException，好处是方法不需要到处 `throws` 声明，由全局异常处理器统一捕获。

**常见追问**

- 常见受检异常有哪些？（IOException、SQLException、InterruptedException）
- 为什么自定义异常常继承 RuntimeException？（免去到处声明，配合全局异常处理）

**易错点**

「Checked」的关键是「编译期强制」，而不是「严重程度」；别把受检异常理解成「更严重的异常」。

## 82. `throw` 和 `throws` 有什么区别？

**面试回答**

`throw` 用在方法体内，主动抛出一个异常实例；`throws` 用在方法签名上，声明该方法可能抛出的异常类型。

**理解**

`throw new RuntimeException("xx")` 是「制造并抛出异常」的动作；`throws IOException` 是「声明这个方法会抛什么异常」，让调用方知道要处理。一个方法声明 `throws`，实际异常由内部 `throw` 抛出来，两者配合使用。

**场景**

项目里业务校验不通过时 `throw new BaseException("库存不足")`；方法签名 `throws Exception` 声明可能抛出的异常（不过用了运行时异常后很多地方就不需要 throws 了）。

**常见追问**

- throw 后面跟什么？（异常对象，一个）
- throws 后面能跟多个吗？（能，逗号分隔多个异常类型）

**易错点**

`throw` 是动词（抛异常实例），`throws` 是声明（列异常类型），一个是动作一个是签名，别写错。

## 83. `try-catch-finally` 的执行顺序是什么？

**面试回答**

先执行 try：try 正常完成就跳过 catch，执行 finally；try 抛异常就进入匹配的 catch，处理完再执行 finally；finally 里的代码无论如何都会最后执行。

**理解**

顺序是：try → （异常时）catch → finally。无论 try 正常返回还是抛异常，finally 都会执行（除非特殊场景，见 [[06-异常#84. finally 一定会执行吗？]]）。finally 通常用来释放资源、关闭连接、清理状态。

**场景**

项目里关闭数据库连接、关闭 IO 流时用 finally 保证资源一定被释放（Java 7 后有 try-with-resources 更优雅）。

**常见追问**

- finally 什么时候执行？（try/catch 之后、方法返回之前）
- try-with-resources 是什么？（自动关闭资源的语法，Java 7）

**易错点**

finally 在「return 之后、方法真正返回之前」执行；如果 finally 里也有 return，会改变最终返回值。

## 84. finally 一定会执行吗？

**面试回答**

不一定。正常流程下 finally 都会执行，但如果 JVM 退出（如 `System.exit()`）、JVM 崩溃、或线程被强制终止，finally 不会执行。

**理解**

finally 的设计意图是「无论 try 是否异常都执行」，但它是 JVM 层面的保证。如果程序在 try/catch 里调了 `System.exit(0)`，JVM 直接终止，后续的 finally 根本轮不到执行；JVM 崩溃、断电、`kill -9` 这些情况同理。除此之外，return、异常都不会阻止 finally。

**场景**

项目里正常关闭资源用 finally 是可靠的；但要意识到 `System.exit()` 这种「强行退出」会跳过 finally。

**常见追问**

- System.exit 在 try 里，finally 还执行吗？（不执行）
- return 会影响 finally 执行吗？（不会，finally 照常执行）

**易错点**

finally「几乎总执行，但遇到 JVM 退出/崩溃就不执行」，别把「一定」说得太绝对。

## 85. finally 中存在 return 会怎样？

**面试回答**

finally 里的 return 会覆盖 try 或 catch 里的 return，成为最终返回值，而且会吞掉异常。

**理解**

方法执行到 try 的 return 时，会先计算返回值暂存，然后执行 finally；如果 finally 里又写了 return，就用 finally 的 return 值覆盖原来的返回值。更严重的是，如果 try 里抛了异常，finally 里的 return 会把异常「吃掉」，调用方拿不到异常、以为执行成功。所以规范上不推荐在 finally 里写 return。

**场景**

这是面试常考的坑：finally 里写 return 会导致异常被吞、返回值被篡改，实际开发应避免。

**常见追问**

- finally 里 return 和 try 里 return 谁生效？（finally 的）
- finally 里 return 会吞异常吗？（会）

**易错点**

finally 里写 return 是坏习惯，会导致返回值混乱 + 异常丢失，面试问到时要点明「吞异常」这个后果。

## 86. 如何自定义业务异常？

**面试回答**

定义一个类继承 RuntimeException（或 Exception），通常加一个业务码字段，提供带消息和业务码的构造器，在业务校验失败时 throw。

**理解**

自定义异常一般继承 RuntimeException，这样方法不需要到处 `throws` 声明。为了配合全局异常处理，通常加 `code` 字段标识业务错误码，`message` 存友好提示。构造器重载：无参、只有 message、code + message 等。

**场景**

项目里定义 `BaseException extends RuntimeException`，带错误码和提示；下单时库存不足就 `throw new BaseException("库存不足")`，由 `@RestControllerAdvice` 统一捕获返回前端。

**常见追问**

- 继承 RuntimeException 还是 Exception？（一般 RuntimeException，免声明，配合全局处理）
- 为什么加 code 字段？（区分不同业务错误，前端可据此处理）

**易错点**

自定义异常继承 RuntimeException 是主流做法，继承 Exception 会让方法到处 throws，很啰嗦；实际项目几乎都用运行时异常。

## 87. 项目中为什么通常要定义统一业务异常？

**面试回答**

为了把「业务可预期的错误」和「系统未知异常」区分开，让全局异常处理器能统一识别、返回友好提示，而不是把底层异常直接抛给前端。

**理解**

业务异常（如库存不足、参数非法）是「正常业务规则被违反」，有明确的用户提示；系统异常（如空指针、数据库连接失败）是「代码或环境 bug」。定义统一的业务异常类后，全局异常处理器能针对它返回业务码和友好消息，其他异常返回通用错误。这样 Controller 不用到处 try-catch，代码更整洁（详见 [[07-项目/01-统一响应与异常处理]]）。

**场景**

项目里 `BaseException` 统一业务异常 + `@RestControllerAdvice` + `@ExceptionHandler` 配合，把异常转成统一响应结构返回前端。

**常见追问**

- 统一业务异常和全局异常处理怎么配合？（advice 里单独 @ExceptionHandler 捕获业务异常）
- 业务异常要记录日志吗？（通常记录，便于排查）

**易错点**

业务异常和系统异常要区分处理，业务异常返回友好提示、系统异常返回通用错误并记日志，别一股脑都返回「系统错误」。
