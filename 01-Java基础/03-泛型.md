# 泛型

## 35. Java 泛型是什么？

**面试回答**

Java 泛型用类型参数定义类、接口、方法和构造器，使同一份代码可在编译期针对不同引用类型进行类型检查，例如 `List<String>` 和 `Result<Order>`。Java 泛型主要通过擦除实现，不是运行时完全具体化的泛型。

**原理与理解**

类型参数可带边界，如 `<T extends Comparable<T>>`。使用泛型后，编译器检查写入和读取类型，并在擦除后的必要位置插入转换；参数化类型默认具有不变性，`List<String>` 不是 `List<Object>` 的子类型。

**成立条件与边界**

类型实参必须是引用类型，不能写 `List<int>`，要使用 `List<Integer>`。raw type 会绕过部分检查；反射、反序列化或不安全转换也可能让运行时值不符合声明。

**实际场景（通用工程）**

统一响应体使用 `Result<T>` 保留 data 的静态类型，集合使用 `List<Dish>` 避免取值后手工强转。

**常见追问**

- 泛型可以出现在哪里？（类、接口、方法和构造器声明）
- 为什么 `List<String>` 不能赋给 `List<Object>`？（参数化类型不变，否则可写入非 String）

**易错点**

不要说“泛型只是一种语法糖所以没有类型安全”；编译期约束是真实的，只是运行时表示主要采用擦除。

## 36. 为什么需要泛型？

**面试回答**

泛型把许多类型错误提前到编译期，减少显式强转，并让容器和算法在保持类型信息的同时复用。没有泛型的 raw 集合可混入不同类型，错误往往延迟到读取和强转时才暴露。

**原理与理解**

`List<String>` 的 `add` 只接受 String，`get` 的静态返回类型也是 String。相比 raw `List`，调用方不必反复强转，接口意图也更清楚。

**成立条件与边界**

泛型不能阻止所有运行时类型问题。raw type、未经检查的强转、可变参数泛型数组和反射都可能产生 heap pollution，最终仍可能抛 `ClassCastException`。

**实际场景（生产能力）**

公共 API 不暴露 raw List；构建时把 unchecked warning 视为需要审查的信号，只在边界封装并能证明安全时局部抑制。

**常见追问**

- 泛型主要解决什么？（静态类型安全、减少强转、复用）
- 有泛型为何仍可能 ClassCastException？（边界代码可能绕过或污染类型约束）

**易错点**

不要把“编译期检查”误说成“运行时绝不会类型错误”，也不要无理由使用 `@SuppressWarnings("unchecked")`。

## 37. 泛型有什么好处？

**面试回答**

核心好处有三点：让编译器尽早发现类型不匹配；让读取结果具有明确静态类型，减少手工强转；让数据结构和算法复用于多种类型，同时在签名中表达约束。

**原理与理解**

例如 `Comparator<T>` 明确比较器适用类型，`Optional<T>`、`Result<T>` 明确容器中的值类型。边界与通配符还能表达“可读取哪一类、可写入哪一类”。

**成立条件与边界**

泛型会增加复杂签名和类型推断难度；擦除也限制了 `new T()`、具体参数化类型的 `instanceof` 和泛型数组创建。API 设计应追求必要的类型表达，而不是参数越多越好。

**实际场景（通用工程）**

分页结果可定义为 `PageResult<T>`，既复用分页字段，又让 Controller 返回 `PageResult<OrderVO>` 时保留元素类型。

**常见追问**

- 泛型是否影响代码复用？（同一实现可服务多种引用类型）
- 泛型越复杂越好吗？（不是，可读性和调用体验同样重要）

**易错点**

回答“类型安全”后应说明安全发生在何时、能防住什么，以及 raw/unchecked 边界仍需治理。

## 38. 泛型类、泛型方法分别是什么？

**面试回答**

泛型类或接口在类型名后声明参数，如 `class Box<T>`；泛型方法在返回类型之前声明自己的类型参数，如 `static <T> T first(List<T> values)`。方法类型参数的作用域和类类型参数彼此独立。

**原理与理解**

创建 `Box<String>` 时为类参数 T 提供类型实参；调用泛型方法时，编译器通常根据实参和目标类型推断 T，也可显式指定。构造器同样可以声明自己的类型参数。

**成立条件与边界**

static 成员不属于某个 `Box<T>` 实例，不能直接使用类的 T；static 方法若需要类型参数，必须自己声明 `<T>`。方法声明中的 `<T>` 位于修饰符之后、返回类型之前。

**实际场景（通用工程）**

`Result<T>` 是泛型类；`<T> T requireNonNull(T value)` 是泛型方法。工具方法独立于对象类型时，方法级泛型通常更合适。

**常见追问**

- 泛型方法一定要返回 T 吗？（不需要，参数或内部约束使用 T 也可以）
- 类 T 与方法 T 是同一个吗？（方法重新声明同名 T 时是独立、且会遮蔽类参数）

**易错点**

只写 `public T get()` 而类或方法都未声明 T 会编译失败；`<T>` 也不能放在返回类型后。

## 39. `<?>` 是什么意思？

**面试回答**

`?` 是通配符，`List<?>` 表示“元素类型是某个未知具体类型的 List”。它能引用 `List<String>`、`List<Integer>` 等，但不等同于 `List<Object>`。

**原理与理解**

编译器会对未知类型做捕获转换。读取元素时只能安全地当 Object；不能添加任意非 null 值，因为调用方传入的实际元素类型可能不是该值的类型。

**成立条件与边界**

“只能读不能写”是便于记忆的近似说法：仍可读取、`clear`、移除元素、交换捕获后的元素，并可添加 null；限制的是不能安全添加任意非 null 新元素。`List<?>` 还是可具体化类型，可用于 `instanceof List<?>`。

**实际场景（通用工程）**

只关心集合大小、遍历输出或清空而不依赖元素具体类型的工具方法，可接收 `Collection<?>`，比 `Collection<Object>` 更通用。

**常见追问**

- `List<?>` 和 `List<Object>` 区别？（前者元素类型未知，后者明确为 Object）
- 为什么只能添加 null？（null 可转换为任意引用类型）

**易错点**

未知类型不等于 Object 类型；把 `List<String>` 当成 `List<Object>` 会破坏泛型不变性。

## 40. `<? extends T>` 和 `<? super T>` 有什么区别？

**面试回答**

`? extends T` 表示未知类型的上界是 T：可把读取结果当 T，但不能添加非 null 值。`? super T` 表示未知类型是 T 的某个父类型：可安全添加 T 或其子类型值，但读取时通常只能当 Object。常用口诀是 PECS：生产者 extends，消费者 super。

**原理与理解**

复制方法可写成 `copy(List<? extends T> src, List<? super T> dest)`：源集合生产 T，目标集合消费 T。通配符描述的是类型参数边界，不是集合对象本身只能执行读或写。

**成立条件与边界**

PECS 是 API 设计指南，不是 Java 语法的全部规则。`extends` 集合仍可删除或清空，`super` 集合也能读取，只是读取静态类型缺少比 Object 更具体的保证。

**实际场景（通用工程）**

批量把 `List<Integer>` 复制到 `List<Number>` 时，上述 src/dest 签名既安全又灵活；Comparator API 也常用 `? super T` 接收能比较 T 的父类型比较器。

**常见追问**

- extends 为什么不能 add T？（实际类型可能是 T 的更具体子类）
- super 为什么读取是 Object？（实际类型可能是 T 的任意父类型，唯一共同保证是 Object）

**易错点**

不要记成“extends 只读、super 只写”的绝对规则；应说清楚允许操作的静态类型边界。

## 41. 什么是泛型擦除？

**面试回答**

类型擦除是 Java 编译器把参数化类型映射到非参数化运行时表示的机制：参数化类型擦除为其原始泛型声明，类型变量擦除为最左边界，未显式限定时通常是 Object；编译器按需插入强转并生成桥接方法保持多态。

**原理与理解**

因此 `List<String>` 与 `List<Integer>` 的对象运行时类通常都是 List。桥接方法解决擦除后方法签名与重写关系的衔接；class 文件还可保留 Signature 等泛型元数据供反射读取。

**成立条件与边界**

“运行时完全没有泛型信息”过于绝对：声明上的泛型签名可能保留并被反射获取，但普通 `new ArrayList<String>()` 实例不会携带可供 `instanceof List<String>` 检查的具体类型实参。`List<?>` 是可具体化类型，`List<String>` 不是。

**实际场景（生产能力）**

JSON 反序列化嵌套泛型时需要 `TypeReference<List<Order>>() {}` 一类类型令牌保存声明信息；框架不能只靠 `List.class` 推断元素类型。

**常见追问**

- T 擦除成什么？（最左边界；无显式边界时通常 Object）
- 能否重载 `m(List<String>)` 和 `m(List<Integer>)`？（不能，擦除后签名冲突）
- 为什么不能 `new T[]`？（运行时数组需要可检查的具体组件类型）

**易错点**

不要把擦除说成“class 文件中一个泛型字符都没有”；应区分运行时对象的可具体化类型与声明处保留的签名元数据。
