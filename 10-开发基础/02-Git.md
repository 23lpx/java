# Git

## 550. Git 的基本提交流程是什么？

**面试回答**

基本流程：`git add` 把改动加入暂存区 → `git commit` 提交到本地仓库 → `git push` 推送到远程仓库。日常开发就是「改代码 → add → commit → push」这套循环。

**理解**

Git 分三个区域：工作区（改代码的地方）、暂存区（add 后）、本地仓库（commit 后）、远程仓库（push 后）。提交流程就是把改动从工作区一步步搬到远程：add 暂存、commit 提交、push 推送。push 前可能还要先 pull 同步远程最新代码。

**场景**

项目里改完功能后，`git add` 指定文件 → `git commit` 写提交说明 → `git push` 推到团队远程仓库。

**常见追问**

- 三个区域？（工作区、暂存区、本地仓库）
- 完整流程？（add → commit → push）

**易错点**

add 只是「暂存」、commit 只是「本地提交」，要推到远程必须 push；三者作用别混。

## 551. `git add` 是做什么的？

**面试回答**

git add 把工作区的改动添加到「暂存区」，标记这些文件要参与下一次提交；此时改动还没被提交，只是准备好了。

**理解**

git add 是「挑改动」：可以把某个文件、某几个文件或所有改动加入暂存区，也可以把文件里的部分改动加入。暂存区是工作区和本地仓库之间的缓冲，add 后这些内容才会在 commit 时被记录。没 add 的改动不会被 commit。

**场景**

项目里改了几个文件，`git add 某个文件` 只暂存想提交的那个，其他改动留着，实现选择性提交。

**常见追问**

- add 后改动提交了吗？（没有，只是暂存）
- 加所有改动用什么？（git add . 或 git add -A）

**易错点**

add 只是「暂存」，不是「提交」；只有 add 进暂存区的内容才会被 commit 记录。

## 552. `git commit` 是做什么的？

**面试回答**

git commit 把暂存区里的改动正式提交到本地仓库，形成一条新的提交记录（带提交说明），此时改动已保存到本地版本历史里，但还没推到远程。

**理解**

commit 是把「暂存区的内容」固化成一条历史记录，生成一个 commit（有哈希 ID、作者、时间、提交说明）。提交后本地仓库就有了这次版本快照，可以回溯。但 commit 只保存在本地，别人还看不到，需要 push 才到远程。

**场景**

项目里 `git commit -m "修复订单查询 bug"` 把暂存的改动提交到本地，写清楚改动说明。

**常见追问**

- commit 提交到哪？（本地仓库）
- 提交说明重要吗？（重要，帮助理解改动）

**易错点**

commit 是「提交到本地」，不是「推到远程」；要别人看到还得 push。提交说明要写清楚「为什么改」。

## 553. `git push` 是做什么的？

**面试回答**

git push 把本地仓库的提交推送到远程仓库（如 GitHub、GitLab），让团队其他人能看到和拉取你的代码，实现代码共享和备份。

**理解**

commit 只在本地，push 才把本地提交同步到远程仓库的分支上。push 后同事 pull 就能拿到你的改动。通常 push 到远端对应分支（如 push origin 分支名）。push 前如果远程有新提交，可能要先 pull 合并再 push。

**场景**

项目里本地完成开发提交后，`git push origin feature-xxx` 把分支推到远程，发起合并请求。

**常见追问**

- push 推送到哪？（远程仓库）
- 为什么需要 push？（共享、备份）

**易错点**

push 是「本地 → 远程」的最后一步；没 push，同事看不到你的 commit。

## 554. `git pull` 是做什么的？

**面试回答**

git pull 从远程仓库拉取最新的提交，并合并到当前本地分支，让本地代码和远程保持同步。

**理解**

pull 其实是「fetch + merge」的组合：先 fetch 拉取远程最新代码到本地，再 merge 把它合并到当前分支。日常开发前先 pull 同步，避免和同事的改动冲突、基于旧代码开发。

**场景**

项目里每天开工先 `git pull` 拉取团队最新代码，再开始开发，避免冲突和重复劳动。

**常见追问**

- pull 是哪个命令的组合？（fetch + merge）
- 什么时候 pull？（开发前同步远程最新代码）

**易错点**

pull = fetch + merge，会自动合并到当前分支；它既「拉取」又「合并」，不是单纯下载。

## 555. `git fetch` 和 `git pull` 有什么区别？

**面试回答**

fetch 只从远程下载最新提交到本地（更新远程跟踪分支），不修改你当前工作分支；pull = fetch + merge，在 fetch 之后还会把远程改动合并到当前分支。fetch 更安全，能先看再合。

**理解**

fetch 是「只下载不动你」：把远程最新代码拉到本地仓库的远程跟踪分支，但不碰你正在开发的分支。pull 是「下载并合并」：等于 fetch 之后自动执行 merge，把远程改动合进当前分支。所以 pull 可能产生冲突、改变工作区，fetch 则不会。

**场景**

项目里想先看看远程有什么新提交、再决定怎么合并时，用 fetch 查看；想直接同步就用 pull。

**常见追问**

- 谁更安全？（fetch，只下载不合并）
- pull 相当于什么？（fetch + merge）

**易错点**

关键区别：fetch 不合并、pull 会自动合并；「pull = fetch + merge」是必背结论。

## 556. Git 分支有什么作用？

**面试回答**

分支用于隔离不同的开发工作：可以在独立分支上开发新功能、修 bug，互不干扰，完成后再合并回主分支，避免直接在主干上改坏代码。

**理解**

分支是「并行的开发线」。主分支（master/main）保持稳定可发布，开发新功能就拉一条 feature 分支，在分支上随便改不影响主干，做完测试通过再 merge 回主干。分支让多人协作、功能隔离、版本管理成为可能。

**场景**

项目里每人拉自己的 feature 分支开发，完成合并到 develop/main，测试分支和发布分支分开，互不影响。

**常见追问**

- 分支解决什么？（隔离开发、并行协作）
- 主分支通常干嘛？（保持稳定、可发布）

**易错点**

分支核心是「隔离」：在分支上开发不影响主干，做完再合并；不是所有人都在一个分支上改。

## 557. `merge` 是什么？

**面试回答**

merge 是合并分支的操作：把另一个分支的改动合并到当前分支，让当前分支包含两者的内容，通常还会产生一个合并提交。

**理解**

merge 把源分支的提交整合进目标分支。如果目标分支没分叉，就「快进合并」直接移动指针；如果两边都有新提交，就生成一个「合并提交」把两边合到一起。冲突时需要手动解决。merge 是最常用的合并方式。

**场景**

项目里 feature 分支开发完，切到 develop 分支 `git merge feature-xxx`，把功能合入主开发线。

**常见追问**

- merge 干嘛？（合并分支）
- 有冲突怎么办？（手动解决后提交）

**易错点**

merge 是「把别的分支合进当前分支」；合并可能产生冲突，需要解决后再提交。

## 558. Git 冲突是什么？

**面试回答**

冲突指两个分支对同一个文件的同一处代码做了不同的修改，Git 无法自动决定保留哪一份，就标记为冲突，需要人工选择。

**理解**

当 Git 合并时发现同一位置有不同改动，它不知道该信谁，就把两边内容都写出来、用 `<<<<<<<` `=======` `>>>>>>>` 标记冲突区域，让你手动决定保留哪个（或都保留、或重新写）。冲突本身不是错误，是「需要人决策」的信号。

**场景**

项目里两个同事都改了同一个方法，后合并的人 pull/merge 时会遇到冲突，需手动解决。

**常见追问**

- 什么时候冲突？（同一位置不同修改）
- 冲突怎么体现？（文件里用标记标出两边内容）

**易错点**

冲突是「同位置不同改动，Git 无法自动合并」，需人工解决；它不代表代码坏了，但要小心别删错内容。

## 559. 遇到代码冲突一般怎么处理？

**面试回答**

先找到冲突文件，打开看标记区域，和同事沟通确认保留哪份（或整合两边），手动修改成正确代码，删除冲突标记，然后 git add 标记为已解决、再 commit 完成合并。

**理解**

处理步骤：①git status 找到冲突文件；②打开文件，找 `<<<<<<<`/`=======`/`>>>>>>>` 标记；③判断保留谁的改动（或融合），删掉标记、改好代码；④git add 该文件表示已解决；⑤git commit 完成合并。关键是要「沟通确认」，别擅自删掉别人的代码。

**场景**

项目里 merge 冲突后，和同事确认保留哪版逻辑，手动改好、add、commit，完成合并。

**常见追问**

- 冲突标记长什么样？（<<<<<<< ======= >>>>>>>）
- 解决后要干嘛？（add 然后 commit）

**易错点**

解决冲突要「沟通 + 手动改对 + 删标记 + add + commit」；最忌不沟通就删掉别人代码。

## 560. `git reset` 和 `git revert` 有什么区别？

**面试回答**

reset 是「回退」：把当前分支的提交记录往回退，丢弃某些提交，会改写历史；revert 是「反向提交」：生成一个新的提交来抵消某次提交的改动，保留完整历史。要撤销已推送的提交用 revert 更安全。

**理解**

reset 直接移动 HEAD 到之前的提交，被撤销的提交从历史里「消失」（--hard 连工作区改动一起丢），改写了历史，不适合已 push 的公共分支。revert 不删历史，而是创建一个「反向提交」把那次改动的效果抵消掉，历史还在，适合已推送的代码。

**场景**

项目里本地提交错了用 reset 回退；已推到远程的提交用 revert 抵消，避免改写公共历史。

**常见追问**

- 谁改写历史？（reset）谁保留历史？（revert）
- 已推送的提交用哪个？（revert）

**易错点**

reset 回退丢历史（本地用）、revert 反向提交保历史（公共分支用）；对已 push 的提交别乱 reset。
