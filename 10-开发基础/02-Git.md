# Git

## 550. Git 的基本提交流程是什么？

**面试回答**

先用 `git status` 和 `git diff` 检查工作区，再用 `git add` 把选中的内容写入暂存区，用 `git diff --cached` 核对待提交快照，`git commit` 创建本地提交，最后 `git push` 将本地分支提交推到远程并发起评审。

**原理与理解**

工作区是当前文件，暂存区/index 是下一次提交的候选快照，本地仓库保存提交对象与引用，远程仓库是另一份仓库。Git 提交记录的是快照及其父提交关系，不是简单把“文件从一个区域搬走”。

**成立条件与边界**

push 前不一定必须执行 pull；应先 fetch 并判断本地与远程关系，再按团队策略 merge、rebase 或 fast-forward。不要把无关改动一次性 `git add .`，也不要跳过测试和密钥检查。

**实际场景（通用工程）**

功能分支上只暂存目标 Markdown 文件，检查 staged diff，执行完整性脚本后提交并推送，再通过 PR 合并到 master。

**常见追问**

- 如何查看真正要提交的内容？——`git diff --cached`。
- commit 后别人能看到吗？——只有推到可共享的远程引用后才可以。
- 工作区干净是否代表已 push？——不代表，只说明没有未提交修改。

**易错点**

`add`、`commit`、`push` 分别操作 index、本地提交和远程引用，不能混为一步。

## 551. `git add` 是做什么的？

**面试回答**

`git add` 用工作区指定路径的当前内容更新暂存区，决定这些新增、修改或删除如何进入下一次提交。它不是提交，也不是单纯给文件打标记。

**原理与理解**

Git commit 从 index 生成树对象。因此同一文件在 add 后继续修改，会同时存在“已暂存版本”和“工作区新版本”；再次 add 才会把后续修改纳入候选快照。`git add -p` 可以按补丁块选择。

**成立条件与边界**

`git add -A` 更新整个工作树的新增、修改、删除；`git add .` 使用当前目录这个 pathspec，范围受所在目录影响。提交前必须用 status 和 cached diff 核对，避免误加入生成物或敏感文件。

**实际场景（通用工程）**

一个文件同时包含功能修改和临时调试代码时，用 `git add -p` 只暂存功能相关块，使提交保持单一目的。

**常见追问**

- add 后再改文件会怎样？——下一提交仍使用已暂存版本，除非再次 add。
- 如何取消暂存但保留工作区修改？——可用 `git restore --staged <path>`。
- 新文件不 add 会进入 commit 吗？——不会。

**易错点**

“只有 add 过的文件才提交”不够准确；真正提交的是 index 中那一版内容。

## 552. `git commit` 是做什么的？

**面试回答**

`git commit` 根据当前 index 创建一个新提交，记录项目树快照、父提交、作者/提交者信息和说明，并让当前分支引用指向它。默认只影响本地仓库。

**原理与理解**

提交是不可变对象，以内容寻址；分支是指向提交的可移动引用。文件内容相同的对象可复用，所以 Git 的语义是快照，内部也能高效存储与展示差异。

**成立条件与边界**

`git commit -a` 只自动暂存已跟踪文件的修改和删除，不包含未跟踪文件。`--amend` 会创建新提交替代分支末端，已共享提交上使用会改写历史并影响协作者。

**实际场景（通用工程）**

提交前核对 staged diff，把“一组可独立评审和回滚的改变”做成一个 commit，并在说明中写清改变目的而非只写“update”。

**常见追问**

- commit 是增量还是快照？——语义上是项目树快照，并引用父提交。
- amend 是否原地修改旧提交？——不是，会产生新的提交 ID。
- commit 后怎样撤销共享分支上的错误？——通常优先 revert。

**易错点**

工作区没有改动不代表远程已有该 commit，也不要把 commit ID 当永久不变的版本号。

## 553. `git push` 是做什么的？

**面试回答**

`git push` 将本地对象发送到远程，并请求更新指定远程引用，例如让 `origin/feature` 指向本地 `feature` 的最新提交。远程通常只接受满足权限和快进/保护规则的更新。

**原理与理解**

常见 `git push -u origin feature` 同时设置上游跟踪关系。若远程分支包含本地没有的提交，普通 push 通常因 non-fast-forward 被拒绝，防止覆盖远程历史。

**成立条件与边界**

push 不是备份全部本地状态：未提交改动、未推送的其他分支和 stash 不会自动上传。需要改写远程历史时，`--force-with-lease` 比 `--force` 更能检测意外的远程推进，但共享分支仍应慎用。

**实际场景（通用工程）**

本地功能完成后推送独立分支，通过受保护 master 的 PR 检查和评审，而不是直接强推 master。

**常见追问**

- push 被拒绝怎么办？——先 fetch，检查分叉并按团队策略整合，不能直接强推。
- `-u` 做什么？——设置本地分支的上游跟踪关系。
- push 会上传工作区修改吗？——不会，只传相关 Git 对象和更新引用。

**易错点**

`origin` 只是常见远程名，不是 Git 固定关键字；push 也不等于合并到主分支。

## 554. `git pull` 是做什么的？

**面试回答**

`git pull` 先从远程 fetch，再把获取的目标分支整合进当前分支。整合方式可配置为 merge、rebase 或只允许 fast-forward，因此不能简单定义为“拉取并合并”。

**原理与理解**

pull 是组合命令：先更新远程跟踪引用，再根据参数执行 `git merge FETCH_HEAD` 或 rebase 等操作。它可能直接改变当前分支和工作区，并可能产生冲突。

**成立条件与边界**

本地有未提交修改时应先判断是否会干扰整合。团队应显式约定 `--rebase`、`--no-rebase` 或 `--ff-only`，避免不同成员得到意外历史形态；不确定时先单独 fetch 更容易审查。

**实际场景（通用工程）**

更新长期分支时先执行 `git fetch origin` 查看差异；确认只需要快进时使用 `git pull --ff-only`，若已分叉则按团队规则处理。

**常见追问**

- pull 一定产生 merge commit 吗？——不一定，可能快进或 rebase。
- 如何中止冲突中的整合？——merge 使用 `git merge --abort`，rebase 使用 `git rebase --abort`。
- pull 会更新哪个分支？——由当前分支的上游和显式 refspec 决定。

**易错点**

不要在不清楚当前分支、上游和本地修改时机械执行 pull。

## 555. `git fetch` 和 `git pull` 有什么区别？

**面试回答**

fetch 下载远程对象并更新远程跟踪引用，通常不改当前分支和工作区；pull 在 fetch 后继续把远程变化整合进当前分支。因此 fetch 适合“先看再决定”，pull 适合策略明确的一步同步。

**原理与理解**

执行 fetch 后，可用 `git log HEAD..origin/main`、`git diff HEAD...origin/main` 等查看远程变化，再自行选择 merge、rebase 或不处理。远程跟踪分支不是远程服务器本身，而是本地对上次获取状态的记录。

**成立条件与边界**

fetch 也会写本地仓库中的引用和对象，所以不是完全“什么都不改”；它只是通常不改当前工作树。pull 的具体行为受配置和命令参数影响。

**实际场景（通用工程）**

准备创建 PR 前先 fetch master，确认功能分支是否落后；必要时整合 master 并测试，减少合并时冲突。

**常见追问**

- fetch 后代码文件会自动变成远程版本吗？——当前工作区通常不会。
- origin/main 是远程实时状态吗？——不是，只是最近 fetch 得到的本地跟踪引用。
- 哪个更安全？——fetch 更便于先审查，但最终仍需正确整合。

**易错点**

不要把 fetch 说成“只下载文件”；它获取的是对象并更新约定的引用。

## 556. Git 分支有什么作用？

**面试回答**

Git 分支是指向某个提交的可移动引用，用于让功能、修复或实验拥有独立的提交链，并通过 merge、rebase 或 PR 再整合。创建分支通常很轻量，因为不是复制整份项目。

**原理与理解**

HEAD 通常指向当前分支，提交后该分支引用前移。不同分支可以共享祖先和对象，只记录各自后续提交，从而支持并行开发和清晰评审。

**成立条件与边界**

分支不是天然隔离环境：工作区仍只有当前 checkout 的版本，后端数据库、配置和部署资源也不会随 Git 分支自动隔离。长期分支越多，整合和维护成本越高。

**实际场景（通用工程）**

从最新 master 创建 `feature/order-query`，只提交订单查询修改，经 CI 和评审后合并，紧急修复则使用独立 hotfix 分支。

**常见追问**

- 分支是否复制全部文件？——不是，主要是一个指向提交的引用。
- 删除分支会删除提交吗？——若提交仍被其他引用或 reflog 可达，不会立即消失。
- HEAD 是什么？——当前检出位置的符号引用或具体提交。

**易错点**

“分支互不影响”只适用于提交历史组织，不代表共享外部环境也互不影响。

## 557. `merge` 是什么？

**面试回答**

`git merge` 将一个或多个提交历史的变化整合到当前分支。若当前分支只是落后，可能 fast-forward；若双方已分叉，通常创建含多个父提交的 merge commit，也可能遇到冲突。

**原理与理解**

三方合并以共同祖先、当前分支 tip 和待合并分支 tip 为输入，计算双方相对祖先的变化。没有冲突不代表业务逻辑一定正确，只表示 Git 能自动组合文本或树变化。

**成立条件与边界**

`--no-ff` 可强制保留 merge commit，`--ff-only` 只允许快进；策略由团队历史规范决定。merge 不会自动运行测试，也不会自动发现跨文件的语义冲突。

**实际场景（通用工程）**

PR 合并功能分支后保留 merge commit，以便从主线看出该功能的提交集合；合并前仍需 CI 验证。

**常见追问**

- fast-forward 是什么？——当前分支没有独有提交，引用可直接前移。
- merge 和 rebase 的核心区别？——merge 保留分叉拓扑；rebase 复制提交到新基底并改写其 ID。
- 无冲突是否代表安全？——不代表，还需编译、测试和评审。

**易错点**

merge 的方向取决于当前分支；“把 A 合到 B”前必须先确认当前所在分支。

## 558. Git 冲突是什么？

**面试回答**

冲突是 Git 在 merge、rebase、cherry-pick 等操作中无法自动决定最终内容或树结构的状态，例如双方修改同一区域、一个删除而另一个修改，或同名文件各自新增。

**原理与理解**

Git 会把可自动合并的部分先合并，对冲突路径在 index 中保留不同阶段的版本，并在文本文件中写入冲突标记供人工选择。冲突是历史整合问题，不等于某个人“代码写错了”。

**成立条件与边界**

没有文本冲突仍可能有语义冲突，例如双方分别改动不同文件却共同破坏接口契约。二进制文件通常难以逐行合并，需要选定版本或借助专用工具。

**实际场景（通用工程）**

两个分支分别修改同一份配置的相邻规则，Git 标记冲突；开发者需理解两边目的，生成同时满足需求的最终配置并测试。

**常见追问**

- 哪些操作可能产生冲突？——merge、rebase、cherry-pick、revert、stash apply 等。
- 冲突标记是什么？——工作区中的 ours、分隔线和 theirs 区段，需要清理。
- 谁应该解决冲突？——了解双方变更意图的人共同确认。

**易错点**

冲突不是简单“保留最新时间的文件”，也不能一律选择 ours 或 theirs。

## 559. 遇到代码冲突一般怎么处理？

**面试回答**

先停止继续叠加修改，用 `git status` 确认冲突操作和文件；阅读双方提交意图，编辑出正确最终内容，删除冲突标记，执行 `git add` 标记已解决，再按提示 commit 或 `rebase --continue`，最后运行测试并检查 diff。

**原理与理解**

解决冲突是在构造一个新的、同时满足两边意图的快照。工具提供 ours/theirs 只是候选输入，不知道业务契约，因此人工判断和验证不可省略。

**成立条件与边界**

若发现基底、分支或策略错误，应使用对应 `--abort` 回到操作前，而不是在错误方向上硬解。rebase 中 ours/theirs 的直觉可能与 merge 不同，使用前要确认上下文。

**实际场景（通用工程）**

Markdown 两边都新增题目时，按题号和目录规则合并内容，运行 Obsidian 完整性脚本，确认标题、Wikilink 和总题数未被破坏。

**常见追问**

- 解决后为什么还要 add？——告诉 index 该路径的最终版本已确定。
- 如何确认仍有冲突？——查看 `git status`，也可搜索残留标记。
- 解决完为何必须测试？——Git 只能处理文本，不能验证业务语义。

**易错点**

不要通过删除对方整段代码来“消除标记”；冲突解决的目标是正确结果，不是让 status 变绿。

## 560. `git reset` 和 `git revert` 有什么区别？

**面试回答**

reset 移动当前分支/HEAD，并按模式选择是否重置 index 和工作区，常用于整理尚未共享的本地历史；revert 根据指定提交创建一个新的反向提交，不删除原历史，更适合撤销已共享分支上的改变。

**原理与理解**

`reset --soft` 仅移动引用、保留 index 和工作区；`--mixed` 还重置 index；`--hard` 进一步让工作区匹配目标提交。revert 则对目标提交的变更求逆并正常追加新提交，复杂变更可能冲突。

**成立条件与边界**

`reset --hard` 会丢弃未保存的工作区和暂存修改，执行前必须精确确认目标。revert merge commit 需要指定主父线，且会影响未来再次合并的语义，不能机械操作。

**实际场景（通用工程）**

本地最后一次提交尚未 push 且需要重新拆分，可 soft/mixed reset 后重做；错误已合并到 master，则通过 revert PR 留下可审计撤销记录。

**常见追问**

- 哪个会改写分支历史？——reset 会移动引用；revert 追加新历史。
- reset 一定删除文件修改吗？——不一定，取决于 soft、mixed、hard 和具体形式。
- revert 能保证无冲突吗？——不能，后续代码已变化时仍可能冲突。

**易错点**

不要把 reset 简化为“回退版本”、revert 简化为“删除提交”；二者对引用、index、工作区和历史的影响不同。
