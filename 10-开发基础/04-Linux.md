# Linux

## 572. `ls` 有什么作用？

**面试回答**

`ls` 列出指定目录项；不传路径时列出当前目录。常用 `-l` 显示长格式，`-a` 包含以点开头的名称，`-h` 将大小显示为易读单位，可组合为 `ls -lah`。

**原理与理解**

ls 读取目录项并按选项排序、格式化。默认输出通常不包含 `.` 开头的名称；`-d` 可查看目录本身而不是展开其内容，`-t` 可按修改时间排序。

**成立条件与边界**

输出受实现、别名、区域和终端格式影响，不适合让脚本可靠解析文件名；脚本遍历应使用 shell 安全写法或 `find -print0` 等接口。`-h` 通常需与 `-l`、`-s` 等产生大小字段的选项配合才有可见效果。

**实际场景（通用工程）**

部署目录中使用 `ls -lah` 查看 jar、配置和日志的权限与大小，再用 `stat` 获取需要精确判断的文件元数据。

**常见追问**

- 如何显示隐藏名称？——`ls -a`。
- 如何查看目录自身信息？——`ls -ld <dir>`。
- ls 适合脚本解析吗？——通常不适合，文件名和格式都可能造成歧义。

**易错点**

点文件并不是真的“隐藏属性”，只是 ls 默认省略以点开头的名称。

## 573. `cd` 有什么作用？

**面试回答**

`cd` 改变当前 shell 的工作目录。常用 `cd <path>`、`cd ..`、`cd -` 返回前一个目录，`cd` 或 `cd ~` 进入用户主目录。

**原理与理解**

当前目录属于进程状态，所以 cd 必须是 shell 内建命令；如果启动一个外部进程执行 chdir，它只能改变自己的目录，无法修改父 shell。

**成立条件与边界**

相对路径基于当前目录，绝对路径从根开始。进入目录需要相应目录的执行/搜索权限；`~` 是 shell 展开，脚本中不要假设所有用户主目录相同。

**实际场景（通用工程）**

排查部署时先 `cd /srv/app`，立即用 pwd 确认位置，再执行只针对该目录的只读命令，避免在错误目录操作。

**常见追问**

- 为什么 cd 通常没有独立可执行文件？——外部进程不能改变父 shell 的工作目录。
- `cd -` 做什么？——切换到上一个工作目录。
- `cd ..` 一定是物理父目录吗？——还会受到 shell 的逻辑路径和符号链接处理方式影响。

**易错点**

不要在脚本中写死个人主目录，也不要把 `~` 与文件系统根目录 `/` 混淆。

## 574. `pwd` 有什么作用？

**面试回答**

`pwd` 输出当前工作目录。常见 `-L` 输出 shell 维护的逻辑路径，可能保留符号链接；`-P` 输出解析符号链接后的物理路径。

**原理与理解**

shell 可通过 `PWD` 维护逻辑目录串，而操作系统记录当前目录对象。因此经过符号链接进入目录后，逻辑路径和物理路径可能不同。

**成立条件与边界**

“pwd 永远输出唯一真实绝对路径”不准确：bind mount、命名空间、符号链接和已删除目录都会影响路径理解。脚本若关心物理位置应显式使用 `pwd -P` 并处理失败。

**实际场景（通用工程）**

发布脚本开始时记录 `pwd -P` 和目标文件校验信息，防止从符号链接指向的错误版本目录执行覆盖操作。

**常见追问**

- `-L` 和 `-P` 区别？——逻辑路径与解析符号链接后的物理路径。
- pwd 与 `echo "$PWD"` 一定相同吗？——通常相近，但环境变量可能失真，行为也受 shell 影响。
- 为什么部署前要 pwd？——确认命令作用范围。

**易错点**

看到相同文件内容不代表两个路径字符串指向不同对象；应理解符号链接和挂载边界。

## 575. 如何查看文件内容？

**面试回答**

小文本可用 `cat file`；交互分页与搜索用 `less file`；只看开头或末尾用 `head -n N`、`tail -n N`。先根据文件大小、格式和目标选择命令，避免把大文件一次性输出到终端。

**原理与理解**

cat 顺序复制内容到标准输出；less 按需读取并支持翻页、搜索；head/tail 只选择首尾部分。命令可通过管道组合，但没有必要写 `cat file | grep pattern`，可直接 `grep pattern file`。

**成立条件与边界**

这些工具不理解任意二进制格式，直接打印二进制可能扰乱终端。读取仍受文件权限、文件变化和编码影响；超大或压缩日志应使用对应工具，如 `zgrep`、`zless`。

**实际场景（通用工程）**

先 `ls -lh app.log` 判断大小，再 `tail -n 200 app.log` 查看近期记录，需要上下文时用 less 搜索 requestId。

**常见追问**

- less 如何搜索和退出？——`/关键字` 搜索，`n` 下一个，`q` 退出。
- 如何看前 20 行？——`head -n 20 file`。
- 为什么少用 cat 看大日志？——会刷屏、产生大量 I/O，且难以定位。

**易错点**

“查看文件”不只有 cat，命令应匹配文件大小与排查目标。

## 576. 如何实时查看日志？

**面试回答**

普通文件可用 `tail -f app.log` 持续读取追加内容；日志可能滚动或被重新创建时，GNU tail 的 `tail -F app.log` 更适合，它等价于按名称跟随并重试。systemd 服务可用 `journalctl -u service -f`。

**原理与理解**

`-f` 默认跟随已打开的文件描述对象；文件重命名后它可能继续读旧文件。`-F` 按文件名重试打开，更能跨越常见日志轮转，但具体轮转方式仍需验证。

**成立条件与边界**

“实时”只是接近实时，受应用缓冲、采集、文件系统和网络影响。高流量日志直接跟随会淹没有效信息，可先按 requestId、级别或实例过滤；远程容器还要考虑日志所在命名空间。

**实际场景（生产能力）**

复现接口问题前运行 `journalctl -u order.service --since "5 min ago" -f`，同时按 requestId 过滤，完成后退出并保存必要时间范围。

**常见追问**

- `-f` 与 `-F` 区别？——前者通常跟随描述符，后者更关注同名文件并重试。
- 容器日志怎么看？——使用平台日志命令或集中检索，不能假设宿主固定文件路径。
- 为什么日志没有立刻出现？——应用或采集链路可能缓冲。

**易错点**

轮转后没有新日志时，不要先断定应用停止；先确认 tail 是否仍跟随旧 inode。

## 577. 如何搜索日志中的关键字？

**面试回答**

使用 `grep`：`grep -n "pattern" app.log` 显示行号，`-i` 忽略大小写，`-F` 按固定字符串匹配，`-E` 使用扩展正则，`-C N` 带上下文，递归搜索可用 `grep -r`。

**原理与理解**

grep 默认把 pattern 当基本正则表达式，不是普通字符串；含 `.`、`[` 等字符时会产生正则语义。确定只查字面值时用 `-F -- "text"` 更清晰，`--` 可防止以连字符开头的模式被当选项。

**成立条件与边界**

关键字可能跨行、日志可能压缩或为结构化 JSON，简单 grep 未必足够。高基数字段和多实例链路更适合集中日志平台；处理敏感日志时注意命令历史和输出权限。

**实际场景（通用工程）**

`grep -nF -C 3 -- "requestId=abc" app.log` 查看目标请求及前后文，再按时间与下游错误继续缩小范围。

**常见追问**

- `-F` 与 `-E`？——固定字符串与扩展正则。
- 如何统计匹配行数？——`grep -c`；若关心实际事件数需确认一事件是否跨多行。
- 如何查压缩日志？——使用 zgrep 或先由安全工具解压读取。

**易错点**

不要忘记给包含空格或 shell 特殊字符的模式加引号。

## 578. 如何查看当前运行的 Java 进程？

**面试回答**

通用系统视角可用 `pgrep -af java` 或 `ps -ef | grep '[j]ava'`；JDK 工具 `jps -l` 可列出其能发现的 JVM 及主类/jar 信息。确认目标后再查看完整命令行、用户、PID 和启动时间。

**原理与理解**

ps/pgrep 查询操作系统进程，jps 依赖 JVM 的本地监控发现机制，因此两者可见范围和展示字段不同。容器、PID namespace、用户权限以及禁用性能数据都可能影响结果。

**成立条件与边界**

进程命令行可能被截断或包含 java 字样但不是目标服务，jps 也不保证列出所有 JVM。不要仅凭名称执行 kill；还应核对端口、工作目录、启动参数或 service/container 身份。

**实际场景（生产能力）**

先 `pgrep -af java` 找候选 PID，再用 `ps -p PID -o pid,ppid,user,lstart,args` 和 `ss -lntp` 验证是否为目标应用。

**常见追问**

- jps 为什么看不到进程？——用户/命名空间不同、监控数据不可用或 JVM 参数限制。
- 如何避免 grep 把自身列出来？——用 pgrep，或 `grep '[j]ava'`。
- Java 进程高 CPU 下一步？——结合 top/pidstat、线程 dump/JFR，不能只看进程列表。

**易错点**

PID 会复用；执行操作前必须重新确认进程身份。

## 579. 如何查看端口占用？

**面试回答**

Linux 常用 `ss -lntp` 查看 TCP 监听端口及进程，指定端口可用 `ss -lntp 'sport = :8080'`；也可用 `lsof -nP -iTCP:8080 -sTCP:LISTEN`。查看 UDP 时改用相应 `-u` 选项。

**原理与理解**

端口属于网络命名空间中的 socket。`LISTEN` 表示服务端监听 socket，已建立连接则是另一类状态；“端口被占用”需要先区分协议、地址族和绑定地址。

**成立条件与边界**

查看其他用户进程信息可能需要权限。`127.0.0.1:8080`、`0.0.0.0:8080`、IPv6 绑定的冲突关系受系统 socket 选项影响；容器内外还可能经过端口映射，不能只看一个命名空间。

**实际场景（通用工程）**

应用启动报 address already in use 时，使用 ss 确认监听地址、协议和 PID，再核对它属于旧实例还是其他服务，不能直接杀进程。

**常见追问**

- netstat 与 ss？——现代 Linux 通常优先 ss；不同系统可用工具不同。
- 为什么看到连接却没有监听？——可能是客户端临时端口或已建立连接，不是服务监听。
- 容器映射端口怎么看？——同时检查容器内监听和宿主的映射规则。

**易错点**

只搜索数字 8080 可能匹配远端端口或客户端连接，应明确 LISTEN、协议和本地地址。

## 580. 如何结束一个进程？

**面试回答**

先确认 PID 和服务身份，再发送可处理的终止信号，例如 `kill -TERM PID`；给进程时间完成停止并验证端口/进程状态。只有进程失去响应且可接受数据损失时，才把 `kill -KILL PID` 作为最后手段。

**原理与理解**

`kill` 的本质是发送信号，不保证进程已经退出。SIGTERM 可被进程捕获以完成拒绝新请求、等待在途任务、刷新状态和释放资源；SIGKILL 不能被捕获或忽略，由内核直接终止。

**成立条件与边界**

信号权限受进程所有者和能力控制。通过 systemd、容器编排或进程管理器启动的服务，应优先用对应管理命令，否则管理器可能自动拉起新进程；向错误或已复用 PID 发信号风险很高。

**实际场景（生产能力）**

使用 `systemctl stop order.service` 触发优雅关闭，观察日志和健康检查；超时后再按运维规范升级处理，并确认没有未完成支付或消息任务。

**常见追问**

- kill 默认发送什么？——通常是 SIGTERM。
- `kill -9` 有什么风险？——无法执行应用清理，可能中断写入或在途请求。
- 如何确认已结束？——重新检查 PID、服务状态和监听端口。

**易错点**

不要把 `kill -9` 当日常停止命令，也不要从旧日志复制 PID 直接执行。

## 581. `chmod` 是什么？

**面试回答**

`chmod` 修改文件或目录的 mode bits，主要包括 user、group、other 的读写执行权限，以及 setuid、setgid、sticky 等特殊位。可用符号形式 `chmod u+x file`，也可用八进制形式 `chmod 640 file`。

**原理与理解**

八进制中 r=4、w=2、x=1，每一位分别组合 user/group/other 权限；例如 640 表示所有者读写、组只读、其他无权限。chmod 改权限位，修改所有者或组应使用 chown/chgrp。

**成立条件与边界**

是否允许访问还可能受 ACL、SELinux/AppArmor、只读挂载、文件能力和父目录权限影响。递归 chmod 风险很高，文件与目录通常需要不同的执行位策略。

**实际场景（通用工程）**

配置文件设为 640，并让服务用户属于相应组；启动脚本单独增加执行位，而不是对整个部署目录执行 `chmod -R 777`。

**常见追问**

- 755 表示什么？——所有者 rwx，组和其他 r-x。
- chmod 与 chown 区别？——前者改 mode bits，后者改所有者/组。
- 目录的 x 是什么？——允许搜索/穿越目录项。

**易错点**

777 不是“解决权限问题”的安全方案；先判断需要哪类主体执行哪种操作。

## 582. Linux 文件权限分别表示什么？

**面试回答**

权限通常按 user、group、other 三组展示，每组包含 r、w、x。对普通文件，r 是读内容，w 是修改内容，x 是尝试执行；对目录，r 是读取目录项名称，w 是增删/重命名目录项，x 是搜索和穿越目录。

**原理与理解**

`ls -l` 首字符表示文件类型，后九位如 `rwxr-x---` 对应三组权限。八进制按 r=4、w=2、x=1 求和，例如 750 表示所有者 rwx、组 r-x、其他无权限。

**成立条件与边界**

目录权限要组合理解：有 r 无 x 可能列出名称却无法访问元数据；删除文件通常取决于父目录的 w+x，而不只看文件自身 w。root、ACL、capabilities 和安全模块还能改变最终授权结果。

**实际场景（通用工程）**

日志目录需要服务用户拥有目录 w+x 才能创建或轮转文件；只给现有日志文件写权限，却不给目录权限，轮转仍可能失败。

**常见追问**

- 文件 x 和目录 x 有何区别？——文件表示可执行许可，目录表示搜索/穿越。
- 为什么只读文件仍可能被删除？——删除改变父目录项，主要看父目录权限。
- sticky bit 用在哪里？——共享可写目录中限制用户删除或重命名他人的条目，如 `/tmp`。

**易错点**

不要把 r/w/x 在文件和目录上的语义完全等同，也不要只看九位权限就忽略 ACL 和安全策略。
