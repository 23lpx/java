# 部署基础

## 621. Docker 是什么？

**面试回答**

Docker 是构建、分发和运行容器化应用的平台。镜像描述应用文件系统与默认运行配置，Docker Engine 根据镜像和启动参数创建容器；容器是在共享操作系统内核上运行的相对隔离进程环境。

**原理与理解**

Docker Client 通过 API 与 daemon 交互，daemon 管理 image、container、network、volume 等对象。在 Linux 上，namespace 提供进程、网络等视图隔离，cgroup 控制与统计资源；macOS/Windows 的 Linux 容器通常运行在 Docker Desktop 管理的 Linux VM 中。

**成立条件与边界**

容器不是虚拟机，也不是没有操作系统依赖的“万能包”。它共享宿主或 VM 内核，隔离强度受权限、capability、seccomp、挂载和运行时配置影响；默认配置不等于安全沙箱。

**实际场景（通用工程）**

把 Spring Boot jar、JRE 和启动命令构建成版本化镜像，运行时通过环境变量/Secret 注入配置并挂载持久卷，而不是把生产密码写入镜像层。

**常见追问**

- Docker Engine 包含什么？——daemon、API 与 CLI 等组件。
- 容器为什么轻量？——不为每个实例启动完整客体内核，主要运行隔离进程和所需用户空间。
- Docker Desktop 与 Linux Engine 一样吗？——使用体验相近，但桌面系统常通过 VM 提供 Linux 内核。

**易错点**

不要说“Docker 把运行中的应用打包成容器”；通常先构建镜像，再由镜像创建容器。

## 622. Docker 解决什么问题？

**面试回答**

Docker 把应用及其用户空间依赖封装为可版本化镜像，统一构建与交付单元，减少环境漂移，并提供进程隔离、资源限制、网络和存储挂载等标准接口，使部署、回滚和扩容更可自动化。

**原理与理解**

同一镜像 digest 可在开发、测试和生产被验证与运行，避免每台机器手工安装不同依赖。镜像分层便于复用和分发，Registry 负责存储版本，编排平台再负责调度多个容器。

**成立条件与边界**

“同一镜像”不等于结果绝对相同：CPU 架构、内核、外部配置、数据库、网络、时区和存储仍会影响行为。Docker 本身也不自动提供跨主机编排、弹性扩缩、零停机发布或应用高可用。

**实际场景（生产能力）**

CI 从固定基础镜像构建并扫描制品，以 digest 部署；配置和数据外置，回滚时切回已验证 digest，而不是在运行容器中手工改文件。

**常见追问**

- Docker 是否解决所有环境问题？——只控制镜像内和部分运行配置，外部依赖仍需治理。
- 容器能否替代 CI/CD？——不能，它提供制品和运行单元，流水线负责测试与发布。
- 扩容是否等于多执行几次 docker run？——单机可增加实例，生产还需调度、发现、负载均衡和容量控制。

**易错点**

“一次构建、到处运行”需要平台、架构和配置满足条件，不能理解为跨任何 CPU/内核都无差别运行。

## 623. 镜像和容器有什么区别？

**面试回答**

镜像是不可变、可分发的分层模板，由内容摘要标识；容器是镜像加运行时配置创建出的可运行实例，拥有进程、网络、挂载及通常的可写容器层。同一镜像可创建多个状态彼此独立的容器。

**原理与理解**

镜像层可被多个容器共享，容器运行时的文件修改通常写入单独的 writable layer。删除容器后，未放入 volume、bind mount 或外部服务的数据会随容器可写层消失。

**成立条件与边界**

“类和对象”只能帮助入门：镜像还包含文件层、元数据和默认命令，容器由镜像与启动参数共同定义。运行中修改容器不会自动修改原镜像；commit 容器虽然可生成新镜像，但不应替代可审计 Dockerfile 构建。

**实际场景（通用工程）**

三个应用实例从同一 digest 启动，日志写 stdout，业务附件写对象存储或 volume；升级时构建新镜像并替换容器，而非 ssh 进去覆盖 jar。

**常见追问**

- 容器删除后数据一定丢吗？——容器可写层会丢，外部 volume/bind mount 数据按其生命周期保留。
- 镜像能运行吗？——镜像本身是模板，创建容器后才有进程。
- tag 与 digest 区别？——tag 可移动，digest 对应具体内容。

**易错点**

不要把镜像说成“包含所有生产配置”，敏感与环境配置通常应在运行时外置。

## 624. Nginx 是什么？

**面试回答**

Nginx 是事件驱动的 Web 服务器和代理软件，可处理 HTTP/HTTPS，也可通过相应模块代理 TCP/UDP、FastCGI、gRPC 等流量。Java 后端常用它提供静态资源、TLS 入口、反向代理和负载均衡。

**原理与理解**

Nginx 由 master 管理配置与 worker，worker 通过事件循环处理大量连接，避免简单的一连接一线程模型。作为反向代理，它终止客户端连接并按配置建立/复用到 upstream 的连接。

**成立条件与边界**

“高性能、低内存”不是对所有负载的无条件保证，TLS、缓存、日志、响应大小、磁盘与模块都会影响容量。Nginx 通常不运行 Java 业务逻辑，也不自动理解应用事务和用户状态。

**实际场景（通用工程）**

在入口配置 HTTPS、请求大小、超时和转发头，把 `/api/` 转发到后端实例组，静态文件由单独 location 处理，并记录 upstream 状态与耗时。

**常见追问**

- Nginx 是应用服务器吗？——通常作为 Web/代理入口，不执行 Spring Boot 业务代码。
- event-driven 有什么价值？——少量 worker 可并发管理大量 I/O 连接。
- Nginx 能代理非 HTTP 吗？——可通过 stream 等模块处理 TCP/UDP，具体依构建与配置。

**易错点**

不要只说“一个进程处理所有连接”；Nginx 通常有 master 与多个 worker，进程数和模型可配置。

## 625. Nginx 常见用途有哪些？

**面试回答**

常见用途包括静态资源服务、反向代理、HTTP/TCP/UDP 负载均衡、TLS 终止、缓存、压缩、限流、访问控制和请求头改写。实际应让入口职责清晰，避免把所有业务规则堆进配置。

**原理与理解**

`server` 与 `location` 选择请求处理配置，`proxy_pass` 转发到上游，`upstream` 定义实例组和负载策略；缓存、限速、TLS 与日志分别由对应模块完成。

**成立条件与边界**

功能是否可用取决于开源/商业版本、编译模块和配置。Nginx 不是默认 WAF，也不会自动做服务发现、证书续期、健康探测和一致性会话；这些可能需要外部控制器或其他产品配合。

**实际场景（生产能力）**

入口只负责 TLS、静态文件、路由、基本限流与转发，鉴权和业务授权仍由应用或专用网关负责；变更配置先执行 `nginx -t` 再平滑 reload。

**常见追问**

- 静态资源为什么适合 Nginx？——直接文件服务和事件 I/O 能减少应用层负担。
- reload 会怎样？——新 worker 使用新配置，旧 worker 尝试完成已有连接；仍需验证长连接等边界。
- Nginx 与 API Gateway 一样吗？——能力有重叠，但网关常提供更强的 API、认证和治理集成。

**易错点**

“支持某能力”不等于默认启用或自动安全，尤其是缓存、真实客户端 IP 和限流必须正确配置信任边界。

## 626. 什么是反向代理？

**面试回答**

反向代理位于服务端入口，代表一个或多个上游接收客户端连接，再把请求转发给选定后端并将响应返回。客户端面向代理地址，不必知道实际实例；正向代理则代表客户端访问外部目标。

**原理与理解**

代理通常终止一段连接并创建或复用另一段 upstream 连接，因此可以做路由、TLS 终止、头部改写、缓存和负载均衡。转发后端时应明确 Host、X-Forwarded-For 或标准 Forwarded 等信息。

**成立条件与边界**

反向代理隐藏拓扑但不是天然安全边界；后端仍需网络隔离、认证和授权。超时与重试配置必须考虑请求幂等性，代理重试 POST 等写操作可能产生重复副作用。

**实际场景（生产能力）**

客户端只访问 `api.example.com`，Nginx 按路径转到不同服务；应用仅信任来自受控代理的客户端 IP 头，并对写请求关闭不安全的自动重试。

**常见追问**

- 正向与反向代理区别？——分别代表客户端和服务端。
- 后端如何获取原客户端信息？——通过受信代理设置的转发头或 PROXY protocol。
- 代理是否只是“原样转发”？——不是，连接、协议、头部、缓存和超时都可能被处理。

**易错点**

直接信任任何客户端传来的 `X-Forwarded-For` 会被伪造，必须定义可信代理链。

## 627. 什么是负载均衡？

**面试回答**

负载均衡把请求按策略分配到多个健康后端实例，以提高整体容量、减少单实例热点并支持故障摘除。Nginx HTTP upstream 默认可轮询，也支持权重、least_conn、ip_hash、hash 等策略。

**原理与理解**

负载器维护后端集合，结合算法、连接状态和健康信息选取实例。无状态服务最易横向分发；有会话状态时可使用共享会话、外部状态或粘性策略，但粘性会降低均衡与故障切换灵活性。

**成立条件与边界**

多后端不自动等于高可用：负载均衡器自身、健康检查质量、跨可用区、容量、连接排空和后端共同依赖都可能形成单点。负载均衡提高的是可利用容量，不会让数据库等共享瓶颈消失。

**实际场景（生产能力）**

发布新版本时先让实例通过 readiness，再加入 upstream；下线先摘流量并等待连接排空。对有状态写请求使用幂等键，防止代理故障重试造成重复。

**常见追问**

- round-robin 与 least_conn？——前者按轮转分配，后者偏向活动连接较少的实例。
- IP hash 能保证会话不丢吗？——不能，实例变化、代理层级和共享 IP 都会影响映射。
- 如何避免负载器单点？——部署冗余入口并配合故障转移与健康监测。

**易错点**

“把请求平均分掉”不是唯一目标；不同请求成本不等，算法也只能近似平衡实际负载。
