# 日志

## 542. Java 项目为什么需要日志？

**面试回答**

日志把程序运行时的事件持久化为可检索证据，主要用于故障定位、运行监控、安全审计和业务链路分析。有效日志应记录时间、级别、位置、请求标识、关键状态和完整异常，而不是无选择地打印所有变量。

**原理与理解**

线上问题往往难以在本地复现，指标能说明“系统是否异常”，链路能说明“请求经过哪里”，日志则提供具体事件上下文。三者相互补充，日志本身不等同监控，也不应替代数据库中的业务事实。

**成立条件与边界**

日志只有在时间同步、字段稳定、可集中检索并设置保留策略时才真正可用。日志可能丢失或重复，不能作为支付、库存等核心业务的唯一事实来源；密码、Token、身份证号等敏感数据不得明文记录。

**实际场景（生产能力）**

接口失败时，通过 requestId 关联入口日志、业务关键节点、SQL/下游调用结果和异常堆栈，判断故障发生在参数校验、数据库还是第三方服务。

**常见追问**

- 日志、指标、链路追踪有什么区别？——分别偏向离散事件、聚合趋势和跨组件调用关系。
- 是否日志越多越好？——不是，要兼顾诊断价值、性能、成本、隐私和信噪比。

**易错点**

不要把日志写成“成功/失败”两句话；没有时间、上下文和异常堆栈的日志通常无法支持定位。

## 543. 常见日志级别有哪些？

**面试回答**

Java 日志体系常见级别从细到重为 TRACE、DEBUG、INFO、WARN、ERROR。以 SLF4J API 为例并没有 `fatal()` 方法；某些具体框架另有 FATAL、ALL、OFF 等级或特殊值，不能把它们当成所有框架统一标准。

**原理与理解**

日志级别用于表达事件严重度，并与 Logger 或 Appender 的阈值、过滤器共同决定是否输出。例如有效级别为 INFO 时，通常不会记录 TRACE 和 DEBUG，但会记录 INFO、WARN、ERROR。

**成立条件与边界**

“低于阈值不输出”只是常见配置模型；具体结果还受 Logger 继承、Appender 阈值、过滤器和 additivity 影响。级别也不等于告警策略，ERROR 是否触发告警仍需监控系统配置。

**实际场景（通用工程）**

开发环境可临时开启某个包的 DEBUG，生产默认保持 INFO，并通过 Appender 或过滤器将 ERROR 路由到单独索引或告警通道。

**常见追问**

- TRACE 和 DEBUG 的区别？——TRACE 更细，适合极详细的执行路径；DEBUG 用于调试上下文。
- FATAL 是 SLF4J 的标准级别吗？——不是 SLF4J Logger 的标准方法。

**易错点**

不能只背级别顺序，还要说明“事件语义”和“配置过滤”是两件事。

## 544. DEBUG、INFO、WARN、ERROR 有什么区别？

**面试回答**

DEBUG 记录排障所需的细节；INFO 记录正常运行中的关键里程碑；WARN 表示出现异常迹象或降级但主流程仍可继续；ERROR 表示当前操作失败或系统能力受损。应根据事件影响选择级别，而不是根据是否抛出异常机械决定。

**原理与理解**

同一个异常在不同层重复记 ERROR 会造成告警风暴。通常由最了解业务结果、且决定不再向上处理的边界记录一次完整异常；底层若继续抛出，可补充上下文后交给上层统一记录。

**成立条件与边界**

可预期的用户参数错误通常不是系统 ERROR；自动重试中一次失败可能是 WARN，但重试耗尽后才是 ERROR。具体约定应由团队统一，并与告警规则匹配。

**实际场景（生产能力）**

下游首次超时且即将重试记录 WARN；全部重试失败、订单创建无法完成时记录 ERROR，并包含请求标识、下游名称、耗时和最终异常。

**常见追问**

- 捕获异常一定记 ERROR 吗？——不一定，取决于是否已恢复以及业务影响。
- 为什么不应多层重复打印同一异常？——会增加噪声、成本并造成一次故障被误判为多次。

**易错点**

WARN 不是“黄色 ERROR”，INFO 也不应记录每一行正常执行细节。

## 545. SLF4J 是什么？

**面试回答**

SLF4J 是 Java 日志门面 API，业务代码面向统一的 `Logger` 接口编程，运行时由 Logback、Log4j 2 等日志 Provider 完成实际处理与输出。它降低了业务代码对具体日志实现的耦合。

**原理与理解**

SLF4J 定义 Logger、LoggerFactory、MDC 等 API，并支持参数化日志。调用 `log.info("orderId={}", orderId)` 可避免手工拼接，也便于实现仅在该级别启用时格式化参数。

**成立条件与边界**

SLF4J 不是完整日志实现。没有 Provider 时通常不能得到预期输出；同时存在多个 Provider 时选择结果可能不符合预期，应整理依赖。2.x 的 Provider 发现机制与旧版绑定方式不同，升级时要检查兼容性。

**实际场景（通用工程）**

Spring Boot 业务类只依赖 SLF4J API，具体使用 Logback 输出到控制台或滚动文件；替换实现时尽量不改业务日志调用。

**常见追问**

- SLF4J 自己写日志文件吗？——不负责，实际输出由 Provider/日志实现完成。
- 为什么使用占位符？——减少无效字符串拼接并保持结构清晰。

**易错点**

不要把 SLF4J 说成 Logback 的别名，也不要同时引入多个相互竞争的 Provider。

## 546. Logback 是什么？

**面试回答**

Logback 是一个具体的 Java 日志框架；其中 logback-classic 可作为 SLF4J Provider。它通过 Logger、Appender、Encoder/Layout、Filter 等组件完成级别判断、事件格式化和输出。

**原理与理解**

Logger 产生日志事件，Appender 决定输出目的地，Encoder/Layout 决定文本或字节格式，Filter 可进一步筛选。RollingFileAppender 可按时间或大小滚动文件，并配合保留策略控制磁盘占用。

**成立条件与边界**

异步 Appender 可以降低调用线程等待，但队列满、进程异常退出时可能丢日志，还会增加排障复杂度。滚动文件不等于集中日志平台；容器环境也常直接写标准输出，由采集器统一收集。

**实际场景（生产能力）**

生产配置控制台 JSON 日志或滚动文件，输出时间、级别、线程、Logger、traceId 和消息；同时限制历史文件数量与总大小，防止日志占满磁盘。

**常见追问**

- Appender 做什么？——接收日志事件并输出到控制台、文件、网络等目的地。
- RollingFileAppender 解决什么？——日志滚动与保留，而不是自动保证远程收集成功。

**易错点**

Logback 不只是“把日志写进文件”，输出位置、格式、过滤和生命周期都由配置共同决定。

## 547. SLF4J 和 Logback 是什么关系？

**面试回答**

SLF4J 是应用使用的日志 API/门面，Logback 是可接在它后面的具体实现之一。常见调用链是“业务代码 → SLF4J API → Logback Provider → Appender”。

**原理与理解**

门面将调用方与实现解耦，库通常只依赖 SLF4J API，最终应用统一选择 Provider。其他日志 API 还可通过桥接器转发到 SLF4J，从而集中配置输出。

**成立条件与边界**

“换实现完全零成本”并不绝对：配置文件、框架特有能力、桥接依赖和版本兼容仍需调整。桥接方向配置错误还可能形成日志循环，例如两个框架互相转发。

**实际场景（通用工程）**

排查“日志不输出”时，先确认 SLF4J API 版本、实际 Provider、Logger 有效级别和 Appender，而不是只检查业务中的 `log.info`。

**常见追问**

- 能否只引入 SLF4J？——API 可以编译，但运行时还需要合适 Provider 才有预期输出。
- Log4j 2 能替代 Logback 吗？——可以作为另一实现，但要调整 Provider、桥接和配置。

**易错点**

门面负责统一入口，实现负责处理事件；二者层次不能说反。

## 548. 为什么生产环境不推荐使用 `System.out.println()`？

**面试回答**

`System.out.println()` 只是向标准输出写文本，缺少统一级别、Logger 名称、结构化字段、过滤、滚动和上下文能力，难以治理；生产代码通常使用日志 API。但在容器平台中“写标准输出”本身并没有错，日志框架也常把规范事件输出到 stdout 供采集。

**原理与理解**

println 通常同步写 PrintStream，无法按包动态调级别，也容易因随意拼接产生性能和敏感信息问题。日志框架则能在统一配置下完成级别判断、格式化、路由和上下文注入。

**成立条件与边界**

不应简单声称 println 一定比日志框架慢，性能取决于目标、缓冲、异步策略和输出量。命令行小工具可以合理使用 stdout；问题在于服务器业务缺少可治理的日志事件。

**实际场景（通用工程）**

将散落的 println 替换为参数化 SLF4J 调用，并由日志配置输出到 stdout；Kubernetes 或日志代理再负责采集，而不是让应用自行假设固定文件路径。

**常见追问**

- 容器应用能写 stdout 吗？——可以，建议通过日志框架输出规范格式。
- 为什么不用字符串拼接？——禁用级别时仍可能产生无效构造，并降低字段一致性。

**易错点**

“禁止 System.out”不等于“生产必须写本地日志文件”。

## 549. 如何通过日志排查接口异常？

**面试回答**

先确定时间范围、环境、接口和 requestId/traceId，再从入口状态码与耗时沿调用链检索；找到第一处异常或状态偏离，结合完整堆栈、业务主键、下游响应和数据库日志验证根因，最后用复现、指标或修复后日志闭环。

**原理与理解**

排查应区分“症状日志”和“根因日志”。上层 500 可能只是下游超时的结果；异常堆栈中的 cause 链、首次异常时间以及同一请求的前后状态更关键。

**成立条件与边界**

不得仅凭一行 ERROR 下结论，也不能在日志中直接打印密码、Token、支付报文或完整个人信息。若没有关联 ID，可结合时间、实例、线程、业务单号缩小范围，但可靠性更低。

**实际场景（生产能力）**

用户反馈下单失败：以订单号和 requestId 查询入口日志，确认 HTTP 500；继续查看数据库与下游调用耗时，发现连接池等待超时，再结合连接池指标和慢 SQL 验证，而不是直接把最外层异常当根因。

**常见追问**

- 日志里至少记录什么？——时间、级别、位置、关联 ID、关键非敏感参数、结果、耗时和异常 cause。
- 只有异常消息够吗？——不够，需要堆栈和上下文。
- 如何避免重复 ERROR？——约定由最终处理边界记录，并保留 cause。

**易错点**

不要边看边只截取“看起来像原因”的单行；先还原同一请求的时间线，再验证假设。
