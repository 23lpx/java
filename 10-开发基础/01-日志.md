# 日志

## 542. Java 项目为什么需要日志？

**面试回答**

日志用于记录程序运行过程中的关键信息（请求、异常、状态变化等），帮助开发者在出问题时定位和排查，也能用于监控和审计。

**理解**

程序跑起来后，出问题不能只靠复现——很多线上问题难以复现。日志把「什么时候、发生了什么、在哪个方法、参数是什么、报了什么错」记录下来，出问题后翻日志就能定位。日志也是系统监控、性能分析、安全审计的基础。没有日志，线上故障基本是「盲查」。

**场景**

项目里用 SLF4J + Logback 记录接口调用、SQL、异常堆栈，线上报错时先查日志定位原因。

**常见追问**

- 日志主要干嘛？（定位问题、监控审计）
- 没日志会怎样？（线上问题难以排查）

**易错点**

日志是「排查问题的关键手段」；不只记录异常，正常请求、关键状态也要记，别等出错才想起日志。

## 543. 常见日志级别有哪些？

**面试回答**

常见从低到高有：TRACE、DEBUG、INFO、WARN、ERROR（有的还有 FATAL）。级别控制「记录哪些日志」，低于设定级别的日志不会输出。

**理解**

日志级别是一个「过滤阈值」：比如设为 INFO，就只输出 INFO、WARN、ERROR，DEBUG 和 TRACE 不输出。级别从低到高：TRACE（最细）< DEBUG < INFO < WARN < ERROR。生产一般设 INFO 或 WARN，开发环境设 DEBUG 看细节。

**场景**

项目里开发环境配 DEBUG 看详细过程，生产环境配 INFO，避免日志过多刷屏、影响性能。

**常见追问**

- 级别从低到高？（TRACE < DEBUG < INFO < WARN < ERROR）
- 级别的作用？（过滤，低于阈值的日志不输出）

**易错点**

级别是「阈值过滤」；ERROR 最高、TRACE 最细，别把顺序记反。生产环境级别不宜设太低。

## 544. DEBUG、INFO、WARN、ERROR 有什么区别？

**面试回答**

DEBUG 是调试细节信息，开发排错用；INFO 是正常流程的关键信息（如请求、业务操作）；WARN 是潜在问题、不影响主流程但值得关注；ERROR 是出错、功能受影响，需要处理。

**理解**

DEBUG：变量值、执行细节，量大，生产不开；INFO：正常业务里程碑（下单成功、请求进来），生产常开；WARN：不致命但可能有隐患（如配置缺失用了默认值、慢查询）；ERROR：真的出错了（异常、调用失败），必须关注。按严重程度从低到高是 DEBUG < INFO < WARN < ERROR。

**场景**

项目里接口调用失败记 ERROR，正常业务流转记 INFO，可疑但没崩的地方记 WARN，排查细节用 DEBUG。

**常见追问**

- 哪种最严重？（ERROR）
- 生产一般开到哪级？（INFO 或 WARN）

**易错点**

WARN 是「有隐患但没挂」，ERROR 是「真出错了」；两者严重程度不同，别混着记。

## 545. SLF4J 是什么？

**面试回答**

SLF4J（Simple Logging Facade for Java）是一套日志门面（接口/抽象层），它只提供统一的日志 API，不负责真正输出日志，具体实现由底层的日志框架（如 Logback、Log4j）来完成。

**理解**

SLF4J 是「门面模式」：代码里用 SLF4J 的 `Logger`、`LoggerFactory` 写日志，但 SLF4J 自己不干活，它把日志转发给绑定的具体实现。好处是代码不绑定具体框架，以后想换 Logback 换 Log4j 都只改依赖不改代码。

**场景**

项目里代码统一 `import org.slf4j.Logger`，底层用 Logback 实现，将来换日志框架也不用改业务代码。

**常见追问**

- SLF4J 是干什么的？（日志门面/抽象接口）
- 它自己输出日志吗？（不，靠底层实现）

**易错点**

SLF4J 是「门面（接口）」不是「实现」；它解决「代码不绑定具体日志框架」的问题，本身不输出日志。

## 546. Logback 是什么？

**面试回答**

Logback 是一个具体的日志框架（SLF4J 的实现），负责真正把日志输出到控制台、文件等，功能强、性能好，是 Spring Boot 默认的日志实现。

**理解**

Logback 是「真正干活」的日志框架：接收 SLF4J 传来的日志，按配置（日志级别、输出格式、输出目标）把它写到控制台或文件，还支持按时间/大小滚动切分日志文件。它是 SLF4J 的原生实现，性能好、配置灵活。

**场景**

项目里用 Logback 把日志输出到控制台和文件，配置日志级别、格式、按天滚动，Spring Boot 默认就用它。

**常见追问**

- Logback 是什么？（SLF4J 的具体日志实现）
- Spring Boot 默认用谁？（Logback）

**易错点**

Logback 是「实现」不是「门面」；它和 SLF4J 配合使用，SLF4J 提供接口、Logback 负责输出。

## 547. SLF4J 和 Logback 是什么关系？

**面试回答**

SLF4J 是日志门面（接口），Logback 是日志实现；代码面向 SLF4J 接口编程，实际输出由 Logback 完成。SLF4J 让代码不依赖具体实现，Logback 负责真正写日志。

**理解**

类比：SLF4J 是「插座标准」，Logback 是「具体电器」。代码用 SLF4J 的接口写日志（不关心谁实现），运行时由绑定的 Logback 实现真正输出。因为只依赖接口，换实现（Log4j2 等）不用改代码。Logback 本身就是按 SLF4J 规范实现的，两者天然配套。

**场景**

项目里 pom 引入 slf4j-api 和 logback，代码用 SLF4J 的 Logger，实际输出走 Logback，解耦了「写日志的代码」和「日志框架」。

**常见追问**

- 谁是接口、谁是实现？（SLF4J 接口，Logback 实现）
- 这样分层有什么好处？（换实现不改代码）

**易错点**

「SLF4J + Logback = 门面 + 实现」，这是面试高频点；别把两者说成「都是日志框架、平级」。

## 548. 为什么生产环境不推荐使用 `System.out.println()`？

**面试回答**

因为 System.out.println 没有日志级别控制、不能方便地输出到文件、性能差（是同步的、不区分级别）、无法统一管理，还会污染控制台，生产环境用它难以排查和治理日志。

**理解**

System.out.println 的缺点：①无级别——不能按 DEBUG/INFO/ERROR 过滤，全打出来；②无文件——只输出到控制台，不落盘，出问题查不到历史；③性能差——同步阻塞、不加锁不优化，频繁调用影响性能；④难管理——不能统一配置格式、滚动、采集。生产要用日志框架（SLF4J+Logback）替代。

**场景**

项目里排查用日志框架记到文件（可回溯、可分级别），而不是 System.out.println 打到控制台就丢了。

**常见追问**

- println 最大问题？（无级别、不落盘、性能差）
- 应该用什么？（日志框架 SLF4J+Logback）

**易错点**

println 的硬伤是「无级别、不落盘、性能差」；生产必须用日志框架，这是工程规范。

## 549. 如何通过日志排查接口异常？

**面试回答**

通过日志里的关键信息定位：根据异常堆栈找到出错的方法和行号，结合请求参数、时间点、链路 ID 等缩小范围，再结合业务逻辑分析根因。

**理解**

排查步骤：①拿到报错时间，查对应日志；②找 ERROR 级别和异常堆栈，定位「哪个类哪个方法第几行」抛的；③看堆栈前的请求参数、入参日志，还原现场；④结合链路 ID（traceId）串起整个请求的日志，看经过哪些环节；⑤分析根因（空指针？参数错？下游超时？）。日志打得好，排查才快。

**场景**

项目里接口报错后，根据异常堆栈 + 请求参数日志定位到具体方法，再配合 traceId 找到完整调用链，定位根因。

**常见追问**

- 最先看什么？（异常堆栈，定位类/方法/行号）
- 怎么还原现场？（看请求参数、链路 ID）

**易错点**

排查靠「异常堆栈 + 入参 + 链路 ID」；日志要提前打全（关键参数、异常），否则出问题查不到。
