# GC与类加载

## 485. GC 是什么？

**面试回答**

GC 是 JVM 的自动存储管理机制，负责识别从 GC Roots 不可达或按引用语义可处理的对象，并回收、整理或复用其内存；具体算法和暂停特性由收集器实现决定。

**原理与理解**

主流 GC 通过可达性分析标记存活对象，再采用复制、标记-清除、标记-整理或 Region 回收等策略。部分阶段可并发，但根扫描、重定位等仍可能需要停顿。

**成立条件与边界**

GC 只管理受管内存，不会自动关闭数据库连接、文件和 Socket；对象不可达只表示具备回收资格，不保证立即回收。循环引用本身不会阻止可达性 GC 回收。

**实际场景（通用工程）**

请求 DTO 用完后若不再可达，可由 GC 回收；连接等资源仍应使用 try-with-resources、连接池归还或框架生命周期管理。

**常见追问**

- GC 是否一定 Stop-The-World？——不同收集器和阶段不同，通常仍存在某些暂停点。
- Java 会内存泄漏吗？——会，无用对象若仍从 Root 可达就无法回收。

**易错点**

“没有任何引用指向就回收”过于简单，应说“从 GC Roots 不可达且满足引用处理条件”。

## 486. 为什么 Java 需要 GC？

**面试回答**

GC 把对象存储的回收责任集中到运行时，避免开发者手工决定每个对象的释放时机，降低悬空引用、重复释放等错误，并支持对象移动和紧凑等运行时优化。

**原理与理解**

运行时掌握引用关系、分配速率和堆布局，可以批量回收与压缩内存；开发者主要控制对象的可达生命周期，而非调用 free。

**成立条件与边界**

GC 不能消除逻辑内存泄漏，也有 CPU、额外空间和暂停成本。资源释放、缓存上限和对象生命周期仍需应用设计；System.gc() 只是请求，不能作为业务正确性机制。

**实际场景（通用工程）**

缓存未设置容量导致对象一直可达时，GC 再频繁也回收不了；应修复保留关系和容量策略，而不是循环调用 System.gc()。

**常见追问**

- GC 最大代价是什么？——吞吐、延迟、内存占用之间存在权衡。
- 为什么仍需性能调优？——分配模式和服务目标不同，默认配置不保证适合全部负载。

**易错点**

“有 GC 就不会内存泄漏”错误；可达但业务上无用的对象仍是泄漏。

## 487. 如何判断一个对象是否可以被回收？

**面试回答**

主流 JVM 以可达性分析为基础：若从活动线程引用、静态/JNI引用等 GC Roots 沿引用图无法到达对象，它通常具备回收资格；软、弱、虚引用还按各自语义处理。

**原理与理解**

GC Roots 是收集器必须保留的起点。标记遍历从 Roots 出发，能到达的对象视为存活，无法到达的普通对象可回收，因此互相引用的孤岛也能被识别。

**成立条件与边界**

“不可达”不等于马上释放，收集时机由 JVM 决定；Reference、类卸载、JNI 全局引用和已弃用的 finalization 都会增加生命周期细节。JIT 还可能让局部对象比源码作用域更早不可达。

**实际场景（通用工程）**

排查泄漏时通过堆转储查看对象到 GC Root 的保留路径，找到静态集合、ThreadLocal 或监听器等真正持有者。

**常见追问**

- GC Roots 是固定清单吗？——规范与实现层面表述不同，常见来源包括活动线程、静态字段和 JNI。
- 两个对象互相引用能回收吗？——若整个环从 Roots 不可达，可以。

**易错点**

引用计数为 0 不是 HotSpot 判活的核心规则，循环引用也不是必然泄漏。

## 488. 什么是可达性分析？

**面试回答**

可达性分析把对象引用看作图，从一组 GC Roots 开始遍历；有路径可达的对象保留，没有路径的对象进入可回收或引用处理流程。

**原理与理解**

并发标记收集器在应用线程修改引用的同时工作，需要写屏障、记忆集或标记队列维护遍历正确性；所以它不是一次简单的全堆 DFS。

**成立条件与边界**

弱可达、软可达、虚可达由 `java.lang.ref` 定义，不能全部按普通强可达判断。对象是否“业务有用”与 JVM 是否“可达”是两个不同概念。

**实际场景（通用工程）**

一个被静态 Map 保存但业务已不用的对象仍从 Root 可达，GC 会保留它；需要删除 Map 条目或采用有界缓存。

**常见追问**

- 可达性分析为何优于简单引用计数？——能回收不可达的循环引用图。
- 什么是保留路径？——从某个 Root 到目标对象的引用链。

**易错点**

不要把“不可达即可回收”说成“下一毫秒必然回收”。

## 489. 什么是强引用、软引用、弱引用？

**面试回答**

普通引用构成强可达，仍强可达的对象不会因内存压力被 GC 回收；SoftReference 在内存需求下由 GC 决定清除，并保证抛 OOM 前清除当时所有指向软可达对象的软引用；WeakReference 在 GC 判定对象弱可达时会被原子清除相关弱引用。

**原理与理解**

ReferenceQueue 可接收已登记且被清除/入队的引用，用于清理外部记录。软引用倾向保留一段时间，弱引用不提供缓存命中期限；虚引用主要用于回收后动作协调。

**成立条件与边界**

“软引用只在内存不足时清除”“弱引用下一次 GC 必定立刻回收”都过度绝对。JVM 对具体时机保留实现空间，软引用也不适合承担可预测、可观测的业务缓存。

**实际场景（通用工程）**

元数据映射可在明确语义下使用 WeakHashMap；业务热点缓存应优先使用有界缓存和显式过期，而不是把软引用当容量策略。

**常见追问**

- ThreadLocal 为什么会有 stale entry？——Map 的 key 是弱引用，value 仍可能被线程持有，必须 remove。
- PhantomReference 有什么用？——配合队列跟踪对象进入特定回收阶段，不能通过 get 取回对象。

**易错点**

弱引用不是“弱化所有到对象的引用”，只要仍有任意强可达路径，对象就不会变成弱可达。

## 490. 什么是类加载？

**面试回答**

类加载是 JVM 根据二进制名，通过启动类加载器或用户自定义 ClassLoader 查找字节表示并创建 Class/接口的过程；它与后续链接、初始化是不同阶段。

**原理与理解**

定义类会解析 class 文件并把二进制名与定义加载器共同纳入运行时身份。数组类由 JVM 创建，不是普通加载器从 class 文件定义。

**成立条件与边界**

“首次使用就完成全部类加载过程”不准确：加载、解析和初始化时机可分离，解析可延迟。相同全限定名由不同定义加载器加载，运行时可视为不同类型。

**实际场景（通用工程）**

插件或应用服务器出现 `ClassCastException: X cannot be cast to X` 时，要检查两个 X 是否由不同 ClassLoader 定义。

**常见追问**

- `loadClass` 与 `Class.forName` 一样吗？——不完全一样，初始化默认行为和可选参数不同。
- 类的身份由什么决定？——二进制名与定义它的 ClassLoader。

**易错点**

类加载的直接结果不只是“把字节码放进内存”，还要建立由特定加载器定义的运行时类型。

## 491. Java 类加载过程有哪些阶段？

**面试回答**

完整生命周期通常表述为加载、链接、初始化；链接包含验证、准备和解析。因此常见展开是“加载 → 验证 → 准备 → 解析 → 初始化”，但解析可以在初始化之后按需发生。

**原理与理解**

加载创建类；验证检查 class 结构和字节码约束；准备创建静态字段并设默认值，同时 ConstantValue 静态常量可在此赋值；解析把符号引用解析为运行时实体；初始化执行 `<clinit>`。

**成立条件与边界**

初始化只在规定的主动使用场景触发，并先初始化需要的父类；接口初始化规则与类不同。不能绝对说“准备阶段所有静态字段只赋零值”。

**实际场景（通用工程）**

读取 `static final int N = 10` 这类编译期常量可能被调用方内联，不一定触发声明类初始化；访问非常量静态字段通常会触发。

**常见追问**

- 解析为何可以晚于初始化？——JVM 允许惰性解析，只需在首次真正使用前完成。
- `<clinit>` 是构造器吗？——不是，它汇总类变量初始化和静态块。

**易错点**

“类加载五步严格同步顺序执行一次”不准确，链接子阶段和解析时机有规范弹性。

## 492. 什么是双亲委派机制？

**面试回答**

常见 ClassLoader 的 `loadClass` 流程是先检查类是否已加载，再把请求委派给父加载器；父加载失败后才调用本加载器的 `findClass`。这是一种类加载器实现约定，不是 Java 继承意义上的“双亲”。

**原理与理解**

现代 JDK 常见层级包括 Bootstrap、Platform 和 Application ClassLoader；Bootstrap 由 VM 实现，在 Java API 中父加载器可能表示为 null。委派让平台类优先由稳定上层定义。

**成立条件与边界**

ClassLoader API 允许自定义加载策略，插件、容器、模块或 SPI 场景可能采用 child-first、线程上下文加载器等方式。Java 9 后应说 Platform ClassLoader，不再沿用 Extension ClassLoader 口诀。

**实际场景（通用工程）**

应用加载 `java.lang.String` 时会先交给上层；插件隔离则可能为各插件建立独立加载器，同时精心定义共享 API 的父加载器。

**常见追问**

- 父加载器是父类吗？——不是，是构造时关联的委派对象。
- 谁加载应用 classpath？——通常是 Application ClassLoader。

**易错点**

不是“请求先一路交到顶层，再由顶层主动向下查找”；每层父加载失败后，当前加载器才尝试自己的 findClass。

## 493. 为什么需要双亲委派？

**面试回答**

父优先委派可让平台类和共享 API 由预期加载器定义，减少同一加载器层级中的重复定义与类型不一致，并降低应用代码伪装核心类的风险。

**原理与理解**

类身份由二进制名和定义加载器共同决定。共享接口若由父加载器定义，子加载器中的实现可以基于同一类型契约交互；否则即使类名相同也可能互不兼容。

**成立条件与边界**

它不保证整个 JVM 中类名全局唯一，不是完整安全沙箱；多个隔离 ClassLoader 可以合法定义同名类。JVM 还对 `java.*` 包定义等施加额外限制，安全依赖模块、访问控制和部署边界共同完成。

**实际场景（通用工程）**

应用服务器与插件系统会保留父优先的共享 API，同时对业务依赖做隔离；若错误打破边界，可能出现 LinkageError 或类型转换失败。

**常见追问**

- 为什么某些框架打破双亲委派？——父加载器看不到子加载器实现时，需要上下文加载器或特定委派策略。
- 同名类一定相同吗？——不一定，定义加载器不同就可能是不同类型。

**易错点**

“双亲委派保证核心类绝对安全且全 JVM 唯一”是过度表述。
