# GC与类加载

## 485. GC 是什么？

**面试回答**

GC（Garbage Collection，垃圾回收）是 JVM 自动回收「不再被使用的对象」所占内存的机制，程序员不用手动释放内存。

**理解**

Java 里 new 的对象由 JVM 自动管理：对象没用了（没有引用指向它），GC 会在合适时机回收它占的内存。相比 C/C++ 手动 free，Java 的自动 GC 减少了内存泄漏和悬空指针问题，让程序员专注业务。代价是回收时有停顿（STW）、不可完全控制时机。

**场景**

项目里大量临时对象（如查询结果、请求对象）用完后，由 GC 自动回收，不用手动管理。

**常见追问**

- GC 回收什么？（不再被引用的对象）
- 对比手动管理的好处？（避免内存泄漏、悬空指针）

**易错点**

GC 是「自动回收无用对象」，但「自动」不等于「无代价」——回收时可能有停顿、时机不可控。

## 486. 为什么 Java 需要 GC？

**面试回答**

因为手动管理内存容易出错（内存泄漏、悬空指针、重复释放），Java 用 GC 自动回收无用对象，让程序员不用手动释放内存，提高开发效率和程序健壮性。

**理解**

C/C++ 手动 malloc/free，一旦忘释放就泄漏、释放了又用就悬空指针，是常见 bug 来源。Java 把「内存回收」交给 JVM：自动判断对象是否无用并回收，程序员不用关心释放。这是 Java 相比 C/C++ 的核心优势之一，大幅降低内存管理的出错率。

**场景**

项目里无需关心对象何时释放，GC 自动处理，开发更安全高效。

**常见追问**

- 手动管理有什么问题？（泄漏、悬空指针）
- GC 的代价？（回收停顿、时机不可控）

**易错点**

GC 的价值是「自动、减少内存 bug」；但要辩证看，它不是免费的，有停顿代价。

## 487. 如何判断一个对象是否可以被回收？

**面试回答**

主流用「可达性分析」：从一组「根对象」（GC Roots，如栈里的引用、静态变量等）出发，能被引用链到达的对象是「存活」的，不可达的对象就是可回收的。

**理解**

可达性分析是当前主流判定法（替代早期的引用计数法）。GC Roots 包括：虚拟机栈里的引用、静态变量、常量、本地方法栈里的引用等。从这些根出发，沿着引用链能找到的对象都是「活」的，找不到的（不可达）就是垃圾，可以回收。

**场景**

项目里方法执行完，栈里的引用消失，之前指向的对象若没有其他引用，就变成不可达，被 GC 回收。

**常见追问**

- GC Roots 有哪些？（栈引用、静态变量、常量等）
- 可达/不可达分别代表？（可达=存活，不可达=可回收）

**易错点**

判断回收用「可达性分析」，核心是「从 GC Roots 出发能不能到达」；不可达即可回收。

## 488. 什么是可达性分析？

**面试回答**

可达性分析是从一组 GC Roots（根对象）出发，沿着引用链遍历所有能到达的对象，能到达的是存活对象，不能到达的是可回收垃圾。

**理解**

想象「从根往下找引用」：GC Roots 是起点（栈里的局部变量引用、静态变量、常量引用、JNI 引用等），从它们出发，通过引用关系能走到的对象都是「还在用」的；走不到的（没有任何根能到达）就是垃圾。它避免了引用计数法的「循环引用」问题。

**场景**

项目里两个对象互相引用但没有外部引用，可达性分析会正确判定它们都不可达、可回收（引用计数法会漏判）。

**常见追问**

- 可达性分析解决什么问题？（比引用计数更准确，能处理循环引用）
- GC Roots 是什么？（判断可达的起点）

**易错点**

可达性分析的核心是「从 GC Roots 遍历」，能正确处理「循环引用但不可达」的对象。

## 489. 什么是强引用、软引用、弱引用？

**面试回答**

强引用是普通引用（`Object o = new Object()`），对象只要被强引用就不会被回收；软引用在内存不足时会被回收；弱引用在下一次 GC 时就会被回收（无论内存是否充足）。

**理解**

三者回收强度递减：强引用——GC 绝不回收，只有引用被置空才可回收；软引用（SoftReference）——内存够就不回收，内存不足时回收，适合做缓存；弱引用（WeakReference）——只要发生 GC 就回收，适合做如 ThreadLocal 的 key、缓存等。还有虚引用（最弱，仅用于跟踪回收）。

**场景**

项目里要「内存不足时自动释放」的缓存可用软引用；要「GC 就回收」的临时关联可用弱引用。

**常见追问**

- 三种引用回收时机？（强引用不回收，软引用内存不足回收，弱引用 GC 就回收）
- 软引用适合什么？（内存敏感的缓存）

**易错点**

三种引用按「回收强度」递减：强 > 软 > 弱；关键是记住各自「什么时候被回收」。

## 490. 什么是类加载？

**面试回答**

类加载是 JVM 把类的 .class 字节码文件加载进内存，生成对应的 Class 对象的过程，让类能被使用。

**理解**

Java 是「运行时动态加载类」的：不是启动时把所有类都加载，而是用到某个类时才加载它的字节码，解析成内存里的 Class 对象（存方法区）。类加载由类加载器完成，包含加载、验证、准备、解析、初始化等阶段。

**场景**

项目里首次用到 Dish 类时，JVM 加载 Dish.class 生成 Class 对象，之后就能 new 对象、调方法。

**常见追问**

- 类加载的结果？（生成 Class 对象）
- 谁来做？（类加载器 ClassLoader）

**易错点**

类加载是「字节码 → 内存中的 Class 对象」的过程，是类被使用的前提；它遵循双亲委派等机制。

## 491. Java 类加载过程有哪些阶段？

**面试回答**

主要五个阶段：加载、验证、准备、解析、初始化（简称「加载 → 验证 → 准备 → 解析 → 初始化」）。

**理解**

加载：读字节码，生成 Class 对象；验证：检查字节码合法性、安全性；准备：为静态变量分配内存并赋默认零值；解析：把符号引用替换成直接引用（如方法、字段的实际地址）；初始化：执行静态代码块、给静态变量赋程序员指定的初值。前三步常一起发生，解析可能滞后。

**场景**

项目里类加载到初始化，静态变量在「准备」阶段赋零值、在「初始化」阶段赋真正的初值并执行静态代码块。

**常见追问**

- 五个阶段？（加载、验证、准备、解析、初始化）
- 静态变量什么时候赋真正的值？（初始化阶段）

**易错点**

类加载五个阶段要能说清各自作用，尤其「准备（零值）」和「初始化（真正赋值）」的区别。

## 492. 什么是双亲委派机制？

**面试回答**

双亲委派是类加载器的工作机制：一个类加载器收到加载请求时，先委派给「父加载器」去加载，父加载器加载不了才自己加载，逐层向上委派。

**理解**

加载顺序：应用类加载器 → 扩展类加载器 → 启动类加载器（最顶层）。请求先到最顶层，能加载就加载，加载不了再层层往下。核心类（如 java.lang.String）由启动类加载器加载，避免被应用层重复加载或篡改。

**场景**

项目里加载 java.lang.String 时，会先委派给启动类加载器加载 JDK 自带的 String，而不是加载自定义的同名类。

**常见追问**

- 委派顺序？（先父后子，从顶层往下）
- 谁在最顶层？（启动类加载器 Bootstrap ClassLoader）

**易错点**

双亲委派是「先让父加载器加载、不行再自己来」；父加载器不是 Java 里的继承父类，是「委派关系」。

## 493. 为什么需要双亲委派？

**面试回答**

为了保证核心类库的安全和唯一：核心类（如 java.lang.String）由启动类加载器统一加载，避免被应用自定义的同名类替换，防止恶意代码篡改核心类、破坏系统安全。

**理解**

如果没有双亲委派，应用可以自己定义 `java.lang.String` 等核心类，替换 JDK 的实现，可能植入恶意逻辑、破坏类型体系。双亲委派让核心类「只能由顶层加载器加载一次」，应用层无法覆盖，保证了类加载的唯一性、安全性和类的一致性（同一个类不会被重复加载成多个版本）。

**场景**

项目里即使有人写了个自定义的 java.lang.String，双亲委派也会让 JDK 的 String 被加载，自定义的无法生效，保护了系统。

**常见追问**

- 双亲委派防什么？（核心类被篡改/替换）
- 还有什么好处？（避免类重复加载、保证类唯一）

**易错点**

双亲委派的核心价值是「安全 + 类唯一」：防止核心类被替换、避免重复加载；不是简单的「代码复用」。
