# MyBatis

## 201. MyBatis 是什么？

**面试回答**

MyBatis 是 SQL 映射型持久化框架，把自定义 SQL、存储过程与 Java 方法绑定，并负责参数设置、语句执行和结果映射；开发者仍显式控制 SQL。

**原理与理解**

配置解析后形成 MappedStatement，`SqlSession`/Mapper 代理通过 Executor 执行，StatementHandler、ParameterHandler、ResultSetHandler 分别参与语句、参数和结果处理。

**成立条件与边界**

“半自动 ORM”是常见口语，但 MyBatis 更准确地是 SQL Mapper；它不会替应用设计事务、索引和数据模型。连接与事务可能由 MyBatis 自己管理，也可能交给 Spring。

**实际场景（通用工程）**

复杂查询需要精确 SQL 时使用 Mapper XML/注解，并以 DTO 或 ResultMap 明确结果契约。

**常见追问**

- 与 Hibernate/JPA 的差异？——MyBatis 以手写 SQL 和映射为中心，后者更侧重对象关系模型与生成查询。
- 核心对象？——Configuration、MappedStatement、SqlSession、Executor 与 Mapper 代理。

**易错点**

不要说 MyBatis 会自动生成全部 SQL，也不要把它等同于 JDBC 工具类。

## 202. MyBatis 和 JDBC 有什么关系？

**面试回答**

MyBatis 建立在 JDBC 之上，仍通过 Connection、Statement/PreparedStatement 和 ResultSet 与数据库交互，但封装了参数映射、执行、结果映射、缓存和插件扩展等样板逻辑。

**原理与理解**

DataSource 提供连接，事务管理器决定提交与回滚，MyBatis 根据 BoundSql 创建 JDBC Statement 并用 TypeHandler 绑定/读取值。

**成立条件与边界**

“自动管理连接和事务”取决于集成方式：Spring 管理的 SqlSession 与独立 MyBatis 使用方式不同。资源关闭也不能让开发者忽略连接池、超时和事务边界。

**实际场景（通用工程）**

业务调用 Mapper，框架最终仍执行 JDBC 参数化语句；SQL 性能与数据库执行计划不会因使用 MyBatis 自动优化。

**常见追问**

- TypeHandler 做什么？——在 Java 类型与 JDBC 类型之间转换。
- MyBatis 是否替代 JDBC？——不替代，内部依赖 JDBC API。

**易错点**

封装样板代码不等于屏蔽数据库和 JDBC 契约。

## 203. Mapper 接口有什么作用？

**面试回答**

Mapper 接口用普通 Java 方法声明持久化操作，方法签名与 XML、注解或 Provider 中的 MappedStatement 绑定，调用方通过类型安全的接口使用 SqlSession 能力。

**原理与理解**

XML 常以接口全限定名作为 namespace、方法名作为 statement id；参数名、`@Param` 和返回类型帮助 MapperMethod 选择参数对象与执行分支。

**成立条件与边界**

接口方法必须已注册并有可解析语句或支持的默认方法；重载会让 statement id 绑定含糊，通常不建议在同一 Mapper 里靠重载区分 SQL。

**实际场景（通用工程）**

OrderMapper 声明插入主表和查询方法，Service 依赖接口而非直接拼 statement 字符串。

**常见追问**

- Mapper 必须手写实现类吗？——通常不需要，运行时由代理实现。
- 参数多个时怎么命名？——显式 `@Param` 最清晰，也可依赖受支持的参数名机制。

**易错点**

Mapper 接口本身不存 SQL 执行逻辑，必须有正确注册和语句绑定。

## 204. Mapper 接口没有实现类为什么可以执行？

**面试回答**

MyBatis 为已注册的 Mapper 接口创建 JDK 动态代理；方法调用由 MapperProxy/MapperMethod 解析为 SqlSession 的 select、insert、update 或 delete，再执行对应 MappedStatement。

**原理与理解**

代理根据接口、方法与 Configuration 缓存解析结果，普通 Object 方法和接口 default 方法走不同分支；数据库方法再按返回类型适配单值、集合、Map、Cursor 或影响行数。

**成立条件与边界**

不是“启动时给每个方法生成一个实体实现类”，而是代理统一分派。缺少 statement、返回类型不兼容或多行映射到 selectOne 都会在运行时失败。

**实际场景（通用工程）**

Spring 注入 Mapper 代理 Bean，调用时才进入当前 SqlSession 与事务上下文执行 SQL。

**常见追问**

- 如何定位 statement？——通常由 Mapper 接口全名与方法名形成 id。
- 为什么适合 JDK 代理？——Mapper 本身是接口。

**易错点**

“没有实现”只表示没有手写实现，运行时仍有代理对象和分派逻辑。

## 205. MyBatis Mapper 动态代理是什么？

**面试回答**

Mapper 动态代理是把接口调用转换为 MyBatis statement 执行的适配层，核心包括 MapperProxy、MapperMethod 和当前 SqlSession。

**原理与理解**

InvocationHandler 接收 Method 与实参，缓存 MapperMethod，构造参数对象，选择 SqlSession 操作，并根据方法签名转换结果。

**成立条件与边界**

代理不是 SQL 缓存本身，也不负责数据库事务决策；SqlSession 生命周期由使用方式决定。接口 default 方法可执行自身实现，不一定映射 SQL。

**实际场景（通用工程）**

一次 Mapper 调用可能加入 Spring 当前事务中的 SqlSession，代理负责分派而事务同步由集成层负责。

**常见追问**

- MapperProxy 是什么？——Mapper 接口代理的 InvocationHandler。
- 返回影响行数如何适配？——MapperMethod 可按 int、long、boolean 等受支持类型转换。

**易错点**

不要把 Mapper 代理与 Spring AOP 代理混为同一种职责。

## 206. MyBatis 注解方式和 XML 方式有什么区别？

**面试回答**

注解把 statement 写在接口或 Provider 中，适合简短 SQL；XML 将 SQL、ResultMap 和动态标签集中在映射文件中，更适合复杂映射与长 SQL。两者最终都形成 MappedStatement。

**原理与理解**

注解也可借助 `<script>` 或 SQL Provider 实现动态 SQL，并非只能固定语句；XML 的 ResultMap、片段复用和可读性通常更强。

**成立条件与边界**

同一 statement id 不应同时由注解和 XML 重复定义。选择取决于团队约定、SQL 复杂度、重构工具和测试，不存在“复杂 SQL 必须 XML”的语言限制。

**实际场景（项目核验项）**

核对项目哪些 Mapper 用 XML、注解或 Provider，再说明选择；不要凭题目假定“项目主要使用 XML”。

**常见追问**

- 可以混用吗？——不同方法可以，重复定义同一 statement 会冲突。
- 动态 SQL 注解能做吗？——可以使用 script 或 Provider，但维护成本需评估。

**易错点**

注解与 XML 是声明方式差异，不是两个不同执行引擎。

## 207. `#{}` 和 `${}` 有什么区别？

**面试回答**

`#{}` 通常生成 JDBC `?` 参数标记并通过 TypeHandler 绑定值；`${}` 在 SQL 构建阶段进行未转义的字符串替换，直接改变 SQL 文本。

**原理与理解**

前者把数据与 SQL 结构分离，适合绝大多数值；后者可替换列名、表名或片段，但输入会成为 SQL 语法的一部分。

**成立条件与边界**

`#{}` 只能降低值位置的注入风险，不会修复授权缺失、错误动态片段或数据库对象名拼接。`${}` 不是自动加引号的模板，也不会做转义。

**实际场景（通用工程）**

查询值全部使用 `#{}`；排序字段由服务端枚举映射到固定列名，避免把客户端字符串直接交给 `${}`。

**常见追问**

- `#{}` 底层一定服务器预编译吗？——它使用 PreparedStatement 参数绑定，数据库/驱动是否缓存或服务端预编译是另一层问题。
- `${}` 何时有用？——必须动态替换 SQL 元数据且已做白名单映射时。

**易错点**

不要把区别简化成“# 会转义、$ 不转义”；核心是参数绑定与文本替换。

## 208. 为什么 `#{}` 可以降低 SQL 注入风险？

**面试回答**

因为 MyBatis 把 `#{}` 变为 JDBC 参数标记，SQL 结构先由语句文本确定，用户输入作为参数值绑定，通常不能变成关键字、操作符或额外语句。

**原理与理解**

ParameterHandler 和 TypeHandler 调用 PreparedStatement 的 set 方法，数据库按目标类型处理该值，而不是把其中字符重新解析为 SQL 结构。

**成立条件与边界**

参数化不是“万能防注入”：动态表/列/ORDER BY 仍需安全生成，LIKE 模式和业务查询逻辑仍可能被滥用，数据库账号也应最小权限。

**实际场景（通用工程）**

登录名、订单 ID 和状态都用绑定参数；列选择通过服务端 Map 映射，不接受任意 SQL 片段。

**常见追问**

- 与转义的差异？——参数绑定从协议/语句层分离结构与值，不依赖手工拼接转义。
- LIKE 怎么写？——由数据库函数或绑定好的模式值构造，仍避免文本拼接。

**易错点**

“用了 #{} 就绝对安全”会掩盖其他动态 SQL 和授权风险。

## 209. `${}` 为什么存在 SQL 注入风险？

**面试回答**

因为 `${}` 把值原样替换进最终 SQL 文本，输入可成为标识符、表达式、关键字甚至额外语句，从而改变原查询语义。

**原理与理解**

MyBatis 不修改或转义该字符串；数据库看到的是替换后的完整 SQL，无法知道哪部分原本来自用户输入。

**成立条件与边界**

风险大小受 JDBC 驱动是否允许多语句、数据库权限和具体位置影响，但不能据此认为可接受。即使只用于 ORDER BY，也可能注入函数、子查询或昂贵表达式。

**实际场景（通用工程）**

不要直接使用 `ORDER BY ${sort}`；将 `createdTime`、`amount` 等 API 枚举映射为代码中固定列名。

**常见追问**

- 正则过滤够吗？——枚举/映射白名单更可靠，且应控制方向和 NULLS 等选项。
- 能用 `#{}` 替代列名吗？——通常不能，参数标记表示值而非标识符。

**易错点**

只过滤引号不能消除结构位置的注入。

## 210. `${}` 一般在什么场景使用？

**面试回答**

只在必须动态生成 SQL 元数据或受信任片段时使用，例如受控列名、表名或方言片段；优先通过 Java 枚举到固定 SQL 的映射减少使用。

**原理与理解**

JDBC 参数标记不能替代标识符，因此某些动态结构只能选择多条固定 statement、Provider/DSL 或文本替换。

**成立条件与边界**

“表名、列名、排序字段”是可能场景，不代表可直接接受客户端输入。多租户动态表名尤其要防跨租户访问、缓存键污染和标识符引用问题。

**实际场景（通用工程）**

API 的 sort 参数解析为枚举，再由 switch 返回硬编码列名；排序方向同样只允许 ASC/DESC。

**常见追问**

- 有哪些替代方案？——固定 SQL 分支、`<choose>`、Provider 或类型安全 DSL。
- 能否把值加引号后再替换？——不应，值位置直接使用 `#{}`。

**易错点**

`${}` 不是“灵活版参数”，而是需要严格信任边界的 SQL 文本生成。

## 211. 什么是 MyBatis 动态 SQL？

**面试回答**

动态 SQL 是 MyBatis 根据参数与 OGNL 条件生成最终 SQL 文本的机制，常用元素包括 `if`、`choose`、`trim/where/set`、`foreach` 和 `bind`。

**原理与理解**

XML 脚本解析为 SqlNode 树，执行时生成 DynamicContext 与 BoundSql；值继续用 `#{}` 绑定，结构由标签有条件组合。

**成立条件与边界**

动态 SQL 每次生成一条最终 statement，但数据库层可能因不同文本形成不同执行计划缓存项。条件过多会难以测试，也可能在无条件时误执行全表查询/更新。

**实际场景（通用工程）**

查询 DTO 的可选条件使用 where + if；高风险更新显式要求主键条件，不允许空条件退化为全表。

**常见追问**

- test 使用什么表达式？——MyBatis 动态 SQL 使用 OGNL。
- 如何观察最终 SQL？——使用安全的 SQL 日志/代理并对敏感参数脱敏。

**易错点**

动态 SQL 解决文本组合，不自动保证 SQL 正确、安全或高性能。

## 212. `<if>` 有什么作用？

**面试回答**

`<if test="...">` 在 OGNL 条件为 true 时把内部 SQL 节点加入最终语句，常用于可选查询条件或更新字段。

**原理与理解**

test 可访问参数对象及 `@Param` 名称；SQL 片段中的值仍应使用 `#{}`。多个 if 相互独立，若需要互斥分支使用 `<choose>` 更清楚。

**成立条件与边界**

字符串、集合、数值的空判断语义不同，不能到处复制 `name != ''`。条件全部不成立可能生成无 WHERE 的语句，写操作必须额外防护。

**实际场景（通用工程）**

状态非 null 时添加 `AND status = #{status}`；批量更新要求至少有一个明确条件，否则服务层拒绝。

**常见追问**

- if 能写 else 吗？——使用 choose/when/otherwise 表达互斥分支。
- 多参数如何引用？——显式 `@Param` 或参数对象属性。

**易错点**

if 只决定是否拼片段，不会自动处理 AND、逗号或危险空条件。

## 213. `<where>` 有什么作用？

**面试回答**

`<where>` 在内部产生内容时添加 WHERE，并移除开头符合规则的 AND/OR；内部为空时不输出 WHERE。

**原理与理解**

它是 `<trim prefix="WHERE" prefixOverrides="AND |OR ">` 的便捷形式，减少 `WHERE AND ...` 等拼接错误。

**成立条件与边界**

内部为空时查询会变成无条件全表操作，语法合法不等于业务安全。prefixOverrides 对空白模式敏感，自定义复杂片段时需测试。

**实际场景（通用工程）**

后台搜索允许空条件查询但强制分页；UPDATE/DELETE 则在服务层和 SQL 层要求关键条件。

**常见追问**

- 所有条件为空会怎样？——where 标签不输出任何内容。
- 与 trim 的关系？——where 是常见 trim 配置的封装。

**易错点**

where 只修正语法，不防止全表查询或更新。

## 214. `<set>` 有什么作用？

**面试回答**

`<set>` 在内部有内容时添加 SET，并移除末尾多余逗号，常与 if 组合生成动态 UPDATE 字段列表。

**原理与理解**

它相当于针对 SET 场景配置的 trim；只有满足条件的赋值片段进入最终 SQL。

**成立条件与边界**

所有字段都未命中时可能生成无效 UPDATE，并不会自动给出友好业务错误。用 null 表示“不更新”还会使“将字段更新为 null”难以表达，应设计补丁 DTO 或显式字段集合。

**实际场景（通用工程）**

状态更新优先使用专用 SQL 和乐观条件；通用 patch 更新要区分未提供与明确置空。

**常见追问**

- set 会处理什么？——SET 前缀和尾部逗号。
- 与全字段更新怎么选？——根据更新语义、并发控制和审计需求选择。

**易错点**

动态 set 不能替代状态机、乐观锁和允许字段白名单。

## 215. `<foreach>` 有什么作用？

**面试回答**

`<foreach>` 遍历 Iterable、Map、数组等集合，为每项生成 SQL 片段，并用 open、close、separator、item、index 控制格式，常用于 IN 和多值 INSERT。

**原理与理解**

每次迭代的值可通过 `#{}` 单独绑定，而不是把整组值拼成未转义文本。Map 的 index 通常是键、item 是值。

**成立条件与边界**

空集合行为受脚本写法和版本/nullable 配置影响，应在服务层定义“空列表”语义。IN 项过多会遇到参数数、SQL 长度和执行计划问题。

**实际场景（通用工程）**

批量按 ID 查询先去重并限制数量，再用 foreach 生成参数化 IN 列表；超大集合分批或改用临时表等方案。

**常见追问**

- collection 名称从哪来？——单参数、`@Param` 或参数对象属性决定。
- index 是什么？——Iterable 中为序号，Map 中通常为键。

**易错点**

foreach 生成片段不代表数据库会自动采用最优批处理策略。

## 216. 如何通过 `<foreach>` 实现批量插入？

**面试回答**

在 `INSERT ... VALUES` 后用 foreach 把每个对象生成一个参数化值元组，以逗号连接，形成数据库支持的多行 INSERT。

**原理与理解**

这是“一条 SQL 多个 VALUES”，能减少往返与解析次数；它不同于 MyBatis `ExecutorType.BATCH` 下重复执行 PreparedStatement 的 JDBC batch。

**成立条件与边界**

单批大小受数据库参数数、包大小、SQL 长度、锁与事务时间约束，不是越大越快。不同数据库语法和批量 generated keys 支持也不同，应分批压测。

**实际场景（真实项目边界）**

项目已确认订单明细使用批量插入；可描述减少数据库交互，但具体批大小、SQL 形态和性能数据需以代码与压测为准。

**常见追问**

- 与 JDBC batch 的差异？——多值 INSERT 是一条长 SQL，JDBC batch 是批量提交多组执行。
- 空集合怎么处理？——进入 Mapper 前拒绝或直接返回，避免生成非法 SQL。

**易错点**

不要断言 foreach 永远只执行一条 SQL；标签只是生成文本，外层脚本也可能设计成其他形式。

## 217. 什么是主键回填？

**面试回答**

主键回填是插入后把数据库或 selectKey 生成的键写回参数对象指定属性，使后续代码获得已持久化记录的标识。

**原理与理解**

MyBatis 可使用 JDBC generated keys，或在插入前/后执行 `selectKey`。`keyProperty` 指定 Java 属性，必要时 `keyColumn` 指定数据库列。

**成立条件与边界**

主键不一定由数据库自增，也可能由应用生成，此时插入前已有值便不属于“数据库回填”。多行插入和复合键是否完整回填取决于驱动与数据库支持。

**实际场景（通用工程）**

先持久化主记录并取得键，再建立子记录关联；如果使用应用侧 ID，可直接在同一事务中复用预生成值。

**常见追问**

- 回填到哪里？——传入参数对象的 keyProperty。
- 除 generated keys 外还有什么？——`selectKey`。

**易错点**

主键回填不是 MyBatis 自己凭空生成 ID。

## 218. MyBatis 如何获取 MySQL 自增主键？

**面试回答**

常用做法是在 insert 上设置 `useGeneratedKeys="true"` 与 `keyProperty="id"`，MyBatis 请求 JDBC 返回 generated keys 并写入属性；注解可使用 `@Options`。

**原理与理解**

底层依赖 JDBC Statement 的 generated keys 能力。属性嵌套、多参数或列名不一致时还可能需要完整属性路径和 `keyColumn`。

**成立条件与边界**

能否返回、返回顺序和批量键数量最终取决于 MySQL 驱动与语句形态。配置正确也要在集成测试中断言对象 ID 已回填。

**实际场景（真实项目边界）**

项目已确认订单主表插入后使用回填主键关联明细；具体 XML/注解配置应以 Mapper 为准。

**常见追问**

- `keyProperty` 与 `keyColumn`？——前者是 Java 属性，后者是数据库结果列。
- 还有替代方案吗？——应用生成 ID 或 `selectKey`。

**易错点**

只设置 useGeneratedKeys 而不确认回填属性、驱动和多行行为并不可靠。

## 219. 为什么项目中的子表插入需要主键回填？

**面试回答**

当主键由数据库在插入主表时生成，子表必须取得该键并写入关联列，才能把明细归属到正确主记录；主表、回填和子表写入应处于同一原子业务边界。

**原理与理解**

流程是插入主表、读取生成键、为每个明细设置外键/关联 ID、批量插入明细。事务负责失败时整体回滚，数据库外键或应用约束继续保护引用完整性。

**成立条件与边界**

如果使用应用侧预生成 ID，就不必等待数据库回填；“同事务”也不能替代并发校验、幂等和数据库约束。

**实际场景（真实项目边界）**

项目已确认订单主表回填 ID 后批量写入关联明细，并使用声明式事务保证主子写入原子性。

**常见追问**

- 为什么不能先插子表？——数据库生成的主键尚未知，且可能违反关联约束。
- 事务解决什么？——避免主表成功、明细部分或全部失败留下不一致。

**易错点**

主键回填解决标识传递，事务解决原子性，两者职责不同。

## 220. 什么是 MyBatis 一级缓存？

**面试回答**

一级缓存是每个 SqlSession/Executor 的本地缓存，默认 localCacheScope 为 SESSION；同一会话中缓存键相同的查询可能复用结果。

**原理与理解**

缓存键综合 statement、分页参数、最终 SQL、绑定参数和环境等信息。UPDATE、commit、rollback、close 等会清理本地缓存；配置为 STATEMENT 时每条语句后清理。

**成立条件与边界**

“相同 SQL 第二次一定不查库”不成立，缓存开关、flush、调用栈、参数与会话都影响命中。Spring 中 SqlSession 生命周期由事务同步/模板管理，也不能简单等同一次 HTTP 请求。

**实际场景（通用工程）**

同一事务内重复读取可能命中，但业务正确性不应依赖一级缓存；写后读与并发可见性按事务和隔离级别分析。

**常见追问**

- 默认范围？——SESSION。
- 如何缩小？——`localCacheScope=STATEMENT`。

**易错点**

一级缓存不是跨 SqlSession 的应用缓存。

## 221. 什么是 MyBatis 二级缓存？

**面试回答**

二级缓存是与 Mapper namespace 关联的事务性缓存，可在多个 SqlSession 间共享；需要在 namespace 声明 `<cache>`/`@CacheNamespace`，并满足 statement 的 useCache 等条件。

**原理与理解**

查询结果先进入事务性缓存管理，通常在 SqlSession 提交后才对其他会话可见；同 namespace 的更新语句默认会刷新相应缓存。

**成立条件与边界**

全局 `cacheEnabled` 默认允许使用不等于每个 namespace 已启用。默认读写缓存会序列化对象并要求可序列化；readOnly 模式语义不同。跨 namespace 写入、外部程序和多实例部署仍可能造成陈旧数据。

**实际场景（通用工程）**

只有读模型稳定且失效边界明确时才评估二级缓存；分布式缓存也不能自动解决数据库一致性，仍需失效策略。

**常见追问**

- 作用域？——namespace，可用 cache-ref 共享其他 namespace 缓存。
- 更新何时清理？——MappedStatement 的 flushCache 等配置决定，更新默认通常刷新。

**易错点**

“二级缓存默认关闭”要区分全局允许开关与 namespace 是否声明缓存。

## 222. 一级缓存和二级缓存有什么区别？

**面试回答**

一级缓存绑定 SqlSession/Executor，默认 SESSION 范围且无需 namespace 声明；二级缓存绑定 namespace，可跨 SqlSession，但需显式声明并在事务提交后共享结果。

**原理与理解**

查询通常先检查二级事务缓存与本地缓存的相关链路，写操作按配置清理；两级缓存都基于精确 CacheKey，不是按实体 ID 的业务缓存。

**成立条件与边界**

二级缓存不必然要求所有对象都序列化，取决于 readOnly/缓存实现；它也不是整个应用的全局一致缓存。一级缓存中的对象引用还可能被调用方修改，需谨慎。

**实际场景（通用工程）**

默认保留一级缓存并避免依赖其副作用；启用二级缓存前验证跨 namespace 更新、批处理和多实例一致性。

**常见追问**

- 两者何时失效？——一级随会话和事务操作清理；二级按 namespace、statement 和事务提交规则处理。
- Redis 能直接替代二级缓存吗？——层级与一致性模型不同，不能只换实现名。

**易错点**

不要只背“一级默认开、二级默认关”，提交可见性与失效范围更重要。

## 223. PageHelper 是什么？

**面试回答**

PageHelper 是第三方 MyBatis 分页插件，通过 PageInterceptor 与数据库方言改写查询，并提供 `startPage`、RowBounds 等入口及 Page/PageInfo 分页结果。

**原理与理解**

`startPage` 把分页参数放入当前线程上下文，紧随其后的第一个 MyBatis select 被插件识别；插件可执行 count，并生成方言对应的分页 SQL。

**成立条件与边界**

它不是 MyBatis 官方组件，也不总是简单追加 MySQL LIMIT。分页只应紧邻目标查询使用；线程池、异步切换、条件分支和意外的先行查询会导致错误目标或上下文问题。

**实际场景（项目核验项）**

项目是否使用 PageHelper、哪些列表调用 `startPage`、是否查询总数需以代码为准；此前仅确认存在分页需求，不扩写具体插件经历。

**常见追问**

- 为什么强调紧邻查询？——分页状态按当前线程影响下一次 select。
- 支持哪些数据库？——依赖对应 Dialect，不是只支持 MySQL。

**易错点**

不要说 PageHelper 对“紧跟的第一条任意 SQL”生效，它针对符合条件的 MyBatis 查询。

## 224. PageHelper 大致如何实现分页？

**面试回答**

PageInterceptor 拦截 MyBatis Executor 查询，读取当前分页上下文和 Dialect；按配置决定是否执行 count，再生成数据库方言的分页 BoundSql，执行并把结果放入 Page，最后清理线程上下文。

**原理与理解**

count SQL 可能由解析器生成，也可映射自定义 count statement；分页 SQL 由 Dialect 生成，因此 MySQL 常见 LIMIT 只是其中一种。PageInfo 通常在查询后包装列表与分页元数据。

**成立条件与边界**

count 并非必然执行，可通过参数关闭或受 pageSizeZero 等配置影响；复杂 SQL 的 count 改写、ORDER BY 和方言选择需要集成测试。插件只改 SQL，不保证稳定排序或深分页性能。

**实际场景（通用工程）**

分页查询必须提供确定性 ORDER BY；大偏移量性能差时改用游标/Seek 分页，而不是依赖插件自动优化。

**常见追问**

- 拦截哪个环节？——核心是 Executor query，通过插件链处理 BoundSql。
- 为什么可能有两条 SQL？——需要总数时先 count，再执行分页数据查询。

**易错点**

PageHelper 不是内存截取结果，也不是固定“count + LIMIT”不可配置流程。
