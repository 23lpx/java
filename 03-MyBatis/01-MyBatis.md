# MyBatis

## 201. MyBatis 是什么？

**面试回答**

MyBatis 是一个半自动的 ORM 持久层框架，通过 XML 或注解把 SQL 和 Java 方法绑定起来，帮我们完成 SQL 执行和结果映射，但对 SQL 的控制权仍然在开发者手里。

**理解**

它封装了 JDBC 的重复操作（连接管理、参数设置、结果集封装），但不像 Hibernate 那样完全自动生成 SQL。MyBatis 需要你自己写 SQL，它负责执行和映射，所以叫「半自动」。核心是 SQL 与代码解耦、灵活可控。

**场景**

项目里用 MyBatis 操作 MySQL：Mapper 接口方法对应 XML 里的 SQL，查询结果自动映射成 Dish、Order 等实体。

**常见追问**

- MyBatis 和 Hibernate 区别？（MyBatis 半自动、自己写 SQL、灵活；Hibernate 全自动、自动生成 SQL）
- MyBatis 核心组件？（SqlSession、Mapper 接口、Executor 等）

**易错点**

MyBatis 是「半自动」ORM，SQL 还是要自己写，别理解成「完全自动生成 SQL」。

## 202. MyBatis 和 JDBC 有什么关系？

**面试回答**

MyBatis 底层就是对 JDBC 的封装：它内部还是用 JDBC 连接数据库、执行 SQL，但把 JDBC 那些繁琐、重复的操作（建连接、设参数、遍历结果集）都封装起来，让开发者只关注 SQL 和映射。

**理解**

直接写 JDBC 要手动加载驱动、建 Connection、写 PreparedStatement、设参数、遍历 ResultSet、关闭资源，样板代码多且易错。MyBatis 把这些都做了，你只需定义 Mapper 接口和 SQL，框架负责执行和结果映射。它是 JDBC 之上的封装层。

**场景**

项目里不再手写 JDBC 样板代码，用 Mapper 接口 + SQL 就能完成数据库访问，底层仍是 JDBC 执行。

**常见追问**

- MyBatis 省掉了 JDBC 的哪些事？（连接管理、参数绑定、结果集映射、资源关闭）
- MyBatis 用的还是 JDBC 吗？（是，底层基于 JDBC）

**易错点**

MyBatis 不是替代 JDBC，是「封装 JDBC」，底层执行还是 JDBC。

## 203. Mapper 接口有什么作用？

**面试回答**

Mapper 接口定义了数据库操作的方法（增删改查），通过方法名、参数和返回类型，与对应的 SQL（XML 或注解）绑定，是业务代码访问数据库的入口。

**理解**

开发者调用 Mapper 接口方法，MyBatis 通过动态代理找到对应的 SQL 并执行，返回映射好的结果。它把「数据库操作」抽象成普通的 Java 方法调用，业务层不用关心 SQL 细节，实现数据访问层与业务的解耦。

**场景**

项目里 DishMapper 定义 list、insert、update 等方法，Service 调用这些方法操作菜品表。

**常见追问**

- Mapper 接口需要实现类吗？（不需要，MyBatis 用动态代理生成）
- 方法怎么和 SQL 对应？（通过 namespace + 方法名/id 匹配 XML 里的 SQL）

**易错点**

Mapper 接口是「操作声明」，真正执行靠 MyBatis 动态代理 + XML SQL，两者要对应上。

## 204. Mapper 接口没有实现类为什么可以执行？

**面试回答**

因为 MyBatis 用 JDK 动态代理为 Mapper 接口生成代理实现类：调用接口方法时，代理拦截后根据方法找到对应的 SQL 并执行，所以不需要你手写实现类。

**理解**

MyBatis 启动时读取 Mapper 接口和对应 SQL，运行时用动态代理为每个 Mapper 接口生成一个代理对象。调用 `mapper.selectById(1)` 时，代理根据接口全限定名 + 方法名定位到 SQL（namespace + id），通过 SqlSession 执行，把结果映射成返回类型。整个过程对调用者透明。

**场景**

项目里 @Autowired 注入的 DishMapper 其实是 MyBatis 生成的代理对象，调用方法时自动执行对应 SQL。

**常见追问**

- 代理怎么定位 SQL？（namespace + 方法名 = SQL 的 id）
- 返回值怎么确定？（根据接口方法返回类型映射）

**易错点**

Mapper 接口能执行，靠的是「动态代理 + SQL 绑定」，不是真的没有实现，只是实现是运行时生成的。

## 205. MyBatis Mapper 动态代理是什么？

**面试回答**

MyBatis 用 JDK 动态代理为 Mapper 接口生成代理对象，代理在方法调用时拦截，把「接口方法调用」翻译成「执行对应 SQL 并映射结果」。

**理解**

核心是 MapperProxy（一个 InvocationHandler）。调用接口任意方法时，代理先判断方法类型（增删改查还是默认方法），然后根据接口全限定名 + 方法名找到 SQL 语句，交给 SqlSession 执行，最后把结果按接口返回类型映射。这样就能「只写接口，不写实现」。

**场景**

项目里 MyBatis 为 DishMapper、OrderMapper 等每个接口都生成代理对象，Service 拿到的是这些代理。

**常见追问**

- 动态代理的处理器是谁？（MapperProxy，实现 InvocationHandler）
- 为什么用 JDK 动态代理？（因为 Mapper 是接口）

**易错点**

Mapper 动态代理是「运行时生成接口实现」，它把方法调用转成 SQL 执行，这是 MyBatis 用起来方便的关键。

## 206. MyBatis 注解方式和 XML 方式有什么区别？

**面试回答**

注解方式把 SQL 直接写在接口方法上（如 @Select），简单直观；XML 方式把 SQL 写在独立的 XML 文件里，适合复杂 SQL、动态 SQL，SQL 与代码分离。

**理解**

注解适合简单、固定的 SQL，写起来方便但复杂动态 SQL 会变得难读；XML 适合复杂查询、动态拼接（if/where/foreach），可维护性更好，SQL 集中管理。项目里通常「简单用注解、复杂用 XML」，或统一用 XML。

**场景**

项目里查询接口较多、SQL 复杂（动态条件、批量插入、联表），主要用 XML 方式管理 SQL，便于维护。

**常见追问**

- 两者能混用吗？（能，但不建议同一个方法两种都写，会冲突）
- 动态 SQL 用哪种更好？（XML，注解写动态 SQL 很别扭）

**易错点**

注解和 XML 是「两种 SQL 定义方式」，本质都绑定到方法；复杂 SQL 优先 XML，别把注解吹成万能。

## 207. `#{}` 和 `${}` 有什么区别？

**面试回答**

`#{}` 是预编译占位符，相当于 JDBC 的 `?`，MyBatis 会把它作为参数安全地设置，能防 SQL 注入；`${}` 是字符串拼接，直接把值拼进 SQL，存在 SQL 注入风险。

**理解**

`#{}` 生成的是 PreparedStatement 的占位符，值由驱动安全绑定，不会被当成 SQL 语法执行；`${}` 是字符串替换，值原样拼进 SQL，如果值是恶意内容就可能改变 SQL 语义。所以「能用 #{} 就用 #{}」，只有特殊场景（如表名、列名）才用 ${}。

**场景**

项目里所有查询条件、插入值都用 #{}；只有极少数需要动态指定列名/表名时才考虑 ${}。

**常见追问**

- `#{}` 底层是什么？（PreparedStatement 的 ? 占位符）
- `${}` 为什么危险？（字符串直接拼接，可注入）

**易错点**

`#{}` 安全、`${}` 有注入风险，这是核心结论；别因为 `${}` 灵活就乱用。

## 208. 为什么 `#{}` 可以降低 SQL 注入风险？

**面试回答**

因为 `#{}` 用预编译（PreparedStatement）把 SQL 结构和参数分开：参数作为「值」由驱动安全绑定，不会被当成 SQL 的一部分执行，所以恶意内容无法改变 SQL 逻辑。

**理解**

SQL 注入的本质是「把用户输入当成 SQL 代码执行」。`#{}` 生成 `select * from user where name = ?`，参数 `'1' or '1'='1'` 只是作为 name 的值传入，数据库把它当普通字符串比较，不会执行其中的 or 逻辑。结构（SQL 语句）和数据（参数）分离，注入就无从下手。

**场景**

项目里用户登录查询 `where username = #{username}`，即使传入恶意字符串，也只是当作 username 的值，不会造成注入。

**常见追问**

- 预编译为什么安全？（SQL 先编译，参数后绑定，结构固定）
- `${}` 为什么不能这样？（它是拼接，参数会混进 SQL 结构）

**易错点**

`#{}` 安全的关键是「预编译 + 参数化」，把数据和 SQL 结构分离，而不是简单「转义」。

## 209. `${}` 为什么存在 SQL 注入风险？

**面试回答**

因为 `${}` 是字符串直接拼接，用户输入会原样嵌入 SQL 语句，成为 SQL 结构的一部分，恶意输入就能改变 SQL 语义，实现注入。

**理解**

`${}` 不经过预编译参数化，而是把值直接替换进 SQL 字符串。比如 `where username = '${username}'`，用户输入 `' or '1'='1`，拼出来就是 `where username = '' or '1'='1'`，恒真，导致查询所有数据。因为输入进入了「SQL 代码」而非「数据」的位置，所以危险。

**场景**

项目里如果对用户输入用 `${}`，攻击者可以构造输入绕过条件、篡改 SQL、甚至删表，这是必须避免的。

**常见追问**

- 注入能造成什么后果？（绕过登录、泄露数据、删表等）
- 怎么避免？（用 #{}，除非必要不用 ${}）

**易错点**

`${}` 的危险在于「输入变成了 SQL 代码」，理解这一点就知道为什么必须谨慎。

## 210. `${}` 一般在什么场景使用？

**面试回答**

只在「SQL 结构本身需要动态变化」的场景使用，如表名、列名、排序字段（ORDER BY 的字段）、分组字段等这些不能用 `?` 占位符的位置。

**理解**

`#{}` 是参数占位符，只能用在「值」的位置；表名、列名、ORDER BY 字段这些属于 SQL 结构，占位符不支持，只能拼接，所以用 `${}`。但因为是拼接，使用时要对输入做白名单校验，避免注入。

**场景**

项目里若有按用户选择排序的接口，`ORDER BY ${sortField}` 需要 ${}，但 sortField 必须从白名单里取值，不能直接接用户输入。

**常见追问**

- 为什么 ORDER BY 不能用 #{}？（占位符会把字段名当字符串值，而不是列名，语义不对）
- 用 ${} 时怎么防注入？（白名单校验、限制可选值）

**易错点**

`${}` 只用于「表名/列名/排序字段」这类结构位置，且必须白名单校验；不是「${} 完全不能用」，而是「不能用于用户输入的值」。

## 211. 什么是 MyBatis 动态 SQL？

**面试回答**

动态 SQL 是 MyBatis 提供的根据条件在运行时动态拼接 SQL 的能力，通过 `<if>`、`<where>`、`<set>`、`<foreach>` 等标签，让一条 SQL 能根据传入参数生成不同的查询语句。

**理解**

实际开发中查询条件往往是可选的：有名字就按名字查、有状态就按状态查。写死一条 SQL 无法适应。动态 SQL 让 SQL 模板根据参数有选择地拼出条件片段，既灵活又避免大量 if-else 拼 SQL 的重复代码。

**场景**

项目里菜品分页查询、动态搜索接口，用 `<if>` 判断条件，`<where>` 处理 where 关键字，`<foreach>` 处理 in 和批量插入。

**常见追问**

- 常见动态 SQL 标签？（if、where、set、foreach、choose、trim）
- 动态 SQL 解决什么问题？（条件可选的查询）

**易错点**

动态 SQL 是「模板 + 条件拼接」，本质还是生成一条最终 SQL，别理解成「执行多条 SQL」。

## 212. `<if>` 有什么作用？

**面试回答**

`<if>` 用于条件判断，当条件成立时（如参数不为空）才把对应的 SQL 片段拼进最终语句，实现「有值才查、无值不查」。

**理解**

`<if test="name != null and name != ''">AND name = #{name}</if>`：test 里的表达式为 true 时，标签内的 SQL 片段才被拼接。它是动态 SQL 最基础的标签，常配合 where、set 使用。

**场景**

项目里菜品查询接口，用户填了菜名才按菜名过滤，填了分类才按分类过滤，就是用多个 `<if>` 实现的可选条件。

**常见追问**

- test 里能写什么？（OGNL 表达式，判断 null、空、比较等）
- `<if>` 单独用有什么问题？（拼多个条件时可能出现多余的 AND/OR，需要 where 配合）

**易错点**

`<if>` 只是「条件拼接片段」，多条件组合时要注意 AND/OR 的连接，常需 `<where>` 或 `<trim>` 处理。

## 213. `<where>` 有什么作用？

**面试回答**

`<where>` 用来包裹条件片段，自动处理 where 关键字：至少有一个条件成立时生成 WHERE，并自动去掉开头多余的 AND/OR，避免拼接出语法错误的 SQL。

**理解**

多个 `<if>` 条件拼接时，第一个条件前可能有 AND，或者所有条件都不成立时不该有 WHERE。`<where>` 智能处理：内部有条件就输出 WHERE 且去掉开头 AND/OR，无条件就什么都不输出。让动态查询的 SQL 始终合法。

**场景**

项目里动态查询 `<where>` 里放多个 `<if>`，无论用户填不填条件，生成的 SQL 都正确。

**常见追问**

- `<where>` 去掉什么？（开头多余的 AND 或 OR）
- 所有条件都不成立会怎样？（不生成 where，查询所有）

**易错点**

`<where>` 的核心价值是「智能去 AND/OR + 空时不输出 where」，避免 `where and xxx` 这种错误。

## 214. `<set>` 有什么作用？

**面试回答**

`<set>` 用于 update 语句，包裹要更新的字段片段，自动加上 SET 关键字并去掉末尾多余的逗号，实现动态更新部分字段。

**理解**

更新操作经常只更新有变化的字段。`<set>` 里放多个 `<if>`，每个成立就拼 `字段 = #{值}`，`<set>` 自动加 SET 并去掉最后一个多余逗号，避免 `set a=?, b=?,` 这种语法错误。若全不成立会提示错误（需至少一个字段）。

**场景**

项目里修改菜品、更新订单状态时，用 `<set>` 动态更新传入的非空字段。

**常见追问**

- `<set>` 去掉什么？（末尾多余的逗号）
- `<set>` 和 `<trim>` 关系？（`<set>` 本质是 `<trim>` 的一种特化）

**易错点**

`<set>` 解决的是 update 里「字段逗号拼接」的问题，和 `<where>` 处理 where 的 AND/OR 是两类问题。

## 215. `<foreach>` 有什么作用？

**面试回答**

`<foreach>` 用于遍历集合（List、数组、Map 等），把集合元素逐个拼进 SQL，常用于 `IN (...)` 查询和批量插入。

**理解**

`<foreach>` 常用属性：collection（集合名）、item（每次元素）、separator（分隔符）、open/close（首尾字符串）。比如 `IN` 查询：`<foreach collection="ids" item="id" open="(" close=")" separator=",">#{id}</foreach>` 生成 `(1,2,3)`。

**场景**

项目里按多个 id 批量查询、批量删除时用 `<foreach>` 拼 `IN` 列表。

**常见追问**

- collection 传什么？（List、数组、Map，或 @Param 指定的名字）
- separator 作用？（元素之间的分隔符，如逗号）

**易错点**

`<foreach>` 是「遍历拼接」，配合 open/close/separator 控制最终形态；注意集合为空时要提前判断，否则可能拼出错误 SQL。

## 216. 如何通过 `<foreach>` 实现批量插入？

**面试回答**

用 `<foreach>` 遍历对象集合，把每个对象拼成一条 `(值1,值2,...)`，用逗号连接，一次性插入多条数据，如 `insert into t(...) values (...),(...),(...)`。

**理解**

写法：`insert into dish(name, price) values <foreach collection="list" item="d" separator=",">(#{d.name}, #{d.price})</foreach>`。这样一条 SQL 插入多行，比循环单条插入效率高得多。要注意 MySQL 的 `max_allowed_packet` 限制，批量太大要分批。

**场景**

项目里批量新增菜品/订单明细时，用 `<foreach>` 拼成一条多值 INSERT，减少数据库交互次数、提升性能。

**常见追问**

- 批量插入为什么快？（一条 SQL 插入多行，减少网络和解析开销）
- 一次插太多会怎样？（SQL 过长，受 max_allowed_packet 限制，要分批）

**易错点**

`<foreach>` 批量插入是「一条 SQL 多值」，不是「循环执行多条 INSERT」；数据量太大要分批。

## 217. 什么是主键回填？

**面试回答**

主键回填指插入数据时，数据库自动生成的自增主键，在插入完成后回写到 Java 对象对应的主键字段上，让你能拿到刚插入记录的主键值。

**理解**

数据库表主键常用自增，插入前 Java 对象的 id 是空的。主键回填让 MyBatis 在 insert 后，把数据库生成的自增 id 取回来，set 回实体对象。这样插入后立刻能拿到 id，用于后续操作（如关联子表）。

**场景**

项目里新增菜品后，需要拿到新菜品的 id 做后续操作；插入订单主表后，要用回填的订单 id 插入明细表。

**常见追问**

- 回填到哪？（实体对象的主键字段）
- 为什么要回填？（插入后需要用到这条记录的主键）

**易错点**

主键回填是把「数据库生成的 id 写回 Java 对象」，不是「自己生成 id 再插库」，两者方向别搞反。

## 218. MyBatis 如何获取 MySQL 自增主键？

**面试回答**

在 insert 标签上配置 `useGeneratedKeys="true"` 和 `keyProperty="id"`，MyBatis 就会把 MySQL 生成的自增主键回填到实体对象的 id 属性上。

**理解**

`useGeneratedKeys="true"` 告诉 MyBatis 使用数据库的自增能力，`keyProperty` 指定回填到哪个属性。底层是通过 JDBC 的 `getGeneratedKeys()` 拿到自增主键。注解方式则用 `@Options(useGeneratedKeys = true, keyProperty = "id")`。

**场景**

项目里订单主表插入用 `useGeneratedKeys="true" keyProperty="id"`，插入后 order.id 就是数据库生成的主键，用于插入子表。

**常见追问**

- useGeneratedKeys 和 keyProperty 分别作用？（开启自增回填、指定回填字段）
- 注解怎么写？（@Options(useGeneratedKeys = true, keyProperty = "id")）

**易错点**

两个属性要配合：`useGeneratedKeys` 开启、`keyProperty` 指定目标字段，缺一个回填就不对。

## 219. 为什么项目中的子表插入需要主键回填？

**面试回答**

因为子表记录要关联主表：子表里存主表的主键作为外键，所以必须先拿到主表插入后生成的自增主键，才能往子表里填这个外键，保证主子表关联正确。

**理解**

比如订单明细表有个 order_id 字段，指向订单主表的 id。插入流程是：先插订单主表 → 拿到回填的 orderId → 再把 orderId 填进每条明细的 order_id → 插入明细表。没有主键回填，就拿不到 orderId，明细无法关联到订单。

**场景**

项目里下单：先插入订单主表并回填主键，再用回填的订单 id 设置每条明细的 orderId，最后批量插入明细表，整个过程在同一个事务里。

**常见追问**

- 不回填会怎样？（拿不到主表 id，子表无法正确关联）
- 主子表插入应该在什么里完成？（同一个事务里）

**易错点**

子表插入依赖主表主键，所以「主键回填 + 同事务」是项目里保证主子表一致的两个关键点。

## 220. 什么是 MyBatis 一级缓存？

**面试回答**

一级缓存是 SqlSession 级别的缓存，同一个 SqlSession 内执行相同的 SQL 时，第二次直接返回缓存结果，不再查数据库。

**理解**

一级缓存默认开启，作用范围是一个 SqlSession（通常对应一次会话/事务）。同一 SqlSession 里第一次查询的结果会被缓存，之后相同 SQL + 参数再查就直接返回缓存。但 SqlSession 关闭缓存就没了，且数据更新、SqlSession 不同时缓存会失效或不可见。

**场景**

项目里同一个 SqlSession（同一次事务）内重复查同一数据，一级缓存能减少一次数据库查询。

**常见追问**

- 一级缓存作用范围？（SqlSession 级别）
- 默认开启吗？（是，默认开启）

**易错点**

一级缓存是「SqlSession 级别」的，不是全局的；换个 SqlSession 就没了，别和二级缓存混淆。

## 221. 什么是 MyBatis 二级缓存？

**面试回答**

二级缓存是 Mapper 级别（namespace 级别）的缓存，多个 SqlSession 共享同一 Mapper 的缓存，相同 SQL 跨 SqlSession 也能命中缓存。

**理解**

二级缓存默认不开启，需要配置。它基于 namespace，缓存的不是对象本身而是序列化后的数据（因此实体类常要实现 Serializable）。多个 SqlSession 操作同一 Mapper 时能共享缓存，但要注意数据一致性：更新操作会清空该 namespace 的缓存。生产环境一般慎用（缓存一致性难保证，通常用 Redis 替代）。

**场景**

项目里一般不用 MyBatis 二级缓存，而是用 Redis 做缓存，因为二级缓存一致性难控制、易出脏数据。

**常见追问**

- 二级缓存作用范围？（namespace / Mapper 级别，跨 SqlSession 共享）
- 为什么不常用？（一致性难保证，分布式环境易脏读，常被 Redis 替代）

**易错点**

二级缓存「跨 SqlSession、按 namespace 共享」，但一致性难控，实际项目多用 Redis 而非 MyBatis 二级缓存。

## 222. 一级缓存和二级缓存有什么区别？

**面试回答**

作用范围不同：一级缓存是 SqlSession 级别，同一 SqlSession 内共享，默认开启；二级缓存是 namespace/Mapper 级别，跨 SqlSession 共享，默认关闭、需配置且实体要可序列化。

**理解**

一级缓存生命周期短（跟随 SqlSession），天然存在；二级缓存生命周期长、跨会话，但一致性风险更高。更新时：一级缓存跟随 SqlSession 提交/关闭失效，二级缓存会在更新后清空对应 namespace 缓存。实际开发一级缓存默认就有，二级缓存很少用（多被 Redis 替代）。

**场景**

项目里一级缓存默认生效；二级缓存基本不用，缓存需求交给 Redis。

**常见追问**

- 各自作用范围？（一级 SqlSession，二级 namespace）
- 二级缓存为什么慎用？（分布式下一致性难保证）

**易错点**

核心区别是「作用范围和是否默认开启」；二级缓存不是全局缓存，是 namespace 级别。

## 223. PageHelper 是什么？

**面试回答**

PageHelper 是一个 MyBatis 分页插件，通过拦截 SQL 自动加上 LIMIT 分页，让你无需手写分页 SQL，只需调用 PageHelper.startPage 即可。

**理解**

它基于 MyBatis 的拦截器机制（Interceptor），在执行查询前对 SQL 进行拦截改写，自动拼上 `LIMIT offset, size`，并把查询结果封装成分页信息（总条数、页码等）。这样业务代码不用管分页细节。

**场景**

项目里菜品、订单列表的分页查询用 PageHelper：`PageHelper.startPage(page, pageSize)` 后，紧接着的查询自动分页，返回 Page 对象带总数等信息。

**常见追问**

- PageHelper 靠什么实现？（MyBatis 拦截器，改写 SQL 加 LIMIT）
- startPage 的用法？（在紧邻的查询方法前调用）

**易错点**

PageHelper 是「拦截改写 SQL」，只对紧跟其后的第一条查询生效；放错位置（中间隔了别的查询）分页会失效。

## 224. PageHelper 大致如何实现分页？

**面试回答**

通过 MyBatis 的拦截器，在执行查询 SQL 前拦截，自动生成并执行 count 查询拿总条数，再给原 SQL 追加 LIMIT 做数据查询，最后封装成 Page 对象返回。

**理解**

PageHelper 拦截 Executor 的 query 方法：①先根据原 SQL 生成一条 count SQL 查总记录数 ②再给原 SQL 加 `LIMIT offset, size` 查当前页数据 ③把两者封装成带页码、总数、列表的 Page 对象。整个过程对业务透明。

**场景**

项目里分页查询调用 PageHelper 后，它自动完成 count + limit 两步，返回的 Page 里有 total 和当前页数据。

**常见追问**

- 它拦截的是哪个环节？（Executor 的 query 方法）
- 为什么能拿到总条数？（额外执行一条 count SQL）

**易错点**

PageHelper 分页 = 「count 总数 + limit 数据」两步，靠拦截器自动完成；核心是理解它「改写 SQL」而非「内存分页」。
